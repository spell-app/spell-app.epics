The site search is a docs-only element, <ui-docs-search>, with its own accessible combobox and results list, rather than ui's <ui-search>.

  • Its own ARIA parts:
    • a combobox, with aria-activedescendant
    • a listbox of groups and options
  • <ui-search> is a Fomantic port, tied to forms:
    • its own matcher and look
    • title / description / price rows
    • it puts the picked result's title in the input
  • Every part of this ask fights it:
    • ranking ACROSS categories
    • groups ordered by their best hit
    • matches marked in the results
    • a pill-shaped field and a floating card in the brand's look
    • results that are real links, which the router takes
    • a staged Escape (J40)

The options:

  1. Its own listbox (done).
  2. <ui-search> with a source property, heavy part restyling, and a matcher hook: a library change.
  • a new docs element, ui-docs-search, in docs-components/
  • <ui-search> is unchanged

Title, as first written: P8 search: own ARIA combobox listbox, not ui-search

Chose a doc-only <ui-docs-search> with its own combobox + listbox (role=combobox, aria-activedescendant, role=listbox / group / option) over building on <ui-search>. Why: ui-search is a form-associated Fomantic port (its own matcher and look, title / description / price rows, it puts the title in the input), and every part of this ask fights it: ranking ACROSS categories, groups ordered by their best hit, marked matches, a pill + floating card in the brand look, results that are real links the router takes, staged Escape. Options: (a) own listbox (done); (b) ui-search with a source property, heavy ::part restyling and a matcher hook (a library change).
