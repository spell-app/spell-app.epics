"The answer" first, then the sketch, then the two questions.
  • Yes, for about a third of Spell UI, nearly whole; for another sixth, as a thin layer.
    • The simple, mostly-drawing components (a divider, a label, a segment, a card) are markup, CSS and a few attributes. drawable-thing gives spell all three.
    • The form controls (a rating, a checkbox) could be written in spell too, on top of base classes that stay TypeScript.
  • The honest catch: the hard part of a Spell UI component isn't the drawing.
    • It's the plumbing: joining a form, focus, keys, screen-reader wiring, the server render, the fallback when it breaks.
    • That plumbing lives in shared TypeScript base classes and helpers today. Spell would inherit it, not replace it.
    • So a spell-written <ui-rating> is about 80 lines of spell plus its CSS, over the same TypeScript underneath.
  • And a second catch: Spell UI must never need spell to run.
    • So spell-written components would be compiled AHEAD, into ordinary TypeScript committed in Spell UI (the second question).
  • Rough size: about 25-35 hours beyond drawable-thing, about the size of drawable-thing again.
  • Every <ui-*> element is the same set of pieces. Here they are for <ui-rating>.
  • Each one is marked:
    • covered drawable-thing already gives spell this
    • new spell needs new words in spell (numbered as in the sketch, 1.3)
    • stays TypeScript spell inherits it or calls it

        name={this.groupName}
        value={String(point)}

        onChange={this.onChange}

  • Compile to the component itself, not to a thing wrapped in an element. About 3-4h.
    • drawable-thing makes a spell THING, then builds an element around it at run time.
    • A Spell UI component must be the element's component class directly, with no spell runtime inside. Otherwise every Spell UI page carries spell's runtime.
    • drawable-thing's last building phase (the TypeScript writer writing a real component class) is most of this.
  • Compile ahead, committed in Spell UI. About 3-4h.
    • A generator turns each .spell file into the .tsx beside it, committed, as Spell UI already does for spell's highlighter.
    • So Spell UI never imports spell, the server render works, and TypeScript checks the result (Q2).
  • The form control base type and its hooks (1). About 3-4h.
  • The element's own state, and starting values (2, 3). About 1-2h.
  • The shared attribute kinds (3): size, colour, icon, and their class words. About 2-3h.
  • A value the page controls (4). About 2-3h: its timing is subtle in TypeScript too.
  • Events sent from the element (5). About 1-2h.
  • Key handlers (6). About 2-3h.
  • Behaviour helpers (7). About 3-4h: the radio-group keys and focus, moved out of the rating into Spell UI, then named from spell.
  • Conditional class words and counted rows (8). About 1-2h.
  • Texts and docs data (9). About 2-3h: the docs site reads the vocabulary, so it must come out complete.
  • Speed and size. About 1-2h to measure; a risk, not a feature.
    • One Solid on the page: drawable-thing already makes sure of it.
    • Re-run the 1,000-button check against a spell-written button.
    • Compare bundle sizes: the generated .tsx should be no bigger than the hand-written one.
  • What it doesn't need:
    • new tests: today's TypeScript tests run, unchanged, against the spell-written element
    • a spell fallback: the native fallback stays hand-written TypeScript, beside it
  • The rule of thumb: spell is good where a component is mostly what it looks like. It's poor where a component is mostly how the browser behaves.

Where does a component written in spell turn into code, given Spell UI must work without spell? (Only matters for A or B above.)

Each .spell file has a generated .tsx beside it, committed, rebuilt by a script. Pages load ordinary TypeScript, as today.

  • You'd see: ui-rating/rating.spell as the source, UIRating.tsx generated beside it (collapsed in pull-request diffs).
  • Why recommended: Spell UI stays standalone; the server render, types, docs data and tests all work as they do now.
  • Cost: a generator to run after a change, like spell's highlighter bundle today.

Spell UI loads spell's compiler and builds the spell-written components on the page, as drawable-thing does for a program.

  • Cost: Spell UI would import spell, breaking the rule that it stands alone; bigger pages; no server render.

Spell UI stays TypeScript. New components are written in spell as a spell library of their own (<ui-...> tags from a library named "ui"), never ported.

  • You'd get: no churn in Spell UI; spell's own components grow beside it.
  • Cost: two sets of components that look alike but are built differently.
