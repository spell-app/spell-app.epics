A drawable element passes its attributes and properties ON to its thing, and nothing comes back: the element shows what the page set, while the drawing shows the thing.

  • Setting rank="ace", or card.rank = "jack" from a script, writes the thing's rank, and the card redraws.
  • Reading card.rank gives what was last SET on the element, not the thing's own rank.
    • If the program changes the thing, the element's attribute and property don't follow.
    • Turning a card over changes its thing's direction; the element's direction still says "up".
  • What you SEE is always right: the drawing comes from the thing.
  • Where: SpellElement.onMount(), one effect per property, writing the element's value to the thing whenever either changes. 
// <drawable-solitaire-card id="ace" rank="ace" suit="spades" direction="up">
const ace = document.getElementById("ace")
ace.turnOver()                   // the thing's direction is now "down":  the card draws face down
ace.direction                    // still "up":  what the page set
ace.getAttribute("direction")    // still "up"
  • Chosen and built.
  • Simple: one effect per property, and no loops.
  • The attributes on the page stay what the page wrote: no churn in the DOM as the game plays.
  • The cost: reading an element's property can be out of date.
  • A second effect per property, writing the thing's value into the element's attribute.
  • Reading card.direction would always be the thing's.
  • The cost: each write bounces (element to thing, thing back to element), so it needs guards against loops.
  • And every change in the game rewrites attributes on the page, which page CSS and observers would see.
  • A drawable element's attributes and properties are inputs only.
  • To read the live value, a script asks the thing, not the element.
  • Mirroring back (option B) can be added later without changing what the page writes.
