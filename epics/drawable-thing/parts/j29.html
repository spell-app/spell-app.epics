When compiled code holds a type's name as TEXT, the javascript writer finds it by the key it sits under, and renames it there. The question about the naming map (Q19) said instead that such a name "gets marked", a tree node of its own, so every writer renames it.

  • Two keys hold a type's name as text today: type and instanceType.
  • The writer renames that text only when it names one of the project's own classes, so other text under those keys is left alone.
  • Type checks needed nothing new: isOfType already compiles to x instanceof <name>, and that name goes through the map like any class name.
  • The function doing it is JSWriter.typeNamed(). 
// spell writes                          // compiled with types in snake_case
declareProp('pile', { type: "Pile" })    declareProp('pile', { type: "pile" })
new List({ instanceType: "Pile" })       new List({ instanceType: "pile" })
  • small: one function in the javascript writer
  • covers every place spell writes a type's name as text today
  • cost: a new place that writes one under another key would be missed, until it's added to the list
  • the spell rules mark each type name in text with a new node, and each writer renames it
  • sturdier if new places appear
  • cost: more rules touched, for the same output today
  • compiled output is the same either way today
  • Q19's "gets marked" is built as "found by its key"
  • a new key holding a type's name has to be added to the writer's list
