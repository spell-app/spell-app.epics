A drawable thing has nowhere to write its own look.

A <css> block in a type's spell is that element's own style sheet.

  • It's adopted in the element's shadow root, after the shared runtime's sheets.
  • The CSS inside is edited AS CSS, in the spell editor and in VS Code.
  • The block sits in the type's outline, indented under its line with the properties (Q13, answer A).

Starts now, built from main (Owen, 2026-10-10; Q15).

  • Now: the rule for the <css> block, in the type's outline (Q13, answer A).
  • Now: compiling the block to the type's style sheet text.
  • Now: colouring the CSS in the spell editor (Monaco) and in VS Code (spell's grammar, embedded CSS).
  • Now: the language server's CSS service (completions, hovers, errors).
  • Later: adopting the sheet in the element's shadow root waits for an element, so P4 is finished once P3 · Element Bridge (P3) exists.
  • A conflict with the output-targets branch in spell's type rule is expected when it lands (C3).
  • A card with a <css> block draws with those styles, on top of the shared theme.
  • In the spell editor and in VS Code, the block is coloured as CSS, offers CSS completions and underlines CSS mistakes.
  • Is it possible? Yes, in three layers:
    • parsing (spell): a rule takes the block raw, like a string, so spell never reads the CSS; it compiles to the type's style sheet
    • colouring, in the spell editor: spell's own SpellTokensProvider hands the lines inside the block to Monaco's CSS colouring
    • colouring, in VS Code: spell's grammar marks the block as embedded CSS, VS Code's standard way for one language inside another; that also gives CSS comment toggling and brackets
    • completion, hover and errors: the language server runs VS Code's own CSS service on the block, everything outside it blanked to spaces so positions line up (how VS Code's HTML support does <style>)
    • the language server is browser-safe, so that last layer is written ONCE for both editors: both already forward to it
