@spell/elements is resolved in three places; each chose the plainest thing that works.

  • The type check maps it to app's source, a small new file, spellElements.ts, which re-exports the element class and Spell UI's E.
    • Chosen over a hand-written declaration of the element class's shape, which would drift.
    • The check also maps spell-ui, and uses the 2023 javascript library, as J41's probes found Spell UI needs.
    • It stays fast: the fixtures' type check runs in about the same time.
  • In a page, the runtime (spell-runtime.js) exports the element class, and an E holding only its two decorators.
    • The two: proto and protoMerged.
    • Exporting Spell UI's whole E put a second copy of two Spell UI files into the runtime bundle.
    • App's build test refuses that (build.test.ts): two copies on a page fail silently.
    • The two files: Cell.ts and Shorthand.ts.
  • Headless runs, such as spell run and the core contract, map it to a stand-in, spellElements.mjs.
    • It's an empty element class with vocabularyFor(), and the two decorators doing nothing.
    • cli's hooks.mjs points the name there.
  • A hand-written element class that uses more of E at run time (not its types) would work in the type check but not yet in a page; no page runs TypeScript output today.
