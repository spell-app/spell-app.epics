@spell/elements is resolved in three places; each chose the plainest thing that works.

  • The type check maps it to app's source, a small new file, packages/app/src/runner/spellElements.ts, which re-exports SpellElement and Spell UI's E. Chose that over a hand-written declaration of SpellElement's shape, which would drift. The check also maps $/ui and uses the 2023 javascript library, as J41's probes found Spell UI needs. It stays fast: the fixtures' type check runs in about the same time.
  • In a page, the runtime (spell-runtime.js) exports SpellElement, and an E holding only proto and protoMerged. Exporting Spell UI's whole E put copies of two Spell UI files (Cell.ts, Shorthand.ts) into the runtime bundle, which app's build.test.ts refuses (two copies on a page fail silently).
  • Headless (spell run, the core contract), cli's hooks.mjs maps it to a stand-in, packages/cli/src/runner/spellElements.mjs: an empty SpellElement with vocabularyFor(), and the two decorators doing nothing.
  • A hand-written element class that uses more of E at run time (not its types) would work in the type check but not yet in a page; no page runs TypeScript output today.
