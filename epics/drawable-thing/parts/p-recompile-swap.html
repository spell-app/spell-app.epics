An edit recompiles the program, but the tag keeps the first compile's class.

Spell UI's element base gains a small "redefine this tag's component" hook that knows nothing about spell, reusing what its hot-reload code already does (Q5). The bridge swaps the class behind the tag; the elements on the page redraw, keeping their things.

  • In the editor, change a card's to draw, and the cards on the page change, without a reload.
  • The cards keep their state (rank, suit, face up or down) across the swap.
  • Spell UI stays free of spell: the hook is generic.
  • In the editor, edit a drawable type's <css> or its to draw, and the page shows the change, with no reload and no "tag already defined" error.
    • The program runs again from the top, so Drawable Solitaire deals a new game (V3).
    • Its cards draw with the new to draw, in the new CSS.
    • Two <spell-app>s of the same project on one page: every card of both takes the newest CSS, since there's one sheet per tag.
  • How it works: each drawable type's tag stays defined (a page can't define a tag twice), and app swaps what's behind it (J20).
    • SpellElement.defineFor() records the new run's runtime and class, which the element draws with from then on.
    • What's drawn comes from the element's thing, so a re-run's new things draw with their new class's draw().
    • SpellElement.restyle() replaces the type's CSS in every element of the tag already on the page, without drawing them again, through Spell UI's own UI.styles.register(), as its hot reload does.
    • Each tag's sheet is named for the tag, and never empty (an empty text would unregister it).
  • No change to Spell UI was needed: the "redefine this tag" hook the plan named isn't there (J20).
