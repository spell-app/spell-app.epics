A drawable list's items show inside its element as its CHILDREN, and they're put there by whatever draws the list, not by the list's own to draw.

  • Drawing a drawable list makes its element with the items' elements already inside it.
    • That's spellCore.drawThing(): for a drawable list, it hands the element its items as children.
    • The items are drawn by spellCore.drawItems(), kept by identity: a card added or removed changes only its own element.
  • The list's own to draw draws only its OUTSIDE, its frame, in the element's shadow root.
    • It puts a <slot/> where the items should show.
    • Left out, the default draw is just that slot (DrawableList.draw()).
  • So the page has the same shape a person would write by hand: a tableau element holding card elements.
// Solitaire.spell
to draw a tableau:
	return <div className="pile tableau"><slot/></div>

// drawing a drawable list, in spellCore.drawThing():  its items go in as children
h(tag, { "prop:thing": thing }, () => spellCore.drawItems(thing))

// the page
<drawable-solitaire-tableau>
  #shadow-root:  <div class="pile tableau"><slot></slot></div>
  <drawable-solitaire-card>...</drawable-solitaire-card>
  <drawable-solitaire-card>...</drawable-solitaire-card>
</drawable-solitaire-tableau>
  • Chosen and built.
  • The list's to draw says only what the list itself looks like: the phase's goal.
  • The page's shape matches hand-written HTML: cards inside the pile.
  • The cost: a frame must leave room for its items with a <slot/> (C12).
  • The list would look after its items with no help from the outside.
  • But the element's children belong to the drawing it sits in: that drawing would replace them, and the element would fight it for them.
  • A drawable list's element holds its items' elements as its children.
  • Its to draw draws its frame, with a <slot/> where the items show.
  • A drawable list with no to draw shows just its items.

<children> as alias for <slot>, and <children id="header"/>

Spell can rename it as it compiles: <children/> becomes the web's <slot/>, and a named <children> becomes a named slot. It's recorded as a todo, T6 · <children/> as spell's word for <slot/>.

  • Where: spell's JSX rule, SpellJSX.getAST(), swaps the tag name and the attribute before either writer sees them. So the page still gets a real slot.
  • <slot/> keeps working: nothing written today breaks.
  • A todo, not a phase: none of the phases still to do is about drawing. P10 is the TypeScript writer, P12 is event handlers, and the new P13 is the element and its thing agreeing. 
<children/>                  =>  h("slot")
<children id="header"/>      =>  h("slot", { name: "header" })     ... with A
<children name="header"/>    =>  h("slot", { name: "header" })     ... with B

Two things to settle:

  1. How a child says which named place it goes in.
    • A page writing tags by hand uses the web's own way: <h3 slot="header"> on the child.
    • A list spell draws puts every item in the unnamed place. What fills header there is still open: it's in the todo, for when it's built.
  2. The named form's attribute, below.
  • Reads naturally: "the children with the id header".
  • But on every other tag in spell, id is the page's id, which must be unique on the page. A named slot repeats in every element of the type: forty cards, forty header slots.
  • A reader who knows HTML may expect it to show up as an id.
  • The same attribute a slot itself takes, so what spell writes and what the page holds match.
  • No clash with what id means on any other tag.
