Six pieces make the element, then three more make it live. Where each lives follows the packages' one-way rule: spell and core may not reach up into Solid or Spell UI, and Spell UI may not reach into spell.

  1. Grammar (spell): type names can be more than one word (P1).
    • "a bank account aka account is a thing" declares one type, with a short name (O5)
    • "drawable thing" and "drawable list of cards" are built-in types, so "a card is a drawable thing" parses with no leftover word (P2)
  2. Two real base classes (core), each built on a class spell already has:
    • Drawable, a kind of Thing
    • DrawableList, a kind of List
    • they join the built-in classes, so compiled code can import them
  3. A hook (core): each drawable class names its tag as it's declared, through spellCore.defineElement() (P3, J16).
    • core only names the tag; the page that runs the program fills in the hook, and defines the element
    • why: core may not import Solid or Spell UI
    • the page defines the tag once the class is whole: at its first draw, or else a moment later
  4. The bridge (app): the element class, SpellElement, a Spell UI component that draws its thing.
    • each tag is defined once, as a sub-class of it carrying the tag and the type's vocabulary
    • its drawing is the thing's own draw(), inside the thing's error net
    • one tag per type per page, drawn by the runtime that defined it last (J13)
    • it uses the page's own Solid and Spell UI, never a second copy
  5. Styles: exactly as a ui-* element does it (P4).
    • the page's theme sheets, adopted the same way Spell UI's own elements adopt them
    • then the type's own sheet, from its <css> block; a super-type's sheet comes first
    • compiled as static css = css`...`; the css tag hands back the sheet as text (P10)
  6. Drawing (core): draw the card puts the card's tag on the page with the card attached, instead of drawing its markup inline (P5).
    • a drawable list draws its frame in its own shadow root (P6)
    • its items go in as its CHILD elements, shown where the frame says <children/> (P15)
    • so a pile of cards is the same shape in a program and in hand-written HTML
  7. The outside (app): the type's properties are the element's attributes and properties, its methods the element's methods (P8), and the two agree both ways (P13).
    • a property holding a thing shows as its reference, pile="Tableau#T1" (P18)
    • a tag's id names its thing, and an element the program draws takes its thing's name as its id
  8. Recompiles (app and core): an edit keeps each tag defined and swaps what's behind it (P7), and carries the program's things over to the new classes (P16).
    • the compiler marks the program's start, so a carried-over run skips it (P17)
    • the runner starts afresh when the edit changed the file that starts the app
  9. Layouts (app): a <spell-app>'s own markup can be its layout, with spell inside it (O6). 
<game-pile>                 <!-- the pile's frame:  its own to draw, in its shadow root -->
  <game-card …></game-card>  <!-- each card:  a child element, shown in the frame's <slot> -->
  <game-card …></game-card>
</game-pile>

The TypeScript writer writes the same element as a short Spell UI class of its own, on the runtime's element (Q6, J41, P10).

  • class CardElement extends SpellElement<Card> says only the card's attributes, methods and sheet.
  • The page builds the tag on it, adding the rest, so both output languages draw the same element.
  • No page runs TypeScript output yet: the classes the writer writes are type-checked and run headless, but have never drawn on a page.
