Where should a layout's spell be turned into JavaScript?

  • A layout written inside a <spell-app> has spell in it: the curly-bracket holes, the actions, and the <spell> blocks.
  • Something has to turn that spell into JavaScript before it can run.
  • For P9 · Spell Inside Markup, and Owen's Klondike sketch (O6).

Here is the spell in question, from the sketch. None of it is JavaScript: it's spell, written in the PAGE, not in the project's .spell files. 

<spell-app name="Solitaire">
  <ui-text>Score {score of the game}</ui-text>          <!-- a hole:  a value, kept up to date -->
  <ui-button action={autoplay}>AutoPlay</ui-button>     <!-- an action:  runs on a press -->
  <solitaire-stock-pile>
    <spell>                                            <!-- a block:  code for this one tag -->
      when clicked
        - deal three cards to the discards
    </spell>
  </solitaire-stock-pile>
</spell-app>
  • What spell may go in the holes and actions is already settled: any spell, both places (Q11).
  • What a block's code sees is settled too: its tag's thing first, then the program (Q12).
  • What's NOT settled: which tool compiles it, and when.
    • Spell compiles to JavaScript only through spell's parser, the big part of the spell language's code.
    • A <spell-app> today runs only a project's compiled JavaScript: it never downloads the parser.
    • The app's build tests pin what the spell-app.js bundle loads: element.build.test.ts.
  • The rest of P9 is built already, with no parser: the markup shows as the app's drawing (Q10), and each drawable tag finds its thing by its id (Q9). Only the spell inside the markup waits on this.
  • A <spell-app> whose layout has a hole, an action or a <spell> block loads spell's parser, lazily (a chunk fetched only then).
  • Each piece is parsed against the project's declarations: its .declarations.json, already published beside its compiled code.
  • Then compiled, and run in the program's scope.
  • A page with no spell in its markup loads exactly what it loads today.
  • Cost:
    • a big chunk, the parser (about 600 kB), on such pages only
    • each page load compiles its layout again
    • the app's build tests change, to allow the parser as a lazy chunk
  • Why recommended: the layout stays where the sketch writes it, inside the page, with no build step.

variables should be looked up in scopes -- the component, the class, the page, the program

Yes -- that's the order a hole's names resolve in, innermost first. With A, each hole is parsed in a scope built for it, so a name finds the nearest thing that has it.

  1. The component: the tag's own thing -- Q12's "its thing first". Inside <solitaire-card>, its rank and a bare "rank" both read the card's.
  2. The class: that thing's type -- its class members and statics, e.g. card suits, a value kind's list.
  3. The page: the layout's named things -- each tag with an id is a name. E.g. <solitaire-tableau id="T1"> is T1, so a hole elsewhere can say the number of cards in T1.
  4. The program: its top-level things, functions and types, as anywhere in it -- score of the game, autoplay. 
<spell-app>
  <ui-text>Score {score of the game}</ui-text>            <!-- the program:  the game -->
  <solitaire-tableau id="T1"></solitaire-tableau>
  <ui-text>{the number of cards in T1} left</ui-text>    <!-- the page:  T1 -->
  <solitaire-stock-pile>
    <spell>
      when clicked
        - deal three cards to the discards               <!-- the component first (it), then the program -->
    </spell>
  </solitaire-stock-pile>
</spell-app>
  • How: the parser's scopes already chain this way (a block's scope falls through to its parent's). The page's scope is new: one variable per id in the layout, its datatype the tag's type.
  • Compiled, each hole is a function of those four: (thing, page, program) => ..., run live, so it redraws when what it read changes.
  • Q18 decided: A, the page loads the parser when it needs it
  • names resolve component, class, page, program -- the rest of P9 builds it
