A layout written inside a <spell-app> has spell in it: the curly-bracket holes, the actions, and the <spell> blocks. Something has to turn that spell into JavaScript before it can run. Where should that happen? For P9 · Spell Inside Markup, and Owen's Klondike sketch (O6).

Here is the spell in question, from the sketch. None of it is JavaScript: it's spell, written in the PAGE, not in the project's .spell files. 

<spell-app name="Solitaire">
  <ui-text>Score {score of the game}</ui-text>          <!-- a hole:  a value, kept up to date -->
  <ui-button action={autoplay}>AutoPlay</ui-button>     <!-- an action:  runs on a press -->
  <solitaire-stock-pile>
    <spell>                                            <!-- a block:  code for this one tag -->
      when clicked
        - deal three cards to the discards
    </spell>
  </solitaire-stock-pile>
</spell-app>
  • What spell may go in the holes and actions is already settled: any spell, both places (Q11).
  • What a block's code sees is settled too: its tag's thing first, then the program (Q12).
  • What's NOT settled: which tool compiles it, and when.
    • Spell compiles to JavaScript only through spell's parser, the big part of the spell language's code.
    • A <spell-app> today runs only a project's compiled JavaScript: it never downloads the parser.
    • The app's build tests pin what the spell-app.js bundle loads: element.build.test.ts.
  • The rest of P9 is built already, with no parser: the markup shows as the app's drawing (Q10), and each drawable tag finds its thing by its id (Q9). Only the spell inside the markup waits on this.
  • A <spell-app> whose layout has a hole, an action or a <spell> block loads spell's parser, lazily (a chunk fetched only then).
  • Each piece is parsed against the project's declarations: its .declarations.json, already published beside its compiled code.
  • Then compiled, and run in the program's scope.
  • A page with no spell in its markup loads exactly what it loads today.
  • Cost:
    • a big chunk, the parser (about 600 kB), on such pages only
    • each page load compiles its layout again
    • the app's build tests change, to allow the parser as a lazy chunk
  • Why recommended: the layout stays where the sketch writes it, inside the page, with no build step.
