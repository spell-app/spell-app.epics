Each property a drawable type declares becomes an attribute of the kind its declared type suggests; a property that holds a thing, like a card or a list, gets no attribute, only an element property.

  • Names: the attribute is kebab-cased, the element's property camelCased.
    • A property declared as short_rank is the attribute short-rank.
    • And the element's property shortRank.
  • Kinds, from the declared type (the table below).
    • A property with no declared type, like a card's rank ("one of ace, 2, 3 ..."), is text.
    • A spell choice is yes or no, so a boolean attribute: present means yes.
  • A legal value written as text becomes the value itself.
    • rank="2" sets the number 2, since 2 is one of a card's ranks.
    • rank="ace" stays the text "ace".
  • Only DECLARED properties: a value worked out from others (a card's colour, its short name) isn't one, so it isn't shown.
  • Methods: each method of the type and its super-types becomes an element method, camelCased.
    • turn_over is card.turnOver(), calling the thing's.
    • Not draw(), and not a method with values in its name, like "is a (suit)".
  • Where: core's spellCore.elementApiOf() lists the properties and methods; app's SpellElement.typePropertiesOf() names them and picks each kind.

A reference would be a short text naming ONE thing by its type and its name: Tableau#T1 is the tableau named T1.

  • It reads like CSS's tag#id.
  • It would give a property that holds a thing an attribute after all: today that's J23's "property only" row.

What it would look like

Drawable Solitaire's real names:

  • the tableaus are named T1 to T7
  • the other piles are named stock and discards
  • the foundations are named by suit, e.g. hearts
  • a card's name is worked out from its rank and suit: queen-of-spades, 2-of-hearts

Reflected into the DOM, a tableau and two of its cards would show:

<drawable-solitaire-tableau thing="Tableau#T1">
  <drawable-solitaire-card thing="Card#king-of-hearts" pile="Tableau#T1" direction="up"></drawable-solitaire-card>
  <drawable-solitaire-card thing="Card#queen-of-spades" pile="Tableau#T1" direction="up"></drawable-solitaire-card>
</drawable-solitaire-tableau>

Written by hand, the same attributes would wire things together:

<!-- the stock is a StockPile:  a reference finds a sub-type too -->
<drawable-solitaire-pile thing="Pile#stock"></drawable-solitaire-pile>

<!-- one particular card -->
<drawable-solitaire-card thing="Card#ace-of-spades"></drawable-solitaire-card>

<!-- a property holding a list:  its items' references, space between -->
<my-hand cards="Card#ace-of-spades Card#2-of-hearts"></my-hand>

How it would work

  • A thing to text: its type's name, #, its name.
  • Text to a thing:
    1. split at the #
    2. find the type by name, as reading saved JSON does (spellCore.things.classNamed())
    3. among the program's things, the one of that type or a sub-type with that name
  • Close to what P9's layout lookup already does (spellCore.thingFor()), but that matches only the EXACT type.
    • So <drawable-solitaire-pile id="stock"> doesn't find the stock, a StockPile.
  • The element would get a new attribute kind beside string, number and boolean: a reference, and a list of them, kept agreeing both ways as P13 does for the others.

What it would do for us

  1. Inspectable: the inspector shows which thing each element draws, and what its thing-holding properties point at.
    • Today a card's element shows its rank, suit and direction, and nothing about its pile.
  2. Settable from HTML: a property holding a card, a pile or a list could be set in markup, not only from a script.
  3. Layouts can wire things together: bind an element to any thing by type and name, a sub-type included, or hand one element another's thing.
  4. Styling and finding: [pile="Tableau#T1"] picks the cards on T1, in CSS or a query, inside the shadow root they're drawn in.
  5. Beyond the DOM (not needed for the above, but the same idea):
    • a short way to print a thing in the console and the Thing Explorer
    • saved JSON could keep identity: a card held by the deck AND a pile written as one card and one reference
      • Today it comes back as two cards: J37's reason for not carrying over through JSON.

What it would cost

  1. Names must be unique per type: mostly true in Drawable Solitaire, but not always.
    • Moving cards names a scratch list after its pile (cardsToMove.name = startPile.name).
    • Two matches need a rule: the first wins, or a stand-in saying so, as P9's "no Tableau named T1" does.
    • It's also why the type prefix beats putting the name in an element's id: an id must be unique in its document, and that scratch list and its tableau would both be T1.
  2. A thing with no name has no reference: the game, the deck and the list of all piles have none.
    • A top-level thing could fall back to its variable's name, which the program already knows: Game#game, Deck#deck.
    • A thing made in a loop with no name: no reference, and the attribute is left off.
  3. Worked-out properties: a card's pile isn't declared, it's worked out from which pile holds the card.
    • So today it isn't on the element at all (J23: only declared properties are).
    • Showing pile="Tableau#T1" is easy.
    • Setting it in markup would mean MOVING the card, which asks the tableau's rules (can it take this card?).
    • So: shown only, or a move. A call to make.
  4. Lists:
    • A tableau of 13 cards is an attribute of 13 references, rewritten on every move, and long in the inspector.
    • A name with a space (a pile named "my pile" is legal) needs quotes or escaping in a list.
    • Reading a list back gives the same things only when every item has a name unique for its type.
  5. Renames break markup: a layout pointing at Tableau#T1 finds nothing once the tableau is renamed.
    • A card's name follows its rank and suit, so it's stable.
  6. Size: roughly 2-3 hours for thing and single references, shown and settable.
    • Lists, the top-level fallback and moving by attribute add about as much again.
