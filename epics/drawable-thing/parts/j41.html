Need more detail

The pick is where the compiled TypeScript gets the code behind <test-project-card> from: Spell UI's own base (A), the runtime's existing element class (B), or nowhere, with types only (C). Below: what an element class is here, what each option writes for Drawable Solitaire's card, and what I checked in the code.

What an "element class" is, and why Q6 wanted one

A drawable thing draws as its own custom element: a card in Drawable Solitaire draws as <test-project-card>.

  • The element has its own styles, and its own outside: the page's code can read its rank and call its turn-over.
  • The class behind that tag is its element class.
  • Today nobody WRITES that class: the page running the program makes one at run time, the same way for every type.
  • Q6 (answered B, "Both, in this epic") asked the TypeScript writer to write it out, so the compiled .tsx reads like a Spell UI element Owen would write by hand, and passes the type check.

Today's flow, in the order it happens:

  1. The compiled card class names its tag as it's declared: static elementTag = spellCore.defineElement(this, "test-project").
  2. defineElement() keeps the tag on the class. A moment later, once the class's CSS is set, it tells the page, through the page's definer (spellCore.elementDefiner).
  3. The page filled that in when it loaded the runtime (installSpellElements()), so app's SpellElement.defineFor() runs: it builds a class extends SpellElement with the card's attributes and sheet, defines the tag, and adds the card's methods to it.
  4. draw the card then draws the card's tag, with the card as its thing. The element draws the card inside it (drawThing()).

About 400 lines, built up over this epic. A hand-written element class that wants the same behaviour has to do all of it:

  • draws its thing in the thing's own error boundary
  • each property is an attribute and a property, and the element and its thing agree both ways (P8, P13)
  • a tag written by hand, with no thing, makes its own card
  • in a <spell-app>'s layout, <solitaire-tableau id="T1"> finds the program's tableau named T1, or shows a stand-in saying it's missing (P9, Q9)
  • a program run again takes the tag over and swaps its CSS in place (P7)

What I checked

Five facts from the code, and three probes run in a scratch folder (nothing in the repo changed):

  • The type check can see Spell UI. The A, B and C sketches below, each added to the real DrawableSolitaire TypeScript, pass tsc with 0 errors, once the check:
    • maps the new module names (Spell UI's core, app's SpellElement), and the paths Spell UI's own files import each other by
    • uses the 2023 JavaScript library: without it, Spell UI's own files give 9 errors (toReversed(), findLast())
    • Those settings are in typecheck(); C needs neither.
  • Spell UI can't load in the headless run. Under node, importing Spell UI's core fails.
    • The error: Unknown file extension ".css".
    • Spell UI's core imports its own CSS files, which only Vite can load.
    • So A and B both need a stand-in module there, mapped in cli's hooks.mjs.
    • The fake page has no customElements either, so a define() as the file loads would throw.
  • "Defined twice" is silent, not an error. Spell UI's define() and the page's defineFor() both quietly skip a tag that's already defined: the first one wins, and the other's settings are lost without a word.
  • No page runs the TypeScript output today. Only spell run and the core contract run it, under node; the editor, VS Code and <spell-app> all run the javascript.
    • So the page-side blockers bite only when someone takes the .tsx into a page of their own.
  • A thing draws as its element only when the page has a definer. elementFor() answers a tag only while spellCore.elementDefiner is set; otherwise the card draws as a plain thing.
    • That's why the core contract prints the same for both targets today: neither makes an element there.

A · A Spell UI class per type, on Spell UI's own base

The writer writes the whole element per type, as Spell UI's own families are written: a vocabulary, a DOM element class carrying the methods, and a component that draws the card.

B · On the runtime's own element, SpellElement

The writer writes a short class on app's SpellElement, saying only what's the card's own, and hands it to the page, which defines the tag with it. 

import { E, SpellElement } from "@spell/elements"

/**
 * `<test-project-card>`:  a card, drawn in its own element, e.g. by `draw the card`.
 * - Its methods are its card's, as for javascript:  `turnOver()`, `play()` ...
 */
export class CardElement extends SpellElement {
  @E.proto static vocabulary = {
    ...SpellElement.vocabulary,
    tag: "test-project-card",
    noun: "card",
    attributes: [
      ...SpellElement.vocabulary.attributes,
      { name: "rank", kind: "string", description: "Its rank." },
      { name: "suit", kind: "string", description: "Its suit." },
      { name: "direction", kind: "string", description: "Its direction." }
    ]
  } as unknown as typeof SpellElement.vocabulary
  @E.protoMerged static elementSetup: Partial<E.ElementSetup> = {
    styleSheets: { "test-project-card": Card.css }
  }
}

  • What a user notices: nothing. It's the same element as javascript's, behaviour for behaviour.
