"a card is a drawable thing" half-parses, and makes a class that can't run.

"drawable thing" and "drawable list" become built-in types, two words each (Q2). Core gains the two base classes they compile to, Drawable and DrawableList.

  • "a card is a drawable thing" parses cleanly, with no leftover word and no error.
  • "a pile is a drawable list of cards" makes a list type that can draw.
  • The compiled program runs: both base classes exist when it does.
  • Programs that don't say "drawable" are unchanged.
  • Try it: a type can now say it is drawn. Both phrases parse cleanly and compile to core's two new classes (spell parse, or the spell editor). 
    a card is a drawable thing            -- export class Card extends Drawable {}
a card is a drawable                  -- the same
a pile is a drawable list of cards    -- export class Pile extends DrawableList { static instanceType = Card }
                                      --   in TypeScript:  extends DrawableList<Card>
a pile is a drawable list             -- export class Pile extends DrawableList {}
  • How spell reads them:
    • Two new built-in types, drawable (a kind of thing) and drawable list (a kind of list).
    • A table of words maps every way to write them, "drawable thing(s)" and the dashed forms included: SP.TYPE_WORDS.
    • "a drawable list of cards" has its own rule, a subclass of the plain list rule (J10).
    • The Type Explorer lists them: "Drawable (is a Thing)", "DrawableList (is a List)".
  • How spell names classes now:
    • A built-in type's class name comes from one table, so drawable list is DrawableList, not Drawable_List (J8).
    • One function names every class, built-in or declared: P.classCase().
    • A type you declare is named as before: "bank account" is still Bank_Account.
    • The TypeScript writer treats a drawable list as a list.
  • In core:
    • Two new classes, Drawable (a Thing) and DrawableList (a List).
    • They do nothing yet: drawing as an element comes in P3 and P5.
    • Every compiled program imports both, so every example's saved output changed in its import line only (J9).
    • The app's runtime exports them, so compiled programs still load.
  • Regenerated: core's built-in scopes, and Spell UI's spell highlighter bundle. The parsing notes (PARSING.md, "Type names") explain the two types.
