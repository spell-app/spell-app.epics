A spell file can hold CSS in a <css> block, but formatted text has nowhere to go: markdown's own symbols would be read as spell.

A <markdown> block is read exactly as written, like a <css> block, drawn with Spell UI's <ui-markdown>, and coloured as markdown in VS Code and the spell editor.

  • Owen (reviewing T5, the todo this phase came from): "do in new phase". The block is his idea, from the raw-text <css> call (J15): "we can do the same for e.g. <markdown>".
  • A <markdown> block in a spell file shows as formatted text, its markdown kept exactly as written. 
    to draw a rules panel:
	return <div className="rules">
		<markdown>
			## Klondike
			Build each pile **down**, alternating colours.
		</markdown>
	</div>
  • Nothing inside the block is read as spell: its *, #, < and braces reach the page as written, as a <css> block's do.
    • Spell's tokenizer reads markdown as a raw-text tag, beside css.
    • The indent its lines share comes off, so the block can sit indented in a drawing.
  • It's drawn by Spell UI's markdown element, <ui-markdown>, with the markdown as its text.
  • The inside of the block is coloured as markdown in both editors:
    • in VS Code, through spell's grammar, as it already colours a <css> block as CSS
    • in the spell editor in the web app, as its <css> blocks are coloured
  • The phase opens by settling T5's three open questions with Owen, before anything is built:
    1. Where a block may go: inside a drawing only, or also in a type's outline (as its description, say) and in a <spell-app> layout.
    2. Whether a {hole} in the markdown shows a live value, as a layout's text does (P9), or stays plain text.
    3. Whether the compiled program hands the markdown to <ui-markdown> as text, to render in the page, or renders it to HTML when it compiles.
