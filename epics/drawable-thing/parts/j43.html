Written down now (T11): the durable doc's "Its thing" explains what an element's thing is, and the three ways it's found, first one wins. References have their own sections beside it: "Thing references".

An element's thing is the spell thing it shows. Every drawable element draws ONE thing of the running program: a <solitaire-card> draws one card object, and the element is that card's view.

  • The element draws the card's own to draw inside itself, and keeps the card's properties and its attributes the same, both ways (P13).
  • The element finds its thing in one of three ways. The first one that applies wins (SpellElement.currentThing).

Spell code says draw the card, or a pile draws its cards as its children.

  • Core makes a <solitaire-card> and hands it the card object itself.
    • The card goes in the element's thing JavaScript property.
    • The code: spellCore.drawThing().
  • Only the property is set: no thing="..." attribute is written. This is the case J43 is about. 
// made NOW:  the thing is a plain value, set once
return (h(tag, { "prop:thing": thing }, ...items) as unknown as () => Drawing)()

Markup written by a person says which of the program's things the tag shows.

  • By a reference in its thing attribute, anywhere on the page (P18): <solitaire-pile thing="Pile#stock"> is the program's pile named "stock".
  • Inside an app's layout, by its id (P9): <solitaire-tableau id="T1"> is the program's tableau named T1.
  • Until the program has that thing, the tag shows a stand-in: ⚠ no Pile#stock.
  • In a layout: the program's ONE thing of the tag's type, e.g. <solitaire-stock-pile> is the stock. None, or more than one: a stand-in asking for an id.
  • On a plain page: the tag makes its own new thing of its type, once it's on the page, from its attributes: <solitaire-card rank="ace" suit="spades"> makes a new ace of spades.

What J43 is about: in case 1, the browser's inspector doesn't say WHICH card an element shows. Its other thing-holding properties already show as references since P18, like pile="Tableau#T1". 

<!-- today:  which card is this?  only its values say -->
<solitaire-card rank="queen" suit="spades" direction="up" pile="Tableau#T1"></solitaire-card>

<!-- after T12:  the card's own reference, first -->
<solitaire-card thing="Card#queen-of-spades" rank="queen" suit="spades" direction="up" pile="Tableau#T1"></solitaire-card>

Why writing that attribute isn't simple: the element would read it back, and lose the card.

  • Spell UI hears every attribute written on its elements as the page changing it (DOMElement.attributeChangedCallback()).
  • So setAttribute("thing", "Card#queen-of-spades") would store that TEXT as the element's thing, in place of the card object the program handed it.
    • The attribute is the "json" kind, and its converter passes plain text through. Converters.json() parses only text that starts like JSON: a bracket, a brace or a quote.
  • The element would then go from case 1 to case 2: it would look the card up by that reference (referencedThing).
  • That finds the card only while it keeps its name.
    • A card's name is worked out from its rank and suit: "queen-of-spades".
    • So after card.rank = 2, the element would show ⚠ no Card#queen-of-spades.
  • Spell UI can write an attribute WITHOUT hearing it, but only for itself (DOMElement.writeAttribute(), private).
    • It does this when a property's value is written back to its attribute ("reflection").
    • A "json" attribute like thing is never written back (ElementDefinition): that's why handing over the card writes no attribute today.

The small Spell UI change T12 needs, and what it would do:

  • Spell UI: a public way for a component to show an attribute without hearing it. It would be the private write above, opened up.
  • The drawable element: in case 1, it writes its card's reference to its thing attribute that way, and again whenever the reference changes (spellCore.referenceFor() follows the card's name).
  • The element keeps the card object itself as its thing property, so nothing is looked up.
  • Typing a different reference into the inspector would still be heard: the element would switch to showing that thing, as in case 2.
  • Cases 2 and 3 don't change: a hand-written tag keeps the attributes it was written with.
