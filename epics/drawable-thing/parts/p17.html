On each recompile the new program still runs its start from the top until its first pause, so what the start does before that happens again: its tests print, and a toast or alert shows again (J36).

The compiler marks which of a program's top-level lines are its START. A recompile that carries the last run's things over loads the program's types, functions and top-level things, and skips the start entirely. A first run and Restart still run all of it.

  • Owen, reviewing J36 (the judgement call that kept P16's way of loading): "later phase in this epic". It's J36's option B, built on top of what P16 built.
  • In the editor, an edit to Drawable Solitaire prints nothing again.
    • No test lines, no logged game: only P16's "Kept ... from the last run" line.
    • A start that shows a toast or an alert, before any pause, doesn't show it again on an edit.
  • Which lines are "the start": a rule the compiler can apply, settled at the phase's start (a question, if it isn't clear-cut).
    • In Drawable Solitaire's compiled code the start is mixed in with what it declares: a card test runs right after the card's type, before the deck's type is declared.
    • Candidate 1: every top-level line that ACTS is the start, wherever it is.
      • A call to one of the program's own functions: testCardSetup(), resetTheGame().
      • An app started: game.start().
      • A console line, a toast, an alert.
    • Kept by candidate 1 (never the start):
      • types and functions
      • top-level things, and the lines that fill them, e.g. allPiles.append(stock)
      • the headings' calls, which the Thing Explorer reads to group things
    • Candidate 2: everything from one marked line on, e.g. start the game. Simpler, but Drawable Solitaire's tests, above that line, would still print.
  • In the compiled code, both writers (javascript and TypeScript) mark the start's lines in place, so their order and scope stay as they are.
    • E.g. each start line runs only when spellCore says the start is on.
    • The exact markup is the phase's call.
  • On a recompile that carries things over, in order:
    1. the runner loads the new program with its start off
    2. its types, functions and top-level things are made, as the program declares them
    3. the last run's things are copied into them, as P16 does
    4. the app starts itself, as the last run had it (P16 already does this when the start never got that far)
  • A top-level thing that can't come over (its type changed, or it's new in this edit) may need what the start does to it, e.g. a deal.
    • Then the program is loaded again the way P16 loads it: from the top, stopping at its first pause. The console says why.
    • P16's never-ending pause stays only for that, or goes, if the phase finds it isn't needed.
  • Unchanged: a first run, Restart, spell run and the core contract run the whole program, start included, and print what they print today.
