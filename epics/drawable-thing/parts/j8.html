Spell's two new built-in types each have a two-word name, but each compiles to ONE class of one word: drawable list becomes DrawableList, not Drawable_List.

  • A type someone declares in several words still compiles with underscores, Bank_Account (the multi-word name call, J4).
  • Built-in types are different: the class already exists in core, under the name the plan gave it.
  • So one table in the parser now says what each built-in type's class is called: P.BUILT_IN_CLASS_NAMES.
  • One function names every class from a type's name, built-in or not: P.classCase().
    • It looks the name up in the table first, and falls back to the usual underscore form.
    • Every place that used to name a class itself now calls it: the type lists in each scope, the type rule, the root scope. 
export const BUILT_IN_CLASS_NAMES: Record<Datatype, string> = {
  list: "List",
  thing: "Thing",
  app: "App",
  drawable: "Drawable",
  "drawable list": "DrawableList"
}

classCase("drawable list")   // "DrawableList"
classCase("bank-accounts")   // "Bank_Account", as before

  • One place decides every built-in class's name; a new built-in class is one more line in the table.
  • Name the datatype drawable-list, and let it compile like any dashed name.
  • No new table, but core would have to export a class called Drawable_List.
  • That name would leak into every compiled program and every TypeScript error message.
  • Have the list rule write DrawableList when it writes the parent class, and nothing else.
  • Smallest change, but every other place that names a class (the scope's type lists, the Type Explorer, TypeScript) would still say Drawable_List.
  • "a pile is a drawable list of cards" compiles to class Pile extends DrawableList
  • a scope finds the built-in type under DrawableList, its class name
  • user types are unchanged: bank account is still Bank_Account
