A type's <css> block becomes its class's style sheet text, but every line after the first gains two spaces in the compiled file.

  • The CSS is compiled to a static css member, as a backtick string (a template literal).
  • The code that writes a class indents every line of each member, to sit inside the class.
  • Inside a backtick string, those spaces become part of the text: lines 2 and on start two spaces further in.
  • CSS ignores whitespace between rules and declarations, so the styles are the same.
  • The one case it changes: a CSS string value that runs over several lines (rare) would gain the spaces in its value. 
// a card is a drawable thing:
// 	- it has a rank as a number
// 	<css> :host { display: inline-block }  .red { color: crimson } </css>
export class Card extends Drawable {
  ...
  static css = `:host { display: inline-block }
  .red { color: crimson }`
}
  • Chosen and built.
  • The compiled file reads like the CSS that was written.
  • The styles are the same; only a multi-line CSS string would differ.
  • The text is exactly what was written.
  • But the compiled file shows the whole sheet as one long, unreadable line.
  • A type's CSS works as written, and reads as CSS in the compiled file.
  • A CSS string value spread over several lines would gain two spaces per line.

Yes, this can be done: a type's CSS would compile to a css-tagged template, the way Lit writes it, and the tag would also fix this call's indent problem. I read your sketch as a request, so it's now part of P10 · TS Solid Elements.

  • A small function, css, exported by spell's runtime library.
    • It sits beside the library's h and on.
    • The compiled file imports it like the others, only when a type has a <css> block.
    • It joins the template's text and hands back the style sheet as plain text.
    • It also takes off the indent every line shares. So the compiled file can indent the CSS inside the class, and the sheet the browser gets is still exactly what was written.
  • The <css> rule, CSSBlock.getAST(), writes a tagged template instead of a plain backtick string.
    • The parser's syntax tree has no tagged template yet: it needs one, written by both writers.
    • Both targets change: the JavaScript output and the TypeScript output.
  • The element's side stays as it is. SpellElement.cssOf() still reads each class's static css as text, and live restyling after an edit keeps working. 
import { spellCore, Drawable, h, css } from "@spell/core"

export class Card extends Drawable {
  static elementTag = spellCore.defineElement(this, "Drawable Solitaire")

  static css = css`
    :host { display: inline-block }
    .red { color: crimson }
  `
}
  • VS Code does NOT colour the inside of a css template on its own: that takes an extension, such as the one Lit users install.
  • Spell's own VS Code extension can colour them, with a small extra grammar.
    • It already colours <css> blocks in spell files.
    • The grammar adds css templates in JavaScript and TypeScript files.
    • Then nothing else needs installing.
  • The spell editor's own view of the compiled JavaScript (in the web app) would still show the CSS as a plain string: that's left out of the phase.

One choice for you: what the tag hands back.

  • Nothing that reads a type's CSS changes: the element, live restyling, the style registry.
  • The registry that shares sheets across shadow roots takes text, so text is what it wants anyway.
  • Works outside a browser too, in tests and on the server.
  • The browser parses the CSS once, when the class loads.
  • But the element and live restyling would have to turn it back into text, or learn a second way to adopt a sheet.
  • And it fails where there's no browser, such as the parser's own tests.
