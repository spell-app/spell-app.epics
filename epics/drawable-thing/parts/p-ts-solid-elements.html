Both targets go through the same steps on the page. The only difference is step 2: javascript hands nothing over, so the page starts from a bare element.

  1. The class is declared: static elementTag = spellCore.defineElement(this, ...) names its tag, and tells the page a moment later, once the class is whole (defineElement()).
  2. TypeScript only: right after the element class, useElement() keeps CardElement on the card's class, for the page to find. Only a class's own counts, never one handed for its super-class.
  3. The page's SpellElement.defineFor() picks what to build on: the handed class, else a bare SpellElement.
  4. Attributes: the class's own, as written (a card's rank, suit and direction), then what the page works out from the type, as for javascript: super-types' properties, and the list holding it (a card's pile). The naming rule is one function both sides share, drawableAttributeFor().
  5. Sheets, in order: the super-types' first, then the type's own (sheetFor()).
  6. The tag is defined on the page once. A program run again only restyles it.
  7. Methods (addMethods()): a method the class has itself, like CardElement.turnOver(), runs on the element; any other, like a super-type's, calls the thing's, as for javascript.

Core can't import Spell UI, so the element classes import their base under a name of their own. Each place that runs or checks compiled TypeScript resolves it differently (J54).
