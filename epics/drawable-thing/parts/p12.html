Spell in a layout can listen for events in one way only: a <spell> block holding when clicked lines, with the handler's statements on the lines under it.

Any element in a layout can carry its own event handlers, written two ways.

  • Any element means Spell UI's tags, such as <ui-button>, and plain HTML ones, such as <div>.
  • The nested <spell> block also takes a handler on one line, when clicked: play a song, and the word on as well as when.
  • A new attribute form puts a handler on the tag itself, in the syntax Owen and Claude pick first (Q20); spellCore's on hooks them up where that helps.
  • Owen (reviewing J27): "Definitely want to be able to add arbitrary events to individual objects ... This should work for any HTML elements."
  • His examples work as written, on a Spell UI tag and on a plain one: 
    <ui-button>
  Play
  <spell>
    when clicked: play a song
    on drag: play another song
  </spell>
</ui-button>

<ui-button on-click={play a song} />     ... or when-clicked={play a song}:  Q20
  • The phase starts by exploring the attribute syntax WITH Owen, before anything is built.
    • The choice: on-click={...}, when-clicked={...}, or both.
    • It's an open question: Q20.
    • Owen's own words: "I'm unclear on the best syntax, we'll explore that when we get to this."
  • In a <spell> block, a handler may sit on one line or several:
    • when clicked: play a song is one handler, its statement after the colon.
    • when clicked with its statements indented under it still works, as P9 built it.
    • on drag: means the same as when dragged:.
  • Any event the browser fires can be listened for, not only the five words P9 knows (clicked, double-clicked, hovered, focused, changed).
  • It works on ANY element in the layout: a Spell UI tag, a plain HTML tag, or one of the program's drawable tags.
    • On a drawable tag, it is that tag's thing, as in P9.
    • On any other tag, the handler sees the page's and the program's names (Q18's order).
  • The handlers are hooked up through spellCore's on where that helps, so a handler is listed and taken back with the program's other listeners on the next run (Owen: "OK for if this requires spellCore 'on' to hook things up").
  • An attribute handler with spaces in it needs quotes today (C15): the browser ends an unquoted value at the first space. The phase says what Owen's bare on-click={play a song} needs, or makes it work.
  • Methods and variables for one element (J27's option B) stay out of this phase, unless Owen asks for them.
