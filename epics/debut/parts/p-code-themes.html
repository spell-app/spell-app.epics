Every theme's code draws in Shades of Purple: Matrix's mint console has purple comments and a purple band on the current line, and in VS Code itself none of Spell's themes exist.

  • Pick Matrix, and the editor's code turns to a mint console palette; pick any other theme, and its code matches it too, light and dark ("yes mint").
  • VS Code's theme picker lists a Spell theme for each of Spell's, in light and dark: 18, wearing the theme's own surfaces, accent and code colours ("make a VSC theme to match each theme, in both light and dark").
  • Code blocks on the docs sites and epic pages take the same code colours as the editor.
  • Every code colour reads: 4.5:1 against the code's own background, comments too, since a Spell file's comments are its prose.
  • The theme bench shows the code colours in its editor frames and tunes them in a Code branch.

yes mint. Let's make a VSC theme to match each theme, in both light and dark.

  • Each Spell theme gets code colours of its own, light and dark: the editor's code, every code block on the docs and epic pages, and a VS Code colour theme.
  • They're part of the theme, in its theme file: one place to change them, and the theme bench tunes them like any other value.
  • The Spell extension for VS Code lists all of them, so VS Code itself can wear any Spell theme, its side bar, tabs and status bar too.
  1. The code colours become part of the theme: a code group in the theme tree
    • Its roles are the ones the editor's Purple port already colours by (ShadesOfPurple.rules()): text, heading, comment, keyword, type, library, name, member, parameter, action, constant, string, tag, punctuation; plus attr, meta, addition and deletion, which code blocks use.
    • And the few editor colours: cursor, selection, current line, line numbers (and the current one), bracket match, find match.
    • Each is a CSS token, --ui-code-<role>, light and dark like every other value. Code blocks (<ui-code>) already read ten of them (--ui-code-keyword, -string, -comment ...), so they follow the theme with no new code; today they fall back to One Dark / One Light.
  2. How many palettes are designed by hand: 3 of 18 in full, the other 15 derived, then tuned
    • A recipe in ThemeFile derives a theme's code colours from its own colours: each role a hue the theme already has (its palette, primary, accent, positive, warning), at a lightness that reads on its code background (OKLCH: about 0.80 in dark, 0.48 in light); comments its muted text, a step toward its primary.
    • A theme file's code group only holds what's changed by hand: one role, or all of them.
    • Designed in full: Spell dark (Shades of Purple, as today), Spell light (the Studio board's light Purple, as today) and Matrix (a mint console: mint keywords, teal types, amber strings, grey-green comments, as Owen's rack viewer).
    • The other 15 (Glass, Fruity, Merlot, Paper, Midnight, Crisp, Pop in both schemes, and Matrix light) come from the recipe, then a designer pass each, tuning a few roles in their files. Every one is looked at; none ships unseen.
  3. Readable: every code colour 4.5:1, comments included
    • Against the code's real background: the code is see-through on the panel in every theme (J129), so the theme's panel colour.
    • Comments too: in a Spell file the comments are the prose (Solitaire's "# A playing card ..."), not asides.
    • Shades of Purple's own comment colour (#b362ff) is 3.85:1 on its navy, but about 4.8:1 on Spell's darker panel. Where a theme's panel is lighter, the recipe lifts it; Spell's stays as it is if it passes.
    • The contrast test gets a check per role, per theme, per scheme: 18 × 18.
  4. The editor's code reads the theme, with nothing generated for it
    • CodeThemes builds Monaco's theme from the page's own --ui-code-* tokens as they draw (a probe element's computed colour, so a light / dark pair comes out as the scheme shows it), and defines it with Monaco.
    • It rebuilds when the theme, the scheme or a tuning changes: it already watches <html>'s classes and the scheme; it adds the theme attribute and the bench's tuning message.
    • So the editor, the theme bench's live tuning and the read-only public build all need nothing more. ShadesOfPurple keeps only its token rules (which Spell token gets which role), its colours moving into Spell's theme file.
  5. VS Code: 18 colour themes, generated, in the Spell extension
    • A new writer beside ThemeFile, CodeThemeFile: pure, no node, so it can run anywhere. From a theme's values in one scheme, it writes a VS Code theme:
      • tokenColors: the roles onto TextMate scopes, Spell's grammar's (keyword.control.spell, comment.line.number-sign.heading.spell ...) and the common ones, so TypeScript, CSS and JSON look right too
      • semanticTokenColors: the language server's token types (type, parameter, comment.heading1 ...), with semanticHighlighting: true
      • colors: the editor colours, and the workbench's from the theme's surfaces, borders, text and primary (side bar and activity bar the page, the editor the panel, tabs, status bar, buttons, focus ring, lists), a fixed table of about 40 keys
    • Written into the Spell extension's themes/ (spell-matrix-dark.json ...) by its build, which may use Spell UI (every arrow points down; Spell UI never writes into spell-app). Committed, and marked generated in .gitattributes and generators.json5.
    • Its package.json lists them (contributes.themes, labelled "Spell Matrix Dark" ...), written by the same build, with a check that fails while stale.
    • The extension's own defaults that colour headings bold (configurationDefaults) stay; they're style, not colour.
  6. The theme bench
    • Its tuning tree gets a Code branch (the roles, light and dark side by side), and its editor frames show the code changing as a role is tuned.
    • "Copy changes" writes the code group like any other.
  7. Order: after One Theme Choice (P21), before Tints and the Full Theme Builder
    • After P21, so the editor's code follows the one stored theme rather than each place's own.
    • Before Tints: a tint changes the page's wash and accent, not the code; and the theme builder (P24) then gets the code group with the rest.
  8. Already there (coherence check)
    • <ui-code>'s ten --ui-code-* tokens: the code group takes their names, so no second set.
    • ShadesOfPurple's roles and token rules: kept as the mapping, its colours moving into the theme file.
    • The kit's colour helpers (spell/util/color: OKLCH, contrast) for the recipe and the test; CONTRAST_TEXT for 4.5.
    • Nothing generates VS Code themes today. The window looks (epic window color) re-hue Tomorrow Night Blue through each window's own colour settings, a different job; a Spell theme could later be a window look, noted, not in this phase.
  9. Left out
    • Publishing the themes to the VS Code marketplace on their own: they ship inside the Spell extension.
    • Tints in the code: a tint doesn't change code colours.
