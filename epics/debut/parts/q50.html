For : the margin and padding fields in your reference (a box per side, its letter inside, laid out top / left-right / bottom) are a new control, <ui-sides>. It needs a value a form can read and a page can write, and a way to say which sides it shows: your reference shows all four (Circuit's Margin), only top and bottom (Routine's Margin), or only left and right (Routine's Padding), the two in one row.

  • No Spell UI attribute holds sides today (a segment's padding is a word: md, lg), so the first fields that show one are a program's own properties, and the docs' examples.
  • value="10 20 10 20": one to four numbers, top right bottom left, as CSS's margin reads
  • sides="top bottom" shows only those boxes, in one row; none: all four, in a cross
  • an attribute like any other: it reflects, the form reads it as text, a program stores a string
  • why: the shape people already know, and it pastes straight into CSS
  • { top: 10, left: 20, right: 20, bottom: 10 }, as a json attribute
  • no text form: a page can't write it in markup, and it never reflects
  • margin-top, margin-left ... each a number; the field groups the four
  • four names per side set, in every schema that has one
  • a new tag, <ui-sides> (Spanish <es-lados>), a form control with a native fallback
  • a new value type, sides, drawn by it in every property editor
  • how it tells them apart: an object, or text starting with {, is read by side names (a side left out is empty); any other text is CSS's numbers
  • it gives back the form it was given (text in, text out; an object in, an object out), and the form reads that
  • sides="top bottom" still says which boxes show
