  • ONE remembered choice of theme, light / dark and (from P23) tint, which every page of every place draws in: the editor and its notebooks, the epic pages and guides, Spell UI's, App UI's and the brand's pages.
  • Kept by the page server, so it carries across the editor's own address and the docs' address; the browser keeps a copy for the first paint, and for when no page server answers.
  • A nested <ui-root theme> that sets its own theme is the only exception.
  1. One key, kept by the page server
    • The theme (with its tint, from P22) and the scheme are kept as ONE choice, in a store every place shares: spell-site:theme beside the existing spell-site:scheme.
    • Kept on the page server, through the kit's ServerPlace (/api/prefs, which spell-app's spaces already answer, in the person's own space).
    • The editor already reaches that address: its dev server passes /api on to the page server. So the editor's address and the docs' address read and write the same value, though their browsers' storage is apart.
    • The browser keeps a copy too, for two jobs:
      • the first paint, before the server answers: the head script and restore() read the copy, then take the server's value if it differs
      • when nothing answers /api/prefs (the read-only build, P9; a page server with no spell-app): the copy IS the choice
  2. Picked anywhere, followed everywhere
    • ThemePreference saves a pick to both places; every theme menu on the page follows (subscribe(), as today).
    • An open tab in another place catches up when it comes back into view: it asks the server again on visibilitychange and focus, and applies a changed choice. Same-address tabs still hear at once, as now (ColorScheme.watch()).
    • ThemePreference.site() loses its own key: a place keeps only its own default, used until the viewer has ever picked, and one shared default is better (the question below).
    • This reverses J87 (each place remembers its own theme), from Owen's r1.
  3. The old keys, moved once
    • spell-app:theme, spell-epic:theme and spell-ui-site:theme: the first page to load after the change takes the value it finds, if the shared one is still empty, and forgets the old key, as ColorScheme moved the scheme's old keys.
  4. The one exception: a nested root
    • A <ui-root theme="..."> inside the page draws its own theme inside it, and its theme menu (if it has one) changes only it: checked, and a test added.
  5. Every place's setup
    • The editor (EditorTheme), the epic pages' bundle, Spell UI's site, App UI's and the brand's pages call the same setup, with no key of their own.
    • The theme bench (I49) needs no bridge for the theme any more; its tuning bridge stays.
  6. Rejected, and what each would touch
    • Serving the editor under the page server's address, so the browser's storage is shared: touches the editor's dev server, its hot reload and its /api, /spaces, /element forwarding, the editor's URLs in the page server's settings, and every bookmark of localhost:3000. A big move for one value.
    • A messaging bridge like the bench's BenchBridge: works only while one place frames the other. Two tabs, or a tab opened tomorrow, never hear.
    • A cookie on localhost: cookies ignore the port, so it would be shared, but every request would carry it, a page can't hear it change, and the public build's host would need its own.
  7. Already there (coherence check)
    • ServerPlace and PrefStore (the kit's persist/) already keep preferences on the page server, and ColorScheme already makes the scheme one choice per address: the theme joins them, no new mechanism.
    • ThemePreference stays the one owner of the choice; BenchBridge keeps only what it alone does (tuning, scrolling, the full view).
    • The site header's own preferences (SiteHeader's session store) are per tab on purpose, and stay so.
