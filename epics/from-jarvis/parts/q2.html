How should a page reach a place that needs a key: Spell's page server serving a project's authenticated places, or the Jarvis repo running its own small place server?

A page can't hold a key, so a web server place that needs one refuses in a browser (WebPlace). Spell has the server half for this, PlaceServer, which holds keys and scrubs them from answers; but the page server only serves data folders and one Airtable base through it.

So with JARVIS_TOKEN set, the Jobs page still shows "Jarvis didn't answer".

  • The page server reads each project's places, and serves the ones with a key at /api/places/<project>/<place>/, its key from the environment.
  • The compiled page goes there instead of straight to the server, as it already does for data folders.
  • Every project gets it, Jarvis included, with no code of its own.
  • Read only by default, as the Jarvis rule wants: a deployment marked read only refuses writes already.
  • jarvis-spell starts a small server, new PlaceServer({ places: { jarvis } }), beside yarn start.
  • No Spell change, but each project that needs a key writes one, and P14 shrinks to the startup check.
  • P14 adds authenticated places to the page server, and the browser half that reaches them
  • the Jobs page works once Spell is packed again, with no Jarvis code
