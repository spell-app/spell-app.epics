Close. The word that fits what Spell already says is is a tree view, without the "ui". The exact words are new, so they're Q10, and the words for the methods it overrides are Q11.

How Spell says it today:

  • A plain view: a "solitaire" is a view.
  • A view on a built-in base, the closest match: a "card" is a draggable two sided view. "Two sided view" is a built-in template, written in Spell, and its Spanish is una vista reversible. The card overrides its hooks in the base's own words, to draw its front and to draw its back.
  • Spell UI's elements are named WITHOUT "ui" in plain Spell. A drawing says <text> and <button> (over 200 uses in the examples), so it says <tree> for <ui-tree>. Spanish says <arbol>.
  • The tree's vocabulary already lists "tree view" as another name for it, and its Spanish lists "vista de arbol".
  • So a "netlist column" is a tree view reads like a "card" is a two sided view, and adds no "ui" to Spell. "ui" would be the first time plain Spell says it, and Spanish has no "ui" at all.

Ambiguities to know about:

  1. A program's own type called "tree" (a family tree app). a tree view could then read as "a view of a tree". The fix: "tree view" is looked up as one name, as "two sided view" is, and a program's own type named "tree view" warns.
  2. Is it every Spell UI element, or a chosen few? a table view and a graph view read well; a button view and a text view don't. Q10 asks.
  3. The name "netlist columns" is plural for one thing. Spell's type names are singular, so the example says "netlist column".
  4. Its tag would follow the project, as views' tags do: <jarvis-netlist-column>, not the handoff's <netlist-columns>.
  5. The tree's hooks have only code names today (rowClass, nodeLabel). Spell needs words for them, as the two sided view has to draw its front: Q11.

A Spell way to declare an element that extends a Spell UI element: its tag, its own stylesheet, and the methods it overrides.

  • a "netlist columns" is a ui tree element, appearance "columns", with its styles in its own CSS file and its overrides as methods.
  • Ask before the exact words: new language.
  • The project keeps NetlistColumns.ts, as today; the compiler defines it through the page's definer.
  • No new language, but not a Spell page through and through.
  1. Start from what exists: core.useElement() lets compiled TypeScript hand the page an element class for a Spell view, and Spell UI's elements are defined with a vocabulary and define(). The handoff's four subclasses (<netlist-columns>, <jarvis-netlist>, the JSON viewer, <netlist-ref>) all do it the same way: a vocabulary, a sheet added in elementSetup, define() from the project.
  2. A project declares an element that extends a Spell UI element: its tag, its own stylesheet, attribute defaults (like appearance="columns") and methods it overrides (rowClass, nodeLabel); the form is this phase's choice.
  3. The page defines it after the base element, through the page's one element definer, as views are today.
  4. The handoff's first gotcha fixed: a vocabulary with no slots or texts crashes Vocabulary.resolve ("vocabulary.slots is not iterable"); the vocabulary type defaults them, so a subclass's small vocabulary works.
  5. Rules, the core's element code, and spell/element if a base needs a hook; English and Spanish.
  6. Checked by: rule tests and a test of a vocabulary without slots; an example declaring a column tree subclass and a graph subclass (both in the kit after the landings), drawn in the editor.
  7. Left out: extending an element that isn't Spell UI's; the handoff's second gotcha (a percentage height not reaching through a shadow root), which is the graph's fill todo.
