Since d7a51fd2b (2026-11-20, 'a site's theme is looked for in its project first, then in Spell UI'), SiteThemes.ts imports spell/ui/components/ui-theme-editor/ThemeTokens dynamically, and sharedSolid() refuses it, so yarn build:element fails on main and the branch.

It fails the app's element.build test, the spell run in spell-viewer test, and blocked checking J110's spell-viewer on a served page.

The cause is older than d7a51fd2b: the import of the theme tree came with old-console-redo's P1 (Project Themes), when the page's viewer started using SiteThemes. The app's element build takes all of Spell UI from its one shared copy, and refuses any other Spell UI file; ThemeTokens and ThemeFile were imported by their own paths, so it refused them.

  • Fix: SiteThemes takes ThemeTokens and ThemeFile from spell/ui, which it already loads in the same step.
  • ThemeTokens is already in that barrel (the theme editor's); ThemeFile joins it, through Spell UI's styles barrel.
  • Why not bundle them like drawnWindow: they hold no state, but ThemeTokens brings every theme and palette file with it. The element build would carry a second copy of all 28 files and the theme tree, which the shared Spell UI already has.

ThemeFile joins the theme editor's barrel, beside ThemeTokens, not the styles barrel: that one stays pure data, with no code in it (Spell UI's I13).
