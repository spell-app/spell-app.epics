A Spell page can show a file input, but no Spell words read the file someone picks or drops.

  • A page shows an uploader that takes .json files, picked or dropped, and lists them
  • The files are posted to the uploader's destination, or handed to its action instead
  • The page hears an event for each file and folder taken, with all its details, the same for a pick as for a drop, and can update its own look from them
  • The events take Spell's drag words: ui-file-dragged-over, ui-file-dragged-out and ui-file-dropped, the moments a Spell program writes as when a file is dropped on it:
  • With drop-zone="page", dropping files anywhere on the page is the same as dropping them on the uploader
  • Something on the page can catch the upload first, and take it over
  • Files too big, too many or of the wrong kind are turned away, with the reason shown

A new Spell UI element, <ui-uploader>, takes files someone picks or drops (or whole folders), on itself or anywhere in its drop-zone. It sends an event for each file and folder taken (ui-file-dropped, and ui-file-dragged-over / ui-file-dragged-out while dragging, after Spell's own drag words). It posts them to its destination URL, or calls its action with them instead, after anything that catches its ui-upload event has had the chance to take them.

It comes in four looks, appearance="hero" (the default), button, inline and compact, each restyled through its named parts and tokens.

  • <ui-input type="file" name="netlist file">'s files binds to a property, as form controls do (coherence: Spell UI's file input, not a native one); dropping a file on its drop area sets the same property.
  • Then the text of the netlist file, a built-in member of a file.
  • No new statements, only a built-in type with members.
  • when a file is dropped on it:, a case of Spell's existing drag handler line (when ... is dropped on it:), with the file in hand; a picked file the same way.
  • No new handler rule, one more case of an existing one.

folder = upload folder(s) rather than files

Either way, what the picked file's type is called in Spell is a new word: Q7.

  2. Its attributes, written as every Spell UI element's are (a vocabulary, a component, a sheet):
    • destination: a URL the picked or dropped files are posted to
    • action: a Spell action to call instead, with the files, as in action={read the netlist} in a drawing
    • extensions: the kinds it takes, a comma list (json, csv), read with the kit's commaList()
    • multiple: more than one file at a time
    • folder: picks or takes dropped folders instead of files, each folder's files with their paths in it
    • max-size: the largest file it takes, e.g. 2 MB (from your comment)
    • max-files: the most files it takes in one go (from your comment)
    • drop-zone: where else a drop counts as a drop on it: page for anywhere on the page, or the id of a section (step 4)
  3. Events for each file and folder, so the page can follow along and update its own look. Your words: "Would be good it the uploader sent file-drag*, file-drop* and folder-* events that could be caught by the page, e.g. to update the UI."
    • The names follow Spell UI's own: every event of a ui-* element starts ui-, lowercase with dashes (ui-changed, ui-selecting, ui-upload).
    • After the ui-, Spell's own drag words, not the browser's: the moments a Spell program already writes, "dragged over", "dragged out of" and "dropped on". So your file-drag* becomes ui-file-dragged-over and ui-file-dragged-out, and file-drop* and folder-* become one ui-file-dropped.
    • Each bubbles out of the element, so a handler anywhere up the page hears it.
    • In Spanish, the names follow Spanish's moments ("arrastra sobre", "arrastra fuera de", "suelta sobre"), as other Spell UI events take Spanish names: archivo-arrastrado-sobre, archivo-arrastrado-fuera and archivo-soltado.
    • A Spell program hears a drop the way it hears a card dropped on a pile, with the same rule: the drop area's when a file is dropped on it:, as a pile's when a card is dropped on it:.
      • The word "file" in it waits on Q7, which decides what Spell calls a picked file.
    Event When What it carries
    ui-file-dragged-over files are dragged onto its drop area, or onto its drop zone how many, and their kinds
    ui-file-dragged-out they're dragged away again, or the drag is called off the same
    ui-file-dropped, for a folder a folder is taken, before its files that it's a folder, its name, path, file handle and list of files
    ui-file-dropped, for a file once per file taken, kept or turned away that it's a file, the file, its name, path in its folder, size, kind, when it last changed, its file handle, how it came in, and the reason when it was turned away
    • "All of the available data" (your words): the browser's own File, and its file handle, the nearest thing a browser has to an OS file handle.
      • Chrome and Edge give a handle, which can read the file again later.
      • Safari and Firefox give none: the handle is left empty there, and the rest is the same.
    • The same events, whichever way the files came in (your words: "the same events should be sent if the drop happened from showing the file open dialog, or from drag-and-drop onto the page/section"). Their detail says which: dialog, drop or zone.
    • While a drag is still going on, browsers show only how many files there are and their kinds, never their names or sizes. So the drag events carry the count and kinds; the drop events carry everything.
    • No folder drag events: while dragging, a browser can't tell a folder from a file, so the two drag events cover both. A folder is known once it's dropped: ui-file-dropped, its detail saying folder.
    • A handler that cancels a file's ui-file-dropped leaves that one file out.
    • Then, for the files kept, the upload's own events as before: ui-upload, then ui-uploaded or ui-upload-failed per file.
  4. Dropping anywhere on the page. Your words: "<ui-uploader> should have a page attribute (push back if the name is unclear) which says 'dropping anywhere on the page is the same as dropping in this component.'"
    • Pushing back on the name: page on its own reads like a page number, or a page's address. The plan calls it drop-zone, with drop-zone="page" for the whole page.
    • It also takes a section's id (drop-zone="editor"), since your words name "the page/section".
    • While files are dragged over the zone, it gets a light overlay saying "Drop to add 2 files".
    • Several uploaders with a drop zone, the case you left open:
      • a drop on an uploader's own drop area always goes to that uploader
      • a drop elsewhere goes to the uploader whose zone is the closest around where it landed: a section's zone beats the page's
      • two uploaders with the same zone: the first on the page takes the drops, and the second logs one warning naming both
  5. What happens when files are picked or dropped, in this order:
    1. Files of a kind it doesn't take, too big, or past the count are turned away, each with its reason on its row.
    2. ui-file-dropped for each folder, then for each file (step 3).
    3. It sends ui-upload, holding the files it kept. It bubbles, so a handler anywhere up the page hears it. A handler that cancels it takes the upload, and nothing below happens. Same shape as the tree's ui-selecting.
    4. With action set, the action is called with the files.
    5. Else, with destination set, each file is posted there as form data, one request per file, so each row shows its own progress and its own failure. When a post ends it sends ui-uploaded (the server's answer) or ui-upload-failed (the error).
    6. With neither set, the files are only held: the element keeps and lists them, and ui-upload has still fired.
  6. Both set: action wins, as your comment's "instead" says, and nothing is posted.
    • The element logs one warning naming both, so a page that sets both by mistake finds out.
    • An action that wants to post too can do so itself.
