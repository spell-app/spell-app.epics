A Spell page can show a file input, but no Spell words read the file someone picks or drops.

  • A page shows an uploader that takes .json files, picked or dropped, and lists them
  • The files are posted to the uploader's destination, or handed to its action instead
  • The page hears an event for each file and folder taken, with all its details, the same for a pick as for a drop, and can update its own look from them
  • Before, while and after: a cancellable event before each step, events while it goes on, and one after, written in Spell as can take a file if:, when uploading:, while a file is dragged over it: and when a file is dropped on it:
  • A Spell view hears them in its own outline, or on the uploader's tag in its drawing; the page hears what no view took, at a program file's top
  • A folder uploader sends folder events, ui-folder-dropped and the rest
  • A handler reads the file's contents: the file as text, as json or as binary, which wait for it
  • With drop-zone="page", dropping files anywhere on the page is the same as dropping them on the uploader; drop-zone="#id" for another element, such as the enclosing <ui-section>, and drop-zone={view} in Spell
  • Something on the page can catch the upload first, and take it over
  • Files too big, too many or of the wrong kind are turned away, with the reason shown
  • Four looks, picked with appearance: hero (the big drop area, the default), button, input (a form field) and compact (a one-line drop area)
  • Pretty, and fully stylable: slots for its icon, message and button, properties for the words it shows while busy, named parts and --ui-uploader-* tokens
  • In English and Spanish

A new Spell UI element, <ui-uploader>, takes files someone picks or drops (or whole folders), on itself or anywhere in its drop-zone. It sends an event before, while and after each step (ui-file-dragged-over, ui-file-dropping, ui-file-dropped, ui-uploading, ui-uploaded; a folder one's are ui-folder-*). It posts them to its destination URL, or calls its action with them instead, after anything that catches its ui-uploading event has had the chance to take them.

Spell hears the events through its own chain: the view that drew the uploader, then the lists holding it, the app, and last a program file's own on lines. Spell words read a dropped file's contents.

It comes in four looks, appearance="hero" (the default), button, input and compact, each with slots for its icon, message and button, restyled through its named parts and tokens.

  • <ui-input type="file" name="netlist file">'s files binds to a property, as form controls do (coherence: Spell UI's file input, not a native one); dropping a file on its drop area sets the same property.
  • Then the text of the netlist file, a built-in member of a file.
  • No new statements, only a built-in type with members.
  • when a file is dropped on it:, a case of Spell's existing drag handler line (when ... is dropped on it:), with the file in hand; a picked file the same way.
  • No new handler rule, one more case of an existing one.

folder = upload folder(s) rather than files

Either way, what the picked file's type is called in Spell is a new word: Q7, answered: file.

What the attribute that takes the upload over is called. Your comment (C19) asks for on-upload in place of action.

  • <ui-uploader action={read the netlists}>: the action is called instead of posting.
  • In Spell UI, an attribute starting on- is always a listener for the event of that name: on-ui-uploading={f} hears ui-uploading. Keeping action keeps that true.
  • Its docs say it's a Spell action, not a URL (an HTML form's action is a URL).
  • the plan as written: action and destination, the action winning
  • <ui-uploader on-upload={read the netlists}> reads well, like a handler.
  • But it'd be the one on- attribute in Spell UI that isn't a listener: there's no upload event, and it sits beside on-ui-uploading, which is one.
  • Spell's writer treats every on- on a ui-* tag as a listener, so it needs a special case there too.
  • Spell's own event rule: a handler that runs TAKES its event. So a view's - when uploading: takes the upload, and nothing is posted.
  • In JSX: on-ui-uploading={(event) => { event.preventDefault(); ... }}.
  • One less attribute, and no "both set" warning; but taking over is less visible on the tag.

    • The names follow Spell UI's own: every event of a ui-* element starts ui-, lowercase with dashes. After the ui-, Spell's own drag words: "dragged over", "dragged out of", "dropped on" (Q12).
    • Before, while and after, as Spell's own events go: an event still happening (-ing) can be cancelled, and then its next step doesn't happen; one that happened can't be. So a drop is ui-file-dropping (cancel it to leave the file out) then ui-file-dropped.
    • A folder uploader sends ui-folder-* events instead of ui-file-* for the drag and the folder itself, then ui-file-dropped for each file in it. While dragging, a browser can't tell a folder from a file; so the uploader names its drag events by what it takes, and a plain file dropped on a folder uploader is turned away with its reason.
    • Each bubbles out of the element, so a handler anywhere up the page hears it.
    • In Spanish, the names follow Spanish's moments, as other Spell UI events take Spanish names: archivo-arrastrado-sobre, archivo-soltado, carpeta-soltada, subiendo, subido ...

    • What each browser gives (your comment: "I think we can get the file handle in Safari/FF based on the File object"). Partly so:
      • Every browser gives the File: name, size, kind, when it last changed, and its contents, read as often as wanted while the page is open.
      • On a DROP, every browser, Safari and Firefox too, gives an ENTRY (webkitGetAsEntry()): it walks a dropped folder and finds each file's path in it. It can't write the file, nor be kept past a reload.
      • A HANDLE (getAsFileSystemHandle()), which can write the file and be kept to read it again another day, is Chrome and Edge only; empty elsewhere.
      • A folder picked in the file dialog: every browser gives each file's path in it (webkitRelativePath), but no entry and, outside Chrome and Edge, no handle.
      • None of them gives a handle from the File itself: it comes only from the drop, or from Chrome's own file dialog.
    • Reading the file in a handler, your words: set contents to the file as text, as json or as binary, which waits for the read. In JavaScript, the detail's file.text().
    • The same events, whichever way the files came in. Their detail says which: dialog, drop or zone.
    • While a drag is still going on, browsers show only how many files there are and their kinds, never their names or sizes. So the drag events carry the count and kinds; the drop events carry everything.

  6. What happens when files are picked or dropped, in this order:
    1. Files of a kind it doesn't take, too big, or past the count are turned away, each with its reason on its row.
    2. ui-file-dropping then ui-file-dropped for each, a folder before its files (step 3).
    3. It sends ui-uploading, holding the files it kept. A handler that cancels it takes the upload, and nothing below happens. Same shape as the tree's ui-selecting.
    4. With action set, the action is called with the files.
    5. Else, with destination set, each file is posted there as form data, one request per file, so each row shows its own progress and its own failure.
    6. With neither set, the files are only held: the element keeps and lists them.
    7. Both set: action wins, as your comment's "instead" says, and one warning names both.
