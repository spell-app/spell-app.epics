A Spell page can show a file input, but no Spell words read the file someone picks or drops.

  • A page shows an uploader that takes .json files, picked or dropped, and lists them
  • The files are posted to the uploader's destination, or handed to its action instead
  • Something on the page can catch the upload first, and take it over
  • Files too big, too many or of the wrong kind are turned away, with the reason shown
  • In English and Spanish
  • Later, once Q7 is answered: Spell words read the picked file's text

A new Spell UI element, <ui-uploader>, takes files someone picks or drops (or whole folders). It posts them to its destination URL, or calls its action with them instead, after anything that catches its ui-upload event has had the chance to take them.

  • <ui-input type="file" name="netlist file">'s files binds to a property, as form controls do (coherence: Spell UI's file input, not a native one); dropping a file on its drop area sets the same property.
  • Then the text of the netlist file, a built-in member of a file.
  • No new statements, only a built-in type with members.
  • when a file is dropped on it:, a case of Spell's existing drag handler line (when ... is dropped on it:), with the file in hand; a picked file the same way.
  • No new handler rule, one more case of an existing one.

You added and picked C: a new Spell UI element, <ui-uploader folder multiple extensions upload={action}>, with a ui-upload event so something can catch the upload. The plan, changes, goal and files are rewritten around it; the Spell words for reading the picked file still wait on Q7.

  1. You picked C, your own option: a new Spell UI element, <ui-uploader>, that takes files someone picks or drops, and sends them on. Your comment on this phase (C2) then split its one upload action into two attributes, one for posting to a server and one for calling a Spell action.
    • The Spell words for reading a picked file still wait on Q7, so this phase builds the element and stops short of them.
  2. Its attributes, written as every Spell UI element's are (a vocabulary, a component, a sheet):
    • destination: a URL the picked or dropped files are posted to
    • action: a Spell action to call instead, with the files, as in action={read the netlist} in a drawing
    • extensions: the kinds it takes, a comma list (json, csv), read with the kit's commaList()
    • multiple: more than one file at a time
    • folder: picks or takes dropped folders instead of files, each folder's files with their paths in it
    • max-size: the largest file it takes, e.g. 2 MB (from your comment)
    • max-files: the most files it takes in one go (from your comment)
  3. What happens when files are picked or dropped, in this order:
    1. Files of a kind it doesn't take, too big, or past the count are turned away, each with its reason on its row.
    2. It sends ui-upload, holding the files it kept. It bubbles, so a handler anywhere up the page hears it. A handler that cancels it takes the upload, and nothing below happens. Same shape as the tree's ui-selecting.
    3. With action set, the action is called with the files.
    4. Else, with destination set, each file is posted there as form data, one request per file, so each row shows its own progress and its own failure. When a post ends it sends ui-uploaded (the server's answer) or ui-upload-failed (the error).
    5. With neither set, the files are only held: the element keeps and lists them, and ui-upload has still fired.
  4. Both set: action wins, as your comment's "instead" says, and nothing is posted.
    • The element logs one warning naming both, so a page that sets both by mistake finds out.
    • An action that wants to post too can do so itself.
  5. What it looks like (your question in C2), drawn as uploaders usually are:
    • a dashed drop area with a line of help ("Drop .json files here, or") and a Choose files button in it
    • under the help, the limits when set: "Up to 5 files, 2 MB each"
    • the area lights up while files are dragged over it
    • under the area, a list of the files: each row its name, size, a progress bar while it's posted, then a tick or the reason it failed, and an ✕ to remove it (or call off its post)
    • greyed while disabled, as every form control is
  6. Clashes with words Spell UI already uses (checked in Spell UI's English vocabularies):
    • A form's action: in plain HTML, a form's action is the URL it posts to, the job destination does here. Someone coming from HTML may write action="/upload" and expect a post. <ui-form> doesn't have one of its own, but the form inside it does.
    • <ui-input>'s action: an attribute and a slot for the buttons joined to a field (bare puts them after the field, left before it), a matter of looks. The uploader holds a <ui-input type="file"> inside, but its own action is a different element's.
    • <ui-action>'s action property: the action a menu item draws and runs. Close to this meaning, so no clash.
    • In Spell itself, "action" is the word for a method, which is what this attribute takes.
    • So: keep action, as you named it, and say in its docs that it is a Spell action, not a URL.
  7. Start from what exists (coherence):
    • <ui-input type="file"> already picks files; the uploader holds one inside, rather than a picker of its own
    • dropping uses the browser's own drag and drop; a dropped folder is walked for its files
    • posting goes through the kit's own request helper, so a failure has the same error shape as everywhere else
