No clever string parsing. Spell already keeps the words you call something by apart from the JavaScript name it calls. What's missing is only where a helper's words come from, and that's new wording for you to pick: Q9.

What existing code already decides:

  • A function's words and its code name are two separate fields. FizzBuzz's to play fizzbuzz is saved in its declarations as the words play fizzbuzz and the code name play_fizzbuzz. The call is matched by the words, then compiled to the code name.
  • So a helper's declaration can say the words read a netlist from (source) and the code name readNetlist. Nothing has to turn readNetlist into words or back.
  • The call rule is the one every Spell function call already uses (DynamicMethodRule). It's rebuilt from a declaration the same way for another project's functions, and it checks each input's type.
  • An options object is already a Spell shape. A to line ending in (with name) compiles to one last argument, an object, as in Spell's own tests: notify with message = "It worked!". That is exactly the shape of readNetlist(source, options).
  • Note: today's call says with name = "x", with an equals sign. Option A's example above, with name "x", left the sign out; dropping it would be new wording.
  • Reading the helper is the kit's one TypeScript reader (readTypeScript()): a real syntax tree, so each export's name, its inputs' names and types, what it gives back and the docstring above it are read, not guessed.

The real example, the handoff's helper:

/** Read `source`, a netlist file's text or its parsed JSON, into a `Netlist`. */
export function readNetlist(source: string | NetlistJSON, options: ReadOptions = {}): Netlist

New code, but no new wording:

  • Turning TypeScript types into Spell ones: string to text, number to number, a class the project declares (Netlist) to its Spell type (a netlist). A type with no Spell twin (NetlistJSON, a function) leaves that input unchecked.

New wording, which needs your OK (Q9):

  • Where each function's words come from. Made from its name, readNetlist becomes read netlist (source), which reads well. But otherEndOf(connection, port) becomes other end of (connection) (port): two inputs side by side, the kind of ambiguity you've been worried about. And a Spanish project would get no Spanish words at all.
  • So the recommendation is that each helper says its own words, in Spell's own to line shape.

So with this I could e.g. call DOM methods from spell somehow? How would that work? I'd set up a helper file in a library?

Yes. A helper is plain TypeScript, so it can do anything the browser can: focus a field, copy to the clipboard, measure an element. Spell calls it by its words, like any Spell function.

And yes, a library is a good home for DOM helpers. Spell's project imports already carry a library's functions into the project that imports it.

What Spell can do with the DOM today, without helpers:

  • Only what Spell has a statement for. Each statement compiles to one of Spell's own runtime methods, and that method touches the page.
  • scroll to the top compiles to core.scrollToTop(), which scrolls the app's element into view.
  • pause video "intro" compiles to core.pause(...); open printing opens the Print dialog for the app alone.
  • There's no general "call this JavaScript method" in Spell, and no way to name a thing's element. A Spell program talks to its things, and the page keeps each thing and its element agreeing by itself.
  • There are no Spell words for focus or the clipboard today. Those are exactly what a helper would add.

How a helper works, end to end. A small helper file, with Q9's option A for its words:

/**
 * Put `text` on the clipboard, as if the person had copied it.
 * - spell:  copy (text) to the clipboard
 * - spell es:  copiar (texto) al portapapeles
 * - NEVER throws:  a browser that refuses says so in the console
 */
export async function copyText(text: string): Promise<void> {
  await navigator.clipboard.writeText(text).catch((error) => console.error(error))
}

Where it sits, and how it's listed. Two places, both through the project file:

  • In the project itself: its project file lists the helper, as option A says.
  • In a library project: the LIBRARY's project file lists the helper. Any project that imports the library gets its functions, with the import line Spell already has for another project. 
// the library, owen@spell/browser-helpers:  its __project.json5
imports: [{ path: "/clipboard.ts", active: true }]

// a program using it:  its __project.json5, an import of another project, as today
imports: [{ path: "/Notes.spell", active: true }, { path: "owen@spell/browser-helpers" }]

// or just the one function, as today's imports already pick names
imports: [{ path: "owen@spell/browser-helpers", import: ["copyText"] }]

The Spell, and what it compiles to:

Spell:
  to share the note:
    copy the note's text to the clipboard

compiled JavaScript:
  import { copyText } from "@spell/project/owen@spell/browser-helpers"
  ...
  await copyText(note.text)
  • The import line at the top is how a library's names reach a program today. Each imported project's module is recorded with the names it provides (SpellDeclarations.load()).
  • The call itself is an ordinary Spell function call, matched by its words and compiled to the code name.

Reaching a thing's element. Most DOM helpers want an element, but Spell hands the helper a thing:

  • focus the first field of the form would hand focusFirstField(form) the form thing, not its <notes-form> element.
  • The page can go from an element to its thing (SpellElement.thingOf()), and Spell's runtime knows the id it gave a thing's element (core.elementIdFor()).
  • But nothing hands a helper the element itself. A helper would need a small runtime call for that, say core.elementOf(thing). That's new, and not in P10's plan yet. 
import { core } from "spell/parser/core"

/**
 * Put the cursor in `view`'s first field it can type in.
 * - spell:  focus the first field of (view)
 * - Nothing to focus, or not drawn yet:  nothing happens
 */
export function focusFirstField(view: object): void {
  const element = core.elementOf(view)     // NEW:  not in core today
  element?.querySelector<HTMLElement>("input, textarea, ui-input")?.focus()
}

  • A helper uses the project's own classes, not a second copy.
