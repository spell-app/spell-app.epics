No clever string parsing. Spell already keeps the words you call something by apart from the JavaScript name it calls. What's missing is only where a helper's words come from, and that's new wording for you to pick: Q9.

What existing code already decides:

  • A function's words and its code name are two separate fields. FizzBuzz's to play fizzbuzz is saved in its declarations as the words play fizzbuzz and the code name play_fizzbuzz. The call is matched by the words, then compiled to the code name.
  • So a helper's declaration can say the words read a netlist from (source) and the code name readNetlist. Nothing has to turn readNetlist into words or back.
  • The call rule is the one every Spell function call already uses (DynamicMethodRule). It's rebuilt from a declaration the same way for another project's functions, and it checks each input's type.
  • An options object is already a Spell shape. A to line ending in (with name) compiles to one last argument, an object, as in Spell's own tests: notify with message = "It worked!". That is exactly the shape of readNetlist(source, options).
  • Note: today's call says with name = "x", with an equals sign. Option A's example above, with name "x", left the sign out; dropping it would be new wording.
  • Reading the helper is the kit's one TypeScript reader (readTypeScript()): a real syntax tree, so each export's name, its inputs' names and types, what it gives back and the docstring above it are read, not guessed.

Yes. A helper is plain TypeScript, so it can do anything the browser can: focus a field, copy to the clipboard, measure an element. Spell calls it by its words, like any Spell function.

And yes, a library is a good home for DOM helpers. Spell's project imports already carry a library's functions into the project that imports it.

What Spell can do with the DOM today, without helpers:

  • Only what Spell has a statement for. Each statement compiles to one of Spell's own runtime methods, and that method touches the page.
  • scroll to the top compiles to core.scrollToTop(), which scrolls the app's element into view.
  • pause video "intro" compiles to core.pause(...); open printing opens the Print dialog for the app alone.
  • There's no general "call this JavaScript method" in Spell, and no way to name a thing's element. A Spell program talks to its things, and the page keeps each thing and its element agreeing by itself.
  • There are no Spell words for focus or the clipboard today. Those are exactly what a helper would add.

How a helper works, end to end. A small helper file, with Q9's option A for its words:

/**
 * Put `text` on the clipboard, as if the person had copied it.
 * - spell:  copy (text) to the clipboard
 * - spell es:  copiar (texto) al portapapeles
 * - NEVER throws:  a browser that refuses says so in the console
 */
export async function copyText(text: string): Promise<void> {
  await navigator.clipboard.writeText(text).catch((error) => console.error(error))
}

  • In the project itself: its project file lists the helper, as option A says.

No, the other way round. core.elementOf(thing) would start from a thing the program already has, and find the element that draws it. It wouldn't walk up the page from an element looking for a thing.

How things and their elements are linked today:

  • Element to thing: every view's element keeps its component, and the component keeps the thing it draws. SpellElement.thingOf(element) reads it. Dragging uses it to know which card was picked up.
  • Thing to id: core.elementIdFor(thing) gives the id the thing's element takes, its name, like queen-of-spades. The element sets that id on itself when it's handed the thing.
  • Id to thing: core.thingFor(Class, id) finds the thing a tag in a page's layout names, as <solitaire-tableau id="T1"> finds tableau T1.
  • Thing to tag name, not element: core.elementFor(thing) answers "solitaire-card", the TAG its class draws as. Despite the name, it hands back no element.
  • Name to element: the runtime can already find a drawn element by its id, looking inside each view's own shadow root too. That's how show "you won" finds the element with id you-won (drawnNamed(), private to that file). 
// app/src/app/runner/SpellElement.tsx:  element => thing
static thingOf(element: Element): object | undefined {
  return (element as Element & { component?: SpellElement }).component?.currentThing
}

// SpellElement.nameAfterHandedThing():  each view's element takes its thing's id
const thing = this.handedThing
return thing && this.entry?.core.elementIdFor(thing)     // then element.id = id

// parser/src/core/ui.ts:  an id => the element, inside every view's shadow root too
function drawnNamed(name: string): Element | undefined {
  const id = drawnIdOf(name)
  const roots: Array<Document | ShadowRoot> = [core.domRoot()]
  for (const root of roots) {
    const found = root.getElementById(id)
    if (found) return found
    for (const element of root.querySelectorAll("*")) if (element.shadowRoot) roots.push(element.shadowRoot)
  }
  return undefined
}

What core.elementOf(thing) would be, put together from those:

  • Ask core.elementIdFor(thing) for its id, then find that id the way drawnNamed() does.
  • Or keep a weak map, thing to element, filled as each view's element is handed its thing. Faster, and it works for a thing with no name, which has no id.
  • A catch either way: one thing can be drawn twice, say the same card in a list and in a detail panel. Then it has two elements. Picking "the first drawn" is the simple answer; a helper that cares could ask for all of them. 
/** The element drawing `thing` now -- the first, if it's drawn more than once;  `undefined` if it isn't drawn. */
elementOf(thing: unknown): Element | undefined {
  const id = core.elementIdFor(thing)
  return id ? drawnWithId(id) : undefined        // drawnNamed()'s search, by the id itself
}

A walk up the page to the nearest thing of a type: nothing in the runtime does that today.

  • The only upward walks are the editor's own: a view checks whether it sits inside a <spell-viewer>, and the right-click menu climbs through shadow roots to collect the menus around what was clicked (SpellElement.programMenuOf()).
  • A helper would want that walk only when it's handed an ELEMENT and needs the thing around it, say a click handler asking "which form is this button in?". Spell code never hands a helper an element, only things, so P10 doesn't need it.
  • If a case comes up, it's small: climb with thingOf() at each step until a thing of the type turns up.
  • no change to P10's plan from this: core.elementOf(thing) stays a thing-to-element lookup, still not in P10's plan, as before
  • its sketch: the thing's id, then the runtime's existing search by id, first element if it's drawn twice
  • no "nearest thing of a type" walk is planned: nothing hands a helper an element
