how do we know the spell for the methods, clever string parsing?

No clever string parsing. Spell already keeps the words you call something by apart from the JavaScript name it calls. What's missing is only where a helper's words come from, and that's new wording for you to pick: Q9.

What existing code already decides:

  • A function's words and its code name are two separate fields. FizzBuzz's to play fizzbuzz is saved in its declarations as the words play fizzbuzz and the code name play_fizzbuzz. The call is matched by the words, then compiled to the code name.
  • So a helper's declaration can say the words read a netlist from (source) and the code name readNetlist. Nothing has to turn readNetlist into words or back.
  • The call rule is the one every Spell function call already uses (DynamicMethodRule). It's rebuilt from a declaration the same way for another project's functions, and it checks each input's type.
  • An options object is already a Spell shape. A to line ending in (with name) compiles to one last argument, an object, as in Spell's own tests: notify with message = "It worked!". That is exactly the shape of readNetlist(source, options).
  • Note: today's call says with name = "x", with an equals sign. Option A's example above, with name "x", left the sign out; dropping it would be new wording.
  • Reading the helper is the kit's one TypeScript reader (readTypeScript()): a real syntax tree, so each export's name, its inputs' names and types, what it gives back and the docstring above it are read, not guessed.

The real example, the handoff's helper:

/** Read `source`, a netlist file's text or its parsed JSON, into a `Netlist`. */
export function readNetlist(source: string | NetlistJSON, options: ReadOptions = {}): Netlist

  words (Q9 decides where these come from):
                read a netlist from {source} (with {name ...})?
  code name:    readNetlist
  inputs:       source as text, then the options object (its "name" a text)
  gives back:   a netlist     (the type Netlists.spell declares)

  Spell:        set the netlist to read a netlist from the text with name = "ssx001"
  compiles to:  netlist = readNetlist(text, { name: "ssx001" })

New code, but no new wording:

  • Turning TypeScript types into Spell ones: string to text, number to number, a class the project declares (Netlist) to its Spell type (a netlist). A type with no Spell twin (NetlistJSON, a function) leaves that input unchecked.

New wording, which needs your OK (Q9):

  • Where each function's words come from. Made from its name, readNetlist becomes read netlist (source), which reads well. But otherEndOf(connection, port) becomes other end of (connection) (port): two inputs side by side, the kind of ambiguity you've been worried about. And a Spanish project would get no Spanish words at all.
  • So the recommendation is that each helper says its own words, in Spell's own to line shape.
  • A Spell page calls readNetlist()-style helpers
  • No options.classes workaround: one copy of the classes

A project can import a helper file and call its functions from Spell; the library target and the page share one copy of the project's classes.

  • A new statement to design and translate.
  1. The skip the paste found is SpellProject.activeImports (coherence): a project lists .js files, but its imports leave them out. That's where a helper file gets in.
  2. No new kind of import (coherence): a helper file becomes a DeclarationsImport, the import Spell already has for code it calls but doesn't compile.
    • its exported functions become SpellDeclarationsData, so Spell code can call them by name
    • its module is the helper's own address, reached through the import scope's modules (P.ImportScope.modules)
    • how a project names its helpers is this phase's choice
  3. Where the declarations come from: in node, read from the TypeScript with readTypeScript(); in the editor, from a compiled .d.ts or a list in the project file.
  4. One copy of the classes: the helper imports the project's classes from the running program, not from its own .lib.ts copy, so the handoff's options.classes workaround goes.
  5. Rules, core and the editor's runner as needed; the TypeScript and Python targets say plainly what they don't support.
  6. Checked by: parser's rule tests; an app test running a project whose Spell calls a helper that makes the project's own objects. The helper is modelled on the handoff's netlistReader.ts, on a small made-up wiring list.
  7. Left out: JSON and object-walking words in Spell itself.
