Reference pages: made from their source, edited for clarity

How a reference page is made from its source, and how you make its words clearer so your edits survive the next time it's made: one worked example first, then seven choices.

session data, while planning its Reference Pages phase 2026-11-18
data -- Spell's places, the back-ends a program reads and writes. The place reference was built as a page in the editor. You said: "This is fine for now, but I'd like to be able to edit these docs for clarity ... We're going to want other reference pages like this (e.g. language reference, app reference) so we'll put a lot of thought into its creation." That is the Reference Pages phase. The design of every reference page, before anything is built. The place reference stays as it is until then. Spell already has most of the parts, in several shapes: each choice picks one, rather than adding another.

Today

  • The ingest writes two files for a place: NetBox.api.spell, its Spell, and NetBox.api.json5, what it found (routes, types, fields, what was verified).
  • The editor's Data tab has a Reference link, which opens a page in the editor drawn from the .api.json5 each time.
  • Every word on it is made by the ingest. There's nowhere to write a clearer one.

Editing one

  1. On the reference page, you hold ⌥ and click "pending, running, completed ...", as on any docs page today.
  2. It opens as text; you rewrite it and press ⌘-Enter.
  3. It's saved into the comment on that line of NetBox.api.spell, the same edit the editor makes when you change a description.

When the ingest runs again

  • Unchanged lines keep your comments: the ingest already merges its new Spell into the old, line by line, keeping what a person wrote.
  • A field renamed (status to state): your comment can't follow by itself. The ingest says so, as it already does for a line a program still uses.
  • A list gone from the API: its comment has nothing left to explain, and the check lists it.
