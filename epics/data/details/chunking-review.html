Five things I found that change the conversation:

  1. Two of the three borrowed ideas are in. The writer already chooses a thing's id, and a folder already refuses a write made from an old version.
  2. owen@spell names nobody in particular yet. Every machine's one person is called that, so until there's sign-in, the same address on Matt's laptop is Matt's own folder.
  3. The database folder has a name waiting. __data is on spaces' list of reserved names, and nothing in a space uses it.
  4. An old note of ours is out of date. We wrote that everything on AT Protocol is public, but since August 20, 2026, its "Spaces" alpha can hold non-public data, by account, not encrypted: its authors say not to run production on it, and its name is confusingly the same as ours.
  5. AT Protocol's version check is only half confirmed. Its published definition lists the refusal we handle, but no real write has been tried yet (M3).

What you see in the address is where the files are, so data can sit beside a program and live in its git. Its cost: a program's folder and its data can mix.

  • A data folder's files don't join a project: only code, style and editor-page files do.
  • Today's address rules read a name with no dot and no end slash as a page of a running app. Saying "a data folder at" tells them apart, so those rules needn't change.
  • It uses your words: "<owen>@<space>". The README calls that whole thing the space, and spell the org: worth one word in the end.

Data can never touch a program's files. Its cost: the address isn't where the files really are, and data can't travel with a project.

  • A full address is a path from the top of that space.
  • The next question, on who can read, is answered by whose space it's in, not by the path.
