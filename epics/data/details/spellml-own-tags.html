spellml's own tags: the spell- prefix, and property editors in a file of their own

Should spellml's three "note" tags take the spell- prefix, so they never hide a Spell UI element; and should a type's property editor move out of its .spellml file?

You suggested <spell-comment>, <spell-description>, and asked for Solitaire before and after. what three tag names are in every language, and where a type's Inspector layout lives.

spellml has three NOTE tags: text Spell keeps but never runs.

  • <description> and <comment>: prose about the type.
  • <property-editor>: the type's own layout for its Inspector card.
  • Directly in a drawing (or an <if> / <for> in one), spellml takes them. Inside other markup (a <content>, a <ui-comments>), they're Spell UI's parts, as you'd expect.
  • So the trap is only at a drawing's top level, but nothing warns: the drawing is quietly empty.

What it costs: smaller than I said in chat

  • I said 197 <description> tags would need renaming. Wrong: every one of them is Spell UI's part, inside markup (<content><description>...), and stays as it is.
  • Notes are written as ATTRIBUTES today (description="..."), never as tags: no file in the examples, notebooks or tests uses <description> or <comment> as a note.
  • The one note tag in use: Solitaire's <property-editor>, once.

Do the three note tags become <spell-description>, <spell-comment>, <spell-property-editor>, freeing the short names for Spell UI everywhere?

One rule: a tag that is spellml's and NOT structure carries the prefix, as templates do. <if>, <for>, <loading> ... stay short, with a check that fails if a Spell UI element ever takes one of their words. Cost: the words lists (en, es), one line in Solitaire, the docs, tests; an old short note warns for a while.

The two that clash with Spell UI elements today; <description> stays, though <ui-description> is a Spell UI part too.

A message when a note directly in a drawing holds markup, pointing to <ui-comment>. No rename; the trap stays, but it's loud.

Where does a type's Inspector layout live, once it moves out of Card.spellml?

Today there are TWO ways to write one, and they don't know about each other:

  • inline, the <property-editor> above: the Inspector reads it from the source
  • a property editor PAGE, Card.editor.html, made by the editor's New Property Editor...: a full page around a <ui-property-editor>, which the Inspector doesn't read

One way: Card.editor.html holds the type's layout, and the Inspector reads it (the page's <ui-property-group>s, as it reads the inline note today). The inline note goes, and with it <spell-property-editor>: Q1 is then about two tags. New Property Editor... already writes the file.

  • Plain markup, never compiled: edited rarely, as you said.
  • Cost: the Inspector's reader points at the page; Solitaire's layout moves to Card.editor.html; the colouring for the inline note goes.

Card.editor.spellml: <spell-more-of "card"><spell-property-editor>..., as P27's API files add to a type from another file. Stays Spell, with its colouring; but two ways remain (this and the page).

Solitaire.editors.spellml, a <spell-property-editor "card"> per type. Fewer files; further from the type it describes.
