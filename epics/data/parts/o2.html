One correction to the kickoff

The kickoff describes fate as gathering each part's needs and sending them to a coordinator at the app level, which should be easy for a compiler. fate has no compiler, and the docs read name no "coordinator", only a single request at the root, batched. So inferring what a page needs isn't copying fate: it would be new (1.5).

Ideas taken

  • The compiler works out what each part reads, so nobody writes a view.
  • Objects are cached by type and id, so one edit shows everywhere with no invalidation.
  • Back-ends have a small required core, optional features and written fallbacks.
  • The back-end says what it handled, and the engine visibly does the rest.
  • Results say what they know, so "none found" never shows until the answer is complete.
  • One action runs on both sides: a local overlay, and a call to the back-end.
  • A read lasts as long as the part showing it: the last reader leaving aborts it.
  • Polling is the fallback for live updates, on any back-end.

Traps

  • A silent fallback that downloads everything, because uniform words hide the cost.
  • A language shaped like one database, with per-client state on the server.
  • Assuming identity: sheets, CSV and files have no reliable id.
  • Treating cancelling as undoing: a write already sent can only be reconciled.
  • Optimistic writes past one click, before the simple case is solid.

What lay tools teach

  • Scratch's cloud variable is the model: the same blocks, with one changed declaration.
  • AppleScript's filter works on some lists and not others, which is what local-feels-like-server must never do.
  • HyperCard needed no save command, at the price of needing a real undo. Spell has one.
  • Excel's cell shows "Loading…" in place, while Retool's people wire a loading flag by hand.
  • SQL shows that looking like English doesn't make a thing friendly to laypeople.
