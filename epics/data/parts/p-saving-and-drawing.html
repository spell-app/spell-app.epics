  2. T5: a page out of date is asked to reload
    • The page says its program's version when it connects to a room.
    • The referee refuses a page from an older version, and that page shows a notice with a Reload button (Referee, LiveRoomPlace).
    • Changes not yet sent stay kept on this device, so they go out after the reload.
  3. T29: an optimistic update on every named action
    • Every named action shows at once, and rolls back if the referee refuses.
    • It's the same action both times: the function the referee runs (a RoomAction) only reads rows and says what to change, so the page runs it first, against its own copy of the room.
    • What it says to change goes in as one held group, as an action's changes already do (PendingChanges): shown at once, ready to be dropped.
    • Then the referee runs it, in the one order. Its answer settles the group: it's made once, however it arrives.
    • If it's refused, the group is dropped, what it changed goes back, and the existing refusal notice shows.
    • An action the page has no code for waits for the referee, as today.
    • Checked with the last seat: two pages press at once, one sees it taken, the other sees it un-take and the notice.
  4. T57: created and modified, on by default
    • What you'll write: nothing. Every type with a place has its created and its modified, dates, Spanish su creado and su modificado.
    • What compiles differently: the compiler (TypeScope, JSWriter) gives every saved type those two date properties, and says so in the type's compiled savedIn. The rows stay named created and modified in every language.
    • It's the same for a type written yesterday: a type's compiled form comes from its lines, so every saved type has them the next time it compiles. Each example's snapshot changes with it.
    • Turning them off: a line under the type, - it keeps no times, Spanish - no guarda fechas.
    • Stamped when it's saved, by Spell: created once, when a thing is first saved; modified each time a change goes out, with its other changes (places, the core's write path). A draft is stamped when it's saved, not per keystroke.
    • A stamp is never a clash, never an undo step, and doesn't tell the program "it changed": it isn't a change anybody made.
    • A server's own field wins: no second stamp. A type that declares its own created or modified keeps it, as Star Wars' its "created" is a date does, and Open Library's created, which isn't a date. A server's differently named field uses the line that already names a field: - an issue's created is its "created at". Spell reads that field, and never writes it.
    • Where Spell doesn't stamp: web servers and GraphQL (the server decides what it keeps, and may refuse a field it doesn't know), and sheets, CSV, Excel and Airtable unless that column exists (each refuses a field with no column today, and adding one would rewrite someone's file). Each stamp is sent only where the place says it can hold it, a new answer in its describe().
    • Rows saved before this: keep working, with nothing to migrate. its created is simply empty, nothing is made up, and it never gets filled in. newest first reads created; a thing with none sorts last, in the order it had, on both the core's sort and a place's own (rowsInOrder()). The next change to an old thing stamps modified only.
    • Python's core: the same in this phase, so the two cores stay twins: a compiled saved type gets the two properties; places.py stamps created in add() and modified on a change, as ISO text, and honours - it keeps no times; both read the shared saved-row fixture. Python has no live rooms, so T29 and T5 have nothing to do there.
    • Checked: a stamp on a new thing and on a change; an old row with none, kept and sorted last; a draft; off with the line; a server's own field unstamped; a sheet with no column left alone.
