Needs: an Airtable account (the free plan is enough for this test, but it stops at 1,000 requests a month, and each poll is one, so stop the servers when you're done). This costs a few hundred requests at most.

  1. In a browser, at airtable.com, make a new base. Name its table Recipes, with these columns, spelled exactly: Spell id (single line text), Title (single line text), Cuisine (single line text), Servings (number), Notes (long text), and Note length (formula: LEN({Notes})). Add one row by hand with a title, and nothing in Spell id.
  2. Copy the base's id from its address: the part starting app.
  3. At airtable.com/create/tokens, make a personal access token, with the scopes data.records:read, data.records:write and schema.bases:read, and that base added to it. Copy it.
  4. Press Stop on the demo page if its servers are running. In VS Code, in window ⎇ data, menu Terminal, New Terminal, run, with your two in place of the capitals: 
    AIRTABLE_BASE=appYOURBASE AIRTABLE_KEY=patYOURTOKEN yarn tsx scripts/recipe-servers.ts
    It should print your Airtable base appYOURBASE is on /api/places/airtable.
  5. In the same window, in a second terminal, run 
    spell server url
    then in Chrome open that address followed by /guides/data/experiments/recipe-box/recipe-box.html?back-end=airtable. Press Command-Option-I for its network tab.
  6. Your hand-made row shows. In the demo, add a recipe, then change its title.
  7. In Airtable, change that recipe's title; clear another row's Notes; add a row. Wait 10 seconds.
  8. Have the same recipe open in the demo and in Airtable, and change one title in both, within a second or two.
  9. In the demo's network tab, filter by pat. Then, in the terminal: 
    curl -s -X PATCH "https://api.airtable.com/v0/appYOURBASE/Recipes" -H "Authorization: Bearer patYOURTOKEN" -H "Content-Type: application/json" -d '{"records":[{"id":"recNOPENOPENOPENO","fields":{"Title":"x"}}]}'
curl -s -X PATCH "https://api.airtable.com/v0/appYOURBASE/Recipes" -H "Authorization: Bearer patYOURTOKEN" -H "Content-Type: application/json" -d '{"records":[{"id":"recA_REAL_RECORD_ID","fields":{"Note length":3}}]}'
    with a real record's id, from its row's expanded address, in the second. Keep what each answers.
  10. Stop the servers with Ctrl-C in their terminal, and revoke the token if you won't use it again.
  • Your hand-made row shows, and can be changed: its Spell id stays empty.
  • A recipe added in the demo has a new row in Airtable, with an id in Spell id.
  • Each edit reaches the other side within about 10 seconds, the cleared notes clear in the demo, and the new row appears.
  • The two title edits end as whichever saved last, the same on both sides, and nobody is told.
  • The network filter finds nothing: the page never holds the token.
  • The servers' terminal shows no 429.

Paste what the two curl commands answered, whichever way this goes: the stub guesses both (ROW_DOES_NOT_EXIST, and a message with "computed" in it). The place finds a refused field by those words, so a different wording means a change there. Also say which edit didn't arrive, and what the terminal printed.

In a browser, open the recipe box demo, with a personal access token in the place server's environment and the one line pointing at your base, using the commands this phase's notes give. Edit one record in Airtable, and another in the demo.

Each edit reaches the other side within about 10 seconds, and the browser's network log never shows the token.
