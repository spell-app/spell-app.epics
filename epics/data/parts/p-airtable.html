Airtable is a natural home for this kind of data, but its key can't reach a browser and all its users share 5 requests a second per base.

  • Airtable is one of the seven back-ends.
  • Its key stays on the server side, named and never written in the program.
  • Many open tabs share one poll, and the queue never trips the 5-a-second limit.
  • Computed fields read as read only, and Spell's own id column lets browser-made ids work.
  • Try it: point the demo's one line at a base of your own, and edit in both the demo and Airtable.
  • An Airtable place, behind the place server only.
  • One shared poll and a queue that stays under the limit.
  1. AirtablePlace: field names and formula filters, pages of 100, batches of 10, saving per field and matching on an id column.
  2. RateQueue: one queue per base, one shared poll that passes changes on to every browser.
  3. A new child record links to one parent, which avoids the lost link the survey warned about.
  4. Checked by: tests for the limit under many tabs, a 429's 30-second wait, a computed field refused, and paging restarting.
  5. Left out: webhooks, since polling works with no public address; running every save through a referee, which The Referee makes possible; per-person rules.
