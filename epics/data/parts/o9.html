The editor's side bar shows values that come from data, and epic editor asked three things of this epic (request r1). All three fit the Overview, but nothing here is built.

  • Already decided: Owen's two side-bar behaviours (), live editing (Q9), and writes sent when an action ends (Q8).
  • Proposed here: everything else in this section, the word "sample" and the shape of each call.
  • Order: the phases will carry all three once they're written (Q12).

1. Swapping in a sample

Yes: a SAMPLE is one more place behind the same interface, swapped in while designing, and the line that declares the real place doesn't change. 

## Still in the program, untouched, with a sample in use
family cookbook is a web service at "https://api.example.com/v1"
## The side bar shows:  family cookbook · Using a sample
  • The word: "sample" is free in Spell's words, the catalog and the parser's rules. People only see it in the side bar, so the language gains no word.
  • Where its records live: in a design-time setting of the project, never a line of the program. A built app leaves it out, so it can't ship.
  • Its first records: a few from the real place when it can be reached, else made from the type.
  • Real data stays local: records copied from a real place stay out of git (J2).
  • Writing: a sample is always writable, whatever the real place allows, and never touches it.
  • Work: the Places engine holds the swap; the editor draws its switch.

2. Asking where a value came from

The editor asks about a thing and one property, because whether a value can be changed can differ by field (Airtable) and by owner (AT Protocol). 

Places.originOf(recipe, "title")
// A saved value:
{
  place: "family cookbook", kind: "web service", collection: "recipes", id: "r-12",
  canWrite: false, whyNot: "owner",   // or "place", "field"
  isSample: false,
  declaredAt: { path: "RecipeBox.spell", start: 412, end: 470 }
}

Places.originOf(recipeBox, "matches")
// A worked-out value has no one place:
{
  workedOut: true, canWrite: false,
  readsFrom: ["family cookbook"],
  declaredAt: { path: "RecipeBox.spell", start: 588, end: 660 }
}
// Not from any place, such as the app's own search:  undefined
  • A worked-out value: it answers read only, with the places it read and the line that works it out. The reactive cells already record who read what.
  • Which line: no run-time call gives this today.
    • The compiler knows each declaration's file and characters (DeclaredAt).
    • The language server's definition lookup needs a position in a file, not a running value.
    • The run-time property info holds no source place, and SourceMarks maps statements for debuggers.
    • So the compiler would write it down for each saved type and property, in design builds only (J3).
  • A hint, not a promise: canWrite says what's known, and a place can still refuse.
  • Work: the Places engine answers the place and writability; the compiler's gathering pass supplies the line.

3. The path a write takes

A side-bar edit of a data value is a plain set of the property, the program's own path. It isn't a source edit, because the program's text only says where the data lives.

  1. The editor sets the property inside one undoable step, titled for the field.
  2. The set reaches noteSetting(), the one place every property write is already noted. The undo history records it there.
  3. The Places engine would hear of it at that same point, as a pending change (not built).
  4. The step ends when the edit does, so the change goes out then, under Q8 (J4).
  5. ⌘Z undoes it as one step: unsent, it's dropped; sent, a reversing change goes out.
  • A read-only value: the field is read only and names its place and why, with a link to the declaring line and an offer to use a sample.
  • If the place refuses anyway: the value heals back to the place's copy, with a notice.
  • A sample: the same path, ending at the sample's records.
  • Work: the Places engine.
