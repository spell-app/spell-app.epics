Chose read, change and write in one synchronous step under FileLock over an async read and a retry on the file's version, because nothing can get in between, in one process or two, and the demo's REST server, which can't wait, shares it. The cost: a save blocks the server for the length of that one file, and a second process holding the lock blocks it until it lets go. A lock held across an await by the same process would stall it, so nothing else here may hold this file's lock asynchronously.
