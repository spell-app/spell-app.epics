"compiled reads are plain synchronous getters" -- "what is this?"

It's about the JavaScript a Spell program compiles to, and why an action can't wait for a read that nothing else has started.

  • A getter is what a property compiles to: code that runs each time something reads the property. Family Cookbook's its "title" is text becomes get title(), and a property worked out from the place, its matches, becomes get matches().
  • Synchronous means it hands back a value at once, with no await. The code that reads it never pauses for the server. 
export class Recipe extends Thing {
  get title() { return this.getProp("title") }
}

  get matches() { return core.waitedValue(this, "matches", async () => {
    return core.sortedBy(core.filter(await core.savedThings(Recipe, {}, "looks through"), ...), ...)
  }, () => [this.search]) }
  • get matches() can't wait itself, so core.waitedValue() starts the read in the background and hands back what it has now: an empty list the first time. When the server answers, it keeps the rows, and everything drawn from matches draws again.
  • For the page that's fine: it shows "loading", then the rows.
  • For an action it isn't. If show the first of the matches runs before anything on the page has read matches, the action gets the empty list, the default, and goes on with it. Nothing tells it to wait.

Why it's T42's limit, not fixed: the only way to make the action wait would be to stop it when it reads a value not there yet, then run it again from the start once the answer comes. But that runs again whatever the action did before the read, such as a save or a notice, twice. P43's plan allowed leaving it out.

In practice it rarely bites: a field the page shows has been read before anyone can press a button. It only hits an action reading a field nothing on the page shows.
