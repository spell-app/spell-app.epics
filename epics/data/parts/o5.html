Spell can work out what each part of a page reads, so a page asks for everything it needs in one trip, with nobody listing fields.

Here Spell would go further than fate, whose authors write every field out, and than Relay, whose compiler only joins what authors wrote. None of this is prototyped.

At compile time

  • A pass walks each type's draw, follows its getters and draw its habits to the item type, and notes each property read.
  • It would sit in the same whole-project step as epic language's waiting pass (WriterProject), so the real pass follows that one, as the Spell words do.
  • Imported projects already carry facts by their declarations, so what a library's draw reads could cross over the same way.
  • A part behind a disclosure could load when it opens, as fate's defer does.

What it can't see

  • draw it on a list of mixed types: a sub-type's draw decides. It can join by name, which over-fetches.
  • Form fields named by a string (name="done"), read by Spell UI at run time.
  • Custom elements and hand-written library code.
  • Reads through a local or an argument need the writer's knowledge of its kind.

Fetching too much is safe, so a read it can't prove widens to the whole thing, with a compile note.

At run time

  • Reactive cells already record who read what, on every read.
  • So a first draw could discover what it needs, one missing field at a time. That's always right, and slow on a first load.
  • Spell uses both: compile-time gathering is the one-trip speed-up, and run-time recording catches what it missed.

Whether the static pass finds enough on real projects is unknown until it's tried. So a prototype measures it on the built-in projects before the real pass is built, and what it finds decides how much the run-time half matters.
