A one-of-a-kind app's variable (pokedex, from <spell-app "pokedex">), and any top-level variable, is declared in its file's own scope: a later file says "Don't understand". Types and methods are stubbed for the whole project; variables aren't (FileScope owns only variables, PARSING.md).

The compiled program is one module, so it would run.

PokéSpell works around it: its other files call free functions its app file defines (to hear (a pokemon), to pick (a type), to guess (a pokemon)), and the app draws the cry itself. Not fixed: a project-wide variable needs the root scope to hold variables, and the incremental parse to stub them.

options? Is this a spell thing, or a package.json thing?

It's a Spell thing: the parser keeps every top-level variable in its own file's scope. The project's settings file only lists the files, and changing it can't fix this.

Why another file can't say the hearing of the pokedex

  • Each file of a project is read with a scope of its own, a FILE scope, and every file scope hangs off the ONE project scope.
    • A name looked up in a file is looked for in its own file, then the project, then the language's built-ins.
    • It's never looked for in the file before it: the files sit side by side, not one inside the next.
  • CreateOneOfAKind, which reads <spell-app "pokedex">, puts the app's one variable, pokedex, into the scope of the line that declared it: that file's.
  • Types, methods and properties are different:
    • the project knows them all before any file is read, from a quick scan of every file
    • so a later file, or a line above the declaration, can name a type or call a method
    • variables get no such scan, and no place in the project to live
  • The compiled program doesn't care: every file goes into ONE module, so export const pokedex = new Pokedex() would be in reach of every file's code. The parser is the only thing saying no.

What the project's settings file does, and doesn't

  • Its imports list (the "package.json thing") names which files are in the project, and the order they're read and written out in.
  • It says nothing about which file sees which names.
  • Putting the app's file first wouldn't help: the later files still look in the project, not in the app's file.
  • PokéSpell lists its app file last only so its start the pokedex runs after everything else.

How PokéSpell gets round it

  • Its app file defines four free functions, to pick (a type), to hear (a pokemon), to guess (a pokemon), to open (a pokemon), which reach into the pokedex.
  • Free functions ARE project-wide, so the card and the guessing game call those instead.
  • It works, but it's a go-between every multi-file app would have to write.

/**
 * `FileScope` -- a scope which encapsulates a discrete file.
 *  - `methods` (from BlockScope) are methods defined at the root of the file.
 *  - `variables` (from BlockScope) are variables defined at the root of the file.
 */
export class FileScope extends BlockScope {}

/**
 * A `ProjectScope` manages a set of `FileScope`s.
 *
 * Like `RootScope`, it manages `.rules`, `.types` and `.constants`
 * for things that are defined in the project.
 */
export class ProjectScope extends RootScope {}   // RootScope extends BlockScope:  it HAS variables, unused
 
  stubDeclaredTypes(scope: P.Scope, texts: string[]): string[] {
    return this.inPlay(() => {
      const names = texts.flatMap((text) => this.declaredTypes(text, scope))
      const lang = this.inflector?.lang
      for (const name of names) if (!scope.types?.get(name)) scope.types?.add({ name, stub: true, lang })
      return names
    })
  }
 
# What a Pokémon or a kind can do, from anywhere
Only this file can name the pokedex:  so its other files ask these.

<spell>
	to pick (a type):
		set the picked kind of the pokedex to it
		set the showing of the pokedex to nothing

	to hear (a pokemon):
		set the hearing of the pokedex to nothing
		pause for 50 msec
		set the hearing of the pokedex to it
	...
</spell>

The options

  • pokedex goes into the project's scope instead of its file's: every file can say the hearing of the pokedex.
  • The scan that already finds pokedex as a type, before any file is read, adds its variable too: so a file read before the app's knows it.
  • Plain set x to 3 at a file's top stays private to its file.
  • One catch: a TOP-LEVEL line in an earlier file that reads the pokedex would run before it exists. The parser says so ("say it inside an action"), as a run-time crash would otherwise. Inside actions and drawings it just works.
  • Cost: small. Two parser files (the one-of-a-kind rule, the scan), the incremental parse's journal, and tests; PokéSpell's four go-betweens can then go, or stay as nice verbs.
  • Why recommended: an app is one of a kind by definition, so there's no clash to worry about.
  • Any set score to 0 at a file's top is seen by every file, as in one big script.
  • Needs a new scan for every set ... to line at a file's top, ahead of parsing.
  • Two files using the same name quietly share one variable: a surprise, and a hard one to find.
  • The "read before it exists" catch from A, on every variable, not just the app.
  • Cost: larger, and it takes away a file's own private names.
  • A line like share the pokedex, or a shares list in the project's settings file: the "package.json" way, as JavaScript's export does.
  • Anything can be shared, not only apps.
  • Cost: new syntax or a new setting, in two languages, and one more thing a kid has to know to write.
  • For the app it buys nothing over A: it's already the only one.
  • Keep the go-between functions; write the rule down in the parsing notes and the guide.
  • Cost: none now; every multi-file app pays it later.

  • other top-level variables stay private to their file
