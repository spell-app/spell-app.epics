Epic pages show that a list of summaries with bodies fetched on open works well, but nothing else can use the idea, and no program can reach a folder.

  • Chunked files: a list of summaries works with no bodies loaded, and each body comes when it's read, from static hosting and no server of ours.
  • A folder and one file also work as places, with changes heard from the disk.
  • A browser reaches a folder through one small server side, which also holds keys.
  • Try it: in the recipe box demo, change the one line to a folder, then open a recipe file in VS Code, edit it, and watch the page follow.
  • A folder place: a list file, and one file per thing, fetched when needed.
  • A small place server, which any place needing a server side runs behind.
  1. ChunkedPlace: shaped after EpicParts and LoadableBody, without importing them, because the arrow would point up and they hold HTML, not things (J8).
  2. FolderPlace: on an object shaped like SpaceStorage, so the app's disk storage fits as it stands, plus the one-file place (J6).
  3. PlaceServer: serves any place over HTTP on the kit's router, holds its named keys, and refuses to answer them. A browser-side RemotePlace speaks to it (J9).
  4. Versions through the file operations' existing conflict check, and changes through the storage's watch.
  5. Checked by: tests for no bodies fetched, a conflict, a change heard, a key never reaching a browser, and a small adapter reading a real epic page's items.
  6. Left out: moving epic pages onto this, which nobody asked for; writing chunked files from a browser with no server.
