Spell can give "wonky for a second, then it heals" with no full CRDT, because Figma already works that way: it says plainly that it doesn't use true CRDTs. The timings and the compiler part below are untested.

The caveat: "heals" means everyone ends up seeing the same thing, not that nothing was lost. That's fine for a colour, and a real loss for a paragraph.

The model

  1. Browsers make their own ids, and a change is one field of one thing.
  2. One referee per shared space puts changes in order. For a field, the last to arrive wins.
  3. The screen always shows the referee's copy, with my unconfirmed changes replayed on top.
  4. One heal routine: fetch the latest, replay. It runs on opening, reconnecting, a missed change, a periodic checksum and a rejected change.
  • Step 3 means there's no flicker, with no special case: my pending change simply wins on my screen until confirmed.
  • Bugs heal the same way as lost messages, since nothing else has to be right for the routine to work.
  • A rough guess, unmeasured: well under a second in a live room, and the poll interval otherwise.
  • Forms are live by default, so others see each change as it's typed, unless Spell batches them.
  • A live room trusts everyone in it until a later epic adds per-person rules, and says so.

Each kind of change

Change How it's handled What people see
Set a property the whole value, last wins the loser's value flips once, never a blend
Add to a list both kept, the referee settles the position a slight shuffle
Remove a marker in the log, trimmed later as snapshots replace it it disappears
Reorder parent and position are one field, and there are no arrays an order nobody chose, with nothing doubled or lost
Add to a number sent as an addition, not a new value both count
Long text a text library (Yjs) for that field only, once epic crdt's comparison agrees; the referee just relays its bytes both people typing live
Delete what another is editing delete wins, with a notice it vanishes, with Restore
Check, then write (the last seat) the action re-runs on the referee one may be put back, with a notice

The compiler's part, the riskiest idea here: it can see what an action reads and writes. A plain write becomes a set, "add 1" becomes an addition, and "check, then write" re-runs on the referee, so nobody chooses.

Without a referee

The browser's code stays the same: the referee's copy, pending changes, replay. Only the transport differs.

Place Live? Same field, two people Long text
A live room, or files through one Spell server yes last wins merged
REST with versions (If-Match) poll every 2-10 seconds a field-by-field merge, then mine wins, with a notice a three-way merge
Plain REST poll last save wins the whole record: warn at compile time lost
Airtable, through a small server side one shared poll, about every 10 seconds last save wins that field, with no warning lost
Files, no server re-read on focus last save wins one person at a time

Airtable sits between the two REST rows: a save changes only the fields it names, like the row with versions, but nothing checks versions, like plain REST.

  • It can't have each browser poll. The limit is 5 requests a second per base, so ten open tabs polling every 2 seconds use all of it, and going over means 30 seconds of failures for everyone.
  • So it needs something in front, which it needs for its key anyway: one server side that polls once and passes changes on. Sending every save through it too would make it a referee, and "wonky, then heals" would hold for people using the Spell app.
  • Linked records can lose an add. A save writes the field's whole list of links, so two people adding a link at once can drop one. Creating the child record with its link to one parent avoids that.
  • People editing in Airtable itself go around all of it. Those changes reach Spell at the next poll, and the last save wins.
  • The rates are arithmetic from Airtable's docs, and nothing has been run against it.

AT Protocol never uses the referee. Each person's records are their own, reads combine accounts, a version check guards your own devices, and the change stream shows other people's changes. So two people never fight over one record, and the people here means something different on it.

Where it ends stable but wrong

These four don't match "wonky, then heals". Sync can't fix them, so the types and the compiler have to.

Case What goes wrong What Spell does about it
Long text stored as a plain field a whole paragraph is gone a long text type, and a compile warning with no room
The last seat, with no referee rule on REST, both people believe they got it a rule on the server, or a compile warning that the check is only in the browser
Two fields each valid, invalid together (start and end dates) a nonsense combination group them as one field, or a checked action
Old offline edits arriving late an hour-old value overwrites newer work each change says what it had seen, so this can be noticed, and the person told or asked

Seeing who's there is the cheapest conflict tool: people avoid what someone else is plainly editing.

How it fits epic crdt

  • is a future epic with no phases, and doesn't conflict in substance: it also picks a referee, and says today's patches may be enough.
  • It's about one running program refereeing, on the editor's server. data may have no running program, only a place holding things.
  • This model answers three gaps it names: browser-made ids in place of counted ones, per-field changes in place of whole things, and changes flowing both ways.
  • The core already mirrors state with last-arrival patches, so a referee may grow from that.
  • data builds the one referee, the per-field changes and the ids. crdt keeps the running-program mirror and the text library comparison, using what data built.
