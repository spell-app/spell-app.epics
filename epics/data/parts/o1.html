A person says once where their data lives, says which types live there, and then writes what they'd write for things in memory.

  • Every line here has now been tried on the real parser (P10's table). Most need a rule that isn't built yet, and only the reading words really run. is saved in is decided, and so is a place's own name plus a kind; the other words are still a proposal.
  • Almost every verb here already works for things in memory, and would now reach the place.
  • There's no save step. Changing a recipe keeps it.
  • Editing is live: a form bound to a recipe changes it as people type. a draft of the recipe holds the changes instead, for an Edit screen with a Cancel button.
  • Removing a recipe removes its ingredients too, and undo brings them back. 
## The ONE line a different back-end changes
family cookbook is a web server at "https://api.example.com/v1"

a "recipe" is a view:
	- it is saved in the family cookbook
	- its "title" is text
	- its "cook" is a person
	- its "minutes" is a number
	- its "ingredients" is a list of ingredients
	- to draw it:
		<ui-form value={it}>
			<ui-input name="title" aria-label="Recipe"/>
			<ui-text>{the number of its ingredients} ingredients, by {the nickname of its cook}</ui-text>
			<ui-button onClick={remove it}>Remove</ui-button>
		</ui-form>
	- to remove it:
		- undone as "Remove Recipe"
		remove it from the recipes

an "ingredient" is a thing:
	- its "name" is text
an ingredient belongs to one recipe

recipe box is an app:
	- its "search" is text
	- its "draft" is text
	- its "matches" is every recipe where its title includes the search, sorted by its title
	- to add the draft:
		if the draft is "" return
		add (a new recipe with title = the draft, cook = them) to the recipes
		clear the draft
	- to draw its shelf:
		for each recipe in the matches
			draw the recipe
		while waiting:
			<ui-loader/>
		if there are none:
			<ui-text>No recipes yet.  Add the first one.</ui-text>
		if that fails:
			<ui-message color="red">
				Can't reach the cookbook right now.
				<ui-button onClick={try again}>Try again</ui-button>
			</ui-message>

start the recipe box

Writing none of the three riders still works. A person would see these defaults:

  • waiting: "…", then it fills in, as epic language decided
  • no recipes: the list's placeholder, or nothing
  • failed: a message where the list would be, with Try again, and never a blank page

The one line that swaps back-ends

Moving the data changes the first line and nothing else:

family cookbook is a graphql server from "https://api.example.com/gql"  // "from" and "at" mean the same
family cookbook is a data folder at "recipes"                          // chunked files, as epic pages do
family cookbook is a file at "recipes.json5"                           // one file
family cookbook is a database on this device                           // the browser
family cookbook is an in memory database                               // gone on reload
family cookbook is a room at "wss://rooms.example.com/family"          // several people at once

Sheet or CSV and Airtable follow the same pattern, and so does one AT Protocol account: 

family cookbook is a sheet at "recipes.csv"                            // or a spreadsheet:  a CSV-style file
family cookbook is a google sheet at "https://docs.google.com/..."     // read only, unless a place server's in front
family cookbook is an airtable at "appXXXXXXXXXXXXXX"                  // kept behind a small server side, see Q11
family cookbook is an atmosphere account at "did:plc:abc123"           // one account's records:  account is optional

AT Protocol's usual shape doesn't fit "is a ... at". There, each person keeps their own records in their own account, so a shared cookbook is everyone's recipes put together, and not one address. It's the hardest test of the one-line swap (below). 

family cookbook is a personal atmosphere account:
	- recipes live at "com.example.recipe"
// or:  family cookbook is a personal atmosphere account at "com.example.cookbook"
// no one account is the address:  given, it's the corner of each person's account the program's records go in

What doesn't carry across

The words stay the same, but a place can't do what it can't do. The compiler should say so at that one line.

  • On AT Protocol, remove it works only on your own recipe, and everything saved there is public today.
  • A CSV file is read only and has no id, so the author names a column, or rows share no identity.
  • Airtable has no version check, so two people's changes to one field can overwrite each other with no warning. It also allows 5 requests a second per base, shared by everyone using that base.
  • A shared cookbook on AT Protocol has no referee: reads combine everyone's accounts, and changing someone else's recipe is refused, at compile time where Spell can tell. So the one-line swap holds for reading, and a program that edits other people's things has to change.
  • A file or this device has no other people, so everyone here is only you.
  • A plain web server can't announce changes, so it needs - check it every 30 seconds.
  • A web server whose names differ needs a few mapping lines under the place, and nowhere else.
  • in one go: is only as real as the place allows, so a plain web server can show a change for a moment.
family cookbook is a web server at "https://api.example.com/v1":
	- recipes live at "/dishes"
	- a recipe's title is its "dish_name"
	- its version is its "version"
	- its id is its "id"
	- its key is the secret "COOKBOOK_KEY"
	- check it every 30 seconds
  • A back-end that follows the usual conventions needs none of those lines.
  • A type with no place stays in memory, as today, so no existing program changes.
  • A key is named, never written. Spell refuses to compile one written into a browser program, and a place that needs a key needs a small server side.
  • is saved in the cloud comes later, after the seven back-ends. This epic builds no hosting: a room runs on a server the person points at, so a later hosted one uses the same words.
