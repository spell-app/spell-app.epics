The settled design (server actions, "Settled") writes a call to an action with a (with reason as text) blank as close the job with reason "done early". P50 built it as close the job with reason = "done early": the form Spell already has for that blank. The page's form, with no =, would be a new call rule.

The two forms, for an action on a job whose server takes a reason.

  • With =: works today, and sends { reason: "done early" } to the server.
  • Without: "Don't understand", and the action is called with no reason at all.
a job is a thing
work is a web server at "https://jobs.test":
	- to close a job (with reason as text) is at "/jobs/{id}/close"
a job:
	- it lives in work

to finish (job as a job)
	close the job with reason = "done early"

// compiles to
finish() {
  return this.close({ reason: "done early" })
}

to finish (job as a job)
	close the job with reason "done early"

// compiles to
finish() {
  return this.close()
  /* PARSE ERROR: Don't understand "with reason "done early"" */
}

Why the builder chose =: it's the call side of every (with ...) blank, and has been since before this epic.

  • A (with reason as text) blank is the with_props_arg rule. The call it makes reads with, then a list of properties, the same list a new card with ... reads.
  • In that list, a property is name = value, name is value or name of value: all three work for the reason today.
  • The rule's own tests write it that way (methods' English rules): notify with message = "It worked!", notify with name = "Bob", message = "How many?" and reply = 2, notify "Really?" with reply = "yes".
  • P50's server call sends the blank by name, { reason }: it changed nothing about how the call is written. 
to notify (with urgent and reason as text):
	print the reason

notify with reason = "done early"        // notify({ reason: "done early" })
notify with reason of "done early"       // the same
notify with urgent                       // notify({ urgent: true }):  a name alone is yes
notify with urgent and reason = "done early"

Spell does have a few places with no =. Each works because the words after with are known in advance.

  • An action's head line, from epic language P48: to "deal the cards" with title "Deal", icon "card". Its words are a fixed list (title, icon, shortcut, undoable).
  • A new thing, from this epic's P32: a new card with suit hearts, short name "foo". The name must be one a type declares (a card has a suit ...).
  • a new tableau with name T1, from epic outline-spell P19: one word, then a name starting with a capital.

That last rule, P32's, already reaches a call: the call's property list is the same one. So the page's form works today by accident, but only when some type in the project happens to declare a reason. 

a job has a reason as text
...
	close the job with reason "done early"

// compiles to
return this.close({ reason: "done early" })
  • So today the page's form works or fails depending on an unrelated line elsewhere in the project.
  • Spell has no other place where a call's words change meaning like that; it's worth fixing whichever way this goes.

What the form without = runs into.

  • A with filter, from P32 (J183, J184). every job with reason "done early" already means "the jobs whose reason is done early". Called on a list, the filter wins, and the reason never reaches the action: 
a job has a reason as text
to tidy (jobs) (with reason as text):
	print the reason

tidy every job with reason "done early"
// tidyJobs(core.filter(core.everyThing(Job), (job) => job.reason === "done early"))
//   -- every job whose reason is "done early";  no reason sent

tidy every job with reason = "done early"
// tidyJobs(core.everyThing(Job), { reason: "done early" })
//   -- every job, with the reason sent
  • Note that today even = only escapes the filter because the filter form has no =: the two forms are what tell those lines apart.
  • A value of several words. The value after the name must be something Spell can read alone: quoted text, a number, a variable. with reason done early fails both ways ("Don't understand"); with no =, there'd be no sign where the name ends and the value starts.
  • A name of several words. A (with short reason as text) blank doesn't parse today at all ("Don't understand"), with or without = at the call. With no =, with short reason "x" could be the name short and something else, once several-word names come.
  • A name alone. with urgent already means "urgent is yes". Fine with no = as long as the next thing is a comma, and, or the line's end.

What supporting the page's form would take.

  • A new rule beside P32's: the call's own blank names (the action knows them, reason), each followed by its value. Like the head line's fixed words, so no type needs to declare them.
  • And its English and Spanish rules, the words shown in the editor's hints, tests for each case above.
  • The filter case stays: a list action called with every job with reason "..." would still read as a filter. That's the same trade the head line and new things already make, and could be a warning when a name is both a blank and a field.
  • No new rule: one way to fill a (with ...) blank, the way its tests and docs already show.
  • The server actions page's Settled line changes to say with reason = "done early".
  • Still close the accident: a call's property without = reads only names a blank declares, so it never depends on another type's fields.
  • The new rule above: a blank's own names, then a value, no =.
  • Reads closer to English, like the head line's with title "Deal".
  • Two ways to write one call, and a list action still loses its reason to a filter with no =.
  • The new rule, and = dropped from calls everywhere: every notify with message = ... rewritten.
  • A list action has no way left to send a value its things also have as a field.
  • A: a call to a server's action reads close the job with reason = "done early", as P50 built it; the page's example changes to match.
  • A: a call's with list stops changing meaning when an unrelated type gains a field.
  • B or C: a new call rule, in English and Spanish, and the filter clash on list actions to explain.
