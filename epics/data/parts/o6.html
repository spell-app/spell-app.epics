Waiting comes from epic language, and cancelling doesn't. So data has to add it, and the rule is simple: walking away stops what the page was doing for you, and never what you asked for.

What language gives, once built

All of this is planned and accepted, and none of it is built (1.8).

  • No word to wait: an action just waits for anything slow, so a data read only has to be marked as slow.
  • A getter may wait: a draw shows "…", then fills in.
  • meanwhile and at the same time: say not to wait.
  • One queue per app: a repeat of the running action is ignored, and another waits, keeping only the latest.

What it doesn't give

  • Cancelling: its queue plan leaves out stopping a running action, and nothing in its waiting phases mentions aborting.
  • A slow action holds clicks: a person's click on a link would queue behind a slow load. Its own says so.
  • So reads need to stay out of the queue: a read through a waiting getter isn't queued, which argues for reads as getters and writes as actions.
  • A search as you type: the queue ignores a repeat, where a search wants the newest to win. So an action can say - a new one replaces the last one.
  • Reading your own write: in an action just after a change, its Q8 got the old value (30, not 50). That's unsolved until its prototype runs.
  • A filter over slow values: where goes one by one, so a filter on a place must be sent to it, or it means one call per row.

What Solid does, checked by running it

The survey couldn't say whether a replaced read gets an abort signal, so this was tried on the repo's Solid (2.0 rc.17), in both createMemo() and createDeferred(), with the same results.

  • Checked: Solid hands the function no abort signal, only one argument.
  • Checked: a replaced answer is dropped: a slow first fetch answered after the second, and was never shown.
  • Checked: onCleanup() inside it runs when an input changes and when it's disposed, so aborting works if Spell's read makes its own controller.
  • Not checked: how this behaves inside language's per-thing values, or across thousands of them.

Read and write cancelling are different

Where it is Cancel means Certain?
A read, in flight abort it; nothing changes yes, though a server may keep working
A write in an unfinished action or a draft drop it, and replay yes: it never left
A write pending, not sent drop it, and replay yes
A write sent, with no answer can't: aborting only stops listening. It resends with the same id until the outcome is known no: the outcome is unknown
A write confirmed a new change that reverses it that's undo, and others may have built on it

Why a write sent is unknown is reasoning from how HTTP works, since no page read says so. An action's writes show at once, and could be sent only when it finishes, which is what makes cancelling real (Q8).

Navigating away

What's running Moving to another page Closing the tab
Reads for the old page aborted, unless another part is still reading them gone anyway
A finished action, its writes pending or sent keeps going, never cancelled saved pending changes resend on the next visit
An unfinished action, waiting on a read cancelled: nothing was sent gone: nothing was sent
A draft form kept, and restored on return kept locally
A failed write, its page gone a notice anywhere in the app: Retry, or Show me a notice on the next visit

The browser's ways to get a write out as a page closes are best effort, with a 64 KiB limit. Saving pending changes, each with an id, is what really guarantees it.
