Each card's drawing failed, and was drawn again, and failed: 207,205 console errors in 30 seconds, and the page froze (a screenshot timed out).

PokéSpell guards it (if its sprites), which a kid shouldn't need. Two things to decide: whether the X of nothing is nothing, and why a failed drawing retries without end.

Yes: the X of nothing should be nothing, and Spell already does it in some places. It just doesn't do it for a thing's own fields yet, which is where PokéSpell tripped.

  • When the compiler thinks a value might be nothing, it reads through it with ?. (in Python, getattr(..., None)), so reading off nothing gives nothing.
    • Its test is ProgramWriter.mayBeNothing(), from epic output-targets Q38.
    • Today it says "maybe nothing" only for an item taken from a list (the last card of the pile), a thing found by name or place, and anything read off one of those.
    • A field such as its sprites is never on that list, because its type says it's always a sprite. So the other of its sprites compiles to a plain ., and it throws until the Pokémon's own page has been read.
  • Why the field is empty at first: PokéAPI's lists give only each Pokémon's name (- its lists give only each one's "name"). Reading any other field fetches that Pokémon's own page, once, and the field fills in when the page arrives (readWholeOnGet()). Until then the field is nothing.

Your idea: a pokemon is a loadable thing, with methods gated on whether it's loaded.

  • Spell already knows which Pokémon fields come later. The place's line its lists give only each one's "name" says so, and reading one of those fields already starts the load. A loadable word would only repeat that line.
  • A gate written in the program (if it is loaded) is the same as today's if its sprites with a new name. The kid still has to remember to write it.
  • Loadable in Spell's util folder is a different thing. It holds one resource's contents and whether that resource has loaded, such as a file loaded by its address. A thing that comes from a place isn't built that way, and a Pokémon has no single "contents".
  • The part of your idea worth keeping is waiting: the program doesn't have to say anything at all.
    • A field the list didn't give could wait the way a slow value already waits (core.waitedValue()).
    • In a drawing it shows the "…" stand-in until the Pokémon's page arrives. An action reading it waits for the answer.
    • That's option C below.

Why the page froze: a drawing that throws runs again and again.

  • Each drawn thing has its own error boundary: when its drawing throws, the boundary shows a small "can't draw" stand-in and the rest of the page keeps drawing (drawInBoundary(), built on Solid's <Errored>).
  • Solid's boundary heals itself: whenever something the failed part read changes, it tries that part again. Each new try that fails logs one more console line and sends one more ui-error event.
  • Here the failure wasn't in the card's draw(). It was in a value that keeps updating inside the drawing: the picture's src: () => this.picture. The tests check a throwing draw(), and a throw while an element is first made, and each logs one line. No test checks a throw inside a value that keeps updating.
  • PokéSpell writes into those Pokémon over and over. The list arrives a page at a time, and each card's own page lands one by one. If every write retries every broken card, that's cards × writes: 207,205 lines in 30 seconds. That's the likely cause, but nobody has measured it yet. The first step of the fix is a test that shows it.
  • mayBeNothing() also says yes for a field whose type is another kind of thing (a sprite, a pile, an owner), since a thing nobody has set yet is nothing. So everything read off it uses ?..
  • The kid's program is one line again: return the front default of the official artwork of the other of its sprites. The picture is blank, then appears when the page arrives.
  • Python gets the same, through the same test (getattr(..., None)).
  • Cost: small, one rule in the writer. Every example's saved compiler output (its snapshots) that reads a field of a field changes from . to ?.. TypeScript accepts ?. on a field that's never empty.
  • On its own, it doesn't stop the endless retries for some other thing that throws.
get picture() {
  return this.sprites?.other?.officialArtwork?.frontDefault

  • The boundary logs and sends ui-error once for each time it breaks, not once for each try. It shows the stand-in until the thing draws without throwing.
  • Add a test with a value that keeps updating and throws (src: () => ...): one console line, and the page doesn't spin.
  • Cost: small to medium, in the drawing code and its tests. First measure whether the retries come from Solid healing or from a write made inside the read.
  • On its own, the kid still needs the if guard, because the picture shows "can't draw" until the page arrives.
  • A field the place's lists don't give waits like a slow value. The card shows "…" until its page lands, and an action waits for it.
  • No new word: the place's lists give only line already says which fields.
  • Cost: larger. The field's getter has to wait, and actions need it too. A card's name, which comes with the list, must still show at once, so only the late fields can wait.
  • It still needs B for anything else that throws, and A for a field that's really empty on the server.
  • The compiler warns about a read of a late field without a guard.
  • Cost: small. But it asks the kid to write the guard we want gone, so it goes against your note.

Recommended: A and B together. A is exactly your "the X of nothing is nothing". B makes sure any other failed drawing costs one line on the console, not a frozen page. C can come later, if a blank picture that pops in looks worse than a "…".
