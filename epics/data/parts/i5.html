It's sent with no id, so a resend after a lost answer makes a second row unless the place remembers changeId. MemoryPlace does; Airtable won't. That phase has to decide: search for the row first, or make the insert through its server side.

Decided in P17 · Airtable: an id column and an upsert. Tested against the stub: the same new row sent twice, and sent again after the answer really was lost, is one row.

  • With - its id is its "...", the browser makes the id, and a new row is a PATCH with performUpsert on that column, so nothing depends on remembering changeId, and a server restart changes nothing.
  • With no id column, Airtable makes the id, and a row can still double: nothing in Airtable can stop that, so the program's line warns, and says what to add.
