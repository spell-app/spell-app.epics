People will say once where their data lives, in one line, and then read and change it in the words Spell already has, so moving from a file to REST, GraphQL or a room changes nothing else. Spell handles the waiting, the cancelling, gathering what each page needs, and several people at once, with changes that may look wonky for a second and then heal, and no full CRDT.

Goal: It's time to get server-based data working in spell, from various data sources, with uniform, convenient semantics.

We've cracked making the front-end easy to write, now we need to do the same for the back-end.

We should support REST, GraphQL, chunked files like epic pages do, file system semantics, and at least one other data collection mechanism out of the gate. This will help keep us from specializing too early.

For inspiration, look at `meteor` JS project and the new `fate` system (https://fate.technology/). Do a survey of other paradigms to see how people have solved these types of problems.

A layperson doesn't understand how all of this stuff works, they just know that data is out there "in the cloud" and want to show it and modify it. Working with "local data" should feel exactly like working with data from the server. We should be able to swap out back-ends without changing the front-end at all.

Async should just work transparently (`language` epic is working on that for the language).
We need to think about canceling "transactions", e.g. if they navigate somewhere else.

We are a compiler! So e.g. the way `fate` aggregates the data needed for the parts of the page and transmits that to a coordinator at the app level should be easy for us.

And "mutli-player spell" is totally going to be a thing, so think also about CRDT-like semantics, but without requiring a full CRDT system. I'm willing to tolerate a little "opps, something changed" to avoid having complicated data semantics. If two people are editing something at the exact same time, things may get wonky for a second or two -- that's ok, as long as things self-heal relatively quickly -- and much better than having a complicated CRDT system that makes things harder to set up or work with.

Start with doing a survey of various ways that "the data problem" has been solved. Then think about human language to express these various concepts. We'll build from there.
