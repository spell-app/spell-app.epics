Nobody can say whether Spell is getting more coherent: the catalog's searches find copies AND noise, and the only numbers so far came from two throwaway scripts.

  • One command says how coherent the code is, over every installed repo: spell coherence score
    • Copies left: per catalog mechanism, the places its search finds outside its home and outside "Fine as it is"
    • Users: the files that use the home, from the code map; without graphify (it's optional), a search for the home's name instead
    • Its score: users / (users + copies); the code's score is their mean, weighted by size, 0-100
    • Words: each word list entry's replaced words, counted
  • The catalog stays the one source: each entry gains a Score: line, a search that matches copies only, and what it leaves out.
    • e.g. "Watching files" counts ServerLink.watch() and ColorScheme.watch() today; "Logging" counts every console.log(), which is noise for a score
  • Each run can save a snapshot, and compare with one: the score as a trend, not a one-off.
    • a snapshot of the code before P6 is the first, so the trend starts where the fixes did
  • The coherence agent uses it: a plan review can say "this plan adds 3 copies"; a sweep records a snapshot.
  • The commands page has its row; the command line's README shows it, as it shows spell map.

The compare words a change as an improvement, never a signed percent (Owen, 2026-10-25: "Coherence score should say improvement, not -70%, e.g. '30% better'").

  • spell coherence score --compare, a plan review and a sweep's report each say "30% better", or "12% worse" when it went the other way; never "−70%".
  • Each line says what the percentage is of, so "better" is honest:
    • copies 1,149 → 820: "29% better (fewer copies)"
    • the score 81 → 88: "9% better (score up)"
  • Tests: a compare line reads "N% better" when copies fell or the score rose, and "N% worse" the other way.
  • The Goal's before / after table, and the compare's own table: a column headed "Improvement", its cells the bare percent ("17%"; a worse one "−12%"), not "17% better" (Owen, 2026-10-25: "Header IMPROVEMENT, drop the better from the cells"). A sentence still says "17% better".

The score measures the code, never the tests (Owen, 2026-10-25: "tests can be excluded from these numbers ... I'm worried about actual code"; "For tests, number of tests is more important than lines of tests").

  • Code coherence: the score, over each repo's src/ only; test folders and test helpers left out.
  • Tests: a count of tests per repo (each it() / test()), beside the score and in each snapshot; never lines of tests, and never part of the score.
  • Test coherence and test coverage: not in this phase; a todo for later, if the count isn't enough.
  1. The catalog's searches, made exact: each entry with a Flag: gains a Score: line the command reads: the search, its home's names, and what it leaves out.
    • e.g. **Score:** `\bwatch\(` from `node:fs` · home `LiveReload` · not `ServerLink.watch`, `ColorScheme.watch`
    • the Flag: stays for people and the agent; "Fine as it is" and each entry's "Fine:" lines are left out by path
    • "Logging" gets no Score: line: console.log() is noise for a score (its Flag stays)
    • the word list's entries gain the same: the replaced words, as a search, for the words' count
    • each search checked by reading its hits once over today's code: copies only
  2. The kit's counting, spell/cli/coherence: one class, CoherenceScore, over the installed repos (the repos list the CLI already has).
    • copies: git grep through the kit's Git, over each repo's src/, skipping bundles and generated data as the prototype did
    • users: the merged code map's links into the home (files that import or use it, outside the home); no map: a search for the home's names, and the report says so
    • per mechanism users / (users + copies); the code's score the mean weighted by users + copies, 0-100
    • --at <commit> counts at an older commit (users then by search only), as the prototype's "before P6" did
  3. The command: spell coherence score [--json] [--save] [--compare <snapshot | last>] [--at <commit>] (Q10: or spell map score).
    • prints a table: each mechanism's copies, users and score, the words' counts, then the total
    • --save writes a snapshot, JSON5, to the epic's details/scores/ in the content repo (Q11)
    • --compare adds each row's change, and names new copies by file
    • first snapshots saved: the commit before P6, and today, so the trend starts with the numbers above
  4. The coherence agent: its procedures and skill run it.
    • a plan review counts the copies a plan's files would add, where it can tell, and says "this plan adds N copies"
    • a sweep saves a snapshot and reports the score's change since the last
  5. Docs: the commands page's row (op "Score how coherent the code is", noun coherence), then spell commands check; README-cli.md's "Scoring coherence", after "Asking the map", its output in a "What it printed" fold; the catalog's header says what Score: is.
