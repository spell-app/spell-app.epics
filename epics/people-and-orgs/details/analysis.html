Six short parts: the idea, what exists, Person in spell today, the shape I'd propose, the catch, and the size.

  • A person is a Thing, written in spell: names, nickname, emails, addresses, dates, friend lists with notes, settings.
  • An org is a Thing too: members, each with a role (admin, read-only ...), public or private, settings. "Team" and "group" are other names for the same thing.
  • A workspace is a folder of projects, one per person and one per org. Special folders at its root: $settings, $sessions, $docs, $data.
  • An address names any of it: matt@three-degrees:bubble-trouble/folder/file.json is a file, owen@spell/solitaire/rules a running page.
  • Storage is readable files on disk, behind one interface (a "storage adapter") that S3 or Git could replace.
  • Spell compiles Person and Org into code that the app and the server import.

Some pieces exist, under other names. None of them knows about people.

Person.ts · compiled · roughly · 6 lines 
export class Person extends Thing {
  @prop({ type: "text" }) accessor id!: string
  @prop({ init: () => new List() }) accessor names!: List<string>
  @prop({ type: "text" }) accessor nickname!: string
  ...
}
  • One file per thing, so two people rarely edit the same file: one per person, per org, per membership.
  • Each file says its type and version, so an old file can be upgraded when it's read.
  • Each folder can have an index, built from its files and never edited by hand: rebuilt when a file changes.
  • Sign-in data stays out of these files: passwords and tokens go in a small database beside them.

You asked for a schema that's declarative and friendly, and not JSON Schema. A schema says what a person file holds, checks it, and upgrades old files.

The spell declaration IS the schema. It compiles to a checker the app runs, and to the JSON Schema VS Code uses to underline mistakes in the file. No new language to learn.

  • Versions: each file says "$schema": "spell:person@2".
  • An upgrade, written in spell: "a person 2 renames name to names". An old file is upgraded step by step when read, and written back when next edited.
  • Borrowed from Protobuf and Avro: a new field has a default, so an old file without it still reads.
  • Cost: we build the checker and the upgrade steps ourselves.

The most used schema library, written in TypeScript code. Ready today; a second description of Person next to the spell one, kept in step by hand. 

const Person = z.object({ id: z.string(), names: z.array(z.string()), emails: z.array(z.email()) })

Schema languages of their own, strong at constraints. Neither has a maintained JavaScript version: they'd run as a separate Go or Java program.

VS Code and a .json5 file's schema
  • VS Code (1.141) has no JSON5 mode of its own. The "JSON5 syntax" extension you have colours the text and checks nothing.
  • Its JSON checker runs on files in "JSON" or "JSON with comments" mode. A setting can open *.json5 in that mode: "files.associations": { "*.json5": "jsonc" }.
  • Run on the test file that way, VS Code's own checker found the schema mistake, and also flagged every JSON5-only bit: "Property keys must be doublequoted" on each bare key, "Value expected" on each single-quoted text.
  • So spell WRITES the JSON-compatible part of JSON5: keys and text in double quotes, comments and trailing commas allowed. Those files check cleanly. A bare key typed by hand gets one squiggle, and the schema check still runs past it.
  • The setting goes in the repo's settings and the spaces folder's. The spell extension can also add .json5 to "JSON with comments" for everyone, to be tried in the phase: an extension can't set files.associations itself.
  • Later, if bare keys should check cleanly too: the spell language server checks .json5 files itself, against the same JSON Schema.
  • Sources: Editing JSON with VS Code, language modes and file associations, vscode-json-languageservice (the checker run in the test).
