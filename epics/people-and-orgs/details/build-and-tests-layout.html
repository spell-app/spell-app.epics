Today compiled files sit beside the sources, all committed, and tests sit beside their modules. Below is only the proposal.

  • Source: what a person writes. A project's .spell files, its project.json, its CSS.
  • Compiled output: what compiling a project writes. Its JavaScript, which the runner runs; its other targets (TypeScript, Python); its scope pack, which the Type Explorer shows.
  • Declarations and words: also written by compiling, but kept beside the source (your note). Declarations say what a project importing this one can use; words are the Thing Explorer's labels.
  • Library: a project compiled for other code to IMPORT, not to run (the library phase, P3).
  • Test project (a "fixture"): a frozen copy of a spell project that tests compile, with snapshots of what it compiles to beside it.
  • Mirror: a file's path under build/ or tests/ is its path under packages/: swap the first folder name, and you have it.

Your note on the partner page puts people's accounts in spell-spaces, beside the repo, one folder for every checkout. Where does a person's compiled project go?

  • In each checkout's build/, under build/spell-spaces/: the same mirror rule, with spell-spaces as the first folder's name.
  • Why not in spell-spaces: every checkout reads it, and each compiles with its own branch's compiler. Two checkouts writing the same compiled file would overwrite each other's, and the runner would show one branch's output in another.
  • Declarations and words stay beside the source, in spell-spaces, by your rule: they're what other projects compile against. They change only when the project's source changes, or when a compiler change changes their shape (caveat 12).
  • Built when needed, as the built-ins: a person's project compiles when it's opened or run, if stale. spell compile --all covers spell-spaces too.

Your note: "avoid having to write the .lib.d.ts by writing just the .lib.ts file if we can". We can.

  • The library phase already writes the library as TypeScript (LibraryTSWriter), and today only hands it to tsc to make the .d.ts. That TypeScript becomes the library.
  • Who reads it as it is:
    • Vite: the app, the editor, every test.
    • tsx: the page server, the spell command.
    • The type check: an importer's yarn ts reads its types straight from it.
  • Who can't:
    • A browser page with no build step, and plain node.
    • But they can't load today's .lib.js either: it imports the core, which is TypeScript with decorators (@spell-app/core/model), and neither node nor browsers run those unbuilt (vite.decorators.ts).
    • For them: a build step later, into build/: the core's model and the library bundled into one JavaScript file.
  • So .lib.ts loses nothing the .js gave, and drops a file and a tsc run per compile.
