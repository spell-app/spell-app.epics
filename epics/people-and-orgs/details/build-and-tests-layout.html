Library types, a build folder, a tests folder

Three ideas from your note on the library's types file: how a compiled library gives TypeScript its types and still loads as plain JavaScript; moving every compiled file into a build/ folder; and moving tests into a tests/ folder. Pictures of each, and what each would cost.

Asked by: session people-and-orgs, while building the library target (its phase 3) Asked: 2026-10-12 Status: waiting for your answer
  • Epic: people-and-orgs gives spell its first Person and Org, written in spell and compiled into a LIBRARY: plain JavaScript that the server and the app import.
  • Just now: phase 3 is being built. spell compile writes the library, People.lib.js, and a types file beside it, People.lib.d.ts. You replied on that call (J5, "a .d.ts beside people.lib.js") with three ideas.
  • This decides:
    • Question 1 (types and JavaScript) bears on phase 3 now.
    • Questions 2 and 3 (a build folder, a tests folder) change the whole repo's layout. They're bigger than this epic: I'd make them their own epic, repo-layout. Meanwhile people-and-orgs keeps today's layout, unless you say otherwise.
  • Heads up, two things I found:
    • No choice of file alone lets a bare browser page load a library: it imports the core by its package name, and the core is TypeScript with decorators. It loads through Vite, as the app does.
    • Compiled output is one file per PROJECT, not one per .spell file: Solitaire's four spell files compile into one Solitaire.compiled.js. So a build/ folder would mirror project folders, not single files.
  • Source: what a person writes. A project's .spell files, its project.json, its CSS.
  • Run output: what compiling a project writes so it can run.
    • Its JavaScript, Solitaire.compiled.js, which the runner runs.
    • Its declarations, Solitaire.declarations.json: what a project importing it can use.
    • Its words, Solitaire.en.js: the labels in the Thing Explorer.
    • Its scope pack, Solitaire.scopes.js: what the Type Explorer shows.
    • When a project asks for them, its TypeScript (.compiled.tsx) and Python (.compiled.py).
  • Library: a project compiled for other code to IMPORT, not to run: People.lib.js and its types file, People.lib.d.ts (the js/lib target, this epic's phase 3).
  • Snapshot: a file a test compares its result against. Vitest keeps them in __snapshots__ folders; spell's test projects keep theirs beside their spell files, e.g. People.snapshot.js.
  • File nesting: a VS Code setting that folds files under another file in the Explorer, with a chevron, the way package.json can fold yarn.lock. Nothing moves on disk.

Object.defineProperty(SP.SpellLocation.prototype, "serverPath", {
  get() {
    const path = [serverPathForRoot(this.projectRoot), this.projectName]
    if (this.filePath) path.push(...this.filePath.split("/"))
    return fileUtils.normalizePath(...path.filter(Boolean))
  }

You want the library as .js so a browser can load it directly. Today no browser page can, whichever file we write, because of what the library imports.

  • Its first line imports the core by its package name, @spell-app/core/model.
  • A browser can't find a package by name alone: it needs an import map saying which URL it is.
  • That URL would be packages/core/src/model.ts: TypeScript, with standard decorators, which neither node nor browsers run without a compile step (the repo's own note on its decorator plugin).
  • So the library loads through Vite (the app, tests) or tsx (the server, the spell command), which compile the core as they go.
  • A page that loads it with NO build would also need the core's model bundled to one .js, plus an import map. That's the same work for every option below.

Keep what phase 3 builds: People.lib.js for loading, People.lib.d.ts beside it for types. TypeScript finds the types file by itself. Nothing to redo; the second file folds away under Q2's or Q3's nesting. 

// anywhere in the repo:  types come from People.lib.d.ts, the code from People.lib.js
import { Person } from ".../people/people.lib.js"
const owen = new Person({ id: "owen", name: "Owen" })
owen.name   // string
  • The types file is made by the repo's own tsc, about 70ms per library (J22).
  • Two generated files, both committed, both marked generated, so a merge rebuilds them.

One file: the JavaScript carries its types in comments (JSDoc). But every package that imports it must turn on reading JavaScript types, which also drags in the big bundles in its folders. 

export class Person extends Thing {
  static { this.declareProp("name", { type: "text" }) }
  /** @returns {string} */
  get name() { return this.getProp("name") }
  /** @param {string} value */
  set name(value) { this.setProp("name", value) }
}
  • "Reading JavaScript types" is TypeScript's allowJs. In ui, say, it would also pick up the committed markdown and highlighter bundles.
  • Types only as good as the comments the writer adds.

The work, as an epic:

  1. The server's file mapping (1.3) sends compiled endings to build/.
  2. A project importing another compiles that one first when its declarations are missing: a fresh checkout has none.
  3. Git forgets the 41 run output files; build/ is ignored.
  4. In build/, .compiled could go from the names: Solitaire.js, Solitaire.tsx, Solitaire.py. Your choice.
