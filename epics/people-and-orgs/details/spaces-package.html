A Spaces Package

How the proposed scheme works. A spaces package owns where projects and people live, and the servers. Spell is the language alone. Every call to the page server is under /api/. Every set of components, Spell UI's, Epic UI's, the app's, the brand's, and a space's own, is laid out the same way and served the same way. The partner page, The repo with build/ and tests/, has compiled output and tests.

The page server's own file operations: files and folders, never projects. Pages it served call them over HTTP; spaces calls the same code in-process.

Call Body What it does
PUT /api/files?path=<url path> the contents saves the whole file, making its folders, all at once. With If-Match: 409 if it changed since.
POST /api/files/create { path, contents? } or { path, folder: true } a new file or folder; 409 if something is there
POST /api/files/rename { path, to } moves a file or folder; 409 if to is there
POST /api/files/duplicate { path, to } copies a file or folder, everything inside
DELETE /api/files?path=<url path> -- deletes a file or folder, everything inside
  • A path is a URL path the server serves (/guides/server/old.png). Reading is the plain URL.
  • Only the shared content folders are writable through it (epics/, guides/, pages/, templates/, brand/): each turn's commit of the shared repo makes a mistake undoable. People's spaces are written through /api/projects and /api/spaces; the built-ins and the code never.

A COMPONENT SET: a group of elements with one tag prefix, their docs pages, and their pack (the one script a page loads to get them). Every set is laid out and served the same way.

A set named <set>, tag prefix <p>- · 16 lines 
<set root>/                  a package (packages/epics/), or a project in a space (@three-degrees/ui)
  components/                 the elements' code:  one folder per family, named for its main tag

    _data/                    pages.json (hand-kept);  components.json, search.json (generated)
  pack/                       generated:  <name>.catalog.ts, <name>.entry.ts, <name>.pack.js

/components/<set>/_assets/   the docs site's script:  the same for every set, laid over by the server
spell dev pack build <set>    the pack and docs/_data/, together
  • Docs pages: one flat folder, docs/; an element's page is its tag. Served at /components/<set>/<tag>.html.
  • The pack: <set root>/pack/<name>.pack.js, at its own file's URL. A page loads it with Spell UI's one loader, <ui-components source>, inside <ui-root>.
  • Tags: every tag starts with the set's prefix; no two sets share one.
  • Why /components/<set>/: one home for every set, so the top bar lists them all from one place; the URL's tail is the same for every set; a repo set's name never has an @, a space's always does, so they can't clash.

An org, a person or a project can write its own elements by hand. They're a component set like the repo's: the same layout inside, the same /components/ docs path, loaded the same way.

  • An org's or a person's set is a project in their space, named as they like: @three-degrees/ui, owen@spell/widgets.
  • A project's own set is its components/ folder, beside its spell files: @three-degrees/bubble-trouble. A built-in example can have one too.
  • Its pack is compiled output: spell compile builds it, when needed, into the checkout's build/; its URL is the project's own.

How it's built, for whoever builds it. Nothing here changes a path or a URL above.

  • Spell asks for a file by URL, /spaces/<address>/<file>, and saves by POST to /api/projects/file/...: one function its three file classes share.
  • In the browser the page server answers. In node (the language server, the spell command, tests) spaces' disk reader answers the same URLs in-process: whatever runs spell installs it first.
  • One list of URL shapes, which the routes and the disk reader both read, with a test that every URL spell builds is answered by both.
  • Spaces registers its groups with spell (addProjectRoot()) from each entry point, with a test per entry; else an address fails as "unknown".
  • The storage adapter sits behind the routes: a save keeps a JSONC file's comments.
  • The file operations: a new class beside the page editor, on node's own file calls (still a leaf). Inside a served folder only (resolveInside()), under the file lock, all-at-once writes.
  • Two write checks in Guard: the strong one (this run's token and the server's own origin) for /api/files, /api/pages and epics' calls; a weaker one, any localhost port, for spaces' calls, since the editor calls them from vite's port, through vite's proxy.
  • The writable list: a "writable" list in the root package.json's "pageServer" block. The page editor saves through the file operations, under the same list.
  • Component sets: one list in the server (COMPONENT_SETS) names the repo's four, by folder; spaces adds a space's sets, and the /spaces/ folders, when its route module loads.
  • /api/projects is spaces' own mount, so its "unknown call" 404 covers only its own paths.
  • The docs routes (answers, comments, review marks, new epics) write through the file operations too, for the same locked, all-at-once write.
  • Epic UI's elements/ pages go flat into docs/; App UI's pages leave components/ for docs/; Spell UI's (from the shared ui/) and the brand's (from the shared brand/components/) move in with Q11's A.
  • Spell UI's site script, in packages/ui/site/, takes a set's folder as its root, as it does for Epic UI and App UI.
  • The app's pack is built by Vite (it imports two ES modules), into pack/; brand becomes a pack with spell dev pack new brand.
  • spell dev pack build writes a set's docs/_data/ too, in place of each package's own site:data script; for a space's set, spell compile does.
  • A set's tests go to tests/<package>/, as every test (the partner page).
