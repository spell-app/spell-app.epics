A Spaces Package

One scheme, built from your notes on this page and on its partner, "The repo with build/ and tests/". A new package, spaces, owns everything about where projects and people live, and the servers that serve them. Spell becomes the language alone. Docs and epics become one package. Spell's built-in projects stay in the repo; people's own spaces live beside it, in spell-spaces. The page server learns to create, rename, copy, delete and save files, knowing nothing of projects; spell's projects API moves into spaces, on top of them. This page shows the packages and who imports whom; the partner page shows the files on disk.

This is what makes your option B safe. The old worry was a cycle: once spell saves projects through the storage adapter, spell would import spaces, which imports spell. It doesn't happen, because spell already never touches the disk itself:

  • Spell asks for every project file by a URL: a file's url is /api/projects/file/<project>/<file> today, and saving posts to the same URL. After round 4 it's /spaces/<address>/<file> (1.6).
  • In the browser, the URL goes to the page server. A read is a plain static file, from the folder spaces says the address lives in; a save reaches spaces' route (1.5).
  • In node (the language server, the spell command, tests), spaces answers the same URLs from disk, in-process: installDiskFetch() swaps spell's fetch for a disk reader. The language server does this today; after the move, the function is spaces', and answers the new URLs (1.6).
  • So the storage adapter sits behind the URL. A save from the editor reaches spaces' route, and the route writes through the adapter, keeping comments (the project.json saves, T1).
  • Spell knows addresses and URLs; spaces knows where they are on disk. Spell imports nothing of spaces.

Your call: "create/rename/duplicate/delete are things the page server should be able to do." So the page server gets them, with save, as its own. They know files and folders, never projects.

  • Where: the server package, a new FileOps (name not final), beside the page editor (PageEditor), which saves pages today.
  • Still a leaf: node's own file calls (copy, rename, remove), no package. Spell's file-utils does the same on fs-extra; those calls go.
  • Two ways in:
    • In-process: node code that imports the server calls it. Spaces' project routes do (1.5).
    • Over HTTP: the routes below, for pages the page server served.
  • Why under /_server/files: the page server's own routes live under /_server/ (the page editor's /_server/page, /_server/ping, live reload). /api/... belongs to the route modules: details answers, comments, review marks, epics, agents, /api/docs/show, and the projects API. /api/files would sit among theirs, under the projects API's /api mount, whose catch-all answers 404 for a path it doesn't know.
Method Path Body What it does
GET the file's own URL -- read: plain static serving, as today (its type from its extension, an ETag). No new route.
PUT /_server/files?path=<url path> the contents save: writes the whole file, making its folders; all at once (a temp file, then a rename), under the file lock. With If-Match: 409 if it changed since. Answers its new ETag.
POST /_server/files/create { path, contents? }, or { path, folder: true } a new file or folder; 409 if something is there
POST /_server/files/rename { path, to } moves a file or folder; 409 if to is there
POST /_server/files/duplicate { path, to } copies a file or folder, everything inside; 409 if to is there
DELETE /_server/files?path=<url path> -- deletes a file or folder, everything inside. No undo.
  • Every path is a URL path the page server serves (/guides/server/old.png), found through the same folders a read is.
  • Safety, as the page editor's today:
    • Inside a served folder only (resolveInside()): no .., no dot files.
    • The page server's write check (Guard): this run's token and its own origin, as on every other write route there. So only a page the page server served can call them. Not the editor: it runs on vite's port, without the token, so it goes through spaces' routes (1.5).
    • Only into folders listed as writable (the table below). A build laid over a folder (Spell UI's _assets/) never is.
