A drawn thing's element shows each property its kind declares as an attribute. The built-in id every thing got in P1 is left off that list, so nothing on the page changes.

  • A drawn thing: one of a kind declared a drawable thing or a drawable list.
    • The page draws each one in its own element: a card is a <solitaire-card>.
  • Its "attributes" are what the browser's inspector shows on the tag: one per declared property, kept in step with the thing both ways (epic drawable-thing).
  • The list of what an element shows is made by one function, spellCore.elementApiOf(). The call: its walk up a kind's super-kinds stops at the built-in drawable kinds, as its walk of methods already did, so it never reaches the id that every thing has.

A card, as the inspector shows it, before P1 and after: the same.

<!-- before P1, and after it with this call -->
<solitaire-card id="queen-of-spades" rank="queen" suit="spades" direction="up" pile="Tableau#T3">

<!-- the thing behind it, in the console:  the card's own id, made up the first time it's read -->
document.querySelector("solitaire-card").thing.id
// "card-k3x9q2mf"
  • Its rank, suit and direction are the properties the card's kind declares; pile is the pile holding it.
  • The tag's id, queen-of-spades, is NOT the card's built-in id: it's the card's NAME.

Three different things are called "id":

Which For example What it's for
the thing's built-in id (P1) card-k3x9q2mf, owen saving, and saved references: Card#card-k3x9q2mf
the element's own id queen-of-spades, T1 the thing's name: a page's layout finds a thing by it, <solitaire-tableau id="T1">, as Tableau#T1 does
a thing's number on one page "@id": "3" a page's state, between the running program and the page

Why the built-in id is left out:

  1. The attribute is taken. An element's id already holds the thing's name.
    • Showing the thing's id there too would give one attribute two values.
    • Each side would keep rewriting the other's.
  2. It could rename a thing. For a tag written by hand, each attribute the page gives it is written to the thing first.
    • So <solitaire-tableau id="T1"> would set that tableau's saved id to T1, and every saved reference to it would break.
  3. Showing it would make one. A thing gets its made-up id the first time anyone reads it, and keeps it.
    • Drawing every card would then stamp an id on each, and each card's saved form and page state would grow an "id", just from being drawn.
  4. A second guard already drops it. When the page turns that list into attributes, it skips every name the browser already uses, such as id and class.
    • So the call changes nothing you can see. It keeps the list honest: it lists only what the element really shows.
    • A core test pins the exact list.

What you'd see: nothing new.

  • The inspector shows the same attributes as before P1.
  • The built-in id is still there on the thing, through the element's thing property, as above.

What showing it would take, if you ever want it: about an hour, no grammar change.

  • An attribute under a name of its own, read only: e.g. thing-id="card-k3x9q2mf", so a page can't rename a thing through it.
  • Read without making one: shown only once the thing has an id (set, saved or loaded), so drawing changes nothing.
  • The same attribute on the element class compiled TypeScript writes, so both targets draw the same tag.
  • A test in core and one in the app's runner.
  • Nothing changes: the call stands as built in P1
  • A read-only thing-id attribute is a todo, if you ask for one
