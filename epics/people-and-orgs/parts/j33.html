A project's index, what the app's API answers about a project, now carries buildFolder: where its built files are, from its own folder.

  • e.g. for Solitaire: ../../../../../../build/spell/projects/system/examples/Solitaire
  • Missing for a project whose built files sit beside its source
  • Who needs it: the Python web app, Solitaire.app.py, is checked in beside the source, but must load the compiled program and its page file from build/
  • So compiling writes the app with an OUTPUTS line, that folder from the app's own, and the app serves from there
  • Why a relative path: the app keeps working when the checkout moves, and in any worktree
  • Not taken: copying the compiled program next to the app, which would make it a checked-in copy again, what this phase removes
  • a Python web app compiled before this phase is rewritten with its OUTPUTS line on the next compile, unless it was edited by hand: then the line is added by hand

I dislike `../` references intensely -- are the imports actually using `$/`?

The ../ in this item isn't an import. It's a folder path on disk, written into a generated Python file, from the app's folder to the build folder. The TypeScript imports do use the $/ aliases, with a few exceptions listed below. The ../ in the app can go: the options are at the end.

Where the ../ is: three places, all the same path.

  1. The project's index carries buildFolder: where the project's built files are, measured from the project's own folder.
    • Made by relativeBuildFolder(), from buildFolderFor().
  2. Compiling to Python hands it to the app writer, as QuartAppSpec.outputs.
  3. The app writer puts it in the app's OUTPUTS line. The app loads the compiled program and its page file from there. 
HERE = Path(__file__).parent
# the compiled program and its page file:  where `spell compile` builds them
OUTPUTS = (HERE / "../../../../../build/spaces/@spell/examples/solitaire").resolve()

# a game per visitor, each running Solitaire.spell.py
sessions = SpellSessions(OUTPUTS / "Solitaire.spell.py")

Ways to drop the ../ from the app. What each must survive:

  • a worktree: the app must load THIS checkout's build, not main's
  • the checkout moving to another folder
  • a project in spell-spaces: its app sits outside every checkout, shared by all of them, while each checkout builds its own copy of the program
  • the app copied elsewhere. spell run --target py doesn't copy the committed app. It writes a fresh one into a temp folder, with the program beside it (OUTPUTS = HERE), so no option changes it.

# spell_quart, beside assets_folder(), which finds the page side the same way
def built_folder(path: str) -> Path:
    """A folder in the build/ of the checkout this spell_quart is in:  `$SPELL_BUILD_DIR`, else found from this file."""
    named = os.environ.get("SPELL_BUILD_DIR")
    build = Path(named) if named else Path(__file__).resolve().parents[6] / "build"
    return build / path
  • SPELL_BUILD_DIR is the variable the node side already reads to move the build folder (tests set it), so both sides would answer to one name.
  • Python's web server, spell_quart, already finds the page side's files this way: assets_folder() counts up from its own file, with an environment variable to point it elsewhere.
  • Each checkout runs the app with its own spell_quart, so the app finds that checkout's build: main's in main, the worktree's in a worktree. That works for spell-spaces too.

  • Not taken in D: counting up from the APP's folder to a marker file at the repo root. It works for the spaces package and the tests, but finds nothing from spell-spaces or from an app copied away.
