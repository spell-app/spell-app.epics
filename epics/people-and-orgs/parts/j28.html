The copy is in the tests folder already: it's tests.types.ts, at the top of ui's tests. What's left outside is the ORIGINAL, in ui's test helpers. And since this epic's Tests Folder phase (P10) moved ui's tests out, nothing beside that original reads the two additions any more. So the copy can become the only one.

What the two additions are:

  • Vitest lets a project add to its own types by "augmenting" them: a declare module "vitest" block that merges new names into Vitest's.
  • ui's test settings add two things, and these two blocks tell TypeScript about them:
    • inject("ci"): true on a CI runner, so a timing test can skip its budget
    • commands.emulateReducedMotion(): a browser command that turns on "reduced motion"
  • Only two tests use them, both in ui's tests: the dropdown's speed test and the reveal's test.
declare module "vitest" {
  export interface ProvidedContext {
    /** Running on CI:  skip timing budgets a shared runner can't hold. */
    ci: boolean
  }
}

declare module "vitest/browser" {
  interface BrowserCommands {
    /** Emulate (or stop emulating) `prefers-reduced-motion: reduce`, through Playwright, in every browser. */
    emulateReducedMotion(reduce: boolean): Promise<void>
  }
}

Why there are two copies:

  • The repo has two copies of Vitest on disk: the root's, and one of ui's own, in ui's node_modules folder. Both are version 5.0.1.
  • Yarn made ui its own copy because ui's dependencies differ from the root's.
    • Most likely the cause: ui lists @vitest/ui (Vitest's optional web screen), which the root doesn't.
    • spell lists it too, and spell has its own Vitest copy as well.
    • Not tried yet: that needs a yarn install.
  • An augmentation reaches only the copy of Vitest that ITS file finds, looking up from its own folder.
    • The original, in ui's helpers folder, finds ui's copy.
    • A test in the tests folder finds the root's copy, so the original never reached the tests.
    • That's why P10 wrote the copy beside the tests.

Who reads the original now: nobody, as far as a search finds.

Could one file at the tests root serve every package? It could be found, but it would claim too much.

  • Each package's tests have their own settings file in the tests folder (tests/<package>/tsconfig.json). Each one takes its package's settings and lists the folders it checks.
  • A file at the tests root would find the root's Vitest, the copy every package's tests use, so it would work.
  • But the two additions describe ui's test settings only. In any other package, inject("ci") would pass the type check and then be undefined when the tests run.
  • It would be right once more packages set the same two things. None does today.
