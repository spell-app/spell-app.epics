The model core (the core without drawing, which a library imports) leaves out two features that need a running program: references by name, and carrying a program over a recompile.

  • References by name, such as Tableau#T1 (references.ts), look the thing up in the running program's list of things.
  • Carrying a program over a recompile (carry.ts) reads that list too.
  • The model has no such list, so both stay out.
  • So a Loader made under the model must be given classNamed, the way to find a class by its name. Without it, it throws, and the error says so.
  • Over: putting a list of things into the model, which would bring the running program back in.
  • a library's code can't use Tableau#T1-style references
  • loading a saved file with a library means passing classNamed to the Loader

I think libraries should be able to use `Tableau#T1` syntax

They can, without bringing drawing or Solid in. The lookups are small and need none of it. The real question is WHERE a library looks a thing up, since a library has no running program whose things it could search.

  • "References by name" are spell's words for one thing: tableau T1 (by name) and the first tableau (by place). Both compile to a call on the core.
    • A reference written as text, such as Tableau#T1, is found by the same code.
    • So "supporting the syntax" means the model core (the core without drawing) gets those calls.
  • Today a library that uses them compiles, then fails when the line runs. I tried it against the model core:
thingNamed: undefined  thingAtPlace: undefined  things: undefined
calling it: core.thingNamed is not a function

thingNamed<T>(Class: abstract new (...args: never[]) => T, name: string): T | undefined {
  const { things } = spellCore
  for (const thing of things.all()) {
    if (thing instanceof Class && nameOf(thing) === name) return thing
  }
  const kept = things.exported[name]
  return kept instanceof Class ? kept : undefined

So where does a library look? Three ways:

  • The four lookups move into the model core, written against a small "where to look" shape.
  • In a running program, that's the program's own list of things, as today: nothing changes for programs.
  • Under the model, the caller hands one. The people store would: person Matt in a library's function finds matt among the people it loaded.
  • Nothing handed: a plain error saying to hand one, not "is not a function".
  • Size: about 100 lines moved, about 60 new (the shape, a loader as one, the error), and tests. No Solid problem.
  • Catch: "the first person" means the first one that store loaded, which is weaker than "the first the program made". 
import { spellCore, Loader } from "@spell-app/core/model"
import { Person, Relationship } from "./people.lib.ts"

const loader = new Loader({ entryFor, classNamed })
// inside, `person Matt` finds Person#matt among what the loader loaded
spellCore.lookingIn(loader, () => family.closest())
  • The running program's list moves into the model core too, its drawable classes added only by the full core: that removes the Solid import.
  • Every thing a library makes registers, as a program's does.
  • Cost: it undoes the Library Target's goal (P3) that things made outside a program stay out of the list.
  • On a server holding people from many spaces, it's one list for all of them: two people with the id owen, in two spaces, and Person#owen finds whichever was made first.
  • Size: about 250 of the 539 lines move, the rest (the Thing Explorer's) stay.
