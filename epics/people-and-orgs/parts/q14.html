How an upgrade step is written: what turns a spell:person@1 file into a spell:person@2 one when it's read (Q3). Most changes are a rename, a new property with a default, or a property dropped; a few need real code (splitting one name into first and last).

  • In the library, beside Person:
a person 2 renames name to names.
a person 2 adds nickname as text, empty.
a person 3 drops fax.

to upgrade a person to 4:
	- set its nickname to the first word of its names.
  • The three sentence kinds compile to data the store applies; the method runs for anything else.
  • Borrowed from Protobuf and Avro: a new property has a default, so an old file without it still reads.
  • upgrades.ts: one function per version, JSON in, JSON out.
  • No grammar work; but Person's history lives outside spell.
  • Files carry @1; an unknown version is refused. Upgrades come when the first one's needed.
  • Three more grammar rules (renames, adds, drops) and an upgrade method form
  • a test that reads a version 1 file and writes it back as the newest version

Owen picked A, with these changes, in his words:

to upgrade a person to version 4. NOTE: Version number is written into file as @version rather than file name. assume v1 with no @version specifier. We only need to increase version if existing properties change, not for new properties.

What that changes in option A:

  • The method reads to upgrade a person to version 4:, and the sentences say "version" too.
  • The version is a field of the file, "@version": 2, not part of its schema's name.
  • A file with no "@version" is version 1.
  • A new property doesn't bump the version: an old file without it still reads, with the default. So the "adds" sentence goes.
  • Renames and drops stay as sentences; anything else is the method.
a person version 2 renames name to full name.
a person version 3 drops fax.

to upgrade a person to version 4:
	- set its first name to the first word of its full name.
