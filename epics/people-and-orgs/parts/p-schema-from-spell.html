Yes: nobody has to write, read or keep JSON Schema. The spell declaration stays the one description of a type, the app and the command line check a file against the compiled class itself, and JSON Schema is made by a machine only for VS Code, which reads nothing else.

  • What this phase, Schema From Spell, has to give, whatever the format:
    • a saved file says what type it is
    • editors and tools can check it
    • an old version can be upgraded (Versions And Upgrades, P6)
  • The first is already settled. You picked C on the file's schema and version (J3, Q19): the schema line names the type's plain address, and its own key says the version.
  • So the question is only what CHECKS the file, and where the description of a Person comes from.

The example used below: a person with a name, an email and a list of friends.

a person is a thing where:
	- it has a name as text
	- it has an email as text
	- its "friends" is a list of people

// the saved file, __me.json5 (J3's option C:  $schema names the newest Person)
{
  "$schema": "@spell/library/people//Person",
  "$version": 2,
  "$type": "Person",
  "id": "owen",
  "name": "Owen",
  "email": "owen@example.com",
  "friends": [{ "$ref": "Person#matt" }]
}

What VS Code can and can't do:

  • VS Code's own JSON support underlines mistakes, offers property names as you type, and shows hover text, only from JSON Schema. It reads no other format.
  • It can fetch that schema from an extension, not just from a file or the web: the spell extension already serves made-up documents this way (the compiled-code view, through a content provider).
  • Any other format means the spell extension does the underlining itself, through spell's language server, and offering property names and hover text are ours to write too.

The four candidates, each shown for that Person:

(a) spell's declarations, served at the type's address.

  • Every compile already writes a declarations file. It's the compiler's own record of what a project provides, so other projects can use its words.
  • It describes a type, but loosely:
    • the list's kind is English, "list of people", which a checker would have to turn back into Person
    • "saved inline" isn't in it at all
    • its properties sit among the project's phrases and line ranges
{
  "spellVersion": "0.8.0",
  "provides": ["Person"],
  "statements": [
    { "type": "Person", "superType": "Thing", "defined": "/Friends.spell:0-115" },
    { "property": "name", "of": "Person", "datatype": "text", "defined": "/Friends.spell:30-51" },
    { "property": "email", "of": "Person", "datatype": "text", "defined": "/Friends.spell:55-78" },
    { "property": "friends", "of": "Person", "datatype": "list of people", "defined": "/Friends.spell:82-115" }
  ],
  "codeLines": [2, 3, 7, 11]
}

(b) the compiled class: the library's TypeScript, and what it carries at run time.

  • The library target (Library Target, P3) writes the class. Its TypeScript types vanish when it runs, but each property's description stays on the class: its kind, a list's item kind, its legal values.
  • That runtime description is what the saver and the loader read already. Util's schemaOf() gives it.
  • So a checker in the app or the command line needs no other file, and can't drift from the code.
  • VS Code can't check a JSON file against a TypeScript class: not by itself.
import { Thing, List, prop } from "@spell-app/core/model"

export class Person extends Thing {
  @prop({ type: "text" }) accessor name!: string

  @prop({ type: "text" }) accessor email!: string

  @prop({ itemType: "Person", init: () => new List<Person>({ instanceType: "Person" }) }) accessor friends!: List<Person>
}

// at run time:  schemaOf(Person).info("friends")  =>  { itemType: "Person", init: ... }

(c) a small shape format of our own, in JSON5.

  • The lightest thing to read: one line per property, in spell's words.
  • But it's a third description of Person, beside the spell and the class. Either someone keeps it in step, against the goal that the schema IS the declaration (Q3), or the compiler writes it, and then it's just another output nobody reads.
  • VS Code can't read it, so the language server does the underlining.
// what a person file holds
{
  $type: "Person",
  $version: 2,
  name: "text",
  email: "text",
  friends: "list of Person",   // each one saved as { "$ref": "Person#matt" }
}

(d) JSON Schema, made by a machine for VS Code only.

  • Made from the spell, in memory or in the build folder; never committed, never written or read by a person.
  • VS Code gets everything it does for JSON: underlines, property names as you type, hover text, legal values.
  • Checking with it outside VS Code would need a JSON Schema checker library in the app. Pairing it with (b) avoids that. 
{
  "title": "Person",
  "type": "object",
  "properties": {
    "$schema": { "type": "string" },
    "$version": { "type": "integer" },
    "$type": { "const": "Person" },
    "id": { "type": "string" },
    "name": { "type": "string", "description": "it has a name as text" },
    "email": { "type": "string", "description": "it has an email as text" },
    "friends": { "type": "array", "items": { "$ref": "#/definitions/Reference" } }
  },
  "additionalProperties": false,
  "definitions": {
    "Reference": {
      "type": "object",
      "properties": { "$ref": { "type": "string", "pattern": "^[A-Z][\\w-]*#" } },
      "required": ["$ref"],
      "additionalProperties": false
    }
  }
}

Half of it exists: the general function is there, and schemas already go to build/. What's missing is a command of its own.

  • The function: jsonSchemaFor(Class), in the core without drawing ($/core/model). It takes any spell type's class and returns its JSON Schema, read from the same property kinds the checker uses, so the two never disagree.
  • Writing to disk, today: only as a side effect of compiling a LIBRARY. spell compile @spell/library/people writes build/spaces/@spell/library/people/schemas/Person.schema.json, one file per type (writeSchemas()), and the repo's VS Code settings point __me.json5 and __org.json5 at them.
  • Why only libraries: a schema is made from the compiled class. A library compiles to classes node can load with no page (people.lib.ts); an app's program draws, so loading it needs the browser runtime.

Where a command would go, as the commands guide asks before one is built:

  • A bare command, as spell compile is: it's about the spell language, not the repo's tools.
  • spell schemas @spell/library/people compiles the project to a library if it's stale, then writes each type's schema into its build folder's schemas/, and prints the paths.
  • --out <dir> writes them elsewhere; --stdout prints one type's (--type Person).
  • A project with no ts/lib target is compiled to one for this run only.
  • spell compile keeps writing them too, so nothing you use today changes.
  • A new row on the commands page (commands.json), and spell dev commands check.
  • A flag on the command that already writes them: no new command.
  • Any project: compiled to a library for this run, its schemas written.
  • Harder to find, and --out / --stdout would mean something else on compile.

Either way, a small helper joins the function: jsonSchemasFor(library), every type of a loaded library at once, so the command and spell compile share it. Built as a new phase before Doc Review is redone, or a todo: your call.

From the judgement call on a file's schema and version (J3): a type's address may name one version, as in Person$v2, so this phase serves one schema per version.

  • The address form itself is read in One Address Scheme (P4); this phase answers it with a schema.
  • The plain address, Person, gets the newest version's schema.
  • The internal keys start with $ by now (P4), so the schema describes a reference as a property named $ref.
    • That's legal JSON Schema: a name under "properties" is a property's name, never a keyword.
    • VS Code's own JSON checker read a test person file written this way correctly.
    • But some tools follow every $ref in a schema, so no sample reference goes in its examples or defaults.
  • Whether a saved file's $schema names its version is still open (Q19); the schemas are served either way.
