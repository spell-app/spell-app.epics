The analysis wrote a file's type and version together, as "$schema": "spell:person@1" (Q3). Two of Owen's later notes pull it apart:

  • In a comment on the plan: schema references can come from any "spell address".
  • On upgrades (Q14): the version "is written into file as @version rather than file name".

Chose a spell address naming the type over keeping the analysis's form, because it then works for any type in any project, Owen's own included, and the version has a field of its own. 

{
  "$schema": "@spell:library/people/Person",
  "@version": 2,
  "nickname": "Owen",
  • VS Code can't read a spell address by itself: the spell extension turns it into JSON Schema (P5).
  • The address's exact form follows the address mapping question (Q15).
  • A file's "$schema" is the address of its type; its "@version" says which version
  • No version in a schema's name anywhere

`$version` rather than `@`. Keep the internal properties starting with `$` always. use `spell:person$v2" to refer to specific schema versions, so we don't conflict with `@` in addresses

Every internal key can start with $: I checked the clashes, and none is real. VS Code's own JSON checker reads a person file full of $ keys correctly.

  • An "internal key" is one the saved JSON uses for itself, never a property of the thing: its kind, a list's items, a reference, a version.
  • The file's type key already starts with a dollar sign, so today a person file would mix the two: $schema beside @type.
What it says Today With $ Where it's written
a thing's kind "@type": "Person" "$type" every thing's JSON: saved files, a page's state, the debug view
a list type's items "@items": [...] "$items" the same places
a reference {"@ref": "Person#matt"} {"$ref": ...} saved files

The clashes checked:

  1. JSON Schema's own keys. JSON Schema has its own $ref, $id and so on.
    • They're keywords only inside a SCHEMA.
    • In a data file, such as a person file, they're plain properties.

    What I checked:

    • I ran VS Code's own JSON language server on a test person file, written with the new keys throughout. It had three planted mistakes.
    • It underlined exactly the three mistakes, and nothing else.
    • The schema describes a reference as a property named $ref. That's legal: a key under a schema's "properties" is a property's name, never a keyword.
    • One rule for the schema writer (P5): never put a sample reference in the schema's own examples or defaults. Some tools follow every $ref they find in a schema.
  2. JSON-LD. The @ keys were picked as JSON-LD's spellings (decision Q49 of epic output-targets).
    • Nothing reads our files as JSON-LD: they have no @context. We lose only the look-alike.
    • The dollar sign has its own precedent: .NET's JSON libraries.
      • They write $id and $ref for a thing held in two places.
      • They write $type for a thing's kind.
      • Those are the same meanings as ours.
  3. Spell's own names. The @ was safe because no spell property can start with it.
    • The same holds for the dollar sign: a spell name starts with a letter.
    • Generated method names such as is_a_$suit have a $ inside, but they're methods, never saved.
  4. Addresses. This is the real reason for your $v2: @ already means a space or a place in an address.
    • owen@spell is a space; Person#matt@three-degrees is a thing in another place.
    • So Person@2 would read as a place called "2".
    • $ appears in no address form, so $v2 at the end of a type's address is unambiguous. 
// the schema, in part:  a reference is an object with one property, named "$ref"
"Reference": { "type": "object", "properties": { "$ref": { "type": "string", "pattern": "^[A-Z][\\w-]*#" } },
               "required": ["$ref"], "additionalProperties": false }

// the person file
{
  "$schema": "file:///.../schema.json", "$type": "Person", "$version": 2, "id": "owen", "name": "Owen",
  "dates": [{ "$type": "DatedEvent", "label": "birthday", "day": "1970-01-01", "oops": 1 }],

Question 1: which keys move to $?

  • All five keys in the table move, to sit beside $schema.
  • One rule to remember: $ means "the file's, not the thing's".
  • Cost: the 45 files above, once, before any file is saved for real.
  • Only $version is new, beside $schema.
  • The kind, items, reference and page number keys keep their @.
  • No churn now.
  • Cost: two prefixes for the same idea in every person file, for good.
  • Every internal key in saved files and a page's state starts with $, in both cores
  • The two shared expected files, the tests and the docs follow; two Spell UI bundles regenerated

Question 2: where does a file say its version?

  • Your spell:person$v2 in the address scheme's own form (Q15): @spell:library/people/Person$v2.
  • Your decision on upgrades (Q14) put the version in the file, and your note keeps a $version key.
  • The catch: VS Code asks for a schema by its address alone, not by the file it's for.
    • So it can only check an old file against ITS version if $schema names that version.
    • Otherwise a version 1 file is checked against the newest Person, and a renamed property shows as a mistake, though the store reads it fine. 
// A:  both
"$schema": "@spell:library/people/Person$v2",
"$version": 2,

// B:  the address only
"$schema": "@spell:library/people/Person$v2",

// C:  the key only
"$schema": "@spell:library/people/Person",
"$version": 2,
  • VS Code checks every file against its own version.
  • The store reads $version, as Q14 said; a save writes both, newest.
  • Cost: said twice. A hand edit that makes them disagree gets a warning from the store.
  • Said once, and VS Code checks each file against its own version.
  • No $version key, which your note and Q14 both asked for.
  • A file whose address has no $v is version 1.
  • As this judgement call stands, with $.
  • An old file shows false mistakes in VS Code until the app saves it.
  • Person$v2 is then used only where a version must be named, such as an upgrade sentence.

  • A file with no $version is still version 1 (Q14)
