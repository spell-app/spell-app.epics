How a saved file points at a thing kept in ANOTHER place: another project, or another person’s or org’s space. Owen picked the form that reads like a handle: the thing first, then @ and the place.

The question, from the issue about two ways to write a reference (I2):

  • Inside one project, a saved reference reads Person#matt: the type, #, the id.
  • That form is built and staged already, in both cores (it was Person/matt).
  • But a reference may point at a thing saved somewhere else, so it has to say WHERE.
  • A place is a whole address, as the address mapping decision (Q15) defines it: a space, and often a project in it.

The two forms weighed in the issue’s reply:

  • A, place first, like a file: @three-degrees:Person#matt
  • B, thing first, place after: Person#matt@three-degrees

Owen picked B, “Thing first, place after”: Type#id@place.

a person of an org        Person#matt@three-degrees
a card in Matt’s game     Card#26@matt@three-degrees:bubble-trouble
a thing in the library    Person#owen@spell:library/people

How a reference is read:

  • Everything up to the # is the type.
  • The id runs from the # to the FIRST @ after it; everything after that @ is the place.
  • So the place may hold an @ of its own: in Card#26@matt@three-degrees:bubble-trouble the place is Matt’s space at Three Degrees, project bubble-trouble.
  • That works only if an id can never contain @: an id with one is refused.
  • Inside the same project the place is left off: Person#matt, as today.

Nothing names another place until the address scheme exists, so this is built in One Address Scheme (P4).

  • Today: every saved reference is Type#id, in both cores
  • In P4: a reference to another place is Type#id@place
  • The reader splits it at the first @ after the #
  • An id may not contain @: making or loading one is refused
