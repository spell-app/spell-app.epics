Compiled code is hard to read against its spell: a class's "saved in its own file" comes last, long TypeScript decorators share their accessor's line, no property says which sentence made it, and the runtime is called spellCore.

The writers put a class's file setting first, and the spell sentence above each property; TypeScript's decorators with arguments go on their own line. Compiled javascript and TypeScript call the runtime core, as Python does.

  • A class's "saved in its own file" comes first, in spell and in what it compiles to. Owen: "When creating a spell thing subclass, it is saved in its own file should come first, before property specification. The JS/PY/etc output savedInFile should also appear at the top of the class definition."
    • In spell: the sentence is written first in a class's outline, in the people library and in the docs and examples that show it
    • In javascript, TypeScript and Python: static savedInFile = true (Python's saved_in_file = True) is the first line of the class body, wherever the sentence sits
    • saved inline, the same kind of sentence, goes first too
    • Why it's last today: the sentence is a member added from outside the class, and the writers add those after the class's own members (withProjectMembers()). Moving it in the spell changes nothing.
  • TypeScript's decorators: short ones on the line, long ones above. Owen: "when outputting decorators in typescript, if the decorator has no arguments, it should go on the same line as the accessor. decorators with arguments should be on the line above."
    • No arguments, on the member's line: @derived get state(), @drawn draw()
    • With arguments, on their own line above: @prop({ type: "text" }), then accessor names!: string
    • @thing, which marks a whole class, stays on its own line above the class: it isn't a member's
