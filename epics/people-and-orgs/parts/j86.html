what is another URL safe character we could use instead of `//`?

Short answer: ~ is the only candidate that passes every check, and only as a part of its own, /~/. Every other mark fails at least one place an address travels. Keeping // is still a fair choice, and the one I recommend.

@spell/examples/solitaire/~/Card.spell       a tilde as its own part
@spell/examples/solitaire~Card.spell         a tilde glued in:  breaks relative links (below)
owen@spell/~/__me.json5                      a space's own file, with the tilde

  • Why the mark must be a part of its own: a page's links are read relative to its URL. From /spaces/@spell/examples/solitaire~Card.spell, a link to Deck.spell lands on /spaces/@spell/examples/Deck.spell, OUTSIDE the project, since the browser drops everything after the last slash. With // or /~/ it lands beside Card.spell, where it should. So any mark, not just ~, has to sit between two slashes.
  • What the URL rules allow (RFC 3986): every candidate is legal in a URL's path as it is.
    • But the browser's own encoder, which our URL function uses, turns + , ; : $ into %2B %2C %3B %3A %24. Each would need the same exception @ has, or the URL stops reading as the address.
    • ~ ! * pass untouched, as // does.
  • What names may hold: a project, folder or file name may hold letters, digits, _ - . $ and a space (SpellLocation.isValidPathSegment()). So $ could clash with a name; none of the others can, so a reader would never mistake them.
  • Shell checks: from zsh's documented rules, not run: this agent's sandbox refuses to start zsh. Your ~/.zshrc turns on none of the options that would change them (extendedglob, for one). 
static isValidPathSegment(segment: string): boolean {
  const LEGAL_SEGMENT_PATTERN = /^[\w\d-$. ]+$/
  const SEGMENT_BLACKLIST = [".", ".."]
  return typeof segment === "string" && !SEGMENT_BLACKLIST.includes(segment) && LEGAL_SEGMENT_PATTERN.test(segment)

Everywhere, or only in URLs?

  • Only in URLs: the address keeps //, and URLs write /~/. This was J48's "other way", turned down.
    • A URL's tail stops being its address.
    • It fixes nothing you see: the address bar already shows // today, thanks to the shim (addressHistory(), since removed).
    • The conversion just moves, from the router's history into the URL function.
  • Everywhere: the address itself becomes @spell/examples/solitaire/~/Card.spell.
    • The router's shim goes, and so do two of J48's rules: nothing squashes /~/, and no URL can start with it and name another site.
    • Two rules stay: a ../ link still climbs over /~/, as over //; and an address is still encoded a part at a time.
    • The work: the two step constants, the splitting code, and a sweep like P4's. Today 36 files in the repo hold a two-slash address (119 lines), plus 18 shared pages.
    • The reading: three characters, not two, and ~ means "home" to anyone who uses a terminal.
  • Later, for hosting: if spell is ever served through nginx, its default (merge_slashes on) squashes // before it picks a route: one setting to turn off. /~/ needs none.
  • It reads naturally, and P4 built and tested it.
  • Only the app's router needs help: a small shim, with a test for pasting a URL, Back and Forward.
  • The browser and every /spaces/ and /api/ URL show the address exactly.
  • Cost: J48's four rules stay, and a future nginx needs merge_slashes off.
  • No shim, and nothing anywhere can squash or misread it.
  • Cost: a second address sweep (about 36 files and the docs); three characters; reads as "home"; the answer to the question on telling a file from a page (Q32) changes from //.
  • Addresses keep //; URLs write /~/.
  • Cost: a URL no longer shows its address, and the conversion moves rather than goes. Not recommended.
  • nothing changes: J86 stays as built, and J48's rules stand
  • if spell is ever hosted behind nginx, its setup turns merge_slashes off
