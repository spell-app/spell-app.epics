People, and the orgs (teams, groups) they belong to, each get a space of their own: a folder of projects, settings, docs and data, stored as readable files on disk and reached by addresses like owen@spell/solitaire. Person and Org are written in spell itself, then compiled for the app and server to use, so spell gets accounts, sharing and roles built from its own language.

It's time to add per-user and teams support to spell.

User = "Person" (never say "user")
People (aka Organization aka Org, aka Team aka Group)

A Person is a Thing. Let's try writing this as a spell and compiling it for use elsewhere.
- id (unique w/in org), names array, nickname, addresses, emails, "friend lists" (in various categories, e.g `family` is a friend group, user can store notes about each person in a friend group), dates (birthday, anniversary, etc), settings.
- each person gets an individual spell workspace (see below)

An Org is a Thing
- id (globally unique), name, nickname, description, members, permissions-per-member, public/private, settings. People have roles in an org, e.g. admin, readonly.
- "Teams" and "Groups" are aliases for Org -- exact same functionality, different names for different user segments
- each org gets its own workspace
- depending on org settings, each person in the org *may* get their own spell workspace (in additional to personal workspace)

Workspace:
- named for person or org
- folder of projects, files within that project
- root`$<name>` are special folders, e.g. `$settings`, `$sessions` (session data when playing a game, editor state when collaboratively editing), `$docs` (SpellWiki), `$data` (cross-project data).
- workspaces can hold: projects, library
- per-project-per-person roles which imply permissions, "admin", "editor", "viewer", "guest". Don't worry about per-file permissions
- workspaces can be public (anyone can join) or private (only members can see, must be invited, email-based invite flow)
- workspace-level notices

Addressing:
- `<person>@<org>` for person's account at an org
- `<person>@spell ` for personal (non-org) account
- `@org` for org-shared workspace. `@spell` is the "master" workspace for e.g. libraries shared by all, etc.

examples
- `matt@three-degrees:bubble-trouble/folder/file.json` is pointer to individual file in "matt" of "three degrees" org project "bubble-trouble"
- `owen@spell/solitaire` is link to running app of project `spell` in my account
- `owen@spell/solitare/rules` is link to running "rules" page in the same app
- `@spell/guides/how-to-create-a-spell-app` is link to running "How to Create a Spell App` guide defined by the system

Default is to store all data in FILES ON LOCAL DISK -- have a `StorageAdapter` abstraction so we can swap out for e.g. S3 or Git.
All file formats should be human-parseable if at all possible (JSON, markdown, etc)
Storage should be granular - editing smaller pieces makes conflicts less likely.
OK to create and maintain indices for sets of data e.g. in a folder. Index setup for file type is automatic, schema'd and versioned. Look for a good schema mechanism that is NOT JSONSchema, but is declarative, friendly and expessive.
Assume we have CRDT-like mechanism for multi-user editing and collaborating in apps.

Explore using `hjson` for structured file storage over json. MUCH easier to read and more forgiving, comments are key. Assume we can have conventions like `@type` and `@id`.

Assume you can communicate with anyone in your workspace with their handle.
Assume email-based signup, oauth fast follow. Should tie into e.g. auth0 or okta without too much trouble, but quite a bit later.
