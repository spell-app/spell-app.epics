Owen (2026-10-04) on the first <ui-brand-color-picker>: "that triangle just looks weird" -- its OKLCH Lightness × Colourfulness plane only shows the triangle of each hue that a screen can show. He asked for an HSL picker, so the plane is now the HSL square for the current hue: saturation 0 -> 100% across, lightness 100% (top) -> 0% (bottom). Every point is a real sRGB colour: no hatch, no gamut mapping on the square.

The alternative is the HSV / HSB square most design tools use (Figma, Photoshop, macOS): saturation across, brightness up, so the top-right corner is the PURE hue and the top edge runs white -> hue; in HSL the pure hue sits in the MIDDLE of the right edge (L 50%) and the top edge is all white. HSV makes vivid colours easier to hit; HSL matches the HSL row's numbers and CSS's hsl() one to one. Switching later is the square's two gradients, the pointer / key mapping and the conversions (Palette would need hsv).

The square is CSS, not a canvas: HSL is linear in (gamma-encoded) sRGB along both axes, so a grey -> pure-hue gradient (the L 50% row) under white / black fading over the top / bottom halves is EXACT, all in srgb. Measured against Palette.hslToRgb() at six points: within 1-2 / 255 per channel (8-bit rounding). A hue change only repaints; nothing is computed per pixel. The hue slider's rainbow is static CSS too (HSL is linear per 60°).

Net effect:

  • no triangle: a full square of real colours for every hue
  • HSL row numbers and the square agree; a vivid colour is at the right edge's middle, not its top
  • no canvas, no redraw cost
