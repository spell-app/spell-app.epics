You asked for an analysis. Today's <ui-field> is Fomantic's .field: a block with a label above a control, which the form finds and puts error messages into.

  • It draws <div class="field"><slot></slot>, plus an error "prompt" label. The label appears when the form calls showErrors().
  • Attributes:
    • state: error, info, success, warning
    • required: an asterisk
    • inline, disabled and width
  • No label attribute: you write the <label> yourself.
  • No place for help text, buttons, a value readout or an info tooltip.

What the brand's inspector field (the Color Set Chooser's "Vibrancy" row) needs:

<ui-brand-field label="Vibrancy" value="100%" info="How saturated the middle steps are.">
  <ui-button slot="actions" size="mini" circular icon="rotate left">Reset</ui-button>
  <ui-slider min="0" max="200" step="20" ticked></ui-slider>
  <span slot="help">Above 100% can leave the sRGB gamut.</span>
</ui-brand-field>
<!-- draws:  Vibrancy ............ [Reset] 100% (i)
               ===========o==================
               Above 100% can leave the sRGB gamut. -->

Every one of these could have been added to <ui-field> without breaking old markup. You chose a NEW element instead, <ui-brand-field>, and to leave <ui-field> as Fomantic's (D3).

  • <ui-brand-field> also answers to the form the way <ui-field> does, so form validation errors show in it. It has :state(field) and showErrors().
  • Whether the two merge is for the follow-up epic that moves the brand elements into Spell UI (T2).
