Nobody can see what the parser and Spell UI learned since the examples were last brought up to date, so the content falls behind (Overview 1.4).

  • One command lists what's new since the last content update: commits in the parser and Spell UI with their epics, the changelog entries of those epics, new components, new grammar.
  • A standing set on this page, "Upgrades on offer", grows as the session finds features worth showing; you tick any of them, add your own, and press Send.
  • Your ticks become a "Content Update <date> <time>" phase, built like any other; the rest stay on offer.
  • Features you said to always upgrade are done without asking; ones you turned down (removed from the set) aren't offered again.
  • The phase ends by running it: the set holds its first features (Q6, J3).

spell content update gathers what changed since the last update; the session adds the features it finds to a standing set on this page, "Upgrades on offer"; you tick and press Send, and your ticks become a Content Update phase (J3, folding in the old P4).

  1. What it remembers, in two places, neither of them shipped with the examples:
    • your picks and turn-downs are the standing set itself: ticked options are stamped Picked, turned-down ones Removed; read back with epic items content --json
    • the commit the last update stopped at, and the "always upgrade" rules, in content-updates.json5 in this epic's shared folder, as the coherence score keeps its snapshots in its epic's (ScoreSnapshots)
  2. The command, spell content update [--json], beside check; one class gathers, the command prints. It reuses what the repo has (app may use the epic folder's code: it sits above it):
    • commits under parser/ and ui/ since the stop commit, through the kit's Git; each subject read by PlanCommits.parseCommitSubject(), so they group by epic
    • each of those epics' changelog entry, one lookup per epic (EpicDocs.changelogEntry())
    • new components: Spell UI's component data (components.json5) at the stop commit against now
    • new grammar: the parser's syntax table (spellSyntax.json) the same way
    • anything matching an "always" rule, or an option already on offer, picked or removed, is marked so
  3. Recording an update's end: spell content update --done [--always id ...] moves the stop commit to now and adds to the always rules.
  4. The standing set (J3), with epic-engine's P50 tools, already on main:
    • made once: epic add content#choices "Upgrades on offer" --multiple
    • each update run: the session turns the new changes into features worth showing (the judgement stays with it), each with the examples and notebooks it would touch, and adds each with epic option add content#s-upgrades-on-offer "Title" "note"
    • you tick and press Send; the session makes a "Content Update <date> <time>" phase from the ticks, and builds it as any phase here
  5. The steps written down: README-examples gets "Keeping the examples current": run the command, add the features, build the picks.
  6. Tests: a throwaway git repo with a few commits; the always / picked / removed marking; the component and syntax diffs on small samples.
  7. The first run, as this phase's last step: run it, and fill the set with its first features.
  8. Checked: yarn review, spell commands check; a short doc pass, changelog entry, merged into main.
  9. Left out: an "Update now" button of its own: Send does it.
