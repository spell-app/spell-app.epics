Owen's comment C10 on the guide's limit "VS Code on macOS": "phase to get VSCode on other machines working".

What assumes macOS today (found by reading the code, 2026-10-29):

  • Every process, by pid: ps -axo pid=,ppid=,comm= (processTable(), the window script). Linux's ps takes it; Windows has no ps.
  • A process's folder: lsof -a -d cwd (the window script, Sessions, CheckoutServers). Linux often lacks lsof, and has /proc/<pid>/cwd; Windows has neither.
  • Running VS Code: spawnSync("code", ...). On Windows the command is code.cmd, which needs a shell.
  • Links: the session folders' link, the plugin's cache and skill links, ~/.local/bin/epic. Windows makes a folder link only as a junction, and a file link not at all without Developer Mode.
  • A pasted picture in the Review tab: AppleScript only (clipboardImage(), DocView); elsewhere nothing happens.
  • The extension is built and installed by hand (yarn package, code --install-extension).

Outcomes:

  • Linux works in full: window moves, handoffs, the Review tab, pasted pictures (wl-paste or xclip).
  • Windows works for everything but what needs a file link, which says so in one line and how to turn on Developer Mode.
  • Tried by real people (Owen's comment C3): a Windows developer is ready to test it, and a Linux one is being found.   • One helper per job, in the kit's spell/server where the kit needs it too (CheckoutServers uses the kit's server finder): no process.platform test scattered through callers.
  • The extension installed by epic init (P13's plugin step), from the .vsix the published package carries.
