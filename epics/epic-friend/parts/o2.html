The plans stay in their own content repo, now with a remote that everyone pulls from and pushes to. The review inboxes stay on each machine.

  • Where the plans live: the content repo gets a remote, and the config names it so epic init can clone it. The other way, keeping the plans inside the code repo, is Q1.
  • Keeping in step: the end-of-turn commit (epic shared commit) gains a pull before it and a push after. Whether that happens on its own or only by command is Q5.
  • What conflicts when two people change one epic page, as the code is today:
    • The page's updated date, which nearly every command rewrites. A merge can take the later of the two.
    • New item ids: each is the highest number plus one, so two people both make T22. Git merges them cleanly, and the page then has two items with one id. Q6 is how to fix that.
    • The log: both sides add lines at the end. Git's "union" merge setting keeps both, in the content repo's attributes file.
    • Each item's and each phase's body is a file of its own, so edits to different items don't touch each other.
  • The review inboxes stay local, as they are today. That's where each page keeps marks, comments and which session is listening.
    • The file is rewritten whole on every change, and holds a heartbeat that updates every 30 seconds.
    • Each person's marks and comments go to their own Claude session. That session writes the answer into the epic page, under the person's name, and the page itself is shared.
    • Whether others should see a comment thread before it's answered is Q4.
