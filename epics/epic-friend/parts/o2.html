The plans stay in their own content repo, now with a remote that everyone pulls from and pushes to. The review inboxes stay on each machine.

  • Where the plans live: the content repo gets a remote, and the config names it so epic init can clone it. The other way, keeping the plans inside the code repo, is Q1.
  • Keeping in step: the end-of-turn commit (epic shared commit) gains a pull before it and a push after, on its own, every turn, whenever the content repo has a remote. epic shared sync does the same by hand. A conflict it can't settle stops the sync and says so; offline, it commits and pushes later.
  • What conflicts when two people change one epic page, as the code is today:
    • The page's updated date, which nearly every command rewrites. A merge can take the later of the two.
    • New item ids: each is the highest number plus one, so two people both make T22. Git merges them cleanly, and the page then has two items with one id. So the sync looks for duplicate ids after each pull, and gives the LOCAL one the next free number (T22 becomes T23), its part file and every link following, with a log line saying so.
    • The log: both sides add lines at the end. Git's "union" merge setting keeps both, in the content repo's attributes file. The log is a file of its own (parts/log.html), and the sync then sorts its lines by time, so a merged log reads in order (O2).
    • Each item's and each phase's body is a file of its own, so edits to different items don't touch each other.
  • The review inboxes stay local, as they are today. That's where each page keeps marks, comments and which session is listening.
    • The file is rewritten whole on every change, and holds a heartbeat that updates every 30 seconds.
    • Each person's marks and comments go to their own Claude session. That session writes the answer into the epic page, under the person's name, and the page itself is shared.
    • So a comment thread reaches the rest of the team only once it's answered, for now. A later phase shares comments through git before they're answered: the inbox split into a shared part (comments and marks, by person) and a local part (who's listening, the heartbeat), and a rule for whose Claude answers.
