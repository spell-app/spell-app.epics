Every plan-doc command reads the skeleton and all its parts as ONE document, then splits it again on write. In between, it runs exactly the code it ran before.

  • The reading: read(), which calls assembleParts().
  • Not chosen: teaching each command where its piece lives.
  • Why: the 4000-line tool stays unchanged, and both shapes (split, one file) work for every command at once.
  • Cost: a few ms to read about 100 small files.
    • An edit takes about 0.15 s inside the process.
    • The CLI's start-up is most of a command's time.
  • Where each body goes is decided by rule, on every write:
    • an item that gains details gets a part
    • a new Overview sub-section written into the skeleton by hand moves into a part on the next command
  • Content a host holds BESIDE its part is kept, after the part's: nothing is ever dropped.
    • A hand edit, or an older checkout writing into an empty panel (e.g. commit --item).
  • Readers of the skeleton alone needed no change: statuses and item lines stay in the skeleton.
    • The docs index, the main server's epic cards, the inbox's item ids.
  • plan-doc works on split and one-file docs alike.
  • These switch shapes:
    • split <name>, or split --done
    • join <name>
