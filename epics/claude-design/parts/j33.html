Every plan-doc command reads the skeleton and all its parts into ONE document (read(), assembleParts()), runs exactly the code it ran before, then splits it again on write. Chose this over teaching each command where its piece lives, because it keeps the 4000-line tool unchanged and makes both shapes (split, one file) work for every command at once.

  • cost: a few ms to read about 100 small files; an edit takes about 0.15 s inside the process (the CLI's start-up is most of a command's time)
  • where each body goes is decided by rule on every write, so an item that gains details gets a part, and a new Overview sub-section written into the skeleton by hand moves into a part on the next command
  • content a host holds BESIDE its part (a hand edit, or an older checkout writing into an empty panel, e.g. commit --item) is kept, after the part's: nothing is ever dropped
  • readers of the skeleton alone (docs index, the main server's epic cards, the inbox's item ids) needed no change: statuses and item lines stay in the skeleton

Net effect:

  • plan-doc works on split and one-file docs alike; split <name>, split --done and join <name> switch shapes
