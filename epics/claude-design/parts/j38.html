Spell UI's design generator reads the brand's elements as data, so they reach the design system. Nothing is imported: ui still depends on nothing of brand.

  • Not chosen: moving the export to a docs or cli tool.
  • Why: the generator already read a brand file the same way, the brand book's CONTENT FUNDAMENTALS.
  • Chosen: DesignBrand reads:
    • the brand's site data, components.json
    • the shared brand pages, one per tag (brand/components/<tag>.html)
  • DesignComponents merges it in as a second source: every family in a Brand group, last.
  • The editor manifests go the other way round (brand may import ui):
    • brand's site data script (site-data.ts) runs Spell UI's ElementManifests on its own data
    • it writes brand's custom-elements.json and html-custom-data.json
    • the repo's VS Code settings (settings.json) load both packages' files
  • Rejected:
    • one combined manifest written by ui: ui would have to know where brand's element classes live
    • a docs tool doing the export: it would move P7's whole generator
  • spell dev design build makes 70 cards: Spell UI 59, Brand 11.
  • The types file (index.d.ts) has every brand element's props type.
  • VS Code autocompletes <ui-brand-*> tags and attributes in any .html file, after a window reload.
  • After changing a brand vocabulary: yarn site:data in packages/brand. The design build then picks it up.
