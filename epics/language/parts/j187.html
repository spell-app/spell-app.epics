What exists today:

  • spell compile turns each Card.editor.html into Card.editor.js, a module defining <card-editor>, its layout and Card's properties written into it (PropertyEditorPages.compile(), from EditorPages).
  • Nothing in the editor loads that module: not for an .editor.html either.
  • The Inspector draws a type's own editor by reading its markup from the file (propertyEditorInSource()), inside ITS OWN <ui-property-editor>: the running class's properties, where each value comes from, Spanish names turned into the class's.
  • Card.editor.spell is opened as plain text (getFileForPath()), and left out of every compile.

So "compiled" can mean, in this order of size:

  1. Parsed: the file is one of the project's spell files, read by a rule for <property-editor "card"> (and <editor-de-propiedades "carta">, the plain head), its body kept as markup. card is a reference to the type: a wrong name is an error, and hover / go to definition work on it. Nothing goes into the program.
  2. Compiled: spell compile writes Card.editor.js from it, the same module the same layout as an .editor.html gives.
  3. Used: the Inspector loads that module instead of reading the markup.

1 and 2. The Inspector's card stays byte-identical, since it still reads the same markup. A phase of its own: a parser rule whose body is markup, the file joining the project's compile (the program, the words file and the scope pack must all leave it out), Spanish, the CLI writing the module. More than a day.

1, 2 and 3. Changes the Inspector's design: the module carries the properties as last compiled, not the running class's (epic property-editor Q18, "both"), and knows nothing of where values come from or of Spanish names; and the editor in the browser would have to build and import a module per type.
