A local hides the property from where it's made, to the end of its block. That's allowed, but warned. 

shuffle the stock          // this.stock.shuffle()
set stock to 3             // a new local, with a warning:  const stock = 3
print the stock            // the local, 3, with a warning
print its stock            // still the property
  • The same word can therefore mean two things in one action. Reading the X where a local or argument hides a property warns; the fix is its X, or renaming the local. The corpus has 17 names like this today: 9 locals and 8 arguments or loop variables. Making a local that hides a property warns too, so the 9 locals get warnings; the 8 arguments and loop variables warn only if read with the.
  • An argument hides a property too: in to go on (a pile), the pile is the argument, and its pile the property.
  • Locals stay block-scoped: after if ...: set score to 1, the local is gone.

The trap was writing. Today set the score to 1 makes a local, which would sit beside reads of the property and silently lose the write. So it will write the property instead: 

if the side is front        // this.side
  set the side to back      // today:  { const side = "back" }, the property never changes
                            // after:  this.side = "back"

Rewriting today's 277 its X reads in actions to the X, as a test, showed what else has to be right:

  • 18 of 480 files compiled differently, and 12 errors appeared, 5 of them in a file that already fails.
  • Most of it was set the X making locals: 52 this.X = lines were lost.
  • Some was properties declared below their use: Solitaire.spellml reads its clubs above its property.
  • One looks like a gap in the prototype, though its cause isn't fully traced: the position of the rank lost its enum lookup.
