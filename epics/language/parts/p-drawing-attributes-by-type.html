In a drawing, a value worked out needs braces, disabled={its count is 0}, while quotes mean text: two marks for a layman to learn.

Owen's words (2026-11-10): “can we make static and dynamic both work with quotes rather than distinguishing between "literal value" and {dynamic value}? Would be a lot easier for a layman to grok if we didn't need the curlies.” For a drawing's attributes: “let's try by type. You should always be able to use {...} for dynamic values.”

  • A component's quoted attribute is read by the attribute's own type:
    • a yes-or-no, number, list or thing attribute reads its quotes as Spell: disabled="its count is 0", visible="it is face up", options="the recipe's cuisines", <ui-form value="the draft">
    • a text attribute's quotes stay text: label="Save", link="/recipes"
    • a text worked out keeps braces, label={its title}, or a fill-in inside the quotes, which text already takes: label="[its title]", src="images/[rank].png"
  • A literal of the attribute's own type stays that literal: columns="3", open="false", open="0" mean what they mean today. Only a value that isn't one is read as Spell.
  • An event handler, onui-changed="set its name to the event's value", always holds steps, so its quotes read as Spell, as HTML's onclick="..." does.
  • Braces always work, on any attribute, and mean what they mean today.
  • An attribute with no known type stays text, as today.
  • Both languages: Spanish components' attributes by the same types.

  1. Wait for P42 and P43: single-quoted text inside a Spell value comes from P42, and the rule is the same one.
  2. An attribute's type. Where it comes from, first match wins:
    • a project's own view: its property's datatype (P.ScopeVariable, found as SpellJSX's P39 check finds a view's member)
    • Spell UI: the attribute's kind in its vocabulary (UI<Name>.en.ts, through SharedVocabulary.attributesFor()): boolean and keyOnly are yes-or-no (101 and 309 attributes), number a number (43), json a list or thing (35); string, enum, color, size, icon, width, the alignments and multiple are text, a value from a set staying a word
    • a platform attribute (href, src, class): text
    • none known: text, as today
    The parser folder never imports Spell UI, so its kinds reach the parser as data, the way translate's uiVocabulary() hands Spell UI's names in; a small table of attribute kinds, built with Spell UI's catalog, beside the element pack the editor already loads.
  3. Reading. In SpellJSXAttribute.parse(), a quoted value whose attribute is yes-or-no, number, list or thing: a literal of that type stays the literal; otherwise it's parsed as an expression, exactly as its braces would be. Its text inside is in single quotes (P42's rule). A [name] fill-in in a text attribute reads as today.
  4. Highlighting. A quoted value read as Spell is coloured as Spell, not as a string, in the editor, VS Code (the language server's semantic tokens) and <spell-code>, so a person sees which is which.
  5. The rename. A spell rename codemod turns braces into quotes on the attributes whose type reads quotes as Spell, in the built-in projects and docs, so the examples people copy show the quoted form; a worked-out text keeps its braces. Whether it rewrites them at all is Q46.
  6. Tests. Each kind, in quotes and braces, in English and Spanish: a yes-or-no, a number, a list, a form's thing, a handler; literals ("3", "false", "0") unchanged; a text attribute's words staying text; an unknown attribute staying text; a project's own view by its property's type.

Census of the braced attributes in the built-in projects' drawings, measured 2026-11-10 (427 in all):

  • yes-or-no, about 70: disabled (32 with Spanish desactivado), active 13, visible 10, selected 13, remember 1: become quotes
  • a form's or a control's bound thing, about 70: value on form / ui-form / formulario 65, ui-textarea, ui-tabs: by its control's own kind; a form's is a thing, so quotes
  • lists and numbers, about 12: options, items, rows, columns, tree, offset, max: become quotes
  • handlers, about 6: onui-changed, on-ui-stuck ...: become quotes
  • text, about 70: link 26, src 10, an item's value 22, color 5, title 4, class 2: keep braces, or a [...] fill-in in quotes (Q46)

The risk: a quoted value's meaning follows its attribute's type. A project's own card view with its "badge" is text draws <card badge="the winner"/> as the words “the winner”; change it to its "badge" is a person and the same line reads the winner as Spell. So:

  • the highlighting shows which it is (step 4)
  • a quoted value read as Spell that doesn't parse is an error naming the attribute's type, never silently text
  • a type change that turns quoted text into Spell shows as a changed program in its project's compiled diff
