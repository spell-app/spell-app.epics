Solid 2 changes the answer: a getter that waits no longer has to be an error. A draw can read one with no Spell syntax, show "…", and fill itself in. I tried this in real Chromium, with Spell's real drawing code on Solid rc.17. It works, but only with one particular Solid tool. The obvious tool freezes a deal partway through.

How Solid 2 handles a slow value

  • A memo is a remembered calculation. In Solid 2 a memo may return a promise, which is a value that arrives later.
  • Reading that memo before its first answer throws a special error, NotReadyError. It means "not yet", not "broken".
  • That error passes straight through any plain getter on its way up, to the nearest <Loading>, which shows a stand-in. Solid then re-runs the read when the answer lands.
  • Later changes keep the old value on screen, and isPending() says a new one is on its way.
  • Spell's getters are already plain JavaScript getters, so the "not yet" gets through them untouched.

What it could compile to

// the score:  wait for the server, then the rank + the bonus
get score() {
  return core.slowly(this, "score", async () => { ... })   // one createDeferred per thing and getter
}

draw() {
  return h("div", "Moves: ", () => this.moves,
    " Score: ", core.waiting(() => this.score))            // <Loading fallback="…">, only where the pass says it waits
}

What Spell would show

  • First load: "…" where the value goes, and the rest of the page draws.
  • A later change: the old value stays until the new one lands, and the rest keeps moving.
  • An if or an attribute that reads it: there's no spot for a "…", so the thing's whole drawing shows "…" first, and that thing is drawn again when the answer lands.
  • A failure: the thing's usual "can't draw" stand-in, and it heals when a later answer works.
  • No <Loading> at all: the whole app stays blank until the value lands, with a warning in development. So Spell must always supply one.

The surprise: which Solid tool matters

A plain async memo holds back drawing. Any write in the same moment as the one that set it off waits for the answer, as do later writes that thing draws. Here's a four-step deal, whose step 2 changes what a 100 ms getter reads: 

                 step 1            step 2            step 3            step 4
createMemo       dealt 1 slow 10   dealt 1 slow 10   dealt 1 slow 10   dealt 4 slow 20    frozen, then a jump
createDeferred   dealt 1 slow 10   dealt 2 slow 10   dealt 3 slow 10   dealt 4 slow 20    every step shows
  • createDeferred is new in rc.16: "a refetch holds nothing". Its value may lag, but the rest of the screen moves on.
  • So a waiting getter would have to be a createDeferred, never a plain memo.

Getters that wait, read from each place

  • A draw: works as above, and a plain getter over it (the score + 1) too.
  • An action: a bare read throws the "not yet" error on first load, so the pass must add a wait.
    • This one is unsolved: just after a change, Solid's resolve() still gave the old value (30, not 50).
    • refresh() gave the right one, but it runs the slow work again.
  • A sort or where: as today's option A, an error for a sort, and one by one for where. I didn't try these.

Three traps for the compile-time pass

  1. Reads after the first wait aren't followed. A getter that read the bonus after its wait stayed at 4 when the bonus became 100. The fix may be to read everything before the first wait, or to warn. Neither is tried.
  2. A remembered getter over a waiting one stays wrong for good. Over derive() it stayed at 31 after the rank changed, when it should have been 41. Compiled TypeScript puts @derived on getters that loop, so the pass must leave it off these.
  3. A raw promise in a draw is a failure. A live value holding one shows "can't draw". So the getter must be compiled as above, and just marking it async won't do.

Other targets

  • ts/solid has Solid and real JSX, so the same design should carry over. Not run.
  • ts/lib keeps only the classes and never draws, so a waiting getter there has no draw to worry about.
  • py has no Solid on the server, where it draws HTML as text. A waiting getter there would be an async property, and that drawing would wait for it before sending the page, with no "…". Its page's drawing half is JavaScript. All of this is from reading the code, and not run.
  • So the words stay the same, but what shows meanwhile would differ by target.

Q6's queue and what draws mid-action

  • Solid's action() doesn't fit. It holds the drawing until the whole action ends. A three-step deal showed "dealt 0" throughout, then "dealt 3".
  • It has no queue either: each call starts by itself, and Solid's docs set no order between them. It also can't be called from a draw, which fails with ACTION_CALLED_IN_OWNED_SCOPE.
  • A plain async action, what Spell writes today, does fit. Every step drew in turn. So the Q6 queue stays Spell's own.
  • The prototype we flagged (o5): an await that doesn't really wait changes the page's contents but not what's seen. Three writes with two such awaits between them changed the page three times, and only the last was painted. This was a tiny case, not Solitaire.
  • Spell's properties and Solid's signals differ: a property reads back its new value at once, even while its drawing is held back. So code and screen can disagree during a hold, which is another reason to avoid holds.

You asked: "Would this be simpler if we ditched the JS output target and just supported TS and Python?"

No, it wouldn't make waiting simpler, and I'd keep JavaScript. This is from reading the code; nothing was tried.

  • The waiting work sits below the writers. Which actions wait is worked out once for every target, and a draw's "not yet" comes from Solid when the code runs. Neither depends on which language is written out.
  • The TypeScript writer is built on the JavaScript one. It extends JSWriter and adds only types, decorators and JSX, so those 1,584 lines stay either way.
  • JavaScript is what runs. The editor, the runners and spell run all run js/solid. Without it, the TypeScript would need compiling again, through Solid's JSX compiler, on every edit.
  • The real split remains. Python has no Solid, and ts/lib never draws, so both still need their own answer for a slow getter.

What it could save is one of two drawing shapes, since JavaScript and TypeScript write a draw differently. That's a separate question from waiting, worth raising only if those two start to disagree.
