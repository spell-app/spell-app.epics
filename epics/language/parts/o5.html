Proposed: an action just waits for anything slow it calls, so nobody writes animation, animated or wait for:. Nothing is built yet, and these phases aren't planned yet. 

// today
- animation deal the cards:
  ...
  wait for: play from the stock

// proposed
to deal the cards:
  ...
  play from the stock

How it works today

  • JavaScript and TypeScript wait only where the source says so. An action is asynchronous only if its own body has a literal wait.
  • Python already waits by default: its writer works out, across the whole project, which actions wait and marks their callers.
  • So one program can run differently by target: Solitaire's start a new game doesn't wait for the deal in JavaScript, and does in Python.
  • Leaving out wait for loses errors, and some forms go silently wrong: if slow value is 5 compares a promise (I2).
  • Small corpus: 4 animations and 17 real wait for lines, all in Solitaire, Solitario and Carta.

How it would work

  • The Python writer's project-wide pass moves down to be shared by every target, starting from what is slow: pause, dialogs, sending, and anything calling those.
  • It's a compile step, not a new engine: the output is ordinary async and await, as Python's is now.
  • Speed isn't the concern: a deal-sized run of 10,400 calls, each awaited, took 0.68 ms.
  • Other languages: _hyperscript and AppleScript wait by default too, and Scratch and Go use their own schedulers or stacks, which plain JavaScript output doesn't have (Q5).

What it changes for someone reading the code

  • A second click: animation also meant "ignore a repeat while it runs". That needs a new home (Q6).
  • Overlap: for each card ... move it starts every move at once today, and would run one by one, so overlap needs its own words (Q7).
  • Same-named actions: the pass joins by name, so one slow play makes every play wait. Harmless to run, though outside JavaScript callers get promises from more methods.
  • Where waiting can't happen: getters, draws, predicates such as where, and sort comparisons (Q8).
  • Opening a program: the top level must not hold the first draw until a deal finishes; today JavaScript shows the deal only because start runs mid-deal.
  • Interleaving: other things can still happen during a real pause, so the queue in Q6 is what protects the step-by-step picture. Two unguarded deals over 3 cards dealt card 3 twice.

Not yet tried: how the extra awaits change what Solid draws mid-action, in a browser. That's the first prototype. One oddity is unsettled too: the running flag is keyed by name, yet one test ran a second thing's action.
