The parser engine (tokenizer, base rules, Rulex matching) is plain TypeScript, and its time grows as the grammar grows: every statement rule is tried on every line, about 600 quick tests per line of Solitaire, and 94% of them say no.

Parse faster, with evidence: each line tries only the rules that can start with its first word, shipped builds stop checking every match's types, and the question of a compiled engine is answered with numbers and written down.

Owen's idea: write the tokenizer, base rules and Rulex engine in WebAssembly or a compiled variant of JavaScript, leaving what happens with each match in TypeScript.

Measured, the compilable parts are at most 54% of the time, and each rule's TypeScript would still be called 63,000 to 155,000 times per Solitaire parse. So this phase makes the TypeScript faster instead: a first-word index on Choice, and no type checks on each Match outside tests. The compiled engine is recorded as rejected for now, with what would change that.

Recommendation: don't compile the engine now. Make the TypeScript faster first. A throwaway first-word index, about 40 lines patched in, took 21% off a warm Solitaire parse with identical output. A compiled engine could not honestly promise more than that, and it would mean rewriting the engine and adding a build step the whole repo depends on.

This plan builds the TypeScript speedup, measures it, and writes down when a compiled engine would be worth another look.

What was measured

The test: Solitaire, 5 files, 530 lines. The machine was busy (load 20 to 33 from other sessions), so the percentages are more trustworthy than the milliseconds, and the comparisons take turns inside one process so the load hits every side alike.

Where a warm parse-and-compile spends its time Share Could be compiled?
Rule matching: Choice, Sequence, Subrule, literals, making Match objects, finding rules by name 44% Yes, in principle
Tokenizing (4.3 of the 9.9 points are the scan for declarations before the real parse) 10% Yes
Each rule's own TypeScript during matching: parse() and test() overrides, scope lookups, reading groups 31% No: this is what stays in TypeScript
After matching: changing scopes, building the AST, writing code, warnings 13% No
Garbage collection and native code 2% No
  • The ceiling is 54%. If the compiled parts took no time at all, the whole job would be 2.2 times faster, and no real compiled engine gets close to "no time at all".
  • On the very first, cold parse the compilable share is smaller: about 41%.
  • Warm Solitaire took about 336 ms of processor time. The docs' older figure (about 110 ms) is from a smaller grammar and a quieter machine.

The boundary: how often the engine would have to call TypeScript

Counted in one real Solitaire parse:

What Count Per line
Quick syntax tests (Sequence.test()), 94% saying no 320,566 605
Calls into a rule's TypeScript the engine could not skip, at most 155,000 290
The same, if hooks only ran after a full syntax match, at least 63,000 120
Match objects made / still in the final tree 18,079 / 4,590
Rules added while parsing or just before 212
  • Why the hooks can't simply go away:
    • Whether card is a word in this line depends on what's declared so far. KnownVariable, KnownType and KnownConstant ask the scope, and those three rejected about 2,000 syntax matches here.
    • Rules with real logic, such as DynamicMethodRule checking that arguments fit, can't become data.
    • There are 188 parse() overrides and 46 test() overrides in the language's code; 128 and 28 of them ran in this one parse.
  • To run without those calls, all of this would have to change:
    • a copy of every scope's names kept inside the engine, rewound and replayed with the journal for incremental parsing
    • compiled rule tables updated on each of those 212 additions, since rules appear mid-parse and Rulex compiles at run time
    • give-back, and expecting mode for editor completion, rewritten in the engine
    • Pattern rules (26,000 regular-expression checks) given a regex engine of their own, or calling back to JavaScript
  • And Match objects and token strings still have to exist in JavaScript, because the AST, the writers and the language server all read them. So part of the 44% doesn't move.

The ways to do it

The toy below is a small tokenizer and the quick-test step in AssemblyScript, run on Solitaire's real text and its real rule tries. These numbers are for the toy only, not a forecast for the real engine.

Toy, best of many runs Tokenizer Quick tests
JavaScript, today's shape (an object and string per token; strings and sets) 0.082 ms 5.97 ms
JavaScript, typed arrays and words as numbers 0.035 ms 2.24 ms
WebAssembly, same data, text already copied in 0.026 ms 1.81 ms
WebAssembly, copying the text in first 0.042 ms
WebAssembly, then building the JavaScript tokens the rules read 0.079 ms
  • What it says: nearly all the gain comes from the data shape (words as numbers, flat arrays), and plain JavaScript gets that too. WebAssembly adds about 1.2 to 1.35 times on top, and the tokenizer's lead disappears once the strings have to come back.
  • A call from WebAssembly into JavaScript cost 3.8 ns against 0.5 ns between JavaScript functions, with only numbers passed. Handing over a match costs more; I did not measure that.
  • AssemblyScript (what "compiled TypeScript" means in practice): 1 KB module, starts in 1 ms, builds in a second. But it is its own language with no closures or regular expressions, and still 0.x (0.28.20). Every class in the engine would be rewritten, not recompiled.
  • Rust to WebAssembly: not installed here and not tried; a second language and toolchain in a TypeScript-only repo. Expect about AssemblyScript's speed on the same flat data.
  • WasmGC: would let matches be garbage-collected objects, but no TypeScript-like language compiles to it for us, and the string support it needs arrived in Safari only at 26.2, too new for the two-year rule. Not tried.
  • All three need a build step before anything runs, in Vite, Vitest, tsx, the published package, the app and the VS Code extension. The runner's page has a content security policy, which would need checking for WebAssembly too. Python output isn't affected either way.
  • First-word index, in TypeScript: measured on the real parser, below.

  • PublicServers' medians are noisy on this machine: a shorter run gave -4% by median and -21% by best time for the index, where this one gives -31% and -23%. Solitaire's 21% is the steadier number.
  • Compiled output was byte-identical on both projects, and the 1,109 rule tests gave the same answers (18 of them fail with or without the index).
  • Estimated, not measured: a compiled engine on top of today's code would save perhaps 15 to 20%, assuming it runs the engine's share twice as fast and pays for the crossings. After this phase's speedups, perhaps 10 to 15% more. That is weeks of rewrite against a few hours here.

What this phase builds

  1. Each line tries only the rules that can start with its first word.
    • Choice.parse() keeps, per list of alternatives, a table from first word to the alternatives worth trying, in their original order so ties still go to the earliest rule.
    • Example: for a line starting remove, the statement list goes straight to the rules that start with remove, plus every rule that can start with anything. Today it tries them all, about 600 quick tests a line.
    • A rule goes under a first word only if its syntax demands it, which is the existing Sequence.leadingWord.
    • Rules that don't start with their syntax must say so. 22 parse() overrides skip super.parse(); audit those and the test() overrides, mark the ones that matter, and add a test so a new one can't slip through. The throwaway checked each function's source text, which won't ship.
    • Expecting mode (editor completion) keeps the full list.
    • addChoice() already replaces the list, so the table is rebuilt only when the list changes; the 212 additions are already in the measurement.
  2. Stop checking every Match's types outside tests.
    • Match.DEBUG_MATCH_INITIALIZATION is on everywhere today, shipped builds included, and costs about 4%.
    • Default it off; turn it on in the parser's test setup, so tests still catch a bad match.
  3. Measure and write it down.
    • Update "Rules and matching" in PARSING.md with the index and the new costs.
    • Record the rejected compiled engine in Choice's docstring, with the numbers above, so nobody re-proposes it blind.
    • Next places to look, if more is wanted, not built here: the scope name lookups (9%), and the declaration scan's tokenizing (4.3%).

When a compiled engine is worth another look

  • After this phase, if parsing a large project still feels slow and matching is still over about 35% of the time.
  • Even then, try the flat data shape in plain JavaScript first: the toy says it gets most of the gain with no new toolchain.
  • WebAssembly comes after that, for the tokenizer and quick tests only, leaving each rule's TypeScript alone.
  • Choice.ts: the first-word table
  • Sequence.ts and Rule.ts: which rules can be filed under a first word
  • The 22 rule files whose parse() skips super.parse(), as the audit finds (under spell/rules)
  • Match.ts, and the parser's test setup: type checks on only in tests
  • PARSING.md: the new costs
  • RuleClass.test.ts: a test that a rule which doesn't start with its syntax says so
  • From the worktree's root, in a terminal: node bin/spell.mjs speedtest --against HEAD, reporting the Previous / Current / Change table. Rule tests parse one line each, so the whole-project timing below is the one that counts.
  • Same output as before: yarn review in parser/ and app/, and spell content check at the root, with no snapshot changes.
  • Editor completion still offers the same words: the parser folder's expectations tests pass, unchanged.
  • Incremental parsing agrees with a full parse: the app folder's IncrementalProject.test.ts.
  • Solitaire and PublicServers re-timed against the numbers in this plan, reported the same way.
