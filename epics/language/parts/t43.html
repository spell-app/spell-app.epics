What P36 found (2026-11-07)

P29 didn't make the parser slower. The parser has grown about 7% slower since then, spread over every module.

  • P29 against the commit before it, timing only the 1008 tests both have: 310.9 ms before, 310.1 ms after, so 0%. The +6% in I14 came from comparing whole runs, and those swing a lot on this machine: one run took 852 ms where the others took about 400.
  • Today's branch against P29, the 1009 tests both have: 308.1 ms, now 330.4 ms (+7%).
  • Today's branch against the commit before P29: 312.9 ms, now 348.9 ms (+11%), on a busier run.
  • The slowdown is spread evenly, 2–14% in every module. The rules that grew most (to_do_something, quoted_property_formula, possessive_property) are the ones that were already the slowest.
  • CPU profiles of the whole rule-test run, before P29 and now, show the same functions in the same proportions (Sequence test and parse about 6% each, Choice parse 5.5%). No new hot spot appears.

Why there's no quick fix:

  • The extra time comes from the grammar getting bigger. Since P29, the work merged from data, atmosphere and P30–P35 added rules, and every new statement alternative is tried on every line.
  • Getting the time back means a structural change: sorting a choice's alternatives by the first word they can start with, so a line only tries the rules that could match it. That needs a phase of its own.
  • Nothing changes in the code. If you want the 7% back, the next step is a todo to index statement rules by their first word.
