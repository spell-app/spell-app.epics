Measured first, as the plan said (Solitaire, in node, per edit). The writing wasn't slow because every file is written again: it was slow because a compile wrote the project twice, and walked its tree reading something expensive.

  • A declaration's marker (/*! SPELL: DECLARES) worked out its lines each time anything READ them, and every compile walks the whole tree several times (the waiting pass, the reads pass ...): about 60% of the whole-project write. Now only a writer reading them works them out.
  • Every compile also wrote each file on its own (SpellFile.compiled), which only the old output pane reads: about 40ms. Now it's written when read.
  • Where a statement ends (Match.end) walked every token of it -- a type's whole body -- and the markers and the side bar's places ask it of every declaration. Now it's found from the end.

Before: compile 120-145ms an edit, of which the project's write about 50ms and each file's own about 40ms. After: compile about 50-70ms, the project's write about 15-25ms, of which the whole-project pass (what waits, what's read) about 9ms and the writing itself about 6ms (JavaScript).

So the cache in the plan (pieces per file and class, the uses record counting action bodies, outlines) would now save at most about 6ms a target, for a real risk of stale output: a reused piece's code also depends on what the parse looked up in other files, which no outline covers.
