For P68 · Upgrading Old Spell, from your request r31: "There should be a version upgrade path for spell code."

What exists today: three version numbers, none of them in the project.

  • The language's version, 0.8.0, set by hand: stamped only on a compiled project's declarations, which are refused from another major version.
  • The npm package's version: what an outside project installs.
  • The compiler's code hash (J44): a cache key, changing every day.
  • A project's file (__project.json5) has its title, its own version, its targets: nothing says which Spell it was written for.

Without a record, every old form's check runs on every parse anyway (they're cheap). The record lets the editor say once "written for an older Spell", and lets the upgrade skip what's already done.

  • "spellVersion": "0.9.0" in __project.json5, written on New and after each upgrade.
  • Each old form names the language version it came in; the language's minor goes up with each one (T166's: 0.9.0).
  • No entry reads as "before any of them".
  • "spellAsOf": "2026-11-19": the day it was last upgraded, matching your dated comments.
  • No version to bump by hand; but two forms on one day can't be told apart, and a date says nothing to someone outside.
  • Every check runs every time, as retired words do today. No "written for an older Spell" notice.
  • Each project file says which Spell it matches; the language version goes up one minor per old form, with its date beside it in the list.
