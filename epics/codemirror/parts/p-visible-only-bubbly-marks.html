Would it help? Yes, for the scroll jumps, though not for the speed-up this phase is about. It also needs a second step for HTML, or the big file still jumps.

  • Why the heights are wrong today. CodeMirror guesses the height of every foot it hasn't drawn yet.
    • A foot is a widget with a row of its own (FootWidget). It doesn't say how tall it is, so CodeMirror guesses one full line, 25px.
    • Drawn, a foot's row is 5px, or 13px right above a band, plus a tab's height for each foot stacked under it (.cmb-foot-row).
    • So every foot not drawn yet is 12-20px off. The file's height changes as feet scroll into view: the jumps I21 worked round for typing, not for scrolling.
  • What the idea fixes. A foot drawn inside the blank line under its block takes no room of its own.
    • It's an absolutely placed mark in a line that's already there, so the line stays 25px and CodeMirror's guess is right.
    • Every Spell line is then one height, and scrolling a Spell file never changes its height.
    • The foot needn't be a block widget any more. So it can be drawn for the lines on screen only, with the pills, instead of staying whole-file in the editor's state.
    • The stacking code for feet that end on the same line goes: several feet share one blank line, each at its own indent, overlapping as Owen said.
  • What it doesn't fix. These lines are still not 25px. CodeMirror still guesses each one wrong until it's drawn:
    • A row of HTML end tags (</row>, </> ...):
      • It's a text line drawn short, about 21px, or 29px above a band (.cmb-feet-row).
      • Table/Examples.spell has 666 end-tag lines and few Spell feet. Every big file in the examples is mostly HTML, so these rows are what make the big file jump, not Spell's feet.
      • Owen's idea, carried over: draw them as one full row each (question 5 below).
    • A head whose description doesn't fit beside it gets rows of its own under it. They're measured only on screen (DescriptionRoom), so they're still guessed wrong. They're rare, and a whole row each, so that's left as it is.
    • Not a problem:
      • the hidden line breaks (a row of end tags, a tag's name joined to its first attribute): CodeMirror knows them, because they stay whole-file
      • wrapping: off in the code pane; only the notebook's short snippet editors wrap
      • a peek: opened on screen only, by a click
  • Edge cases, counted in Solitaire.spell (211 lines, 31 block ends):
    • No blank line under the block: 12 of the 31, e.g. if the stock is empty / reset the stock pile, then set the next card ... straight after. The same case is a block followed directly by its parent's next line. Question 3 below covers it.
    • The file's last block: no line under it at all. The same answer as for no blank line.
    • Several blocks ending on one line: 11 of the 31, up to three deep (for row, for column, if column is the same as row, then turn over the next card). Today each foot is a tab further down than the one inside it. In one 25px line they need another layout (question 4).
    • A blank line inside a body (Solitaire's -- Remove kings ... has one above it): it isn't a block's end, so it gets no foot. The layout already knows each block's last line.
    • Two blank lines: the foot goes in the first.
    • Typing on the foot's blank line: it isn't blank any more.
      • The foot is moved off it at once, as a blank line typed into is redrawn at once today (blankLinesDrawn()). Otherwise the words sit on the foot until the next layout.
      • Enter at the end of a block's last line puts the new line above the foot's line, in the block.

  3. One builder, two outputs (BubblyDecorations, CodeMirrorDecorations).
    • It walks the drawing as now, but makes marks only on lines inside the ranges it's given; the whole file when given none (the unit tests, a slice).

      • on-screen only: the marks (bands, pills, colours, quote marks, braces, a plain line's indent room) and the replaced pieces inside one line (curly quotes, a tag's />)
    • Line decorations stay whole-file: one per line is cheap, and typing on a blank line reads them far up the file (blankLinesDrawn() looks for the head or tag above).
