Every relayout rebuilds the bubbly look's marks for the WHOLE file, though CodeMirror only draws what's on screen.

  • A relayout costs about a screenful, not the whole file: measured on Solitaire.spell (207 lines) and a big one, SpellUI's Table examples (2,667 lines), before and after.
  • Nothing looks or behaves differently: bands, pills, rails, feet, descriptions, folding, find, peek, clicks and typing on a blank line all as now.
  • Lines scrolled into view arrive drawn, never plain for a moment.
  • No new scroll jumps: the line heights CodeMirror estimates stay what they are now (I21).
  • From Owen's question, "does codemirror have the concept of only rendering what's visible on the page?": it does, and the bubbly look now uses it.

The height-changing parts (feet, rows of feet, tags joined over lines) stay worked out for the whole file, in the editor's state.

The colouring and pill marks move to a view plugin that builds them only for the lines CodeMirror draws, again as the view scrolls.

  1. Measure first, and decide.
    • A headless Playwright script opens Solitaire.spell (207 lines) and SpellUI's Table examples (2,667 lines) in the app's editor, and times a relayout: the parser's layout (SP.BubblyLayout.of()) and the decoration building, separately, with performance marks.
    • Solitaire is short: CodeMirror draws about half of it at once (the screen plus a margin of about 1,000px), so its gain is at most about half. The big file shows the real gain.
    • If the decoration building is under a third of the relayout on the big file, stop and report: the layout is where the time goes, and this phase would buy little.
  2. The layout stays whole-file.
    • The parser lays out the whole text (each character's paint, every block's body under its head): a foot or a rail needs its whole block. That's not changed.
    • What's cheap to skip: each line's stretches (SP.BubblyStretches.ofLine()) are already worked out a line at a time in the editor, so they're only worked out for lines on screen.
  3. One builder, two outputs (BubblyDecorations, CodeMirrorDecorations).
    • It walks the drawing as now, but makes marks only on lines inside the ranges it's given; the whole file when given none (the unit tests, a slice).
    • Its build() returns two sets:
      • whole-file, in the editor's state: feet (block widgets), the hidden line breaks of a row of feet and of tags joined over lines, every line decoration (rails, cmb-head, group lines), and the drawing itself
      • on-screen only: the marks (bands, pills, colours, quote marks, braces, a plain line's indent room) and the replaced pieces inside one line (curly quotes, a tag's />)
    • Line decorations stay whole-file: one per line is cheap, and typing on a blank line reads them far up the file (blankLinesDrawn() looks for the head or tag above).
  4. A view plugin draws the marks (in CodeMirrorRelayout).
    • Rebuilt from the field's drawing when it changes, and when the drawn stretch changes (viewportChanged); mapped through edits as now.
    • While typing, the drawing is a few keystrokes old: the field keeps the edits since (a change set), and the plugin maps the marks it makes through them, so a line scrolled into view mid-typing is still drawn.
    • At the lowest precedence, as the field is now, so a found word's mark still goes inside a pill.
    • Its atomic marks (a comment's dash) join the field's in EditorView.atomicRanges.
  5. Check: the same measurement after; the bubbly unit and browser tests unchanged; a new browser test scrolling the big file end to end, and typing then scrolling, every line on screen drawn; screenshots of Solitaire top and bottom, before and after, the same.

Risks:

  • A line scrolled into view arriving a frame late, plain: CodeMirror runs the plugin's update before it draws, so it shouldn't; the scrolling test catches it.
  • Find and peek read their own marks, not ours; the selection band reads atomicRanges at the pointer, which is always on screen. A caret moved by Page Down past the drawn stretch meets no dash mark until it's drawn: harmless.
  • Heights don't change: lines off screen are estimated by CodeMirror today too, and the feet, which are what change heights, stay whole-file (I21).

Left out: laying out only part of the file in the parser; the description rows (DescriptionRoom), which already measure only what's on screen.
