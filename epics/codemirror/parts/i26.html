From a file's text alone, a head naming a type another file declares can parse as a DIFFERENT rule than in its project's parse: in Solitaire.spell, the foundation's it is droppable when reads as drag_and_drop (a plain band) alone, list_guard (a property's) in the project, because only the project knows a foundation is a pile. Its last line, and the card is on top of its pile, is 8px taller alone (46 vs 38). Same in Pile.spell: belongs to one pile and it "is on top of its pile" if ... are properties' bands only to a parse that knows pile. Only the project's names can settle these.

Laid out from its text alone, a line in a type's body that doesn't read whole (it is droppable when reads only as far as droppable; belongs to one pile not at all) is read once more, as the line of a LIST's body: a stand-in type that is a list of things, made only for that one read.

  • A list's body is where these lines belong: it is droppable when is a list's own rule, and a list is a thing too, so belongs to one pile reads as well.
  • If it reads whole that way, it draws as that rule's band: a property's, as the project's parse draws it.
  • It's the parser's own rules, so Spanish's es soltable cuando and pertenece a una pila come along.
  • Only for those few lines, and only when there's no project parse to read: nothing else is parsed again, and the project is never touched.

Rejected: laying out with the project's names. Parsing the file again inside its project's scope would add its types and members to the project's own, and the docs pages have no project at all.
