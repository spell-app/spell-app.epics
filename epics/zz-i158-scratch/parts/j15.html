So an <epic-*> element works on any page, not just epic pages: guides, list and details pages, and the changelog. The docs runtime's loadEpicsPack() (spell-doc-runtime.js) loads the pack once, at start, through Spell UI's ComponentPacks.load(). That is the same loader <ui-root> uses for <ui-components source>, so a page gets one script and the pack registers once. A page that already names the pack (an epic page's root, or a saga page's old ../../packages/epics/pack/ path) loads it from the address it names.

  • Why not append a <ui-components> to the page's <ui-root>: 43 of 48 guides have no root, and a new root would hide the page until it was ready.
  • Why at start and not on demand: Spell UI loads a pack when it is declared, not when an epic- tag first shows up, and the comment threads and pane are becoming <epic-*> elements, so every served page will need the pack anyway. Our tools just create the element.
  • The cost, measured headless on a scratch server (median of 7 cold loads), airplane.html before and after: one more request and +480 KB (the server sends it uncompressed; 132 KB gzipped). First paint stayed at 56 ms and DOMContentLoaded at 142 ms vs 139 ms; the load event went from 143 ms to 153 ms. On the changelog: first paint 104 ms both times, load 401 ms vs 404 ms. The script is added asynchronously, so it never holds up the first paint.
  • The alternative: load it only when the page has (or gets) an epic-* element. That saves the 480 KB on pages that draw none, but every tool that draws one would have to ask for the pack first.
