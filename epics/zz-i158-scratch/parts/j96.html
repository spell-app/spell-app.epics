Before, the machine's epic server took ANY free port when 4848 was taken. That's how it drifted: two epic hub ensures ran at once (the log shows two starts in the same moment), both started a server, the first got 4848, the second a random port, and the second wrote the pid file last. From then on every restart replaced only the second one, on yet another port (52126, 52621, 53264, 62727, 51084), while the first sat on 4848 unnamed, and every page opened from the moved server lost it at the next restart.

Now:

  • The machine's server (the one with a pid file) never falls back: a taken port makes it stop and exit, writing nothing. So two ensures at once leave ONE server: the loser exits (checked by hand on a scratch home: two ensures at once, one server, both answered with it).
  • ensure asks whatever is on the port (/api/server). An epic server of the same home (epicServer: true, same root) that the pid file doesn't name is ADOPTED: the pid file names it, and the one it did name is stopped. It's then restarted as usual if its code is older.
  • A server of record on another port is stopped, so a fresh one starts on 4848.
  • Anything else on the port (another home's epic server, another program) is never stopped: ensure refuses, saying what holds it, on one line (epic server: port 4848 is taken, by another program ...).
  • Demo checks' own servers (no pid file) still take a free port when theirs is taken.

The trade-off: if something else ever squats on 4848, the epic server won't start until it's gone, rather than starting somewhere pages can't find again.
