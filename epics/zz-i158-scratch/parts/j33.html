The comments draw with elements now (Owen on I26: "page controls AND contents"). What our code drew as HTML strings and createElement trees is the epics pack's:

  • <epic-thread>: one comment's whole thread (header, Owen's answer, messages, his box), each message an <epic-thread-message> in its shadow root
  • <epic-threads>: the box of threads under one block
  • <epic-comment-pane>: the floating pane for a new comment (it places itself, Owen drags it)
  • <epic-page-note-head>: an old page note's head line

How the work is split:

  • The elements DRAW and say what Owen did (events: fold, edit, delete, answer, close).
  • The comments' code keeps everything else, as before: the routes, the drafts, seen/orange, the anchors, where a thread goes, the bullhorns. One <epic-thread> per comment for the visit, given what the server holds at each redraw and moved only when its place changes, so Owen's box and the cursor stay put.
  • Owen's field (the pane's, a thread's reply box, the pen's box) stays a native <textarea> the comments' code makes and slots in: it must live through every redraw with the cursor in it.

The alternatives:

  • Saves and drafts inside the elements (ServerLink-style): the list, drafts, Send and redraws are page-wide, so it would split one flow in two; no gain for Owen.
  • <ui-textarea> for the field: its Fomantic form look (padding, font size, focus border, fixed height) would have to be undone through ::part(), the "fighting the component" J16 turned down.
  • <epic-text-box>: it joins a details page's answer and has a placeholder; the comment field has none.
