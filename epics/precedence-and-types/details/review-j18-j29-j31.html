Nothing changes in code during the review.
  • Saved declarations: when a project compiles, each thing it declares (a type, a property, a method) is written into the compiled file as a /*! SPELL: DECLARES { ... } */ comment. Another project that IMPORTS it reads those comments to know its types and methods, and to rebuild the rules that let it write move the card to the pile.
  • A method's call rule: writing to move a card to a pile creates a rule, so later lines like move the card to the pile parse. Since last night every method has TWO such rules: the statement one (on its own line, its last argument takes a whole expression) and the expression one (inside a bigger expression, its last argument stops before an operator: if double x is 4 → double(x) == 4).

When a library is compiled, how many call rules does each method's saved declaration list? Today: ONE (the statement rule); an importing project registers it, and registering it creates the expression twin automatically, so the importer still ends up with both. You'd earlier picked "declarations list both rules".

The saved format didn't change; the twin always matches the rule it came from. Tests pin that an importer gets both. 

/*! SPELL: DECLARES {
  syntax: "move {thisArg:expression} to {callArgs:expression}", output: "move_to_$pile",
  rule: "method_call", of: "Card", alias: ["statement", "expression"], kind: "method",
  name: "move a card to a pile", params: [{ name: "pile", datatype: "Pile" }],
  defined: "/Pile.spell:418-487",
} */

On import: scope.addRule() sees the method's class says "has an expression twin" and registers both.

The declaration also carries the twin's syntax, e.g. expressionSyntax: "move {thisArg:expression} to {callArgs:operand}". Explicit and readable in the file; but two copies that must agree, and older compiled files lack it.

Since last night, the first set the X of Y to … on a property nobody declared DECLARES it, so it's reactive. That needs a few lines of compiled code that register the property on Y's class. Where do those lines, and their saved-declaration comment, go?

At the top of the file the set is in; or, when the class is declared in that same file, right after the class (a class can't be patched above its own declaration). The comment sits with that code.

The set is inside a method; the declaration lands right after class Deck: 

/*! SPELL: DECLARES {
  property: "is_set_up", of: "Deck", datatype: "choice", auto: true,
  defined: "/Deck.spell:275-311",
} */
Deck.declareProp('is_set_up', { type: 'choice' })
Object.defineProperty(Deck.prototype, 'is_set_up', {
  get() { return this.getProp('is_set_up') },
  set(value) { this.setProp('is_set_up', value) },
  configurable: true
})

Why not inside the method: it would run on every call, and reads before the first call wouldn't be reactive.

Code placed as A, but the saved-declaration comment stays on the set line, where you'd look for it. Cost: the comment can't carry its source position (defined:) -- method bodies' compiled text is reused across edits, so the position went stale and the editing tests failed -- so an importer can't jump to where it was declared.
