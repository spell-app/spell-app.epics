You're right: packages/ only makes sense in a monorepo. spell-epic has it because P6 copied the epics package over whole, at its old path.

What a normal single-package JS repo does, and what Claude Code adds:

  • src/: the code you write and run. No extra epics/ level inside it: the whole repo is the epics package.
  • tests/ (or test/): at the root, beside src/, mirroring its folders. Tests inside src/ are unusual: build and publish tools then have to be told to leave them out.
  • bin/: at the root. That's npm's convention for a package's commands ("bin": { "epic": "bin/epic" }), and Claude Code's too: a plugin's bin/ goes on the PATH.
  • scripts/: at the root, for dev-only scripts (build, release). Code the product RUNS doesn't belong there: so the window script moves into src/.
  • types/, templates/: usually at the root: ambient type files, and data the package ships. Inside src/ works too.
  • vscode/: its own package, with its own package.json and build (the .vsix), so it sits beside src/, not in it, the way a docs site or an example app would.
  • The plugin's parts: .claude-plugin/, skills/ and hooks/ (with hooks.json) sit at the root, where Claude Code looks for them by default (plugins: components). 
.claude-plugin/   plugin.json, marketplace.json
bin/epic
hooks/            hooks.json and the hook scripts
skills/
src/              the engine:  today's packages/epics, one level up
                  (tool/, list/, components/, tools/, docs/ ...), and window.mjs
tests/            mirrors src/
templates/
types/
scripts/          dev-only scripts
vscode/           the extension:  its own package
