Both pains in the kickoff prompt, and the third one (/epic can't go to another project), have one cause: the epic system is TOOLING, but it lives inside the PRODUCT repo.

  • Git versions it per branch, like the product code.
  • So every worktree carries its own copy of the epic tools, as old as the worktree.
  • And each window runs a MIX of copies: some pieces from main, some from its worktree.

Which copy a window runs

What happens, in order, when you type /epic in a worktree window:

  1. The session started at the MAIN checkout's root (the root-first trick, below). So the epic skill's text Claude reads is main's, and so are the hooks that run around it.
  2. The skill runs spell dev plan-doc .... The spell command is a link to main's command-line tool, so main's front end starts.
  3. That front end hands most commands on to the checkout it was called FROM: the details pages, the window commands, the page server, the agents list, the doc links. In a worktree, that's the worktree's own copy, as old as the worktree (findCheckout() picks it).
  4. Opening the plan doc builds a link through the worktree's own address on the page server, so the side bar loads the worktree's committed plan-doc script (epics.pack.js). The plan doc LOOKS as old as the branch, even though the doc itself is shared and current.
  5. The VS Code extension (the Review tab, the side-bar docs) is whichever checkout last ran spell dev vscode, for the whole machine. Today it was built from output-targets, 54 commits behind, at 02:44, then from main at 02:55.
  6. Only the shared content (the plan doc itself, the templates, the agents/ rules) is the same in every window at once.

So a feature added from one window reaches another one piece at a time, and some pieces only when its branch merges main.

Root causes, ranked

  1. Nothing makes a running worktree catch up with main.
  2. One feature is split across copies that update at different times. Main's skill and front end drive the worktree's tools and plan-doc script, so a new feature lands half-done in an old window.
  3. The side bar shows plan docs through the worktree's address, so it gets that worktree's old plan-doc script.
  4. Epic work done IN a worktree isn't live anywhere until it merges, not even in its own session.
  5. One VS Code extension per machine: the last checkout to build it wins, with no version bump, and every window needs a reload to pick it up.

Plus three hazards:

  • An old worktree's docs-index script rewrites the SHARED docs index in its old format (the papercuts log, 2026-10-05).
  • A tool missing from a worktree silently runs main's instead, because worktrees sit inside main's folder and node finds main's copy by climbing up.
  • 36 page servers left running for worktrees that are gone.

The duplicate files

Why every worktree window shows main's files too: main's root is the window's FIRST folder, on purpose. Call it the root-first trick:

  • The Claude panel lists only the sessions saved under a window's first folder.
  • The worktree hook (worktree.mjs) was meant to keep every session saved at main's root, so that every window lists every session.
  • That trick already fails: 18 sessions since 2026-10-02, this one included, were saved under their worktree's folder instead.

What leaks out of having main in every window:

  • Quick Open and Find in Files show both copies of a file. The setting that hides main's files only hides top-level entries. Owen edited main's UINagHost.ts by mistake (the papercuts log).
  • Source Control shows two repos.
  • The window's VS Code settings are main's (folder 1's), not the worktree's.
  • The window script's header (window.mjs) claims Quick Open shows each file once: that's wrong.
  • Worktrees nest inside main (.claude/worktrees/), so node and yarn, looking for a package, can climb into main's tree.
