The epic system is TOOLING, but it lives inside the PRODUCT repo, so git versions it per branch like the product code. Three things go wrong because of that.

This is how spell-app worked until 2026-10-18: spell-epic fixes each one, and spell-app switched over to it that day (where it stands).

  • The lag: a feature added in one window reaches the others one piece at a time, and some pieces only when their branch merges main.
  • The duplicate files: every worktree window shows main's files too.
  • /epic can't run in another repo: it is tied to spell-app's folders and names.

Which copy a window runs

What happened, in order, before the switch, when you typed /epic in a worktree window:

  1. The session started at the MAIN checkout's root (the root-first trick, below). So the epic skill's text Claude reads is main's, and so are the hooks that run around it.
  2. The skill runs epic .... The epic command is a link to main's copy, so every epic page verb runs main's code: current.
  3. The skill also runs the window, worktree, park, session, stock and shared verbs of spell dev.
    • Those still hand most of their work on to the checkout they were called FROM (runTool()).
    • In a worktree, that's the worktree's own copy, as old as the worktree.
  4. Opening the epic page in the side bar goes through the worktree's own address on the page server.
    • So it loads the worktree's committed page script: the epic page LOOKS as old as the branch, though the page itself is shared and current.
    • Quick Relief (P1) fixed this: shared pages load from main's page server, from any worktree.
  5. The VS Code extension (the Review tab, the side-bar docs) runs spell-app's command-line tool by its path (DocView), and it is whichever checkout last built it, for the whole machine.
  6. Only the shared content (the epic page itself, the templates, the rules in agents/) is the same in every window at once.

Root causes

  1. One feature is split across copies that update at different times: main's skill and epic drive the worktree's own spell dev tools and page script.
  2. Nothing makes a worktree catch up with main.
  3. Epic work done IN a worktree isn't live anywhere until it merges, not even in its own session.
  4. One VS Code extension per machine: the last checkout to build it wins.

The duplicate files

Main's root is every worktree window's FIRST folder, on purpose. Call it the root-first trick:

  • The Claude panel lists only the sessions saved under a window's first folder.
  • With main first, every window lists every session.
  • It already fails: 18 sessions between 10-02 and 10-10 were saved under their worktree's folder instead.

What leaks out of having main in every window:

  • Quick Open and Find in Files show both copies of a file, so it's easy to edit main's by mistake (the papercuts log has one).
  • Source Control shows two repos.
  • The window's VS Code settings are main's, not the worktree's.
  • Worktrees nest inside main (.claude/worktrees/), so node and yarn, looking for a package, can climb into main's tree and quietly use main's copy.

What still ties it to spell-app

What main still had on 2026-10-17, each one fixed in P4 to P7 (what's on main already):

  • No per-repo config: the content folder, the base branch, the install command and the worktree folder are written into the code.
  • ../spell-app-dev, /Users/owen and .claude/worktrees appear in about 30 places: the hooks, the window script, the shared, session, park, stock and worktree commands, the running-epics list, the page tools, the page server, the Spell spaces' server and the skills.
  • No plugin: the skills and hooks are spell-app's own .claude folder.
  • Half the verbs are still spell dev, and they load the whole spell compiler through the command-line package's single entry file.
  • The epic views ship inside the spell LANGUAGE extension for VS Code.
  • The epic page template loads its styles and scripts by paths inside spell-app.
  • Airplane mode's server side still sits in the page server (AirplaneMode).

Depending on spell's packages is fine (the kickoff prompt): the elements are built on Spell UI and Solid 2, and the page server on spell's server package.
