The browser's quick storage holds about 5MB per site, and only text; nothing keeps a preference beyond one browser.

Two waited-on places to keep values: the browser's database (IndexedDB), and the page server, which keeps them in the person's space.

  • The browser's database: one per site, a table per store; for big values (whole files)
    • values kept as the browser copies them, so a file handle survives: the way to save straight to disk later
    • a Blob or a 10MB string fits
  • The server store: a generic client that talks to a URL it's given; read, save, change, list and forget under a prefix.
  • Its server, on the page server, in spell-app's spaces, beside the people routes:
    • read, save and forget a key, and list a store's keys under a prefix (/api/prefs/...)
    • kept in the PERSON's space, e.g. @spell/owen@/__prefs/<store>.json5, through spaces' one file interface, comments kept
    • the person: this machine's (owen) until sign-in, from ONE function the sign-in replaces
    • a store name can't reach outside the person's __prefs folder
  • Neither throws when it fails (offline, refused, full): it logs, and answers the default.

The browser-database place is our own, on the browser's IndexedDB with no library (Owen's pick, Q20): 'read, change, save' in one database transaction. The other project's version had three bugs (Q19): its tests cover each.
