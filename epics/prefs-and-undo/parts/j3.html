Three details of P2 came out differently from the plan's words, each for a reason:

  • The database: the plan said a table per store. It's ONE table, each value under [store, key].
    • A browser database adds a table only while it changes version, so a table per store would mean a new version for every new store, and a wait on every other open tab.
    • One table lists a store's keys, or a prefix's, with a key range, just as fast.
  • The routes: four named ones, the store and key in the query or the body, rather than one path for each key. 
    planned:  GET / PUT / DELETE  /api/prefs/<store>/<key>
built:    GET load, POST save, GET keys, POST forget, under /api/prefs
    • A store is often named like a project (@owen/solitaire), and a key like a folder (layout/left): both have slashes, which a path can't keep apart.
    • Every other route of the app's API is a GET or a POST, and its writes are POSTs, which the page server already refuses from a foreign site.
  • Naming a place: the plan said place: "database" or "server". They're handed in: { place: DatabasePlace.shared }, { place: ServerPlace.shared }.
    • By name, every file that keeps a preference would carry both places' code, Spell UI's too.
    • Handed in, only the files that use one pay for it.
  • the places and routes are as built; the epic's guide says so
