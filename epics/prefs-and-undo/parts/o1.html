A preference is something a person sets once and expects the app to remember: a theme, a panel's width, the last folder they opened. Every repo keeps them through ONE pref store, the kit's PrefStore, in util's persist folder (Q11), built on ideas Owen proved in another project.

One way to remember, several places to keep it

The app always asks the same way. Where the value lives is the store's PLACE, one of five:

  • the browser's lasting storage: per site, it survives a reload
  • the browser's per-tab storage: gone when the tab closes
  • memory: for servers and tests, and the fallback when the browser blocks storage
  • the browser's database, for big values and file handles: it has to be waited on (P2)
  • the person's space on the page server, one file per store: waited on too (Q9)
  • No stand-in that lasts one request, as the other project had: memory serves a server.

Every key belongs to its store

  • Each store has one name, and every key it writes starts with it: spell-site:scheme.
    • The name is everything before the key's first colon, so every key that existed before keeps its bytes (Q15).
  • So two apps on one site never share a pool, and "forget everything" wipes only the store's own keys.
  • A lesson learned the hard way: once, in the other project, the app's name got lost by mistake. Every app shared one pool, and one app's "forget everything" wiped another app's preferences. A store here takes its one name, so that can't happen.

Values, defaults and forgetting

  • Values are text a person or a plain script can read: JSON only when they look like it, anything else is text, e.g. dark (Q12).
    • The browser's database keeps a value as the browser copies it: a date, a file, a file handle.
  • Reading takes a default, returned when nothing was saved.
  • A pref may be declared, with its type, choices and default: nothing saved, it reads the declared default, else the first choice, else its type's (Q13).
  • Saving "nothing" forgets the key.
  • It never throws when storage fails (blocked, full, bad JSON): it logs, and answers the default.

A quick way and a waiting way

  • Every store can check, read and save quickly (no waiting), and also in a way that's waited on (load(), save()).
  • The waited-on way adds a read-modify-write: "give me the value, I'll hand back the new one", done as one step (update(); one database transaction in the browser's database).
  • The browser's database and the page server are the waited-on places.

Keys as folders

  • Keys with a shared prefix act like a folder, e.g. every key starting layout/.
  • The store can list the keys under a prefix, forget a prefix, or forget all of its own keys.
