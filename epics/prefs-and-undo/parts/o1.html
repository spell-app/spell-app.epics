A preference is something a person sets once and expects the app to remember: a theme, a panel's width, the last folder they opened. These are the ideas Owen proved in another project, written so they can be rebuilt here.

One way to remember, several places to keep it

The app always asks the same way. Where the value lives is the store's business:

  • the browser's lasting storage: per site, it survives a reload
  • the browser's per-tab storage: gone when the tab closes
  • a larger database in the browser, for big values: it has to be waited on
  • a stand-in on the server that lasts for one request, so the same code runs when a page is drawn on the server

Every key belongs to its app

  • Each store is made for one app, and every key it writes is prefixed with that app's name.
  • So two apps on one site never share a pool, and "forget everything" wipes only the app's own keys.
  • A lesson learned the hard way: once, the app's name got lost by mistake. Every app shared one pool, and one app's "forget everything" wiped another app's preferences.

Values, defaults and forgetting

  • Values go through a serializer that keeps dates and other rich values, not plain JSON.
  • Reading takes a default, returned when nothing was saved.
  • Saving "nothing" forgets the key.

A quick way and a waiting way

  • Every store can check, read and save quickly (no waiting), and also in a way that's waited on.
  • The waited-on way adds a read-modify-write: "give me the value, I'll hand back the new one", done as one step.
  • Each store says whether it has to be waited on.
  • The browser database does: it refuses a quick read, with a message saying to use the waited-on one.
  • A quick save to it still works, but fire-and-forget: a failure is logged, never thrown.

Keys as folders

  • Keys with a shared prefix act like a folder, e.g. every key starting layout/.
  • The store can list the keys under a prefix, forget a prefix, or forget all of the app's keys.

The kit's PrefStore keeps these ideas, with three differences:

  • Where values live:
    • quick, by name: the browser's lasting storage, its per-tab storage, or memory
    • waited on: the browser's database, and the person's space on the page server (P2)
    • no stand-in that lasts one request: memory serves servers and tests
  • Values are text unless they look like JSON (Q12), so people and plain scripts can read them: no serializer for dates.
    • The browser's database keeps a value as the browser copies it: a date, a file, a file handle.
  • A pref may be declared, with its type, choices and default (Q13).
