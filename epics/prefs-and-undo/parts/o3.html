How the ideas in 1.1 and 1.2 work in Spell's runtime now. The runtime does all of it; only the spell to say it waits for epic elemental-spell (Q4, C7), so for now it's written by hand, in the declarations a compiled class carries.

A remembered property

  • A property marked remembered keeps its value for each person, across visits.
  • It's kept in a pref store named for the project's id, e.g. @owen/solitaire:theme; whoever runs the program picks the place, and the property doesn't say (P8). 
// today, in a compiled class
declareProp("theme", { oneOf: ["light", "dark"], remembered: true })

// the spell, once elemental-spell writes it
- its remembered "theme" is one of light or dark

Undo for the actions that ask for it

  • Only an action declared undoable records undo (Q2): a plain property change is no step.
  • An action names its undo, so the menu says what it does: declareAction("turnOver", { undoneAs: "Turn Card" }); the spell may one day say to turn it over, undone as "Turn Card":. Every change the action makes is that ONE step.
  • It's a TRANSACTION (Q6): what starts while it's open, waits and nested actions included, folds into its one step.
  • A property declared undoable: false (a selection) is left out; an action declared cantBeUndone keeps or clears the history (Q10).

Undo and redo in every app

  • Every app has undo() and redo(), with live canUndo, canRedo and titles for the Edit menu, in the program's language.
  • ⌘Z and ⇧⌘Z come with them, through Spell UI's keyboard registry, while the app has the focus (Q16).
  • They're plain methods, not yet built-in actions: elemental-spell's Actions and Menus phase may wrap them.

Ties to epic elemental-spell

  • Its words: a property belongs to a Template, an action is an Action.
  • Its event model (its T1): events and actions go through one place, which is where an undo would be recorded and a shortcut would fire.
  • declareAction() is a thin wrapper over the run's history, so its Actions and Menus phase can take it over (Q21).
