README-element.md: the element framework

  • Lead, for a React reader: a custom element here is two objects: the DOM element the page talks to (attributes, properties, events) and the component that draws it (state, `render()` into a shadow root, on Solid 2). Every component set (Spell UI's `ui-*`, spell-epic's `epic-*`, the brand's `brand-*`, the app's `<spell-app>`) is written on this one framework.
  • HERO PICTURE: a page loads its elements: the eight-step sequence (`<ui-root>` connects, hides, draws skeletons from the catalog, imports each family once, loads packs, the runtime chunk, each element renders, `ui-ready`). Caption: "Nothing loads up front; the root loads what the page uses."
  • What it can do, bullets: reactive members that read fresh after a write; attributes and properties from one vocabulary file; custom states and ARIA from decorators; shared behaviour every element gets (disabled, loading, hidden, animation); an error boundary per element; hot reload in place; a static render for no-JS pages.
  • What it is not trying to do: the list from explore-2 C8 (no knowledge of any set, no runtime of its own, one copy per page, no light-DOM rendering, not a framework binding, fallbacks only for form controls).
  • The two objects, and why (the owner's M14), with a picture (DOM element ↔ component) and the lifecycle in five steps. Then, for the React reader: unlike a React component, an element is a real node in the page, and the page (or any framework) talks to it through its attributes, properties and events while it lives; so the browser's side (the DOM element) and the drawing side (the component) are two objects that point at each other. Why that's wanted: it works from plain HTML and every framework; state survives moves and re-parenting; each element is its own error boundary; the page can be rendered static. Why it's as fast as a virtual DOM, or faster: the component renders ONCE into its shadow root, and Solid's fine-grained reactivity updates only the text nodes and attributes that read the changed value, with no tree to diff; the measured numbers (1,000 buttons built in about 100 ms; a property write reaches the screen on the next frame); a small picture of "diff the tree" vs "update the node".
  • The vocabulary and the language system: every name in a `.en.ts` file; code reads names through it; the two halves of localization (a dictionary renames what authors type: `<ie-boton primario>`; `UI.i18n` holds texts people read); honest status: designed and tested, no translations ship.
  • Packs and `<ui-root>`: what a pack is (one classic script, any prefix), the three generated files, `PACK_MODULES` and why one Solid per page, the six-step "a page loads a pack" picture; the real markup from an epic page.
  • Theming through shared CSS: the layer order, tokens that inherit into shadow roots, one adopted sheet per shadow root, themes applied page-wide; link to spell-ui's README-themes.
  • Restyling your whole site with the app stylesheet (the owner's M15), a worked recipe: one `<style id="ui-app-stylesheet">` (or a `<link>` with that id) on the page; the runtime mirrors it into every component's shadow root, adopted last, in the `ui.app` layer; so `.ui.button { border-radius: 0 }` squares every button on the site, `.ui.card { box-shadow: none }` flattens every card, and tokens on `:root` (`--ui-primary`, `--ui-font-size`) change every element at once. The before / after as two small pictures; what goes in the app stylesheet vs in a theme file vs in tokens, as a three-row table.
  • The method: making an element for a thing: the eight steps with the `<ui-counter>` code from the custom-elements guide (vocabulary, component, sheet, barrel, catalog, tests, docs page).
  • The examples: Spell UI is the host (the runtime, `<ui-root>`, 62 families); spell-epic is a pack (`epic-`, ~40 families, every epic page loads it); spell-brand a second pack; the app's root subclass.
  • Tools and test helpers: `spell-pack build | check`, the root catalog, the elements' Vite settings; `ElementFixture`, `A11y`, `Viewport`.
  • Expands: every decorator with one line; the settings the element layer reads from the page's runtime; the lint guard's rules; the files table.
  • Sources: explore-2 B5, C1-C9; element/AGENTS.md; the custom-elements guide (the methodology).
