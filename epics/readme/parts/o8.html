README.md: the Spell app

  • Written for a non-programmer first (the owner's M29): the front page's first half (the lead, the live loop, what you can do, spaces and people, the ambition, the examples) is readable by someone who has never programmed: no jargon without a plain explanation, every term a reader might not know defined in a few words or linked, pictures before prose. The developer material (folders, setup, working on it) comes after a clear line: "If you want to work on Spell itself".
  • Lead: Spell's editor is a live programming environment for people who don't call themselves programmers: you write (or ask an AI to write) a program in English, and it runs beside the text as you type; what the AI made is readable, checkable and changeable, not a black box.
  • Spaces, organizations and people, a top section right after the lead (the owner's M30): a SPACE is a person's or an organization's folder of projects; every project has an address (`@spell/examples/todos`); people and organizations are things in spell too, with ids and readable files; your own space is where `spell new` puts things; sharing a space is coming. Link to README-spaces.
  • HERO PICTURE: the live loop: the eight steps from explore-5 A.4 (open a project → type → compile in the browser → load the runtime → run → the game keeps going across a recompile → draw → inspect). Caption: "An edit recompiles the program and carries the running things over."
  • What you can do today: write in sentences or outlines; see errors, hover and completion from the same language service the command line uses; run a program as a page, with each drawable thing its own element; inspect things and types; compile to JavaScript, TypeScript or Python; embed `<spell-app>` on any page.
  • The ambition, in its own section: 🌱 drag and drop: build a program by placing Spell UI components, setting their properties (the property editor), and attaching spell to them; HyperCard's browse, author and script levels as modes. 🌱 shared editing: several people in one project, each copy kept in step (what the plan says first: one running program shared on a local network; then the source; Q12). 🌱 AI in the editor: explain this line, write, fix, translate. Each with one line of what it stands on.
  • The folders: the table (app, spaces, lsp, cli, page-server, vscode), one line each with its README; the dependency flow in one picture (`cli → app → lsp → spaces → spell-lang → the kit`).
  • Setup from zero: the kit's install, then `yarn start` (what it prints: the editor's URL), `yarn cli:install`, `spell dev vscode`; Python needs uv (one line); the first project to open.
  • The example apps: the table of the eight examples and two libraries with what each shows (explore-5 A.5), linking README-examples; "and ideas for yours".
  • Working on it: the checks, `tests/<folder>/`, where to hack on what (link to the kit's README-development); App UI's docs pages.
  • Expands: every yarn script; who serves what at run time (the port picture). No history section (the owner's M31).
  • Sources: explore-5 A.1-A.5, B; today's README (its FizzBuzz opener moves to spell-lang's front page; its folders table is right).

  • Picture: the app's parts: the editor store (one instance, spell cells), the routes (`/edit`, `/run`, the chooser), the screens, Monaco with the language service in-process, the runner, the runtime copy.
  • The editor store: what it holds and does (project root, project, file, selection, notices; show, create, compile, restart, modals); how Solid follows it.

  • The components: `<spell-app>` (a root itself), `<spell-editor>`, `<spell-code>`, `<spell-markdown>`; how to embed them (the two markup lines); the builds (`build:element`, `build:runner`, `build:page`).
  • App UI: the docs pages at `/components/app/`; the demos.
  • Expands: the routes and hotkeys; the Monaco plumbing; one Solid per page and the shared builds.
  • Sources: explore-5 A.3 (app), A.4; app/AGENTS.md.

README-spaces.md: where projects and people live

  • Lead: a space is a person's or group's folder of projects; an address names a project or file (`@spell/examples/solitaire/Card.spell`); spaces holds the built-in projects, the models, the servers that serve them, and the Python web server.
  • Picture: the groups and their folders (the built-in examples and library in the repo, the frozen tests in spell-lang, your own group outside git), and the URLs that read and write them.
  • Addresses: the grammar block (`<group>/<project>/<file>`, `@here`), from the `SpellLocation` docstring; your own group's name (I1).
  • Setting up spaces for your project (the owner's M7), a numbered recipe with what each step prints: where your spaces folder is (beside the kit; the env var that moves it); `spell new <name>` and what it writes (`__project.json5`, a first `.spell`); the project file's fields (files, targets, version); opening it in the editor and on the command line; adding a project to a group; importing a library project; keeping it in your own git repo.
  • The models: project groups, the project root (create, copy, rename, delete), project files, people; browser-safe.
  • The servers: the route module on the page server (the API, `/spaces`, the editor started as a child, builds on demand), the API alone on 3001.
  • The Python server (the owner's M13), its own section: `spell_quart`, a Quart app in spaces' `server/py/`; what `spell run --target py` does (compile to Python on `spell_core`, start Quart, open the page); one program per visitor; the page gets the whole state by id when it opens, then a patch after each message, drawn by the program's JavaScript half; the sequence picture; what it needs (Python 3.12, uv); how it differs from the page server.
  • People and orgs: every thing gets an id and a readable JSON5 file; the people library; the "You" panel.
  • 🌱 Coming: spaces for orgs, sign-in and invites, sharing (the shared-editing plan, Q12).
  • Expands: the env vars; the API routes; what's committed beside the source (declarations, words).
  • Sources: explore-5 A.3 (spaces); spaces/AGENTS.md; the people-and-orgs guide.

README-examples.md: the example apps, and ideas for yours

  • Lead: the example projects that ship with the app, each one worth opening; what each shows, and what to build next. Only the finished ones (the owner's M32): the writer runs each and keeps those that work and aren't superseded.
  • The table: address, what it shows, a screenshot (explore-5 A.5), in a learning order: fizzbuzz, calculator, todos-form-based, outline-solitaire, drawable-solitaire, then the two libraries (cards, people). Left out as superseded or half-baked: `todos` (the form-based one replaces it), `solitaire` (the outline one replaces it), `solitaire-import` (deals nothing: a known runtime problem); todo T3 asks whether they leave the repo too.
  • Screenshots (the owner's M8): one of each example running (the editor's runner pane, or the `<spell-app>` page), taken headless by the writer with the page-check script into `docs/images/examples/<name>.png`, each under 300 KB with alt text; the front page shows two of them (todos, drawable solitaire).
  • Three short walkthroughs: fizzbuzz (loops and print), todos-form-based (types, phrases, lists, a form, drawing with events), outline solitaire (the outline style, things that draw themselves, `<css>`, `pause for`; the owner's M33). Each with a real excerpt and its screenshot.
  • Kept up to date by a tool (the owner's M34, todo T2): the table and the screenshots are generated from the example projects themselves (each project file's description, a headless run per project), between marker comments in the page, so a new example appears by running one command.
  • Picture: the todos app's one type with its properties, phrases and drawing, as a diagram of the sentences.
  • Ideas for new projects: the eight from explore-5 A.6 (flashcards, a habit tracker, a recipe scaler, dice games, memory, a collection catalogue, a sign-up sheet, a text adventure), each one line and what it exercises; `spell new` to start one.
  • The frozen test projects: one line and a link (they're spell-lang's, with snapshots).
  • Sources: explore-5 A.5, A.6; the examples' own files and headers.

README-lsp.md: the language server

  • Lead, assuming nothing (the owner's M35): what a language server IS, in two sentences (the program behind an editor's red squiggles, hover text and completions, talked to over the Language Server Protocol, LSP, so one server serves every editor), with links to the protocol's site and VS Code's guide; then: Spell has one language service (diagnostics, hover, completion, definition, references, rename, outline, folding, formatting), run in three places: the browser editor, VS Code over stdio, the command line. "The command line and the editor can't disagree."
  • Picture: the service in the middle, the three hosts around it, the disk workspace under it.
  • The pieces: the service, the server (one ordered change queue, diagnostics after a delay), the disk workspace, the scope explorer and scope packs.
  • In VS Code: how the extension finds the checkout's server; link to the kit's README-vscode.
  • Working on it: `yarn lsp:start`, `yarn lsp:scopes`; it must stay browser-safe.
  • Written as done (the owner's M36, and the end-state rule of Q2): `spell lsp` starts the server; the language service lives in spell-lang and this folder holds the server, the disk workspace and the VS Code side. One folded "until repo-split P13 lands" note with today's spelling.
  • Sources: explore-5 A.3 (lsp), C.1; lsp/AGENTS.md.
