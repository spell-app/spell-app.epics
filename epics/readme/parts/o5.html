README.md: Spell UI

  • Lead (the new one-liner, a judgement call for the page: J1): "Accessible, themeable web components that load themselves on demand, from plain HTML or any framework." Then: shadow DOM with semantic markup, cascade layers and OKLCH tokens, dialog and popover and anchor positioning, form-associated controls; written on Solid 2 but a plain custom element to the page.
  • The thirty-second demo, two ways (the owner's M23), written as if the package is on npm: in a plain HTML page, one `<script type="module">` importing `spell-ui/ui-root` from an npm CDN (esm.sh, or jsDelivr / unpkg) with the import map it needs, then the markup (a root, a segment, a header, a button); and in a program, `npm install spell-ui solid-js @solidjs/web` then `import "spell-ui/ui-root"` in a Vite or other bundler app. What happens in both: the root loads the three families it sees, nothing else. One folded note: until the packages are published, the kit checkout and `yarn build` stand in.
  • HERO PICTURE: a page loads its elements: the nine steps from explore-4 A.3 as a sequence diagram (root connects, hides, skeletons, catalog lookup, import once, packs, runtime chunk, ready).
  • `<ui-root>`: what it is (the top of a page or app), its attributes in a table (display, loading, timeout, theme, size, icons, emoji, width/height/fixed, stack-with), `ui-ready` and `ui-error`, the settled promise, nested roots, a subclass is a root (spell-app's).
  • Component packs: another package's elements loaded the same way; the markup; one Solid per page; the two packs today (epics, brand); link to the kit's README-element for how one is built.
  • Page-level CSS: the four ways page CSS reaches inside (tokens, utilities, `::part()`, the app stylesheet), the layer order, "an unlayered page sheet always wins"; the two real examples from the theming page. Link to README-themes.
  • The families by topic: a short table (Elements, Collections, Views, Modules, spell-ui's own) with the tag names in each, linking README-components and the live component index.
  • Using it from a framework: three lines (attributes for primitives, properties for rich data, `ui-*` events with `detail`) and the link to README-frameworks.
  • Other ways to load: everything, one family, the no-JS stylesheet, the static server render.
  • Install: in the kit today (`yarn clone spell-ui`, `yarn dev`); 🌱 Coming: `npm install spell-ui` with Solid 2 as a peer (Q10).
  • Working on it: `yarn dev`, `yarn review`, `yarn test` (a real browser), `yarn test:visual`, the site scripts; link to README-site and AGENTS.md.
  • A note on where it comes from, last, two lines: the vocabulary and class grammar are Semantic UI's and Fomantic UI's, kept as attributes; each family's CSS is a port of Fomantic's, inside the shadow root; why (modern CSS, accessibility, no jQuery). Not the lede (the brief).
  • Expands: every root attribute with its values; the sizes and budgets; the browser features it assumes; every yarn script.
  • Sources: explore-4 A.1, A.3, A.4, A.5, A.7, A.8, A.11; the getting-started page.

README-runtime.md: what's under the elements

  • Lead: one `UI` runtime per page, loaded as one lazy chunk by the first element that connects: the services every element shares.
  • Picture: the runtime's services as boxes (browser, keyboard, overlays, focus, styles, vocabulary, i18n, transitions, toasts, modals, icons, sources, themes) around the elements.
  • The vocabularies and localization: one `.en.ts` per tag, what it holds, what reads it (the catalog, the site, VS Code autocomplete, the design system); the dictionary half and the texts half; the honest status.
  • Icons: packs (Font Awesome 7 Free by default, Brands and Fomantic opt-in), the pack format, `yarn icons:pack`. Then "Using another icon set" (the owner's M24, partly aspirational): what works today (a folder of SVGs → `yarn icons:pack --id` → `<ui-root icons="my-pack.js">`), and 🌱 coming: named packs for Material Symbols, Lucide, Heroicons and Phosphor installed by name, an icon browser that searches across packs, per-element pack overrides.
  • Styles: the sheets (layers, tokens, colours, sizes, typography, utilities, native, themes), which are generated; one adopted sheet per shadow root.
  • The static render: `ui-*` pages to plain HTML in node, for search engines and no-JS; `spell static`. Then "From Python, Flask or Quart" (the owner's M25): what works today (serve the prebuilt `page.static.html` and `ui.static.css` from any server; a Python-compiled spell app's drawing half is JavaScript, served by Quart); 🌱 coming: a render step a Flask or Quart app can call (a node sidecar, or the static renderer as a service), so a Python template can emit `ui-*` markup and get plain HTML back.
  • Spell UI's half of the element core: form controls, parts, loadable elements, native fallbacks; the kit's half linked.
  • Expands: the runtime's API in a table; the `UI.themes` calls; the i18n lookup order.
  • Sources: explore-4 A.5, A.6; spell-ui/AGENTS.md "Layout"; explore-2 C2, C7.

README-themes.md: theming (a stub)

  • Lead: a theme is CSS in the theme layer, applied to the page and every shadow root at once; tokens do the rest. This page is short on purpose: 🌱 Coming, picking and making themes.
  • What ships: the layer order; the token families (`--ui-font-size`, spacing, radius, shadows, colours and their roles, component tokens); dark mode (`light-dark()` pairs, `ui-dark` / `ui-light`, `theme="dark"`); the themes list (classic plus 24 Fomantic ports, `spell`, `spell-brand`); `UI.themes.apply()`.
  • Four recipes: sitewide defaults (tokens on `:root`), one component's defaults (its `--ui--*` tokens), applying a theme, and restyling base styles for the whole site through the app stylesheet (the owner's M15: one `<style id="ui-app-stylesheet">`, class-grammar rules in `@layer ui.app`, mirrored into every shadow root; `.ui.button { border-radius: 0 }` squares every button).
  • 🌱 Coming: a theme picker, making a theme from a brand, per-component theme files.
  • Sources: explore-4 A.5; the theming docs page and notes.

README-migrating.md: from Semantic UI, Fomantic UI or Semantic UI React

  • Lead: if you have a Semantic UI, Fomantic UI or Semantic UI React page, most of what you know carries over: the vocabulary is the same, written as attributes on `ui-*` tags instead of classes on `div`s. This page shows the mapping, what changes, and the migration tool as it will be (the owner's M6; future epic semantic-ui-migration).
  • Picture: the same card three ways: Fomantic classes, Semantic UI React JSX, the `ui-*` markup.
  • What carries over: the class grammar as attributes (`class="ui small primary basic button"` → `<ui-button size="small" primary basic>`), the Types / Content / States / Variations taxonomy, the component names, the themes (24 of 25 ported); a table of twenty common classes and their attribute.
  • What changes: shadow DOM (no reaching in with CSS selectors: tokens, utilities, `::part()`, the app stylesheet); behaviour without jQuery (events are `ui-*` CustomEvents; invoker commands); the content parts style by owner context; `width` not `wide`; `selected` not `active`; what has no counterpart yet.
  • From Semantic UI React: props become attributes or properties; callbacks become listeners; no wrapper components; React 19's property passing; a before / after of one form.
  • 🌱 Coming: the migration tool, written as if it existed: `spell migrate semantic <folder>` rewrites class-grammar markup to `ui-*` tags file by file, reports what it couldn't map, keeps a per-file diff; a Semantic UI React codemod for JSX; a checklist page it leaves behind. What someone would want from it, listed: dry run, one file at a time, a report of unmapped classes, theme carry-over, a side-by-side check in the browser.
  • Expands: the full class → attribute table; the components with no counterpart; the theme list.
  • Sources: explore-4 A.7, A.9; spell-ui/AGENTS.md "UI rules"; the component index.
