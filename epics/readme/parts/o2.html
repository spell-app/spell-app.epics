Every README in this epic is written to ONE brief, so a dozen writers (Fable first, then Opus agents) produce pages that read as one set. This is that brief: the audience, the shape of a page, the layout it describes, the pictures, the links and the words to avoid. A writing phase's agent reads this, its repo's outline, and the research reports in this epic's research/ folder.

Who reads them

  • First: developers who know another framework. A reader of the element README knows React; a reader of the language README has used a compiler or a template language. Explain Spell's ideas by contrast with what they know, never from zero.
  • Second: coding agents (Claude Code today, others later). A README says what a thing IS and how to run it; the rules for working on it stay in the repo's AGENTS.md, which the README links.
  • Setup commands are written for a Node novice: every command complete, run from a named folder, with what it prints when it worked. Nothing assumed: installing Node 24, enabling yarn through corepack, cloning the kit, the one install, cloning the child repos.

The shape of a page

  • A plain lead paragraph: what the thing is, for whom, a few sentences. Then a picture.
  • Sections open with a short paragraph, then bullets (WWOD §6): a paragraph says the idea, the bullets carry the facts; never a wall of prose.
  • Details fold: anything a first reader skips goes in an expand, GitHub's <details><summary> block. The summary line says what's inside in words ("Every yarn script, one line each"). A page reads whole with every expand closed.
  • Tables for anything with three or more rows of the same shape: folders, commands, components, options.
  • A repo's root README is the front page: the pitch, the picture, the map of its folders, setup, things to try, and links to every secondary README. Reading it gives a FULL orientation without diving into details: this is an ambitious project, so a front page runs as long as that takes (300-500 lines with expands closed is fine); what's reference or detail still folds or moves to a page of its own.
  • A secondary README, README-<folder>.md at the repo's root, goes deep on one folder or one topic. An existing in-folder README is FOLDED into it and then deleted (Q5): every fact kept, long references in expands, a second page when the front one overflows; every link to the old file repointed in the same phase.
  • Every page ends with a "See also" list: the pages beside it, the repo's front page, and the kit's.

The layout the pages describe

  • The end state after repo-split P13 and P14 (Q2), not today's checkout: the command line's base in the kit's cli/, each repo's commands in its own cli/; package names in every import (spell-kit/server, spell-ui/core), #/ for a package's own deep files, no $/ anywhere; the assembler inside the server.
  • Where P13's picks are open, the pages use its recommended ones: the twelve language commands in spell-lang, serve / new / projects / vscode in spell-app, icons / static / pack / design in spell-ui, docs and epic in spell-epic; the eight repo tools without dev (spell pack build, spell server start).
  • Setup sections and "things to try" use only commands that work today AND after: the language commands keep their names; yarn scripts; epic. A page that names a planned command carries ONE folded note, "Until repo-split P13 lands", giving today's spelling.

Pictures

  • Diagrams are Mermaid blocks, which GitHub and VS Code's preview draw: flowcharts for structure and data flow, sequence diagrams for a request or a load, a block diagram for how pieces fit. One picture per big idea, right after the paragraph it illustrates.
  • Each diagram has a one-line caption under it, in italics, saying what to look for ("Every arrow points down: a repo uses only what's below it").
  • Writers draw a PLAIN diagram; the prettifier (T1, built in P8) gives every block the Spell look in one pass: the theme directive, shared node classes (repo, folder, step, data, coming), rounded shapes. So no hand-styling in a block.
  • Hero pictures (Q1): a few drawn SVGs in docs/images/ of their repo, each named in its repo's outline (the six repos; a page loading its elements; the language pipeline; an epic's life; the app's live loop). Drawn in P8, after the Mermaid version has settled the content.
  • Screenshots only where a picture of the real thing says more (the Review tab, the editor): PNGs under 300 KB with alt text. The outline names each one.

Links

  • Relative links, so they work on GitHub and in the editor: inside a repo README-server.md; to another repo ../spell-lang/README.md; up to the kit ../README.md.
  • Dense: the first mention of any other page, folder, command or concept with a page is a link. A reader lands anywhere and can get everywhere in two clicks.
  • Code is linked by file, with its path as the link target, never a bare path in prose (WWOD §6).
  • No link into the content folder (Q3): the guides are named by title and served path in a folded "More in the docs site" list at the end of a page, with one line saying the docs site needs a checkout with the content folder and the page server running.
  • External links only to things that stay: Solid, Fomantic UI, GitHub's docs on Mermaid and details blocks.

Stubs: what's planned, written as planned

  • A feature named repeatedly is in the plan, so the README says so, in its own short section headed with a seedling: "🌱 Coming: ...". One paragraph of what it will do for the reader, one line of where it stands, never a date.
  • The list of stubs and their pages: Q10; shared editing in two stages (Q12).
  • A stub never pretends: nothing is shown as working that a reader can't run today.

Words

  • "People", never "users". "Spell UI", "Spell", "the kit"; tags in code spans (<ui-root>).
  • The house style is WWOD, "What Would Owen Do?", expanded as written where a page introduces it (Q4). The one other place the name appears: the sample address of your own projects group, owen@spell, which the owner allowed (I1). Nowhere else: not in history or asides ("the project", "the maintainer").
  • No epic names in a sentence a reader can't follow: a README says what IS. Where the story matters, an expand names the epic and what it did.
  • No old names: packages/, @spell-app/..., "monorepo", "plan doc", "Fomantic reborn", "the fork", spell-hub, spell-spaces, .compiled.js, $/; the full list is in the research reports (each one's "stale" section).

Checks before a page is done

  • Every relative link resolves (a link checker runs over every README in the cross-links phase); no link to a deleted in-folder README anywhere in the six repos.
  • Every Mermaid block renders (the same check draws them headless).
  • Every command in a setup section was run once, or is listed in this epic's To test for a hand check.
  • yarn format leaves the Markdown alone (oxfmt formats Markdown in every repo).
