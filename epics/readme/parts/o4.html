README.md: the language

  • Lead (the direction, then the facts): "Spell is English you can run." Because the source IS English, the person who asked an AI for a program can read what it wrote, change it, and learn from it. Three lines of what's built: English spell compiles to JavaScript, TypeScript and Python; the editor runs it as you type; the parser knows no language, so markdown runs on it too. One honest line: no AI feature ships in the editor yet; today, agents write spell and you read it.
  • A second lead, the parser (the owner's M19): underneath spell is a generic rule-based parser that knows no language: rules are classes with a regex-like syntax over words, scope lets earlier lines teach later ones, and a second language (GitHub markdown) runs on it at 670 of 670 spec examples. A cool thing on its own, for anyone who has fought a parser generator; link to README-parser and README-rulex.
  • FizzBuzz: the whole program (the brief's and today's README's opener), then its JavaScript and Python side by side in a two-column table. Caption: "One program, three languages out."
  • HERO PICTURE: human languages in, targets out: English (today) and Spanish (coming) on the left; the one spell tree in the middle; JavaScript, TypeScript, Python (today) and WebAssembly (coming) on the right. Caption: "N languages plus M targets, never N × M."
  • The pipeline: the nine-step Mermaid flow (source → tokens → rules in Rulex → matches and scope → the spell tree → a writer → output files → the runtime), each step linking its page.
  • The pieces: a table of the five folders (parser, markdown, core, py, spell) plus Rulex: import name, one line, its README. Then "what's NOT here": the editor, the language server, the command line's home, the projects on disk, each with a link.
  • Try it in two minutes: `spell parse "print 1 + 2 * 3"` and what it prints; `spell explain print`; `spell run` on a copy of fizzbuzz; `--target py`. Link to README-cli for the rest.
  • The language commands: one table (compile, check, watch, format, run, test, parse, repl, explain, describe, explore, speed), one line each, "these keep their names when the CLI moves".
  • How spell reads, in six bullets, each example shown BOTH ways, the sentence version and a sketch of the outline version side by side (the owner's M20): types and things (`a card is a thing` / `a card is a thing where:` with its bullets); phrases become rules (`a card "is face up" if its direction is up` / `- it "is face up" if ...`); properties and derived values; lists from 1; precedence; ids and addresses. Link to README-spell.
  • 🌱 Coming: Spanish (the `Card.spell-es` sample, labelled a hand translation nothing parses yet), WebAssembly, mixins, Spell UI written in spell, a program on a server mirrored in the page; and the other direction (the owner's M17): an agent reads a program in React or Python and rewrites it as spell, so a person can read what they already have.
  • Working on it: the checks (`spell-folders` over five folders), tests in `tests/<folder>/`, the frozen test projects with snapshots per target, `yarn spell:test:rules`; link to the kit's README-development.
  • Expands: the size of the grammar today (from the generated syntax table, with its date); the history (2017's talk, HyperCard's lineage) in three lines; the full targets list with their output file names.
  • Sources: explore-3 A, B, C6, D1-D5; today's README (its folder table is right).

README-parser.md: the generic rule-based parser

  • Lead, for someone who has used a parser generator: rules are classes with a syntax string; a parse builds a tree of matches, each knowing its rule, tokens and named groups; scope records what earlier lines declared so later lines understand new words. No grammar file, no code generation step: the rules are the program.
  • Pictures, one per stage (the owner's M1): input → tokenizer → parser → rules → matches → AST → output, drawn as one pipeline across the top of the page, then each stage's section opens with its own close-up (tokens from a line; the rule tree of one syntax; a Match tree with its groups; the AST nodes; a writer's output). Plus the scope chain (root with built-in types → project → file → block/method) and how `mutateScope()` lets earlier lines teach later ones.
  • Sections, in the owner's order:
    • Defining rules: a rule is a class with a syntax (Rulex, linked); the kinds (Keyword, Symbol, Sequence, Choice, Repeat, Subrule, Pattern); registration and tie-break order; the pets language in twenty lines (verified), then two more worked examples (a dates mini-language, markdown's heading rule).
    • Working with matches: what a Match holds (rule, tokens, groups, data, datatype); how a choice is settled (every alternative parses; highest priority, then longest, then earliest); errors never throw, a line nobody understands becomes a parse-error match; scope and `mutateScope()`; incremental re-parse.
    • AST: 83 node classes, language-neutral (`equals`, not `==`); `getAST()` is pure; "they hold what was parsed, never write output".
    • Output and bundling: the writers (one class per target, one method per node class, found by name); what a project compile writes and where (`build/`, declarations, words); how the runtime is bundled for a runner.
    • Running the output: compiled JavaScript imports `@spell/core`; under node (`spell run`), in a page (the runner rewrites imports onto URLs), as Python on `spell_core`; link to README-core and README-targets.
    • Creating parsers for other languages (the owner's M21): the recipe for a new language on the parser: a tokenizer setting (what's a word, a symbol, whitespace, strings), rule modules (one folder, one class per rule, registration order), what scope records, an AST or your own data, a writer; markdown as the worked example (its heading rule, its block scanner where rules weren't enough); a toy language built in the section (a dates mini-language, twenty lines); how spell in another human language would start (its own syntax strings on the same rule classes). Link to README-markdown.
  • Testing rules: the rule-test format (tests beside the syntax), blessing, `speedTest` (warm-up then runs). Then "Adding a rule" as a numbered recipe.
  • Expands: the token classes; the Match fields; the writer base classes.
  • Sources: explore-3 B, C1; parser/AGENTS.md; the precedence and parser-model guides; deep-wiki items 1, 4, 7.

README-rulex.md: regular expressions for words

  • Lead: Rulex is the syntax a rule is written in: it reads like a regular expression over words and sub-rules, compiles once at registration, and prints back. Opt-in by one import.
  • The cheat sheet: the construct table from explore-3 C2 (keywords, symbols, escapes, subrules, named groups, choice, lists, optional / repeat / counts, case-insensitive, spacing, `{space}`), each with SEVERAL examples (the owner's M4): the syntax, two or three inputs it matches, one it doesn't, and what it compiles to.
  • Three real spell rules: `Plus` (with its tests), `for each`, `print`; the syntax string beside what it accepts.
  • What it can't say, and what's hand-written instead (fences, "any token but", block nesting, emphasis).
  • Where it runs: eager at registration (a bad syntax fails at load); `toRulexSyntax()` round-trips.
  • Expands: its own grammar in words ("rulex can't define itself"); the tokenizer it uses; the tests.
  • Sources: explore-3 C2; the rulex guide; deep-wiki item 3. Don't quote a count of syntaxes without saying what's counted.

README-markdown.md: the second language, as the worked example

  • Lead: GitHub-flavoured markdown written as rules on the same parser: the proof that the parser knows no language, and a real engine spell's docstrings, the editor's previews and the language server use.
  • Picture: a markdown line through the same pipeline (tokenizer → line rules in Rulex → block scanner → inline parser → markup or `ui-*` tags).
  • How to call it: the verified `MD.toHTML()` and `MD.render({ ui: true })` examples with their output; the options; "raw HTML passes through: the caller sanitizes".
  • How it's built: line rules (the heading rule in two lines), the block scanner and inline parser ported from commonmark, the renderers.
  • The numbers: 670 of 670 spec examples; 1.8× marked's time; 59 kB gzipped, which is why Spell UI's `<ui-markdown>` keeps marked and spell-app's `<spell-markdown>` uses this.
  • What uses it: the three users, linked (spell-app's element, docstrings, the language server).
  • Expands: the files; the spec test and `yarn markdown:spec:update`.
  • Sources: explore-3 C3; markdown/AGENTS.md; the markdown guide.

  • The twenty modules as a table (the owner's M22): module, what it reads, one example line, one output line (core, variables, constants, expressions, math, properties, lists, UI, classes, async, draw, JSX, types, assignment, statements, events, if, methods, tests, blocks).
  • What it reads, each with a real line and its output: sentence style and outline style (Card.spell both ways); types, enums and derived properties; phrases that become rules (`a card "is a (suit)" for its suits`); lists and `where`; drawing (`a card is a drawable thing` with a `<css>` block); events; tests (`to test ...`); things with ids and addresses (`@spell/examples/solitaire/Card.spell`).
  • The compiler: `SpellProject` and its files, what `compile()` writes (the `.spell.js`, `.spell.tsx`, `.spell.py`, declarations, words), `build/` is never committed; the targets table linking README-targets.
  • The frozen test projects: the eleven, with snapshots per target and empty `tsc` / `pyright` output; "never edited to follow the live examples".
  • Adding a rule: the recipe (module folder, class file, syntax and tests, registration order, bless).
  • What's not here: project groups are registered by spell-app's spaces; the highlighter is; the node-only helpers (type check, pyright, the syntax table).
  • Expands: the built-in types table (text, list, thing, app, date); the files; PARSING.md as the deep map (linked, with its stale paths noted for fixing).
  • Sources: explore-3 C6; spell/AGENTS.md; the spell-syntax, outline-spell and people-and-orgs guides; deep-wiki items 2, 5, 6.

README-core.md: the runtime compiled spell runs on

  • Lead: what a person reading compiled output meets first: `core`, `Thing`, `List`, `App`, drawing, events, saving by id; one object assembled by accretion, imported by compiled code as `@spell/core`.
  • Picture: a compiled line and the core calls it makes (`core.getRange`, `core.isOfType`, `trigger("card-click")`).
  • The pieces: classes, list helpers, drawing with Solid and error boundaries per thing, events, JSON with `$type`, carrying things across a recompile, saving by id, seeded random, the model-only entry for libraries.
  • Three things a reader trips on (the owner's M2), each its own section with a worked example:
    • Reactivity: a thing's properties are cells; a write reads back at once (`set x to 1` then `print x`), Solid follows for drawing; why not Solid signals.
    • Positions count from 1: `the first item`, `item 3 of the list` → `core.getItem(list, 3)`; the JavaScript and Python helpers that make it so; where 0-based leaks are caught.
    • The TypeScript and Python runtimes side by side: the same `core` surface in both, the declarations file that pins it, what Python doesn't have yet (`not_ported_yet`); a table of one line through `core` in JS and in Python.
  • Who may import it: only the app's runner entry, so a page has one copy; the Python twin (link to README-targets).
  • Expands: the generated declarations file and what it pins; the files.
  • Sources: explore-3 C4; core/AGENTS.md; the core-reference guide.
