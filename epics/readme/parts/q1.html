The brief asks for "lots of pretty pictures". Pictures in a README have to render on GitHub, in VS Code's Markdown preview and in the docs site, and stay editable by the Opus agents who finish the pages after the hard work is done. Two ways to draw them, and they can be mixed.

  • A MERMAID block is a diagram written as text inside the Markdown (```mermaid): flowcharts, sequence diagrams, block diagrams. GitHub and VS Code draw it; an agent edits it like prose. It looks tidy, not designed.
  • An SVG ILLUSTRATION is a drawn picture, a file beside the README (docs/images/*.svg): as pretty as its author. An agent can write SVG by hand, but editing one later is slow, and a wrong picture is worse than none. 
```mermaid
flowchart BT
  kit[spell-kit:  util · toolchain · server · element]
  lang[spell-lang:  parser · markdown · core · py · spell] --> kit
  ui[spell-ui:  the ui-* elements] --> kit
  brand[spell-brand] --> ui
  epic[spell-epic] --> ui
  app[spell-app:  app · spaces · lsp · cli · page-server] --> lang
  app --> brand
  app -.runs.-> epic
```
  • Every structure, flow and sequence is a Mermaid block: cheap to make, cheap to keep true.
  • Three to five "hero" pictures are drawn SVGs: the six repos, a page loading its elements, the language pipeline. Each drawn once, in the outline's list, and kept small.
  • Cost: the hero SVGs are a few hours of care; everything else is minutes.
  • Fastest, and every picture stays editable by any agent.
  • Cost: nothing looks designed; "pretty" is a stretch.
  • The prettiest pages.
  • Cost: each picture is slow to make and slower to fix; Opus agents will drift them out of truth.
  • The writers' brief (1.2) says "Mermaid, with the hero pictures listed per README".
  • Each repo's outline names its hero picture, if it has one; P8 · Cross-links checks every Mermaid block renders.
