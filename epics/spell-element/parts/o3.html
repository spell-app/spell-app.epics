How the custom-element layer under every <ui-*> tag works today (packages/solid-element), and how it would work once this epic folds it into DOMElement / UIComponent (the fold: 1.2). Written for you to read BEFORE any code changes, so you can decide whether, and how, the fold goes ahead. Nothing here has been built.

  • Written 2026-10-08 in epic wwod-spell-ui, as its Overview 1.5, for its phase "Fold solid-element"; moved here the same day, with only its ids, numbers and links changed (1.1).
  • The code it describes is the wwod-spell-ui branch's, as of its P17 commit (6b97b076).
  • solid-element is the code that turns a Solid component into a custom element: it defines the tag, turns attributes into values, makes the shadow root, and runs the component inside Solid.
  • It started as a copy of Solid's own @solidjs/element and the older component-register (both MIT, Ryan Carniato), merged into one package, then fixed in 11 places. None of the fixes was ever sent upstream (its UPSTREAM.md: "Nothing here has been filed").
  • Read in order: today's flow (1.3.1 to 1.3.6), then the fold (1.3.7 to 1.3.12).
  • Two surprises worth knowing first:
    • packages/app uses solid-element too, directly: <spell-app> and <spell-editor> are defined with its customElement(). The fold as first written didn't count them (1.3.9).
    • The Vite hot-reload plugin is NOT unused: ui's vite.config.ts runs it for yarn dev. It moves, it doesn't go (1.3.7).

Three packages import it. ui uses a handful of its exports; app uses its main function for two elements of its own; brand only points its Vite config at its source.

What happens, in order, from a family's index.ts calling UIButton.define() to a styled button on the page. The steps marked "solid-element" are the ones the fold would move. 

static defineTag(this: UIComponentClass, definition: E.ElementDefinition): CustomElementConstructor {
  const {
    DOMElement: BaseElement,
    delegatesFocus,
    assignSlots,
    isAFormControl,
    Fallback
  } = UIComponent.setupFor(this)
  UIComponent.register.call(this, definition)
  return customElement(
    definition.tag,
    definition.props,
    (attrs, { element }) => new this(element as unknown as DOMElement, definition, attrs).onMount(),
    {
      BaseElement,
      shadowRootInit: {
        mode: "open",
        delegatesFocus,
        slotAssignment: SlotAssignments[assignSlots]
      },
      internals: true,
      formAssociated: isAFormControl,
      keepAlive: true,
      errorBoundary: UIComponent.ISOLATE_ERRORS,
      onError: (element, error) => UIComponent.onError(element as unknown as DOMElement, error),
      fallback: (element, error) => UIComponent.renderFallback(element as unknown as DOMElement, error, Fallback)
    }
  )
}
  • Every option ui passes is fixed except three: BaseElement, delegatesFocus / slotAssignment, formAssociated. internals and keepAlive are always true.
  • So most of solid-element's options are choices ui never makes (1.3.8).

Owen decided (2026-10-08) that attribute values get ONE store (Q5, built in P3): DOMElement keeps one CONVERTED value per attribute, from the attribute's text or a property write, and no copy of the raw text, which stays on the attribute itself (Q18). ui's reactive record gives each attribute one change signal; the Solid signals (component.attrs, createProps()) go, and with them the stale read described below. The property rules stay, with tidier definitions: one converter per kind of value, and a property that would hide a DOM member is one clear error when the tag is defined (Q6, built in P2).

Each element holds its attribute values TWICE, on purpose: once in a plain record that is always up to date, and once as Solid signals that tell Solid code a value changed.

  • The record: domElement[STATE].values, one entry per attribute, already converted (size: "large", disabled: true). A write lands there at once.
  • The signals: component.attrs, one Solid signal per attribute (createProps()). A Solid 2 signal write lands a microtask later, so a read right after a write still sees the old value.
  • ui's reactive members (epic wwod-spell-ui, P14 · Reactive Shape) use both: a getter like this.size reads the RECORD (fresh), and, when Solid is listening, also reads the SIGNAL, only to subscribe. That signal is the "notifier".

An attribute change

  1. The page runs button.setAttribute("size", "large").
  2. The browser calls attributeChangedCallback("size", old, "large") on the element.
  3. solid-element skips it when it is its own reflection (below), or when a property set before the upgrade is still waiting (that one wins).
  4. It converts the text with ui's converter (ElementDefinition.convert()).
  5. It stores the value in the record: no reflection back to the attribute.
  6. It calls every change callback with (key, value, old, "attribute"): withSolid's writes the signal; a component's own (UIRadio re-joins its group when name changes).
  7. Solid re-runs what read the signal; this.size already returns "large".

A property write

  1. The page (or a framework) runs button.size = "large".
  2. The setter on the prototype converts the value (fromProperty) and stores it in the record.
  3. If the attribute reflects, it calls setAttribute("size", "large") at once, with a flag up: the browser calls attributeChangedCallback inside that call, and the flag makes it ignore its own write.
  4. The change callbacks run with "property", and the signal is written, as above.
  • Defaults never reflect: a bare <ui-icon> grows no attributes, as a native element doesn't.
  • A component writing its own attribute (this.isOpen = true on a @controlled member) goes through the same setter: it IS a property write. 
// solid-element attributes.ts:  every write, from an attribute or a property
export function setProp(element: SolidElement, prop: NormalizedProp, value: unknown, source: ChangeSource) {
  const state = element[STATE]
  const old = state.values[prop.key]
  if (source === "property") value = prop.fromProperty(value)
  state.values[prop.key] = value
  // dev only:  a hot redefinition re-converts attribute values, keeps property writes (`hot.ts`)
  if (import.meta.hot) (state.sources ??= {})[prop.key] = source
  if (source === "property" && prop.reflect) reflect(element, prop, value)
  for (const callback of state.propertyChangedCallbacks.slice()) callback(prop.key, value, old, source)
}

  • Today Reactive.ts reaches into solid-element's private record through the exported symbol STATE: the one place ui depends on solid-element's insides.
  • After the fold the record is DOMElement's own member, and that reach goes (1.3.7).

Owen decided (2026-10-08) that form association lives on DOMElement, switched per tag (Q7, built in P2): the four form callbacks are DOMElement methods, each calling a component method (onFormReset() ...) whose default on UIComponent does nothing. static formAssociated is still set per tag from elementSetup.isAFormControl, so non-controls like <ui-section> never get them called. No registered functions, and no replay to a late registration: the early call is kept on the DOM element and handed over when the component is made.

Form association

  • A form control (elementSetup.isAFormControl) is defined with formAssociated: true: solid-element sets the platform's static formAssociated = true on the tag's class.
  • Its constructor calls attachInternals(), for every ui element (:state() needs it too), unless the base class did.
  • The browser then calls four form callbacks on the element. solid-element forwards each to the functions a component registered:
    • formResetCallback to onFormReset: FormComponent.onFormReset()
    • formDisabledCallback to onFormDisabled: UIComponent.formIsDisabled
    • formStateRestoreCallback to onFormStateRestore: rating, calendar, slider
    • formAssociatedCallback to onFormAssociated: the radio's group
  • A catch: the browser calls formAssociatedCallback on insertion, BEFORE the component exists. solid-element remembers the last "associated" and "disabled" report and replays it to a late registration, which is why UIComponent defers that first write a microtask.
  • Submitting the value (internals.setFormValue()) and validity are ui's own, in DOMFormControl / FormComponent: solid-element plays no part.

Owen decided (2026-10-08) to keep each element's safety net, always on, and drop the switch (Q8, built in P2): UIComponent.ISOLATE_ERRORS and the test that measures drawing without the net go. Why the net can't be optional is his question at the end of this part.

Error catching and the fallback

  • Why it exists: in Solid 2, an error thrown while one element renders halts Solid's scheduler for the whole page ([REACTIVITY_HALTED]): every other element freezes.
  • solid-element wraps each element's render in Solid's <Errored> boundary. When the constructor, render() or an effect throws:
    1. the element gets :state(errored)
    2. UIComponent.onError() runs, OUTSIDE any Solid owner (so it may change state): one console.error, a cancelable ui-error event, ready resolved
    3. UIComponent.renderFallback() runs: a form control's plain-DOM fallback, else a bare <slot>, a microtask later
  • UIComponent.ISOLATE_ERRORS = false turns the boundary off, only to measure what it costs (test/isolation.test.tsx).
  • Unused by ui: solid-element's own errorEvent option; ui sends its ui-error itself.

Owen asked (2026-10-08): "If a component fails inside a container that has <Errored>, do we lose the page? If not, make the net optional."

The answer: yes, we would lose the page, so the net stays always on.

  • Each element draws in a Solid root of its own.
  • Once the owner lookup goes (Q9), that root has no parent, so an error can't climb to a container's net.
  • Even today it couldn't for an element written in HTML: the owner is the JSX that CREATED the element, never the element it sits in.
  • So without its own net, one failing element freezes the whole page. P2 adds a test proving it: a failing element inside a container that has a net still gets :state(errored), while its siblings keep updating.

Owen decided (2026-10-08) to drop this rule (Q9, built in P2): an element's Solid root no longer starts under the owner Solid's compiler stamped on it. lookupOwner() and the reliance on the stamp go; app context is found by walking up the page to the nearest <ui-root>, which holds the value. The test tool tools/frameworks/solid/identity.js, today the only provider, sets it on <ui-root> instead. A Solid app's own providers no longer reach inside ui-* tags.

Context across the element boundary (owner adoption)

  • In Solid, context (useContext) flows down the tree of OWNERS: each component runs under the owner that created it. A custom element starts a new Solid root, so by default context stops at it.
  • Solid's compiler stamps _$owner on every custom element its JSX creates. solid-element starts the element's root UNDER that owner, so an app's context reaches inside: UIComponent.appContext reads UIComponent.AppContext that way.
  • Fix 8: an element created WITHOUT JSX (innerHTML, a template clone) has no stamp. The walk up to the nearest stamped ancestor now continues past a shadow root to its host.
  • Fix 11: the original preferred the owner of the <slot> an element is assigned to. In Solid 2 that made the element's whole root die whenever its host re-created the slot (inside a <Show>): slotted elements silently froze. Now the creator's owner always wins; the price is that context provided AROUND a <slot> doesn't reach slotted elements. ui uses PartContext / OwnerContext for that.
  • A stamp from a different copy of Solid (a second solid-js on the page) can't be adopted: solid-element warns and renders without an owner. 
export function lookupOwner(element: Element): Owner | undefined {
  let next: Stamped | null = element as Stamped
  while (next) {
    const owner = next._$owner
    if (owner && !isDisposed(owner)) return owner
    // a ShadowRoot (nodeType 11 with a host) continues at its host;  NEVER read `host` elsewhere (`<a>.host` is a URL part)
    next = (next.parentNode ?? (next.nodeType === 11 ? next.host : null) ?? null) as Stamped | null
  }
  return undefined
}

The event re-targeting fix

  • Solid doesn't put an onClick listener on each button: it puts ONE listener per event type on a container (here, each shadow root) and walks the event's path itself ("delegation").
  • That walk leaves its state ON THE EVENT OBJECT, which breaks the platform's rules for everyone listening outside:
    • a page listener on <ui-input> sees event.target = the inner <input>, not the element (the browser's re-targeting is overwritten)
    • a Solid app's <ui-button onClick={...}> never runs for clicks inside the button: Solid's "already handled" marker points into a shadow root the app's container can't see into
  • Fix 10 (events.ts, 238 lines) wraps Solid's listener on each shadow root: after it, the event's own target / currentTarget are deleted (the platform's come back) and the marker moves to the host; before it, a walk an inner element already did is resumed, not repeated.
  • It reads private parts of Solid's DOM runtime (_$SOLID_EVENT_OWNER, _$$click, what registerDelegatedContainer() returns): a Solid version bump may move them. Its tests fail when they do.
  • ui's AGENTS.md: "NEVER work around a wrong target in a component -- fix it there".

Hot reload (yarn dev only)

  • The goal: edit a component and every live <ui-button> re-renders with the new code, in place: same element objects, same attributes and property values, no page reload.
  • The obstacle: the platform can't define a tag twice. So the class stays, and what it READS is swapped: its component, its prop definitions, its options.
  • The chain, on saving UIButton.tsx:
    1. Vite re-runs the family barrel (ui-button/index.ts), a hot-reload boundary because solid-element's Vite plugin appended import.meta.hot.accept(() => hotUpdate(import.meta.hot)) to it
    2. the barrel calls UIButton.define() again; HotDefinitions (dev-only, ui) sees a NEW class of the same name and calls defineTag() for every tag the old one had, translated aliases included
    3. customElement() finds the tag defined, and hot.ts swaps the class's component, props and options in place; or records why it can't (observed attributes, formAssociated, base class or shadow options changed)
    4. hotUpdate() re-renders every live instance (tracked by weak references, dev only), keeping property writes and re-converting attribute values; or, after a refusal, asks Vite for a full reload
  • Sheets: a family's ?inline CSS updates through HotDefinitions.updateStyle(), no re-render.
  • Shared code (core, forms, the runtime) reaches several barrels: the plugin reloads the page.
  • Checked end to end by yarn test:hmr (tools/hmr.e2e.ts).
  • In a production build, import.meta.hot is undefined, so none of this ships.

The server render

  • $/ui/static renders ui-* markup to plain HTML in node, for search engines. Node has no HTMLElement, so the element class can't exist there.
  • solid-element's /server entry, ServerElement, gives a linkedom element the instance API a component may call (addReleaseCallback ...), converts its attributes as the browser element would, and runs the component with that element "current", so onConnect() registers instead of throwing. Hooks never run on a server.
  • ServerDOMElement.ssr.ts wraps it; StaticRender.ssr.ts builds each component with it, then renderToString.
  • Not the same as the declarative shadow DOM adoption (shadowRoot.ts): that one is in the browser, emptying a server-rendered <template shadowrootmode> before the first client render (test/dsd.test.ts).

The proposal. The platform's custom-element callbacks become DOMElement's own methods; rendering under Solid becomes UIComponent's; three big, separate jobs keep files of their own beside them.

export class DOMElement extends BaseElement {
  readonly internals: ElementInternals = this.attachInternals()

  /** The attribute values, converted:  read fresh by the component's getters. */
  readonly attributeValues: Record<string, unknown>

  connectedCallback() {
    this.restoreUpgradeProperties()
    if (!this.component) this.definition.Component.mount(this)
    this.component?.onConnect()
  }

  disconnectedCallback() {
    this.component?.onDisconnect()
  }

  attributeChangedCallback(name: string, _old: string | null, text: string | null) {
    const attribute = this.definition.attributeNamed(name)
    if (!attribute || this.reflecting === name || this.upgrade?.has(attribute.property)) return
    this.setValue(attribute, attribute.fromAttribute(text), "attribute")
  }

  formResetCallback() {
    this.component?.onFormReset()
  }
  // ... formDisabledCallback, formStateRestoreCallback, formAssociatedCallback, renderRoot, dispose()
}

For someone writing a ui component, ideally nothing. Two things do change, and each is a question for you: Q1 and Q2.

  • Unchanged: UI<Name>.define(), the vocabulary, elementSetup, render(), onMount(), the reactive members, this.on() / send(), the fallback, and the DOM element's public API (attributes, properties, events, ready, dispose()).
  • The component's constructor (domElement, definition, attrs) stays: the caller becomes UIComponent itself instead of solid-element.

Owen decided (2026-10-08): methods on the component (Q1, option A, built in P2). Each lifecycle event is a component method with an empty default; a component overrides only the ones it needs.
