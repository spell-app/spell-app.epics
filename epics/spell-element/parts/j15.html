@protoMerged (P3) merges each class's elementSetup down the class chain as the class is defined. The agent made four calls in how it landed.

  1. setup is deleted, not kept as an alias:
    • this.elementSetup IS the merged value, so one name is enough
    • every reader now says this.elementSetup, e.g. this.elementSetup.styleSheets
  2. no static setupFor():
    • code outside an instance (the server render, the docs tools) reads SomeClass.prototype.elementSetup
    • why: the merged value already sits on the prototype; a helper would only wrap that read
  3. styleSheets comes first in each elementSetup literal, so it reads the same everywhere
  4. keys merge one level deep:
    • a subclass's styleSheets REPLACE its base's whole
    • to add to them, spread the base's: styleSheets: [...Base.prototype.elementSetup.styleSheets, mine]
    • why: the same as the static it replaced, so no component changed behaviour
  • setup gone, no setupFor(), shallow merge
  • two names for one thing; a deep merge would ADD style sheets where a subclass meant to replace them
  • this.setup no longer exists: read this.elementSetup
  • outside an instance: Class.prototype.elementSetup
  • style sheets inherit as before: replaced unless spread

Can we use protoype reassignment to do @protoMerged

Yes, for the top level of elementSetup. Each class's own setup object would get its parent's as its prototype, so a key it doesn't state is looked up on the parent's. Nothing is copied. Nested objects (styleSheets, aria) can't use the same trick, because code walks over their keys.

  • One story with J25 (the CSS states move back into elementSetup) and J17 (the type of its DOMElement key): all three are about how this one object is inherited. 
return function (this: This, value: Value): Value {
  const parentPrototype = Object.getPrototypeOf(this.prototype) as Record<PropertyKey, unknown> | null
  // a NEW object:  the parent's merged keys, then this class's
  const merged = { ...(parentPrototype?.[context.name] as object | undefined), ...value }
  Object.defineProperty(this.prototype, context.name, { value: merged, writable: true, configurable: true })
  ;(this as ProtoAware).protoDefined?.(context.name, merged)
  return value
}
 
return function (this: This, value: Value): Value {
  const parentPrototype = Object.getPrototypeOf(this.prototype) as Record<PropertyKey, unknown> | null
  const parentValue = parentPrototype?.[context.name] as object | undefined
  // a key this class doesn't state is looked up on the parent's object
  if (parentValue) Object.setPrototypeOf(value, parentValue)
  Object.defineProperty(this.prototype, context.name, { value, writable: true, configurable: true })
  ;(this as ProtoAware).protoDefined?.(context.name, value)
  return value
}

What it gives:

  • ONE object per class: UICheckbox.elementSetup and UICheckbox.prototype.elementSetup are the same object
    • the note "the static keeps only what THIS class stated; read the merged result from the prototype" goes away
    • in the browser's console, its own keys are what that class changed; the rest show under [[Prototype]], the parent's
  • live inheritance: a key changed on a parent's object later shows in every subclass
    • no practical gain today: nothing changes a setup after the class is defined (hot reload makes a new class)

What it costs:

  • anything that COPIES the whole setup sees only that class's own keys: a spread, Object.keys(), Object.assign(), JSON.stringify()
    • today only three test helpers do it, imitating the decorator: { ...Component.prototype.elementSetup, ...setup } in DOMElement.test.tsx, HotDefinitions.test.tsx, UIItem.test.tsx; they'd chain the same way
    • every real reader reads keys by name, which goes through the chain: this.elementSetup.styleSheets, const { canRenderUnstyled } = this.elementSetup, tagSetupFor()'s destructure
    • hot reload, the site data and the static render never copy a whole setup
  • a read walks up a few objects (UICheckbox → CheckControl → FormComponent → UIComponent): a handful of reads per element built, too small to measure

Why styleSheets and aria keep the spread:

  • code walks over their keys, and would silently miss the parent's: Object.keys(this.elementSetup.styleSheets) (styleSheetNames, UIItem), Object.entries(...) (UITable, the static render's sheet), Object.assign(internals, this.elementSetup.aria)
  • sheet ORDER matters, and a spread lets each class choose it: UIPanel puts its base's sheets first, UICard its own first; a chain can't say which
  • one object per class, nothing copied
  • styleSheets: { ...UISection.prototype.elementSetup.styleSheets, panel: panelCSS } as today
  • a spread of a whole setup keeps working; two objects per class, the static only what it stated
  • protoMerged() in decorators.ts: its body (2 lines) and its doc
  • the three test helpers chain instead of spreading
  • the "static keeps only what that class stated" lines go from UIComponent's doc and packages/ui/AGENTS.md
  • no component file changes; no change in behaviour
