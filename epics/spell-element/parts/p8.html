Only some elements take disabled (43 vocabularies declare it, with different meanings), and nothing generic takes visible.disabled and visible work on every element, read by the base class, each with one meaning that a family can extend.
  • Owen: “we should support disabled on anything, not just form fields”, and “I’d also like to support visible as well”
  • every element takes disabled:
    • one shared attribute, read by the base class (isDisabled by default)
    • so a vocabulary does not have to declare it
  • every element takes visible
  • decide first, with Owen, on a details page; the questions to decide:
    1. what disabled MEANS on an element that is not a control:
      • it swallows clicks and keys, as a control does
      • or it only LOOKS disabled, as <ui-icon> and <ui-segment> do today
      • or either, by a setting
    2. does it reach the elements INSIDE, as <fieldset disabled> does to its controls (by inert?), and how does it combine with a <fieldset disabled> around a control (formIsDisabled)
    3. accessibility:
      • aria-disabled
      • leaving the tab order
      • moving focus off an element that becomes disabled
    4. visible and the platform’s own hidden attribute, which every HTML element has:
      • visible="false", or hidden?
      • visible already means something on 4 vocabularies (sidebar, dimmer, popup ...): shown or open, often animated
      • rename theirs, or let visible be the same idea everywhere
    5. how visible hides an element:
      • display: none: out of the layout
      • visibility: hidden: it keeps its space
      • or a transition (<ui-transition>)
    6. the server render ($/ui/static) and the docs (components.json) showing both on every element
    7. others in the same family to consider:
      • loading (17 vocabularies)
      • readonly (6)
      • inert
