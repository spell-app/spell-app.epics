Chose to start a @fromContent getter's MutationObserver on the member's first read over starting every watch in onMount() / onSettled() (the brief's design), because a value computed and watched at the same moment is never stale, needs no extra rescan once the watch starts, and a member that's only read sometimes costs nothing until it is.

  • Option A (chosen): first read starts it. LoadableComponent.inlineText watches only when it's shown (no source); no isServer guard in onMount().
  • Option B: start every watch in onMount(), then rescan once. Watches members nobody reads.
  • A @fromContent METHOD has no read, so it starts from Reactive.startEffects() (UIComponent.onMount()), and isn't called at the start.
  • Timing moved slightly earlier for UICard, UIReveal, UIProgress, UITreeDiagram, EpicUpdate, EpicItem (first read, usually in render), later for none.
  • Stopped when the DOM element is released, as before (NOT on disconnect).

`@fromContent()` => `@watches()` ?

The decorator has two jobs, and one name reads well for only one of them. On a GETTER it says what the value is (read from the element's children and text). On a METHOD it says when the method runs (when those change). @E.watches reads fine on the method and vaguely on the getter.

  • 11 getters use it (UICard, UITable, UIReveal, UIProgress, UITreeDiagram, LoadableComponent, brand's color set, 4 in epics); 1 method (UIAccordion).
  • @E.watches: watches WHAT? @E.onChange("isOpen") also watches something. And watch() is already a method name in UIRoot, UIDocsToc and ThemePreference.
  • @E.fromChildren: wrong for half the sites. UIProgress, UITreeDiagram and LoadableComponent read the TEXT; UIReveal watches attributes deep inside.
  • @E.watchesContent: clear on both, but on a getter it says how, not what.
// UIProgress.tsx:  a getter
@E.fromContent({ childList: true, characterData: true, subtree: true })
get elementText(): string { ... }

// UIAccordion.tsx:  a method
@E.fromContent({ childList: true })
protected onChildrenChanged() { ... }
 
// a getter:  what the value IS
@E.fromContent({ childList: true, characterData: true, subtree: true })
get elementText(): string { ... }

// a method:  WHEN it runs
@E.onContentChange({ childList: true })
protected readPanels() { ... }
 
@E.watchesContent({ childList: true, characterData: true, subtree: true })
get elementText(): string { ... }

@E.watchesContent({ childList: true })
protected onChildrenChanged() { ... }
  • With A, the method form joins the other "when it runs" decorators (@E.on, @E.onChange, @E.onConnected), so the method is named for what it does (readPanels()), not onChildrenChanged() twice over.
  • Same options, same single observer per element, same timing: only the names change.
  • Parentheses stay: both take the "what to watch" options.
  • On a field or getter, the decorator says what the member IS: @E.state, @E.controlled, @E.derived, @E.lazy, @E.cssState("open"), @E.aria("busy"), @E.fromContent(...).
  • On a method, it says WHEN the method runs, and starts with on: @E.on("command"), @E.onChange("isOpen"), @E.onConnected, @E.onContentChange(...). Every one of these runs its method untracked.
  • Two say HOW a method runs: @E.once, @E.untracked.
  • A decorator with no arguments has no parentheses: @E.state, @E.onConnected.
  • Each reads as English where it sits; fits the naming story
  • Two names to learn instead of one
  • One name; says it watches the content
  • On a getter it says how the value stays fresh, not what it is
  • Shortest; but doesn't say what is watched, and sits beside watch() methods
  • No change; the method form keeps reading oddly
