Owen picked "as a component pack" (bedtime page, 2026-10-09). The elements ARE a pack now (vocabularies, `UIComponent` subclasses, DOM element classes, loaded by `<ui-components source>` under a `<ui-root>`), but the stock pack build can't make their script, for real reasons:

  1. It writes ONE classic script (an IIFE): no code splitting, so Monaco (4.2 MB) and the parser (0.9 MB) would sit in it, and every page with only a `<spell-app>` would download all of it (~1.3 MB gzipped, against 29 kB today). Monaco's worker can't be found from a classic script either.
  2. `<spell-app>` loads `spell-runtime.js` afresh per app, by URL, and shares React with it: that is a Vite ES build (`dist-element/`) whatever the pack is.
  3. A pack's `pack/` is committed: megabytes of minified churn on every app / spell / parser / lsp change.
  4. Its staleness hash follows only the pack's own `components/` and `src/`: a parser change would never mark it stale.
  5. It shares only Solid and Spell UI's core, from `SpellUI.packModules`, which only the docs bundle sets.

Built instead: `vite.element.config.ts` (`componentPack()`) writes `dist-element/spell.pack.js`, a classic script calling `SpellUI.registerPack()` with a catalog read by Spell UI's own `RootCatalog`; its `define()` imports `spell-app.js` and `spell-editor.js` beside it. `spell-ui.js` gives the page `SpellUI.registerPack`. Spell UI's `ComponentPacks` now waits for a `define()` that returns a promise.

Limit: it works only where Solid and Spell UI are `dist-element/`'s (the demos, any page loading `spell-ui.js`), never on a docs page, whose bundle brings a second Solid.
