Owen's answer to analysis Q9, "Solid context: how does it reach inside an element?" (2026-10-08): B · Drop it; context through ui's own channels.

An element's Solid root no longer starts under the owner Solid's compiler stamped on it; app context is found on the page instead.

  • today each element's root starts under the stamped owner (_$owner, from Solid's contextToCustomElements compile option), found by lookupOwner() climbing past shadow roots
  • after: each element finds app context by walking up the page to the nearest <ui-root>
  • elements made by innerHTML then behave like ones made in JSX
  • why each of today's fixes exists: 1.3.5
  • not chosen: A (keep today's rule, moved as is), C (keep it, with a page fallback)

Owen asked: "<ui-root> acts as the 'provider element', correct?"

The answer: yes.

  • each element finds app context by walking up the page to the nearest <ui-root>, which holds the value
  • a smaller provider element nested deeper is possible later, but nothing needs one today
  • the evidence:
    • the only Solid context ui has is UIComponent.AppContext (UIComponent.tsx, about line 241)
    • it is read once, in the constructor (about line 142)
    • in the repo it is provided only by the test tool identity.js
  • the lookup on owners (lookupOwner()) and its reliance on the compiler's stamp go
  • app context is read from the nearest <ui-root>
  • identity.js changes to set the value on <ui-root>
  • a Solid app's own providers no longer reach inside ui-* tags
