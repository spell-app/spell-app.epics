Chose to run every @onChange method inside untrack() (Reactive.startEffects() wraps the apply), over decorating each such method @E.untracked or leaving its untrack()s.

  • Owen decided @E.on handlers run untracked by default (bedtime page, 2026-10-09); the same reasoning holds for an effect's apply: only the members it names should re-run it.
  • Solid 2 already runs an effect's apply untracked, so behaviour doesn't change; the server's writesDOMElement apply is now untracked too.
  • untrack() inside @onChange methods went (UIPopup, UIShape, UIRadio ...); documented in @onChange's docstring and ui's AGENTS.md.

Should this be a default, can you can pass `{ tracked }`?

It already is the default, and the only way: an @E.onChange method re-runs only when a member it NAMES changes. A { tracked: true } option couldn't do what its name says, so I'd leave it out.

  • Each @E.onChange is a Solid effect in two halves: the first READS the named members (and is followed), the second runs the method with their values.
  • Solid 2 never follows reads in the second half, with or without us. This change only stopped our code from saying so by hand (untrack(() => ...) around each read).
  • To make the method's own reads count, it would have to run in the FIRST half. But Solid forbids writes there, and almost every @E.onChange method writes (a member, the DOM element, a timer).
  • The way to re-run on one more thing is already there: name it. Every on… method decorator works this way (@E.on, @E.onChange, @E.onConnected, @E.onContentChange). 
@E.onChange("isReady", "activeSideIndex")
protected onActiveSideIndexChanged(isReady: boolean, index: number) {
  if (!isReady) return
  // `sides` and `queuedIndex` are read, but don't re-run it:  only the two names above do
  const next = this.normalize(index, this.sides.length)
  if (next !== this.queuedIndex) void this.enqueue(this.defaultFlip, next)
}
 
@E.onChange("isReady", "activeSideIndex", "sides")
protected onActiveSideIndexChanged(isReady: boolean, index: number, sides: E.DOMElement[]) { ... }
  • On a field or getter, the decorator says what the member IS: @E.state, @E.controlled, @E.derived, @E.lazy, @E.cssState("open"), @E.aria("busy"), @E.fromContent(...).
  • On a method, it says WHEN the method runs, and starts with on: @E.on("command"), @E.onChange("isOpen"), @E.onConnected, @E.onContentChange(...). Every one of these runs its method untracked.
  • Two say HOW a method runs: @E.once, @E.untracked.
  • A decorator with no arguments has no parentheses: @E.state, @E.onConnected.
  • As built: the named members are the whole list of what re-runs it
  • One rule for every on… decorator
  • The method would run in the first half: no writes, no cleanup, so it couldn't do what these methods do
  • No site needs it today; a getter (@E.derived) already covers "recompute from whatever I read"
  • No code change: J33 stands as built
  • @E.onChange's docstring gains one line: "To re-run on another member, name it; there is no tracked mode"
