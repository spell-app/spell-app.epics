Owen's answer to analysis Q7, "Form controls: where does form association live?" (2026-10-08): B · All on DOMElement, switched per tag. One class for every element; whether the browser treats a tag as a form control is set per tag, as today.

  • controls like <ui-input>, <ui-select> and <ui-checkbox> join a page's <form> through ElementInternals
  • today's flow: 1.3.5
  • not chosen: A (internals for all, the form callbacks only on a DOMFormControl subclass)

Owen asked: "The extra callbacks are set up on UIComponent, and only things that need them need to override, correct? So for e.g. <ui-section> there would be no change?"

The answer: nearly.

  • the four platform callbacks (formAssociatedCallback, formResetCallback, formDisabledCallback, formStateRestoreCallback) are methods on DOMElement, the custom-element class every ui-* tag gets
  • each forwards to a hook method on its component (onFormReset() ...), whose default on UIComponent does nothing
  • only FormComponent's controls override them
  • static formAssociated is set per tag from elementSetup.isAFormControl, so for <ui-section> (not a form control) the browser never calls them: its code and behaviour don't change
  • the only cost is those few methods existing on every element's class
  • no DOMFormControl class: the four form callbacks live on DOMElement
  • the early form call (it arrives before the component exists) is kept on the DOM element and handed over when the component is made
  • every element's class carries a few form methods it never uses (a few hundred bytes)
