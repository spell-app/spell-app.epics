`@onConnected()` ?

@E.onConnected fits the other method decorators (@E.on, @E.onChange), so yes, with one guard. It sits two letters away from onConnect(), the hook every component already has, and the two run at different moments.

  • onConnect(), the hook: runs at once, inside the browser's "connected" call, maybe while Solid is drawing. Overridden in 3 places (UIComponent, UIRadio, a test).
  • the decorated method: runs a moment later, from an effect, once isConnected has turned true; never before the component has mounted. Its returned function runs on disconnect.
  • The trap: @E.onConnected onConnect() on an override would run it TWICE per connect, at two moments, and TypeScript can't see it. The guard: the decorator throws on a method named onConnect (one line).
  • Also near: onConnectedChanged() in UINag and UIToast, which are @E.onChange("isConnected", "isReady") methods. Fine: those names describe what changed, which is what an @E.onChange method is named for.
  • What it loses: "while" said the cleanup runs on disconnect. The docstring says it instead, as @E.onChange's says its cleanup runs before the next call.
  • No parentheses: it takes no arguments, like @E.state.
/** SIDE EFFECT:  `/` and Cmd / Ctrl+K, while connected;  the cleanup stops listening. */
@E.whileConnected
protected listenForShortcuts() {
  UIDocsSearch.listen(this)
  return () => UIDocsSearch.unlisten(this)
}
 
/** SIDE EFFECT:  `/` and Cmd / Ctrl+K, while connected;  the cleanup stops listening. */
@E.onConnected
protected listenForShortcuts() {
  UIDocsSearch.listen(this)
  return () => UIDocsSearch.unlisten(this)
