A third build, packages/app/vite.solid.config.ts, runs FIRST in yarn build:element (and in yarn build:runner, --outDir dist-runner): its one entry is a virtual module re-exporting solid-js, @solidjs/web and @spell-app/solid-element WHOLE as spell-solid.js, plus loadSpellUI = () => import($/ui), which makes ui's barrel a lazy chunk, spell-ui.js, whose own lazy chunks go in ui/. The element, editor and runner builds add sharedSolid() (vite.shared.ts): an enforce-pre resolveId that makes solid-js, @solidjs/web, @spell-app/solid-element and $/ui externals, written as ./spell-solid.js / ./spell-ui.js by output.paths; any other Solid / ui specifier is a build error. Why not one build with three entries: cssCodeSplit false would put Monaco's CSS in spell-app.css (CODE-DEBT). Why ONE entry, not spell-ui as a second: with two entries rolldown split Solid into a shared ui/customElement.js chunk; as a dynamic import of spell-solid.js everything ui needs from Solid is exported by spell-solid.js (allow-extension). base ./ so Vite's module preloading of ui's chunks doesn't 404 at the page's /. spell-runtime.js never loads either file. The runner uses the same layout (one pin, one webview CSP). Bonus: an import-map variant of the elements is the same configs without output.paths.
