Chose to port commonmark.js 0.29's inline parser, rather than write inlines as rulex rules. That goes against D15 ("as much in rulex as possible"): what decides an inline is which character wins, not a grammar.

  • Emphasis pairs runs of delimiters after the fact (left and right flanking, the rule of 3). That was always planned as hand-written.
  • A code span ends at a run of backticks of the SAME length: rulex can't say "as long as the opening".
  • Link text must have balanced brackets; it may hold emphasis, but not a link. References resolve by their normalized label: a bracket stack, not a rule.
  • Where constructs overlap, which one wins is the order of scanning: code spans and autolinks bind tighter than links, links tighter than emphasis.

Rulex does carry the BLOCK phase's kinds of line (P3, 8 rules). The result: the GitHub spec passes 670 of 670.

    • inlines as rulex rules around a hand-written core: more code, the same behaviour
    • a rulex extension for "the same length as" and balanced brackets: a big parser change (D28)
