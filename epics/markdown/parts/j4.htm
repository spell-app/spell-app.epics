Chose to port commonmark.js 0.29's inline parser over writing inlines as rulex rules, against D15 ("as much in rulex as possible"), because what decides an inline is character-level precedence, not a grammar:

  • emphasis pairs delimiter RUNS after the fact (left / right flanking, the rule of 3): not a grammar (planned hand-written all along)
  • a code span ends at a backtick run of the SAME length: rulex can't say "as long as the opening"
  • link text must have balanced brackets, may hold emphasis, can't hold a link; references resolve by normalized label: a bracket stack, not a rule
  • which construct wins where they overlap (code spans and autolinks bind tighter than links, links tighter than emphasis) is order-of-scanning

Rulex does carry the BLOCK phase's line kinds (P3, 8 rules). Result: the GFM spec passes 670/670.

  • Options: this; inlines as rulex rules wrapping a hand-written core (more code, same behaviour); or a rulex extension for "same length as" and bracket balancing (a big parser change, D28).
