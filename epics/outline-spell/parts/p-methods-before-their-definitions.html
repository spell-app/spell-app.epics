A method can't be called above where it's defined. So Solitaire.spell re-opens a solitaire: after to play a card: the solitaire's moves and to play a card call each other.

A pre-pass reads every method's first line before the file parses, as the type pre-pass does, so a method can be called above where it's defined, in any file of the project. The biggest of the six new phases; its risk is the parser's speed.

Owen, 2026-10-19: "to play a card and card-click should be after the game is defined, before the stock pile etc". Asked how, he picked "call before defining": a pre-pass.

  • A method can be called above where it's defined:
    • further down the same file
    • in another file of the project, whatever the files' order
  • A pre-pass reads every method's first line before the file parses:
    • the way the type pre-pass (SpellParser.TYPE_DECLARATION) finds a type declared further down
    • to ..., animation ..., and a type body's - to ... lines
    • a method it finds is known to the parser as a defined one is: the same words, the same receiver
  • A call to a method defined nowhere still says "Don't understand".
  • The editor the same: hover and completions on a call above its method.
  • The parser no slower to speak of: by Owen's standing rule, the parser speed test runs on the branch and on HEAD, both numbers reported.
  • The outline guide says it: order no longer matters for methods.

  • Where to see it: the two new tests in outline.test.ts, under "methods before their definitions (P22)".
  • A line can call a method defined further down, or in a later file.

    • set x to double 21 in a file loaded before the one with to double (n as a number)
    • a call to a method defined nowhere still says "Don't understand"
  • How:
    • before a project's files parse, after the type pass, SpellParser.declaredMethods() scans each file for methods' first lines:
      • to ... and animation ... at a file's top
      • - to ... in a type's outline body, parsed in that type's subject scope, so P20's body methods work too
    • each first line, parsed alone, registers its call rule early, MethodDefinition.callAhead(), marked ahead
      • it steps aside once the real definition has run (DynamicMethodRule.test())
      • registered straight on the parser, journaled, NOT in the scope's rules: a project's declarations never export one
    • the generic hooks are on the parser package's Parser: declaredMethods(), stubDeclaredMethods(), changesMethods()
  • Editing (P.IncrementalProject):
    • an edit that adds or deletes a method re-parses the whole project, as a type change does
    • in the editor's keep-last-good mode, a method whose first line is being edited keeps its early call until the next full parse
      • so a half-typed first line doesn't re-parse everything, and later lines keep working
    • two fixes found on the way, by the incremental tests and the language server's tests: deleting a method must re-parse, else its calls kept parsing, and so in keep-last-good mode too
