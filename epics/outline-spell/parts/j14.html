A line that leaves out it / its is read by a new rule that stands in for the missing word and takes no words of the line. It was option A of the implicit-subject todo (C16), built on a small addition to the generic parser.

  • The new rule, subject_implied, is a third subject beside it and its.
    • it matches only directly in a type's outline body, and answers "the type this body is about"
    • each member rule that names {type:subject_it} or {type:subject_its} got a twin with {type:subject_implied}
  • The generic parser learned what a rule that takes no words is.
    • a rule says so with Rule.zeroWidth
    • the parser's quick pre-check of a line (Sequence.test()) used to assume every sub-rule eats at least one word; now it stays in place for such a rule, if the rule says it could match here at all
    • it knows those rules by name, from a set addRule() fills (Subrule.zeroWidthRules): looking the rule up for every sub-rule was too slow (below)
  • Why not option B, re-reading a failed line with an invisible its put in front:
    • every "Don't understand" line in a body would be parsed twice
    • the error for a line that fails both ways would have to pick which reading to report
    • the hover's "Reads as" and the highlighter would see words that aren't in the file
  • The cost: the parser is about 5% slower on its rule tests (the parser-speed caveat, C5). The first version, looking the rule up per sub-rule, cost 12%.
  • A rough edge: the set is by rule NAME, and shared by every parser.
    • so a rule called subject_implied in another parser, one that does take words, would be pre-checked wrongly; none exists
  • the generic parser has a new rule property, zeroWidth, and the quick test honours it
  • spell has a third subject rule; 17 new syntaxes use it
  • no line is parsed twice; "Reads as" puts the subject back from the match itself
