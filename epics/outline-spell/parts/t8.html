In a class definition, I'd like `- "suit" is a suit of its deck` to work without the it/its. What's the impact on parseability?

Also, it looks like the "where" is optional in `a "card" is a thing where:` correct?

Two answers. Dropping it / its doesn't work today, but it can, inside a type's outline body only, at a small cost in speed and one real risk to readers. And yes, where is optional: the colon is what opens the body.

  • I ran each line below through the real parser on main (a throwaway test, deleted after), with a deck that keeps the suits, as in the live Solitaire.
  • This reverses part of an earlier answer: the property-shape decision (Q4) chose "always its"; what you ask for is its option B, "its optional".

What a bullet in a type's body accepts today

Every member rule has a second way of writing it, where the type is the word it or its instead of a card. Those words only count directly inside a type's outline body.

  • the words it and its are two small rules, SubjectRule; each answers "the type this body is about"
  • 12 syntaxes use them, in 8 rule files; the property ones are in DefinePropertyHas
  • a line naming no subject matches none of them, so it's "Don't understand"

"{type:subject_its} {property:quoted_member} is {specifier:outline_specifier}"
"{type:subject_its} {property:member_words} is {specifier:outline_specifier}"
// PropertyValueGetter.ts
"{type:subject_its} {property:quoted_member} is :? {expression_body}?"
"{type:subject_its} {property:member_words} is :? {expression_body}?"
// ItsQuotedProperty.ts (its "color" is red if ... otherwise ...)
"{type:subject_its} {property:quoted_member}"
"{type:subject_its} {property:member_words}"
// QuotedPropertyFormula.ts, QuotedTypeExpression.ts (phrases)
"{type:subject_it} {alias:text}"
"{type:subject_it} {signature:quoted_method_signature} (if|is)? :? {expression_body}?"

Making the subject implicit, in a body only

Each of the 12 syntaxes gets a twin with no subject. The twin matches only directly inside a type's outline body, and takes its type from the body, exactly as it does now.

  • A bullet needs a quoted name, or a verb first, to drop its subject.
    • works: - "suit" is ..., - "is face up" if ...
    • works: - has a name as text, - belongs to a pile, - is saved inline
    • NOT a bare name: - suit is one of ... already means "set the variable suit" (last row above). So a property line keeps its quotes or its its, never neither.
  • Outside a body nothing changes.
    • at the top level, "suit" is ... stays an error
    • inside a method or getter in the body, it is the card, as now; I tried "hi" is its name in a method: still an error

What it could collide with

  • A kind of value, one word away. In the deck's body, - "suits" as one of clubs, ... makes a new kind of thing, the suit, kept on the deck.
    • - "suits" is one of clubs, ... would make a property of each deck instead
    • only as versus is tells them apart: the cost Q4 gave option B
    • guard: hovering says what the line was read as (the Reads as line)
  • The getter line, value if condition. A phrase (declaration priority) beats it, so - "is face up" if ... would become the phrase you meant. The misreading above should be fixed anyway (I9).
  • Statements starting with a quoted word: the value kind is the only one. Others start with a word: if "a" is x:, to "draw its front":.
  • Nested bullets: a bullet under a bullet is still about the type, not the line above it.
    • I tried - it has a rank under - it has a name: both became card properties
    • with the subject left out, - "name" is text nested under - its "deck" is a deck looks like the deck's name; it would be the card's
  • Getter or property: - "x" is total has the same reading as its "x" is total (a getter, as now). Nothing new.

Ambiguity and speed

  • No new "two fit" guess (the guessing caveat, C2). A body is about exactly one type, so the left-out subject always has one answer.
  • The new guess is the shape of the line: is means a property, as a kind.
  • Speed (the parser-speed caveat, C5): each syntax gives up at its first word if that word can't start it.
    • the twins start with a quoted word, or with has, belongs or is
    • an ordinary line pays one cheap check per twin: about 12 more, beside some 730 rule tests
    • my guess: 1-2% slower; spell speed --against main says for sure
  • The hover's Reads as line finds the it / its word in the line to spell it out. With no such word, it has to insert one: - "suit" is a suit reads as the "suit" of a card is a suit.

The "its" in "of its deck" stays

  • It isn't the line's subject: it says WHOSE deck, the card's.
    • a suit of deck isn't English, and is "Don't understand" today
    • a suit of the deck could be taught too; it's a one-line syntax
  • Those words are only for the reader.
    • the kind, a suit, already says the deck keeps the list
    • - its "suit" is a suit compiles the same
    • so does a suit of its banana: never checked, which I've logged (I10)

Is "where" optional? Yes

The heading's last word is one small rule, with_nested_statements, and the word in it is optional. The colon is required. Where and with mean the same (the openers decision, Q7). 

syntax: "(where|with)? :"
The heading, then - it has a name as text Today
a "card" is a thing where: works
a "card" is a thing with: works
a "card" is a thing: works
a card is a thing: (no quotes) works; the quotes on the type's name are optional too
a "deck" is a list of cards: works
a card is a thing where (no colon) "Don't understand where", and each bullet errors
a card is a thing (nothing) the type is declared; each bullet says "it" and "its" mean a type only in its outline, indented under e.g. "a card is a thing where:"
  • That last message is a little off: the bullet IS indented under the type. It could say "end the line above with a colon". A few lines in BlockLine, if you want it.

The ways to go

  • every bullet in the table above works without it / its, except a bare name
  • each of the 12 subject syntaxes gets a twin without one; the rules take their type from the body
  • the hover's long form learns to put the subject back
  • it / its keep working: both styles, the same output
  • cost: about a day; some 150 lines in 8 rule files, about 15 tests
  • also changes: the parsing map, the outline guide, the syntax table, the highlighter bundle
  • cost: the "suits" as / "suits" is pair, one word apart
  • why recommended: it's what you asked for; the quotes keep it from colliding with ordinary statements
a "card" is a thing:
	- belongs to a deck
	- "suit" is a suit of its deck
	- "is a (suit)"
	- "is face up" if its direction is up
  • a bullet in a body that didn't parse is read again, with an invisible its before it
  • gain: one file, about 40 lines; no new syntaxes, so no speed cost
  • cost: a line that parses WRONG today is never retried: - "is face up" if ... stays the misreading
  • cost: the invisible word isn't in the text, so hover, colouring and error positions need special cases
  • a bullet with a quoted name and no its says what to write
  • e.g. a property starts with its: its "suit" is ...
  • cost: small, about 20 lines, like the hint a line outside its body gets now
  • cost: one more word on most lines

Whichever you pick, the misreading (I9) should be fixed first. Nothing is changed yet.

  • its stays required before an unquoted name: - its rank is a number
  • the its in of its deck stays
  • the property-shape decision (Q4) changes from "always its" to "its optional"
  • the parser gets about 1-2% slower, to be measured
