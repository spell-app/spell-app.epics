Curly quotes: what has to change so they all work

Spell reads only the straight double quote as a quote. That was chosen on purpose, so that an apostrophe in isn't is never the start of a string. 

new P.Tokenizer({
  // Only support double-quotes as quote symbols (so we can do contractions with single quotes)
  // TODO: backtick as alternative quote, for embedding double quotes?
  quoteSymbols: [`"`],
  ...
  • Reading them: the tokenizer's matchText() closes a string only with the SAME mark that opened it. It needs pairs instead:
    • " opens, and only " closes: a curly mark inside straight quotes stays text, as now
    • “ opens, and ”, “ or " closes, whichever comes first
    • that covers the sketch's slip, source=“images/...png“, and the mixed “suit"
    • cost: straight quotes inside curly ones, “say "hi" now”, end the text early: an error on that line
  • The text inside: three places strip the quotes assuming they're straight, and each would go wrong with curly ones:
    • TextToken.innerText strips only " and ', so “hello” would keep its curly marks as part of the text
    • the javascript writer writes the text as the SOURCE spelled it (ASTStringLiteral()), so “hello” would land in the compiled file as is, and javascript can't read it
    • a quoted phrase's name is read with JSON.parse (QuotedMethodSignature, where T1's "methods.ts" now lives), which throws on a curly quote, with nothing to catch it
    • one fix covers all three: the token keeps a straight-quoted copy of itself, and everything after the tokenizer reads that
  • Compiled output: always straight quotes, since the target languages need them; the words inside exactly as typed.
  • The formatter: curls only the two marks around a string, never what's inside it.
    • inside, a ' or " is part of what the program prints or compares: if the answer is "don't" must keep matching what someone types into a form
    • it's whitespace-only today, and gives up if its result reads differently from the original; that check has to count curly and straight quotes as the same
    • markup (<ui-image source="...">), css and markdown blocks keep their quotes as written 
// Tokens.ts:  TextToken
get innerText() {
  const string = this.value
  let start = 0
  let end = string.length
  if (string[start] === '"' || string[start] === "'") start = 1
  if (string[end - 1] === '"' || string[end - 1] === "'") end = -1
  return string.slice(start, end)
}

// JSWriter.ts:  the source's own spelling, `raw`, wins
ASTStringLiteral(node: P.ASTStringLiteral): string {
  if (!node.quote) return node.value
  return doubleQuoted(node.raw ?? jsText.inQuotes(node.value, node.quote))
}

Apostrophes: why single curly quotes should not be quotes

The curly apostrophe and the closing single quote are the SAME character, ’. Phones and pasted text put it in every contraction.

  • today isn't, can't, won't and doesn't have work because ' is never a quote; isn’t is an error
  • Q3's net effect says the tokenizer takes ‘ ’ as quotes too: then it isn’t red could open a string at ’ and run on
  • so: ’ between two letters is an apostrophe, read exactly like '; and ‘ ’ are never quotes, just as ' ' aren't today
  • isn’t means isn't; it’s inside text stays as typed
  • matches today's rule: single quotes aren't quotes
  • cost: a narrow change to Q3's net effect, which listed ‘ ’
  • a phrase could be written ‘is face up’
  • cost: every curly contraction (isn’t, don’t) needs special handling to not be read as a quote

Capitals: what is case-sensitive today

  • Keywords: exact. A, If, To, Its, The and Print starting a line are all errors, on their line.
  • Type names: the first letter is ignored. a card, a Card and cards are all Card, but a CARD silently names a class nobody declared.
  • Values: any case. Clubs finds clubs.
  • Properties and variables: exact, and reading an undeclared one isn't an error, so its Rank and the City silently read names that don't exist (issue I12).
  • Text: as typed, always: "Paris" stays Paris, a capital mid-sentence inside quotes means nothing to spell.
  • The parser can already match a keyword in any case (rulex's /i, the caseInsensitive flag on a literal); spell's grammar doesn't use it anywhere yet.
  • A card is a thing works
  • If its rank is 1, To start: stay errors
  • the first word of a line may start with a capital, as an English sentence does: If, To, Its, The, A
  • only keywords: a NAME starting a line keeps its case, so this adds no new silent meaning
  • cost: about the same as A, the same mechanism on every keyword rather than two
  • IF its rank IS 1 works
  • cost: more to test, and nobody types it; names would still be exact

The dash

  • -: a bullet starting a line, minus inside one. T1 doesn't touch it.
  • -- outside quotes: a comment to the end of the line, today, anywhere on it. The formatter would turn it into —.
  • — outside quotes: an error today; after T1 the same as --.
    • a line that starts and ends with it is a heading: — Definition of a card —
    • starting a line, or after code, it's a comment: — suit and rank
    • the risk: an em dash pasted into a line of code, as in prose, turns the rest of the line into a comment, with no error. That's the cost -- already has; the highlighter colouring it as a comment is the only guard.
  • Inside quotes, any dash is text: the nine return "—" lines in the card projects stay as they are.

Existing code: nothing changes meaning

  • Searched all 47 spell files in the repo, examples and test projects: no curly quote, curly apostrophe, or em dash outside quotes.
  • The only em dashes are inside text (return "—").
  • The only lines starting with a capital are inside markdown blocks and markup, which spell never reads as code.
  • So no snapshot should move from the tokenizer change; the formatter never runs on the test projects.
  • The one possible change: a line ending in -- after a -- comment would become a heading, if -- x -- counts as one (Q5 says -- may mark headings too). No file has one.

The editor

  • Colours for strings follow on their own: the highlighter uses the parser's tokenizer. Headings don't: three places decide "heading" by a leading #, the highlighter, the language server's heading spans, and a file's top docstring.
  • The TextMate grammar (the colours shown before the language server answers) needs “ ” strings and — comments.
    • it also treats ' as a quote today, which the parser doesn't: an isn't may colour everything up to the next apostrophe as a string, until the language server repaints it. Worth a look in T1.
  • VS Code's auto-closing pairs could add “ ”, for people who type them on purpose.
