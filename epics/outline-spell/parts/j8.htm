P2 · Value Types set out to keep two kinds that list the same value from colliding, and I dropped that goal. Values are plain text when the code runs (your answer to Q10, "values stay text"), so red in two kinds is the same text, and both compile to 'red'. Checking it properly turned up one real collision, though: it isn't in the values, it's in the phrases built from them. if the game is red calls the CARD's method, and the program fails when it runs.

  • "Value kind": a list of values that is a kind of thing of its own, declared in a type's outline body, e.g. - "colors" as one of red, black in a card's body makes the kind color.
  • "Known value": a word spell has already seen in a value list above the line it's reading. Inside the parser this is a "constant", a ScopeConstant.
  • "Scoped to its kind": red would mean "a color" in a card's code and "a team" in a game's code, and a word one kind doesn't list would be an error there.
  • Every spell line below was run through the parser on this branch (2026-10-06), with P2's uncommitted changes, in a throwaway test since deleted.

What P2 decided, and why

  • Values are plain text when the code runs (Q10), so red in two kinds is the same text: both compile to 'red', and nothing in the compiled VALUES collides.
  • What would change that: values that are objects (Q10's other option).
  • That still holds. What the check below adds: the values don't collide, but a few things that READ values do.

How values are stored today

  • One list for the whole project, scope.constants. Every value list adds its words to it:
    • a value kind, - "colors" as one of red, black (value_kind.mutateScope() in classes.ts)
    • a sentence-style list, a card has a color as one of red, black (define_property_has.mutateScope(), the same line as on main)
    • a getter's bare answer, its "color" is red if ... (property_value_either)
  • Two kinds listing red add TWO records named red, each remembering which line declared it. A lookup by name, scope.constants.get("red"), always returns the FIRST one (ScopeList.get() in ScopeList.ts).
  • The data a scoped version would need is already there per kind: the kind's P.TypeScope has valueKind.values, and its owner has the list, e.g. Card.Colors. Nothing reads them to decide what a word means yet.

Where sharing a value does NOT matter

  • Two kinds, each comparing its own value: a card's - it "is hot" if its color is red and a game's - it "is home" if its team is red.
    • Compile to return (this.color == 'red') and return (this.team == 'red'): right.
  • Two kinds, each with a property of the same name: the "warmth" of a color is: and the "warmth" of a team is:, both with - 1 if it is red-style lines.
    • Compile to Color.warmth(color) and Team.warmth(team), and a game's its "heat" is the warmth of its team to return Team.warmth(this.team): the kind's class keeps them apart already.
  • A sentence-style list and a value kind sharing hearts: Card.Suits = ['clubs', 'hearts'] and Deck.Marks = ['hearts', 'stars']. Each property's check uses its own list.
  • Top-level code: if the color of the card is red compiles to if (card.color == 'red').

Where it DOES matter (found 2026-10-06)

  1. A phrase on one kind answers for another kind, and the program fails when it runs: if the game is red calls the card's method.
    • "Phrase": a quoted sentence with a (placeholder) filled from a value list, e.g. - it "is (color)" for its colors, which lets you write if the card is red.
    • Each phrase becomes a rule that matches is plus one of ITS values, here is (red|black). That rule never checks whose phrase it is. With a card's "is (color)" and a game's "is (team)", is red fits both, and the card's, declared first, wins.
    • The same happens with no shared value at all: with only the card's phrase, if the game is black compiles to game.is_$color('black'). Sharing a value makes it hit CORRECT code too.
    • On main too, in the sentence style: a card "is (color)" for its colors.

  2. Whether a line parses depends on ANOTHER kind declared above it.
    • A card's - it "is odd" if its color is red or blue, where blue is only a team:
      • game declared BELOW the card, or no game: error, "Don't understand or blue" (line 4, column 35)
      • game declared ABOVE the card: no error, return spellCore.includes(['red', 'blue'], this.color)
    • A card's - it "is blue" if its color is blue: an error with the game below, but return (this.color == 'blue') with the game above. That's a test that can never be true, compiled without a word.
    • Why: is red or blue reads as "one of" only when every word is a known value (value_choices in lists.ts), known from ANY kind, and only from lines above. Moving the game up or down changes the card's meaning.
  3. Another kind's value can be assigned: set the color of the card to blue compiles to card.color = 'blue'. The property's setter warns when it runs (blue isn't in Card.Colors), so it's caught, but only then. purple, listed nowhere, is a parse error.

    • "Go to definition" and "Find references" on red in the game's code go to the CARD's "colors" line, since every use resolves to the first red record
    • the Type Explorer is right: each kind lists its own red

Found while checking, not about kinds

Both happen on main too, with a sentence-style list. Scoping values to kinds wouldn't fix either.

  1. A value can't be used as a variable's name afterwards, and the output is broken JavaScript. a card has a color as one of red, black, then set red to 5, compiles to 'red' = 5: the browser refuses to load it ("Invalid left-hand side in assignment").
  2. The other way round, a variable named like a value is read as the variable: set red to 5 ABOVE - "colors" as one of red, black compiles to Card.Colors = [red, 'black'], i.e. [5, 'black'], and its color is red to this.color == red.

What scoping values to their kind would take

  • Where values would live: on their kind, which already has them (valueKind.values); the project list kept only for words nobody owns (a getter's red with no list).
  • The hard part: spell reads red before it knows what kind is wanted. Every place that reads a value would need "the kind expected here", passed in while parsing:
    • a comparison, its color is red: from the left side. Today an operator after a value (is red) is parsed WITHOUT seeing the left side (compound_expression.parse() in expressions.ts), so this is new plumbing
    • is red or blue (value_choices) and is one of ... (is_in)
    • an assignment, set the color of the card to red: from the property
    • a getter's answer, its "color" is red if ...: from the property, when it has a kind
    • a phrase's placeholder: from its own list (it already matches only those words)
  • Sentence-style lists (a card has a color as one of ...) have no kind, only a property: their values would be scoped to the property, a second case.
  • A word with no expected kind, set x to red at the top level: still the project list, or an error asking which red.
  • The editor: completion and "go to definition" by expected kind.
  • Size: a phase of its own. constants.ts, lists.ts, expressions.ts, assignment.ts, classes.ts, ScopeConstant, the language server, their tests, the snapshots, and the ui highlighter bundle rebuilt. What it buys is compile-time errors; what the code does when it runs doesn't change, since values stay text.

The ways to go

A · Keep as is
  • values stay one project-wide list of text; nothing changes
  • gain: no work; the compiled values are right
  • cost: if the game is red still fails when it runs; a line's meaning still depends on other kinds above it
  • not recommended: the evidence shows a real collision
// if the game is red
game.is_$color('red') // TypeError
 B · Scope values to their kind
  • red means a color in a card's code, a team in a game's
  • gain: its color is blue is "blue isn't a color", wherever the game is
  • gain: completion and "go to definition" by kind
  • cost: a phase of its own (see above): the expected kind threaded through every place that reads a value; sentence-style lists scoped to their property
  • runtime unchanged: values stay text (Q10)
