Each left-out word is a guess. A wrong guess is a program that reads right and does something else.

  • guard: infer only when exactly ONE answer fits; two fit: an error naming both
  • guard: hover shows the long form the line was read as (P6)

in the case when 2 fit, can VSC/Monaco show as an error with both possibilities and allow them to pick?

Yes, and most of what it takes is built: what's missing is in spell itself.

  • both editors can already list several quick fixes under one error, and let you pick one
  • spell never notices that two fit: the guard this caveat promises ("two fit: an error naming both") was never built
  • today the phrase declared first wins, silently

Where "two fit" happens today

  • Not where a phrase is declared any more.
    • since the parens became required (J9, option A), a blank names its property by name
    • it "is a (suit)" reads the property suit, or it's an error: one answer or none
  • It happens where a phrase is USED, when two of a thing's phrases match the same words.
    • e.g. a card with a color (red or black) and a team (red or blue), and a phrase for each
    • the card is red fits both: its color is red, or its team is red
  • I tried it on a scratch project: spell check says no errors, and the compiled line calls whichever phrase was declared first. 
    a card is a thing where:
	- its "color" is red or black
	- its "team" is red or blue
	- it "is (color)"
	- it "is (team)"
the card is a new card with color = red, team = blue
set x to the card is red

-- compiles to:
export const x = card.isColor("red")

-- the same lines in the sentence style, team declared first:
export const x = card.isTeam("red")
  • Why: two rules matching the same words, with the same priority, are settled by the parser's tie-break, and the earliest rule wins (Choice.getBestMatch()). Nothing records that there was a tie.
  • Found on the way, and logged as I8: the obvious long form crashes.
    • the team of the card is red compiles to card.team.isColor("red")
    • it runs as TypeError: card.team.isColor is not a function, with no error in the editor
    • it matters here: that long form is exactly what a "pick one" fix would write

How an error reaches VS Code and Monaco

  • One language service feeds both editors: SpellLanguageService.
    • its diagnostics() turns spell's parse errors and warnings into red and yellow squiggles
    • VS Code gets them through the language server, over the standard protocol
    • the app's Monaco editor calls the same service directly, in the page
  • Quick fixes exist already, in both editors.
    • the service's codeActions() offers one today: "Define to <phrase>" on a line that didn't parse
    • the language server announces quick fixes to VS Code (SpellLanguageServer)
    • Monaco registers a quick-fix provider that asks the same service (SpellLanguageFeatures), and turns its edits into Monaco's (LspToMonaco.codeAction())
  • So "pick one" is just two quick fixes on one error.
    • both editors show a lightbulb on the line; Cmd+. opens the list
    • e.g. "Read as its color: the color of the card is red" and "Read as its team: the team of the card is red"
    • neither marked as the preferred one, so "fix all" never picks for you
    • the VS Code extension and Monaco need no new code for it

What it would take

  1. Fix the crash first (I8): a card's phrase must not match a value of one of its properties. Otherwise the fix writes a line that crashes.
  2. spell notices the tie. When the parser's tie-break picks between user phrases, it keeps the others on the winning match (only in the tie, which is rare, so the parser's speed shouldn't move).
  3. spell says it, with the choices. The phrase's use becomes an error naming both: "red" could be the card's color or its team.
    • the error carries one fix per meaning: the words to put in its place
    • today an error is only a message: it gains an optional list of fixes
    • where: QuotedPropertyRule, the rule that matches a phrase where it's used
  4. The language service offers them: codeActions() adds one quick fix per listed fix, next to "Define to ...", in about 30 lines.
  5. Tests: the outline tests (the error and its fixes), and the language service's quick-fix test.
for (const error of SP.Block.getParseErrors(file.match) ?? []) {
  for (const fix of SP.ParseFixes.of(error)) {
    const range = this.rangeOf(file, fix.replace)
    if (!range) continue
    actions.push({
      title: fix.title,
      kind: CodeActionKind.QuickFix,
      diagnostics: [this.diagnosticFor(file, error)],
      edit: {
        changes: { [this.addresses.uriFor(file)]: [{ range, newText: fix.text }] }
      }
    })
  }
}
  • Rough size: one small phase, about 150 lines with tests, plus I8's fix (likely small: an "is red or blue" property's value should count as text, not as "could be anything").
  • VS Code picks it up once merged into main and the extension is rebuilt (spell dev vscode).

Error, or warning?

  • the line doesn't compile until you pick
  • gain: what this caveat promised, "never a guess"; a wrong guess runs and does something else
  • cost: adding a second phrase can turn working lines red, e.g. adding a team to a card that had only colors
  • the line compiles as today (the first-declared phrase), with a yellow squiggle and the two fixes
  • gain: nothing that worked stops working
  • cost: the guess stays; a warning is easy to miss
  • it "is (team)" could warn at once: "red is both a color and a team, so the card is red won't say which"
  • it catches the clash before any line uses it, but can't offer a pick: the choice belongs to each use
  • cheap to add alongside either option
