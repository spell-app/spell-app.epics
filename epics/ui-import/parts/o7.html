What it would take to write a markdown parser on spell's own parser, beside the spell language. Worth it only if spell's tools need markdown inside them: a todo (T5), not a phase.

  • Where it would live: a package of its own, packages/markdown/.
    • named @spell-app/markdown
    • imported as $/markdown, its namespace MD
    • it imports only the parser and the util package
    • app, docs and spell may import it
  • What the parser already does well for it:
    • source positions on every match, so an editor can map back to the text
    • parsing a part again (a block pass, then inline)
    • unit tests per rule
    • Match.compile() returning HTML strings, the way rulex returns Rules
  • What would need hand-written parse() code:
    • A tokenizer of its own, which keeps whitespace: the default one breaks markdown.
      • // and -- start comments
      • <Tag is read as JSX
      • _ is a word character
      • ' strings run across lines
    • Container blocks (lists, quotes, lazy continuation, tab stops of 4): CommonMark's line scan.
      • not breakIntoIndentedBlocks, which makes one level per whitespace character
    • Emphasis: a pass over a stack of delimiter runs.
    • Link reference definitions: two passes.
    • HTML blocks: 7 ways to start one.
    • Tables: the delimiter row decides.
    • Around the parser's limits:
      • it has no lookahead or negation
      • Choice parses every alternative
      • IncrementalParse assumes indentation
  • Effort:
    • a useful subset of GitHub markdown: about 1.5-2 weeks
    • all of CommonMark and GitHub's extensions (about 650 spec examples): 4-8 weeks
    • incremental parsing: 1-2 weeks more
  • Speed: marked takes about 1 ms a doc; spell's parser about 77 ms on 259 lines.
  • Verdict:
    • worth it if markdown must live inside spell's tooling: the language server, completion, one AST, editing that knows spell
    • for rendering alone, marked is about 70 times faster
