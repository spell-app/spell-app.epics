What an epic’s helpers are doing shows only in the chat, and steering one means typing into a busy session.An "Agents" section on every plan doc, live from agents.json, each running agent with a box to redirect it. A page-server route takes the redirect, and the session passes it on to the agent.
  • the pattern: the review inbox (reviewRoutes.ts, inbox.js, spell-doc-runtime.js)
  • the page:
    • spell-doc-runtime.js draws an "Agents" section at the top of every plan doc while its list is not empty: no markup in the doc, so no migrate
    • each agent: name, task, status, age
    • each agent also gets a growing textarea and a Send button
  • the route, agentRoutes.ts (a RouteModule, listed in the root package.json’s pageServer.routes):
    • GET /api/agents?page=: the list; the page polls it
    • POST /api/agents/redirect { page, name, note }: token and origin guarded, a locked write; the note lands in the entry’s redirects
  • the session hears it:
    • spell dev agents wait (in the background, as plan-doc inbox wait is) exits when a redirect arrives
    • the session sends it to the agent (SendMessage, "Owen redirects: <note>"), marks it told (spell dev agents told), and waits again
    • armed while the session has listed agents running: the /bg skill and the standing rule say so
    • whether a message reaches a RUNNING agent mid-task is not checked yet (C4)
  • the page shows a sent redirect as "told" once the session has passed it on
