The fallbacks' attribute reader, NativeFallback.attr(), still answers null for an absent attribute, while the rest of ui answers undefined. Nobody using a page would notice: it only shows when you read or write a fallback's code. The question is whether that one method should follow the epic's "undefined, not null" rule too.

  • Native fallback: the plain-DOM copy of a component (no Solid) that an element shows when its real render throws. Each family has one, ui-<name>.fallback.ts, built on the base class src/elements/NativeFallback.ts.
  • Platform boundary: a place where our code touches a browser API that itself speaks null. ui's AGENTS.md ("Functions & types") allows null only there: getAttribute(), setFormValue(), the fork's toAttribute, useContext's default. Everything of ours is undefined. That is the rule decided in Q9.
  • attr(name) is host.getAttribute(name), only typed to the family vocabulary's attribute names. So J5 counted it as part of the platform boundary and left it at null.
  • The rest of NativeFallback did go to undefined: form(), and the private defaultText(). 
/**
 * Host attribute `name`, or `null`.
 * - `null`, not `undefined`:  it IS `getAttribute()`, a platform boundary.  Subclasses test `=== null` for
 *   "absent", and TypeScript wouldn't flag one of those left behind by a switch to `undefined`.
 */
protected attr(name: E.AttributeNameOf<V>): string | null {
  return this.host.getAttribute(name)
}

The closest thing elsewhere is HostAttribute.get(), which reads a host attribute that isn't in the vocabulary. In Q17 Owen answered that it returns undefined, so it turns getAttribute()'s null into undefined the moment it reads it. 

/**
 * Current value, `undefined` when absent;  tracked.
 * - `getAttribute()`'s `null` stops here:  `null` only at platform boundaries (epic `wwod-spell-ui`, Q9, Q17).
 */
readonly get: Accessor<string | undefined>
// constructor:  const read = () => host.getAttribute(name) ?? undefined

So the two readers of the same thing, a host attribute, disagree:

  • HostAttribute.get() answers undefined.
  • NativeFallback.attr() answers null.

Why switching is not a find-and-replace:

  • TypeScript allows x === null on a string | undefined without a word. It was tried during P3: attr() switched alone, and yarn tsc reported nothing.
  • Each of the 24 null tests left behind would then be silently always false (or always true for !== null). For example, every <ui-button> fallback would become a link, and every <ui-nag> fallback would lose its default close button.
  • The fallback tests would catch some of them, but not all: a fallback test checks a family's main cases, not every absent-versus-empty pair.
  • Two sites turn the value into a number with no fallback (<ui-toast display-time>, <ui-rating value>). Number(null) is 0 but Number(undefined) is NaN. Both happen to come out the same (no timer, no star chosen), but each needs a look.
  • A few signatures accept null only because of attr(), and would drop it: slot(fallback?: string | null), <ui-section>'s named(), <ui-modal>'s dialogAttr(), and <ui-item>, which writes its own null for a disabled link's href.
  • attr() stays getAttribute(), a platform boundary; its docstring says why
  • no code changes; no risk of a silently flipped test
  • the 16 ?? undefined stay, and so does the mismatch with HostAttribute.get() (Q17)
  • each new fallback author has to remember: attr() is null, everything else is undefined

Why A was chosen, honestly:

  • The real reason was risk during a style pass: a switch that the compiler can't check, in 24 places, mid-epic, for no change anyone would see.
  • The "platform boundary" argument is weak against Q9 and Q17. HostAttribute.get() wraps the very same getAttribute(), and Q17 decided it returns undefined. By that answer, attr() is a wrapper of ours, not the boundary itself, and should return undefined too.
  • So the honest framing is: A is a deferral, not a different reading of the rule. B is what Q9 and Q17 point to; it costs one careful pass over 24 lines, not a codemod.
  • It also still means two rules for one job: a fallback author reading a host attribute must remember that attr() is the exception.
  • attr() stays string | null, and its docstring says why it's null
  • the 16 callers that write this.attr(x) ?? undefined keep it; P5-P7 could have revisited this per family, auditing each === null by hand
  • ui's null rule (Q9) has one unlisted exception, NativeFallback.attr(), that disagrees with HostAttribute.get() (Q17)
  • choosing B later: one hand pass over the 24 null tests in 16 files, the 16 ?? undefined deleted, 4 signatures narrowed, then the fallback tests; no measurable bundle change
