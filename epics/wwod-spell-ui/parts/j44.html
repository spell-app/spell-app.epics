Where a family constant met a UIT one or another family's copy:

  • DEFAULT_VALUE = "on" was declared in both ui-checkbox.types and ui-form.types, and written twice more in the checkbox fallback: now ONE UIT.CHECKBOX_DEFAULT_VALUE (// ## Checkbox group of components.types.ts)
  • accordion's GROUP = "panels" shared a NAME with UIT.GROUP = "group" but not its value: renamed DETAILS_GROUP (the <details name> of an exclusive accordion), never swapped
  • accordion's TITLE = "title" was UIT.TITLE exactly: deleted; ARROW_UP / HOME / END => UIT.Key.*, radio's arrow-key sets too
  • a word only one class used moved below that class (Q18): accordion's types file went from 22 constants to 6, form's from 19 to 2 (+ StateFlags, one helper for three classes' error / info / success / warning host states), checkbox's from 13 to 4
  • form's on values are a set now, ValidationTriggers + ValidationTrigger, read by the vocabulary
  • no value changed; ui-checkbox.types.ts no longer VALUE-imports ui-radio.vocabulary.en (it only needed the type)

Short answer: these are two separate questions. A @proto static default would let a whole CLASS of checkboxes submit something other than on. It would NOT give you a checkbox that toggles between two values. That needs a second value, for the unchosen state. I recommend a new off-value attribute, and keeping "on" as the shared UIT constant.

What happens today

  • A chosen <ui-checkbox name="panel"> submits panel=on. With value="open", it submits panel=open.
  • An unchosen one submits nothing at all, as a native checkbox does. The server never hears "closed".
  • Three places read the "on" default, in three different classes:
    • the element's controller, CheckControl.choiceValue(), which submits through the host's ElementInternals
    • the plain-DOM fallback, CheckboxFallback.value(), used when the element's controller didn't load
    • the form, FormFields.chosenValueFor(), which reads the host's value ATTRIBUTE, and native <input>s too
  • ui-change's detail is { selected, value, originalEvent }. value is always the element's value, so unchoosing still says "on".
  • form.values reads a lone checkbox as value (or true with no value) when chosen, and false when not. 
// CheckControl.tsx

  return this.common.value ?? UIT.CHECKBOX_DEFAULT_VALUE
}
formValue(): E.FieldValue {

1. A checkbox with two values: how others name it

Nobody in the native / Fomantic / web-component world has it. It lives in the Vue world and in server-side form helpers:

Library Chosen Unchosen Submits when unchosen
native <input type="checkbox"> value (default on) none nothing
Fomantic (our reference) value none nothing; its get values reads false
Shoelace / Web Awesome, Material Web, Ionic value (default on) none nothing
Vue (v-model on a native box), Vuetify, Quasar, Element Plus true-value false-value only the bound model gets it; a real form submit still sends nothing (Vue's docs say so)
Naive UI checked-value unchecked-value model only
Rails' check_box helper checked_value unchecked_value yes: it writes a hidden <input> of the same name before the box
  • Checked in the reference clone (spell-old/ui/reference/Fomantic-UI, src/definitions/behaviors/form.js): values[name] = isChecked ? value || true : false. Fomantic's checkbox module has no second value.
  • The rest is from each library's docs as I know them, not checked in the repo.
  • Because ElementInternals.setFormValue() lets OUR host submit anything, we can do what Vue can't: a real form submit sends panel=closed, with no hidden input.

2. Would a @proto static default help?

A @proto static puts a default on the class's prototype once (WWOD §12). An instance reads it as its own, and a SUBCLASS overrides it. An attribute is per ELEMENT. So: 

// @proto:  per CLASS
class CheckControl {
  @E.proto static defaultValue = "on"
}
class UIYesNo extends UICheckbox {
  @E.proto static defaultValue = "yes"
}
// every <ui-yes-no> submits "yes",
// no `value` on each one

// attribute:  per ELEMENT (exists today)
// <ui-checkbox value="yes">
  • It changes the CHOSEN value only. Your open / closed case needs the unchosen one, which is still nothing.
  • We have no subclass that wants a different on. Per element, value="open" already works.
  • Two of the three readers can't see it: the fallback is a separate class, and FormFields reads the host's attribute (and native inputs, whose default is the browser's). Both would need to ask the host instead.
  • "on" is HTML's own default for a checkbox's value: a platform fact, not our config. A shared constant is the right home for it.
  • If a subclass ever needs its own default, the switch is small: one @E.proto static and the two re-routed readers.

The options

  • value="open" off-value="closed"
  • chosen submits open, unchosen closed
  • no off-value: exactly today's behaviour
  • checkbox only; radios have their group
  • "on" stays UIT.CHECKBOX_DEFAULT_VALUE
  • reads like a toggle: on / off
<ui-checkbox type="toggle"
  name="panel" value="open"
  off-value="closed">Open</ui-checkbox>

chosen:    panel=open
unchosen:  panel=closed
values:    { panel: "closed" }
  • values="closed open": off first, then on
  • one attribute instead of two
  • the order is a rule to remember; nothing in markup says which is which
  • clashes with value: which wins when both are set?
  • a value with a space can't be said
<ui-checkbox name="panel"
  values="closed open">Open</ui-checkbox>

chosen:    panel=open
unchosen:  panel=closed
values:    { panel: "closed" }
  • A's attribute, and @E.proto static onValue = "on" / offValue on the class
  • a subclass sets both once for all its elements
  • the fallback and FormFields must ask the host instead of reading attributes
  • no subclass needs it yet: config nobody sets
class UIDoor extends UICheckbox {
  @E.proto static onValue = "open"
  @E.proto static offValue = "closed"
}
// <ui-door name="panel">Open</ui-door>

chosen:    panel=open
unchosen:  panel=closed
values:    { panel: "closed" }

Why A

  • It answers the real want, a second value, with the smallest new word.
  • Two attributes say which value is which. B's pair needs a rule about order.
  • off-value over the other names:
    • false-value would want a true-value, a second name for value
    • unselected-value matches our canonical selected, but it's long
    • off-value matches the checkbox's own description ("often on or off") and the toggle / slider looks, which are role="switch"
  • C's class defaults can be added later, if a subclass ever wants them. Nothing in A blocks it.

What A does, step by step

  1. Submitting: CheckControl.formValue() returns value while chosen, else a new offValue() hook. UICheckbox returns its off-value; UIRadio returns nothing, so radios don't change.
  2. ui-change: detail.value becomes the value it stands for after the change: "open" when chosen, "closed" when unchosen. Without off-value, it stays as today (the element's value). So a handler can write state = event.detail.value.
  3. form.values: a lone checkbox reads off-value instead of false when unchosen. Several boxes of one name list what each submits, so an unchosen one with an off-value adds it.
  4. Fallback: its sync() submits off-value instead of null when unchosen.
  5. Server render, no JavaScript: a native box can't submit a second value. The static output adds a hidden <input name="panel" value="closed"> before the box, as Rails does. The browser then sends both when chosen (panel=closed&panel=open), so the server must take the last. The alternative is to list it in the fallback's degraded notes and skip it.
  6. required: unchanged. It still means "must be chosen", whatever the off-value is. 
formValue(): E.FieldValue {
  return this.isSelected() ? this.choiceValue() : this.offValue()
}

/** Submitted while unchosen;  none ~== nothing. */
protected offValue(): string | undefined {
  return undefined
}
