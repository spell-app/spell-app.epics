The docs-site checker, SiteCheck, had 5 bare sleeps. Each is now a named constant that says why it waits; one became a real wait.

  • The nav flyout: a real wait, then a short sleep.
    • NAV_OPEN_MS: it waits for the flyout to say it's open (waitForFunction(navState)). That replaces part of the old 600 ms, so a flyout that never opens fails fast.
    • NAV_SLIDE_MS (600 ms): then it waits for the slide-in, so the screenshot shows it whole.
  • Still sleeps:
    • RUNTIME_SETTLE_MS: 500 ms, after every load
    • SCROLL_SETTLE_MS: 400 ms
    • LAND_MS: 900 ms, for the deep link's own 400 ms timer
  • Tried and dropped: waiting until the page has no running animation that ends (document.getAnimations()).
    • It didn't see the flyout's slide, inside its shadow root.
    • So the nav screenshot caught it half open (checked by eye, index-phone-nav.png).
  • yarn site:check index.html and ui-button: OK, screenshots as before.
  • Also:
    • --keep-going, which nothing read, is deleted.
    • Its arguments go through node's parseArgs.
    • The folder it was run from comes from environment.invocationDir, not INIT_CWD.
    • A check that can't start throws SiteCheckError (exit 2), instead of a process.exit() deep inside.
    • main() stays on the class, since site-check.ts (Tools 3) calls it.
