@onChange now runs only when a member's value actually changed. A memo that compares the values sits before the effect.

  • Group 6 found the problem: Solid rc.13 runs an effect's apply on EVERY re-run of its compute.
    • createEffectNode() sets _equals: false.
    • A getter, or a @derived member, tracks the sources UNDER it.
    • So an @onChange over one re-ran whenever anything underneath moved.
    • For example, <ui-tab>'s ui-show fired three times.
  • The fix, in Reactive.startEffects(): a memo compares the members' values one by one (===), before the effect. 
    createEffect(createMemo(compute, { equals: isSameList }), apply)
    • Skipping inside the apply was no option: by then, Solid has run the previous cleanup.
  • Workarounds removed:
    • UITab's wasShownLastTime
    • UITabs' swappedForValue, and its roving memo (sameRovingKey, RovingKey). Now it's one @onChange: 
      @onChange("isReady", "isConnected", "isVertical", "tabs", "selectedIndex") onRovingChanged()
    • UISearch's two combined getters (shouldShowPopover, shownHighlightedResult). It's back to the table's two-member @onChanges, which return early in the same cases.
  • Tests, in Reactive.test.tsx:
    • An @onChange over a getter, with a side effect, runs once per real change of its value.
    • One over several members skips a re-run where no value changed.
    • Both fail without the fix (checked).
  • The cost: one more memo per @onChange, a few bytes per element.
  • Every family's @onChange behaves as the old memo chains did. It runs when its value changes, not when a source under a getter moves.
  • UIMenu's roving @onChange("isMenubar", "orientation"), group 10's caveat, no longer restarts on a notify without a change.
