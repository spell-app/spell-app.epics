Group 6 found it: Solid rc.13 runs an effect's apply on EVERY re-run of its compute (createEffectNode() sets _equals: false), and a getter or @derived member tracks the sources UNDER it, so an @onChange over one re-ran whenever anything underneath moved (<ui-tab>'s ui-show fired three times).

  • Reactive.startEffects(): createEffect(createMemo(compute, { equals: isSameList }), apply) -- the members' values compared one by one (===). Skipping inside the apply was no option: Solid has run the previous cleanup by then.
  • Workarounds removed: UITab's wasShownLastTime, UITabs' swappedForValue and its roving memo (sameRovingKey, RovingKey: now @onChange("isReady", "isConnected", "isVertical", "tabs", "selectedIndex") onRovingChanged()), UISearch's two combined getters (shouldShowPopover, shownHighlightedResult: back to the rows' two-member @onChanges, which return early in the same cases).
  • Tests (Reactive.test.tsx): a non-idempotent @onChange over a getter runs once per real change of its value, and a multi-member one skips a re-run where no value changed; both fail without the fix (checked).
  • One memo per @onChange more (a few bytes per element).

Net effect:

  • every family's @onChange behaves as the old memo chains did: it runs when its value changes, not when a source under a getter moves
  • UIMenu's roving @onChange("isMenubar", "orientation") (group 10's caveat) no longer restarts on a notify without a change
