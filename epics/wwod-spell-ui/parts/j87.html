The site's two data loaders now agree on what reset() does: with no URL, it goes back to the default URL. Before, they disagreed (I10).

  • Before:
    • SiteData.reset() kept its URL.
    • SearchData.reset() cleared it.
    • So tests wrote SiteData.reset(); SiteData.url = undefined.
  • Now both follow SearchData's rule: reset(url?) forgets the fetch, and SETS the URL.
    • So reset() alone goes back to the page's own default.
    • That default is the page's <meta>, or SITE_DATA_PATH, beside the data file.
  • Why: reset() reads as "back to the start". No shipped code calls it, only tests, and they always want a clean slate.
  • One shape, not one class.
    • Both keep the same static members: a URL, load() and reset(url?).
    • Both fetch through the same SiteData.request().
  • Rejected: a shared SiteFile<T> base class.
    • A base's statics are shared by its subclasses unless each redeclares them. So both files would share one "loading" state.
    • Instance singletons instead (SiteData.file.url) would change SiteData.url for its callers. That's site.ts, brand-docs.ts and ~40 test lines.
    • All that for two 30-line classes.
  • The tests' SiteData.url = undefined after reset() is now redundant. It's left for P8, which restyles the tests.
  • A caller that wants to reset but keep the URL passes it: SiteData.reset(SiteData.url). None does.
