When a docs-site file fails to load, the site now throws ui's own E.SourceError, with a house-style message. Its three fetches share ONE helper for it, SiteData.request().

  • Before: three hand-rolled fetches each checked response.ok, and threw a plain Error.
    • SiteData.ts
    • SearchData.ts
    • SiteShell.ts
  • Now: SiteData.request(url, { method, fix }) throws a "load" E.SourceError.
    • It has P3's shape: cause: { kind, status }, or the network error as cause.error.
    • Its message, for example: 
      SiteData.load(): …/components.json answered 404 Not Found; run `yarn site:data` in spell-ui, or check `SiteData.url`
  • Chosen over ui's own source loader, UI.sources.load(), because it:
    1. refuses data: URLs as cross-origin, and the docs tests point SiteData.url at one
    2. needs the runtime chunk, which the layout fetch must not wait for (SiteShell.mount(), before <ui-root>)
    3. caches the 780 KB text beside the parsed JSON
  • And not spell's own fetch helpers ($fetch, ResponseError). They live in util's spell folder, which ui must not import.
  • SiteData.ts now imports ui's core namespace, E. Every bundle that loads it already had the core, through ExampleSource: the site entry and brand-docs.js.
  • The same failures, typed and worded the house way.
  • A layout that has no .site-content is a "render" SourceError.
  • SiteRouter's failures to swap a page are SourceErrors too:
    • no main#main
    • an include that shows ui-error
    • the 10 s timeout
  • Every site warning goes through E.Warnings.warn("Spell UI site", …).
    • They were 3 bare console.warns: in SiteShell, SiteRouter and site.ts.
    • UIDocsSearch's already used Warnings (P2).
