The doc-only <ui-docs-*> elements (the live example box, the API table, the side nav, the theme picker ...) are no longer something <ui-root> can load by itself: only a bundle that asks for them, today the Spell UI site's site.js, can show them. This was part of the fix for the extra chunks in the library build (I12, "yarn measure's structure checks already fail on main"), done in P2, commit c5d58cc7.

  • Family: one element folder and the tags it defines, loaded as one file (ui-card/ defines <ui-card>, <ui-cards> ...).
  • Barrel: a family's index.ts; importing it defines the family's tags.
  • Glob: import.meta.glob("../*/index.ts"), Vite's way of saying "every file matching this pattern, each as a lazy import()". The build turns each match into a file of its own.
  • RootLoader: the part of <ui-root> that finds the undefined ui-* tags on a page and imports the family for each, once (RootLoader.ts). <ui-include> uses it too.

What went wrong

  • RootLoader had a second glob, over src/docs-components/*/index.ts, so it could load the seven <ui-docs-*> families too.
  • In the LIBRARY build (dist/), that glob made seven lazy files that import the core and other families.
  • Rolldown (the bundler under Vite) only keeps a shared module in core.js when every lazy file that uses it can be reached from core. These seven could be reached from <ui-root> but not from core.
  • So core's own modules (ValueSets, Vocabulary, BuiltInPacks, the decorators ...) moved out of core.js into a shared BuiltInPacks-<hash>.js that every page then had to load as well.
  • It was one of four causes in I12 (the others: ThemeSheets, MDEngine, MarkdownSanitizer, see J3); each one alone was enough to bring an extra chunk back. 
const FAMILIES = import.meta.glob(["../*/index.ts", "!../ui-root/index.ts"])

/** The doc-only families' barrels, lazy like `FAMILIES` ... */
const DOCS_FAMILIES = import.meta.glob("../../docs-components/*/index.ts")

// in load():
const importer = FAMILIES[`../${folder}/index.ts`] ?? DOCS_FAMILIES[`../../docs-components/${folder}/index.ts`]

The options

  • RootLoader globs only the library's families
  • a new RootLoader.add(barrels) lets a bundle register more
  • the docs glob moves to DocsFamilies; the site's bundle calls DocsFamilies.add()
  • the docs families leave dist/ entirely
  • keep the glob in RootLoader, behind import.meta.env
  • the library build sets the flag off, the site's on
  • one more switch to keep in step between two configs
  • force core's modules back into core.js with a chunk group
  • for the sanitizer, a codeSplitting group named core changed nothing (J3)
  • even if one worked, the seven docs files would still ship in dist/

Why A

  • The docs families aren't part of the library. With them out of RootLoader, they're out of dist/ and out of the docs' single-file bundle (bundle-spell-ui.js builds from dist/index.js), with no flag to keep in step.
  • It fixes the cause (where the import lives), not the symptom (where Rolldown puts it): I12's fix changed import paths and entry structure only, no Rolldown option.
  • The catalog (ROOT_CATALOG) still names the <ui-docs-*> tags. In the library, such a tag now fails like any unknown family ("no family ..."). Only pages that load the site's bundle use them.
  • brand-docs.ts, the brand pages' bundle, already imports its three docs families itself (ui-docs-example, ui-docs-api, ui-docs-tokens), so it needs no change.
  • DocsFamilies imports RootLoader from its leaf file, not the ui-root barrel: the barrel defines <ui-root>, which the site defines only after the theme is in. 
// A leaf, not the barrel:  `spell-ui/components/ui-root` defines `<ui-root>` ...
import { RootLoader } from "spell-ui/components/ui-root/RootLoader"

export class DocsFamilies {
  /** Let every root on the page load the `<ui-docs-*>` families. */
  static add(): void {
    RootLoader.add(BARRELS)
  }
}

const BARRELS = import.meta.glob("./*/index.ts")
 
static load(folder: string): Promise<void> {
  // ...
  const importer = FAMILIES[`../${folder}/index.ts`] ?? RootLoader.added.get(folder)
  load = importer
    ? importer().then(() => undefined)
    : Promise.reject(
        new Error(`RootLoader.load():  no family "${folder}";  add() its barrel before a root needs its tags`)
      )
}

static add(barrels: Record<string, () => Promise<unknown>>): void {
  for (const [path, importer] of Object.entries(barrels)) {
    const folder = BARREL.exec(path)?.[1]
    if (folder) RootLoader.added.set(folder, importer)
  }
}

Yes: it fits on what J2 built. RootLoader.add() already takes "folder => importer" pairs page-wide; a component pack is the same thing written in a file, plus a skeleton per tag. A sketch, then the one choice that needs you.

  • Component pack: a JSON file listing tags a page's roots may meet, each with where its code lives, when to load it, and what to draw until then.
  • Skeleton text: a one-line way to write today's SkeletonSpec object (the skeleton field every vocabulary already has), parsed by ONE function, so the vocabularies and the packs say it the same way. 
<ui-components source="_assets/docs.components.json"></ui-components>
<ui-root> ... <ui-docs-example> ... </ui-root>

<!-- _assets/docs.components.json -->
[
  { "tag": "ui-docs-example", "source": "ui-docs-example.js", "skeleton": "40 x 12" },
  { "tag": "ui-docs-api",     "source": "ui-docs-api.js",     "skeleton": "header, 6 line paragraph" },
  { "tag": "ui-docs-tokens",  "source": "ui-docs-tokens.js",  "load": "eager", "skeleton": "none" }
]

The fields:

  • tag: the element's tag; any custom-element name, not only ui-* (brand's <ui-brand-*>, an app's own)
  • source: the module to import(), relative to the pack file
  • load: today there's ONE policy, "on demand" (a root loads a family when its tag shows up); <ui-root display> (skeleton / when-ready / immediately) is how a root SHOWS things, not when it loads. So: "on-demand" (the default) and "eager" (import as soon as the pack is read)
  • skeleton: the text below, or "none" (today's false)

Skeleton text, each form against the object it means (sizes in em, as today):

text today's SkeletonSpec used by, e.g.
18 x 15 { width: "18em", height: "15em" } ui-ad
2 tall { height: "2em" } ui-progress
inline 6 x 2.5 { display: "inline", width: "6em", height: "2.5em" } ui-button, ui-input
header, 4 line paragraph { parts: [header, paragraph 4] } ui-markdown
18 wide: square image, header, 3 line paragraph { width: "18em", parts: [image square, header, paragraph 3] } ui-card
long line, long line, long line { parts: [line long ×3] } ui-accordion
none false ui-popup, ui-column
  • Parts, comma-separated, top to bottom: <n> line paragraph, header / header with image, image / square image / rectangular image, <length> line (full ... very short, as <ui-placeholder-line>)
  • A leading inline; a size, <w> x <h>, <h> tall or <w> wide: before the parts
  • "Sync with the vocabulary": vocabularies write skeleton: "inline 6 x 2.5" too, and yarn gen:root parses it into the catalog as it does today, so the catalog, the docs and a pack all read one form. test/vocabularies.test.ts parses every one, so a typo fails a test, not a page

What else it touches (small, but worth knowing):

  • A root that meets an unknown tag while a pack is still loading waits for the pack before calling it unknown
  • The docs site would ship its pack, written by yarn site:bundle (its chunk names are hashed), and its layout part gets one <ui-components>; DocsFamilies.add() stays for bundles that prefer JS
  • source runs whatever module it names, like a <script type="module">: no new risk, but a pack is code, not data
