The checkbox's on and off values have class defaults. onValue is set on the shared CheckControl, while offValue is only declared, on the checkbox.

  • Hosts read them through two new getters.
  • CheckControl sets the on value: 
    @E.proto static onValue = UIT.CHECKBOX_DEFAULT_VALUE
    • Radios get it too: a radio subclass may want its own on value.
  • offValue is only DECLARED on UICheckbox, and left out.
    • WWOD: optional properties are left out.
    • Rejected: the card's literal offValue static on the base, since radios never submit an off-value.
  • Card C left open how FormFields and the fallback ask the host. Chosen: two host getters, CheckHost.chosenValue and unchosenValue.
    • They sit beside checkable, which works the same way.
    • Rejected: reading the component from FormFields, which stays plain DOM.
    • Not named onValue and offValue on the host: there, offValue is the off-value attribute's property.
  • New and public:
    • the off-value attribute, and its offValue property
    • el.chosenValue and el.unchosenValue, read-only
    • for subclasses, @E.proto static onValue and offValue
  • FormElement.validationValue() is a new protected hook; by default it's formValue(). A checkbox validates its chosen state, so an off-value never satisfies required.
  • A checked rule in <ui-form rules> on a box with an off-value reads that value, "closed". So it passes while unchosen: use the box's own required.
  • choiceValue() is renamed chosenValue(), internally.
