Every file of src/static/ now imports its own folder through import { SSR } from "$/ui/static" (SSR.ServerHost.attach(), SSR.ROOT) and the element core through import { E, UIT } from "$/ui/core" (E.ElementDefinition, E.NodeType, E.IconGlyph); no more $/ui/elements / $/ui/util / $/ui/vocabulary / ./Peer imports.

Where I drew the WWOD §4 › "Circular imports" line:

  • StaticSelectors and StaticStylesheet build private static readonly selector strings from ROOT / SLOTTED / LIST_ITEM at class evaluation, so those three come from ./static.types.server directly, with // Import directly to avoid circular import; the rest of each file uses SSR.. Proven needed: switching one initializer to SSR.ROOT made 13 of the 14 barrel tests fail (Cannot read properties of undefined (reading 'ROOT')).
  • StaticInteractions' command tables read UIT.TOGGLE_COMMANDS at evaluation too, but through $/ui/core: core never imports $/ui/static, so it's fully loaded first. The exception is applied to the folder's OWN cycle only; a comment there says why.
  • Browser, I18n, IconPacks stay $/ui/runtime/<Service> deep imports in ServerRuntime: the runtime barrel (and so $/ui/core) exports service classes as types only, and the server runtime constructs them.
  • $/ui/styles stays its own import (StaticStylesheet): a separate lib entry, not part of core.
  • StaticCatalog keeps importing each family's class file: a family's index.ts calls customElements.define().
  • new src/static/barrel.ssr.test.ts (WWOD §8 › "Barrels"): enters the barrel by all 12 routes (the barrel, then each file first) and checks every export is defined, flat and under SSR, with the same bindings
