Six short parts: the idea, what exists, the word "CRDT", the catch, a shape, and the size.

  • Two or more people open the same spell project in the editor, on their own screens.
  • Each one's typing shows up on the others' screens as they type, with no "save and reload".
  • Maybe also: they watch, and play with, the same RUNNING program, e.g. two people in one Solitaire game.
  • The base you named: the Python target's way of keeping a page in step with its program.
    • The page gets the program's whole state once, each thing with an id.
    • After that, only the things that changed: a "patch".

Two separate pieces, neither shared between people yet.

  • A CRDT ("conflict-free replicated data type") is a shared document that every copy can change at the same time.
  • Copies swap their changes in any order, and still all end up the same, with nobody's change lost.
  • No referee needed: that's what sets it apart from today's patches, where ONE program decides everything.
  • Text is the hard case: two people typing in one line at once must both see both edits, in one order. Libraries do this: Yjs (with a Monaco binding, y-monaco), Automerge, Loro.

They work because there's always one referee: the running program. Without one, four things break.

  • Ids: the server hands them out, counting up ("3", "26"). Two editors making new things at once would both make a "27".
  • Whole things: a patch sends a changed thing whole, and the last one to arrive wins. You change a card's suit while I turn it face up: one of the two changes is lost.
  • One way: only the program sends patches; a page sends requests, which the program may refuse.
  • Text: source is text, not things. A "whole file" patch would wipe out whatever the other person typed meanwhile.

So the patches fit the RUNNING program well (a referee, every viewer's page mirrors it), and the source text badly.

  • The source text: a text CRDT library in the editor, with the editor server relaying changes between tabs and saving the file to disk.
    • Each person sees the others' cursors and selections.
    • The language server parses each copy in its own tab, as it does today.
  • A running program: ONE program on the server (Spell Server State, for javascript), with every viewer's page mirroring it through patches.
    • Two people's clicks both go to that program, which settles them in order: no CRDT needed there.
  • What goes away: saving a whole file on each change, and "the last tab to save wins".

A text CRDT library for the source (Yjs, with its Monaco binding); our patches stay for running programs.

  • Yjs: widely used, small, plain javascript, a ready Monaco binding and cursor sharing.
  • Loro and Automerge: newer designs, in Rust compiled to WebAssembly; bigger downloads.
  • The plan would compare them before picking one.

Make the patches a CRDT ourselves: ids unique per person, a clock per property, a text merge. We own all of it; text merging is the hard part, and months of work to get right.

Every person's tab has a copy; something must pass changes between them, and save the files.

The app's own editor server relays changes between tabs, and writes the files to disk as they change.

Tabs talk to each other directly (WebRTC), no server in the middle. Someone still has to save the files.

A service on the internet keeps the shared copy (e.g. Liveblocks). Easy to reach; an outside dependency.

Who can join an editing session, and from where.

Tabs on your machine, or people on your network: no accounts, no sign-in. Enough to build and try it.

Anyone with a link, from anywhere: sign-in, permissions, hosting. An epic of its own.
