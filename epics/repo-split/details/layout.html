Repo Split: the layout

What the repo split leaves behind once all of it is built: where every package and repo lives, how someone works with it (the whole thing, or Spell UI alone), and what it costs against today's one repo. Nothing to decide here: it's so you can judge the approved plan by what it makes.

The plan is approved and nothing is built. It runs in three stretches:

  • Phases 1-6, inside today's one repo: cut every import that points the wrong way (util trimmed, Spell UI's plugins, spell-solid renamed spell-element, the server split, the pack build moved into Spell UI's tools, package names and a shared toolchain). Each is an ordinary change that merges into main.
  • Phases 7-8, the cutover: spell-app becomes the meta repo, and four new repos are cut out of its history: spell-server, spell-element, spell-parser and spell-ui. spell-epic moves inside spell-app.
  • Phase 9, the tooling: worktrees, merging main, /isolate done, the VS Code extension and CI learn about several repos.

Words this page uses:

  • Repo: a git repository of its own: its own history, branches, pull requests and releases.
  • Meta repo: the repo at the top that holds the others and the ONE install for all of them. Here that's spell-app itself: its package.json lists its own packages and every child repo's, so one yarn install links them all.
  • Child repo: a repo cloned INSIDE spell-app's folder (spell-app/spell-ui/ ...). It's still its own git repo; spell-app just holds it on disk.
  • Git-ignored: listed in spell-app's .gitignore, so spell-app's git never sees the child repo's files. git status at spell-app's root shows only spell-app's own changes; each child repo has its own git status.
  • Lower and higher: a lower repo is one others use (spell-element, spell-parser); a higher one uses others (spell-app). The rule: arrows only point down.
  • Worktree: a second checkout of a repo on another branch, in its own folder. An epic gets one.

It doesn't move. The editor app stays in spell-app, at ~/www/spell-app/spell-app/packages/app/, with its tests at ~/www/spell-app/spell-app/tests/app/, exactly as today. So do core, py, spell, spaces, lsp, cli, vscode and brand. What leaves packages/ is the lower layers: util (to a top-level util/ folder), and parser, markdown, spell-solid, ui, server and assembler (to child repos). Table 2.4 has every package.

Every child repo has the same shape as spell-app has today, only smaller:

  • its own package.json, with its scripts (ts, test, lint, review)
  • its own AGENTS.md and CLAUDE.md: today's package rules, plus the repo's
  • an agents link to spell-app's agents/ folder (WWOD and the logs)
  • its own .epic/config.json5, .gitattributes and generators list (the generated files it commits)
  • packages/<name>/ for its code, and tests/<name>/ beside it
  • no yarn.lock and no CI of its own while it lives inside spell-app: the meta repo's install and CI cover it

spell-epic keeps its own shape (one package laid out as a repo), less the copies it carries today.

Two people: one hacking on everything, one who only wants Spell UI. Then the parser and the epic engine.

  • Set up once: clone spell-app, clone the five child repos inside it, run one yarn install at spell-app's root.
  • The cloning step is a proposal (the plan doesn't name it): a small script in spell-app, scripts/repos.mjs, that reads the child repos' list from spell-app's package.json and clones the missing ones.
    • It must run with plain node the first time, not as yarn repos clone: yarn runs no script before yarn install, and the install needs the child repos present first (spell-app's packages depend on theirs).
    • After that, yarn repos pull (or spell dev repos ...) updates them all.
  • Checks: yarn review (or yarn ts, yarn test) at spell-app's root covers every package of every repo, since they're all one install. One repo's alone: its own scripts, from its folder.
  • A change across two repos is two commits, one in each repo, then two pull requests. No publish, no version bump: spell-app's packages use spell-ui's source straight from spell-ui/.
  • Git: git status at spell-app's root shows only spell-app's files. Each child repo answers for itself (cd spell-ui && git status); VS Code's Source Control lists them all.

What gets better, and what gets worse, once the split is done.

What Today (one repo, plus spell-epic beside it) After the split Net
A fix to Spell UI A commit in spell-app, among 16 packages' history. One commit in spell-ui, its own history, pull requests and releases. Better
Spell UI standing alone Commits 970 KB of bundles built from the language and markdown, stale until someone regenerates them. Builds and runs with no parser, language or server: those come in as plugins. Better
spell-epic's install Its own install, through links into spell-app: Solid's pins, the catalog and the lint config copied by hand, a second alias table, "which checkout?" bugs. On the one install: one Solid, one catalog, no copies, no link to the wrong checkout. Better
CI spell-app only; spell-epic has none. spell-app's CI clones the child repos inside it and checks all six. Better
Which way imports point By convention only; every alias works from every package. Package names say which repo an import comes from, a lint rule stops climbing into another package's folders, and a repo cloned alone can't see the repos above it. Better
A change across repos One commit, one pull request. One commit and one pull request per repo, merged in order (the lower repo first). Worse
An epic's worktree One git worktree. Up to six git worktrees, one per repo, in one folder; merging main and /isolate done loop over them, and can stop with one repo merged and another not. Worse
Git, day to day One git status, git log, git grep. One per repo; history searches go repo by repo. VS Code's Source Control lists them together. Worse
Getting started Clone, install. Clone, clone five more inside it (one script), install. Slightly worse
Per-repo upkeep One AGENTS.md, one epic settings file, one list of generated files. Each repo its own: rules, epic settings, .gitattributes, generators list. Worse
The rules and logs One copy in the content repo, seen by every branch at once. In spell-app's agents/, linked into every repo. A folder in a git repo has branches: a log line written in an epic's worktree shows elsewhere only once it merges, unless every checkout links the main checkout's copy. Worse, unless linked to main
The cost of getting there Nothing. About 20-27 hours over ten phases; a rewrite of about 3,100 import lines in 970 files; the cutover runs on main, and other sessions' worktrees merge main before it. Cost
A lower repo cloned alone Not possible: one repo. Not possible either, until util and toolchain are on npm: the repo loop (4.2). Same, for now
  • spell-parser, spell-element and spell-ui (the lower repos) all use @spell-app/util, which lives in spell-app's util/ folder: the top repo.
  • No package needs a package that needs it back, so the code has no cycle. But the REPOS loop: spell-app needs spell-ui, and spell-ui needs spell-app.
  • Inside the meta checkout you never see it: it's all one install. It shows the moment someone clones a lower repo alone (3.2, 3.3): it can't install.
  • toolchain/ and agents/ make the same loop, for the tools and the rules.

How it came about: on the analysis page you picked a repo of its own for util (Q2, spell-util); your comments on the plan then made spell-app the meta repo, with util/ and toolchain/ as top-level folders in it, so there's no spell-util repo (, ).

What would fix it, either way:

  • util (and toolchain) on npm, the later step the analysis page already picked for release ().
    • A lower repo alone installs versions, and stands on its own.
    • Inside the meta checkout nothing changes: it still uses the live source.
    • The cost: a build, an exports map and a version bump for util whenever a lower repo needs a util change.
  • util in a small repo of its own, spell-util, at the bottom, as your first pick had it (Q2, and Q7's B: separate from the server).
    • A seventh repo, cloned inside spell-app like the others; the loop is gone from the picture.
    • A lower repo alone then needs only spell-util beside it, not the whole of spell-app; with no npm, still a clone.
    • toolchain and the rules could live there too.

The plan as approved keeps util in spell-app and lives with the loop until npm.
