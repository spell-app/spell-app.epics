You proposed five repos: spell-parser, spell-epic, spell-element (spell-solid, renamed), spell-ui and spell-app (the editor and its server). The epic was written down. Nothing is planned yet. Two read-only research passes mapped who imports whom, the files one package builds for another, the links that only exist at run time, and what spell-epic's own move out of the monorepo (epic epic-eject) has cost so far. Words this page uses:

  • Repo: a git repository of its own, with its own history, checks and releases. Today spell-app holds 16 packages, and spell-epic (the epic engine) sits beside it.
  • Package: one folder of packages/, imported as $/name ($/parser, $/ui ...).
  • Cycle: two repos that each need the other. Neither can be built, tested or released first, so every change touching both is two changes that must land together. Drawn in red.
  • Import site: one import line in one file. The numbers on the arrows count them.
  • Portal link: how spell-epic reaches spell-app today: a folder link on disk, and yarn dependencies like portal:.spell-app/packages/ui. Live source, nothing published.
  • Meta repo: a parent folder with its own package.json whose workspaces are the repos, so all of them share one install (1.4).

Six repos, cut along the seams the research found: every arrow points down, no cycles. The cost: four new boundaries, and the fixes in 1.2 first.

  • spell-parser: parser, markdown, and util's heavy half (Q2).
  • spell-element: spell-solid, and util's small generic files.
  • spell-ui: ui. It stops shipping bundles built from spell: it keeps a slot for the spell highlighter that spell-app fills, and takes markdown's from spell-parser.

Once there are several repos, how does one use another's code? The three ways, with pictures, are in 1.4. The worst cost today is the toolchain copied by hand, and the risk of two copies of Solid on one page.

While building: a parent folder holds every repo as a workspace, with one install. At release: publish the packages outsiders use to npm.

  • One lockfile, so ONE Solid (today spell-epic copies Solid's four version pins by hand), one set of tool versions, one alias table.
  • A change across two repos is two commits, but no publish and no version bump.
  • CI runs from a meta checkout, so spell-epic gets CI at last.
  • npm later, for outsiders: ui already has a build and exports; the rest are private 0.0.0 packages shipping raw .ts, so publishing all of them now would mean a build and a version bump for every change that crosses repos.
  • The costs: worktrees are per repo, so an epic touching two repos needs a worktree in each (the tooling assumes one); each repo's yarn settings must not clash with the parent's (spell-app's settings already guard against a parent's leaking in).

Example: ~/www/spell/package.json lists "workspaces": ["spell-parser", "spell-ui", "spell-epic", "spell-app" ...]; one yarn install at the top links them all.

  • the hand-synced toolchain and the Solid risk go away
  • the worktree tooling learns about several repos

Every repo builds and publishes its @spell-app/* packages; the others install versions.

Example: a button fix is a spell-ui commit, a version bump to 1.4.1, a publish, then a bump in spell-app and spell-epic.

  • each repo truly stands alone, pinned to versions
  • builds and exports for every package; a publish per cross-repo change

Each repo links to the folders of the ones it uses, as spell-epic does now.

Example: spell-ui gets a .spell-element link, spell-app links to four repos, and each has its own alias table and copied tool versions.

  • nothing new to learn
  • 1.3's costs for every link: many more "which checkout?" bugs
