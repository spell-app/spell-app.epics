One import name, and the leftovers

What we can clean up now the old worktrees are gone, and what ONE way to name a package in every import (tests too, no $/ left) involves.

  • It works in every tool we run, with one small catch for the type checker.
  • About 4,200 imports change, by script; about 6,000 lines of old-layout code can go.
  • Six calls are yours, below.

How a deep import is written from now on, what happens to names baked into built files and to old epic pages, what old tools to delete, and when the work happens.

Words this page uses:

  • $/ alias: today's short name for a package inside its own repo, e.g. $/ui/core, $/parser. Each repo has its own table of them.
  • Package name: the name in a package.json, e.g. spell-ui, spell-kit. Another repo already imports by it: spell-ui/core.
  • Entry: one name a package's exports lists, e.g. spell-ui/core. Only entries can be imported by package name.
  • Deep import: an import of a file that isn't an entry, e.g. $/ui/elements/ClassBuilder.
  • Barrel: a package's or folder's index.ts, which re-exports the files under it.
  • Subpath imports (#/): node's own way for a package to name its OWN files, an imports field in package.json. Private: another package can't use it.
  • Built declarations: the .d.ts files spell-types builds into each package's git-ignored dist-types/ folder. The type checker reads another repo's package through them.
  • Condition: a key in an exports entry that says which file a tool gets, e.g. types for the type checker, default for everyone else.

Where it's defined

  • Six alias tables, one tsconfig.base.json per repo, plus a frozen copy of the old monorepo's for a test. Every package's tsconfig extends its repo's.
  • Vite and Vitest read them through resolve.tsconfigPaths, in 18 configs. Five more files list the aliases by hand, because they sit outside any tsconfig.
  • The run-time alias hook (spell-kit/toolchain/aliases), for tsx and node. 79 lines load it: about 20 places that start a child process, 20 yarn scripts, three bin files ...
  • spell-types rewrites every $/ in the built declarations into a relative path, so another repo can read them.
  • About 12 hand-written resolvers: esbuild plugins, the pack build's "may not import" check, the app's shared-module maps, a type check that writes its own paths, and spell dev pack new, which writes new $/ aliases.

Why it's the reason for the hook

  • tsx reads ONE tsconfig for every file it runs.
  • spell-app's CLI runs spell-lang's and the kit's source. It meets $/server/... with spell-app's table, which hasn't got it: Cannot find package '$'.
  • So the hook finds each importing file's own repo, and resolves by that repo's table.
  • Package names and #/ resolve by the importing file's own package.json, in node itself. With no $/ left, the hook has nothing to do.

 The run-time alias hook, its heart · aliases.ts · 10 lines 
registerHooks({
  resolve(specifier, context, nextResolve) {
    if (specifier.startsWith("$/") && context.parentURL?.startsWith("file:")) {
      const file = aliasedFile(specifier, fileURLToPath(context.parentURL))
      if (file) return nextResolve(pathToFileURL(file).href, context)
    }
    return nextResolve(specifier, context)
  }
})

"Package name everywhere" means a file in spell-ui imports spell-ui/core, as spell-app does. That's a self-import: a package naming itself. It was tested with real files, in every tool the repos run.

The type checker's catch

  • Every entry has a types condition pointing at the built declarations. That's how spell-app reads spell-ui today.
  • So spell-ui naming itself gets its OWN built declarations, not its source.
  • Mixed with a relative import of the same file, one class has two types, and the check fails.
  • Building the declarations fails too: it would overwrite its own input.
  • A fresh clone (no dist-types/ yet) passes by accident, so it would bite later.
  • So no self-import by package name is safe for the type checker until the fix is in.

The fix: a condition of its own per package

  • Each entry gets a spell-ui-source key FIRST, pointing at the source.
  • spell-ui's tsconfig lists only its own: customConditions: ["spell-ui-source"].
  • So spell-ui reads its own source, and every other package's built declarations, as today.
  • Vite, Vitest, tsx and node ignore both keys, and take default, the source.
  • Published builds don't carry it: publishConfig.exports replaces exports whole.
  • Why not one shared source key: spell-app would then type-check spell-ui's and spell-lang's source under ITS settings (JSX, lib, types differ), and a third-party package (tar) already uses that key.

Pack-module keys

  • A component pack doesn't bundle Spell UI's core: it asks the page for it, by a name.
  • The names are still the old ones: $/spell-element, $/ui/core, $/ui/forms, $/ui/components/ui-code ...
  • packModuleKey() turns each npm name back into its $/ name: spell-kit/element is $/spell-element, spell-epic is $/epics. We kept them on purpose in phase 9 [J72].
  • Who offers them: spell-epic's docs bundle, Spell UI's site, the app's shared-module maps (9 strings).
  • Who reads them: the committed packs (the brand's, the epics'), the app's built pages, and one guide's live-elements bundle in the content repo.
  • Four tests pin them.
The keys, and the mapping back · packModules.ts · 13 lines 
export const PACK_MODULES = ["solid-js", "@solidjs/web", "$/spell-element", "$/ui/core", "$/ui/forms"]

export function packModuleKey(specifier: string): string {
  const family = /^spell-ui\/(ui-[a-z-]+)$/.exec(specifier)
  if (family) return `$/ui/components/${family[1]}`
  const kit = /^spell-kit\/([^/]+)(.*)$/.exec(specifier)
  if (kit) return `$/${kit[1] === "element" ? "spell-element" : kit[1]}${kit[2]}`
  const folder = /^spell-(?:lang|app)\/(.+)$/.exec(specifier)
  if (folder) return `$/${folder[1]}`
  const flat = /^spell-(ui|brand|epic)((?:\/.*)?)$/.exec(specifier)
  if (flat) return `$/${flat[1] === "epic" ? "epics" : flat[1]}${flat[2]}`
  return specifier
}

The order, so nothing is ever half-broken

With $/ gone, how does a file import a file of its OWN package that isn't an entry? 2,434 imports, into 818 files, do that today (1.3).

Package name for entries, #/ plus the real extension for the rest. Works in every tool, no hook; other repos still see only the entries.

  • Each package gets an imports field of 1-5 lines, mirroring its $/ table.
  • The cost: two forms, not one. A name for an entry, #/ for anything inside.
  • And the extension: #/util/index.ts, not #/util.
  • spell-types rewrites #/ in built declarations, as it rewrites $/ now.
