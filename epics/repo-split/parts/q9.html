Today an epic gets one worktree of spell-app, with its own yarn install. With a meta repo, one install covers every repo, so a worktree of spell-ui alone has nothing to install against.

  • spell-app.worktrees/<epic>/ holds a git worktree of EACH repo, and the meta package.json.
  • Repos the epic changes are on branch <epic>; the rest sit on main, untouched.
  • One install per epic, as today; an epic that touches two repos needs nothing extra.
  • Cost: epic worktree, merge-main and /isolate done learn to work over several repos.
  • Lighter: one git worktree, the other repos linked from the main checkouts.
  • But yarn won't take linked folders as workspaces, and an epic changing two repos is stuck.
  • an epic is still one folder and one window
  • the worktree tooling grows a loop over repos

What does A mean in terms of working with files in VSCode?

You also asked, on the plan: “provide more detail in Q9 for how this will affect 'file open' in vscode”. In short: with A, an epic's window shows ONE folder holding every repo, and any file you open there is the epic's own copy, ready to edit.

One change to A first, so that last part is always true:

  • EVERY repo in an epic's worktree is on branch <epic>, not only the repos the epic changes.
  • So any file you open is editable, in any repo, with no step to "check out" a repo first.
  • A repo the epic never touched has an empty branch, and merging the epic skips it.

What the window holds

The epic's window, titled ⎇ repo-split, has two folders:

  1. spell-app's MAIN root.
    • It's first so the Claude panel lists every session (Q10).
    • Its files are hidden in Explorer and Quick Open, as today, so you never open main's copy by mistake.
  2. The epic's worktree.
    • spell-app's own files, with the five child repos inside it: spell-server, spell-element, spell-parser, spell-ui and spell-epic.
    • Each child repo is a git worktree of its own repo, on branch repo-split.
spell-app.worktrees/repo-split/     spell-app, on branch repo-split
  util/  toolchain/  packages/ ...  spell-app's own files
  spell-server/                     spell-server, on branch repo-split
  spell-element/                    spell-element, on branch repo-split
  spell-parser/                     spell-parser, on branch repo-split
  spell-ui/                         spell-ui, on branch repo-split
  spell-epic/                       spell-epic, on branch repo-split

Opening a file, every way

How you open a file What happens
Quick Open (Cmd+P) It searches every repo in the worktree. Button.tsx shows once, its folder beside it (inside spell-ui). Main's copies stay hidden.
The same name in several repos package.json, AGENTS.md and index.ts show one row per repo, told apart by the folder beside each. Typing ui/AGENTS narrows it to one. Editor tabs add the folder when two names clash.
Explorer One tree: spell-app's folders, with the child repos among them.
Go to Definition, or Cmd+click on an import An import of @spell-app/ui resolves, through the one install, to the epic's own spell-ui folder: the epic's copy, editable. Never a copy in node_modules: TypeScript follows the link to the real file.
A link in Claude's reply Written from the worktree's root, so it starts with the repo's folder (spell-ui/...). Still one click.
A path into MAIN's checkout It opens main's copy, not the epic's: the same risk as today. It's hidden from Quick Open and Explorer, but a pasted full path still gets there.
The terminal It opens at the worktree's root. cd spell-ui for one repo's checks, or run the root's scripts for all of them.
Source Control One entry per repo, each with its own changes. Repos the epic didn't touch show nothing.
