Every change across the repos is six commits, six pushes, six CI runs and six merges, for what is one product with one version.

Owen asked (2026-10-26) whether the child repos still need to be separate repos, now that there's one version, one npm install spell that brings everything, and one spell publish. The trade-off:

What separate repos buy What it's worth now
Imports only point down, enforced by cloning A lint rule over the folders can enforce the same
Small clones Nobody outside clones them yet
A GitHub page per project The READMEs and npm pages stay anyway
spell-brand private Only spell-brand needs that: it stays a repo of its own
spell-epic installs as a Claude plugin from its own repo Not needed: a plugin can come from a folder of a bigger repo, or from npm (the aside below)
Each repo's CI is faster A change across repos still needs all of them

What they cost, all of it seen in this epic:

  • Every change across repos is six commits, pushes, CI runs and merges.
    • The New Names took six rounds of merging main, each with its conflicts.
    • Pushing a branch doesn't start CI, so a red repo shows up late.
  • A worktree is a worktree of the kit plus five worktrees of the child repos.
    • Moving the spell-lang folder to spell-parser needed git worktree repair in each.
    • Merging main skipped a repo, because it looked it up by folder name.
  • CI rebuilds the layout by cloning, so a hang in it is hard to find (the CI hang, I73).
  • TypeScript reads the other repos through their built declarations:
    • stale declarations fail the type check until spell-types --below rebuilds them
    • each package needs three conditions in its exports
  • Lookups that accept either name, and the resolver esbuild needs to find our names.
  • A push sweeps in commits other sessions left on the branch.
  • The versions drift, and were all forced to 0.8.0 anyway.

What this phase delivers:

  • The four repos are folders of the kit's repo, with their history: git log on a file in ui/ goes back past the merge.
  • One install, as today: yarn workspaces over the folders, one yarn install at the root.
  • The rule that imports only point down (the kit, then parser and ui, then epic, then app) is a lint rule over the folders, with its test, in place of the clone that enforced it.
  • TypeScript reads the other packages' source where that's simpler, or keeps the built declarations (Q59).
  • CI is one workflow for the repo, plus spell-brand's own.
  • spell publish works as before: the same five packages, the same names.
  • The spell-epic plugin still installs:
    • for Owen, loaded in place from the checkout, never copied
    • for anyone else, from npm, or from a marketplace file at the repo's root that points at ./epic (Q58)
  • An epic's worktree is ONE worktree, not six.
    • That's epic-engine's tooling: the hook that makes worktrees, epic worktree merge-main, the window files. Most likely a request sent to it (/send), not built here.
  • The four old GitHub repos are archived, each with a README pointing at the new home (Q60).
    • Their URLs redirect nowhere: GitHub redirects a renamed or moved repo, not one whose code moved into another.
  • Branches still open in other worktrees have a way across: a script that moves each child repo's branch into its folder of the merged repo, or the branch is merged into main first.
  • A marketplace file at the merged repo's root can list the plugin as "source": "./epic": a relative path is read from the marketplace's root.
    • /plugin marketplace add spell-app/spell then works.
    • Keeping the marketplace's NAME spell-epic keeps the install command the same: /plugin install spell-epic@spell-epic.
  • On install, Claude Code copies ONLY the plugin's folder, into its plugin cache.
    • Files outside that folder aren't copied, and a path out of it (../) is refused.
    • So the folder must stand on its own. Today it doesn't: the hooks import spell-epic's own code and its packages through node_modules, and a copied plugin has no yarn install.
    • Claude Code can install a plugin's dependencies when it installs it, but only from an npm or bun lockfile in the plugin's folder, not from yarn.lock.
  • Two other ways to name a plugin's source:
    • a folder of a git repo (git-subdir: its URL, path, branch or commit), fetched as a sparse checkout of that one folder
    • an npm package (npm: its name, version, registry). This fits Publish Prep: the packed spell-epic already ships the plugin's parts (its manifest, hooks, skills, monitors) and its built code, with its dependencies.
  • Recommended: npm for people outside; Owen's machine keeps loading it in place, from a folder marketplace or --plugin-dir.
  • Still open:
    • how installs made from the old spell-epic repo move over: the docs don't cover a repo moving
    • whether the skills' paths into src/ under the plugin's root need fixing, since only the built code ships on npm (already noted in J199)
  • The docs: marketplace reference, loading plugins, making a marketplace, hosting one.
