What goes where once the monorepo is split, who uses whom, how you set it up, and the order the work happens in. The most current picture, with every repo's insides, the tests and the cost, is the layout page. This part becomes the epic's guide in the last phase.

The top repo, spell

A new repo, spell, checked out at ~/www/spell, holds every other repo on disk and the ONE install for all of them, and nothing else (Q15).

  • No package lives in it: nothing anyone imports. So no lower repo ever needs it, and there's no repo loop.
  • The child repos are cloned inside it, git-ignored: each still its own git repo, with its own history.
  • Its package.json names every spell-* folder as a workspace, and each child repo names its own packages.
  • The content repo and your projects move inside it too, as data folders, so one VS Code folder covers everything (J5). 
~/www/spell/                 the spell repo:  ONLY the glue
  package.json               "workspaces": ["spell-*"];  scripts:  clone, pull, status
  yarn.lock  .yarnrc.yml     one install, one Solid, one set of tool versions
  repos.json5                the child repos:  name, git URL, which repos each needs
  spell-util/      util (with its node-only util/json5), toolchain, agents/ (WWOD + the logs)
  spell-server/    server (with the site header), assembler
  spell-element/   flat:  IS @spell-app/spell-element (was spell-solid)
  spell-ui/        flat:  IS @spell-app/ui;  <ui-code> on highlight.js, <ui-markdown> on marked
  spell-brand/     flat:  IS @spell-app/brand
  spell-lang/      parser, markdown, core, py, spell;  <spell-code>, <spell-markdown>
  spell-epic/      flat, as today:  the epic engine, with its own VS Code extension (the Review tab)
  spell-app/       app, spaces, lsp, cli, vscode, page-server:  the editor and its servers
  spell.epics/     the content repo (was spell-app.epics), git-ignored
  spell.spaces/    your projects (was spell-spaces), git-ignored
~/www/spell.worktrees/<epic>/    an epic's worktree:  of spell, with each child's inside it

The eight code repos, bottom to top

Every package lives in one of eight child repos, in layers: a repo uses only the repos below it.

spell-app     ->  spell-lang, spell-brand, spell-ui, spell-server, spell-util
                  (spell-epic by the page server's settings only, never imported)
spell-epic    ->  spell-brand, spell-ui, spell-server, spell-element, spell-util
spell-brand   ->  spell-ui, spell-element
spell-ui      ->  spell-element, spell-util, spell-server (its site tools and tests only)
spell-lang    ->  spell-util
spell-element ->  spell-util
spell-server  ->  spell-util (the assembler's data files read util's json5)
spell-util    ->  nothing
  • spell-util is at the bottom: util kept whole (Q22), plus JSON5 (Q18), the shared toolchain, and the house style and logs (Q6).
  • The parser and the language are one repo, spell-lang (Q20, J2).
  • brand is its own repo, so spell-epic never points up to spell-app (J3).
  • spell-app keeps the editor and its servers (J4).
  • Inside each repo, every package is a folder at its root, and a one-package repo IS its package: no packages/ folder anywhere (Q16).
  • Tests go to tests/<name>/ at the repo's root, or straight to tests/, mirroring the code, in a flat repo.
  • One repo names another's code by package name (@spell-app/ui); $/ stays inside a repo (Q8).

Spell's code and markdown in Spell UI

Spell UI has no spell in it. It keeps its own code and markdown elements, and spell-lang subclasses them for spell (Q19).

  • <ui-code> stays on highlight.js, with its language registry, as today.
  • <ui-markdown> stays on marked.
  • <spell-code>, in spell-lang: loading it registers spell with Spell UI's code registry, so a spell block in any markdown is coloured.
  • <spell-markdown>, in spell-lang: spell's own markdown engine, plain and editable.
  • No plugin system: that was the first plan for P2, replaced.
  • Whether marked goes, once spell's markdown bundle is slimmed, is still open (Q21).

Setting up

Two yarn commands in the top repo, and nothing else (Q17).

git clone <spell's URL> ~/www/spell && cd ~/www/spell
yarn install            # quick:  no child repos yet, so nothing to link
yarn clone              # clones every child repo, then installs again:  one install for all
yarn clone spell-ui     # or just Spell UI and what it needs:  spell-element, spell-server, spell-util
yarn pull               # git pull in every child repo
yarn status             # each child repo's git status
  • Checks at ~/www/spell cover every package of every repo; inside a repo, just its own.
  • A change across repos is a commit in each, merged lowest first (C5). No publish, no version bump while developing.
  • Once the packages are on npm (Q4's later step), a repo works with no spell at all.

The order of the work

  1. The seams, inside today's one repo (P1 to P6): cut every import that points the wrong way.
    • util stops reaching into spell, and takes JSON5 in.
    • Spell UI loses its spell bundles; <spell-code> and <spell-markdown> arrive.
    • spell-solid is renamed spell-element, and its tests stop needing Spell UI.
    • The server splits from its page layer (the site header stays with the server, C7).
    • The pack build moves into Spell UI's tools.
    • Imports across repos use package names, and the toolchain becomes a package.
    • Each is an ordinary change with ordinary checks, merged into main before the cutover (Q12).
  2. The cutover (P7, P8): the top repo spell, then spell-app cut into the child repos, each with its history; spell-epic, the content repo and your projects move in.
    • Every path moves once, so other sessions finish or park first (C3, C6).
  3. The tooling (P9): worktrees at ~/www/spell.worktrees, merging main, /isolate done, the VS Code window (folder 1 is ~/www/spell), the extension and CI.
  4. The text pass and the guide (P10).
