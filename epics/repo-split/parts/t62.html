Publishing Spell's three npm packages (spell, spell-ui, spell-epic) moves off the 30-day token in your ~/.npmrc and onto npm's trusted publishing. A GitHub Actions workflow in the kit's repo publishes them, and you start it by hand from the Actions tab, picking the tag. npm trusts that workflow by name, so no token is kept anywhere.

Why now: two dates.

  • Your current token expires on 2026-11-28. It's a granular access token with "Bypass two-factor authentication" on, made for 30 days, as Publishing to npm says ("Logging in: a token, not npm login").
  • npm says tokens like it lose direct publishing around January 2027 (GitHub changelog, 2026-07-08).
    • After that, such a token can only STAGE a publish, which goes public once a person approves it with 2FA.
    • npm's recommended replacement for automated publishing: trusted publishing, or staged publishing.
    • "Around January" is npm's estimate, not a fixed day.
    • The earlier step already happened (early August 2026): those tokens can no longer skip 2FA for account and package settings.
  • Until the workflow works, a new 30-day token still bridges the gap after 2026-11-28, but only until January.

What trusted publishing is.

  • On npmjs.com, each package names ONE GitHub repo and ONE workflow file allowed to publish it (npm docs, Trusted publishers).
  • When that workflow runs npm publish, GitHub hands it a short-lived identity token (OIDC), and npm checks it against the package's settings. No secret is stored in GitHub or on your laptop.
  • npm adds a provenance statement by itself, because the repo and packages are public: npmjs.com then shows which commit and workflow built each version.
  • It needs npm 11.5.1 or newer and Node 22.14 or newer, on GitHub's own runners (not self-hosted ones). Your machine has npm 11.19; the workflow would pin a new enough npm too.

The workflow, step by step (a new file beside the checks workflow, say publish.yml).

  1. You open the repo's Actions tab, pick "publish", press "Run workflow" on main, and choose:
    • the tag: next (the default) or latest
    • dry run: yes or no
  2. It checks out that commit. The version is whatever the kit's package.json says there, as now.
  3. It sets up the same machine the checks workflow does: Node 24, yarn, yarn install, the two VS Code extensions' installs, and headless Chromium (the scratch install draws a <ui-button> in it).
  4. It builds the epic extension's .vsix (yarn vscode:package in epic/). It isn't committed; without it the publish only warns, and epic plugin install can't install the extension from the published package.
  5. It runs the dependency check (spell deps check): the standing rule says dependencies are checked before any publish.
  6. It runs spell publish --tag <tag> (with --dry-run when asked): the same command you run today, unchanged.
    • build, pack and check the three packages
    • the two scratch installs, lean and whole, with their audits
    • then, only if every check passed: npm publish for each, spell first
  7. npm publish finds it's running in GitHub Actions with permission to ask for an identity token, and publishes with no login at all.
  8. The run's summary keeps what the publish printed, and the packed .tgz files as a download.
name: publish
on:
  workflow_dispatch:
    inputs:
      tag: { type: choice, options: [next, latest], default: next }
      dry-run: { type: boolean, default: false }
permissions:
  id-token: write    # the identity token npm checks
  contents: read
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: corepack enable
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: yarn }
      - run: npm install -g npm@^11.5.1
      - run: yarn install
      - run: yarn install
        working-directory: epic/vscode
      - run: yarn vscode:package
        working-directory: epic
      - run: yarn playwright install --with-deps chromium
      - run: node bin/spell.mjs deps check
      - run: node bin/spell.mjs publish --tag ${{ inputs.tag }} ${{ inputs.dry-run && '--dry-run' || '' }}

What you do by hand, once, on npmjs.com (only you can: it needs your login and 2FA).

  1. For EACH of spell, spell-ui and spell-epic: open the package's Settings, find "Trusted Publisher", pick GitHub Actions, and fill in:
    • Organization or user: the repo's owner, as in its GitHub address
    • Repository: spell
    • Workflow filename: publish.yml (the name only, not its folder)
    • Environment: leave empty, unless we add a GitHub "environment" that asks you to approve each run
    • Allowed actions: direct publish on
  2. Or the same from the terminal, one line per package, after a plain npm login (a bypass-2FA token is refused for this): npm trust github <package> --repo <owner>/spell --file publish.yml --allow-publish. npm offers to skip 2FA for 5 minutes after the first, so the other two go through at once.
  3. Then start a run within 2 days: npm drops a new trusted-publisher setting that hasn't published within 2 days, and it has to be made again.
  4. Once a real run has published all three:
    • each package's Settings, "Publishing access": "Require two-factor authentication and disallow tokens" (trusted publishing keeps working; only tokens are shut out)
    • revoke the 30-day token on npmjs.com, and delete its line from ~/.npmrc
  • npm doesn't check the setting when you save it: a typo shows up only as a failed publish.
  • All three packages already exist on npm (next is 0.8.9 for each), which trusted publishing needs: it can't be set up for a name that was never published.

What stays the same.

  • spell publish itself: its checks, the three packages, one version, spell first.
  • next by default; only latest moves latest.
  • You can still run spell publish --dry-run on your laptop: it never publishes, so it needs no token.
  • You bump the kit's version and commit it to main before a run, as now: the workflow never changes the version.
  • Moving latest to a version already out (npm dist-tag add) stays a command you type, after an npm login: a 2-hour session is plenty for one command.

Risks, and what to check on the first run.

  1. spell-epic would fail its publish. With provenance, npm requires each package's repository to name the repo that built it, or it answers E422 ("repository.url ... expected to match") (one report).
    • spell and spell-ui on npm already name the kit's repo.
    • spell-epic@next names none: the plugin's own manifest still names its old repo, spell-app/spell-epic, and the published one drops it. Spell UI's folder manifest names its old repo too, though the published one is right.
    • So the plugin's published manifest has to name the kit's repo first.
  2. Publishing a .tgz. spell publish publishes the packed files, not a folder. Trusted publishing should take a tarball the same way, but npm's examples all publish a folder: the first run, under next, proves it.
  3. Making the plugin latest edits a file. Under latest, the publish rewrites the root marketplace file so epic points at npm's spell-epic, "to commit". In a workflow nobody commits it: the run should print it, or open a pull request, or you commit it after.
  4. A long run. The publish builds the declarations, the app's editor, three packages and two scratch installs, so it may take a while: give it its own time limit, like the checks' hour.
  5. No half-published versions. The publish stops at the first failed npm publish: spell could be out at a version whose spell-ui isn't. That's true today too; a re-run after the fix needs a new version, since npm never reuses one.
  6. The scratch installs need the network, which GitHub's runners have: --no-scratch is never needed there.
