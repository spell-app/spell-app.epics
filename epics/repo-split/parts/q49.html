How the kit is cut into packages so that every import reads @spell/..., with no folder moved. On npm a scoped name such as @spell/element is always a package of its own, so the kit can't stay ONE package (the one-package decision, Q35) and still be imported as @spell/element and @spell/util. Owen would notice it in every import line, and in seven small package files inside the kit's folders.

  • Seven small package files, one in each folder of src/: @spell/util, @spell/toolchain, @spell/server, @spell/cli, @spell/element, @spell/element-tools, @spell/test-helpers.
  • They're workspaces of the kit's one install, so yarn links each one into node_modules: nothing moves, and the link the install makes by hand today (J77) goes.
  • One version in all of them, bumped together: Owen's "shared version number with the rest of the kit" stays.
  • The kit's root package is named spell: the workspace root, the scripts, the commands.
  • The child repos stay one package each: @spell/ui, @spell/lang, @spell/brand, @spell/epic, @spell/app.
  • Cost: each folder lists its own dependencies; each folder's declarations live inside it (C18); the import lint rule, the esbuild resolver and the declarations build learn a package that is a folder of src/.
  • Why recommended: it's exactly the names Owen asked for, and the only shape that gives them without moving folders.
  • The kit's imports read spell/element, spell/util; the child repos are still @spell/ui ...
  • The least work: the one-package decision (Q35) stands, and the tools barely change.
  • But it's not what Owen asked: the kit's own imports aren't @spell/....
  • Imports read @spell/kit/element, @spell/kit/util.
  • Still one package, and scoped.
  • But every kit import is longer, and it isn't the @spell/element Owen wrote.
