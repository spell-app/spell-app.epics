What a state file could hold, and what it can't

  • It can hold anything that comes from the plan doc itself: the title, the phases, and the count of open and total items of each kind. For this epic it would read: 
    {
  "doc": "sha1:3f9c…",
  "title": "Review Review",
  "phases": { "done": 6, "total": 10, "active": "P7 · Bedtime And Isolate", "next": "P8 · Rewrite The Rest" },
  "items": {
    "question": { "open": 1, "total": 17 },
    "judgement": { "open": 21, "total": 37 },
    "issue": { "open": 3, "total": 6 },
    "caveat": { "open": 7, "total": 7 },
    "todo": { "open": 1, "total": 2 },
    "test": { "open": 13, "total": 13 }
  },
  "notReviewed": 44
}
  • It can't hold the things that change without the plan doc changing. /epics still has to look these up each time:
    • the session working on the epic and whether it's busy or waiting for your input: that's live, in Claude Code's own session files
    • the commits on the epic's branch that aren't in main yet, and the uncommitted files (git)
    • the marks you left on the page and not sent yet, and whether a review session is listening: those are in the inbox file, <name>.inbox.json
    So "waiting for input" in your list would come from the session, not from the state file.

Keeping it true

  • Every structured edit goes through one function, edit() in plan-doc.js: add, decide, phase, close, details, inbox apply and the rest. It already reads the whole doc, so writing the state file there costs almost nothing (PlanDoc.summary() already has the numbers).
  • But several things change a plan doc without going through edit():
    • Claude editing the prose by hand (the Rules allow it for the summary, Overview and item details)
    • the page's edit mode (the page server's PageEditor writes the file directly)
    • a git merge, pull or checkout: e.g. merging main into a worktree brings in its copy
    • yarn docs:update (link targets, formatting) and one-off scripts like the renames
  • So the state file has to carry a fingerprint of the doc ("doc": "sha1:…" above). Whoever reads it hashes the doc first (about 1 ms for 268 KB) and, if the fingerprint differs, reads the doc again and rewrites the file. Then it's a cache: edit() keeps it fresh, and anything else just makes the next reader rebuild it.
  • A fingerprint of the contents is safer than the file's modification time: copying a folder can keep old times on new contents.

Committed or git-ignored, JSON or JSON5

  • Git-ignored, like the inbox file: epics/*/*.inbox.json* is already in .gitignore. A committed state file would conflict every time two worktrees both changed an epic and merged, as the docs index (index.html) used to. It would also be stale straight after every merge, because merges don't run edit().
  • JSON, not JSON5. JSON5 allows comments and unquoted keys, which only help a file people write by hand, and nobody would write this one. json5 is installed (2.2.3, used by the app, lsp, spell, util and server), but not by the docs tools. Plain JSON needs no import: RunningEpics (the docs index's Epics cards, in the server package, which imports nothing) could read it with JSON.parse. The repo's other data files are JSON too (commands.json, <name>.inbox.json).
  • The name: <name>.state.json beside the doc, e.g. epics/review-review/review-review.state.json, matching review-review.inbox.json.
