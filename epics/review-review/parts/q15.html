• When the page's own file changes, the live client (packages/server/src/liveClient.ts) fetches the new version and fires a cancelable spell-server:change event on window (detail: { path, html, etag, reload() }). If nothing takes it, the page reloads as before.
  • The docs runtime (spell-doc-runtime.js wireLiveUpdate()) takes it and patches the page. It does the patching because only it knows what it built from the markup (contents, rail, counts, item filters, folds) and how to rebuild those; pages without the runtime (Spell UI's site, proxied pages) keep reloading.
  • The patch compares the source as the page LOADED with the new source, never the live page (which the runtime and the elements have added to). The runtime reads that baseline once at start, and trusts it only when its ETag is the one the page was served with.
  • Only what changed is touched: elements are matched by id, else in order by tag; a changed attribute is set in place, changed text replaces the smallest element that holds it, new elements are added folded as the reader would expect. Scroll, folds, open panels, focus and typed text survive.
  • After the patch the runtime re-wires (counts, item filters, contents and rail only when their entries changed, sticky lines when sections came in, code colors) and fires spell-doc:updated with the changed elements.
  • For agent C (runtime chrome): an element the runtime adds inside main should carry data-spell-added (or join ADDED), and the patch never calls wireFolds() again (that would refold link-opened sections on a plan doc). trackStickyHeights() is called again when sections are added; making it drop its previous ResizeObserver would stop a small leak.
