When Spell itself changes

Spell grows a phrase at a time, and a new phrase can take words a person already uses. It nearly happened when Spell learned play, and a person's to draw (a card) already loses to Spell's own draw. This page shows how Spell decides who wins, what's already planned for upgrades, and how the two styles, Spanish and synonyms multiply the ways a line can read.

Every result here is a real run of today's compiler, on the built-in examples or copies of them.

When Spell changes, a line can go wrong two ways:

  • An old wording leaves. The line stops parsing. The upgrade phase already plans for this.
  • A new reading arrives. The line still parses, but now means Spell's thing, not yours. Nothing warns, because nothing is wrong with the line.

A new reading arrives three ways:

  • a new built-in phrase uses the same words as one of your to lines
  • a new phrase reads words that used to be plain names: the second of the deck is its 2nd card, and the date words added the second of now (Date and time words)
  • a new synonym, style or language adds another way to read the same line

On 2026-11-06 Spell learned play and stop for sounds (epic data's T145). Their words are the words of actions programs already had:

  • FizzBuzz's play fizzbuzz
  • a solitaire's play from the stock
  • a clock's stop it

Their author made a project's own action of the same words win, with a level set by hand (Priority.overridable), and tested those three. At the ordinary level they would have tied with the program's action, and the order rules were registered in would have decided. Today Solitaire's game uses both, a few lines apart:

	...

	if it is face up or its pile is solitaire's stock
		play the card                // =>  this.play():  Solitaire's own action

It worked because one author thought of FizzBuzz. Nothing in Spell would have pointed it out.

When two rules read the same words, the parser keeps one (getBestMatch()):

  1. the higher level (each rule sets one, by hand)
  2. then the longer match
  3. then the rule registered first

"Upgrading Old Spell", planned, waiting for your Accept:

  • one list of old wordings, each deprecated in one Spell version and dropped in a later one
  • a yellow warning on each, with a "Fix it" button that rewrites it
  • the project file records the Spell version it matches
  • spell upgrade, the same rewrite as spell lint --fix, and an "upgrade on open" setting
  • no new Spell words: the version lives only in the project file

What it doesn't cover: a line that still parses but now means something new. It's no old wording, so no warning fires. The recorded version is the hook this page's shapes C and D would hang on.

  • Every example, guide and frozen test project is compiled and compared with its snapshot (spell content check). One snapshot per example shows which rule reads each line: a reading diff, for Spell's own projects, re-blessed by whoever changed the rule.
  • A test pins each collection's registration order; another pins every rule's level.
  • An analysis test, run by hand, recompiles every rule test and frozen project with and without one word (compileEverything()): the before-and-after harness a reading diff needs.
  • The editor's re-parse knows which rules changed and which lines they could match (ParseDiff).
  • spell translate check lists Spanish rules registered in a different order from English's: "a tie between two rules may break the other way".
  • Two styles. The outline and the sentences say the same facts in different words, and a test proves they compile alike. Every fact has two syntaxes, so twice the places a new rule can collide.
  • Synonyms. Spell reads 773 syntaxes on 496 rule classes today. By the same count the Spell README gave 619 on 407 on 2026-10-22: 154 new ways to read a line in four weeks. 95 rules have more than one way; the wording rule has 62.
  • Spanish (Encanto). 765 syntaxes of its own, and ties English doesn't have. para is both "to", an action's first line (para dibujar eso), and "for", a loop (<para cada artículo en sus artículos>). The census found 21 lines in the examples that both read; registration order picks the loop. In English, to and for never meet.
  • Spell UI's names collide differently in each language: Spanish's pila is Spell UI's stack and Solitario's pile (One word, two meanings).

How to measure it: the census, per language and per style, over the examples and their Spanish twins. Its numbers over time say whether the language is getting more ambiguous. Testing it all in each language is Testing it in many languages.

  • Rust's editions. A crate names its edition in its manifest (2015, 2018, 2021, 2024). Words like async and dyn became keywords only in a new edition, cargo fix --edition rewrites old code, and crates of different editions build together.
  • Go. A module's go line says which Go it's written for. Go 1.22 gave each loop pass its own variable only in modules that say 1.22 or later: a meaning change, gated by the project's own version. go fix rewrites old APIs.
  • Python's soft keywords. match and case (3.10) and type (3.12) are keywords only where their statement can start, so old code using them as names runs unchanged.
  • JavaScript. "Don't break the web": Array.prototype.flatten was renamed flat in 2018 because an old library, MooTools, had its own flatten on many live pages.

What they teach: a new word doesn't take an old name (Python, JavaScript), or applies only to projects that say they're ready (Rust, Go); and a tool does the rewrite.

A change to Spell's rules compiles every example, guide and frozen test project, in both languages, with and without it, and lists each line now read by a different rule. It can't merge until each line on the list is accepted.

The Spell version a project records decides which readings it gets. A new reading applies only to projects at or after the version it came in, as Go's loop change did.

  • The person's program never changes meaning until they upgrade it, and the upgrade lists what changes.
  • No agent.
  • Cost: big. The parser carries both readings, every new rule says its version, and the tests run per version.
  • The census script, made a check, run over every example in both languages.
  • Its numbers kept on a page, by language and style, so a growing tangle shows.
  • A change that adds an order-settled tie whose two readings compile differently fails.
  • No agent. 1-2 days. The parser's "collect what every rule was waiting for" mode is the pattern to copy.
  • Everything above works with no agent: the parser knows which rule read each line.
  • An agent can word a reading diff for people: the release notes, the upgrade message, a guess at which meaning a person's line wanted.
  • Cost: one cheap-model call per release or per upgrade, a few cents; optional.
  • It asks nothing new of epic agents-in-spell beyond reading the diff as a look-up.
  • A diff needs the old reading. On a person's machine that means the old parser, or a record kept from their last compile.
  • "Yours always wins" undoes deliberate choices. draw the card draws the card's element on purpose, not a person's to draw (a card).
  • Ties settled by order are invisible. The order is pinned; what depends on it isn't.
  • Spanish can break a tie the other way. Its rules may be registered in another order; spell translate check flags the order, not the lines it changes.
  • The grammar grows fast. 154 syntaxes in four weeks: any check that needs a person to look at each change has to be cheap to look at.
