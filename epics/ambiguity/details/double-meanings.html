One word, two meanings

Today a word can mean your thing in one line and Spell UI's or a library's in the next, and nothing says so. Adding a three-line library to Solitaire's card turns every heart black, and Spell's checks still pass. This page shows where that happens, what Spell already catches, and the shapes a fix could take.

Every result on this page is a real run of today's compiler, on copies of the examples in a scratch folder.

A word gets a second meaning in Spell three ways today:

  • A tag in a drawing. <card> is your own card if you declared one as a view, and Spell UI's card otherwise.
  • The words is a. it is a heart asks about the card's suit, unless something called a "heart" exists anywhere in the project: then it asks whether the card is one.
  • A library. Importing another project brings its types and its quoted phrases into every file. Either of the two above can then flip, in lines nobody touched.

In each case the new meaning wins silently:

  • it compiles, and spell lint passes
  • the editor shows no warning
  • only a test, if there is one, notices that the program now does something else

Solitaire's card is a view: it draws itself. Spell UI also has a card, a box with a header and a description.

In a drawing, a bare tag means the program's own view first, then Spell UI's component of that name (componentTagFor()). So what <card> means depends on a line far away:

The card's own line The same drawing line Compiles to Draws
a card is a thing <card>Hello</card> h("ui-card", "Hello") Spell UI's card
a "card" is a view <card>Hello</card> h("cardview-card", "Hello") the program's own card
  • Turning a thing into a view later changes every <card> in the project, with no message.
  • <ui-card> still reaches Spell UI's card beside your own, but the examples' rule is to name Spell UI's components bare.

  • Spell UI has 157 bare names a drawing can use. Many are everyday nouns a program wants too: card, item, list, column, row, table, step, message, comment, event, title, label, link, page, section, term.
  • At least 9 of the 33 examples, and 6 of the libraries, declare a type named like one: Solitaire's card and column, Shopping List's item, Recipe Cards' step, Bill Splitter's and Checkers' table, Star Wars' card, section and title, Public Servers' author, link, label and comment, Sign-Up Sheet's and Picnic Letter's message, the games library's card, and the org apps' message, event and term.
  • Recipe Cards draws Spell UI's own <card> and <column>. If it ever declared a card view, or imported the games library's card, its recipe card would draw as a playing card.
  • Each language collides on its own words. Spanish's Spell UI card is tarjeta, so Solitario's carta is safe. But Spell UI's stack is pila and its grid column columna, which are Solitario's pile and column (more on Testing it in many languages).

Solitaire's card asks about its suit with it is a heart. Spell reads that as "its suit is hearts", because hearts is one of the suits and no type is called a heart. A type always wins over a value, on purpose (is_listed_value).

So here is a library with nothing to do with cards:

Valentines, a whole library · 3 lines 
a "heart" is a thing
	-- a valentine heart, with a message on it
	its "message" is text

A copy of Solitaire's card file that imports it compiles and lints clean. Three lines now mean something else:

"♥" if it is a heart this.suit === "hearts" this instanceof Heart
if its card is a heart this.card?.suit === "hearts" this.card instanceof Heart
  • Every heart is now black, and drawn as a spade.
  • spell compile and spell lint both say ✓.
  • Only the card's own tests catch it.
  • The same would happen to it is a king in Solitaire's auto play and its column, if anything declared a king.

Recipe Cards imports Shopping List's item, to send ingredients to its list. Shopping List's item is a view.

  • So in Recipe Cards, a menu's <item> is no longer Spell UI's menu item: it's Shopping List's item.
  • Nothing in Recipe Cards draws a menu today, so nothing shows it yet.
  • The tag it writes is named for Recipe Cards, while Shopping List's item draws under Shopping List's name. So the menu likely draws an element nobody defined. Not checked in a browser: it looks like a second bug.

  • Everything it provides, unless the project file names a list: the default is every name ("*").
  • Its types, their properties, its constants, and its quoted phrases, each as a rule of its own.
  • A type it shares with the project, or with another import, is an error: 'cards' declares 'Card', which it also imports from '@spell/library/games/cards'.
  • A quoted phrase, or a value word like heart, is never checked: only types are (checkImportClashes()).
  • A type can be renamed as it comes in, in the project file: "import": ["Heart:Valentine"]. Only a type, and only once you know you need to.

Spell already guards several double meanings. Each was added by hand, for one case, when someone tripped on it.

Double meaning What Spell does Its words, today
a local named like a property warns, where it's made and where the X reads it Here "score" hides the property "score": use another name, or say "its score" for the property
the name of the character's friend, when both readings work reads the nearest, and warns Read as the character's friend's name; the character has a name too: for that one, write "the name of the character"
- it is red, when two properties list red refuses red is a value of both its color and its suit: say which, "its color is red"
a type declared twice, by the project and an import refuses the import 'cards' declares 'Card', which it also imports from ...
character, a word programs want freed: one letter is a letter or char --
play the card beside Spell's own play "card slide" the program's own action wins -- (see When Spell itself changes)
it is a heart: a type, or a suit the type wins, silently --
<card>: your view, or Spell UI's your view wins, silently --
a local named like a value: Solitaire's test says set the queen to a new card whose rank is queen, and Checkers' set man to ... beside the rank man the local wins, only because its rule was registered first; no warning --
a quoted phrase in the other form, (suit) against (suits) reads as something else: card === "spades".queen -- (the "sharp edge" in the Spell README)

And the tools a person could ask:

  • VS Code's hover shows the JavaScript a line compiles to, so this instanceof Heart is visible there.
  • The editor app's hover leaves compiler words out, so a beginner there can't see it.
  • spell explain heart in Solitaire says Nothing called 'heart', though it is a heart reads it.
  • spell explain card lists Solitaire's card, and never mentions Spell UI's.
  • The parser picks one reading and throws the others away; nothing reports a tie (getBestMatch(), whose note still says TODO: match all valid choices).

Spell's docs, hovers and errors have double meanings of their own, which a beginner meets before any line of theirs:

  • "Alias" is a quoted phrase that teaches Spell new words (it "is a face card"), but Spanish's alias is a type's short name (, alias "carta", English's aka), and in the code it's also the list of places a rule may stand.
  • One idea, several names: a to line is an action, a method, a phrase, or your "to rule".
  • A template is a type in the code; Spell UI's pieces are components, elements and widgets.

Settling them is word work, not code: it belongs with the guides (Guides for people and agents).

  • Python warns against from library import *: its own style guide says it leaves readers unsure which names are present. Spell's imports bring every name by default.
  • Rust lets two wildcard imports share a name, and refuses only a line that uses it, naming both. The error is where the confusion is, not where the import is.
  • AppleScript puts an app's words in scope only inside its tell block, and lets you write |name| with bars when a word clashes with a term. Its scripters still tripped on terms added by scripting additions, which changed scripts that never mentioned them.
  • Inform 7 asks the player, never guesses: "Which do you mean, the red ball or the blue ball?". Its Index lists every kind, phrase and definition a project knows, including those from extensions.
  • TypeScript's language server answers "which one?" with hover and Go to Definition on every name. Spell's hover does this for most words, but not for a tag's two meanings, and not in plain mode.

When two readings of the same words would compile differently, Spell keeps the usual winner and says so, as it already does for the name of the character's friend.

  • No agent. Works in the editor, VS Code and spell lint.
  • The parser has a mode that collects what every rule was waiting for, for completion (Expectations.collect()): a "second readings" collector could copy it.
  • Cost: the parser keeps the runner-up when it reads the same words, on its busiest path; it needs the speed test.
  • Most ties compile the same either way: the warning must only fire when they don't, so both readings are compiled. The census on When Spell itself changes counts them.

If you want the choice in Spell itself, not the project file, a new phrase is needed. Two proposals, each with its own double meaning:

Proposed, not in Spell Its own double meaning
call Valentines' heart a "valentine" call already means running a program's own code: call native copyText
<card from Spell UI> from reads as an attribute named "from", as suit=clubs does
  • No agent. The quick fixes are the cheap part: each is a rewrite to a form that exists.
  • The language epic's upgrade phase chose "no new Spell words, the project file holds it" for a project's Spell version: the same choice fits here.
  • Everything above works with no agent: the parser knows both readings, and the fixes are rewrites.
  • An agent adds judgement: reading the flagged lines and the comments around them, and guessing which meaning the person wanted ("this is a card game: you meant the suit").
  • Cost: one small call to a cheap model, only when the check finds something; a fraction of a cent to a few cents (prices on epic agents-in-spell's models page).
  • What this epic would ask of epic agents-in-spell: only that its look-ups can read the clash list, as they would read spell explain. No new plumbing.
  • Most double readings are harmless. Across the 33 examples the parser settles about 6,000 ties by registration order alone; 5,669 of them are a property's name, which two rules both read for the same job. Telling the few harmful ones apart means compiling both readings.
  • The parser throws the loser away. Keeping it costs time on the hottest path, line by line, as you type.
  • "A type wins over a value" is on purpose. A warning would fire in Solitaire the day anyone imports a library with a king or a heart in it; the fix has to be one click.
  • Words grow on both sides. Spell UI adds components, libraries add types, and each language collides on its own words.
  • A project's library isn't in the repo. Spell can check its own examples before a release, never a person's mix of libraries: the check has to run on their machine.
