Our elements send hyphenated events (ui-change, ui-toggle ... about 50 of them), and from rc.17 a Solid page has no way to listen for one in JSX.

  • Every one is sent from ONE place: UIComponent.send().
  • onUIChange listens for uichange: Solid lowercases what follows on, and keeps no dash.
  • rc.14 made a lowercase on* a plain attribute.
  • rc.17 made on:ui-change a compile error. It's an error on <ui-select> too, not just on native tags: checked with both compilers.
  • Today the only way is a ref that calls addEventListener.

Owen's three questions

  1. Does it have to be Babel? No.
    • Our builds compile JSX with Solid's NATIVE compiler (Rust, @solidjs/compiler), the Vite plugin's default. Babel is only its escape hatch (compiler: "babel"), which we never set.
    • A compile-time rewrite could be a Babel plugin handed to the Solid plugin (its babel option). That brings back a whole Babel pass over every file: the plugin's own docs say native mode is "normally fully Babel-free" until you do.
    • Or our own Vite pre-pass, beside the decorator one, with a JSX parser. Either way it's a compile step we'd own.
    • And options A and C below need no compile step at all.
  2. Are we using Babel anywhere else? No.
    • The only mention in our code is a comment in the decorator pre-pass (standardDecorators()) saying why it uses esbuild rather than SWC or Babel.
    • Babel is installed only because the Solid Vite plugin depends on it, and the kit pins @solidjs/babel-plugin in its resolutions to match.
  3. Can we make on-ui-change work? Yes, at run time, with no compile step (option C). But Solid's dev build warns about it, and there's no switch to quiet that.
    • Solid sets on-ui-change={f} with setAttribute, on every path: plain JSX, a spread, h(), a reactive value.
    • So our element's own setAttribute() sees the FUNCTION, before it would become text, and can turn it into a listener for ui-change.
    • The catches are in option C's card.

What the compiler emits

Both compilers emit the same code, character for character apart from formatting.

  • onUIChange: an INLINE addEventListener("uichange", f), no runtime call in between.
  • on-ui-change: the runtime's setAttribute, with the function as the value.
  • prop:onUiChange: a property, el.onUiChange = f.
  • A spread: the runtime's spread(), which sorts the keys the same way (assignProp()).
  • The template's flag 1 marks a custom element: it's made with document.importNode, which upgrades a DEFINED element before any prop is set.

_$setAttribute(_el$2, "on-ui-change", f);

_$addEvent(_el$, "uichange", c() ? f : g);
_$effect(() => c() ? f : g, (_v$) => { _$setAttribute(_el$, "on-ui-change", _v$) });

Where JSX is compiled

Every Solid JSX file goes through ONE compiler: the Solid Vite plugin, in native mode.

  • The kit's element settings (elementBaseConfig()): Spell UI's library, its docs and tests, every component pack, spell-epic's and the brand's packs.
  • spell-app's own settings (vite.shared.ts) and Spell UI's framework host page (HostApp) call the plugin themselves.
  • Vitest runs the same Vite settings.

What a compile-time rewrite (option B) would MISS:

  • spell-lang's compiled spell: no JSX, it calls Solid's h() (drawing.ts), which goes through assignProp() at run time.
  • A spread whose keys aren't known until it runs ({...props}).
  • Anyone using Spell UI from their own Solid build: they'd need our plugin too.
  • And it would need wiring into all three Vite settings above. The esbuild builds (spell-epic's extension, the brand's design bundle) compile no Solid JSX, so they need nothing either way.
