Edits in the side bar change only the running app, with no undo, and are lost on restart.
  • A change in the side bar shows at once, and goes into the file's text, touching only those characters.
  • The file's tab shows its unsaved dot, and Save saves it.
  • One source edit, for .spellml first and then .spell, taking the notebook's exact-span logic.
  • The file owns its text, so this works with the code editor not loaded; with it loaded, the edit goes through it.
  • The editor keeps its own history on the shared undo stack, so a change to many things is one step; ⌘Z goes by focus.
  • Every field has a home, and acts on it: written on this tag, not written yet, the type's default, worked out, an expression, or set while running.
  • After a base edit, things still holding the old default take the new one.
A side-bar change becomes a small edit to the file's text. The editor gets its own history, and every field knows its home.

Source Places counted the built-in projects: 64% of the values holding something are on things made in a loop, against 18% written on a tag or as an expression. So this phase builds edits to the type's default first, then edits to a tag. The numbers are on Source Places.

  1. One source edit. "Set this attribute on this tag to this value", worked out from the parser's exact spans, for .spellml. It has ONE home, SourceEdits, which returns TextEdits, the shape the language server already uses.
    • The notebook's moved(), its deleted() and its add come from their two files into it, so Add And Move uses them too.
    • It's a small file in the language server's folder that loads neither the service nor the code editor, because a side-bar edit must work with the code editor not loaded.
    • It uses the file's own language's words, and keeps quotes as written.
    • .spell follows, from its parse positions.
  2. Into the file.
    • Code editor not loaded: the same steps typing takes without it, which already exist: the file's text, a re-parse, the unsaved dot, kept in the browser on the preview, then a compile.
    • Code editor loaded: through its model as an edit. Writing the file directly would wipe its typed undo.
  3. The editor's history. One generic UndoStack on editor.
    • Each step holds a meaning: which home, the value before and after. Undo finds the home again from the current parse, so typing elsewhere doesn't break it.
    • A drag on a slider folds into one step, by its target. A change to many things is one transaction, which is your nested undo.
    • If the home is gone, because someone deleted that tag, undo says so and skips the step.
    • A step can also hold a whole file's text before and after, for what has no one meaning: the notebook's steps, and Change This's.
  4. ⌘Z goes by focus, and the Edit menu's titles follow it ("Undo Change Suit"):
    • In the code: the code editor's own undo.
    • In the running app, in Run: the program's own undo, as today.
    • Anywhere else in Edit: the editor's history.
    • All of this is decided in one place, the undo entry of the editor's list of keys.
  5. The notebook joins the same history.
    • Its add, move, delete and lock become steps here, holding the text and the cells' keys as they do today, and its private list goes.
    • Its own ⌘Z registration goes too: ⌘Z on a notebook page reaches the editor's history.
    • Typing in a cell keeps that cell's own undo, as today.
    • It keeps today's limit: undoing an add puts back the whole text, so typing done after it goes too.
  6. Every field acts on its home: in place, added to the tag, the type's default, a link to the code, or opening the code. The side bar's write stays as it is, for the instant change, and onWritten adds the source edit.
  7. Base edits show. When a recompile carries things over, a value still equal to the old default takes the new one.

Checked by: tests that an edit changes only its characters, with the code editor loaded and not; undo after typing elsewhere; a step whose tag was deleted; a Spanish file keeping its words; a notebook's move and lock undone by ⌘Z, and the page undoing in the same order as before; in a browser, change a tag's value, save, reload, and it's still changed.

Left out: adding, moving and deleting tags (Add And Move); a change to one thing among many made in a loop (This Or All); undo across a reload.

  • Where to see it: the Inspector, with Solitaire's clubs foundation selected: change its suit, and the file's text changes with it, touching only those characters. The tab shows its unsaved dot, ⌘Z and ⇧⌘Z work, and Save saves it. It all works with the code editor not loaded.
  • Before and after, in Solitaire.spellml: suit = clubs becomes suit = hearts.
  • Undo still works after typing elsewhere in the file. If the text it changed has gone, it says so and does nothing.
  • Changing a type's default also changes every thing still holding the old value, and undo puts them back.
  • Rough: most of what's on screen in Solitaire still can't be saved, because cards come from suit = the suit in a loop. The card says why, with "Show the code". This Or All takes this up.
  • Not tried: Spanish beyond parse tests, a real slider drag, real typing in a field, the static build, and a real Mac.
