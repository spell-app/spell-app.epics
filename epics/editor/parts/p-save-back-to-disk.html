Owen, 2026-11-19: “`it can only ask after a click` -- that should include a menu item choice, optimally a command key, etc. This can be tricky to plumb through. In another app, I had to go through a login step before saving because marketing. I had to show a ‘Welcome X’ alert with ‘Save File’ to get around this.   • The browser's rule is “a recent person action”, not only a click: a key press (⌘S) and a menu item chosen by mouse or key both count, as long as the ask starts while that action is still fresh (a few seconds in Chrome).
  • What breaks it is anything slow in between: a sign-in, a network wait, a dialog. By the time it's done, the action has gone stale, which is why the “Welcome X: Save File” alert was needed.
  • The workaround to try first: ask for the file permission AT ONCE, the moment the Save command starts, before any sign-in or other wait; the slow steps then run with permission already granted. The test page checks whether the permission, once granted, survives the slow step.
  • The plumbing: every way into Save (button, menu item, ⌘S, a Spell save ... back to its file run from a click) calls one Save entry that asks first, then awaits the rest. A Save started with no person action (a timer, a when line) never asks: it saves to this device and shows a “Save to file” button instead.
  • Fallback when the ask must come later: the same one-button note as Q70's, so the person's click on it is the fresh action.

The spike, run headless in Chromium, Firefox and WebKit (Playwright), against the browser's own private files, which behave like a picked file's handle for everything but the permission prompts.

  • Today's Chromium HAS the change observer (FileSystemObserver), and the file picker; Firefox and WebKit have neither, so they take the download fallback, as planned.
  • Modified time and size are enough: a rewrite of the same size a few milliseconds later still changes the modified time, so no hash of the contents is needed for the check before each save.
  • Moved, renamed or deleted: reading through the kept handle fails with "not found", as the web said.
  • A new file at the old name: the kept handle reads THAT file, as the web said; its modified time differs, so the check calls it changed by someone else.
  • The surprise: in Chromium, SAVING through the kept handle after a rename makes a new file at the old name, with no error. So the place reads the file first, before every save (the check), and stops at "not found" before it ever writes: the plan already does the check; it now also guards this.
  • A handle is kept in the browser's database and comes back after a reload in all three.
  • A file's contents must be read at once: Chromium refuses to read a File object after the file changed.
