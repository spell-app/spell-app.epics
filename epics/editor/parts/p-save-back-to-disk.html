  • Then: an app whose data is a file on your computer opens it once, picked or dropped, and every later save goes back to that same file: no download, no second copy in your Downloads folder.

  • The tricky cases, each with what the app does:
    • Reloaded: Chrome usually forgets you let the app use the file; if it still remembers, the app reads the file quietly; if not, you see your data from the copy on this device, and a short line, “Reopen recipes.json to save to it”, with a Reopen button (Q70).
    • Permission taken away (in Chrome's site settings): the same line as after a reload.
    • Changed by someone else (another program, another tab, a sync like Dropbox): the app notices before it saves, and never silently writes over their change: it asks you to keep theirs (your unsaved changes set aside on this device, not lost), keep yours, or keep both (yours saved to a new file you pick) (Q72).
    • Moved, renamed or deleted: the app can't find the file any more, and says so in plain words, “Can't find recipes.json. It may have been moved, renamed or deleted.”, with two buttons, Find it and Save as new file; your data and unsaved changes stay from the copy on this device meanwhile (Q73).
    • A different file now sits at the old name: the app treats it as changed by someone else, not as its own file.
    • Changed while the app is open: the app checks before each save, and when you come back to its tab; where Chrome has the change observer, at once. Then a line offers “This file changed. Read it again?” (Q74).
  • In Safari and Firefox, which can't save back to a file, the app still works: your changes are kept on this device, and saving hands you the file to download, with the same name; the first time, one line says it lands in your Downloads folder, and why (Q71).
  • Spell has words for it, once you've agreed them (Q67): a place that is a file on your computer, and the actions to open one and save back to it.
  • It's one more kind of place, beside a web server, a sheet and a data folder: the same reading, saving, pending changes and copy on this device every place has (Q68).
  • A handle can be kept in the browser's database (IndexedDB), and comes back after a reload: Chrome's File System Access article. Spell's DatabasePlace already keeps one as it went in.
  • After a reload its permission is usually "prompt" again; asking needs a click, and Chrome 122+ can offer "Allow on every visit": Chrome's persistent permissions post, MDN queryPermission(), Transloadit's walk-through.
  • A handle to a file on disk names its PATH, not the file itself: after a move, rename or delete, reading it fails with NotFoundError; the standard's wording is still settling: whatwg/fs #59, whatwg/fs #14, MDN getFile(). So a new file at the old path would read as "the same file": the spike checks this.
  • A save writes a temporary file beside it, and swaps it in only when the save finishes, so a half-written file never shows; two tabs saving at once: the last one wins, unless the save asks for an "exclusive" lock: MDN createWritable(). Nothing in the API stops a write over someone else's change: the app has to compare the file's modified time and size (or its contents) first.
  • isSameEntry() tells whether two handles are the same file: a dropped file the app already has, say: MDN isSameEntry().
  • A change observer, FileSystemObserver, tells a page when a file changes, moves or disappears; Chrome tried it out from 129 to 134 and meant to ship it in 133, but it's still marked experimental and not standard: MDN FileSystemObserver, its change records, Chrome's origin trial post, its Intent to Ship. The spike checks whether today's Chrome has it.
  • Picking a file with a handle (showOpenFilePicker()) is Chrome's and Edge's only; Safari and Firefox give a plain file, which can't be written or kept: MDN showOpenFilePicker().

Owen, 2026-11-19: “`it can only ask after a click` -- that should include a menu item choice, optimally a command key, etc. This can be tricky to plumb through.   • The browser's rule is “a recent person action”, not only a click: a key press (⌘S) and a menu item chosen by mouse or key both count, as long as the ask starts while that action is still fresh (a few seconds in Chrome).
  • What breaks it is anything slow in between: a sign-in, a network wait, a dialog. By the time it's done, the action has gone stale, which is why the “Welcome X: Save File” alert was needed.
  • The workaround to try first: ask for the file permission AT ONCE, the moment the Save command starts, before any sign-in or other wait; the slow steps then run with permission already granted. The test page checks whether the permission, once granted, survives the slow step.
  • The plumbing: every way into Save (button, menu item, ⌘S, a Spell save ... back to its file run from a click) calls one Save entry that asks first, then awaits the rest. A Save started with no person action (a timer, a when line) never asks: it saves to this device and shows a “Save to file” button instead.
  • Fallback when the ask must come later: the same one-button note as Q70's, so the person's click on it is the fresh action.
