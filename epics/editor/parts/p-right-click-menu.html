One menu on a part and on its Views row: Cut, Copy, Paste, Duplicate, Delete, a line, then Show in Code, Inspect. It selects what you clicked first. A running program's own right-click is left alone.
  1. One way to open a menu where you clicked. Add And Move builds a small right-click menu on the app's parts, placed by hand. A running program's context-menu= places its own the same way, so that's two copies, and neither flips at the window's edge. <ui-popup> grows the one way to open at a point: in the top layer, flipping at the edges, with arrow keys and Enter, Escape and a click away closing it, and focus going back. Both menus move onto it. No new widget.
  2. Shift, as Owen asked: One Selection's rule changes in one place, ListSelection. In a list, Shift follows Owen's Finder model, which he says we can tune:
    • A plain click selects one, and sets the pivot, the fixed end of a range.
    • Command-click toggles one. Adding moves the pivot to it; taking the pivot away moves it to the last one still selected.
    • Shift-click selects the run from the pivot to the clicked item. Shift-clicking again swaps that run for the new one, and the pivot stays. Items selected with Command outside the run are kept.
    Outside a list, such as parts on the app's page, Shift toggles the part, as Command does. Checked against a real Finder window by hand, in a manual test.
  3. The items, growing Add And Move's menu rather than a second one. In order: Cut, Copy, Paste, Duplicate, Delete, a line, then Show in Code, Inspect. The first five are the same actions and keys as the Edit menu, one copy. Each of them is one source edit and one undo step, as Add And Move builds them.
  4. Inspect and Show in Code. Inspect opens the Inspector if it's closed and shows the selection in the properties card and the tree, with Inspect app off and staying off. Show in Code goes to where the part is written, using Source Places' marks.
  5. What's greyed, each with a tooltip saying why.
    • Inspect: never.
    • Show in Code: when nothing in the source made it, such as what a widget drew.
    • Cut, Duplicate and Delete: for a part made in a loop, or by a widget, or the app itself.
    • Copy: when there's no source to copy.
    • Paste: when nothing's been copied, or the part can't hold it.
  6. What's selected. Outside the selection, the part is selected first, replacing it. Inside it, the selection stays, and the items act on them all. On the app's background: Inspect, for the app, and Paste.
  7. The Views tree. A right click on a row does the same, with the same menu, through <ui-tree>'s own row events. A row for something not drawn offers what applies to it.
  8. Where the browser's or code editor's own menu stays.
    • In the code: the code editor's own menu, unchanged. Following a line to its part is Code Follows Along's.
    • In a field you can type in: the browser's own, for spelling and paste.
    • Anywhere else in the panels: nothing new.
    • Shift-right-click on a part: the browser's own, so its Inspect Element stays reachable.
  9. A running program. In Run, the editor adds nothing: the program's context-menu=, its right-click handlers and the browser's own menu all work as they do on its own page. In Edit, the editor's menu wins on a part, so a program's menu is tried in Run.
  10. Mac and Windows. The right button opens it on both. On a Mac, Command-click adds to the selection and Control-click is a right click; on Windows, Ctrl-click adds. On Windows, the Menu key and Shift+F10 open it on what's selected. Keys show as ⌘ or Ctrl.
  11. Texts and docs. Show in Code and the tooltips in English and Spanish; the popup's docs page and vocabulary; the app's README.

How it's checked: real right clicks, headless, on a foundation, a card made in a loop, a Views row and the background, reading what's enabled and each result in the file. In Run, a program with its own context-menu= still shows it. A menu opened in each corner of the window stays inside it.
