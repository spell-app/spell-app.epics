A change in the side bar becomes a small edit to the program's text, as if you had typed it. That's what makes the editor the main way to build an app, rather than a toy beside the code.

What happens when you change a field:

  1. The running app shows it at once, as it does today.
  2. The same change goes into the file's text, touching only those characters.
  3. The file's tab shows its unsaved dot, and ⌘Z takes the change back.
  4. Save saves it. The program compiles again in the background, which confirms it.

How it's built, on what exists:

  • One source edit: the shape the language server already uses, a list of "replace this span with that text". The notebook's exact-span logic moves into it, for .spellml first, then .spell.
  • One undo: edits go through the code editor's own model, so typed and side-bar changes share ⌘Z, the unsaved dot and Save. No second undo stack.
  • One map: the compiler marks each drawn element with its place in the source. That replaces today's best guess, and SourceMarks stays the only map.

Every field has a home, and the side bar shows which:

Where the value comes from What an edit does
Written on this tag Changes it in place
Not written yet, on a tag in the source Adds it to the tag
The type's default Changes the default ("All cards")
Worked out by the program Read only, with a link to the code that does it
Written as an expression, {...} Opens the code
Set while running, by the program Offers the type's default, or the code

The two risks:

  • Many things have no tag of their own. Solitaire's cards are made in a loop, so "this card" has nowhere in the source to go (Q7). The first step counts how often this happens across the built-in examples, before the design is fixed on it.
  • A base edit can look like nothing happened. A recompile carries the running things' values over, so they'd keep the old default. Things still holding the old default must take the new one.
