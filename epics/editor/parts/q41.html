For the Step Debugger phase, right after P32 · Spell Console. It decides how "pause inside a method" works at all.

The problem: the running app and the editor are one page.

  • The app runs inside the editor's own page, in a <spell-viewer>, not in a window of its own.
  • A page does one thing at a time. If the app truly stops mid-method, the browser's way, the editor stops too: no highlighted line, no buttons, no values to show.
  • The good news: every line of the running code already knows which Spell line it came from (the source map the editor uses to follow along), so any of the three can show the right Spell line.

The three ways, each for a breakpoint in move a card to a pile:

  • A, each line waits its turn (recommended): while debugging, the app runs a debugging build of its code, where each Spell line first asks "may I go on?".
    • At a breakpoint, the answer is "not yet": that method waits, the rest of the page (the editor) carries on, and Step Over says "go on" for one line.
    • What you'd see: everything in the goal, in the editor, live, with the real game.
    • The catch: to wait, a method has to be able to pause, so in the debugging build every method becomes one that can wait. Things that must happen at once (drawing the screen) could show half-done while paused. The biggest of the three to build.
  • B, the browser's own debugger: a breakpoint in the editor becomes a real one in the browser's developer tools, which already show Spell lines through the source map.
    • Small to build, and exact.
    • The catch: you step in the browser's developer tools, not in the editor; the editor freezes while paused; and none of it works in the VS Code runner the same way.
  • C, record, then step through the recording: the method runs at full speed once, noting each line and its values; then you step through what it did, forwards and backwards.
    • Safe: nothing ever freezes, and you can step backwards.
    • The catch: it isn't paused for real. By the time you look, the move has already happened in the game, and you can't change a value mid-way to see what would happen.
  • The compiler gets a debugging build: each statement first asks the debugger whether to go on, at the place its source-map mark goes today.
  • The app runs that build only while debugging is on; the shipped code never has it.
  • The editor stays live while the app is paused, so the highlight, buttons and values all live in the editor.
