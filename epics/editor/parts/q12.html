You asked us to think about read-only or hard-to-change data from a back-end, which epic data is working on. That epic is still at its Overview, and its compiler already plans to refuse a write to read-only data.

Say a list of orders comes from a REST service, and you select one row and change its total. That isn't a code edit at all: the code says only where the data lives.

  • The field is read only and says where it comes from ("from orders"), with a link to the line that declares it.
  • The row's look still edits, through "All rows", as a loop-made thing does.
  • Nothing can damage real data while designing.
  • Where the data allows writes, the side bar writes them to the back-end, with a clear mark.
  • Handy for a file or a sample, but a slip in the designer can change real data.
  • While designing, a read-only or slow source can be swapped for an editable sample, so a newcomer can see and shape it with no back-end.
  • The nicest in the end, but it needs epic data to offer samples first.
  • This epic adds one row to the table of where a value comes from.
