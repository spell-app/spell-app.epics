Of the 312 parts: 171 have a place of their own, 122 are things made in a loop, and 19 were made by a widget, with no tag.

What it adds up to:

  • Expressions don't block this. 50 of the 228 values written in the source are expressions, 22%. So the promise of editing without code stands, and there's no stop.
  • Loops are the biggest group of values: 809 of the 1,273 values holding something, 64%. By part it's 45%, under half, and it's concentrated in the programs that deal or list things: Solitaire, Solitario, tic-tac-toe, TaskList, ListaDeTareas.
  • Adding to a tag is the widest open door: 1,824 fields are on a part with its own tag, not written yet. Those are every attribute a widget could take.
  • No built-in project here keeps its data in a place, so the count has no "from data" values.

Limits of the count:

  • "Set by the program" includes values a type's create() sets, since nothing else separates them. The count found no value still at a declared plain default, so it doesn't split out "the type's default".
  • Spanish attribute words are matched by value, not by name, so a few could land in the wrong column.
  • 7 of the 12 guides were run. fizzbuzz has no parts at all, so it counts in the 20 and has no row.
  1. Count first, with a small headless script. It runs each built-in example, English and Spanish, selects every part, and sorts every field by its home:
    • written on its own tag
    • its tag is in the source, but this field isn't written yet
    • made in a loop: its tag is shared, or it has none
    • the type's default
    • worked out by the program
    • an expression, {...}
    • set while running
    The table goes into this phase's Done.
  2. What the count could change:
    • Most things loop-made: This Or All starts on "All", and Sidebar Writes Source builds default edits before tag edits.
    • Most editable values are expressions: the side bar can't edit much as it stands, so I stop and bring you the numbers, because that changes the promise of editing without code.
    • Otherwise both go ahead as written.
  3. Mark what's drawn. While the editor compiles, each drawn tag's h() call gets its place in the source, from SourceMarks. Each thing made by add a new card gets that statement's place.
  4. Published output stays the same. The marks are on only in the editor's runs, so compiled code and the snapshots don't change. A test says so.
  5. After a recompile: the marks are simply made again. A selection is found again as it is today, and reads its new place.
  6. The Inspector reads the mark, and the best guess in InspectorSource goes, with its "Fine as it is" line in the coherence catalog. Rows of one list all point at their one tag, as they should.

Checked by: a test selecting elements in Solitaire and Solitario, and finding the right tag; the parser speed test on the diff and on HEAD.

Left out: changing anything in the source, which is the next phase; reading the maps back for code mode (Code Follows Along).
