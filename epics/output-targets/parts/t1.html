Added 2026-10-06 (Owen): an EARLY phase of the Python epic, "Lists Start at 0". Python developers expect the first item at position 0; spell counts from 1.

  • A per-project setting, project.json "listsStartAt": 0 (default 1), applied when COMPILING: @spell/core stays 1-based, the one canonical form, and a 0-based project's numeric positions are shifted as they're written
    • item n of the deck => spellCore.getItemOf(deck, n + 1)
    • the position of the card => spellCore.itemOf(deck, card) - 1
    • ranges, remove item n, add ... at position n the same way (about 50 rule sites through 7 core helpers: getItemOf, itemOf, rangeBetween, rangeStartingAt, removeItemOf, removeRangeBetween, addAtPosition), and a loop's position
  • Ordinal words don't change: "the first card", "the last card" mean the same in both
  • Libraries keep working: a 1-based library imported into a 0-based project talks to the same core
  • NOT a runtime flag (spellCore.INDEX_BASE): one core serves every project in a program, so a library would silently read the wrong item
  • The Python writer writes native 0-based indexes; ranges stay inclusive in spell, so it adds 1 to a slice's end
  • To decide in the epic: -1 still means last in a 0-based project (Python's way); the editor's hover text and the Type Explorer's "counts from 1" follow the setting
  • the Python epic gets an early phase, "Lists Start at 0", about 1-2 days
  • it works for js/solid and ts/solid too, not just Python

Also (2026-10-06): the shift can't be plain arithmetic on itemOf(): not found is undefined, and undefined - 1 is NaN, not "nothing". Put the base in core instead (a "start at" argument, or a 0-based twin of each helper), so missing stays missing.
