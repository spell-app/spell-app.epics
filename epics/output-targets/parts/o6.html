Half-way: what today's output does that a person wouldn't

ts/solid today (P7) is the JavaScript target's output with types added. It runs, and tsc checks it, but nobody would write it. From the real output for Card (spell compile Solitaire --target ts/solid --stdout):

  • JSX isn't JSX. Each tag becomes spellCore.element({ tag: "div", props: { className, onClick }, children: [...] }), and core turns that into React.createElement() (packages/core/src/ui.ts). So the output draws with React, not Solid, and says className.
  • A drawing re-runs whole. React's bridge (view()) redraws all of Card's draw() when anything it read changes; nothing is fine-grained.
  • Four lines per property. static { this.declareProp('rank', ...) }, then a getter and a setter over getProp() / setProp(), with an as cast. A person writes one line, @prop(...) accessor rank!: Rank. Compiled JavaScript can't use decorators (it runs from a blob: URL, with no build step: spellDecorators.ts's header), but TypeScript is built anyway.
  • Lists lose their values. static Ranks = ['ace', 2, ...] without as const, so a rank's type is string | number, not the 13 ranks.
  • Types spell knows are dropped. is_a_$suit(suit: any /* spell: type unknown */), though spell wrote for its suits. (The whole untyped gap: 1.7.)
  • JavaScript's names. is_a_$suit, turn_face_up, short_rank: names made legal JavaScript while parsing (1.3), not TypeScript's own isASuit, turnFaceUp.
  • Members patched on from outside. the pile of a card (written in Pile.spell) is export interface Card { readonly pile: any } plus Object.defineProperty(Card.prototype, 'pile', ...), far below the class. (play(), from Solitaire.spell, is already folded into the class.)
  • Machine tidiness. let for everything, (((("Card face-" + a) + " ") + b), { return x } braces, an unused (event: any) => on every handler, the same handler written twice.
  • No error net. Nothing guards a drawn thing: a card whose draw() throws takes React's whole tree down with it.

The full monty: what changes

The list follows Owen's answers (2026-10-09): Q18, Q19 and Q22 as recommended; the error net a decorator on draw() (Q21, B); JavaScript moves to Solid first (Q23, B); the decorators themselves still open (Q20).

One bullet per change, each with the question that settled it. The after below shows Owen's answers, and the recommended option where a question is still open.

  • Real JSX, compiled by Solid. The file becomes Solitaire.compiled.tsx; a spell tag is written as the tag (<div class={...} onClick={click}>).   • A drawing in Solid's shapes. The statements of to draw become Solid's: a local that's computed becomes an accessor (const className = () => ...), an if ... return chain becomes <Show> / <Switch>, draw cards in it becomes <For>. Any other shape re-runs whole, inside its net. Decided: Q19, A.
  • Decorators. @prop({ oneOf: RANKS }) accessor rank!: Rank, from $/util's spellDecorators.ts, re-exported by @spell/core: the SAME runtime shape as today's declareProp plus accessor pair, so Thing checks and stores it as now. @derived only where a getter loops over a list (Pile.state); @thing only on a class with a to create.   • Spell cells stay the state. Properties stay spell cells (getProp() / setProp() under @prop), never Solid signals or stores: spell needs a read right after a write to see it, which Solid 2's staged writes can't give (guides/solid/solid-2.md, "Spell's decisions").   • An error net per drawn thing, from a decorator on draw(). @drawn draw() { ... }: the decorator, from core, runs the drawing ONCE, untracked, inside Solid's <Errored>. Compiled JavaScript has no decorators, so it applies the same function by hand, as it lowers @prop today: ONE net for both targets. Decided: Q21, B (not the <Drawn> component this sketch first showed).
  • <ui-root> and UI. start the game mounts with Solid's render() into the page's <ui-root>, which loads any <ui-*> tag a drawing uses by itself (UIRoot.tsx's banner): a spell program could write <ui-button> and it would just work.   • Types where spell knows them. Lists as const RANKS = [...] as const plus type Rank; parameters spell knows (isASuit(suit: Suit)); a callback's item ((pile: Pile) =>). The rest of the gap: 1.7.
  • TypeScript's names. Methods, getters and functions in camelCase (isASuit, turnFaceUp, playFromTheStockPile); properties keep spell's names, as they're data a program prints. Decided: Q22, A.
  • One class body per type. Every member of Card, wherever in the project spell wrote it, inside class Card: get pile() moves in, its merged interface goes.
  • Tidy as written by hand. const where a variable is never set again, template text (`${this.rank}-of-${this.suit}`), no extra parentheses or braces, no unused parameters, a shared handler written once.
  • Imports. solid-js (Show, For) and @spell/core (spellCore, Thing, prop, drawn), plus UI from @spell-app/ui only when the program uses it.

// @spell/core's Solid side, sketched:  each drawn thing in its own error net, as spell-element's
// `UIComponent.mount()` gives each element one.  BOTH targets draw on it.
import { Errored, runWithOwner, untrack } from "solid-js"
import { render, type JSX } from "@solidjs/web"

/**
 * `@drawn draw() { ... }`:  the drawing runs ONCE, untracked, inside its own error net.
 * - So a parent draws a child with a plain call, `{card.draw()}`:  it neither re-runs when the card's reads change,
 *   nor dies with the card's errors.  A drawing Solid can't follow in pieces re-runs whole, inside its net.
 * - Compiled JavaScript has no decorators:  it applies this same function by hand, as it lowers `@prop`
 *   (its exact lowered form, and the decorator set it belongs to:  per Q20).
 */
export function drawn<T extends Thing>(draw: (this: T) => JSX.Element, _context: ClassMethodDecoratorContext<T>) {
  return function (this: T): JSX.Element {
    return untrack(() => <Errored fallback={(error) => drawFailed(this, error())}>{draw.call(this)}</Errored>)
  }
}

/**
 * `thing.draw()` threw:  log it ONCE on the program's console, send a cancelable `ui-error` from the app's
 * `<ui-root>`, then show a small stand-in, unless the app cancelled the event.  The rest of the page keeps drawing.
 * - Outside any owner (`runWithOwner(null)`), so it may change state:  as spell-element's `onError()`.
 */
function drawFailed(thing: Thing, error: unknown): JSX.Element {
  const showsStandIn = runWithOwner(null, () => {
    spellCore.console.error(`${thing.type} failed to draw:`, error)
    const detail = { error, thing }
    const event = new CustomEvent("ui-error", { bubbles: true, composed: true, cancelable: true, detail })
    return spellCore.appElement()?.dispatchEvent(event) ?? true
  })
  return showsStandIn ? <ui-label color="red" icon="exclamation triangle">{thing.type}</ui-label> : undefined
}

// App.start(), in Solid:  into the page's <ui-root>, which loads any <ui-*> tag a drawing uses
export class App extends Thing {
  start() {
    render(() => this.draw(), spellCore.appElement() ?? document.querySelector("ui-root")!)
  }
}

What stays the same, on purpose:

  • Spell's built-ins stay spellCore calls: getItemOf(rank, 1) counts from 1, includes() and isOfType() take spell's lists and nothing. A person would write this.rank[0]; the contract test (P8) needs both targets to print the same.
  • Spell's is stays == (forgiving: "2" is 2).
  • turnOver() still calls turnFaceDown() without await: spell waits only when told to (wait for).
  • The headings and the test still run when the file loads (spellCore.heading(), testCardSetup()), as in JavaScript.
  • A class name spell builds as text stays text (class={className()}), not Solid's array form: the writer can't know which words a string holds.

The catch: what makes it hard

With JavaScript moving first (Q23, B), core's Solid side is core itself, for both targets, and spell-runtime.js runs on the page's shared Solid; the JavaScript snapshots change once, in the JavaScript stage.

  • Core draws with React. element() builds React elements, Thing.Component is a React class through view(), App.start() uses React's createRoot(). So core moves to Solid, for both targets, JavaScript first: element() on @solidjs/h, draw() returning Solid's JSX.Element, @drawn, App.start() with Solid's render(). That's the whole "Core + JSX" move, and React leaves compiled spell, the runners and the app with it (view(), the forms kit, semantic-ui-react; I2).
  • spell-runtime.js and Solid. Compiled JavaScript imports only @spell/core, never Solid, and runs from a blob: URL (packages/core/AGENTS.md, "Who may value-import it"). Its core, spell-runtime.js, now draws with Solid, but must use the page's ONE shared Solid (spell-solid.js, through sharedSolid()), never bundle its own: two Solids on a page fail silently (solid-2.md, "Spell's decisions"). ts/solid output imports solid-js itself and needs a build (Solid's compiler, the decorators lowered).
  • Running it. The contract test runs ts/solid output through tsx as a .mts file (packages/cli/src/contract.test.ts). A .tsx with Solid JSX and decorators needs a build step first: esbuild for the decorators (vite.decorators.ts), then Solid's compiler (@solidjs/compiler, rc.13, already installed); and Solid's CLIENT build under node, which resolves the server build by default (solid-2.md, "Testing"), with the fake page (linkedom).
  • Translating to draw. Spell's drawing is statements: locals, ifs, early returns, loops. Turning the common shapes into accessors, <Show>, <Switch> and <For> is the bulk of the writer's new work; every other shape must still be right, re-running whole (Q19).
  • Names shared across projects. A library's declarations (Solitaire.declarations.json) name its members as JavaScript does; a ts/solid project importing a library must use the same names its own writer gives (Q22).
  • as const lists are read-only. spellCore.itemOf(Card.Ranks, ...) and friends must take readonly arrays in core's types.
  • tsc and the snapshots. typecheck() (packages/spell/src/node/typecheck.ts) gains JSX settings and Solid's and <ui-*>'s JSX types; every fixture's .snapshot.ts becomes .snapshot.tsx and changes whole, once, and the .snapshot.tsc.txt files are blessed again. The JavaScript snapshots change once, in the JavaScript stage (live values as functions), and must not move after it.

A Thing could compile to a Spell UI element (<spell-card>, on UIComponent), which would bring spell-element's net for free. Not proposed: a card isn't a widget a page author places, every drawn card would get a shadow root and a DOM element of its own (1,000 <ui-button>s build in about 100 ms), and a person writing Solitaire by hand would write components, not elements.
