When compiled code names what a class has, should a stored property be camelCase too, like getters and methods already are in TypeScript?

  • A class's members are everything a thing of that class has. There are three kinds:
    • a stored property: a value the thing holds, set and read back. In Cards' deck: a deck has is set up as yes or no.
    • a getter: a value worked out each time it's read. In Cards' card: a card "is face up" if its direction is up.
    • a method: something it does, e.g. to turn face up: ....
  • Spell's own name for each comes from its words, in snake_case: is_set_up, is_face_up.
  • Today the two writers name them differently:
 
// TypeScript (ts/solid):  getters and methods camelCase, stored properties keep spell's name
get isFaceUp() { ... }
@prop({ type: "choice" }) accessor is_set_up!: boolean

// javascript (js/solid):  every member keeps spell's name
Object.defineProperty(Card.prototype, 'is_face_up', { get() { ... } })
Deck.declareProp('is_set_up', { type: 'choice' })
  • Your javascript-names answer (Q51) was "camelCase in javascript, as TypeScript". Tonight P19 does exactly that: javascript camelCases getters and methods, and keeps stored properties as they are, the same as TypeScript.
  • The open part: should stored properties go camelCase too, in BOTH writers?
  • A stored property's name is used outside the code, so more follows if it changes:
    • saved JSON's keys: { "@type": "Deck", "is_set_up": true }
    • the Thing Explorer's property list
    • print the deck, which shows its props by name
    • getProp("is_set_up") in core, and the scopes the editor completes from
  • It's also why declarations carry "getter": true (J44).
    • A writer reading another project's Card must know whether is_face_up is a getter or a stored property.
    • A getter is written isFaceUp; a stored property, is_face_up.
    • With one rule for every member, that flag isn't needed.
  • accessor isSetUp!: boolean, and JSON { "isSetUp": true }.
  • The Thing Explorer shows isSetUp.
  • One rule: a person reading the code sees one style.
  • The "getter": true flag goes (J44), and so do the declarations' extra lines.
  • Cost: what shows a property's name to a person (the Thing Explorer, print) shows camelCase, not spell's words. Every snapshot changes again.
  • accessor is_set_up!: boolean, as today; JSON and the Thing Explorer unchanged.
  • A property's name stays the program's own words wherever a person sees its data.
  • The "getter": true flag stays: it's what tells the two kinds apart.
  • Cost: two styles side by side in compiled code (this.is_set_up beside this.isFaceUp).
  • Nothing more to do: P19 already builds it.
  • Pick A and it's a small follow-up: the naming is one writer method, and J44's flag goes with it.

Answer · Every member camelCase, in both writers
