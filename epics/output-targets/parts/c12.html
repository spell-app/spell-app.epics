Making Spell UI's reactive members run on spell cells, so both sides react exactly alike, has four costs to measure or settle before the switch. Found while answering Q20.

  • The members: @E.state and @E.derived.

The four:

  1. The bridge on every page.
    • Spell cells reach Solid by wrapping EVERY Solid computation, once per page (bridgeSolid()).
    • Today only the app's pages install it. Spell UI would install it itself, so every Spell UI page pays for it.
    • Re-run the 1,000-button check (UIButton.perf.test.tsx), and yarn measure: the cells code joins Spell UI's core.
  2. Test flushes.
    • A Solid reader of only a derived value hears of a change a microtask later (scheduleCellCheck()).
    • So Spell UI's test helper, ElementFixture.settle(), must call flushCells().
    • Not Solid's bare flush().
  3. The static server render.
    • It runs Spell UI on Solid's server build.
    • That build exports enableExternalSource, but the bridge has never run there.
  4. spell-element first.
    • That epic (running, not merged) rewrites Spell UI's reactive members (Reactive.ts): 579 more lines.
    • It adds six more decorators:
      • @aria, @cssStates
      • @on, @untracked
      • @fromContent, @whileConnected
    • So the switch must come after it merges.
  • The switch is its own piece of work, after spell-element, with these four checks in its goals.
