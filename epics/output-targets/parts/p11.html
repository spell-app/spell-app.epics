  • 2. What Spell UI lacks, made in Spell UI (each with its example on its docs page)
    • A form bound to a thing: <ui-form value={the app}>.
      • Each field with a name shows that property of the value, and writes it back as the person types or clicks, live both ways.
      • Today <ui-form> only gathers its fields' values: Fomantic's get.values(), here FormFields.values().
      • The binding reads and writes through the shared reactive engine P10 put in $/util/reactive.
      • So a spell thing and a Spell UI element see each other's changes.
    • A repeat: the kit's <UI.FormRepeat name="tasks">.
      • Its fields are drawn once per item of a list property, each row bound to its own item.
      • Rows come and go with the list.
      • Its name, a <ui-fields> option or its own element, is settled while building.
    • The rest as found:
      • a field's width (<ui-field> has it)
      • a header item in a menu
      • the form's debug view of its values: made if small, else dropped from the example
      • Anything else the rewrite trips over is made in Spell UI, not worked around in the example.

      • So <ui-form value={the app}> gets the app itself, not the text "[object Object]".
