Spell's rules sit many to a file (lists.ts holds about 40), and each rule's inline tests check only the javascript output.

Each rule gets a file of its own, and each of its inline tests checks both writers.

  • A rule's file holds the rule and the definitions it needs: its AST helpers, types and constants.
  • An inline test says both outputs, { input, js, ts }, so it checks the javascript writer and the TypeScript writer.
  • One rule and its definitions per file.
    • For example, list_add_relative.ts.
    • A folder for each of today's files: rules/lists/ for today's lists.ts.
    • Each folder's index.ts re-exports its rules, so imports from outside the folder don't change.
    • What to call the files: the rule-file names question (Q50).
  • Inline tests read { input, js, ts }.
    • Today's output is renamed js.
    • ts is what the TypeScript writer writes. It's blessed once from today's writer output, then Owen reads it as part of the review.
    • A single rule has no project around it, so sometimes it can't say a type. There, the ts shows what the writer does without one.
    • A test may leave ts out where it's the same as js, for example a plain literal. 
    // before
{ input: "the last item of the stock", output: "spellCore.getItemOf(stock, -1)" }
// after
{ input: "the last item of the stock", js: "spellCore.getItemOf(stock, -1)", ts: "stock.lastItem" }
  • The test runner compiles each input with both writers.
    • That's the parser's unitTestModuleRules(), and spell's own rule test helpers (spell/src/test).
  • Nothing about what a rule parses changes.
    • The parser speed test, SP.spellParser.speedTest(), is the same before and after.
    • Every fixture's snapshot is the same before and after.
  • Owen asked, 2026-10-10: "are those tests not relevant anymore?" They are.
    • They're the only test of each rule by itself: about 1000 of spell's 1076 tests. The fixtures test whole programs.
    • With ts added, they test the TypeScript writer rule by rule too.
  • Every rule module is a folder now, one rule class per file: 19 folders under spell's rules/.
    • Each has its <module>.parser.ts.
    • An index.ts, in the old registration order.
    • And a <module>.shared.ts, where rules share helpers.
    • events/ was the model.
  • Rule classes are PascalCase; rule NAMES (what syntax says) are unchanged. ruleNames.test.ts pins every name and the registration order: unchanged.
  • Every rule test says both outputs, { input, js, ts }.
    • yarn test:rules:bless writes the ts.
