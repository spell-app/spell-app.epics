Renumbered after the split (Q27, A): the ts/solid rewrite this page counts on is P12, and the fixes and Owen's answers below are built in P13, the Untyped Gap phase.

How much of the TypeScript that ts/solid writes is really typed, where each gap comes from, and what closes it. Owen asked for it on 2026-10-09 ("make an analysis of untyped stuff in the TS port and let's see if we can't close the untyped gap"); the fixes are queued to P13.

  • In one line: about half of what the writer declares is typed (53% across the projects, Solitaire 61%), and half of the anys are types spell already knows but loses on the way to the writer.
  • Words used below:
    • a marker: the any /* spell: type unknown */ (or any /* spell: list */) the writer puts where it has no type, so every gap shows (J13). The writer never writes a bare any, as any or as unknown as: none in any project.
    • an implicit any: a value TypeScript itself couldn't type, which strict mode reports as an error (TS7006, "Parameter 'event' implicitly has an 'any' type"). There are none today, only because every parameter the writer can't type gets a marker.
    • a declaration: anything that has a type: a parameter, a local variable, a getter, a method's return, a static, a member merged in from outside the class.
    • typed %: the declarations whose type is neither any nor unknown.
  • Every project that compiles, as spell compile <project> --target ts/solid --stdout prints it, on 2026-10-09 (branch output-targets at main). user/Errors doesn't parse, so it's left out; examples/FizzBuzz and examples/OutlineSolitaire are the fixtures' twins, so they're left out of the totals.
  • Errors: tsc 7 with typecheck()'s settings (core's strict, which includes noImplicitAny), all projects checked together, Solitaire-import against the example Solitaire it imports.
  • Declarations: TypeScript 6's API (@typescript/typescript6, the same settings) asked the type of every declaration, and of every name, member read and call (an "any value": how far an untyped value spreads).
  • The causes: the writer patched in a scratch copy to log, for each marker, the rule that made it and what spell knew there (the match's datatype, the loop's scope). The what-ifs below come from the same patch writing the fix. No product code changed.

Errors with other causes

Beyond the markers, the other projects' errors come from five places the writer or core can fix:

  • Statics set after the class (OutlineSolitaire, 13 errors and 5 inferred anys): the outline style (a "deck" is a list of cards with: - "suits" as one of ...) writes Deck.Suits = [...] below class Deck, which TypeScript doesn't see as a static; and static get instanceType() (read when set) leaves Deck as a plain List, not List<Card>.
  • A member patched on from another project (Solitaire-import, 1 error): C6, now seen for real: export interface Card { play(): ... } clashes with the imported Card (TS2440).
  • Named arguments typed Object (both Todos, 3 errors and 3 inferred anys): to create a new task (with title as text) becomes create_a_new_task(props: Object = {}), so let { title } = props fails, though spell says title is text.
  • Enumerations widened (cards, 2 errors): static Colors = ['red', 'black'] is a string[], so a joker's color can't override a card's, whose getter returns 'red' | 'black'. Written as const (as 1.6 plans), every enumerated property becomes the union of its values.
  • core's loose returns: the four helpers above return unknown; and itemOf(this, card) inside a List sub-class is string | number, not a position (KeyOf can't resolve this), 1 error each in the example Solitaires.

What only Owen can decide

Owen answered all three on 2026-10-09; each is built in P13:

  • Q24, B (not the recommended A): spell ASKS. A program that doesn't say a type gets a new warning on that line, "say what it is", e.g. a calculator has an input as text, to append (digit as text) to (a calculator); the marker stays until the author says. The system examples get their types written.
  • Q25, A: spell declares a member used where it isn't declared, for TypeScript only (declare droppable: boolean in class Pile).
  • Q26, A: a list read by position is read as found, !.
  • A program that doesn't say a type (Q24): a calculator has an input, to append (digit) to (a calculator), set state to []. Spell could work it out from what the program does with it, require the type, or keep the marker.
  • A member used where it isn't declared (Q25): droppable, symbol, can play (a card) on a plain pile.
  • A list read that may find nothing (Q26): item column of the tableaus, the position of its rank in card ranks.
