The plumbing for .compiled.tsx: how it's checked, built and run, and two dev dependencies it needed.

Checked: the type check now understands Spell UI pages.

  • It reads JSX the way app and ui do.
  • It adds app's types for <ui-*> tags (solid.types.ts).
    • Because Spell UI doesn't ship any.
  • It finds solid-js and the other packages in the repo, even though it runs from a temporary folder.
  • Standard decorators with accessor check as they are: not the old experimental kind.
  • The exact settings, in typecheck(): 
    jsx: "preserve"
jsxImportSource: "@solidjs/web"
files: + packages/app/src/solid/solid.types.ts
the temp folder links the repo's node_modules; no experimentalDecorators

Built: buildTsx(), in two steps.

  1. esbuild first: it strips the types, and lowers the decorators as the repo's own setting does (vite.decorators.ts).
  2. Then Solid's compiler, drawing to the page's DOM.
  • That's the app's own order. Solid's compiler takes TypeScript too, so the other order works as well.
const lowered = await transform(code, {
  loader: "tsx", jsx: "preserve", target: "es2022", format: "esm", keepNames: true, sourcefile: filename
})
const drawn = await compileSolidJsx(lowered.code, {
  filename: filename.replace(/\.tsx$/, ".jsx"),
  generate: "dom",
  moduleName: "@solidjs/web"
})
return drawn.code

Run:

  • runCode() builds a .tsx into a .mjs first.
  • The contract test runs ts/solid as .tsx.
  • The runner's hooks (hooks.mjs) now find Solid from @spell/core's folder. So the built program, in a temporary folder, and its runtime share ONE Solid.

Dev dependencies:

  • Solid's compiler, for spell (@solidjs/compiler 2.0.0-rc.13). It was already installed, through @solidjs/vite-plugin; now it's declared.
  • linkedom, for core's tests. They now run Solid's CLIENT build (vitest.config.ts), so core's drawing test (drawing.test.ts) can draw into a fake page.

One rule bent:

  • A spell node tool reading an app file goes against the one-way package order.
  • But it's a declaration file, read by tsc only.
  • The alternative, a second copy of those 5 lines, would drift.

Proven on a hand-written sample of the target's output (Cards.sample.tsx):

  • It uses:
    • @prop, @drawn, @thing
    • <Show>, <For>
    • a <ui-button>
  • It checks clean.
  • Run with runCode(..., { extension: ".tsx", dom: true }), it draws.
    • A click flips a card, through <Show>.
    • A <ui-button>'s handler bumps the score.
  • .compiled.tsx checks, builds and runs, with no change to the JavaScript side.
  • Two dev dependencies added, both at versions already in yarn.lock.
