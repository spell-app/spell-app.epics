Owen, 2026-10-09, reading Solitaire's TypeScript: "the spellCore.RUNTIME.trigger / .on is horrible -- how can we slim that down?"

Spell's events compile to the program's runtime, spellCore.RUNTIME. For example fire event card-click with card = it, and on card-click with a card:

  • a new one each time a program starts (spellCore.resetRuntime()), so a handler from the last run never hears this one
  • so a short form can't just hold on to it (const { on } = spellCore.RUNTIME at the top would keep the first run's): it must look it up on each call 
// today
const click = () => spellCore.RUNTIME.trigger("card-click", { card: this })
spellCore.RUNTIME.on("card-click", (event: { card: Card }) => {
  const { card } = event
  card.play()
})
// A:  core's own `on()` / `trigger()`, imported like `prop`
const click = () => trigger("card-click", { card: this })
on("card-click", ({ card }: { card: Card }) => card.play())
  • core exports on(), off(), once() and trigger(): each calls the current spellCore.RUNTIME's
  • the TypeScript writer imports them as it imports prop, and destructures the payload where the handler takes it: ({ card }: { card: Card }) => card.play()
  • a program of its own called trigger would clash: the writer imports core's under another name then (trigger as triggerEvent)
  • JavaScript unchanged (or B)
  • spellCore.on(...) / spellCore.trigger(...) in compiled JavaScript, which imports only spellCore
  • the events rules' tests and the JavaScript snapshots change once
  • nothing to build; reads as machinery
  • trigger("card-click", { card: this }) and on("card-click", ({ card }: { card: Card }) => card.play()) in TypeScript
