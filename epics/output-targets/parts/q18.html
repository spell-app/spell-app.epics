For the TS Solid for Realz phase (P10; the sketch: 1.6). Today a tag in a spell drawing, <span className="suit">{the short suit of the card}</span>, is written as spellCore.element({ tag: "span", props: { className: "suit" }, children: [this.short_suit] }), and core draws it with React. Owen wants "straight solid calls" instead. Three ways to write the same thing; all three draw with Solid, live where a value can change.

  • Solid's compiler: the tool that turns JSX into Solid's DOM calls; any Solid app is built with it.
  • Hyperscript: h(tag, props, ...children) calls that build the DOM at run time, with no compiler (@solidjs/h, not installed yet).

Choices

A · Real JSX in a .tsx file (recommended), chosen

  • <span class="suit">{this.shortSuit}</span>
  • reads exactly as a person writes it; tsc checks every tag and attribute
  • Solid's compiler makes each {...} its own live binding: the fastest Solid there is
  • cost: the output must be built before it runs (Solid's compiler, @solidjs/compiler, is already installed); the file becomes Solitaire.compiled.tsx
  • recommended: it is what "as if I was writing the class by hand" means

B · h() calls, no compiler

  • h("span", { class: "suit" }, () => this.shortSuit)
  • runs without a build step
  • every live value must be written as a function, and a handler on a component must take a parameter or it silently becomes a getter (guides/solid/solid-2.md, "Hyperscript")
  • nobody writes an app this way; @solidjs/h must be added

C · Solid's compiled calls, written out

  • const _tmpl$ = template(`<span class="suit">`), then insert(span, () => this.shortSuit): what Solid's compiler would emit
  • literally "straight solid calls"; no build step for the JSX
  • nobody writes it by hand, and it's the compiler's private output: it changes between Solid releases
  • ts/solid writes <Project>.compiled.tsx, its drawings as JSX
  • running it (the contract test, a host app) builds it with Solid's compiler first
  • tsc's check gains JSX settings and Solid's JSX types
