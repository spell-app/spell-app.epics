    How a hand-made component carries its words

    • Each Spell UI element has a vocabulary file beside it, named for its language: UIForm.en.ts.
      • Pure data: every name the tag uses, with what each means.
      • The class points at it, @proto static vocabulary = formVocabulary, and the Vocabulary registry reads it from there.
      • Node tools (the docs site's data) import the same file.
    • Another language is a dictionary: the English name on the left, that language's on the right.
      • A name it leaves out stays English.
      • Designed, not built yet: the translation contract says "Designed now, built later".
    • Its schema has no place for methods: only attributes, events, slots, parts, states and texts. So compiled code can borrow the IDEA (one file per language, beside the code, keyed by the code's own names), not the type.

    "Other languages" reads two ways, and one file serves both

    • Human languages: a Spanish words file beside the English one, as Spell UI's dictionaries are.
      • The Thing Explorer would show "mover (una carta) a (una pila)".
      • Later, a Spanish program could call an English library's methods in Spanish. There's already a sketch of Spanish spell, Card.spell-es, but nothing reads it.
    • Other output targets, like the later Python epic:
      • Python would write move_to_pile, and lose the slot the same way.
      • Each target's writer writes the file with its own names as the keys; the wording is the same.
    • A new file per project, Solitaire.en.js: each type's members, by their compiled name, with spell's wording (the code below).
    • The compiler writes it from the declarations it already gathers, beside the other three files.
    • It records the name the writer actually used, so the reader never has to guess how a name was camelCased.
    • The runner loads it beside the scope pack and hands it to the Thing Explorer.
      • The compiled code doesn't import it, so it stays as a person would write it.
      • Code the editor pushes in memory still runs: the editor pushes the words with it.
      • The one difference from a hand-made element, whose class imports its own file. A program could do that later, once it's built for use outside the runner.
    • Another language is another file, Solitaire.es.js, the same shape.
    • Properties get their words back as well: isSetUp shows as "is-set-up".
    • Cost:
      • a fourth file beside the output, written by the compiler, the language server and the CLI
      • a route on the page server to send it, and one more field in what the runner is given
      • snapshots gain a file
    • The runner already has both, for the Type Explorer.
    • The Thing Explorer would camelCase each of spell's names the way the writer does, and match them up.
    • Cheapest: no new file, nothing new written.
    • Cost:
      • the reader re-works-out the compiled names; if the writer ever names one differently (a clash, a reserved word), the label silently goes missing
      • the scope pack is missing when the project has errors; the declarations when the project is run from a bare compiled file
      • no home for another language: the declarations are for importing, and translating them makes no sense
    • static words = { moveToPile: "move (a card) to (a pile)" } inside class Card.
    • Always there: it travels with the code, even run from a bare compiled file.
    • Cost:
      • noise in code P19 just made read as a person would write it
      • another language means changing the code, or a second table that overrides it
      • the Thing Explorer still needs a way to swap in another language's words
