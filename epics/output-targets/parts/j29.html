A warning is spell's second kind of problem, beside parse errors: something the program should say, which doesn't stop it parsing, compiling or running.

  • A rule notes one on its OWN match while parsing: SP.SpellWarnings.note(match, message, at?), into match.data.warnings. at is the match it shows under (default: the noting match).
  • NOT rolled up line by line like parse errors (data.errors): SP.SpellWarnings.in(file.match) walks the file's matches as they are now, matched plus the matches rules keep in data. So incremental parsing needs nothing new: a kept line keeps its warnings, a re-parsed one gets fresh ones. The incremental test now checks warnings too, on every edit (they match a full parse).
  • Only warnings about the file's own tokens are kept: a match parsed from a string (a quoted method signature) sits at the string's offsets, so quoted_method_signature notes its parameters' warnings again, about the quoted text.
  • Editors: SpellLanguageService.diagnostics() returns parse errors, then warnings as DiagnosticSeverity.Warning, so VS Code and the app's Monaco underline them in yellow.
  • spell compile lists them under its errors, as path:line:col warning: message, and counts them in its note (8 warnings), but never as errors: exit code, the project's state and the scope pack are as if they weren't there. spell check prints only errors on stdout, as before; its stderr note counts warnings too.
