output-wasm, a FUTURE epic: written down, not planned yet. It's a new output target, so spell compile --target wasm writes a .wasm module. you asked for it ("OK if it is doing a subset of spell at this point, e.g. no html"). I read how the JS, TS and Python targets work, to see the options and the hard parts. the shape of the plan, when /epic output-wasm plans it later. Nothing is built now.
  • Spell compiles to JavaScript (and TypeScript). Python is a target on its own branch, not merged yet.
  • WebAssembly ("wasm") is a low-level binary format browsers and node run fast. It knows numbers, functions and memory, and nothing else on its own: no text, lists or objects unless we bring them.
  • So the target is two jobs: a WRITER that turns spell into wasm, and a RUNTIME for what wasm lacks.
  • A target is one entry in packages/spell/src/targets.ts: a name, a writer, a file suffix, and whether it can draw.
  • A WRITER walks spell's syntax tree (the "AST": the program's meaning, not JavaScript's spelling), with one method per kind of node: about 60 of them in the JS writer.
  • Compiled JS leans on the RUNTIME, @spell/core (about 8,000 lines): things with reactive properties, 1-based lists, pauses, drawing, tests.
  • Python closed that gap by PORTING the core to Python, and using plain Python wherever it could. Its branch also adds ProgramWriter, a writer base for languages that aren't JavaScript.
  • No wasm tooling is in the repo yet. Node 24 runs modern wasm (garbage-collected objects, exceptions, JS strings) with no setup, so tests can run wasm directly.
FizzBuzz, the "real test of a new target" · 9 lines 
to fizzbuzz:
  for each number in 1 to 100:
    if number / 15 is an integer: print "FizzBuzz"
    otherwise if number / 3 is an integer: print "Fizz"
    otherwise if number / 5 is an integer: print "Buzz"
    otherwise: print number

It needs only numbers, a range loop, if / otherwise and printing. Its compiled JS makes 4 calls into the core, and each has a plain wasm equivalent (printing goes out to the host).

  • A wasm target that can't draw (can: { draw: false }): a project that draws gets the existing "this target can't draw" error.
  • The writer writes wasm's TEXT form (.wat), so its output is readable and reviewable; a small JS assembler turns it into the .wasm binary.
  • Numbers are always 64-bit floats at first: spell has one "number" type, and "is an integer" is a test it makes at run time.
  • A tiny JS "host" gives the module printing (and seeded random), so the contract test can run it beside JS and Python.
What one FizzBuzz line might become · wat 
;; if number / 3 is an integer: print "Fizz"
(if (call $isInteger (f64.div (local.get $number) (f64.const 3)))
  (then (call $print (global.get $text_Fizz))))
  • Nothing: JS stays the running target, and wasm is one more, like TypeScript and Python.
  • Inside the subset, wasm needs no @spell/core at all.
  • Text: wasm has no strings. Either borrow JS strings (modern wasm can) or build our own.
  • Mixed values: a card's rank is "ace" | 2 | ... | "king": text or number. Wasm needs every value's type up front, so mixed ones need boxing.
  • Memory: things and lists need garbage collection. Modern wasm has it built in ("WasmGC"); older wasm means writing an allocator.
  • Pauses and events: pause for, processes and reactive properties don't fit wasm's model; leave them out at first.
  • Binary output: the house rule "written as a person would" can only hold for the .wat text.
  • FizzBuzz-level (numbers, actions, if, loops, print): about a day of work, plus the host and the contract line.
  • Things with number properties, and lists of numbers: a few days more.
  • Text and mixed choices (enough for Cards, without pauses): a week or more, mostly runtime.

Wasm lacks text, lists and objects. Something must provide them: the module itself, or JavaScript beside it.

The subset needs almost no runtime; each new feature brings its own small wasm runtime piece. Only printing and random come from the host. It becomes a "wasm core", as Python got a Python core.

  • The module stands alone: it runs anywhere wasm runs.
  • Cost: every feature past numbers means runtime work in wasm.

Wasm does the arithmetic and control flow, and calls @spell/core in JavaScript for text, lists and things. Quick to cover a lot of spell.

  • Cost: wasm becomes a thin layer over JS. Every list access crosses the boundary, which is slow, and the module never runs without the JS core.

A full wasm port of the core contract up front, as Python's port did, then the writer.

  • Cost: weeks before the first program runs; much of the core is drawing and reactivity, which a non-drawing target doesn't need.

The writer can write wasm's text form, the binary directly, or another language that compiles to wasm.

Readable output, reviewable in snapshots; an npm assembler (wabt or binaryen, pure JS, no native build) makes the binary.

No new dependency, but nothing to read: snapshots would be hex, and bugs harder to see.

Write AssemblyScript (TypeScript-like) and compile it with its compiler. The writer could lean on the TS writer, and gets text, arrays and GC for free.

  • Cost: a heavier dependency and its own runtime; we'd be targeting AssemblyScript's dialect, not wasm, and give up control of what the module looks like.

Things, lists and text need memory that's freed when they're no longer used.

Use wasm's built-in garbage collection for things and lists, and borrow JS strings for text. Node 24 and current browsers have both.

  • Cost: older browsers and some non-JS wasm runtimes can't run it.

Our own allocator over plain memory: runs on every wasm runtime, but means writing memory management by hand. Much harder.
