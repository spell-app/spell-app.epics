Context first, then the questions. The first three decide the most.
  • Today a spell type has exactly ONE parent: a card is a thing, a deck is a list.
    • Everything a card can do comes from thing, or is written on the card itself.
  • Some behaviour cuts ACROSS the family tree.
    • Being drawn as its own element, being sortable, being dragged, being selected, being saved between visits.
    • Both things and lists want them: a sortable deck, a sortable card in a hand, a selectable task, a selectable list of tasks.
  • With one parent, every mix needs its own built-in type.
    • drawable-thing already needs two: drawable thing AND drawable list.
    • Add "sortable" the same way and it's eight, and it doubles with every ability after that.

  • A mixin is the usual answer: a named bundle of behaviour (properties, methods, drawing) that any type can take on, beside its one parent.
    • So a card is a drawable, sortable thing: the card's parent is still thing; "drawable" and "sortable" are mixed in.

Spell's grammar: a type takes ONE word after "is a".

create_type, its syntax and output · 3 lines > 
classes.addRule(create_type, {
  syntax: "(a|an) {type} is (a|an) {superType:type} {with_nested_statements}?",
  // "a card is a thing"  =>  "export class Card extends Thing {}"
  • So a card is a drawable thing today makes "drawable" the parent, and fails on the leftover "thing".
  • Spell has three built-in parents: thing, list and app.
    • drawable-thing adds two more: drawable thing and drawable list.

Spell's runtime already uses a mixin, by hand: every Thing is Eventful.

Thing and Eventful, a class factory · 8 lines 
// Thing.ts
export class Thing extends Eventful(Observable) { ... }

// SpellEvent.ts:  takes a class, returns a subclass of it with on / off / once / trigger
export function Eventful(BaseClass) {
  const newClass = BaseClass ? class Eventful extends BaseClass {} : class Eventful {}
  SpellEvent.makeEventful(newClass.prototype)
  return newClass
}
  • That's a class factory: a function that takes a class and returns a new subclass of it with the extra behaviour. It's the standard JavaScript way to mix in, since the language has no mixin keyword.

Spell already patches behaviour onto a type after it's made: a card belongs to one pile.

What "a card belongs to one pile" compiles to · 2 lines 
Pile.exclusive = true
Object.defineProperty(Card.prototype, 'pile', { get() { return Pile.ownerOf(this) } })
  • A second way to mix in: copy members onto a class that already exists. No new class, but no super either.

The two output targets (epic output-targets, on its branch):

  • js/solid, what runs: plain JavaScript, NO decorators (it runs without a build step).
  • ts/solid, TypeScript as a person writes it: with decorators, checked by TypeScript.
    • A decorator is the @prop written before a member, saying what kind of member it is.
  • So whatever a mixin compiles to must work as plain function calls in js/solid.

How Spell UI's <ui-*> elements share behaviour today: four ways, none called a mixin.

Way Example
One parent chain Every element's base class, then one of three below it:
  • FormComponent, for form controls
  • LoadableComponent, for elements that show a file
  • PartComponent, for content parts (a card's header)
A helper object, one per element StickyWatch, shared by two elements, the sticky box and the sticky section title.
  • Its own words: "families may not render each other's elements, so the behaviour lives here".
  • Two more like it: the on-demand body loader, and auto-controlled values.
Decorators on members Reactive state, CSS states, work while on the page, event handlers: @state, @cssState ...
Setting flags Yes / no settings merged down the chain, like "is a form control" and "is a part".
  • A form control that also loads a file, or a part that's also sticky, can't have both parents: it takes one, and a helper for the other.

Sortable, as spell would say it · 4 lines

What it would compile to: a class factory per mixin, applied in the order written.

js/solid and ts/solid · the card · 7 lines 
// js/solid
import { Thing, Drawable, Sortable } from "@spell/core"
export class Card extends Sortable(Drawable(Thing)) { ... }
// ts/solid:  the same line, typed;  members as decorators
export class Card extends Sortable(Drawable(Thing)) {
  @prop({ type: "number" }) accessor rank!: number
}
 packages/core · a mixin, hand-written · 8 lines 
export const Sortable = mixin("sortable", (Base) =>
  class Sortable extends Base {
    @prop({ type: "number" }) accessor order!: number
  }
)
// mixin():  remembers each result, so Sortable(Thing) is ONE class every time;
//           marks it, so "if the card is sortable" works (instanceof can't see through a factory);
//           lists it, so the language server can offer its members
  • The same mixin() helper could later serve Spell UI's elements too.
    • It would live in the shared utilities package, which knows nothing about spell.
    • So spell's types and the <ui-*> elements would share one model.
  • The combination types.
    • A drawable list becomes Drawable(List), not a class of its own.
    • A drawable, sortable list never needs a class of its own either.
  • Eventful's hand-rolled factory becomes one more mixin().
  • Maybe, later: some of Spell UI's helper objects, where a mixin reads better (Q6).
  • What stays: spell's one-parent types, every program written today, belongs to one.
  • The grammar is ambiguous. In a drawable thing, is "drawable thing" one type (drawable-thing's answer), or "drawable" plus "thing"?
    • Both must read the same way, so the words don't change meaning when mixins land (Q4).
    • And a card is a drawable, sortable thing needs a list of words before the parent, with commas and "and".
  • "Is it sortable?" needs help.
    • card instanceof Sortable is false: each call of a factory makes a new class.
    • So the helper has to mark each class it makes.
  • Two mixins with the same method: which one runs, and can it call the other (Q5)?
  • Drawing combines. Draggable and selectable both change how a thing is drawn: each has to wrap the drawing the type gives, not replace it.
  • TypeScript is fussy about factories.
    • A class made inside a function can't export private or protected members in its types.
    • The types it writes for one are long.
    • So the ts/solid writer has to spell them out readably.
  • The language server has to know a mixin's members, so the order of the card completes and checks.
  • Schemas merge down the chain.
    • Each class lists its declared properties, and must see the mixins' too.
    • Likely fine, since that list is inherited, but untested.
  • About drawable-thing's size, if mixins are built in only: the grammar, a mixin() helper, two or three built-in mixins, both writers, the language server, docs.
  • Bigger with mixins written in spell (Q3): a new kind of declaration, its scope, importing one from another project.
  • Bigger again if Spell UI moves onto the same model (Q6): that's best its own epic.

What does a word like "sortable" bring to a type? This sets how much a mixin can do, and so everything else.

Properties, methods and drawing, all given to the type: a sortable card gets an order, and a sortable hand gets to sort, for free.

  • You'd get: real reuse, the same thing mixins are in other languages.
  • Cost: the most work; clashes between mixins become possible (Q5).

A list of what the type must HAVE, checked, with no code given: "a sortable thing must have an order".

  • You'd get: checks and completions, like a TypeScript interface.
  • Cost: every type writes its own to sort; little is saved.

A word that turns on behaviour the runtime already has, with no members of its own, as belongs to one sets Pile.exclusive.

  • You'd get: the smallest change; no clashes.
  • Cost: every ability is built into the runtime by hand; spell authors can never add one.

The words a spell author types to give a card two abilities. Several can be allowed; this picks the main one, the one the docs and examples use.

a card is a drawable, sortable thing, and in an outline body, - it is sortable. Short where it's declared, and the long form fits the outline style.

  • Reads like English; matches drawable-thing's a drawable thing.
  • Cost: the grammar must tell an adjective from a type name (1.5, "The catch").

a card is a thing that is drawable and sortable. The parent stays one plain word; no ambiguity.

  • Cost: longer; reads differently from drawable-thing's a drawable thing, so two ways to say "drawable".

a card is a thing. cards are sortable. Can be added anywhere later, even in another file.

  • You'd get: the simplest grammar, like cards have a rank today.
  • Cost: what a card IS is spread over several lines; order of lines starts to matter.

Only spell's own built-in ones (drawable, sortable ...), or can a spell author declare new ones?

The epic ships two or three built-in mixins; declaring your own (sortable is a mixin where:) is a later phase, once the built-in ones have shown the shape.

  • You'd get: something to use early; the declaration grammar designed from real cases.
  • Cost: a second step to plan.

Authors declare mixins in spell from day one; the built-in ones are written the same way, in spell's library project.

  • You'd get: one mechanism, no special built-ins; libraries can share abilities.
  • Cost: a new kind of declaration, its scope and its importing, all at once.

Spell's runtime offers a fixed set; authors pick from it but never add one.

  • Cost: every new ability waits on a change to spell itself.

drawable-thing makes drawable thing and drawable list two built-in TYPES. Once mixins exist, should "drawable" become one, with the same words?

a card is a drawable thing keeps working, and now means "thing, with drawable mixed in". drawable list stops being a class of its own.

  • You'd get: one model; a drawable, sortable list just works.
  • Cost: drawable-thing's Drawable and DrawableList classes are redone (compiled code changes, programs don't).

Drawing is special (its own element, its own tag); it stays a parent type, and mixins are for the other abilities.

  • Cost: "drawable" and "sortable" look alike but work differently; drawable list stays its own class.

Say draggable and selectable both have to draw, or two mixins both have to sort. What happens?

The later word wins, the type's own method beats them all, and each can call the one before it (as super does). A warning when a mixin's method is hidden without being called.

  • In a card is a draggable, selectable thing: the card's own to draw runs, then selectable's wraps it, then draggable's wraps that.
  • You'd get: drawing that layers; what class factories do anyway.
  • Cost: the order of the words matters, which a reader may not expect.

The compiler refuses, naming both, until the type writes its own method and says which to use.

  • You'd get: nothing surprising.
  • Cost: no layering: drawing can't combine without hand-written glue.

Spell UI's <ui-*> elements share behaviour with one parent chain, helper objects and decorators (1.2). Should they use the same mixins as spell's types?

The mixin() helper lives in $/util, generic, so Spell UI CAN use it; moving Spell UI onto it is its own epic.

  • You'd get: spell's types and drawable elements on one model (your output-targets Q20: "They should share a reactive runtime engine"); Spell UI untouched for now.
  • Cost: two models side by side until that epic.

Spell UI's components move onto mixins here too (a form control that also loads a file, a sticky part).

  • Cost: doubles the epic; touches every <ui-*> element.

Mixins live in spell's runtime ($/core); Spell UI keeps its own ways.

  • Cost: a drawable spell type and a <ui-*> element stay built differently.
