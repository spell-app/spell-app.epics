Why they didn't work: VS Code's webview host listens for keydown only on the view's own page (src/vs/workbench/contrib/webview/browser/pre/index.html, contentWindow.addEventListener('keydown', handleInnerKeydown), which posts did-keydown to the workbench). Our page is a cross-origin iframe inside that page, so its keys never reached it. A key pressed by a script still counts for an extension's webview: mainThreadWebviews.ts reviveWebviewContentOptions() sets forwardUntrustedKeypressEvents: true ("always enabled for extensions"), whose doc in webview.ts names our case: "when a webview embeds an iframe". Checked in installed VS Code 1.141.0 too.

Which keys go to VS Code (forVsCode() in liveClient.ts): F1-F19, and Cmd/Ctrl + any key except the page's edit keys (A C X V Y F, Z and G with or without Shift), modifiers alone, keys that move or edit in place (arrows, Home/End, Page Up/Down, Backspace, Delete, Enter, Escape, Space), Ctrl-without-Cmd in a field on a Mac (caret keys), and B/I/U in rich text. Sent only after every handler had the key, so one the page took (Cmd+K jump, Cmd+I comment, UI.keyboard shortcuts) stays the page's.

  • Cmd+Shift+P, Cmd+P, Cmd+Shift+O, Cmd+B, Cmd+W, F1 ... work from inside a doc in either side-bar tab.
  • editKey() no longer takes Shift with A C X V F: Cmd+Shift+F (search files), Cmd+Shift+X, Cmd+Shift+V reach VS Code; the page's find bar is Cmd+F only.
  • Still the page's: Cmd+K (jump) outside a field, so VS Code's Cmd+K chords (Cmd+K Cmd+S ...) only start from inside a field; Cmd+I with text selected.
  • Keys are forwarded on keydown only (no keyup): VS Code's keyup-only uses (modifier-only bindings) don't fire.
