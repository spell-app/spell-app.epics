"Admin" means two different things in this epic, so a page or a log line saying "admin" is ambiguous.

  • In the code today: a space's manager, the person who adds and removes its members. Its role is "admin", the one with the manage flag (canManage), and every space's owner holds it.
  • In the Spaces guide: the org's technical Admins (RS's IT volunteers), a role beside "Lead"; they keep the Admin space, not every space.
  • Org Roles (P20), Paired Spaces (P22) and the Admin page (P25) will put both on one screen.

The words.md word list has no entry for it yet: the answer goes there.

  • A space's role "admin" becomes "manager", as its flag (canManage) already says.
  • "Admin" is only the org's technical Admins, as the guide says.
  • Cost: membership files saying "admin" are still read, as "manager".
  • The space role keeps "admin"; the guide's Admins become "Stewards".
  • Cost: the guide and its pages change, not the code.
  • An org's Admin is simply the admin of the Admin space; both are "someone who manages a space".
  • Cost: "an Admin" (the org's) and "an admin of this space" still read alike.

Is canManage our thing or ATSpace's?

You asked: Is canManage our thing or ATSpace's?

Ours, shaped like theirs

  • canManage is Spell's own: one of the three rights a place gives a person, beside canRead and canWrite (SpaceMember).
  • Each role sets it (ROLE_FLAGS): guests read, members also write, admins also manage.
  • Spell checks it before adding or removing members, changing a space's settings, or deleting the space.
guest: { canRead: true, canWrite: false, canManage: false }, member: { canRead: true, canWrite: true, canManage: false }, admin: { canRead: true, canWrite: true, canManage: true }, "spell-admin": { canRead: true, canWrite: true, canManage: true }

What Spaces has instead

  • A Spaces member list has no roles and no manage flag: each entry is a person with two yes / no flags, read and write.
  • Managing is something an APP is allowed to do, not a kind of member: the sign-in permission manage=update lets an app change the space and add or remove members, acting for the space's owner (its "authority").
  • So only the owner manages a member space. Our trial showed it: a member who tried to add someone got NotSpaceOwner.
  • That's why AtProtoSpace copies only read and write to a Spaces member list: an admin's managing stays Spell's, and Spell's server does it as the owner's account (Q6 C).
