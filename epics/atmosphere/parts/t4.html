Signing in should send a short code to type, not a link to click: a link opened on another device can't finish.

  • Why: AT Protocol's sign-in (OAuth) is started by one browser, which holds secret keys for it, and the request it starts expires in about 90 seconds.
  • So Ana asks to sign in on her laptop, opens the email on her phone, and taps the link: the phone has none of the laptop's keys, and the sign-in fails.
  • Spell runs the sign-in server itself, so the sign-in screen is ours, and an emailed code or link is our choice. No proposal covers how accounts are made: that's ours to build too.

The fixes:

  • A typed code: she types the six digits on the laptop, where the sign-in started.
  • An invite link: it only opens Spell, which starts a fresh sign-in on whichever device opened it.
  • Spell's own app can keep people signed in for a long time, with no "allow this app?" screen, if it has a small server side of its own (proposal 0010).

Changed, 2026-11-04 (Q12): the emailed link works too, on any device. The problem above is AT Protocol's sign-in being started by one browser; Spell's own sign-in isn't, so it gets around it.

  • The email carries both a link and the six-digit code. The asking page waits, checking a one-time sign-in request by its id.
  • Tapping the link on her phone shows where the request came from, with one confirm button; confirming signs the phone in, and the waiting laptop signs in a moment later.
  • The link signs her in on Spell's sign-in server, and each device then starts its own fresh sign-in, so neither needs the other's keys.
