Solid 2 analysis

Everything Solid 2 offers, new and old, and its whole ecosystem, set beside how Spell does the same things today. Then what we might build, whether to join Solid's ecosystem list, and whether "Web Component First" holds up.

session solid-2-final (its agent solid-2-final-pages), before the rework starts 2026-11-20
solid-2-final, a FUTURE epic: moving every part of Spell built on Solid from its last test release (2.0.0-rc.21) onto the stable Solid 2.0. You asked for this groundwork before the rework: read the Solid 2 guides, list every feature and library, and compare each with Spell. Four research agents gathered the facts; this page puts them together. Nothing in the code has changed. What the rework takes on, and how Spell talks about itself. The summary table is on the Solid 2 features page; every row there links back here.

The dozen things that matter most, in plain words. Each points to the section with the detail.

  1. Solid 2's headline features are unused here.
    • Stores, projections, optimistic values, actions, isPending(), latest(), refresh(), <Reveal> and dynamic(): zero imports anywhere in the kit.
    • The one Solid 2 async feature Spell leans on is createDeferred(), chosen because an async memo froze drawings.
    • Spell draws with Solid everywhere (964 <Show>, 279 <For>), but keeps its STATE out of Solid.
  2. Spell runs two reactive engines of its own (section 4).
    • Spell cells (1,786 lines): Spell's Things, the editor's state, compiled programs.
    • Spell UI's reactive members (1,377 lines): @state, @derived, @onChange and the rest.
    • Both exist because Solid 2 holds a write back until the next tick, and Spell needs set x to 1 then print x to print 1.
    • They don't see each other's derived values: that's logged as code debt.
  3. Spell's data layer does far more than Solid's (sections 4 and 6).
    • Places: 17,155 lines, plus 7,403 on the server. Many back-ends behind one line, a copy kept on the device, offline writes, three-way merges, live rooms, sign-in.
    • Solid's actions and optimistic values are in-memory, one tab, online.
    • But places could put Solid's async reading on top: <Loading>, isPending(), refresh() over any back-end.
  4. No real server rendering.
    • Spell UI has a static render for search engines (spell ssr), with no hydration: the page it writes must not load the elements.
    • A server-drawn shadow root is accepted, then emptied. No streaming. A Spell site is drawn in the browser.
    • This is the weakest answer to every web-components critic (section 8).
  5. Of 225 libraries on solidjs.com, Spell uses one: Solid Router (a test release), in the editor app's 88 lines of routes.
    • For nearly everything else on the list (UI kits, forms, i18n, storage, undo, drag and drop, icons, testing), Spell has its own (section 3).
    • The real gaps: head and meta tags, true list virtualization, list animation, a Solid-level devtools view, charts.
  6. Spell's element layer began as Solid's own @solidjs/element, folded in and fixed (2026-10-09).
    • It took 11 fixes and sent none back. The plan for sending them, one pull request per fix, was written and never filed.
    • It's likely the most complete custom-element layer on Solid 2 (inferred): a natural thing to give back.
  7. The move to 2.0 final breaks one thing for sure: the shadow-root events fix, which reads Solid's insides.
    • Solid 2 fixed two of the three problems it repairs. The third may still be open, with no issue filed: a chance to file one, with the repro Spell already wrote.
  8. Getting listed on solidjs.com is easy: one pull request adding one entry, and nearly every recent one was merged (section 7).
    • But it's blocked today: Spell UI pins Solid 2.0.0-rc.21 exactly, so it won't install into a Solid 2.0 app; npm's latest is a placeholder; and the repo has no LICENSE file.
    • Best first move: goodwill. File the shadow-root bug, fix the stale solid-element entry on their page, then apply after the December 1 release.
  9. "The first framework where the entire app is web components" doesn't hold (section 8).
    • YouTube (Polymer, 2017), Firefox's own UI (2019), Salesforce, Photoshop ("the entire Photoshop app is built using Lit-based Web Components"), Reddit and Edge all did it first. Imba already compiles a language to custom elements.
    • Even in Spell, the editor's shell is Solid components, and inside every element is ordinary Solid.
  10. What IS defensible, and rare:
    • a language whose compiler makes every view a real HTML element named after your own types (<solitaire-card>)
    • one element layer under all of Spell: its UI kit, its docs, every program
    • tags in the program's own language: <solitario-carta>, <es-boton> (no other framework found translates tag names)
    • the honest one-liner: Solid inside, web components at every boundary.
  11. Platform features worth taking up next: Declarative Shadow DOM kept on upgrade (the biggest win), a Custom Elements Manifest for every compiled project, Reference Target for labels, connectedMoveCallback(), scoped registries once Firefox ships them.
  12. Two generator ideas pay off widely (section 6): compile a Spell action to a generator (exact cancel, one build for running and debugging, Solid's held writes), and stream a long list as pages.
    • For Python on Quart, the first fix is small: writes today block the one event loop every visitor shares.

Your question: how does Spell's way of loading and saving apply to a Python program running in Quart? What about streaming? Where could generators make things better under the hood?

  • The paradigm is "a place": one small interface for every back-end, and an engine above it that
    • shows what you wrote at once
    • keeps it on the device until the place says yes
    • heals after a refusal or a reconnect
    • shares one request between every reader
  • Python goes about a third of the way (inferred).
    • It has places: 6 kinds, the same rows and the same wire format as the browser.
    • It has none of the engine: no pending changes, no retry, no healing, no live updates, no pages of a list.
    • Under Quart, its writes block the one event loop every visitor shares.
  • Streaming today is websockets only: rooms, live reload, AT Protocol's Jetstream, and the Quart page's patches. No HTTP response is streamed anywhere: no server-sent events, no line-by-line JSON, no streamed server rendering.
  • The best streaming move: make a list a stream of PAGES, sent one JSON line per page by Spell's place server, by Quart (an async generator) and read by the browser's remote place. The drawing shows rows as they arrive, with the "while loading" lines it already has.
  • The best generator move: compile a Spell action to a generator (function*), run by the core.
    • Each pause, each wait and each debug step becomes a yield.
    • One build then gives exact cancelling, skipping pauses, stepping in the debugger, and Solid 2's action(), whose writes land as one transaction.
    • Python gets the same from async def and asyncio, mostly already.

What happens, in order:

  1. Compile. The compiler gathers what the program reads from each place before it runs: everything a first drawing reads, asked for together, and only the fields something reads.
  2. First read. The program's first mention of a place loads the places code. No place named, nothing loads.
  3. One request per list. Every reader of the same list shares one request; the last reader leaving cancels it. Lists asked in the same moment go in one request where the place allows; a newer search cancels the older.
  4. The place answers with rows, and a "next page" token when there's more. What the place can't do (filter, sort, slice) is done in the browser, under a ceiling. A rate limit is waited out. With - keep a copy on this device, every answer is kept in IndexedDB, and a fresh one answers without asking.
  5. One row per thing. One row per type and id, its fields reactive, turned into Things.
  6. What the reader sees. Each read says where it is, in words: "still waiting", "complete", "from an earlier visit", "couldn't update".
  7. Drawing. An async read keeps what it showed until a new answer lands (Solid's createDeferred()); <Loading> shows the program's own "while loading" lines; a failure shows a message and Try again, never a blank page; a long list is drawn as you scroll, each next page read as it nears the view.
  8. A write. Setting a saved field IS the write: no save step. It's recorded with its own id, shown at once (you read your own writes), kept on this device per tab so it outlives a reload, and sent in the background, in order, until it goes through.
  9. The place answers the write. No answer: sent again with the same id. Refused: put back and healed, one failure raised. Out of date: a three-way merge per field, sent again, and the program hears what was lost.
  10. Healing. Fetch the latest, replay what's pending: on opening, on a refusal, on demand.
  11. Hearing other people. Each place says how: polling at its check it every, asking only what changed; or pushed, by a live room (everyone's changes in one order) or AT Protocol's Jetstream.
  12. The server half. Spell's place server serves ANY place over HTTP, every request a POST of JSON: list, get many, apply, call, changes. It holds keys and scrubs them from every answer.

The Python target runs a program on asyncio; spell_quart serves it as a web app, a game per visitor, its page drawn in JavaScript from state sent down a websocket.

What exists today

  • Places in Python: places.py (783 lines, the twin of the JavaScript core's), on place_kinds.py (410).
  • Six kinds:
    • database on this device: one JSON file beside the program
    • data folder, sheet, excel file: the page server's place routes, the SAME requests a browser sends, with the write token
    • atmosphere account, personal atmosphere account: an app password from the environment
    • every other kind is refused while compiling: a web server is "not in Python yet"
  • The same rows: plain JSON by JavaScript's field names, so a page and a Python program share them.
  • The same as the browser: one thing per type and id; a saved thing writes only the fields that changed; in one go: sends changes together; check it every asks again once a read is that old (on the next read, not by a timer); a rate limit is waited out.
  • Missing (the module says so itself: "no undo of a write, no notices, no samples, no live rooms, no pages of a list"):
    • no pending changes: a write that fails is a console line, and it's lost
    • no retry and no change ids, so no "sent twice, made once"
    • no healing, no three-way merge
    • no live updates
    • no paging: a data folder is read whole
    • no web server, GraphQL, Airtable, Google sheet or cloud kinds
  • A Python program's write is sent straight on the event loop, with plain urllib waiting for the answer. Reads are off the loop, except in a drawing.
  • Quart was picked BECAUSE one thread serves every page.
  • So one visitor's card move, saved to a data folder, stalls every other visitor's game for the round trip (inferred from the code; not measured).
  • Also: database on this device under Quart is ONE file on the server, shared by every visitor (inferred). "This device" means the server, which reads wrong for a web app.

What Spell streams today

  • Websockets, always. Live reload says why not server-sent events: "an EventSource holds one of Chrome's 6 connections per host for good, and every VS Code window shares them". HTTP/2 lifts that limit (100+ streams a connection); the page server is HTTP/1.1 today (inferred).
  • Over them: rooms (numbered steps, heal on a gap), live reload and page patches, AT Protocol's Jetstream, and the Quart page (whole state, then a patch after each message and at each pause, so a deal animates).
  • Reading a body as it comes, but only to count it: a sheet's CSV is read chunk by chunk up to a ceiling, then parsed whole.
  • Nothing streams to a drawing. The editor's Explain This waits for Claude's whole answer.
  • The closest thing to streaming a list: "next page" tokens, and the drawing reading the next page as it nears the view.

What it could stream

  1. A long list as a stream of pages (the best move).
    • The place answers one JSON line per page (or per row). The place server's list gains a streaming option; Quart returns an async generator, which it streams; the browser reads the body line by line, each page landing as it arrives.
    • The rows it has show; the rest wait under the lines it already has. No new loading state per item: the list grows.
    • What it gives: a 10,000-row sheet shows its first rows in one round trip, not after all of them.
  2. Server-sent events for a place's changes, where a websocket is too much: a read-only push feed, "what changed since" held open instead of polled. Against it: the 6-connection limit on HTTP/1.1. So: for a public feed on an HTTP/2 host; websockets for everything two-way.
  3. AI text that grows. A Spell line that asks a model for text would draw it as it comes: each chunk a write to one value, read by Solid 2's from(). Nothing in Spell asks a model at run time yet (inferred).
  4. Solid 2's streamed server rendering: a Spell site's page arrives drawn, its places filling in. For Python, a Quart route could stream the page Python draws a section at a time (inferred).
  5. The Quart page's patches already stream over the socket; an HTTP fallback (events down, POST up) would get through proxies that drop websockets (inferred).
  6. Uploads and big files: a streamed body would send a big file with progress, hashed as it goes (inferred).

How much Spell uses generators today: nearly none. Five function* in all the JavaScript, no async function*, for await only over node streams; Solid's action() 0 uses; a few yields in Python as iterators.

  1. A Spell action compiled to a generator (the best move).
    • Today an action is an async function; cancelling stops it "at the next wait" by throwing; the debugging build is a SECOND build, every line awaiting the debugger.
    • As a generator, each pause, wait and line step is a yield, and the core drives it:
      • cancel is return(): exact, and its finallys run
      • "skip the pauses" (the Quart start, tests) is the driver not waiting
      • stepping is the driver stopping at a yield: one build for running and debugging (inferred)
      • Solid 2's action(function* ...) takes it as it is: the writes held as one transaction, no half-dealt board
      • a place write inside it joins its pending-changes group, ended at the generator's end, cancelled on return()
    • Effort L. Risk: every core method an action awaits has to be yieldable; a getter that waits stays as it is.
    • Python: asyncio already gives most of it (task.cancel() is exact); its gap is the debugger, which yield points would also give.
  2. A place's list as an async iterable of pages: one way to page every place (a Link header, AT Protocol's cursor, a sheet's rows); the last reader leaving ends it by return(); the next page asked only when the drawing pulls. Feeds the stream above, both ends. Python: async def pages(...). Effort S each.
  3. A room's changes as an async iterable: createStore(() => room.changes()) gives any Solid app multiplayer state in one line; async for step in room.changes() in Python for a shared game. Effort M.
  4. The compile yielding between files: a key lands mid-compile; as a generator, a newer edit ends the old compile instead of waiting it out (inferred). Effort S for the yield, M for cancelling.
  5. Parsing a big CSV as it arrives: rows as a generator over a stream, so a big sheet shows its first rows at once, and the ceiling counts rows, not bytes. Effort M. (A workbook is a zip: no gain.)
  6. Undo as a generator: weak. The history is a list of steps either way; replaying a game's moves for a test or time travel fits an iterator (inferred).
  7. Generators in the Python target itself: repeat with each over a place's list read page by page; a lazily worked-out list (the first 10 of ...) as a generator expression (inferred).

What IS true, and rarer

  1. A language whose compiler makes every view a custom element named after the program's own types. a card is a view in a solitaire project becomes <solitaire-card>, its app <solitaire-app>. A drawn view mirrors its properties as attributes, and refers to other things by reference (pile="Tableau#T1"). Imba also compiles to custom elements, but you name each tag yourself (inferred).
  2. One element layer under everything Spell draws: Spell UI's 104 tags, Epic UI, App UI (<spell-viewer>, <spell-editor>), the brand's set, and every compiled program's views.
  3. Tags in the program's language.
    • Spell UI's components get Spanish tags on a Spanish page: <es-boton> for <ui-button>, <es-cuadricula columnas="7">.
    • Spell's OWN things are encanto- in Spanish (Spell is "Encanto"), as <encanto-propiedad nombre="palo"> would sit beside <spell-property name="suit">. In the code today only <encanto-historias> (the stories block) exists; neither of those two property tags was found.
    • A Spanish program's views are named from the project and its Spanish type names: <solitario-carta>.     • No other framework was found that translates tag names (inferred, after a search).
  4. Words, not props, as the element API: Fomantic's vocabulary as attributes (<ui-button size="small" primary>), translated per language, every tag described by a Custom Elements Manifest.
  5. The newest platform parts, used rather than rebuilt: ElementInternals, custom states, form association, popover, <dialog closedby>, invoker commands, anchor positioning (8.3).

A draft "honest section" for the docs

Is Spell a web-components framework? Every view you write in Spell becomes a real HTML element, named after your own types, and Spell's UI kit, docs and editor pieces are elements too. Inside each element, Solid draws it. You're not the first to build whole apps from web components: YouTube, Firefox, Salesforce and Photoshop do. What Spell adds is that you never write an element class: your program's nouns become tags, in the language you wrote it in. What it doesn't do yet: server rendering with hydration, and typed tags in React's JSX.

Your question: "Is there a way we can lean into 'Solid drafts' more? Can we use stores more efficiently? Any way we can get rid of the 'Cell' concept that we use for local 'update model immediately so Spell sees the new values right away' while maintaining a separate copy for Solid's reactivity?"

A Spell value lives in one place: its object's record, a Map. A cell holds no value at all, only who read it and a version number.

What IS doubled is the bookkeeping of who read what:

  • Spell keeps its own list per value: the readers of each cell.
  • Solid keeps its own per computation. The bridge between them, bridgeSolid(), gives EVERY Solid computation on the page a cells reader, and Solid adds a signal of its own to each one.
  • Spell UI's members are built the same way: a record holds the value, and a Solid signal with no value tells Solid it changed (Reactive).

What else the stores showed:

  • A store never writes to the object you gave it: its first write copies that object, and everything above it.
  • So a Spell thing put in a store isn't itself any more: its copy changes, and === fails. 2.0.3's markRaw(Card) keeps a class out of stores, and then it isn't reactive either.
  • 200 nested writes in 101 draft setters re-ran a drawing ONCE.
  • Snapshots share nothing between versions: each one copies every record that was ever written, even with nothing changed between two of them.
  • Spell is imperative: set the score to 5 then print the score must print 5, in a click handler, in a drawing, and halfway through an action that waits.
  • No Solid read gets that everywhere; snapshot() comes closest, and fails twice.
  • flush() after each statement can't stand in: actions refuse it, effects ignore it, and loading work holds it back.
  • The same was found on rc.11 and rc.13; nothing since has changed it.

Each was tried on 20,000 things of 3 fields: a program writing and reading back 200,000 times, then the same with every field drawn. Times are ratios to today's cells; the machine was very busy, so read them as rough.

Where drafts don't help

  • Undo: Solid's drafts keep no record of what changed, and snapshots share nothing. Undo already keeps each property's value before and after: the smallest change there is.
  • Places' pending changes: Spell's outlive the tab, resend, and merge with other people's; Solid's optimistic stores are one tab, in memory. Spell even has its own drafts: an Edit screen's copy that sends nothing until Save, kept on this device.
  • The Inspector: it already sees every write, with the value it was. A store's snapshot would give a whole copy per moment, not a change.

Where stores DO fit: state nothing reads back at once

  • The editor's own UI state: 189 signals and 110 memos in plain Solid components. A panel's signals as one store means one setter and one draft per change (inferred).
  • The epic pages' PageStore: a version and a subscribe, which is a store made by hand.
  • "Is this row selected" in a long list: a projection re-ran only the two rows that changed.
  • A place's read for a drawing, as a Solid async value (section 5.2's createPlace()).
  1. Keep the record as the one copy: it already is. Say so in the Solid 2 rules, so "a separate copy for Solid" stops being how we think of it.
  2. A cheaper bridge (D3). Small; this epic re-checks the bridge on 2.0 anyway, so a phase of its own here. Its tests pin what programs see.
  3. Spell actions inside Solid's actions. No half-dealt board, and fresh reads. Needs actions compiled to generators, and a guard for the midway case: large, its own epic.
  4. Stores where nothing reads back at once: the epic pages' stores, selection in long lists, the editor's panels. Small each; only where a phase is in that code anyway.
  5. Nested JSON reactive through cells, not a store. Medium; its own todo.
  6. One engine for Spell UI and Spell's own state. Onto cells with D3, or onto Spell UI's signals (D1) with a guard against the forever-loop. Medium to large; its own epic.
