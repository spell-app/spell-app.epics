Spell Epic Solid 2.0 Final Web performance

Web performance

Where Spell is slow, heavy or hard to use in a browser today, measured, and everything worth exploring to make apps built with Spell, and the editor itself, as tight as possible: load, memory, CPU, style, network, battery and accessibility. Nothing here is built yet; it's the list to choose from.

session solid-2-final (its agent solid-2-final-perf-page), gathering six research notes into one page 2026-11-20
solid-2-final: moving Spell onto the stable Solid 2.0, and measuring performance and memory in the browser so everything is as stable and fast as it can be. In your words: "as performant as VS Code", and able to "run the Spell editor on a 2-year-old Android phone over a good 5G connection without memory problems". Research agents ran quick browser tests (desktop and a slowed-down phone), measured every bundle, read the code for expensive patterns, and looked at keeping big projects small. This page lists what they found and what to explore. Nothing has been optimized yet, except the old Semantic UI stylesheet, which an agent is dropping now (todo T6 on the epic page). Which of these become phases of this epic, which become epics of their own, and a few standing choices (questions at the end).
  • The browser tests ran while other sessions loaded the Mac (its 1-minute load was 14-64 on 18 cores; quiet is under 9).
  • Times (paints, "usable", long tasks, typing) are inflated by an unknown factor, estimated 1.2-2x. They are marked busy machine where they appear.
  • Bytes, heap, element, listener and sheet counts, and growth per cycle, don't move with load: trust them.
  • The measurement can be run again on a quiet machine with one command (section 2.6).

Where we're falling down now, worst first, in plain words. Each points to the section with the detail.

  1. Pages with many Spell UI elements spend most of their time working out styles (section 4.2).
    • Every element with a shadow root (its own private piece of the page) takes in about 400 KB of shared CSS: the same sheet objects, but the browser matches them against each root separately.
    • The kitchen sink page (every component's examples): 4,467 shadow roots, 22.7 s of style work on desktop and 62 s on the phone, against 1.6 s of script busy machine.
    • The biggest sheet holds 874 custom properties and starts with a :root rule, which matches nothing inside a shadow root.
  2. The editor starts slowly on a phone (sections 2.1 and 4.10).
    • On a phone's CPU in landscape: usable at 7.5 s, then blocked until 27 s busy machine. Desktop: usable at 1.4 s.
    • 62% of that phone load's CPU profile was the page server's live-reload client, which scans every script on the page for each message it hears. Part of that was this machine's other sessions; the scan is still ours to fix.
  3. Nothing is compressed, and nothing is cached (section 4.1).
    • The editor's first screen is about 5.7 MB on the wire, every visit; about 1.2 MB with brotli, and about 6 KB on a warm visit with normal caching.
    • An epic or docs page is about 5.2 MB, every page and every live reload.
  4. Every run of a program in the editor likely stays in memory for good (section 4.3).
    • Each compile imports the program afresh from a new blob: address, and a browser never lets go of a module it imported.
    • One run every 2-second pause: an hour of editing could hold tens to a few hundred MB (inferred: to confirm with a heap snapshot).
  5. Each edit waits for uploads before it runs (section 4.4).
    • The compile saves what it wrote, about 5 uploads one after another, before the program takes the edit.
    • Over 5G: about 150-300 ms more per edit and about 100 KB sent per pause (inferred).
  6. Nothing runs off the page's main thread (section 4.4).
    • No web worker anywhere: parsing, compiling and the language service all share the thread that handles keys and drawing.
    • A declaration typed near the top of a project freezes typing about 110 ms on a Mac, about 450 ms on a phone (inferred).
  7. Heavy for small things: 99-232 MB of JavaScript heap, and about 5 event listeners per element (sections 2 and 4.3).
    • After a forced clean-up: the editor on Solitaire 127 MB, Solitaire alone 99 MB, the kitchen sink 232 MB, the biggest epic page 138 MB.
    • The editor has 28,700 listeners for 5,594 elements; 12,821 of them sit on shadow roots, the same 14 kinds in each.
  8. Startup builds both of Spell's grammars, English and Spanish, with their test tables (sections 4.1 and 4.4).
    • The grammar is 267 KB brotli of the editor's first load; Spanish dictionaries add 71 KB for every reader.
    • The Spanish grammar is built for English projects too.

Is the editor viable on a 2023 mid-range phone today? It runs, but the first 20-30 seconds are not acceptable, and it isn't VS Code-class yet. Once settled, typing is fine (48 ms median), and memory fits (127 MB of heap) with little room left for the person's own app.

The browser timings are noisy, so the whole measurement is one command, to run when the machine is quiet.

From the kit's root · 2 lines 
spell server start        # the page server serves the docs and epic pages, and the editor's API
node /Users/owen/www/spell/spell.epics/epics/solid-2-final/research/perf-scripts/perf-run.mjs
  • How long: about 45-55 minutes with the default 5 loads per page (estimated: 3 took 35 minutes on a busy machine). The editor's phone loads are the slow part, 20-35 s each.
  • A quick check of one page (--page docs --profile desktop --runs 1 --steps load) takes about a minute.
  • It waits for a quiet machine first: a 1-minute load under half the cores (9 on this 18-core Mac), checked every 30 s for up to 10 minutes. Still busy: it runs anyway and marks the result busy; --force skips the wait.
  • It builds the editor twice into a temporary folder (production, and unminified for the CPU profile), serves both, measures, then stops them. Nothing in the kit changes.
  • It writes a dated result beside the others and prints every number against the last one, with WORSE on anything more than 10% worse.
  • Flags pick pages, profiles, runs and steps (load, leaks, typing, accessibility, listeners, sheets, CPU): the scripts' README.
  • Not measured yet: a real phone (slowing the CPU doesn't slow the GPU or limit memory); DOM and style memory (only the JS heap); Safari and Firefox; the editor's file-switch and typing leak loops.

A suggestion, not built: make it a command, spell perf run, so it's run from anywhere and its results live with the code rather than in this epic's research folder. A new command needs your OK first (question 3).

Grouped by dimension, ranked within each. Effort: S is a day or two, M a week, L a phase or more. Nothing here removes a feature.

Where we stand: the editor's first load is 1,014 KB of JavaScript brotli (4,879 KB raw, 85 files); about 1,500 KB with a project open (estimated). vscode.dev, measured the same day, is about 6.4 MB gzipped cold, cached for a year. So with compression on, Spell's editor is about 4x lighter than vscode.dev cold; today, uncompressed, it's about the same, and paid again every visit.

  1. Compress everything. Brotli files written beside each built file, served when the browser accepts them; gzip on the fly for the rest. Also the house network's site (its Caddy file has no compression). Editor −4.5 MB cold, docs page −4.1 MB. Effort S.
  2. Cache properly. Files with a hash in their name cached for a year; pages and fixed names checked each time (a "not modified" answer); development worktrees keep "never store". A warm editor visit drops from 5.7 MB to about 6 KB. Later, a service worker for offline. Effort S.
  3. Split the docs bundle and the epics pack. Each family loaded on first use, as the Spell UI site already does (its first load is 169 KB brotli). It was one classic script so pages worked from disk; pages are always served now. About −700 KB and −150 KB brotli a page (estimated). Effort M.
  4. Load the CSS language service when CSS is first edited, or in a worker. −180 KB brotli and 1.25 MB less to parse at start. Effort S.
  5. Load Spanish only when something speaks it: the dictionaries (−71 KB brotli) and the grammar's Spanish half (~−120 KB, estimated). VS Code does the same, loading a language's support on first use. Effort M.
  6. One copy of the grammar across the element builds (three today, 791 KB brotli), and no rule tests in what ships. Effort S-M.
  7. Drop the Semantic UI stylesheet (598 KB raw, 75 KB brotli, at the editor's start, 85-90% unused, estimated). Being done now (todo T6 on the epic page). A suspected bug goes with it: the built editor linked that sheet and its font from a folder the production server doesn't serve.
  8. Smaller pieces elsewhere: a piece per dialog (~−400 KB on the first dialog); the editor's routes lazy, preloaded on hover; tree-shakable lodash (~−45 KB in a cloud app); an icon sprite per app; the Spell UI help table and the defaults table on first hover (17 KB brotli). Effort S each.
  9. HTTP/2 for the page server and the cloud (plain HTTP/1.1 today, so 85 files share 6 connections). Effort S-M.

Phones pay in CPU more than network: on good 5G (~100 Mbps), 7 MB is about 0.6 s of transfer; at the slower typical mobile network Alex Russell uses (7.2 Mbps) it's about 8 s, and 1.5 MB about 1.7 s. But parsing 4.9 MB of raw JavaScript at start costs an estimated 1-2 s on a 2-year-old phone, and compression doesn't shrink that: only shipping less does (items 4-6).

The biggest single cost found. The sheets ARE shared (one object per name per page, no copies), but each shadow root is its own style scope, so the browser matches its ~12 sheets against its own elements, root by root.

  1. Take :root rules out of shadow roots. Of the base sheets every root adopts, the biggest (163 KB, 140 rules, 874 custom properties), and others of 33, 20 and 13 KB, start with a :root rule, which matches nothing inside a shadow root. If they're :root-only, every root holds ~230 KB of rules that can't apply (only each sheet's first selector was checked). Effort S to check, M to move.
  2. Fewer, smaller base sheets per root. Custom properties already inherit into shadow roots, so tokens can live on the page once. Whether the page's animations reach inside needs checking per browser. Today: layers, reset (14 KB), tokens (15 KB), colours (81 KB), sizes (11 KB), animations (28 KB, 58 of them), then utilities (13 KB). Effort M.
  3. The 874 custom properties. Plus 328 colour properties in another sheet and 206 in another. Many are fallbacks behind a container style query each element evaluates. Fewer, or on the page only. Effort M.
  4. Fewer shadow roots for leaf elements. The editor has 179 <ui-icon>, 149 <ui-action> and 112 <ui-text>, each a root. Effort M-L.
  5. Stop the forced style reads in the panel's scroll shading (3.5 s of the editor's phone load). Effort S.
  6. Measure unused CSS. The families are ports with every size, colour and variation; on a typical page 70-85% of a loaded family's rules likely match nothing (estimated). The browser's CSS coverage would say. Effort S.
  7. Share the layout elements' sheets by value instead of one per instance, and keep CSS text only in development. Effort S.

What happens after one key is pressed in the code pane, in the order it really runs. All of it on the main thread.

  1. CodeMirror takes the key; typing helps run, and the marks move with the edit. Cheap, and drawn only for lines on screen.
  2. The file takes the WHOLE text, every key: the editor flattens CodeMirror's text into one string to compare, twice, and bumps an edit counter that re-runs half a dozen readers.
  3. After a 200 ms pause, the parse runs again, incrementally: a body edit ~10 ms; a comment ~1-2 ms; a member added ~45-75 ms; a declaration near the top of the first file ~110 ms, a full parse (on a Mac; ~450 ms on a phone, inferred). CodeMirror already knows what changed, but that's thrown away.
  4. Problems are worked out for each file whose parse changed; the bubbly look is laid out again from the whole file.
  5. Hovers and suggestions ask the language service, in the page, each after another whole-text copy.
  6. Two seconds after typing stops, the compile: every file hashed; the whole project written again, every file; then the built files uploaded, about 5 one after another, before the program runs; then the program logged whole to two consoles.
  7. The program runs again: imports fetched afresh, the source map inlined, the code imported from a new blob: address. Live edit then redraws only what changed.

Ranked:

  1. Don't upload while typing. The timed compile skips saving (the option exists); built files are written on Save, or by the server, which can compile already. About 5 round trips less per edit. Offline is unchanged. Effort S.
  2. Yield between compile steps. The compile is already a list of tasks, one per file; letting the browser handle a key between them needs no data moved. Effort S.
  3. Parse, compile and the language service in a worker, the main thread a thin client: what vscode.dev does, its language servers in workers speaking the language-server protocol over messages. Spell's service already answers in that protocol's shapes, and already runs in a separate process for VS Code. The hard part: the Inspector, side bar, bubbly look and notebook read the parse directly today. Effort L.
    • In between, a compile-only worker takes the 2-second compile off the main thread, but holds a second parse in memory: only once memory is freed elsewhere.
    • Data passing: text and plain arrays copy fast; shared memory would need special headers that would break Spell apps reading data from other sites, and isn't needed.
  4. Hand the parser the edit, not the text: CodeMirror's changed ranges, instead of the whole file and its own diff. VS Code's lesson: don't make strings you throw away. Effort M.
  5. Less per pause: write only what changed, drop the console dump of the program, don't fetch unchanged imports again, don't lay out the whole file's look. Effort S-M each.
  6. Time the pipeline. The parser's speed test times its rule tests only: not a whole project's parse, an edit, a compile, a run or startup. The incremental tests already make the right edits; time them. Effort S.
  • The parser in WebAssembly: measured, and rejected for now. Tokenizing and matching are at most 54% of a warm Solitaire parse, so 2.2x at best overall. A trial showed nearly all the gain came from flat data (words as numbers, arrays), which plain JavaScript gets too; WebAssembly added 1.2-1.35x on top. Each rule's TypeScript would still be called 63,000-155,000 times a parse across the boundary. Look again if matching passes ~35% of a large project's time: flat data first, then WebAssembly for the tokenizer.
  • A WebAssembly target for Spell programs: not as a target. WebAssembly with garbage collection reached every browser by December 2024, so it meets your 2-year rule in December 2026. But a Spell program is mostly the page, Solid and reactive reads, all of which would cross the boundary, copying text each time. The browser already compiles the JavaScript target to machine code. Worth it later for heavy calculations a program holds (a game's search, a simulation).
  • tree-sitter, oxc in the browser: not needed. CodeMirror's own grammars show compiled JavaScript and Python; nothing in the browser parses TypeScript.
  • Images: the browser's own bitmap and canvas tools in a worker first; a WebAssembly encoder only if those aren't enough.
  • Already native: the bundler, transforms, linter and formatter (Rust and Go, through Vite+); TypeScript 7 (Go); esbuild (Go); uv and ruff (Rust).
  • Faster tooling without a rewrite (faster for you, not for people's apps): run spell from a prebuilt bundle instead of transpiling on every start (its cache once grew to 953 MB; a hook run went from 2.5 s to 0.9 s once cleared); the content check and example compiles across threads; integration tests (~15 min, one file at a time) with an editor per worker; the whole test run is ~10 min. Effort S-M.
  • A Rust rewrite of the parser and compiler: not now. One engine for the command line, the language server and the browser, but capped at ~2x unless the rule classes move too, and they are the language. The page server, epic tool and command line are waiting on files and network, not CPU: no gain worth a second language.
