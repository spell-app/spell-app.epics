Spell still runs on a test release of Solid, and the real Solid 2.0 is out. Three choices shape the move: when, how far it goes, and what moves together.

What changed What it touches here Risk
Solid's event sharing (one listener per root, "delegation") was rebuilt inside: the function that registers a root no longer hands back its state, and roots are found a new way. ShadowEvents, which keeps clicks inside an element's shadow root from leaking out or being dropped. It reads exactly those insides on purpose (marked HACK, as of rc.17). Every Spell UI element with a click handler goes through it. High: it will break, and must be redone. Its tests say so at once.
A ref={(el) => ...} callback that makes an effect, a memo or a cleanup now THROWS in development builds (rc.22). At least one does: the Inspector's pill field for a type's values makes an effect in its ref. 325 refs to look over. Medium: development only, so the tests and a live run in dev mode find them.
List updates MOVE a row's element with the browser's moveBefore(), rather than taking it out and putting it back. Spell UI elements inside <For> lists: how they hear "added to a page" and "removed" when a list reorders. Medium: needs a browser check.
A click handler written as an expression that reads live state (onClick={picked() ? a : b}) now warns in development. New console warnings, which the editor's console check after each merge would show. Low
Solid now tells agents NEVER to wrap a read in untrack() just to quiet its "read outside tracking" warning. Our Solid 2 rules, and 87 untrack() calls outside tests to look over (most are deliberate, as the @untracked decorator is). Low: rules first, code by review.
<Errored>, the error boundary, got several fixes (a change now lands while it shows its fallback). Drawing's workaround for it, which builds each drawing once by hand. The code-debt log says "re-measure on every RC bump". A chance to delete code, if the measurement says so.
Store fixes (frozen objects, markRaw() for classes). Nothing: Spell uses no Solid stores. None
Router 2.0: the old component API (<Router>, <Route>, <A>) removed. Nothing expected: the app already uses only createRouter(), defineRoutes(), useNavigate(), useBeforeLeave() and memoryHistory(). Low
Vite plugin 3.0: new optional extras (a dev toolbar, a diagnostics option that lets an agent or a test ask the running page why something re-ran). Nothing removed that we use. The extras are opt-in. Low

Spell is on a Solid test release, and stable Solid 2.0 came out three days ago, with fixes still landing daily. When should we move?

Plan it now and run it this week, on whatever 2.0.x is newest that day. Exact pins mean later fixes reach us only when we choose.

  • You'd get: every Solid fix from here on, Solid's current advice for agents, and no more "re-measure on every RC" chores.
  • Cost: we may want a small follow-up bump in a week or two, as 2.0.x settles.
  • Why first: the 2.0.x releases are bug fixes; the behaviour changes that touch us came in rc.22, and stay either way.

Leave it a week or two, until the releases slow down, then move once.

  • You'd get: one bump instead of possibly two.
  • Cost: new Solid work in the meantime is written against rc.21, and the two breaks above wait.

No epic of its own now: fold it into the next time the kit's dependencies are refreshed, as rc.21 was.

  • You'd get: one less epic to run.
  • Cost: the shadow-root events fix is real work, and would hide inside a wider phase.

The move can be just the version change, or also a clean-up of what we built around the test releases, or also take up what's new in Solid. How much should this epic take on?

Move, fix what breaks, re-measure each workaround that names an RC and delete the ones Solid made unneeded, and bring the rules and guides up to 2.0.3.

  • You'd get: the shadow-root events fix slimmed down, maybe drawing's "build once" workaround gone, rules that match what Solid now teaches agents.
  • Cost: half a day to a day; each removal needs its measurement first.

Move, fix only what breaks, update the version lines. Leave the workarounds as they are.

  • You'd get: the smallest change, a few hours.
  • Cost: workarounds for bugs Solid fixed stay in the code, and the code-debt entries stay open.

Also try Solid's new tools: its diagnostics harness for tests and agents, and a comparison of our custom-element base with Solid's own, now stable.

  • What's new:
    • @solidjs/diagnostics: records Solid's dev warnings as data, so a test or an agent can check a page has none, or ask why something re-ran.
    • the Vite plugin's diagnostics option, which serves that to the running page
    • @solidjs/element, Solid's own custom-element package, which our spell/element grew from; since 2.0.0 it registers shadow roots for events itself
  • Cost: a day or more, and each tool is a new dependency (the house rules ask you first).
  • Could be its own epic later, instead.

Solid itself, its router and its Vite plugin all went stable. spell-brand, beside the kit, is still two test releases further back (rc.17). What should this epic move?

Every Solid package in the kit at once, router and Vite plugin included. spell-brand follows in its own session, right after this merges.

  • You'd get: one Solid per page, as the rules require, in one merge.
  • Why brand after: it's its own repo and install, and brand work runs in its own session.
  • Cost: spell-brand stays on rc.17 a little longer.

Same as A, and this epic also moves spell-brand from rc.17, in its own session or worktree.

  • You'd get: everything on one Solid when this epic is done.
  • Cost: spell-brand skips rc.21 too, so it meets the rc.17 to rc.21 changes as well.

Move Solid's own packages now; the router and the Vite plugin in a second step. Their current test versions accept stable Solid.

  • You'd get: a smaller first step, and a break is easier to place.
  • Cost: two merges, two lockfile changes, for packages that look low-risk.
