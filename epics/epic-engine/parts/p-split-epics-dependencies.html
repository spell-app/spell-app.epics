npx spell@next epic init installs the whole product, 562 packages and 517 MB, for a tool that needs a fraction of it.

Someone running npx spell@next epic init will install only what epic needs. Owen, on how to fit this and the upgrades together: through solid/etc, split epic dependencies another phase, done first. So this phase comes first, and Dependency Safety follows it.

  • Epic's own run-time needs are small. Tracing the published 0.8.9 from the epic command, the epic server and its routes reaches only:
    • chalk, commander, json5, linkedom and parse5
    • json5-writer, loaded by name so the trace can't see it
    • vite-plus, used for one thing: formatHTML() calls its vite-plus/fmt, which only re-exports oxfmt
  • That trace reads import text. It can't follow an import whose name is worked out at run time, so the lean install below is the real proof.
  • Where the space goes today: Monaco 105 MB, the Vite+ tools about 115 MB with their native binaries, Solid 22 MB. Spell's own files are 75 MB.
  • The same six packages with oxfmt in place of vite-plus measured 28 packages and 26 MB.

Recommended: one lean spell, with optional peers

  • It stays ONE package and every import name stays the same.
  • A new spellPublish list will name the packages that aren't needed to run the tools. PublishedPackage.manifest() will publish those as optional peerDependencies, the way solid-js already is. npm doesn't install an optional peer by itself.
  • The checkout's own package.json doesn't change, so the repo's install stays as it is.
  • formatHTML() will use oxfmt directly, at the exact version vite-plus pins, so epic needs no Vite+. vite-plus becomes an optional peer: people building pages with Vite still add it.
  • A command that reaches a missing package will say what to install, instead of a bare "module not found".
  • No extra package: spell@next stays the one name, and a command that needs an add-on prints the npm install spell@next ... line to paste.
  • spell epic runs npx spell-epic, which installs spell a second time. The build will measure that, and use the epic code spell already holds if the plugin's files allow it.

Rejected

  • A bundled spell-epic with few dependencies. npx spell@next would still install all of spell first, so the one command stays heavy unless the docs change it. It would touch PluginPackage and ScratchInstall, and ship a second copy of the engine.
  • Splitting spell into base and app packages. It undoes repo-split's "ONE npm package" (Q35). It would touch the exports, PublishedPackage's folders, every spell/app/... user outside the package, the publish checks and the READMEs.

Nothing goes to npm until Owen says so (push but don't update npm stands). This phase's work must also pass Dependency Safety's check before it's pushed.
