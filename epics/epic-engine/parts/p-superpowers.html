Devs you know like the superpowers skills plugin, and we don't know what it does, how it overlaps epic, or what happens with both installed.

This phase is an evaluation first: what superpowers is, where it overlaps epic, where the two would trip over each other, and how epic could live with it. Its build is the way recommended in the question at the end.

"new phase: superpowers. A couple of devs I know really like the superpowers agent skills. Evaluate and give me a summary of what it does, how it overlaps with epiic, how we could integrate it / integrate with it"

1. What superpowers is

  • A free plugin of 15 agent skills by Jesse Vincent (Prime Radiant): obra/superpowers, MIT licence. Copies under other names on GitHub are forks of it; this is the one people mean.
  • It's a whole way of working, not a set of tools: talk the idea through, write a design, write a plan of 2-5 minute tasks, build each task test first, review, then finish the branch.
  • It switches itself on. A session-start hook puts its "using superpowers" skill into every session, after /clear and after compaction too. That skill tells the agent that if there's "even a 1% chance" a skill applies, it MUST use it, before answering or even asking a question.
  • Very active and very popular: v7.0.2 on 2026-11-03, a release every two or three weeks; GitHub showed about 300,000 stars when this was written.
  • Runs in 15 agents: Claude Code (in Anthropic's official plugin list, and its own marketplace), Codex, Cursor, Gemini CLI, OpenCode, GitHub Copilot CLI, Devin, Factory, Grok, Kimi, Qwen, Pi, Hermes, Antigravity and Muse.
  • It writes nothing outside the repo but a git-ignored scratch folder, and has no server of its own (the brainstorming skill's optional "visual companion" starts a small local page).
Skill What it does
brainstorming Asks why, lays out two or three approaches with a pick, writes a design doc you approve, before anything is built. Its description says to use it before ANY creative work.
writing-plans Turns the design into a plan file of small tasks: exact files, exact code, the failing test, the command to run, a commit.
executing-plans Runs the plan in this session, task after task, no stopping; one fresh review at the end.
subagent-driven-development Runs the plan with a fresh agent per task and a reviewer after each (does it match the plan, then is it good code); keeps a progress ledger on disk so a compacted session doesn't redo work.
dispatching-parallel-agents Splits independent problems across agents at once.
test-driven-development Red, green, refactor. "No production code without a failing test first": code written before its test is deleted.
systematic-debugging Four steps to a root cause before any fix: "no fixes without root cause investigation first".
verification-before-completion Run the check and read its output before saying "done" or "fixed".
requesting-code-review Hands a diff to a fresh reviewer agent with a template.
receiving-code-review Weigh review comments on their merits: no "you're absolutely right", no blind changes.
using-git-worktrees Makes sure work happens in a worktree: Claude Code's own tool first, else git worktree add under .worktrees/; then installs and runs the tests for a clean start.
finishing-a-development-branch Runs the tests, then offers merge, pull request, keep or discard, and cleans the worktree up.
writing-skills How to write and test a new skill.
using-superpowers The always-on introduction the hook injects: "invoke relevant skills BEFORE any response".
diagnosing-superpowers Works out why a superpowers session went wrong, and builds a bug report.

2. Where they overlap

Both run a piece of work from idea to merge in a worktree, with a written plan and agents. They keep the record in different places, and care about different things.

Step superpowers epic
Working out what you want brainstorming: a conversation in the chat, one question at a time the Overview stage: questions on the epic page, answered when you have time
The design a Markdown design doc, committed in the code repo (docs/superpowers/specs/) the Overview, on the epic page, in the epic repo
The plan a Markdown plan, committed (docs/superpowers/plans/): tiny tasks with the code written out phases, each with a short build plan; one Accept Phases
Building straight through, no stopping; decisions written as "Rulings" in a ledger file straight through, no stopping; decisions written as judgement calls (J items) on the page
Worktrees one per piece of work, Claude Code's own tool when there is one one per epic, its own branch and VS Code window, made by epic's worktree hook
Agents a fresh agent per task, a reviewer after each named, listed background agents for page work, coherence and designer reviews
Review an agent checks each task against the plan, then for quality you review on the page; the coherence and designer agents review plans and pages
Tests test first, always no rule of its own; Spell's house style writes tests after, to match the code
Debugging a four-step root-cause method nothing; issues (I items) record what was found
Finishing merge, pull request, keep or discard /epic done: merge or pull request, changelog, worktree gone, the page kept
Other agents 15 Claude Code, and Codex; any other agent from epic guide

3. What each has that the other doesn't

  • Only superpowers:
    • engineering discipline inside the work: test first, root cause before a fix, proof before "done"
    • a reviewer agent that checks each piece of work against the plan
    • very small, very exact plan tasks, which a cheaper model can carry out
    • a progress file that survives compaction
    • 15 agents, and a large community
  • Only epic:
    • a live page you read and answer on, instead of the chat; questions wait for you instead of stopping the agent
    • the record after the merge: decisions, judgement calls, issues, manual tests, commits, how long each phase took
    • several epics at once, each in its own window, with sagas above them
    • requests from other sessions (/send), parking, bedtime runs, airplane mode
    • a page shared by a team, in a git repo of its own
  • In one line: superpowers is about how the agent works; epic is about how you and the agent agree, and what's kept.

4. Where they'd clash, both installed

  1. Who plans. superpowers' brainstorming says to run before "planning anything new", and before plan mode. /epic seo ... would likely start a chat-style brainstorm and a design doc, instead of (or as well as) the Overview on the page. (A guess until tried: superpowers says your own instructions win over its skills.)
  2. Two plans. writing-plans commits a plan file into the code repo; the epic page already holds the plan. Two records drift, and the committed files land in the branch's diff.
  3. Worktrees, mostly fine. superpowers uses Claude Code's own worktree tool when it has one, which runs epic's worktree hook, so the worktree lands where epic puts it. But:
    • it asks first, unless your instructions already say
    • its set-up step runs npm install for any package.json: wrong in a yarn repo like Spell; epic runs the install command its config names
    • without the tool (Codex) it makes its own under .worktrees/, beside epic's
  4. Two ways to finish. finishing-a-development-branch offers merge, pull request, keep or discard, and removes the worktree; /epic done does the merge with the changelog and its own checks. Its "discard" deletes the branch.
  5. Commits the page doesn't see. superpowers commits after every small task, with its own messages. epic finds a phase's commits by their subject (P3: Name -- ...), so those commits never reach the page.
  6. Agents nobody listed. superpowers starts an agent per task, plus reviewers. Spell's rule is that every agent is named and listed (epic agents); these wouldn't be, and many more would run than Spell's five.
  7. Decisions in two places. superpowers writes its "Rulings" into a ledger file that's deleted at the end; epic writes judgement calls onto the page for you to review.
  8. Tests first vs. tests after. superpowers deletes code written before its test; Spell's house style (WWOD §1) says the code is the spec and tests are rewritten to match it. A real difference of taste, not a bug.
  9. Session start. Both plugins hook session start; they don't collide, but superpowers adds about 65 lines of "EXTREMELY IMPORTANT" text to every session, every /clear and every compaction.
  10. No skill names collide: every superpowers skill is named superpowers:..., and none shares a name with epic's.

5. Checked against its source (2026-11-11)

Each clash above, checked against superpowers' own files: version 7.0.2, commit 22f0b463 (2026-11-03), read only, nothing run. Of the ten above, eight happen as written, one doesn't, and one is still a guess. Seven more turned up: two happen, two are still guesses, three don't happen.

  • CONFIRMED: the skill's own words say it happens.
  • DOESN'T HAPPEN: its words, or epic's, rule it out.
  • STILL A GUESS: it depends on what the model does with the words; only a live run (the trial todo, T71) can tell.

The key fact for options A and B: how a project tells superpowers to stand aside

  • There's no setting. No config file, no switch per skill, no environment variable; the only variable it reads turns off the visual companion's usage count.
  • The one way is the agent's instructions. Its always-on skill ends by saying the person's instruction files and direct requests win over its skills.
  • Those files are named: CLAUDE.md, AGENTS.md, GEMINI.md. Another plugin's skill (the epic skill), or text another plugin's hook adds at session start, isn't on that list. Whether the model treats epic's words as "your instructions" is still a guess; a line in the repo's own AGENTS.md or CLAUDE.md is certain to count.
  • Its worktree, design and plan skills each say a place set in your instructions is used without asking.
  • Agents started by another agent skip the always-on skill entirely, so epic's named background agents aren't pushed into brainstorming.

From its always-on skill, using-superpowers, its last lines: 

## User Instructions

User instructions (CLAUDE.md, AGENTS.md, GEMINI.md, etc, direct requests) take precedence over skills, which in turn override default behavior. Only skip skill workflows or instructions when your human partner has explicitly told you to.

Its first lines, for agents started by another agent:

<SUBAGENT-STOP>
If you were dispatched as a subagent to execute a specific task, ignore this skill.
</SUBAGENT-STOP>

And the places it lets your instructions set:

  • worktrees: "Has the user already indicated their worktree preference in your instructions? ... Honor any existing declared preference without asking."
  • design docs: "Your human partner's preferences override both."
  • plans: "(User preferences for plan location override this default)"

Clash Verdict What its source says
1. Who plans STILL A GUESS
  • Its always-on skill says to use any skill with "even a 1% chance" of applying, and "Let's build X → brainstorming first"; brainstorming says "You MUST use this before any creative work".
  • But typing /epic seo is itself a direct request, which it says wins; and brainstorming says "Never ask what the project or their context already answers, or reopen what they've already decided".
  • Its plan-mode trigger never fires: epic never enters plan mode (below, the new ones).
  • The live run looks for "Using brainstorming to ..." after /epic, a question in the chat instead of on the page, and a design file under docs/superpowers/specs/.
2. Two plans CONFIRMED, if brainstorming runs
  • The design doc goes in the code repo, "committed"; the plan file is saved beside it, in docs/superpowers/plans/.
  • Both only happen when clash 1 does: they're the steps after brainstorming.
3. Worktrees CONFIRMED, and better than feared
  • Its first step checks whether the session is already in a worktree, and if so makes none. An epic's session is always in its worktree first, so inside an epic superpowers never makes a second one.
  • It asks first only when your instructions don't say: confirmed.
  • The install is confirmed, and worse: it runs even when it skipped making the worktree (below, the new ones).
  • Without a worktree tool of the agent's own it makes one under .worktrees/ in the repo, unless your instructions name a folder.
4. Two ways to finish CONFIRMED, one detail wrong
  • It offers exactly three: merge into the base branch here, push and open a pull request, or keep the branch.
  • Section 4's "discard" is wrong for 7.0.2: it isn't offered. It deletes the work only when you ask for it in so many words and then type discard.
  • Its merge is a bare one: it goes to the main checkout, switches it to the base branch, pulls, merges and runs the tests. None of epic's steps: no changelog, no regenerated files, no epic page.
  • It removes only the worktrees it believes it made, under .worktrees/ or worktrees/; "Everything else belongs to the host". (A trap in that wording: below.)
5. Commits the page doesn't see CONFIRMED, if its plans are used
  • Its plan template ends every task with a commit, its example message feat: add specific feature.
  • epic files a commit by its subject's phase name or <epic> I3:; those never match.
6. Agents nobody listed CONFIRMED
  • Its plan runner starts an implementer and a reviewer for every task, one task at a time, plus a final reviewer: two per task in all, never named or listed.
  • Not many at once, but a ten-task plan is over twenty agents, past Spell's five for a task. In Owen's own setup, his CLAUDE.md rule (every agent named and listed) should win, by superpowers' own rule; anyone else's epic gets no such line.
7. Decisions in two places CONFIRMED
  • Rulings go in a git-ignored ledger in the working tree, under .superpowers/sdd/, deleted when the plan's final review is clean.
  • Before that, every ruling is copied into the agent's final message, "Rulings I made": so they reach the chat, never the page.
8. Tests first vs. tests after CONFIRMED "NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST ... Write code before the test? Delete it. Start over."
9. Session start CONFIRMED
  • Its hook pastes its whole always-on skill, 65 lines, wrapped in "EXTREMELY_IMPORTANT", on start, /clear and compaction (not on resume).
  • No collision: epic's session-start hooks are separate scripts, and add text only when the worktree is behind main or a sync stopped on a conflict.
10. No skill names collide DOESN'T HAPPEN (no collision)
  • Its 15 names and epic's 20 share none.
  • In Codex too: epic links its skills into the shared skills folder (~/.agents/skills), while superpowers comes in as a Codex plugin from Codex's marketplace; and the names differ anyway.

11. An npm install inside an epic's worktree CONFIRMED
  • Its worktree skill, finding the session already in a worktree, skips straight to its set-up step, which runs npm install for any repo with a package.json, then the tests.
  • So in an epic it would run npm in a yarn repo (Spell's, or anyone's): a stray npm lockfile and a second layout in the shared install. epic has already run its own install command by then.

12. Its finish could remove an epic's worktree its own way STILL A GUESS
  • It removes a worktree "under .worktrees/ or worktrees/", meaning its own folder in the repo.
  • But every epic worktree's path holds those words: epic's default folder is ../<repo>.worktrees (Spell's, spell.worktrees), and Claude Code's own is .claude/worktrees.
  • Read literally, after a local merge it would remove an epic's worktree with a bare git command: the worktree's servers left running, its window file left, none of /epic done.

  • The key fact above: a line in the repo's own instruction files is certain to win; the same words in the epic skill, or added by epic's session-start hook, may or may not.

6. The ways to go

The four ways, what each takes and what breaks, are in the question below (Q71). In short:

  • Side by side, epic in charge, borrowing two disciplines (recommended): epic says where superpowers stands aside, and uses its test, debugging and proof skills inside a phase.
  • Side by side only: the same rules, nothing borrowed.
  • Compatible: epic writes its phase plans as superpowers plan files, and reads a superpowers design doc in as a new epic.
  • Nothing: say what epic gives a superpowers user, and leave it there.

An evaluation of superpowers against epic, its clashes and the ways to integrate, on this page; then the way you pick, built: recommended, epic stays in charge and borrows superpowers' test, debugging and proof disciplines inside a phase.

The recommended way, option A of the question: epic stays in charge of the plan, the worktree and the finish, and uses superpowers' disciplines inside a phase. If you pick another option, this plan is rewritten before anything is built.

  1. Try both together first, in a throwaway repo (as P71's proof did), with superpowers loaded for that one session only (claude --plugin-dir), never installed into your Claude Code.
    • Run /epic sp-test with one small phase, and write down what really happens for each clash in section 4: does brainstorming take over, where the worktree lands, whether a plan file or npm install appears, what the commits say.
    • The clashes marked "a guess" become facts, or drop out.
  2. Tell superpowers where to stand aside, in the words it already obeys (its skills say your own instructions win, and that a plan's or worktree's place set there is used without asking).
    • One short paragraph, "With superpowers installed", in the epic skill and in its plain guide (one copy of the words, as the guide's rule says): in an epic, the epic page is the design and the plan; /epic makes the worktree; /epic done finishes; so no brainstorming, writing-plans, executing-plans, subagent-driven-development, using-git-worktrees or finishing-a-development-branch.
    • Inside a phase, DO use superpowers' test-driven-development (where the repo wants tests first), systematic-debugging (for any issue found) and verification-before-completion (before closing the phase).
    • The same few lines added to session start in an epic's worktree only, through one of epic's existing session-start hooks (no new hook), and only when superpowers is enabled: it's what reaches the agent at the same moment superpowers' own text does.
  3. Borrow two disciplines for every epic, superpowers or not, in epic's own words, crediting superpowers (MIT, so a copy is allowed with its notice; borrowing the idea needs none):
    • Proof before done: a phase's Done list names the checks run and what they printed (test count, lint, the command), as Spell's house style already asks of a reply.
    • A plan check before a phase closes: one named agent (<epic>-p<N>-check) reads the accepted build plan and the phase's diff, and lists what the plan said that wasn't built, and what was built that it didn't say. Each miss is filed as an issue, calm unless it changes what you asked for. The coherence review checks it against the coherence and designer agents first, so it's one more kind of review, not a second review mechanism.
  4. Say so for people who use superpowers: a short section in epic's settings README ("With superpowers"): what to expect, what epic tells it, and that test-first is the repo's call.
  5. Left out, as todos: epic writing a phase plan as a superpowers plan file, and reading a superpowers design doc in as a new epic (option C). Worth it only if the devs you know ask for it.
  6. Checked by: the throwaway run again after steps 2-3, each clash in section 4 marked fixed, stands, or never happened; the epic tests and lint pass.
