  • One command instead of six steps. You type spell runbook start netbox-demo, and it takes you through the rest.
    • It stops wherever you stop: the next start carries on from that step.
    • spell runbook status netbox-demo says which steps are done; reset starts over.
  • Each step is one of three things.
    • Something to do by hand: the exact words, the link, what you should see. It offers to open the link, then waits for Enter (done), s (skip) or q (stop).
    • A value to type in, such as a token. A secret one isn't shown as you type, and is kept where only you can read it.
    • A command it runs for you. It must succeed, and it can also say what the command should print, as the README examples do. A check is just a command too (curl -f ...).
  • Values flow into later steps by themselves. Each one is handed to the commands as an environment variable, so there's no export step, and no new template syntax.
  • Secrets stay secret.

    • A command that prints one has it replaced by its name, as the page server already does for place keys.

About 10 minutes, in one sitting:  the demo wipes itself every night at 04:00 UTC.

## Make an account

Open [demo.netbox.dev](https://demo.netbox.dev/plugins/demo/login/).
Leave Username and Password empty, and click **Create & Sign In**.

Should:  NetBox's home page, signed in as `user` and a number, top right.

## Make a token

Click your user name, top right, then **API Tokens**, then **Add a Token**.
Leave everything as it is:  Version v2, Enabled and Write enabled ticked.
Description:  `spell`.  Click **Create**.

```ask NETBOX_TOKEN secret
Paste the whole token:  it starts nbt_ and has a dot in the middle
```

## Make the NetBox place

```sh
spell place ingest https://demo.netbox.dev --kind "web server" --spec "https://demo.netbox.dev/api/schema/?format=json" --key-secret NETBOX_TOKEN --name netbox --into NetBox.api.spell --no-examples --no-ai
```

```sh
spell place verify NetBox.api.spell
```


A runbook: a short file of steps that a new command, spell runbook start, walks you through.

It runs the commands itself, tells you exactly what to do by hand and waits, asks for a token without showing it, and remembers where you got to.

What a runbook file is written in.

  • It reads as plain instructions even without the tool: on GitHub, in VS Code's preview, in an epic page's link.
  • A step is a heading; a command is a sh block, with an optional Output fold, as the README examples are.
  • A value to ask for is a small ask block.
  • Agents already write steps this way, so their reply becomes the file.
  • Exact, and easy to check: { do: "...", run: "...", ask: "NETBOX_TOKEN", should: "..." }.
  • But long instructions with links and code inside are awkward in strings, and it doesn't read as a document.

Where a secret you type in (a token) is kept.

  • One file per secret, in ~/.spell/secrets/: only you can read it, as Spell's place sign-ins are kept.
  • Spell's places read it when the terminal doesn't have the key, so spell place verify works in a new terminal too.
  • Never in a repo.
  • The system's own encrypted vault.
  • Mac only, and it can pop up an "allow access" dialog the first time a command reads it.
  • Kept in memory, handed to the walk's commands, never on disk.
  • But you paste it again every time, and a command in another terminal still needs an export.

What the command is called. Not spell run: that already compiles and runs a Spell project, and "run page" already means a command that stopped to ask you on a page.

  • "Runbook" is the usual word for exactly this: steps, some by hand, some commands.
  • Noun then verb, like every other spell command.
  • Reads well for NetBox.
  • But not every runbook is a setup: a release checklist, a demo before a meeting.
  • Plain, but "steps" is already a word in the epic pages and the manual tests.
  1. Move the shared pieces down first, so the runbook uses them rather than copies.
    • The hidden-typing prompt goes beside the kit's other terminal questions: askSecret(), next to ask() and choose(). The app's mail setup then uses it.
    • The README examples' reader (a command block, its Output fold, and the ... matching) moves into the kit's command base; the README tester uses it from there, still runnable by plain node.
    • A small secret store, SRV.Secrets: one private file per secret in ~/.spell/secrets/, written the way place sign-ins are. The place keys read the environment first, then it.
  2. The runbook reader, Runbook: the settings at the top (title, folder, fresh until), a step per heading, each step's kind from its blocks. A mistake names the step and the line.
  3. The walk, RunbookWalk:
    • a by-hand step: its words, offer to open its link, then Enter, s or q
    • an ask: the question, hidden for a secret; plain values kept with the progress
    • a command: run in the runbook's folder with every value in its environment, its output shown with secrets replaced by their names, checked against its Output fold
    • a failure: stop there, show its "If not:", and start from that step next time
    • progress in ~/.spell/runbooks/<name>.json5 (never a secret), dropped after its "fresh until" time
  4. The command, spell runbook start | status | reset | list | check, in the kit's own commands. A name finds the file in any folder's runbooks/, or an epic's epics/<epic>/runbooks/; a path works too.
  5. NetBox's runbook, written from I107's reply, beside the code it drives: the parser folder's runbooks/netbox-demo.runbook.md. A More Details card on the data epic's I107 points at it.
  6. The rule for agents, in one place, the kit's agent instructions ("Commands"): three or more steps for you, with commands to type, become a runbook, and the reply gives the one command. The epic skill's reply rules and the manual tests' guidance point at it; the epic guide's build topic gets a line.
  7. Keep the docs true: the commands page (a row, and runbook in its nouns), its check; the CLI's README page; the word list ("runbook", beside "run page"); the catalog of mechanisms ("Walking a person through steps").
  8. Tests: the reader (each kind, each mistake), the walk on a fake terminal (resume, skip, stop, a failing command, fresh-until), the secret store (private file, never printed), and the README tester still passing.
