The docs toolbars fit their titles to the row (the longest titles shorten first, with "…", and once any title would be cut under 50px the whole row shows icons only), but that behaviour lives in spell-epic's docs runtime, not in Spell UI. No other page can have it, and the runtime has to measure Spell UI's shadow boxes from outside:

  • fitTitles(), titleFit(), titleCap() and keepFitted() (a ResizeObserver on the toolbar, its row and each item's box, plus the fonts loading), with MIN_TITLE_PX = 50
  • its look in spell-toolbar.css: --spell-toolbar-title-max, .spell-toolbar-icons, .spell-toolbar-label, and the segmented exception
  • a refit by hand whenever the row changes (the comments' bullhorn, fitToolbar), since nothing watches what's in the row

  • <ui-menu fit="titles"> and <ui-toolbar fit="titles"> fit their items' titles to the row, as the docs toolbars do today:
    • every title whole while they fit
    • then the longest give way first, down to one width, each ending in "…"
    • once any title would be cut under the minimum (--ui-menu-title-min, 50px), the whole row shows icons only: :state(icons-only)
    • still too wide: a toolbar scrolls, with its ‹ › keys
  • With the titles gone, each item's title is its tooltip, and still its accessible name.
  • Without fit, nothing changes: no new markup, a toolbar scrolls as now. A segmented menu keeps scrolling.
  • The docs runtime just writes fit="titles", and its own copy of the fitting goes, code, styles and test.

A new fit attribute on the menu (and so the toolbar), one small helper class beside the menu that measures and fits, a title box and a badge slot on <ui-item>; the docs runtime then uses it and deletes its own.

  1. The public API, on <ui-menu>; <ui-toolbar> gets it all for free, as its vocabulary is built on the menu's:
    • fit: how the items fit the row. none, the default: as today. titles: the titles shrink, then go. An enum like the item's kind, so it draws no class word. Spanish: ajuste, values ninguno (shared) and títulos. (Open question 1.)
    • --ui-menu-title-min, a public token, 50px: the narrowest a title may be cut before the row goes to icons. Read through its alias, --_ui-menu-title-min, as every menu token is.
    • The cap itself, the widest a title may be right now: --_menu-title-max, written by the menu on its own box, which its items inherit. Plumbing no page sets, so it takes that shape, not a public token's alias (spell-ui's rule, epic wwod-spell-ui Q13).
    • :state(icons-only) on the menu while the titles are gone, so a page can style the icon-only row (the docs make each button 34px square).
    • On <ui-item>: a title part (its title box) and a badge slot and part, for counts that must stay when the title is cut or gone. Spanish titulo and insignia, both already in the shared words. (Open question 2.)
    • Checked against ui-gaps' renames: fit clashes with nothing (fitted became padding), names one concept, and takes words as values, as padding, align and wrap do; badge is the word ui-gaps chose for a count. The member-clash test covers the component's own members.
  2. How the item shows its title. While its menu fits titles (the menu says so in the item context it already hands every item), <ui-item> wraps its default slot in <span class="title" part="title">:
    • one line, cut with "…" at --_menu-title-max
    • icons only: the box is squeezed to nothing and clipped, not removed. So its text still names the item for a screen reader, and its natural width can still be measured without showing it again (no flash). Its gap after the icon goes too.
    • icons only: the item's title is also its box's tooltip (title): its label, else its text. A title or aria-label the page wrote wins.
    • a menu without fit draws no title box, so a vertical menu's sub-menu or an input inside an item is never clipped
    • <ui-action>'s own title box (it already has a title part) becomes the item's, one drawing for both
  3. Where the code lives: one helper class, TitleFit, in ui-menu/TitleFit.ts, beside SegmentedThumb and shaped like it:
    • the pure maths, moved from the docs runtime as statics: TitleFit.cap(widths, room) (was titleCap()) and TitleFit.fit(widths, room, min) (was titleFit(), the minimum now a parameter): "whole", a width, or "icons"
    • start() measures the menu's box: its width, less its padding and gaps, less every other thing in the row (a button, the bullhorn), less each item's icon, badge and padding; what's left is the titles' room
    • it refits when any of those change size (a ResizeObserver on the box, each item's box and each other slotted element), when the slot's children change, and when the fonts load; it writes only when the answer changed, so it can't loop
    • each title's spacing is counted whether it shows or not, so the answer is the same from either side: a width between "icons" and "titles" never flips back and forth
    • the minimum is read as a length (px, or em of the menu's font size)
    • UIMenu runs it as it runs the thumb: @E.onChange("isReady", "fit") starts it on the top menu, its cleanup stops it; the answer is an @E.state member, and @E.cssState("icons-only") follows it. Never on a server: the static render draws the titles whole.
    • the lint guard: a raw ResizeObserver is allowed in component files (the lint patterns test lists it as valid; the toolbar, the button group and the thumb use one), so no disable comment
  4. Segmented menus keep scrolling: a segmented menu ignores fit, with a development warning; a single choice whose labels vanish is a different control. The docs runtime doesn't ask for it there anyway. (Open question 3.)
  5. Items with no icon: they can't go to icons only, so a row holding one never does; it caps down to the minimum and then overflows (a toolbar scrolls), with a development warning naming the item. Every docs toolbar item has a mark already. (Open question 4.)
  6. Moving the docs runtime onto it:
    • toolbarMenu() writes fit="titles" on a titled toolbar that isn't segmented (today's fitsTitles())
    • toolbarItem(): the title straight in the item (no span.spell-toolbar-label), its access letter's <u> inside it as now; the badges in slot="badge"
    • deleted: fitTitles(), fitsTitles(), titleFit(), titleCap(), keepFitted(), MIN_TITLE_PX, TITLE_MAX, the fitToolbar option through wireComments() and the comments, and both keepFitted() calls (the page runtime's and Epic UI's band); the menu watches its own row now
    • spell-toolbar.css: .spell-toolbar-icons becomes :state(icons-only) (the square buttons, the letter marks shown only then); the .spell-toolbar-label and --spell-toolbar-title-max rules go
    • the two bundles rebuilt (bundle-spell-ui.js: spell-ui.js, spell-comments.js); titleCap.test.ts deleted, its cases moved
  7. Tests and docs:
    • TitleFit.cap() / TitleFit.fit(): the old cases, plus a minimum other than 50 and the no-flip width
    • browser tests for <ui-menu fit> and <ui-toolbar fit> at three widths (whole, cut, icons only): the cap, :state(icons-only), the tooltip, the accessible name (axe too); a resize and an added button refit; a segmented menu still scrolls; a toolbar too wide even as icons shows ‹ ›; no fit, no title box; the static render draws the titles whole; the Spanish tag fits the same
    • a Fitting titles example in each family's elements examples (three rows at fixed widths), so the visual tests take it; baselines updated in this change, after looking at every diff
    • both components pages: a "Fitting titles" example in a box you can drag narrower, its usage and accessibility lines; yarn site:build and site:check on both
    • Spell UI's notes (grammar's Menus, the menu's token table, status) and spell-epic's src/AGENTS.md (the toolbar's fitting is now the menu's)
    • then yarn review in spell-ui and spell-epic, and check-spell on a guide, a details page and an Epic UI page at 1200px, 400px and phone width
  8. Estimate: 8-12h. Spell UI's part (API, helper, item, tests, pages, baselines) about 6-9h; the docs runtime's move and its checks 2-3h.
  9. Open questions, each with what I'd do:
    1. The attribute's name: fit="titles" (recommended: a short concept word, room for other fits later), or overflow="shrink", or a bare switch fit-titles?
    2. How the item's title is cut: a title part around its default slot, and counts in a new badge slot (recommended: plain <ui-item>Questions</ui-item> keeps working), or a title slot pages must fill?
    3. A segmented menu with fit: ignored with a warning (recommended), or fitted like any other?
    4. A row with an item that has no icon: never icons only, with a warning (recommended); or that item shows its title's first letter as its icon, as the docs' letter marks do?
    5. Icons only: just :state(icons-only) (recommended), or also Fomantic's icon menu class word, which re-pads and centres every item?
    6. Should <ui-toolbar> fit by default? Recommended no: a toolbar scrolls by default, as its page says; fit="titles" opts in.
