The docs toolbars fit their titles to the row (the longest titles shorten first, with "…", and once any title would be cut under 50px the whole row shows icons only), but that behaviour lives in spell-epic's docs runtime, not in Spell UI. No other page can have it, and the runtime has to measure Spell UI's shadow boxes from outside:

  • fitTitles(), titleFit(), titleCap() and keepFitted() (a ResizeObserver on the toolbar, its row and each item's box, plus the fonts loading), with MIN_TITLE_PX = 50
  • its look in spell-toolbar.css: --spell-toolbar-title-max, .spell-toolbar-icons, .spell-toolbar-label, and the segmented exception
  • a refit by hand whenever the row changes (the comments' bullhorn, fitToolbar), since nothing watches what's in the row

  • <ui-menu shrinkable> and <ui-toolbar shrinkable> fit their items' titles to the row, as the docs toolbars do today (Q29):
    • every title whole while they fit
    • then the longest give way first, down to one width, each ending in "…"
    • once any title would be cut under the minimum (--ui-menu-title-min, 50px), the whole row shows icons only: :state(icons-only)
    • really tiny, even as icons: every item folds into one overflow button, "…", which opens a menu of them all, each with its icon and title
  • With the titles gone, each item's title is its tooltip, and still its accessible name.
  • Without shrinkable, nothing changes: no new markup, a toolbar scrolls as now. A segmented menu keeps scrolling.
  • The docs runtime just writes shrinkable, and its own copy of the fitting goes, code, styles and test.

  1. The public API, on <ui-menu>; <ui-toolbar> gets it all for free, as its vocabulary is built on the menu's:
    • shrinkable, a boolean: the titles shrink, then go, then the items fold into the overflow button. Off, the default: as today. Spanish: encogible. Decided in Q29.
    • --ui-menu-title-min, a public token, 50px: the narrowest a title may be cut before the row goes to icons. Read through its alias, --_ui-menu-title-min, as every menu token is.
    • The cap itself, the widest a title may be right now: --_menu-title-max, written by the menu on its own box, which its items inherit. Plumbing no page sets, so it takes that shape, not a public token's alias (spell-ui's rule, epic wwod-spell-ui Q13).
    • :state(icons-only) on the menu while the titles are gone, so a page can style the icon-only row (the docs make each button 34px square).
    • On <ui-item>: a title part (its title box) and a badge slot and part, for counts that must stay when the title is cut or gone. Spanish titulo and insignia, both already in the shared words. (Q30)
    • Checked against ui-gaps' renames: shrinkable clashes with nothing, and is a plain switch, as segmented and vertical are; badge is the word ui-gaps chose for a count. The member-clash test covers the component's own members.
  2. How the item shows its title. While its menu is shrinkable (the menu says so in the item context it already hands every item), <ui-item> wraps its default slot in <span class="title" part="title">:
    • one line, cut with "…" at --_menu-title-max
    • icons only: the box is squeezed to nothing and clipped, not removed. So its text still names the item for a screen reader, and its natural width can still be measured without showing it again (no flash). Its gap after the icon goes too.
    • icons only: the item's title is also its box's tooltip (title): its label, else its text. A title or aria-label the page wrote wins.
    • a menu without shrinkable draws no title box, so a vertical menu's sub-menu or an input inside an item is never clipped
    • <ui-action>'s own title box (it already has a title part) becomes the item's, one drawing for both
  3. Where the code lives: one helper class, TitleFit, in ui-menu/TitleFit.ts, beside SegmentedThumb and shaped like it:
    • the pure maths, moved from the docs runtime as statics: TitleFit.cap(widths, room) (was titleCap()) and TitleFit.fit(widths, room, min) (was titleFit(), the minimum now a parameter): "whole", a width, or "icons"
    • start() measures the menu's box: its width, less its padding and gaps, less every other thing in the row (a button, the bullhorn), less each item's icon, badge and padding; what's left is the titles' room
    • it refits when any of those change size (a ResizeObserver on the box, each item's box and each other slotted element), when the slot's children change, and when the fonts load; it writes only when the answer changed, so it can't loop
    • each title's spacing is counted whether it shows or not, so the answer is the same from either side: a width between "icons" and "titles" never flips back and forth
    • the minimum is read as a length (px, or em of the menu's font size)
    • UIMenu runs it as it runs the thumb: @E.onChange("isReady", "shrinkable") starts it on the top menu, its cleanup stops it; the answer is an @E.state member, and @E.cssState("icons-only") follows it. Never on a server: the static render draws the titles whole.
    • the lint guard: a raw ResizeObserver is allowed in component files (the lint patterns test lists it as valid; the toolbar, the button group and the thumb use one), so no disable comment
  4. Segmented menus keep scrolling: a segmented menu ignores shrinkable, with a development warning; a single choice whose labels vanish is a different control. The docs runtime doesn't ask for it there anyway. (Q31)
  5. Items with no icon: they can't go to icons only, so a row holding one never does; it caps down to the minimum and then goes straight to the overflow button, with a development warning naming the item. Every docs toolbar item has a mark already. (Q32)
  6. The last stage, the overflow menu (Owen, 2026-10-25: "if it's really really tiny, go to hamburger or ... menu"):
    • when even the icons don't fit, the items fold into ONE overflow button, which opens a menu of every item, each with its icon, title and count; :state(overflow) on the menu while it shows
    • which items stay in the row: none, the row's other things (a button, the bullhorn) stay, the selected item ticked in the menu (Q35)
    • its button: "…" (ellipsis horizontal), titled "More" (Spanish "Más"), its title its tooltip and accessible name; a page's own in slot="overflow" (Spanish desborde) (Q36)
    • counts: summed on the button, each in its own row; a dot for counts that aren't numbers (Q37)
    • a shrinkable toolbar no longer scrolls: this stage replaces its ‹ › keys; one that isn't scrolls as today (Q38)
    • TitleFit.fit() gains a fourth answer, "overflow": when the icons, their spacing and the button's room add up to more than the row has; the same no-flip rule as icons only
    • the menu is a <ui-popup> on the button holding a <ui-menu vertical>; its rows are drawn from the page's items (as <ui-dropdown> reads its items, SlottedItems), and picking one clicks the real item, so the page's own listeners still run
    • keyboard and ARIA: the button has aria-haspopup="menu" and aria-expanded; Enter, Space or ↓ opens it on the selected item (else the first); ↑ ↓ Home End move; Escape closes it and puts focus back on the button; Tab closes it; the rows are menuitem, a selected one menuitemradio with aria-checked
