A repo on GitLab, gitlab.com or self-hosted, gets the same automatic setup as a repo on GitHub. This is I248, and it is being built now: nothing below is finished yet.

  • A new setting, codeHost, will say github or gitlab.

  • One chooser will pick between two host classes: GitHub, and a new GitLab that uses the glab command.

  • epic will detect a protected main, and open and find merge requests.

epic will work out whether a repo is on GitHub or GitLab, and use the right tool for it.

A GitLab repo will get the same setup, with merge requests where GitHub has pull requests.

One new command, epic pr <name>, will replace the gh pr steps in the skills.

epic init now sets up a repo on GitLab, gitlab.com or self-hosted, the way it does on GitHub. It’s published as 0.8.9.

Still rough, or not tried:

  • Nothing has run against a real GitLab or a real glab yet. The runs below used a stand-in.
  • Some of the GitLab API’s field names, and what glab mr create prints, come from its documentation and are unconfirmed.
  • GitHub Enterprise isn’t handled.

What was built:

  • A setting, codeHost: "github" or "gitlab", worked out from the host part of the remote’s address. When the address doesn’t say, you pass epic init --host, or epic asks you one question.
  • One chooser, CodeHost: it picks between GitHub and a new GitLab class that uses glab.
  • epic init on GitLab:
    • it creates the shared epic repo and removes the protection on its main, so your teammates can push to it
    • where your code’s main is protected, it puts the setup on a branch and opens the merge request
  • epic pr <name>: it replaces the gh pr steps in the skills.
  • epic worktree remove --branches: it now knows a squash-merged merge request, and deletes that branch.
  • The rest: commit links on the epic pages go to GitLab, the wording says “merge request” there, and the README has a section, “On GitLab”.
GitLab: codeHost, GitLab beside GitHub behind one chooser, and epic pr <name>0.8.9
  • The two host classes and the chooser: GitHub, GitLab, the chooser.
  • The code that uses them: RepoInit, Worktrees, PlanCommits, EpicConfig.
  • The three skill files with gh pr steps.
  • README-epics.md and epic’s command README.

How this will be checked:

  • Tests with a stand-in glab.
  • An end-to-end run against a local remote that refuses pushes to main.

What this won’t show: it hasn’t been tried against a real GitLab yet, and glab isn’t on this machine.
