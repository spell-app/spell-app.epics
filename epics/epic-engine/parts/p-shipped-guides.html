Spell's guides are only on the epic pages' site, in the epic repo: nobody who installs Spell gets them, and there's no way to read them in the app.

A subset of the guides ships with Spell, and people read them in the Spell app. This is about Spell, not epics.

    • Ship a subset of the guides with Spell, read in the Spell app, from the installed package.
    • One copy: the shipped guides move out of the epic repo into the code repo. "We could make aliases in our epic folder here."
    • "This should be easy for other people to set up -- generic stuff vs repo-specific."
    • "Would be fine if this was saga-by-saga."
  • You pick which guides ship. A choice page lists the candidates with a recommendation for each (being made now, by the epic-engine-guide-pick agent); this phase starts from your picks.
  • One copy, in the code. A shipped guide lives in the kit, versioned with the code it explains, and is edited on a branch like any other file.
    • The epic repo no longer has its own copy.
    • A whole saga's guides can move together.
  • Nothing breaks in the epic folder. The moved guides keep their addresses ("aliases in our epic folder"): the Guides list page, saga pages, See Also boxes, links and comments all still find them.
  • Generic, not Spell's own. Any repo using epics says where its guides folder is in its epic settings, and the epic tooling does the rest. Nothing in the mechanism names Spell.
  • Each shipped guide says who it's for and its topic.
    • Who: people making things with Spell, or programmers working on Spell.
    • A topic, and whether it's one of the short "Start here" set.
  • A Guides page in the Spell app, read from the installed package, not from the epic pages:
    • listed by topic, a short "Start here" set on top
    • the programmers' guides folded under their own heading
    • a search box
    • the app's home page shows only "Start here", and a link to the Guides page
  • The guides you pick move out of the epic repo into the code, versioned with it and edited on branches, and ship in the spell package.
  • The epic folder keeps them at their old addresses, so the Guides list page and every link still work; any repo using epics can do the same.
  • The Spell app gets a Guides page: by topic, "Start here" on top, the programmers' ones folded, a search box.

How the epic folder keeps a moved guide at its old address ("aliases in our epic folder").

  • The page server already serves the checkout's file before the epic folder's, so the address works with nothing added.
  • A worktree's address shows that branch's copy: you review a guide's change where it's made.
  • Works on any machine, and in any repo that declares a folder.
  • Like the kit's other links; the epic tools need no change.
  • But one epic folder serves every checkout, so a link only ever shows main's copy; a branch's edit is invisible until merged.
  • The epic repo is pushed to GitHub: on another machine the links point at nothing; and Claude's Edit refuses to write through a link.

Where the code's guides folder is in the kit.

  • The address is the file's path, so nothing needs mapping.
  • One place to look; ships as one entry.
  • Closest to its code, but the addresses change, and the page server needs a map from address to folder.

Where "who it's for" and the topic are written.

  • As the saga meta already is: the facts travel with the page, and a moved page keeps them.
  • Easy to read and reorder in one place, but a second thing to keep in step with the pages.

How the app shows one guide.

  • The guides are Spell UI pages, which the app already loads: it shows the body in its own page, theme and dark mode included.
  • The epic site's header, comment button and editing are left out.
  • Looks exactly as on the epic pages' site, but needs the epic site's styles and scripts shipped too, and doesn't follow the app's theme.

The app's home already has a "Guides" section: Spell projects that teach by example, opened in the editor (epic debut). How do they and the shipped guides fit together?

  • The project guides become a topic of the Guides page; either kind can be marked "Start here".
  • The home's Guides section shows only "Start here" and the link, as you asked.
  • Less to change, but two things called guides in one app.

The app is the editor epic's area, and its session may be changing the same files (the home page, the routes). Who builds the app's Guides page?

  • One phase delivers the whole thing; a /send editor says which files, so the two don't collide.
  • The editor epic owns its look and home page; the app page waits on its queue.
  1. Start from your picks. The guide-pick choice page's answers say which guides ship, each with who it's for and its topic; whole sagas where you picked one.
  2. A repo declares its guides folder, generically:
    • one new key in a repo's epic settings, guidesFolder (the kit's: "guides", at its root); left out, a repo has none, and everything works as today
    • EpicConfig reads it; epic init mentions it, commented out; epic config guidesFolder prints it
  3. The moved guides keep their addresses (Choices, first set):
    • the code folder keeps the same paths as the epic folder's guides/, so /guides/solid/solid-2.html stays /guides/solid/solid-2.html
    • the page server already serves the checkout's file first, then the epic folder's: on main it shows main's copy, under a worktree's address that branch's copy, with no link at all
    • a guide's comment inbox (<page>.inbox.json5) and its pictures stay in the epic folder, at the same path: comments are epic things, not code
    • editing a moved guide in place writes the checkout's file, a normal change on that branch
  4. The epic tooling finds guides in both places, through ONE helper on EpicConfig (every folder that holds guides, the code's first): the list pages' writer (epic pages index, the Guides list page's saga sections), Sagas.guides(), SeeAlso, the guide inboxes, doc-links, voice, the page openers.
  5. Moving them: epic guides move <page | SAGA:/id>, run in a worktree:
    • copies each page (and its experiments and images) into the code folder, for the branch to commit
    • takes it out of the epic folder only when that branch merges into main, so main never loses it in between
    • a saga's address moves every guide that names that saga
    • the name follows the commands guide; suggested to you before it's built, and added to the commands page
  6. Who it's for, and its topic (Choices, second set): metas in each shipped guide's head, beside spell-saga: spell-audience (makers or programmers), spell-topic, and spell-start-here. A build step writes one list of them, guides.json5, which ships too, so the app reads one small file.
  7. A shipped guide stands on its own (Choices, third set): nothing in it needs the epic tooling; its breadcrumb, comment button and editing show only on the epic pages' site. A check fails a shipped guide that links an epic page or the epic repo.
  8. The app's Guides page (Choices, fourth and fifth sets), Spell UI elements on Solid 2:
    • a route, /guides, beside the place reference page; a guide at /guides/<path>
    • "Start here" on top, then a <ui-section> per topic, the programmers' guides folded under their own heading, a <ui-input> search over titles and descriptions
    • read from the installed package through spell/package.json, never a path into another folder
    • the home page's guides section: only "Start here", and a link to the Guides page
    • its words in AppTexts, with Spanish; checked with spell voice check
  9. Shipping: the guides folder goes on spellPublish.files; spell publish's scratch install checks the list and every guide it names are there.
  10. Tests: the settings key, the both-places lookup (the Guides list page with one guide in each), the move command, a moved guide served on main and under a worktree, the shipped-guide check, the app page (lists, folds, search, opens one).
  11. Docs: README-epics.md (how any repo ships its guides), the kit's AGENTS "The epic repo", the epic folder's AGENTS "guides/", the app's AGENTS, the commands page, the changelog.
