The epic command on your PATH is a link to main's checkout (~/www/spell/epic/bin/epic). Run inside a worktree, it still runs main's epic code, not the worktree's own.

For most commands that's fine: the epic pages and the epic repo are shared, so main's code edits the same files. But a worktree that changes the epic tool itself, like epic-engine, can't try its own changes through epic. I298's agent had to run ./epic/bin/epic by hand for its dry run.

The spell command already does this hand-off (I282): run inside another installed copy of the kit, it passes the command to that copy's own bin/spell.mjs. And since I287, a page server always runs its own checkout's code. epic has neither.

The catch: epic window and other commands must work in a fresh worktree before yarn install, which is why spell falls back to main's copy there. epic would need the same fallback.

It may also be deliberate that the epic tooling runs main's settled code: one broken worktree then can't break the page tooling for every session. That's a real choice for you.

Fixing it would mean the same hand-off as I282 for epic, either for every worktree, opt-in per worktree, or only in epic-engine's own worktree.
