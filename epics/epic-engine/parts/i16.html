This is I1's problem again, for comments on docs pages instead of epic pages. I found it while checking I1.

  • epic comments gather takes a guide's comments into a phase of epic guide-changes. It marks each one taken: { epic, phase: 7 } (GuideChanges.markTaken(), CommentList.take()), and that phase is stored by NUMBER.
  • The thread then shows "Taken into guide-changes P7", with a link to #p7 (spell-doc-runtime.js, planLink()). An old address like that lands on whatever phase is 7th now.
  • So once add-phase --before 7 runs on guide-changes, the link opens the new phase, not the one the comment went into.
  • Possible fix: markTaken() already has the phase's id (phaseId). Store it in taken too ({ epic, phase, phaseId }), then have the runtime link to #<phaseId> and draw the number from the page, or skip the number. That touches src/tools, the runtime and the spell-ui.js bundle, which were outside this agent's files.
  • PLAN-DOC.md, "Migrations", already lists taken: { phase: 7 } as a number kept as a record.

Fixed in P1: a comment taken into a phase now records that phase's stable id and title, and its thread links to the phase by id.

  • GuideChanges.markTaken() passes the phase's id and title, so the comment is stored as taken: { epic, phase, phaseId: "p-memory", title: "Memory", at } (CommentList.take()). Undo (restore()) keeps both.
  • The thread now reads "Taken into guide-changes · Memory" and links to #p-memory (takenInto() in CommentList.ts, used by spell-doc-runtime.js). An insert ahead of the phase no longer moves the link.
  • A comment taken before this fix has no id, so it still reads "guide-changes P7" and links to #p7, as before.
  • Checked by new tests in tests/tool/CommentList.test.ts and tests/tools/GuideChanges.test.ts. The second gathers a comment into P1 · Memory, inserts a phase before it, and checks the link still lands on Memory, now P2.
  • Pages show the new link once spell-ui.js is rebuilt (bundle-spell-ui.js).
