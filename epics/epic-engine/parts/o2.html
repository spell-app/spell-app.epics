so I'm wondering if we even need claude's original "plan mode" at all with epics. Going back and forth in the epic doc is working really well, especially with the bullhorns.

So rather than creating the claude plan being a blocking step, when starting an epic

  • you write the overview, ask your questions, we go back and forth updating the overview as I answer the questions. Overview text gets rewritten with the answers -- updated or new things marked in the text w/ orange text background highlight, collapsed summary of the Q/A inline. I can "accept the change" by clicking on a button next to the hilight, or re-open.
  • Until the overview is done, hide phases/judgement calls/to test/log. So we keep `questions` and `todos` -- and I can promote them to new plans or say "defer."
  • once we agree on the overview, you write the phases and we go back and forth on them as we did with the overview. So phases basically record what we decided.

Once phases are decided, you write the claude plan (if you need to, for you) and start chunking away.

Later on, I can reopen new phases in the same mode -- "Add Phase" just like add todo, with the same back and forth cycle for the new phase(s).

Would also be nice to reorder the open phases, and mark "do in parallel" or "do at bedtime" somehow

As things continue, questions relevant to a phase which are decided update the phase's text with the new plan. You can keep the question/issue/etc, but mark it out as "handled in phase 4".

Part of what is driving this -- once phases start, the overview / phases section kinda becomes useless -- it doesn't reflect what was actually done. And I have to wade through a giant sea of issues/caveats/questions, when much of the stuff was covered in a phase at some point.

Especially when I'm looking back later, I want overview / phases to reflect *what was done* and not have to bother with issues/todos/etc so much. This also relieves some of the burden of the "durable doc" page -- I can just go back and look at the epic.

While you're at it, can `caveats` get merged with `todos`

We should also rethink the "durable doc" thing, in combination with the new `readme` structure. The "durable docs" pass should be updating the READMEs (or, rarely, making a new one) so we don't have two places for a developer to go to understand what was done.

And it would be cool if I can view/comment/edit the readmes within the review tab!

Why

  • Before this, an epic started in Claude's plan mode: a plan file in an editor tab, approved in one go, then copied into the page. The back and forth that works (the page, its bullhorns) only started after.
  • Once building started, the Overview and phases still said what was PLANNED. What was really done was scattered across Done lists, Update blocks and dozens of items.
  • So looking back meant wading through questions, issues and caveats that a phase settled long ago; and the epic's guide repeated what the READMEs should say.

Stage 1: the Overview

Every new epic starts here: epic create writes the Overview stage, and Claude writes the Overview and its questions on the page.

  • The page shows only the Overview, Questions and Caveats. Phases, judgement calls, To test and the log are hidden: the file still has them, it's a view.
  • Each answer rewrites the Overview's text where it applies. The changed words are on an orange ground, a small folded chip after them naming the question; unfolded, its title and the answer in short.
    • Nothing to approve: you already answered the question. The orange lasts 3 days, then goes quiet; the chip stays for good, so you can always see why a sentence says what it says.
    • While a mark is new, Reopen sits in a tooltip on its words: it puts the question back to open, and its next answer rewrites the words with a new mark.
    • Claude never waits on the marks: it goes on with the next answer.
  • A caveat raised meanwhile can go to the next phase or be dropped, as before; promoting one to a new epic was not built.
  • The stage ends with the page header's button: the paper plane becomes "Accept Overview", the wand still beside it, so answers keep sending meanwhile (Q14, J117).
  • The Overview says: "Caveats and todos stay two sections."
  • You answer the caveats question (Q16).
  • It now says: "One list, Caveats; todos fold into it", those words in orange, a folded "Q16" chip after them.
  • Three days later the orange goes by itself; the sentence and its chip stay. Reopen, while it's orange, asks the question again.

Stage 2: the phases

  • After Accept Overview, Claude writes the phases, and the Phases section appears.
  • The same back and forth: you comment, Claude rewrites a phase, the change is marked.
  • Each open phase's pills are two in this stage: Looks good, and Defer (it moves after the other phases, still to do).
  • So each phase records what was decided about it, in its own text, not in items beside it.
  • The stage ends the same way: the header's button says "Accept Phases". Once building starts, the paper plane comes back (Q14).

Stage 3: building

  • Before building a phase, Claude writes its own build plan into it (epic update #P3 --plan): "Claude's plan", with an orange rule, and the phase's buttons Accept plan and Revisit.
    • Your Accept plan starts the build. Why: that plan gets into detail you sometimes have an opinion on (M1).
  • A question decided mid-way that's about a phase rewrites that phase's text, marked as changed.
    • The mark makes the question "handled in P4" by itself, the first time it's stamped: grey, out of what needs you, its line linking the phase (Q17, A).
    • Reopen on the rewritten words takes it off again: the item is back, red.
  • While Claude works, the toolbar says so in a word ("Responding", "Building P35"), with what it's answering in a tooltip; "N agents running" opens the agents in a popover.
  • The Overview and the phases always say what was DONE: a phase's text is brought in line with what was built when it finishes, not left as the plan.
  • So the items left showing are the ones still open; the rest has been folded into the text.

Later: more phases, and their order

  • Add phase, on the Phases section: its name and a note go to the session, which drafts it for the same back and forth.
  • To-do phases are reordered by dragging one by its title, and only that: no up / down buttons (Q20, B). Done and active phases never move; epic move does the same from the command line.
  • Phases are renumbered on a move or an insert, never "P4.1": every link, item, Update block and "P8 · Name" in the text follows (r21).
  • Deferred until the new flow works (Q21): the marks on open phases.
    • "In parallel": run beside the next one, in an agent.
    • "At bedtime": left for the next /bedtime.
    • A marked group, "do these all at once, without input": an unattended run, like /bedtime but now. Phases still run in order otherwise (M2).

Todos fold into caveats

  • One list, Caveats (C), holds the todos too: work still to do, or a limit to know about, drawn calmer.
  • Tests are T. epic add #C adds work, --limit a limit, #T a test (#V still works).
  • The migration caveats-and-tests ran on all 55 epic pages: old caveats kept their ids and became limits, todos were renumbered after them, V became T (Q16).
    • Each page's log lists old id to new, so an old "T4" in chat or a commit can be looked up; 133 links in 54 other files followed.

Old epics

  • New epics, and future epics being planned, start in Stage 1 (Q15, A); a page with no stage reads as Building, so it looks as it did.
  • ALL the old epics are being re-done in one lump, in the background, in P36: each gets a stage, and its Overview and done phases rewritten to say what was built.

Deferred: the guide, and READMEs

Deferred: later, after a review of what a guide loses as a README. The rest of the flow was built first (Q18, Q19).

  • The direction (Q18, B): fold the old guides into READMEs, so a developer has one place to go.
    • Sagas correspond to READMEs: N sagas per project.
    • For each guide that might stay a page of its own, ask Owen: the Solid 2 guide would make a good README.
    • The commands get READMEs too.
  • Before that phase: review what would be lost if a guide becomes just a README.md.
    • Maybe better: HTML pages per project, in a folder like dev-docs.
  • Until then, Doc Review still writes the epic's guide and updates the READMEs, as before.
  • Built already (P33): the doc pass floats.
    • a new phase goes before a last Doc Review, and a Doc Review already done is to do again
    • a standing epic (like this one) has none: its short doc pass follows each phase, or each group built together
  • The epic page, saying what was done, is the record for looking back.
  • Also waiting: the 26 guides already written, and where an epic with no code records what it did (Q18).
  • And READMEs in the Review tab, rendered, to read, comment on and edit (Q19): "let's defer this a bit, start the rest of the process first".
