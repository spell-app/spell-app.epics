How I36 is fixed, and the two calls in it.

  • The CSS: Spell UI stacks a <ui-table> below a 768px window unless it says unstackable, and has no page-wide switch for "never" (--ui-table-stack-by only picks the window or the table's own width). So spell-doc.css sets back the flag Spell UI's own stacking rules raise (--_table-stack: 0 on ui-table > table): the value unstackable leaves. Our sheet is unlayered, so it wins over every rule in Spell UI's layers; it's on every page that loads the sheet, epic pages included, so an item's details and a reply are covered (their tables are light DOM, slotted). It names a private custom property: if Spell UI renames it, tables stack again until we follow. The alternative, the docs runtime adding unstackable to every table as the page starts and as parts load: a stacked first paint, and a watcher for every table that arrives later. Better still, later: a public token in Spell UI (--ui-table-stack-by: never), a spell-app change.
  • A table that ASKS to stack (stackable, stack-by) still does, and the migrations leave it, listed: the component creation guide's live demo of stack-by="container" is one, the only one in the content folder outside Spell UI's own ui/ pages. The alternative: never, even there, which breaks the demo.
  • The epic pages' step is unstackable-tables, a step of its own, not part of engine-links: one job per named step, so --step and the log name it; it shares its rule with the docs pages' components-not-markup (unstackTables() in to-components.js), and so does the tool's way in (IncomingHtml). It runs on command, not on every edit, so pages change when the main session migrates them after the merge, not when an agent's edit happens to touch one.
