Only epic pages update in place when their file changes: Spell UI's component-set pages (and any other page) reload and flash, and the page fetches its own new version after being told it changed.

  • The page patch moves out of spell-epic's docs runtime into the kit, as ONE shared patcher every page runtime uses, each with its own hooks.
  • The page server sends the new page down the live-reload line with the change, and the patch is a list of small steps: text edited in place, nothing the reader touched replaced.
  • Spell UI's component-set pages use it, so an edit to one never flashes.
  • Owen (2026-10-25, r29): 'page server, when reloading a live page, sends the new content to the running page. It then runs a diff on current/new HTML and only updates what has changed -- inserting/removing sections, updating prose, leaving <inputs> alone; the insertions should be as granular as possible.' And: 'reload MUST NOT FLASH anything other than what has actually changed!'
  • ONE page patcher, in the kit, plain DOM: it compares the page's source as loaded with the new source, and changes only what differs in the live page.
  • Each page runtime hands it its hooks: which attributes are the reader's (kept), which elements are never replaced (epic-*, an open editor such as Monaco in a cell), which elements manage their own children, what to re-wire after.
  • spell-epic's docs runtime uses it in place of its own copy: epic pages behave as today.
  • The page server pushes the new page and its ETag with the change: no fetch.
  • Finer steps: edited text changes in place, not the whole paragraph; inputs, focus, typed text, folds and scroll are left alone.
  • The patch is a list of steps (insert, remove, set an attribute, set text), so the server could work them out later for multiplayer Spell without the page changing.
  • A page's own save is known by its ETag: it doesn't patch itself.
  • Spell UI's component-set pages (/components/ui/...) use it, through the site's runtime.
