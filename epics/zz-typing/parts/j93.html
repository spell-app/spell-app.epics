epic worktree status <name> took 53 seconds. The time went into Sessions.named(), which looks through every saved session for ones in worktree <name>. It asked which worktree a folder is in for EVERY line naming a folder (hundreds of thousands of lines, 4.5 GB of transcripts), and each ask follows links on disk. The lines name only a few hundred different folders.

Step 1: each different folder is asked once per search (a small map). That alone took it from 53 to 5.5 seconds; what was left was reading every line as JSON.

Step 2: before reading a transcript line by line, one quick text search pulls out every cwd and customTitle value in it (Sessions.mayBeNamed()). If none can match, the transcript is skipped. It looks at every such value anywhere in the file, so it never skips a session the full read would have found; for the rest, the full read is unchanged. Now 3 seconds (2 for a name with no sessions).

Not done: a cache of real paths that lasts the whole process. The epic server runs for days while worktrees come and go, so a cached answer could go stale. A cache that lasts one search can't.

Checked: epic session find gives the same output, old code and new, for seo, epic-eject, epic-engine and repo-split. A new test counts the lookups and line parses for 600 lines naming one folder; on the old code it fails (605 lookups).
