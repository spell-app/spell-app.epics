What today's parser already gives a two-way conversion, and what it doesn't. From the survey of the language at the start of this epic.

The parse keeps every word: the Match tree

Parsing a file builds a tree of matches, one per line and one per piece of a line. It is faithful to the source: nothing the author wrote is dropped. 

- its "color" is:                         <- rule define_property_has, its outline form
    red if its suit is diamonds or hearts <- rule value_if
    black otherwise                       <- rule value_otherwise

Each line's match keeps:
  rule        which wording matched (outline or sentence, "is one of" or "is either")
  tokens      every word, each with the spaces after it
  start, end  where it is in the file
  comments    their own matches:  the "//", the gap before it, the text
  blank lines their own matches
  the "- "    kept as a token of the line
  • The class: Match.
  • One catch: a body's line breaks aren't in a match's own text. The exact source comes from the file, by the match's start and end.

The AST does NOT keep the wording

After the matches, the compiler builds an AST, a tree shaped like JavaScript: classes, getters, methods. It is what every output target writes from.

  • It forgets which wording was used: outline or sentence, is one of or is either.
  • It moves a type's members into its class, even from another file.
  • Every AST node links back to its match, so the words are still reachable from it.
  • So the kickoff's "elemental spell => AST => code spell" has to mean the Match tree (or a chunk model built from it), not today's AST. Writing from the AST would lose the author's words.
  • The class: ASTNode, 84 node classes.

Nothing writes Spell back out yet, except the Spanish translator

  • No pretty-printer, no "Spell writer". The formatter changes only spaces and tabs.
  • The Translator is the precedent: it writes each line again with the SAME rule's syntax in the other language, line for line, layout kept. 
// What the Spanish translator does today, line by line (Translator.ts):
// the same rule's syntax in the other language, its blanks filled from the match
a card is a thing where:                     ->  una carta es una cosa donde:
	- its "rank" is one of ace, 2 ... 10      ->  	- su "valor" es uno de as, 2 ... 10
	- it "is a face card" if ...              ->  	- "es una figura" si ...
// indent, bullet and the gap before a comment are kept;
// a line it can't write keeps its source, marked "// TODO: translate"
  • Code spell to elemental spell can be written the same way: each declaration line, rule by rule, as its tag (Q10).

Tags in Spell today

  • The tokenizer reads any <tag>...</tag> as one piece of markup, even across lines.
    • So today a <spell-view> wrapper would be swallowed as markup, and the spell inside it would not be read as spell lines.
    • Owen: rewriting it is fine (Q8).
  • Only <css> and <markdown> keep their insides as raw text (the parser's rawTextTags).
  • A <markdown> block inside a type is already its description (MarkdownDescription).
  • Named places in a drawing are <children name="header"/>, filled by a child written <h3 in="header">.
  • Spell's own tags already start with spell-: <spell-app> runs an app on a page, and a <spell> block holds spell inside a page's markup.
  • The property editor's elements are <ui-property-editor>, <ui-property-group> and <ui-property> (epic ).

Two forms that compile the same already exist

  • The outline style (- its "rank" is ...) and the sentence style (cards have a rank ...) compile to identical JavaScript.
  • A test checks it, by comparing the compiled output, not the source (outline.test.ts).
  • Hovering an outline line shows its sentence form, "Reads as".

How the editor and language server read a file

  • One SpellFile per file holds its matches, its AST and its compiled code.
  • An edit re-parses only the top-level item it touched: a whole outline type is one item. About 1-2 ms for a comment, 110 ms for all of Solitaire.
  • The language server never parses again: hover, outline, completion and folding all read the matches.
  • The outline view knows types, properties, methods, functions, variables and events; phrases show as methods.
