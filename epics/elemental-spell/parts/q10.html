The two forms must say exactly the same program, always. Which of them does the compiler read, and how does the other one get there?

Owen, 2026-10-24: "it might make sense to have the compile path for elemental spell be: .spellx => .spell => JS/TS/etc". That is option A below, now the recommended one.

  • Either way, only the declaration lines differ between the forms; every body is the same code spell (1.1).
  • The other direction, .spell to .spellx, is rare (Q19): a one-off conversion, the same in A and B. It goes over the Match tree rule by rule and writes each declaration as its tag, as the Spanish translator writes each line in Spanish (1.2).

A: a .spellx file is written into code spell, then compiled as today

A small .spellx reader finds the tags and their raw bodies, and writes the .spell text, in memory. 

 1  <spell-view name="playing card" aka="card" template="two sided view">
 2  	<spell-property name="color" one-of="red, black" alias="is (color)">
 3  		red if it is a diamond or it is a heart
 4  		black otherwise
 5  	</spell-property>
 6  </spell-view>
 
 1  a playing card aka card is a two sided view where:     <- written from line 1's tag
 2  	- its "color" is one of red, black:                  <- written from line 2's tag
 3  		red if it is a diamond or it is a heart          <- line 3, copied
 4  		black otherwise                                  <- line 4, copied
 5  		- it "is (color)"                                <- written from line 2's alias=

the position map:  .spell line 3 = .spellx line 3, same column
                   .spell line 5 = .spellx line 2, the alias="..." attribute
  • Bodies are copied word for word, so the position map is just a shift in indent, line by line.
  • Errors, hover and completion land on the right .spellx line, as Vue and Svelte do for the code in their blocks (1.3). 
Card.spellx, line 3:  "diamond" isn't a suit:  did you mean "diamonds"?
	<- the compiler found it on line 3 of the .spell text, the map sent it to line 3 of Card.spellx

B: one parser reads both

  • Each declaration rule (template, property, phrase, action, drawing, event, css, markdown: about a dozen of the 472) gets a tag form beside its English and Spanish ones.
  • A rewritten tokenizer (Q8) reads a <spell-*> tag as a line with an indented body, instead of one piece of markup.
  • Positions are the file's own: no map.

C: a new chunk model in the middle

  • A tree of chunks (template, property, phrase, action, drawing, prose), each holding its fields and raw body.
  • Both forms are read into it, and printed from it; the compiler reads it too, or it writes code spell.
  • Equal by construction: the compiler only ever sees code spell, so the two can't drift apart.
  • The compiler is untouched; the new code is a small reader plus a position map.
  • Incremental parsing works as today, on the .spell text: an edit in one tag re-writes that tag's lines.
  • Cost: the language server maps every position through the map, both ways (Vue's and Svelte's precedent).
  • A .spellx file may still hold a raw <spell> chunk: copied into the .spell text as it is (Q11).
  • Buys over A: no position map; errors and hover are on the file's own lines.
  • Cost: a dozen rules get a second syntax, and the tokenizer is rewritten for tags with bodies.
  • Cost: "the same program" is held up by tests (compiled output compared), not by construction.
  • Buys over A: the notebook and the per-chunk editors get a tree of chunks to edit directly.
  • Cost: a third representation to keep true to the other two; most work of the three.
  • A already gives the editors their chunks: the .spellx tags themselves.
  • new: a .spellx reader that writes .spell text and a position map
  • new: a one-off .spell to .spellx converter, rule by rule over the Match tree
  • the compiler and the output targets don't change
  • the language server learns to map positions for .spellx files
