A .spellx file is spell in a third style, beside sentences and the outline: spell's own parser reads it, and it compiles straight to JS (Q69, Q70).

  • A spellx tokenizer reads each tag at a line's start as a tag token, so a tag and its indented body are a line and its block, like an outline item; one rule per tag word, in English and Spanish, builds the same tree as its code-spell twin (P6).
  • Tag heads go through the real grammar (<on mouse down>), and bodies are parsed in place by today's rules: so Card.spellx and Card.spell compile to the same JS.
  • Drawings go through spell's JSX tokenizer, which learns control tags, </> and bare component names (P7).
  • Positions are native, so errors, hover, completion and the notebook's edits land on the right .spellx line with no map in between (P8, P11).
  • The .spell text of a .spellx file is a view, written rule by rule as the Spanish translator writes another language (P8); the same writer runs the other way as the one-off converter, which lays a .spell file out afresh as .spellx (P12; Q19).
  • Last, standard source maps in the build folder point a runtime error at the .spell or .spellx line (P14).

The first plan wrote a .spellx file into .spell text with a span map, then compiled that (Q10, Q11); P3 built a hand-written reader for it, now retired, its fixtures kept as the structure the rules must produce.
