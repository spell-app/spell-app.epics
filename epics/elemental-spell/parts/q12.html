The notebook mixes prose (markdown) with code. Where does prose go in a .spellx file, how is a member's description written, and what does each become in code spell?

Two different things are both "prose":

  • A description belongs to one thing: the card, its suit, its "turn it over". It shows in hover, in the property editor and in docs.
  • A prose cell belongs to no one thing: a heading and a few sentences between chunks, like a notebook's markdown cell.

The proposal, shown on the card:

  • Inside a template, loose text is markdown; code goes only inside tags (raw code in a <spell> chunk).
  • Text first in the template, before any tag, is the template's description.
  • A member's description: description="..." when it's one line, a <description> child when it's longer.
  • Any other loose text is a prose cell, up to the next tag.
<spell-view name="playing card" template="two sided view">
	A playing card has a suit and a rank.                      <- the view's description
	It shows its front when it's face up.

	<spell-property name="suit" one-of="clubs, diamonds, hearts, spades"
		description="Which of the four suits it belongs to"   <- short:  an attribute
	/>

	## Turning it over                                         <- a prose cell:  free markdown
	Turning a card takes a moment, so a game can wait for it.

	<spell-action name="turn it over">
		<description>                                         <- long:  a child
			Flips the card.
			- face up becomes face down
			- face down becomes face up
		</description>
		...
	</spell-action>
</spell-view>

In code spell, today's docstring rule already tells the two apart:

  • comment lines right above a declaration are its description
  • comment lines followed by a blank line are free prose: a prose cell
  • a ## heading is a heading, in both
// A playing card has a suit and a rank.                      <- comment lines right above:  its description
// It shows its front when it's face up.

  • Two prose cells side by side are kept apart by their blank line, so a round trip never merges them (Jupytext's seam, 1.3).
