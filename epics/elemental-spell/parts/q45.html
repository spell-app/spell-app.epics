Is .spellx its own, friendlier markup that compiles into JSX and HTML, rather than HTML with prefixed tags? Tags lose their spell- prefix, may hold spell phrases with spaces, close with </>, and say <button> for Spell UI's button.

Now: may a tag's head be a spell phrase, with spaces in it: <on mouse down>, <if the mouse is down>, <for each card in its cards>?

Most of Owen's proposal is settled since this was asked:

  • Prefixes: only the template tags keep one, everything inside is a short word (Q37).
  • <button> is always a pack's button, never HTML's (Q46).
  • Our own reader reads it, and the JSX reader may be rewritten (Q5, Q8).
  • Self-closing /> (Q47); accents kept (Q49).
  • What </> closes: its own question, Q40.

The card, in this form

The same playing card as o1's Card.spellx, line for line, so the two can be read side by side. 

<view "playing card" aka="card" template="two sided view">
	A playing card has a suit and a rank.
	Face up it shows them;  face down, the back every card shares.

	## Suit and color

	<property "suit" one-of="clubs, diamonds, hearts, spades"
		description="Which of the four suits it belongs to"
		phrase="is a (suit)"
	/>
	<property "color" one-of="red, black" phrase="is (color)" phrase="is a (color) card">
		red if it is a diamond or it is a heart
		black otherwise
	</>
	<property "symbol" description="Its suit's sign, for drawing">
		"♣" if it is a club
		"♦" if it is a diamond
		"♥" if it is a heart
		"♠" if it is a spade
	</>

	## Rank

	<property "rank" one-of="ace, 2 ... 10, jack, queen, king"
		description="Ace is low:  ace = 1 ... king = 13"
		phrase="is a (rank)"
	/>
	<phrase "is the (rank) of (suit)" />
	<phrase "is a face card">if its rank is jack, queen or king</>
	<phrase "is a number card">if it is not a face card</>

	## Playing it

	<action "show it">
		<description>
			Turns it face up, if it isn't already.
			A pile shows its top card each time a card leaves it.
		</>
		if it is face down
			turn it over
	</>

	<on mouse down>
		<comment>Face down:  turn it over.  Face up:  pass the press on, so its game can move it.</>
		if it is face down
			turn it over
		otherwise
			pass event
	</>

	## Drawing it

	<draw section="front">
		<comment>One line of text, the size of the text around it:  its pile scales it to fit.</>
		<text part="face" color={its color}>{its rank} {its symbol}</>
		<if it is a face card>
			<image part="portrait" src="{its rank}.svg" alt="the {its rank}" />
		</>
	</>
	<draw section="back">
		<image part="back" src="card-back.svg" alt="the back of a card" />
	</>

	<test "card setup">
		get a new card whose rank is queen, suit is spades and direction is down
		echo "testing the " + its rank + " of " + its suit
	</>
</view>

  • Accents stay (sección=, <al presionar el ratón>), unlike J4's plain-ASCII tags: spellx words never reach the browser, only what they compile to (<es-texto>) does.
  • The last line closes with </view>, by name: an optional named closer, checked (below).

The idea

A spellx tag's head can be a spell phrase, so <on mouse down> is just the code-spell line on mouse down: in brackets, and </> is the end of its indented body.

Tag head in Card.spellx Line in Card.spell
<view "playing card" template="two sided view"> a "playing card" is a two sided view:
<property "color" one-of="red, black"> - its "color" is one of red, black:
<action "show it"> - to show it:
<on mouse down> - on mouse down:
<if it is face up>, in a drawing if it is face up
</> the end of the indented body: nothing is written

So .spellx to .spell (Q10) gets simpler: a control or event head is copied as it is, a declaration head is a quoted name plus fields, and the body is copied one indent in.

What it gains

  • It reads like what a novice would say: <on mouse down>, not <spell-on-mouse-down>.
  • Translation is natural: <propiedad "palo">, <al presionar el ratón>. No prefix in any language, so the Encanto prefix (Q36) and which tags carry it (Q37) stop mattering.
  • Fewer characters: almost every line of the card above is shorter than in o1.
  • Nothing new to parse with: our own parser reads it already (Q5), and rewriting the JSX reader is fine (Q8).
  • Less rope for agents than HTML: the words are a closed set, so an unknown tag or attribute is an error the moment it's written, not a silently ignored element.

What it costs, and the guardrail for each

  • A bare name needs a lookup. <button> could be this app's own template named button, a pack's ui-button, or HTML's native button.
    • The order: this app's own templates (and the ones it imports), then each pack in the order the project lists them, then HTML.
    • A real name always works too: <ui-button> is always Spell UI's.
    • Reaching HTML's own element past a pack: its own question, Q44.
    • The real collisions, Spell UI components whose bare name is an HTML element: button, code, embed, form, input, label, menu, progress, search, section, select, table; and SVG's image and text.
  • Structure words are reserved: view, thing, page, app, template, property, phrase, action, draw, section, test, event, on, if, otherwise, for each, description, comment. None of them can name a template.
    • Three clash with something that exists: section (HTML, and Spell UI's ui-section), template (HTML's <template>), comment (Spell UI's ui-comment). The structure word wins; the others are reached by their real name.
    • The context rule: outside a drawing a tag is a declaration; inside one it's markup, except the control words (<if>, <otherwise>, <for each>) and <section>.
  • Where a tag head ends. A declaration's head is a quoted name, then key=value fields; a control or event head is a spell phrase.
    • The rule: the head ends at the first > outside quotes, parentheses or braces. So <if (its rank > 10)> works, and so does <if its rank is more than 10>; a bare <if its rank > 10> is an error that says which to write.
  • </> closes the innermost open tag, so a wrong closer has no name to check.
    • A named closer (</view>) is allowed anywhere, and checked.
    • The editor shows what each </> closes, as a faint label after it.
    • JSX uses <>…</> for a fragment: spellx has no fragments (a drawing may draw several things), and <group> if one is ever needed.
  • No outside tool understands it: no HTML or JSX highlighter, formatter or GitHub preview.
    • We ship its grammar; the language server already colours spell.
    • Agents and programmers fall into HTML habits (<ui-button>, </view>, on-click=): each is accepted as an alias, and spell lint --fix rewrites it in the friendly form, so a habit never fails.
  • Where the packs are named. Owen said package.json5; today a project's settings are its __project.json5 (title, description, imports), so the pack list goes there (packs: ["spell-ui"]), or in the package's json5 if that's the file meant.
  • Programmers read the output: .spellx to .spell to JSX and HTML, so the compiled drawing says <ui-button>, and .spell stays the programmer's form.

The choice

Choices

A · Its own language, compiled to JSX and HTML (recommended)

  • <on mouse down>…</>, <view "card">, <button>
  • Gains: reads like plain words in every language; no prefixes; a closed vocabulary our parser enforces.
  • Costs: a name lookup, reserved words, our own grammar and tools; every guardrail above, and HTML habits accepted and rewritten.

B · Halfway: no prefixes, but no spaces and real markup names

  • <on-mouse-down>…</>, <if test={…}>, <ui-button>
  • Gains: HTML-ish highlighters and tokenizers half-work; no name lookup.
  • Costs: hyphens and {…} where a novice expects words; markup names stay English.

C · Keep o1's prefixed shape

  • <spell-property name="suit">, <encanto-propiedad nombre="palo">
  • Gains: what's settled stands (Q25, Q37); plain HTML tools can read it.
  • Costs: the longest form, prefixes in every language, and HTML's rope.
  • .spellx is Spell's own markup: plain words for tags, spell phrases in heads, </> to close
  • it still compiles .spellx to .spell to JSX and HTML; that first step gets simpler
  • bare markup names (<button>) resolve to this app's templates, then its packs, then HTML
  • a closed set of words per language; HTML habits are accepted and rewritten by lint
  • Q37 is moot; Q25, Q36, Q39, Q40, Q42, Q15 and Q16 read as the table above says; Q43 and Q44 settle the rest
