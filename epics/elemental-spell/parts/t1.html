Ideas from Owen's action manager, for Spell's events and actions

Owen's action manager from another project already does much of what his event model asks for. These are its ideas, in our words, for the events phase to start from.

1. The keys and the mouse, readable anywhere

  • This is his HyperCard point: any code can ask "is shift down?", not only an event handler.
  • What's tracked:
    • the modifier keys: shift, option, control and command
    • "the platform key": command on a Mac, control everywhere else
    • whether the focus is in a text field
    • whether a modal is open
  • How: every key press and mouse press is read early, before any handler sees it, and the state is kept.
  • All of it is cleared when the window gains or loses focus, so a key let go in another window doesn't stay "down".
  • It's mirrored as classes on the page's root element, so CSS can react: a copy cursor while option is held, say.
  • The limit: ordinary keys can't be tracked reliably.
    • A Mac never reports a letter key being let go while command is held.
    • So only an opt-in list of extra keys is tracked, e.g. space for panning.
  • Spell words this suggests: 
    if the shift key is down:
	add the card to the selection
if the platform key is down ...      // command on a Mac, control elsewhere
if the mouse button is down ...
if the focus is in a text field ...

2. An action is a described command, not just a function

  • Besides its steps, an action carries:
    • a stable id, from its name. It never changes when the title is reworded, because tours and analytics key off it.
    • a title, defaulted from the id
    • an icon
    • a tooltip, in markdown
    • "enabled when": may it run right now?
    • "selected when": does it show a checkmark?
    • its keyboard shortcuts, listed per operating system with a fallback. Every key it accepts is listed, e.g. the number pad's twin of a number key.
    • the key caps, worked out once for display: ⌘S on a Mac, Ctrl+S elsewhere
    • two switches, both off by default: does it still work while typing in a text field? While a modal is open?
  • What that could mean for <spell-action> (the tag spelling follows whatever shape Q25 picks): 
    <spell-action name="turn it over" icon="rotate" shortcut="Space"
              enabled-when="it is in a pile" selected-when="it is face up">
	<description>Turns the card face up, or face down.</description>
	if it is face up:
		turn it face down
	otherwise:
		turn it face up
</spell-action>
    • The description doubles as the tooltip.
    • The name is the stable id; a title= only when the menu should read differently.

3. One definition, many places

  • The same action drives a menu item, a button, a key shortcut and a hint.
  • A menu is just a list of actions, with separators between groups.
  • So the title, icon, enabled state and checkmark are written once, and every place shows them the same way.

4. Actions switch in and out with their view

  • A view switches its set of actions in when it appears, and out when it goes.
  • The key bindings are rebuilt from every set in play, batched, so a burst of views appearing rebuilds them once.

5. Several actions on one key: the first enabled one wins

  • The newest set is asked first.
  • The first ENABLED action runs, and CONSUMES the key: nothing after it sees it.
  • A disabled action lets the key fall through to the next one.
  • That is his "events are swallowed unless passed" rule, already proven in practice. In Spell, pass is the fall-through.

6. One choke point for running anything

  • Every way of running an action (a key, a click, a menu, a hint) goes through one "run it" step.
  • That step answers: it ran, it was disabled, or it failed.
  • Observers hear "the person did X", and whether it was by key or by click:
    • guided tours advance on it
    • analytics count it
  • A failing observer never breaks the action. A failing "enabled when" counts as disabled.
  • A tour can claim a key to block it for one step, or hand it back by being disabled.

7. Modals

  • A modal claims the focus while it's open, and most shortcuts sleep until it closes.
  • A stack of modals (one opening over another) was a known to-do there.

What this suggests for Spell

  • send runs through one choke point, so when the person does ... observers, guided tours and undo all hook in there.
  • Events and actions share one rule: enabled runs and consumes; disabled, or pass, falls through.
  • The input state is a set of properties of the app, readable anywhere: the shift key, the mouse button, the focus is in a text field.
  • An action's description, icon, shortcut and "enabled when" are part of declaring it, so a menu, a button and a shortcut all come from the one <spell-action>.
  • The events phase starts from these seven ideas, not from a blank page.
  • Nothing changes now: T1 stays a todo for its own phase.
