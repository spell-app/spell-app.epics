Elemental spell is a second way to write the same Spell program: each piece of a template (a property, a phrase, an action, a drawing) wrapped in its own tag, with plain markdown between them.

  • Code spell, today's form, reads like an essay; it stays, in .spell files.
  • Elemental spell is the same program cut into chunks, in .spellx files ("spellx" is our flavour of JSX; Q9).
  • The two must be 100% equivalent, and switching between them must be instant.

Why

  • A novice who knows a little HTML can read it: each chunk says what it is in its tag.
  • A notebook editor, like Jupyter's or Observable's, can show it:
    • the markdown between tags is a prose cell
    • each tag is a code cell
  • Each kind of chunk can get its own editor: a property's tag is a natural fit for a <ui-property>.
  • An agent can walk the chunks one by one, and find one by a selector: property[name=color].

What's settled

After three rounds, a .spellx file is a template tag holding short words, all in the file's language, with markdown between them; it's written into .spell and compiled from there. The rules, each with the decision behind it:

  • Only the template tags carry the language's prefix: <spell-view>, <encanto-vista>. Everything inside is a short word: <property>, <propiedad>. Lint rejects any other word (Q25, Q36, Q37).
  • No native HTML: a drawing's components are a pack's, by bare name, so <text> is Spell UI's ui-text; no <html-*> escape for now (Q46, C1).
  • A tag with no body ends in />; Spanish words keep their accents, and the editor adds them as you type (Q47, Q49).
  • A .spellx file is written into code spell, then compiled: exactly, with a map between the two (Q10, Q11).
    • The other way, code spell into .spellx, lays the file out afresh (Q19).
  • Loose text is markdown: first, the template's description; later, a prose cell. A member's description is description="...", or a <description> child when long (Q12).
  • Phrases, not aliases: phrase="..." on a property, repeatable, or a <phrase>; in code spell, a property's phrases sit indented under it (Q6, Q13, Q22).
  • A drawing's markup lines are drawn, and spell lines around them decide; <description> and <comment> may sit inside (Q14).
  • A parent's drawing places a named part; a child draws it (Q15). Which word places it is Q48: <section> is now Spell UI's folding block.
  • Owen's tag model (Q16):
    • templates: <spell-thing>, <spell-view>, and the page and app templates
    • one of a kind: <spell-page>, <spell-app>
    • template="..." names the parent
    • a thing is made by its own tag: <solitaire-card>
    • today's runtime <spell-app> becomes <spell-viewer>
  • A test is one more action of its template: <test "card setup"> (Q21).
  • A sentence-style declaration becomes the same chunk as its outline form (Q20).
  • Code spell keeps a "card" is a two sided view: "template" is the word people read for what it declares (Q24).
    • The parser keeps its own words inside, Type and Method (Q23).
  • Events (Q26 to Q32, Q35):
    • send, pass event
    • cancel event
    • target and the original target
    • the mouse words, and which action gets a shared key first
  • An action is a described command, and menus are built from actions (Q33, Q34).
  • Every <ui-*> is there, it's all compiled, our own parser reads it, and the editor keeps the indentation right (Q3, Q4, Q5, Q7).

The card, its template and its app, as files

Owen's playing card, in the settled shape. It extends the library's two sided view, which draws the front or the back; the card says what each one looks like. 

<spell-view name="two sided view">
	A view with a front and a back:  it shows one side at a time.
	A view that extends it says what each side looks like, in `<draw name="front">` and `"back"`.

	<property name="direction" one-of="up, down"
		description="Which way it faces"
		phrase="is face (direction)"
	/>

	<event name="flipped" side="direction"
		description="Sent each time it turns over;  side is the way it faces now"
	/>

	<action name="turn it face up">
		set its direction to up
	</action>
	<action name="turn it face down">
		set its direction to down
	</action>
	<action name="turn it over">
		<description>Flips it:  face up becomes face down, and back.</>
		if it is face up
			turn it face down
		otherwise
			turn it face up
		send flipped with side = its direction
	</action>

	<draw>
		<description>The front when it's face up, the back when it's face down.</>
		<if it is face up>
			<draw name="front" />
		</>
		<otherwise>
			<draw name="back" />
		</>
	</draw>
</spell-view>

<spell-view name="playing card" aka="card" template="two sided view">
	A playing card has a suit and a rank.
	Face up it shows them;  face down, the back every card shares.

	## Suit and color

	<property name="suit" one-of="clubs, diamonds, hearts, spades"
		description="Which of the four suits it belongs to"
		phrase="is a (suit)"
	/>
	<property name="color" one-of="red, black"
		phrase="is (color)"
		phrase="is a (color) card"
	>
		red if it is a diamond or it is a heart
		black otherwise
	</property>
	<property name="symbol" description="Its suit's sign, for drawing">
		"♣" if it is a club
		"♦" if it is a diamond
		"♥" if it is a heart
		"♠" if it is a spade
	</property>

	## Rank

	<property name="rank" one-of="ace, 2 ... 10, jack, queen, king"
		description="Ace is low:  ace = 1 ... king = 13"
		phrase="is a (rank)"
	/>

	<phrase name="is a face card">if its rank is jack, queen or king</>
	<phrase name="is a number card">if it is not a face card</>

	<action name="show it">
		<description>
			Turns it face up, if it isn't already.
			A pile shows its top card each time a card leaves it.
		</description>
		if it is face down
			turn it over
	</action>

	<on mouse down>

		if it is face down
			turn it over
		otherwise
			pass event
	</>

	## Drawing it

	<draw name="front">
		<comment>One line of text, the size of the text around it:  its pile scales it to fit.</>
		<text part="face" color={its color}>{its rank} {its symbol}</text>
	</draw>
	<draw name="back">
		<image part="back" src="card-back.svg" alt="the back of a card" />
	</draw>

	<test "card setup">
		get a new card whose rank is queen, suit is spades and direction is down
		echo "testing the " + its rank + " of " + its suit
	</>
</spell-view>

What code spell has to grow

Where the elemental form says something code spell can't, code spell grows (Q2):

  1. A property with a list of choices AND value lines: - its "color" is one of red, black:.
  2. A property's own phrases, indented under it (Q13).
  3. A drawing per side, - to draw its front:, and a place for it in the parent's drawing (Q15).
  4. A drawing whose body is markup lines, with no return (Q14).
  5. An event a template sends: - it sends "flipped" with a side as a direction (J3).
  6. A test as a member: - to test card setup: (Q21).
  7. The two sided view itself: a template in Spell's library (Q1).
  8. Still open: how an action says its shortcut (Q38), and a named menu (Q41).
