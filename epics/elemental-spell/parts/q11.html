Switching between the forms: what must come back exactly, and what may be laid out afresh? And what happens to a line that has no tag?

Owen, 2026-10-24: ".spell => .spellx will be very rare. It would be OK if that lost formatting/etc." (Q19). So the two directions are different jobs:

  • A .spellx file is the source. Its .spell form is a view of it, made on demand, and what the compiler reads (Q10).
  • .spellx → .spell is exact. Bodies are copied byte for byte; each tag's header is written in its one code spell wording. A span map pairs the two texts, so edits made in the .spell view map back.
  • .spell → .spellx is a one-off conversion. It may lay the file out afresh: one wording per declaration, its own spacing. It must give the same program, and a test checks that by compiling both.

The span map

Owen asked whether a code map, like a source map, could solve the back and forth. It carries the .spell view: a span map pairs each piece of one text with the piece of the other that says the same thing.

  • Each tag's header pairs with its declaration line.
  • Each body pairs with its body: the same bytes, its indent shifted.

For the color property:

.spellx span .spell span When it changes
<spell-property name="color" one-of="red, black" - its "color" is one of red, black: rewritten when edited
alias="is (color)" - it "is (color)" rewritten when edited
alias="is a (color) card" - it "is a (color) card" rewritten when edited
red if it is a diamond or it is a heart the same copied: same bytes
black otherwise the same copied: same bytes 
Owen has Card.spellx open, and switches to its .spell view.

He edits a body line in the .spell view:
	black otherwise   ->   blue otherwise
	the same span in Card.spellx changes;  nothing else is rewritten

He edits a declaration line in the .spell view:
	- its "color" is one of red, black:   ->   - its "color" is one of red, black, blue:
	that tag's header in Card.spellx is rewritten:  one-of="red, black, blue"
  • A map alone can't write the other form: the reader writes the .spell text once, and the map follows each edit after.
  • With the map:
    • the cursor and the selection stay where they were when Owen switches forms
    • an edit inside a body goes into the same span of the other text, with nothing rewritten
    • only an edited header is rewritten, the way recast reprints only what changed (1.3)
    • errors, hover and completion land on the right line
  • Whether the compiled JavaScript gets a source map too is its own question (Q18).

Lines with no tag

Some code spell has no tag form: a sentence-style declaration (cards have a value as a number), a top-level test. The conversion puts it in a raw <spell> chunk, word for word, as MakeCode keeps code it has no block for (1.3). 

a card is a two sided view where:
	- its "suit" is one of clubs, diamonds, hearts, spades
cards have a value as a number          // sentence style:  no tag form

to test card setup:                      // a top-level test:  no tag form
	expect the first card to be face down
 
<spell-view name="card" template="two sided view">
	<spell-property name="suit" one-of="clubs, diamonds, hearts, spades" />
	<spell>
		cards have a value as a number          // sentence style:  no tag form
	</spell>
</spell-view>

<spell>
	to test card setup:                      // a top-level test:  no tag form
		expect the first card to be face down
</spell>
  • .spellx → .spell: exact, with a span map, so the .spell view can be read and edited.
  • .spell → .spellx: once per file, laid out afresh; the same program, checked by comparing the compiled output.
  • Matches Owen's "very rare ... OK if that lost formatting".
  • Cost: converting a .spell file may reword its declarations ("is either" comes back as "is one of").
  • Either file could be the source, and switching never changes a byte.
  • Cost: every declaration needs exactly one wording, and sentence-style files come over as mostly raw chunks; more work for a direction Owen says is rare.
  • The .spell text is made only to compile; nobody reads or edits it.
  • Cost: Owen loses "switch back and forth instantly" for reading a .spellx file as code spell.
  • .spellx is the source; its .spell view is made on demand, with a span map kept up to date as either is edited
  • a one-off .spell → .spellx conversion, laid out afresh
  • new chunk: <spell>, for code spell with no tag form
  • new test: every example project converted, both forms compiled, the JavaScript compared

  • Why it works: the parser records the same pieces for both (the type, the property's name, its choices), and the .spell to .spellx writer reads those pieces, not the words around them.
  • Since .spell to .spellx may lay a file out afresh (Q19), the sentence-style wording isn't kept: coming back, it's the outline line.
  • So the raw <spell> chunk shrinks to what truly has no chunk of its own.
  • every declaration, in either wording, is a chunk; <spell> is rare
