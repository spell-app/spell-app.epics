Today (P3) spellx has its own hand-written reader, SX.SpellxReader: it finds the tags and copies the bodies as raw text, and P6 would write that into .spell text for the real parser. The other way: spellx becomes a THIRD STYLE of spell, beside sentences and the outline, read by spell's own tokenizer and rules.

  • A tokenizer for .spellx, a subclass as the markdown one is (MarkdownTokenizer extends P.Tokenizer): at the start of a line, <property "suit" ...>, </> and /> become tag tokens, NOT one JSX token swallowing the rest. A tag line plus its indented body is then a line and its block, exactly like an outline item; the closer is a check, the indentation already nests it.
  • One rule per tag word in a new spellx rule module, with English and Spanish syntax tables as every module has (spellx.en.ts / spellx.es.ts), about 15 rules. Each builds the SAME match data and AST as its code-spell twin (the property tag as - its "suit" is one of ...), so they compile to identical JS by construction -- the way outline and sentences already do, checked the same way (compile(a) === compile(b)).
  • Tag heads parsed by the real grammar: <on {event}> is the event rule's syntax, <if {condition}> the if rule's. Completion, hover and errors work in heads for free.
  • Bodies parsed by today's rules, in place: no text written in between.
  • Prose cells: a fallback rule for a line inside a template that isn't a tag (markdown).
  • Drawings: the hard part. The JSX tokenizer has to take control tags (<if ...>, <otherwise>) inside markup, </> closing any tag, and bare component names -- the JSX rewrite Q8 already allowed.
  • P3's reader is retired; its 5 fixtures and outline snapshots stay, as the structure the rules must produce.
  • Q10 (".spellx => .spell => JS") changes: a .spellx file compiles straight from its own parse; the .spell text becomes something you can LOOK at (written rule by rule, as the Spanish translator writes another language), not a step in the compile.
  • P6 · Spellx into Spell becomes "Spellx Rules" (bigger); P7 · Drawings carries the JSX work; P8 · Editor and Language Server mostly comes free (hover, completion, colours, folding, outline all read the match tree); P12's converter is the same rule-by-rule writer, both ways.
  • Rough size: 14-18h for the rules path, against about 17-22h for P6 + P7 + P8 as planned, plus the 6-8h P3 already spent (partly kept). About even; the result is one parser instead of two.
