A new package, packages/epics (@spell-app/epics, alias $/epics), holds the plan doc's elements and the one description of each that the browser and the node tools share (analysis Q3).

  • One description per element: a plain-data file for each tag (its attributes, its events, which children it takes). It's written the way Spell UI writes its *.vocabulary.en.ts files, plus a list of the children each tag allows.
    • the components (browser) read it to know their attributes
    • the plan-doc commands and the converter (node) read it to write and check markup: the "shared code, DRY" you asked about in analysis Q2
  • The elements: one folder per element family (components/epic-item/ ...), written exactly like the brand's own <ui-brand-*> elements (packages/brand, the closest precedent): a Solid 2 class on $/ui/core, its CSS, a plain-DOM fallback, browser tests.
  • A component pack (Q6, your sketch): the elements are built into one classic script, epics.pack.js, which a plan doc names inside its <ui-root>: <ui-components source="…/epics.pack.js">. The root loads it on demand, with the page's own Spell UI and Solid (never a second copy), and it works from file://. Packs are new, built in Spell UI for any package (P1), with commands to make, build and check them (P2).
  • The plan-doc tool (Q7): PlanDoc, part files, the review inbox and the commands move here from packages/docs/tools, as TypeScript (P7).
  • Its own rules: an AGENTS.md of its own saying small fixes go straight on main, real changes in a worktree, merged promptly, since main draws every doc (your note on analysis Q3); and a README.md.
