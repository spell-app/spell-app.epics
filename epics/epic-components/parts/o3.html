Each element draws its chrome in its own shadow DOM, like every Spell UI element, and shows the doc's prose through slots. The prose itself stays in the page, where find-in-page, links and the live update reach it.

  • Shadow DOM, prose in the page: <epic-item> draws its line (chip, title, fold) inside itself; its paragraphs, option cards and answer stay its children.
    • so #d7 links into an answer, and find-in-page, still work
    • and the live update (the page patching itself when the file changes) keeps patching prose in place
  • Bodies from part files: an element with source="parts/q7.htm" loads that file into its own children the first time it opens, as ui-accordion[source] did. It fires the same ui-load event, so everything that re-runs after a body loads (counts, contents, review buttons) still does.
  • The review buttons: the page code used to bolt them onto each item (wireReview(), in the docs runtime, spell-doc-runtime.js); they moved into the elements one piece per phase (analysis Q4): the item's buttons and note box in P9, the Choose pills, the header's Send and Review Now, the filters and counts in P10. All before the switch (Q9), so there was never a mix of the two.
  • The live update: it patches the epic-* elements in place, never replacing them, so an open item stays open, a half-typed note keeps its text and focus, and the scroll stays put; before, it replaced a whole item when anything inside changed.
  • Where it runs: every plan doc is drawn by main's page server, with main's elements (analysis Q1). A branch previews its elements on its own server, on copies of the docs.
  • From disk (file://): the skeleton still draws (the pack is a classic script, which file:// allows), but bodies, as today, need the page server.
