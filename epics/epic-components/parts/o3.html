Each element draws its chrome in its own shadow DOM, like every Spell UI element, and shows the doc's prose through slots. The prose itself stays in the page, where find-in-page, links and the live update reach it.

  • Shadow DOM, prose in the page: <epic-item> draws its line (chip, title, fold) inside itself; its paragraphs, option cards and answer stay its children.
    • so #d7 links into an answer, and find-in-page, still work
    • and the live update (the page patching itself when the file changes) keeps patching prose in place
  • Bodies from part files: an element with source="parts/q7.htm" loads that file into its own children the first time it opens, as ui-accordion[source] does today. It fires the same ui-load event, so everything that re-runs after a body loads (counts, contents, review buttons) still does.
  • The review buttons: today's page code bolts them onto each item (wireReview(), in the docs runtime, spell-doc-runtime.js); they move into the elements one piece per phase (analysis Q4): the item's buttons and note box in P9, the Choose pills, the header's Send and Review Now, the filters and counts in P10. All before the switch (Q9), so there's never a mix of the two.
  • The live update: today it REPLACES a whole item when anything inside changes (it treats ui-accordion as one block). It learns the epic-* tags: their attributes are patched in place, never replaced, so an open item stays open and a half-typed note survives.
  • Where it runs: every plan doc is drawn by main's page server, with main's elements (analysis Q1). A branch previews its elements on its own server, on copies of the docs.
  • From disk (file://): the skeleton still draws (the pack is a classic script, which file:// allows), but bodies, as today, need the page server.
