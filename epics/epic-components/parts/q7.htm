Your note on analysis Q2: "I assume there will be shared code for reading/changing these files, correct? DRY?" Yes: each element is described once, in $/epics. The open part is how much of the plan-doc TOOL moves with it.

  • today: packages/docs/tools/plan-doc.js, 4,625 lines of JavaScript, run as a child process (spell dev plan-doc spawns it, since nothing may import docs)
  • its class PlanDoc (about 2,330 lines) is pure: a document in, edits on it; about half of it builds layout markup, which goes away either way
A · Descriptions move, the tool stays (recommended)
  • $/epics holds the element descriptions and small read / write helpers (Markup.item(doc, "q7"), Markup.set(el, {status}))
  • plan-doc.js stays in packages/docs/tools, imports them, and loses its layout code
  • cost: the tool stays JavaScript and a child process for now
  • a todo records "move PlanDoc into packages/epics as TypeScript" for later
 B · The whole tool moves
  • PlanDoc, parts, inbox and the commands move into packages/epics, rewritten in TypeScript; the CLI calls them directly
  • one home for everything about plan docs
  • cost: about 6,000 lines ported while the markup also changes: two big changes at once, harder to review; adds roughly 6-8h

Net effect (A):

  • packages/epics/src/definitions/ and src/markup/, used by the elements AND plan-doc.js
  • plan-doc.js shrinks by its layout builders, relayout and most of migrate
  • a todo for the TypeScript move
