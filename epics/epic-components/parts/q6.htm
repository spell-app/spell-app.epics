Plan docs load ONE script today, the classic bundle packages/docs/tools/_assets/spell-ui.js (2.8 MB, committed): Spell UI, the doc runtime, the site header. The new elements must reach the page too. Which way?

  • "classic bundle": one plain script, no imports, so it runs even from file://
  • the catch: the bundler (esbuild) can't compile Solid's JSX, and a page must never hold two copies of Solid or of Spell UI (two copies: elements defined twice, or not at all)
  • the brand already solved this for Claude Design: packages/brand/vite.design.config.ts builds its elements with Spell UI and Solid left OUT, and bundle-spell-ui.js folds that file into the one bundle
A · Into the one classic bundle (recommended)
  • a Vite build of packages/epics, Spell UI and Solid left out, folded into spell-ui.js as the brand's is
  • plan docs keep loading one script; the skeleton draws from file://
  • today's runtime keeps working beside the elements, which the step-by-step move (analysis Q4) needs
  • cost: every docs page carries the elements (small: a few dozen KB beside 2.8 MB)
 B · A bundle of their own for plan docs
  • a brand-style ES-module bundle that REPLACES spell-ui.js on plan docs
  • it must then carry all spell-ui.js carries: the doc runtime, the sources saver, lazy code engines, the site header
  • no file:// at all (modules are refused there)
  • cost: a second bundle to keep in step, and plan docs drift from every other docs page

Net effect (A):

  • packages/epics/vite.docs.config.ts builds dist/epics-docs.js; bundle-spell-ui.js takes it in, after the brand's
  • spell dev docs update builds it first; its GENERATORS entry in mergeMain.ts runs before the docs bundle's
