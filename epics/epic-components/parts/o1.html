A new package, epics, holds the plan doc's elements (it's @spell-app/epics, alias spell-epic) and the one description of each that the browser and the node tools share (analysis Q3).

  • One description per element: a plain-data file for each tag (its attributes, its events, which children it takes). It's written the way Spell UI writes its *.vocabulary.en.ts files, plus a list of the children each tag allows.
    • the components (browser) read it to know their attributes
    • the plan-doc commands and the converter (node) read it to write and check markup: the "shared code, DRY" you asked about in analysis Q2
  • The elements: one folder per element family (epic-item/ ...).
    • written exactly like the brand's own elements, the closest precedent (brand's <ui-brand-*>)
    • a Solid 2 class on spell-ui/core, its CSS, a plain-DOM fallback, and browser tests
  • A component pack (Q6, your sketch): the elements are built into one classic script, epics.pack.js.
    • a plan doc names it inside its root element: <ui-components source="…/epics.pack.js">
    • the root loads it on demand, with the page's own Spell UI and Solid, never a second copy
    • it works from file://
    • packs are new: built in Spell UI for any package (P1), with commands to make, build and check them (P2)
  • The plan-doc tool (Q7): PlanDoc, part files, the review inbox and the commands move here from tools, as TypeScript (P7).
  • Its own rules: an AGENTS.md of its own saying small fixes go straight on main, real changes in a worktree, merged promptly, since main draws every doc (your note on analysis Q3); and a README.md.
