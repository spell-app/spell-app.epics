First asked while windows-and-review was building its window colours (P5), on 2026-10-06; /epic epic-components plans it from your answers. you proposed writing epic pages as components: <epic-page>, <epic-section>, <epic-phase>, <epic-item>. the shape of a new epic, epic-components: where the components' code runs from, how old docs keep working, how we get there, and when.

Today a plan doc is HTML that already carries its layout: every item spells out its accordion, its id chip and its title span. A change of layout means rewriting every doc. With components, a doc holds only the data and the prose, and the components draw the layout.

  • Today: the markup the script writes, layout and all.
  • As a component: attributes for the data, children for the prose. The chrome (chip, buttons, folding) is drawn by <epic-item>.

  • Every plan doc is ONE shared file (in spell-app-dev), seen by every checkout.
  • The code that draws it is per branch: each checkout's page server serves its own bundle.
  • Today's example: I changed the "Plan hung?" notice in P3. Had I changed the shared template, docs made from main would have kept the notice forever, because main's older script didn't know the new one.
  • With components, the same bites harder: a doc written for a newer <epic-item> and shown by an older bundle draws wrong. So "no need to update other epics' docs" needs one answer to: whose code draws a doc? (Q1)
  • Goes, or shrinks to almost nothing: migrate, relayout, most of the layout code in plan-doc.js (about 4,300 lines), the hand-kept markup rules in plan-doc.md.
  • Moves into components: the review runtime (wireReview(), about 1,500 lines of spell-doc-runtime.js): buttons, note boxes, the fold button.
  • Stays: part files (<epic-item source="parts/q7.htm">), the inbox and its routes, the commands (they set attributes instead of writing layout), opening from disk (the components go in the one classic bundle).
  • Dogfoods <ui-root> and the @spell-app/ui components, as you said.

Plan docs are shared, the components are code. Which copy of the components draws a doc, so old and new docs all look right? (See 1.3.)

Every link to a plan doc goes to main's page server, which draws it with main's components. A branch changing the components previews them on its own server. Closest to today; nothing new to build.

  • You'd see: every doc in the side bar drawn the same, whatever window you're in.
  • Cost: a branch's component change shows on everyone's docs only once it merges, as with P3 and P4 today.

The components' bundle is published into shared content (epics/_components/epic-components.v3.js), and every doc loads it from there, from any checkout.

  • You'd see: the same as A, and even a doc opened from a worktree's server draws with the published components.
  • Cost: a publish step (spell dev epic-components publish), and a bundle in the shared repo that a branch can overwrite before it merges.

As today: each server draws with its branch's components, and the components stay able to read every older doc.

Cost: a doc written by a newer branch looks wrong in an older checkout's window until that checkout merges main.

When <epic-item> changes how it reads its markup, what happens to the docs written before?

Each element carries v="1"; a component reads every version it knows. Docs are never rewritten for a layout change; a doc can mix versions.

Example: <epic-item v="1" title="..."> beside <epic-item v="2" title="..." kind="risk">, both drawn right. This is your "version the components individually".

<epic-page v="2">: the whole doc is one version; a component picks how to read it from the page.

No versions: a script converts every doc at each change, as migrate does today.

Which package holds <epic-page> and the rest?

packages/epics (@spell-app/epics), built on @spell-app/ui; the docs bundle includes it. Its own tests, its own AGENTS.md.

Beside today's runtime in packages/docs/tools/_assets/. Fewer moving parts; mixed in with the docs runtime.

As general document components. Against the rule that ui stays generic, knowing nothing about epics.

The review runtime is the bulk of the work. Step by step, or all at once?

First the elements draw what today's markup draws, and a one-time script converts the 25 docs. Then the review controls move into <epic-item>, one piece per phase. Every phase leaves the docs working.

Build every component and the converter, then switch over in one go. Fewer half-states; a long stretch where nothing is usable.

New epics use the components; old docs keep today's markup and runtime for good. Two systems to keep alive.
