A view defined inside a page (Q6) is lifted out to just before the page, so as built it would be an ordinary view of the project: usable from any file. 

<spell-page "counter page">
	<view counter> ... </view>
	<counter/>                     -- here, surely
</spell-page>

<spell-page "other page">
	<counter/>                     -- and here?
</spell-page>
 It's a view like any other, only written where it's first used; nothing new in the compiler. Local to the page: two pages can each have their own <counter>; the compiler needs scoped tag names. Writing a view inside a page is a convenience of placement, not a new kind of view.

What's the impact of B?

B is a new kind of type, a view that belongs to a page, and that reaches further than the page.

How a view is named today, which A keeps:

  • Every type is the PROJECT's: one name, looked up from anywhere (scope.getType()).
  • Its class is named for it (Counter), and its element for the project and it (notebooks-counter, as solitaire-card).
  • A bare <counter/> finds the project's view first, then Spell UI's (SpellJSX.componentTagFor()).
  • Two pages each writing <view counter> in one project: an error today, "There's a counter already, on line 4 of Usage.spellml".

What B would have to add:

<spell-page "usage">    <view counter> ...      <counter/>   -- usage's counter
<spell-page "examples"> <view counter> ...      <counter/>   -- examples' counter
  1. Plain Spell has no way to say it. Code spell declares a type only at a file's top level; every spellx file has a plain-Spell twin, and the editor shows both. B needs a new phrase for "a type inside a page" (the usage page's counter is a view:?), in English and Spanish, and the writers both ways.
  2. Names in the compiler: the class (Usage_Counter), its element (notebooks-usage-counter), and the lookup: the page's own views first, then the project's, then Spell UI's.
  3. Python's twin names it the same way.
  4. The editor: the Views tree, the Inspector and the palette list a page's views under it; the language server's go-to and hover follow the page's scope.
  5. Size: about one more phase, 4-6h, most of it the plain-Spell phrase.

Who would feel the difference now: nobody. Four notebook files define a view inside them, in four different projects: no two clash.

  • It matters once Spell UI's 94 projects become ONE site (epic mockup, T1): ~360 pages in one project, where two examples both called counter would clash under A.
As built: a clash is a clear error naming the other page. Page-scoped views go to the site work (epic mockup), where many pages share a project. A new phase here (about 4-6h): the plain-Spell phrase, scoped names, the editor's lists. Nothing changes for today's content; the question comes back with the one-site work, where it bites.
