Before this epic, VS Code knew our custom elements in HTML files, but not in JSX: every <ui-*> tag in a .tsx file took any attribute, with no completion, no hover docs and no check.

This is how things stood when the epic started (2026-10-22); what changed is in the next two parts.

  • What each element says about itself: its vocabulary, one plain-data file per tag (buttonVocabulary).
    • every attribute: its name, its kind (boolean, size, colour, a list of values ...), its values, its default, a description
    • its events (and their detail), slots, parts and custom states
    • the shape: ComponentVocabulary, in the kit
  • HTML files were covered, for Spell UI and Spell Brand only.
    • ElementManifests wrote VS Code's HTML data and a Custom Elements Manifest, from the vocabularies.
    • Only spell-app's own folder settings turned the HTML data on, so a window opened on the kit (every epic's window) didn't get it.
    • Spell Epic's and the app's elements had neither file, and still don't (C6).
  • JSX got a loose stand-in, written by hand, five times over.
    • the app: every ui-* tag took any attribute, of any type: [attribute: string]: unknown
      • in solid.types.ts, "loose ON PURPOSE until ui ships typed tags"
    • Spell UI's docs components, Spell Epic's 76 epic-* tags, Spell Brand's tags: each named by hand, each just as loose
    • the spell compiler's TypeScript writer emitted the same loose entry for every drawable tag
  • How much JSX it touched: about 740 <ui-*> tags in .tsx files.
    • Spell UI 454 (101 files), the app 180 (22), Spell Epic 106 (23), Spell Brand 3
  • Half the work existed already, as types: AttributeValues<V> turns a vocabulary into its attributes' types (a list of values into a union), as each component class's own properties.
    • It wasn't used for JSX, and still isn't: the JSX types are generated instead (1.2).
    • A shared value set (values: "hues") came out as plain string; now typed by its values, so the casts in I7 are gone.
