Today VS Code knows our custom elements in HTML files, but not in JSX: every <ui-*> tag in a .tsx file takes any attribute, with no completion, no hover docs and no check.

  • What each element says about itself: its vocabulary, one plain-data file per tag (buttonVocabulary).
    • every attribute: its name, its kind (boolean, size, colour, a list of values ...), its values, its default, a description
    • its events (and their detail), slots, parts and custom states
    • the shape: ComponentVocabulary, in the kit
  • HTML files are covered, for Spell UI and Spell Brand only.
    • ElementManifests writes VS Code's HTML data and a Custom Elements Manifest, from the vocabularies.
    • Only spell-app's own folder settings turn the HTML data on, so a window opened on the kit (every epic's window) doesn't get it.
    • Spell Epic's and the app's elements have neither file.
  • JSX gets a loose stand-in, written by hand, five times over.
    • the app: every ui-* tag takes [attribute: string]: unknown (solid.types.ts), "loose ON PURPOSE until ui ships typed tags"
    • Spell UI's docs components, Spell Epic's 76 epic-* tags, Spell Brand's tags: each named by hand, each just as loose
    • the spell compiler's TypeScript writer emits the same loose entry for every drawable tag
  • How much JSX it touches: about 740 <ui-*> tags in .tsx files.
    • Spell UI 454 (101 files), the app 180 (22), Spell Epic 106 (23), Spell Brand 3
  • Half the work exists already, as types: AttributeValues<V> turns a vocabulary into its attributes' types (a list of values into a union), as each component class's own properties. It isn't used for JSX, and a shared value set (values: "hues") comes out as plain string.
