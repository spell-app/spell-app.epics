A set of Spell UI elements that draw a property editor (a header, folding property groups, one field per property) straight from a schema: a spell class, a web component's vocabulary, or a JSON block. It edits one thing or many at once, live or on Apply, and the spell editor can save a generated one as an .editor.html page to tweak by hand, check against its schema, and compile for use without spell.

goal: a set of components to make a "property editor" for any class / json block / web component / etc. This is part of spell-ui

Feed in one of the above (assume there is some sort of schema, starting with the schemas we currently output) and instantly construct a form / panel like the above (from spell-design-system/Theme Creator.spell). Specifically:
- There is a header ("Theme")
- Within that we have "property groups" (COLOR / TYPE / SHAPE)
- Within each, we have type-specific "fields" for each of the various properties.

Note that the fields might have equivalent representations for various data types -- e.g. "text size" might resolve to "xs | sm | md | lg | xl | 2xl | huge" -- and we might want to show it as a range input rather than a select. "Corners" is anotehr example, here we are showing it as a "button group" rather than a "select".

Also, fields can have: hints (below the input), "pattern" for regex pattern, "tooltip" (the "i" icon to the right, possibly "actions" as buttons to select presets. They must also be able to show errors interactively.

The default is that these are "live editors", where things change as I select them in the UI. Some fields may need a "debounce" (text fields) or "onblur" mechanics (e.g. changing an ID may be a big change to a larger entity, so it only fires when I leave the field). When shown in a modal, applying the values would come all at once, when the modal is closed.

Editing certain properties may have special "onchange" logic -- e.g. setting property A changes property B as well, or changes the set of options for "B". Default "validation" should come from the type, but there may be specific validation rules for certain fields.

The editor itself should work with a single "entity" (a single theme) or with a group of entities -- e.g. select many themes in an external panel, edit properties for all at once. This should present actual values when all items agree on a property, or a "blank" value if there is variance.

On the schema, assume:
- The labels, headers, and visible values shown to the user should must be translatable (think about how this would apply given our current translation scheme for web components and spell).
- the possible values (e.g. "dark mode surfaces" or "text size") come from the schema, an external (possibly async) function (e.g. "all available fonts") or be explicitly specified in the form (this should be rare).
- "validaton" and "onchange" logic as above can come from the schema itself as well, or can be special-purpose in the form (rare)

These property editors can be nested, and should work in sidebars, modals and other popups (e.g. a tooltip).

Four new elements, nested the way the Theme Creator's panel already is.

  • <ui-property-editor>: the whole editor. It takes the thing (or things) to edit, its schema, and when to apply changes (live, or on Apply). Its header is the panel's header ("Theme").
  • <ui-property-group>: a folding band of fields ("Color", "Type", "Shape"). A <ui-panel> underneath.
  • <ui-property>: one property. It draws the label row, the info tip, the hint under the control, the error, and preset buttons, then picks the control for the property's type.
  • The controls are the ones Spell UI has: <ui-input>, <ui-select>, <ui-slider>, a segmented <ui-menu> as a button group, <ui-checkbox>, the colour pickers. A property may ask for another control than its type's default (as="range").
  • A property whose value is itself a thing nests a whole editor inside it.
<ui-property-editor header="Theme" schema="Theme" mode="live">
  <ui-property name="name" hint="Used for the file name"></ui-property>

  <ui-property-group header="Color">
    <ui-property name="primary" as="color-set"></ui-property>
    <ui-property name="darkSurfaces" as="buttons"></ui-property>
  </ui-property-group>

  <ui-property-group header="Type">
    <ui-property name="headings" options="fonts"></ui-property>
    <ui-property name="textSize" as="range">
      <ui-button slot="actions" icon="rotate left" data-preset="md">Reset</ui-button>
    </ui-property>
  </ui-property-group>

  <ui-property-group header="Shape">
    <ui-property name="corners" as="buttons"></ui-property>
    <ui-property name="depth" as="buttons"></ui-property>
  </ui-property-group>
</ui-property-editor>

The editor reads ONE description of a property, whatever it came from. A small adapter per source turns what that source has into it.

  • A spell class: its compiled property info (type, one-of choices, default, list item type), and its words file for the labels.
  • A web component: its vocabulary (each attribute's kind, values, default, description).
  • A JSON block: JSON Schema if it has one, else guessed from the values it holds.

What the description adds that no source has today:

  • a label and a tooltip, apart from the description, each a translation key
  • numeric limits (min, max, step) and a regex pattern
  • where the choices come from: the schema's own list, an outside (maybe async) function such as "every font installed", or a list written in the form (rare)
  • an ordered scale, so "xs, sm, md, lg, xl, 2xl, huge" can show as a slider with named steps
  • validation rules, and "on change" rules (setting A changes B, or B's choices)
  • when a change applies: at once, after a pause (debounce), when the field is left, or on Apply
const textSize: PropertySpec = {
  name: "textSize",
  label: "theme.textSize",            // a translation key;  English default "Text size"
  tooltip: "theme.textSize.tip",
  type: "choice",
  options: ["xs", "sm", "md", "lg", "xl", "2xl", "huge"],
  ordered: true,                      // a scale:  may show as a slider
  default: "md",
  as: "range",
  commit: "live",
}

The editor writes changes straight into the thing it edits, as the Theme Creator does by hand today, unless it is told to wait for Apply.

  • Live (the default): each change lands at once. A text field waits for a short pause first (debounce); a field marked "on leave" (an id, say) lands only when the cursor leaves it.
  • In a modal: changes are kept in the editor, and land all at once on Apply. Cancel drops them.
  • Many things at once: a field shows the value when every thing agrees, and a blank "mixed" state when they don't. Typing into it sets that property on all of them.
  • Errors show as you type, from the property's type first, then any rule the schema or the form adds. A value that fails is not written.
  • "On change" rules run after a write: setting the font family can change the weights offered.

The spell editor makes a default editor from a schema, and saves it as a page you can tweak by hand: Theme.editor.html.

  • It holds only the markup above: groups, order, which control, hints. Everything else still comes from the schema, so the page stays short.
  • A check-and-fix tool compares the page with the schema as it is now:
    • a property the page names that the schema dropped: flagged, or removed with a fix
    • a new property in the schema: added to the page, in an "Other" group
    • a control that no longer fits (a list of choices became free text): flagged
  • Validators and "on change" rules: TypeScript first. Written in spell later, in English (and other languages once spell reads them).
  • Compiled: the page and its rules become one TypeScript module defining a custom element (<theme-editor>), so it runs where the spell parser isn't loaded.
