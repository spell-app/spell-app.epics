Rules on a type, in spell

The new words a spell type uses to say what its properties must be, like "its title must not be empty". They're new language, so you get to approve the words before I build them.

session property-editor, starting P9 (Spell Rules) 2026-10-20
property-editor: Spell UI elements that draw a form from a schema, for the spell editor and anything else. You chose to build only rules ON THE TYPE in this phase (change rules and rules in an editor page wait for later). What you'll write in a .spell file to say a property must be filled in, match a pattern, be in a range ...; and what happens when a value breaks one.
  • Today a type's outline can say only what KIND each property is: - it has a name as text, - its direction is up or down. Nothing says "must".
  • A RULE, here, is a line in that outline saying what a property's value must be. It travels with the type: through the compiled declarations into every property editor drawn for it, and into the type's JSON Schema (what VS Code and other tools read).
  • Each rule turns into one of the form's existing checks (Spell UI's Validator, Fomantic's rule names), so the form says what's wrong in words it already has: "Title must have a value", "Version must match the pattern". 
a project-card is a thing where:
	- it has a title as text
	- it has a version as text
	- it has a summary as text
	- it has a rating as a number
	- it has a homepage as text

	- its title must not be empty
	- its version must match "^\d+\.\d+\.\d+$"
	- its summary must be at most 140 letters long
	- its rating must be between 1 and 5
	- its homepage must be a url

Every row is a separate rule word; comment on any of them in the box below.

Spell Means Form check JSON Schema
its title must not be empty must be filled in empty minLength: 1, required
its version must match "^\d+$" a pattern (a regular expression) regExp[/^\d+$/] pattern
its name must be at least 3 letters long shortest minLength[3] minLength
its name must be at most 40 letters long longest maxLength[40] maxLength
its rating must be between 1 and 5 a number in a range, ends included range[1..5] minimum, maximum
its age must be at least 18 smallest number minValue[18] minimum
its age must be at most 120 largest number maxValue[120] maximum
its contact must be an email an email address email format: "email"
its homepage must be a url a web address url format: "uri"
  • "Letters long" counts characters, spaces and digits too, as the form's check does.
  • "One of" needs no rule: - its size is small, medium or large already limits it to those.

A rule is about one property. Where in the type's outline is it written?

A line of its own, among the property lines, starting with the property: - its title must not be empty. Reads as a sentence; works for a property declared anywhere, even in another file.

Indented under the property's own line; shorter (- must not be empty) but outline lines don't nest today, so it's more grammar. 

	- it has a title as text
		- it must not be empty

Tacked onto the declaration: - it has a title as text, which must not be empty. One line per property, but long lines when it has several rules.

Which rule words should P9 build? (The table in 1.2 has each one.)

its title must not be empty

its version must match "^\d+$"

must be at least / at most 3 letters long

must be between 1 and 5, must be at least / at most 18

must be an email, must be a url

When a value breaks a rule, the form shows a message. Can the rule give its own?

Spell UI's message unless the line adds one: - its version must match "^\d+\.\d+\.\d+$", saying "Write it like 1.2.3".

Always Spell UI's own ("Version must match the pattern"); less to learn, but a pattern's message tells the reader little.

Some rules compare properties: - its end must be after its start. Build those in P9?

P9 builds the words above; any spell condition after "must" comes later. Those can't become a form check by name: they need compiled code, which only a running class has.

its X must <any spell condition>, compiled into a check method on the class. The editor runs it when it edits a live thing; declarations and the JSON Schema can't carry it. About +3h.

A form checks rules as you type. What happens when a running spell program sets a value that breaks one (set the card's title to "")?

The value is set, and the console warns, as it does today for a value of the wrong type.

Only forms check. Cheapest; a program's mistakes go unseen.

The program stops with an error. Strict, but a typo in a rule can then break a running program.
