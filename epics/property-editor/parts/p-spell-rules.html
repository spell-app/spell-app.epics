• A spell type could say only what KIND each property is (- it has a name as text).
  • Nothing said what its value must be, so the forms drawn for it couldn’t check anything.
  • Checking a value (validation) was TypeScript only.
  • Built rules on the type only: what a property's value must be, written in spell after must.
  • Nine rule words, written in any of three places, with an optional suggestion or message.
  • Each compiles to the rule object Spell UI's form checks read, in javascript, TypeScript and Python, and the declarations record it.
  • A spell type's rules show in its property editor, with no running program
  • The JSON Schema for VS Code gets the matching keywords
  • A program breaking a rule still sets the value, and warns in the console, the same words in each target
  • Rules in the page, "when it changes" rules and rules comparing two properties wait for a later epic (C13, C14, C15)
  • The rule words, after must:
    • not be empty
    • match "..."
    • be at least / at most N letters long
    • be between A and B
    • be at least / at most N
    • be an email, be a url
    • then with suggestion "..." or saying "..."
  • Three places to write one:
    • a line of its own
    • the property's own line: , which must ...
    • indented under it: - it must ...
  • as a url / as an email as kinds.
  • Compiled into the class's schema (rules), in javascript, TypeScript and Python.
    • The declarations record them, so the property editor checks them.
    • The JSON Schema gets the matching keywords: minLength and the rest.
  • A program breaking a rule: set, with a console warning, the same words in javascript and Python
  • Form messages name a property by its shown label (J23); a pattern read as typed (J24)
