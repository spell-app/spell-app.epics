Most of the pieces exist already. What's missing is the part that turns a schema into fields, and the parts of a schema a form needs.

  • The Theme Creator page is the model for how an editor looks.
    • It's a hand-written page in the brand folder.
    • About 380 lines of script wire it, copying each control's value into one state object. It stays hand-wired in this epic.
    • Its "Text size" is a slider in pixels (13 to 19), with a Reset button that shows once it's moved; not a named scale yet.
    • "Corners" and "Depth" are segmented menus used as button groups.
    • Every field has an info tip.
  • Schemas we output today:
    • spell classes: a JSON Schema per class, written by jsonSchemaFor(). It carries types and choice lists only: no labels, limits, patterns or groups, and it drops the default.
    • web components: each element's vocabulary, the richest source. Every attribute has a kind, its values, a default and an English description, and describe() returns it at run time.
  • The controls are all there (input, select, slider, segmented menu, checkbox, colour pickers), and they all send the same change events. None of them debounces, and none shows a "mixed" value except the checkbox.
  • The field shell is <brand-field>: a label row with actions, an info tip, help text and an error. It lives in the brand package, not Spell UI.
    • Spell UI's own <ui-field> is a plain wrapper: a label, the control, and an error prompt <ui-form> shows.
  • The spell editor's Project Settings form, <ProjectSettings>, is a scaffold: five placeholder fields on <ui-form>, and nothing shows it yet.
  • <ui-form> already binds named controls both ways to an object (Solid signals, Spell UI members, spell objects), with validation rules.
  • Translation: only a component's own text is translated so far.
    • A component's visible text goes through UI.i18n, keyed per element, falling back to English.
    • Attribute descriptions are English only.
    • Spell's own words (its labels) are English only so far.
