The brief saved for this epic (from output-targets):

Epic `python-target`: a `py` target, so spell compiles to Python -- a third writer (`PyWriter`) on the same spell tree that `JSWriter` and `TSWriter` already walk.

## Goal

- Spell is WRITTEN in several human languages; it should RUN in several programming languages too (output-targets O1).
`js/solid` and `ts/solid` proved the split. Python is the first target that ISN'T javascript underneath.
- Done means: `spell compile FizzBuzz --target py` writes `FizzBuzz.compiled.py`, it runs under `python3`,
and the core contract's test programs print the same lines on all three targets.
- Python is the stress test for everything the tree still assumes about javascript:
lambdas, truthiness, names, nothing / `None`, async, lists counted from 1.

## What's already decided

- The words (Q1, Q2): `py` is a TARGET, `PyWriter` is its WRITER. Docs say "the Python writer".
- Python is its own epic (Q3, T1), starting from what output-targets left:
the writers, the meaning-only tree, `SP.TARGETS`, and the contract's test programs.
- Names are a feature of the WRITER (Q51): each writer says how it writes spell's names, in `nameOf()`.
JS / TS went camelCase; "a Python writer will want snake_case" -- for every member (Q56, T25).
- Per-target naming table (drawable-thing P11, "Names By Target", still todo):
each target says in ONE place how it writes types, methods, variables, properties, constants.
"A later Python target sets its own table (snake_case members, say) in one line." Build on it, or build it first.
- Declarations live in `<Project>.declarations.json` beside the output, the same for every target (Q8),
so a Python project could import a JS-built one.
- A project lists its targets in `project.json` (`"targets": ["js/solid", "py"]`); `--target` overrides one run (Q7).
`js/solid` is ALWAYS compiled: the editor, runners and language server run it (J12).
- The targets table is `{ name, writer, suffix, can: { draw } }` (J12). A `core` field and `can.observe`
(NEVER `can.react`) join it when Python needs them.
- "Lists Start at 0" is an EARLY phase of this epic (T1 reply, Owen 2026-10-06; memory note "compile-targets"):
- `project.json` `"listsStartAt": 0` (default 1), applied when COMPILING. Core stays 1-based, the one canonical form.
- NOT a runtime flag (`spellCore.INDEX_BASE`): one core serves every project in a program, so a 1-based library
imported into a 0-based project would silently read the wrong item.
- Ordinal words don't change: "the first card", "the last card" mean the same either way.
- Not plain arithmetic: `positionOf()` not found is `undefined`, and `undefined - 1` is `NaN`.
Put the base in core (a "start at" argument, or a 0-based twin per helper), so missing stays missing.
- About 50 rule sites through 7 helpers (now `getItemAt`, `positionOf`, `rangeBetween`, `rangeStartingAt`,
`removeItemAt`, `removeRangeBetween`, `addAtPosition` -- P16's position names, Q47), plus a loop's position.
- Works for `js/solid` and `ts/solid` too, not just Python. The Python writer writes native 0-based indexes;
spell's ranges are inclusive, so it adds 1 to a slice's end.
- Deprecated core names (old position names, `spellCore.element()`) are NOT part of the contract:
Python's core needs only the new names (J55, J94).

## The hard parts / open questions

1. Readable or just runs? (carried over from Q3 / T1) Python a person would happily read and edit leans much harder
on datatypes and the writer. Decide FIRST.
2. The runtime: what is `spell_core`? A Python package porting `@spell/core` (about 4,000 lines in `core/src/`,
tests left out): lists, text, things, JSON, console, tests. Plus a machine-readable list of core methods,
which output-targets never wrote (J15): so the port can't miss one.
3. Drawing: Python has no DOM. Does `draw` do nothing (`can: { draw: false }`, a project that draws gets an editor
error), or write HTML text for server pages (`py/html`, `draw: "html"`, sketched in O1)?
4. Lists counted from 1 vs Python's 0: the core papers over it (`getItemAt(list, 1)`), or "Lists Start at 0" writes
native indexes. Open (T1): does `-1` still mean last in a 0-based project? Do hover text and the Type
Explorer's "counts from 1" follow the setting?
5. Events: `on()` / `trigger()` with no page. Does `on card-click` mean anything in Python?
The contract never clicks anything (C7), so handlers aren't tested on any target yet.
6. Async: `pause for 50 msec` is `async` / `await` in JS; `async def` + `asyncio` in Python, or plain `time.sleep`?
7. Types: type hints (`def deal(self, pile: Pile) -> None`)? Checked by `mypy` / `pyright` the way `tsc` checks
`ts/solid` (`checkedBy`)?
8. Names: snake_case members, PascalCase types. `$` is illegal in Python, and the tree still holds JAVASCRIPT names
(`is_a_$suit`, `'up'`, `"clubs"`) in scope records (J4, T4). A Python writer sees those as is until T4 makes
them spell names, read by every reader and spelled by each writer. Do T4 in this epic, or before it?
9. The words file (J87): the Thing Explorer labels an action from its compiled name, so `moveToPile` lost spell's
slot word ("move to (pile)"). The Python target would write `move_to_pile` and lose it the same way.
Owen: "carry the original wording somewhere for reflection, especially into other languages."
A `<Project>.en.js` words file keyed by the COMPILED names -- does Python get its own, or share one?
10. Where languages disagree (the sketch's table): empty list as a condition (`[]` is false in Python), text plus a
number (`TypeError`), nothing (`None`), `45 / 15` is `3.0`, multi-line lambdas (lifted into a nested `def`),
getters (`@property`), class set-up after the class, reserved words (`class`, `None`, `is`).
11. How tests run Python: the contract needs all targets to print the same, line for line.
`CLI.runCode()` runs node today; Python needs a `python3` child process, a pinned version, and a seeded random
(the deal must match `Math.random()`'s seeded one, or Solitaire's transcript differs). The fake page's printed
body won't exist in Python: compare only the console part? CI needs Python installed.
