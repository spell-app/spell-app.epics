Yes: the same to draw methods can draw Solitaire in a terminal, and take its clicks.

  • A prototype draws one element tree three ways: as HTML, with Rich, and with Textual.
  • A small sketch draws it with Ink, the CLI's own.
  • Recommended: a future py/terminal target on Textual, as its own epic (the terminal target todo, T1).

What the prototype shows

The prototype is P15 · Terminal Drawing Study's: a small Solitaire, hand-written in the shape the Python writer gives a to draw method.

  • Hand-written, because compiled Python didn't draw yet when it was made: P15 was built before P12.
  • Its h() builds a TREE: tag, props, children.
    • The calls are the same as compiled Python's: h("div", {"class": ..., "onClick": ...}, ...).
    • The tree turns back into the same HTML, so nothing is lost by keeping it.
    • spell_core's own h() builds a tree too, since P12 (J29), but drops the click handlers: a terminal target would keep them.
  • textual_board.py draws the tree with Textual: a live board in the terminal.
    • Clicking a card calls its onClick, which fires card-click with the card.
    • The game's on card-click plays it, and the board is drawn again.
  • rich_board.py draws the same tree with Rich: a still picture, printed once.
  • ink_board.tsx draws a smaller tree of the same shape with Ink, the CLI's own (Ink 5, React 18).
    • Ink reads no mouse: Tab moves between the clickable elements, and Enter clicks one.
  • A test proves it headless, with Textual's own test driver:
    • the board draws
    • a click on the 2 of diamonds fires card-click with that card
    • the redrawn board shows it on the 3 of spades
  • Textual and Rich are in a dependency group of their own, study: spell_core itself still needs nothing but Python.
  • It was clicked headless only, never by hand in a real terminal: the commands below do that.

class Node:
    """What every drawn element's widget shares:  its element's click handler."""

    handler: Callable[[], Any] | None = None

    def on_click(self, event: events.Click) -> None:
        if self.handler is None:
            return
        event.stop()
        # to the app, not run here:  drawing again removes this widget, which can't wait for its own removal
        self.app.post_message(Clicked(self.handler))


class SpellApp(App):

        """Call a click's handler, then draw the board again."""

        await self.query_one(Board).recompose()

Textual does the most of what a spell app needs; Rich is the drawing underneath it; Ink is JavaScript's.

How spell's elements map

A drawn tree is HTML-shaped, with Fomantic's classes on it. Each element became the nearest thing each library has.

On the page Textual Rich Ink
a div, a table, a cell a box, its children one under another a group of renderables; a Table for a table a column Box
tr a row of boxes, equal widths a table row a row Box, each cell grown equally
an element holding only text (a card) one line of styled text one styled Text one Text
span inside it a styled run in that line a styled run nested text
class the widget's classes, plus the tag (el-td) looked up in a class-to-style table looked up in code
onClick a mouse click nothing focus with Tab, then Enter
a stacked pile (cards on top of each other) every child docked to the top, so they overlap only the last child only the last child
an icon (<i class="bicycle icon">) a pattern of text, ░░░░: the terminal has no pictures

What doesn't carry over

  • The page's CSS doesn't run in a terminal: a terminal target needs a style sheet of its own.
    • Textual's CSS reads the same class names, so a project could keep one beside its styles.css.
    • A plain one for Fomantic's classes (ui button, red) could come with the core.
  • Sizes are in character cells, not pixels: a card is one line high.
    • Positions such as position: absolute have no equal; docking stood in for the stacked piles.
  • A class name can't start with a digit in Textual: a card's rank is one (class="Card 8 clubs").
    • The prototype writes it _8; the page's CSS can't name .8 plainly either.
  • Rich and Ink have no colspan: "Klondike Solitaire" wraps in its narrow column under Rich.
  • Emoji suits: ♠️ is two characters, the suit and a "draw me as a picture" mark.
    • Terminals disagree on how wide that draws, one cell or two, so columns slip.
    • The prototype leaves the mark out in the terminal: ♠.
  • Nothing tracks what changed: after each click the whole board is drawn again.
    • Fine for Solitaire (instant); a bigger app would redraw only the things whose properties changed.
  • A click handler that redraws must not run inside the clicked widget: Textual waits forever for the widget to remove itself.
    • The prototype sends the click to the app instead.

A terminal target?

Four ways forward. Each is a later epic, not more of this one: this epic's Python still draws HTML text (Q2).

  • A second Python target: the same compiled program, its app drawn in the terminal and clicked.
  • Its steps:
    1. spell_core's h() keeps each element's click handler in its tree (since P12 it builds the tree, and prints it as the same HTML)
    2. a terminal half of spell_core draws the tree with Textual, clicks calling back
    3. a style sheet: a plain one for Fomantic's classes, and a project's own beside its CSS
    4. Spell UI's elements as Textual's widgets: buttons, checkboxes, inputs, tabs
    5. redrawing only the things that changed
    6. the contract clicking through a game, headless
  • The same app also runs in a browser, through textual-serve.
  • Textual and Rich become an optional extra of spell_core: a program that never draws needs neither.
  • Cost: an epic of about 20-30 hours.
  • Why recommended: it's the only one of the three with clicks, a style sheet by class and a test driver.
  • A second javascript target, its app drawn by Ink.
  • Keyboard only: Ink reads no mouse, so every click becomes Tab and Enter.
  • javascript draws with Solid; Ink is React. A compiled program would need a second drawing path, or a tree both could read.
  • Ink stays at 5 while the CLI is on React 18.
  • Cost: an epic of about 15-25 hours.
  • Python's spell run prints the app's board as a picture when the program ends, beside or instead of its HTML.
  • Nothing to click: a still picture.
  • Cost: about 3-4 hours, after Python draws (P12).
  • A good first step of A, since Rich comes with Textual anyway.
  • Python draws HTML text only, as decided (Q2); the prototype stays a study.
  • Owen's "translate widgets into CLI programs" waits.
  • T1 becomes a future epic, py-terminal, started from this section and the prototype.
  • Nothing changes in this epic: its Python keeps drawing HTML text.
  • The prototype stays in the repo as that epic's starting point; its tests run only when asked for.
