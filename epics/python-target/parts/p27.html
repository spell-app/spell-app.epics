A page's event names the thing it happened to inside its details, by an id only Python's state knows: {"card": {"@id": "3"}}.

An event names its target in the reference words the drawable-thing epic brings, a string or a list of them: "target": "Card#3", Tableau#T1, UIButton#4.

Its details are kept for the event's other details.

It waits for drawable-thing to merge into main; while it hasn't, the phase is parked.

  • Owen, on the durable doc, word for word (cm2, on "details": { "card": { "@id": "3" } }): "for just identifying what gets the event, use `target` as string or array of strings with the new `Tableau#T1` or `UIButton#4` syntax. Ok to keep `details` for event details."
  • What a page sends, before and after: 
    // today
{ "trigger": "card-click", "details": { "card": { "@id": "3" } } }
// after
{ "trigger": "card-click", "target": "Card#3" }
{ "trigger": "cards-moved", "target": ["Card#12", "Card#13"], "details": { "count": 2 } }
  • The reference words are the drawable-thing epic's (its P18, Thing References):
    • Tableau#T1: a tableau by its name; Tableau#1: the first tableau, by place (digits always mean a place)
    • a super-type finds a sub-type's: Pile#T1
    • the javascript core's thingForReference() reads one; referenceFor() writes one
  • The page: sendTrigger() writes each thing's reference as the target. The state and the patches keep their @ids (P17, P18): a reference names a thing for a person, an id ties the mirror together.
  • Python: spell_core gets thing_for_reference() and reference_for(), ported; the page session reads target and hands the handler its thing, as now.
  • A call's "on" may take a reference the same way, so a message names things one way; if done, a judgement call.
