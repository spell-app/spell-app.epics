For P17 · Web Components For HTML: the program's things live in Python. How does the page learn what they are, and what changed after a click?

  • spell_core already writes a thing as JSON, its class under "@type", a list's items under "@items".
  • What's missing is identity: the javascript core's JSON reader warns that "a card in two places comes back as two cards".
    • A card sits in a pile, and the game also holds it as the card being moved.
    • A click must name THE card, so Python finds the same one, not a copy.
    • So every option below gives each thing an id, and a second mention of it is a reference to that id.
 
{ "@type": "Tableau", "@id": 9, "name": "T1",
  "@items": [
    { "@type": "Card", "@id": 17, "rank": "queen", "suit": "spades", "direction": "up" },
    { "@type": "Card", "@id": 18, "rank": "4", "suit": "hearts", "direction": "down" }
  ] }
  • Python sends every thing the app can reach, each with its id.
  • The page updates its mirrors in place, by id; Solid redraws only what actually changed.
  • Solitaire's whole state is 52 cards and 13 piles: a few kilobytes, cheap on a local server.
  • Simplest to get right: no change tracking in spell_core, nothing to miss.
  • Changes only (B) can come later, if a program grows.
  • spell_core notes each property set and each list change, and sends just those.
  • Smallest messages.
  • Cost: spell_core has no change tracking today (things are plain dictionaries, 1.4), and a change it misses leaves the page wrong.
  • Each element gets its thing's properties as attributes, <solitaire-card rank="queen">, as drawable things' elements already read them.
  • No JSON reader on the page.
  • Cost: a drawing that reads other things (a pile's cards, the game's score) has nothing to read; only flat, drawable things would work, and Solitaire's cards aren't drawable things.
  • spell_core's JSON gains "@id" and references to an id
  • the javascript core's JSON reader updates things in place by id, rather than making new ones
