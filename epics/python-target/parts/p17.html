A Python program draws only HTML text, printed when it ends: nothing a browser can show live, or click.

Compiling to Python also writes the program's drawing as JavaScript: an element per drawable type, and one for the app, on the javascript core.

Python hands its things to the page as JSON, each with an id; the page draws them, and sends each click back as a message naming things by id.

A test page draws Solitaire from a saved Python state, before any server exists.

    • The HTML bits: each type's to draw, its styles, and the layout of the app.

  • Compiling Solitaire to Python writes a second file beside the Python: Solitaire.elements.js, the drawing half of the program, in JavaScript.
    • What goes in it is the fork in Q20; recommended: each type's properties, the getters its drawing reads, its to draw and its styles.
    • An element per drawable type, as today, and one for the app itself, so a page can hold the whole game.

  • The Python program hands its things to the page as JSON: the "@type" and "@items" spell_core already writes, plus an id for each thing.
    • Why the id: JSON keeps no identity, so the card a click names must be found again as the SAME card in Python, not a copy.
    • The page rebuilds the things as stand-ins ("mirrors") and draws them; new state updates them in place, so only what changed redraws.
    • Whole state or only changes: Q21.
  • A click goes back as a message, never run on the page:

    • whoever hosts the page (P18's Flask app, or a test) says where the messages go
