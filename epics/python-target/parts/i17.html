Two tabs of one browser showed the same Solitaire game, but only the tab Owen clicked in changed: the other tab stopped following after its first board.

  • Owen tried the Python web app hand check (T6) in Chrome on 2026-10-11, after the branch had merged into main.
  • He wrote: "same browser windows, 2 tabs -- same game. state sync problems."
  • The Quart server kept the wrong handle for each tab's connection, in SpellSessions.serve().
    • It kept Quart's websocket, which is not a connection: it stands for whichever connection's code is running at that moment.
    • A click in one tab sends the changes to every tab of that visitor. While that click's code runs, every tab's "send" went to the CLICKING tab.
    • So the clicking tab got the other tab's changes too, and the other tab got nothing after its first board.
  • Seen in the browser: before the fix, after one click the clicking tab received 5 messages and the other tab 1.
  • Python's own side was fine: two tabs' sessions on one game stayed equal over 300 moves.
  • Each tab now keeps its own connection, not the stand-in, so a send reaches the tab it was meant for.
  • A new browser test, "a visitor's tabs share one game, each following the other's clicks, both ways", in quartApp.test.ts.
    • It fails without the fix, and passed with it three runs out of three.
    • All six Quart browser tests pass, and the Python packages' review passes.
  • Also fixed: the generated app (Solitaire.app.py) now runs without Quart's reloader.
    • The reloader is on by default. When a file the server had loaded changed, it restarted the server under a name Python couldn't find, and the server died.
    • A restart would also end every visitor's game, which lives only in the server's memory.
