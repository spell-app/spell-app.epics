Python is spell's first target that isn't javascript underneath: spell compile Cards --target py writes Cards.compiled.py, and Python runs it.

  • It took four pieces, as the targets guide's "Adding a target" lists them:
    • a WRITER, PyWriter, walking the same spell tree the JavaScript and TypeScript writers walk
    • two entries in the targets table, SP.TARGETS:
      • py: plain Python, where a pause sleeps
      • py/asyncio: the same program on asyncio, Python's own way to wait (Q18)
    • a RUNTIME, spell_core: a small Python package, the Python twin of the core
    • a place in the core contract: all six test programs print the same lines on every target
  • Four things changed for the JavaScript targets too, because Python needed them first:
    • a project can count its lists from 0 ("Lists start at 0", 1.3)
    • the core's position methods take where lists start, call by call (Q10)
    • the core has a seedable random of its own, and a machine-readable list of its methods (1.4)
    • the tree holds spell's own values, not JavaScript spellings like 'up' (1.5)
  • A project asks for Python in its project file, "targets": ["py"], or for one compile with --target py.
  • The editor, the runners and the language server still run the JavaScript target.
    • Python is compile-only: spell run and spell test don't run it yet (T4).
    • A compiled program runs through spell_core's own runner, seeded as the javascript is (P9):
    uv run --project packages/core/py python -m spell_core.run Cards.compiled.py --seed 1 --page
  • the JavaScript writer: 1,601 lines; the TypeScript writer on top of it: 1,278
  • the facts both writers share about a project (getters, members, item types): 525 lines, mostly reusable
  • the core: about 4,450 lines; the plain-logic part a Python port needs, about 3,000 of them
  • a first spell_core in Python: roughly 1,500 lines to run Cards and Solitaire's logic
