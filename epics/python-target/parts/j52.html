Chose a patch that lists the things changed since the last one, each written whole, over a list of property-by-property changes as the phase goal sketched.

  • A changed thing is written with all its properties, and a list with all its items.
  • What it holds is named by id alone, or written whole if the page has never seen it.
  • So a card moved to another pile is the two piles, each naming its cards by id.
  • Why:
    • A mirror reads a patch as it reads any state: no new code on the page.
    • No separate "add" and "remove" bookkeeping for lists to get wrong.
    • The cost: a pile of twenty cards resends twenty short {"@id": ...} mentions, not one.
[ { "@type": "StockPile", "@id": "2", "name": "stock", "@items": [{ "@id": "5" }, { "@id": "6" }] },
  { "@type": "DiscardPile", "@id": "4", "name": "discards", "@items": [{ "@id": "7" }] },
  { "@type": "Card", "@id": "7", "rank": "queen", "suit": "spades", "direction": "up", "pile": { "@id": "4" } } ]
Read as any state; a little larger.Smallest, but a second format, and a reader of its own on the page.
