pause for 50 msec makes JavaScript methods async. Should Python's be async def too, or plain functions that sleep?

  • The catch: compiled JavaScript calls async methods without waiting for them.
    • Card's turnOver() calls this.turnFaceDown() bare.
    • In JavaScript that still runs.
    • In Python, an async def called that way does NOTHING, so "the card is face down" would fail.
  • Python without a page has no animation to wait for: a pause only slows the program down.
  • Methods stay plain: def turn_face_up(self).
  • A pause sleeps: core.pause_for(50, "msec") calls time.sleep.
  • The simplest Python, and what a person would write for a script.
  • A test run can make pauses instant.
  • Limit: "wait for" and two things running at once (Solitaire's animations) run one after the other.
  • Matches JavaScript's shape; every caller of a pausing method becomes async too, and awaits it.
  • The writer must add the awaits JavaScript leaves out, or start tasks.
  • Heavier Python: asyncio.run(main()), await on many lines.
  • no async in compiled Python; core.pause_for() sleeps, instantly in tests

The asyncio option became a target of its own, py/asyncio, not the project setting "pythonAsync": true this answer names (Q18).

  • Owen's note on the question: "make this a language option, or twisted python?"
  • A project option, then: by default, compiled Python is plain defs and a pause sleeps; a project that sets "pythonAsync": true gets async def, the awaits JavaScript leaves out, and asyncio.run().
  • Why asyncio rather than Twisted:
    • Twisted is the older third-party library for waiting on many things at once, from before Python had its own
    • asyncio is the standard library's answer, built into Python since 3.4, and what new code uses
    • so the option writes asyncio
  • Both modes are built in P11 · Pauses And Events, and must print the same.
  • no async in compiled Python unless a project asks for it
  • a project setting, "pythonAsync": true
