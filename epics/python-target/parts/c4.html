Owen chose a game per visitor (Q24, B): each browser session gets its own spell_core and its own run of the program, in one server process. spell_core isn't built that way today, and the choice has limits worth knowing.

  • Today, spell_core is ONE core object for the whole process (J5): compiled Python writes from spell_core import core once, and every call goes to it.
  • What P20 changes:
    • core becomes a stand-in that forwards each call to the current session's own core, kept in a Python context variable (one value per asyncio task, so each session's handlers see its own).
    • The compiled program runs once per session, in a fresh namespace: its module-level things (the game, the deck, the piles) are that session's alone.
    • A plain run (python -m spell_core.run, the core contract) has no session: the stand-in forwards to the one default core, as today.
  • What it leaves out, for now:
    • A project the program imports (from cards import Card) is imported once per process: its classes are shared, which is fine, but any things it makes at its top level are shared by every visitor.
    • Games live in memory: restarting the server ends every game.
    • A game is dropped after its session has been idle a while (an hour, say), so memory doesn't grow without end.
    • One process only: a server run with several worker processes would split a visitor's clicks between games.
  • spell_core's core is a stand-in for the session's core
  • spell-quart runs the program once per session, and drops idle ones
