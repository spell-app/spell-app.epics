The four phases, in order:

  1. P17 · Things As JSON By Id: the program's whole state as JSON.
    • spell_core writes it: each thing with an "@id", and each later mention of it as a reference.
    • spell_core reads it back by id, and so does the javascript core, into mirrors: javascript copies of Python's things.
  2. P18 · Only Changes Sent: spell_core notes each change to a thing or a list, and hands over a patch of what changed since the last one.
  3. P19 · JS Web Components: compiling to py also writes the drawing half, with the javascript writer.
    • It's an elements file, of custom elements.
    • Its things are mirrors of Python's, and clicks go back to Python as messages.
  4. P20 · Quart Spell Apps: a Quart app serves the page and a WebSocket, a game per visitor; the state goes down when the page opens, then only the changes.

What happens, step by step, once all four are built (each step's decision linked):

  1. Compiling Solitaire to py writes its Python, and two files beside it:
    • the elements file, Solitaire.elements.js (Q20)
    • the app file, Solitaire.app.py: a short Quart app with every route spelled out (Q23, Q25)
  2. Running the app file starts the server, on spell-quart, a package of its own beside spell_core (Q26).
  3. A browser opens the page. Its session gets its own core, and its own run of the program, which deals its own cards (Q24).
  4. The page loads Spell UI, the javascript core and the elements file, and opens a WebSocket back to the server (Q22).
  5. Python sends the whole state, each thing with its id (Q21, A); the page reads it into mirrors, and the elements draw the board from them.
  6. A click on a card sends a message up the WebSocket: card-click, with the card's id.
  7. Python finds that card by its id and runs the game's on card-click, in Python, where it was written.
  8. After the handler, and at each pause in it, Python sends only what changed (Q21, B); the mirrors take it, and only the elements whose things changed redraw, so auto-play animates.

The questions' recommended answers drew one app:

  • The compiler would have written each type's drawing as JavaScript, Solitaire.elements.js, run on the javascript core (Q20, A): close to the plan now.
  • Python would have sent its things as JSON with ids from the start, for the page to draw (Q21, A).
  • Clicks would have been posted to the server, with a stream pushing changes back (Q22, A).
  • The server would have been plain Flask running the py target, one game shared by every visitor, made by create_app() in spell_core, with Flask an extra of spell_core (Q23 to Q26, A).
