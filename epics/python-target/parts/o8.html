Owen added this after Doc Review, 2026-10-11: a Python spell app becomes a web app, its logic and its drawing in Python on a Quart server, the browser only its view.

  • His words:
    • P17 · Web Components For HTML: "python compiler outputs compiled JS web components for the HTML bits"
    • P18 · Flask Spell Apps: "spell apps" in python are python flask based apps, using these web components
  • His answers to the seven questions, the same day (Q20 to Q26), chose a different path from the one first drafted: Python draws the page itself, on Quart rather than Flask, a game per visitor.
  • The phase names are kept, since the plan-doc tool can't rename a phase; read P17 as "Python Draws The Page" and P18 as "Quart Spell Apps".

What happens, step by step, with his answers (each step's decision linked):

  1. Compiling Solitaire to py/asyncio writes the Python as today, and beside it an app file, Solitaire.app.py: a short Quart app with every route spelled out (Q23, Q25).
  2. Running that file starts the server, on spell-quart, a package of its own beside spell_core (Q26).
  3. A browser opens the page. Its session gets its own core, and its own run of the program, which deals its own cards (Q24).
  4. Python draws the page as HTML, as it does today, in a web mode that adds a few marks (Q20):
    • each thing's id and properties as attributes on its element (Q21)
    • an id on each click handler
  5. The page shows it with Spell UI's elements and styles, and opens a WebSocket back to the server (Q22).
  6. A click on a card sends its handler's id up the WebSocket.
  7. Python runs that handler, the game's on card-click, in Python, where it was written.
  8. Python draws the page again, after the handler and at each pause in it, and sends the HTML down the WebSocket.
  9. The page client morphs the new HTML in: only what changed is touched, so auto-play animates.

Then two more phases, in the order Owen gave for Q21: "start with C, new phase to do a, then subsequent phase to do b".

  • P19 · Things As JSON By Id: the whole state travels beside each drawing, each thing with an id, and the page keeps a mirror of each.
  • P20 · Only Changes Sent: only what changed travels, and only the drawings it touches.
  • How those read when Python draws, and what to pick if that isn't what Owen meant: J46.

The questions' recommended answers drew a different app:

  • The compiler would have written each type's drawing as JavaScript, Solitaire.elements.js, run on the javascript core (Q20, A).
  • Python would have sent its things as JSON with ids from the start, for the page to draw (Q21, A).
  • Clicks would have been posted to the server, with a stream pushing changes back (Q22, A).
  • The server would have been plain Flask running the py target, one game shared by every visitor, made by create_app() in spell_core, with Flask an extra of spell_core (Q23 to Q26, A).
  • The tension worth a second look: Owen first asked the compiler to OUTPUT JavaScript web components, and the path he chose compiles none. The reading recorded in Q20's answer is that the web components are the page's own, drawn by Python.
