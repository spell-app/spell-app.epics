The core's method list is a JSON file only a test reads; nobody can browse what the core offers.

A docs page made from the method list: each method, its parameters, its file, its Python name, and whether Python has it yet.

Made and checked as the list is, so it can't go stale.

  • Owen, on the durable doc, word for word (cm12, on "A machine-readable list of the core's methods, so a port can't miss one: spellCore.declarations.json."): "do JS/TS targets use this as well? Great for documentation!"
  • The answer: no, not to compile.
    • The javascript core writes the list (yarn gen:declarations, in core), and a core test fails when it's out of date.
    • Its only reader is Python's test, which checks spell_core has each method, in snake_case.
    • The javascript and TypeScript writers compile against the core's TypeScript itself.
  • The page: a reference to the core, one row per method, grouped by the file it's in:
    • its javascript name and parameters, and its Python name
    • whether Python has it yet, and if not, which phase is expected to port it (J17)
    • a line of description, from its docstring: the list holds no descriptions today, so the generator reads them from the source
  • Where the generator lives follows the commands guide, read first: beside gen:declarations, or a spell dev command. The phase suggests one before building it.
  • Kept current: made again with the list, and a test fails when the page is out of date.
  • packages/core/src/writeCoreDeclarations.ts, coreDeclarations.ts and their test
  • a new guide page, in the shared guides folder
  • guides/dev/commands/commands.json, if a command is added
  • the page lists every method in the list, with the right Python names
  • a change to the core without making the page again fails a test
  • spell dev docs fuss on the page; the docs index lists it
