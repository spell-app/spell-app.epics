A language is a set of rules, not a fork of the parser. Everything the table in 1.1 says "changes" is gathered into one thing, a LANGUAGE PACK: English is the first pack, Spanish the second, and each file's name says which one it's written in.

What a pack holds:

  • which characters make a word, the decimal separator, and how words inflect (singular and plural, with irregulars): the INFLECTOR is the pack's, so the English one (the npm pluralize) is loaded by English programs only
  • the small words: articles, the subject words (it / its), booleans, number words, ordinals, the identifier blacklist, member stop words, dangling prepositions
  • the built-in types' words and their members' words, onto the same core calls:
    • types: texto / número / lista / cosa …
    • members: largo / año / caracteres …
  • every rule's syntax and its tests, registered on the SAME rule classes as English (below)
  • the messages an author reads: the warnings (an article that doesn't agree among them) and the "Don't understand" fallback, with examples in that language
  • spell's own JSX words (children, in)

Where a language's words live (Owen's shape, from his comment M5):

  • a rule file holds its CLASS and nothing else: what the rule compiles to
  • a <module>.en.ts per rules folder registers every rule of that folder with its English syntax and tests
    • e.g. expressions.en.ts, assignment.en.ts
  • a <module>.es.ts beside it does the same in Spanish; a third language is a third file per folder
  • the small words a rule used to test in code (is not, a / an …) are WORD RULES each language registers; a rule's code reads their match, never a word:
    • definite_article, indefinite_article
    • is_or_is_not
    • is_or_is_not_a, singular and plural, so cards in the hand which are not a face card parses
    • has_or_has_not, can_or_cannot
    • it / its
    • and_or …
// rules/expressions/IsEqual.ts:  the class, nothing else
export class IsEqual extends InfixOperatorSuffix {
  getOperator(operator: P.Match) {
    return Negatable.isNegated(operator) ? "not equals" : "equals"   // a match, never the word "not"
  }
}

// rules/expressions/expressions.en.ts:  the folder's rules, in English
expressions.addRule(Negatable.specialize({ ruleName: "is_or_is_not" }), { syntax: "(is|(negated:is not|isn't))" })
expressions.addRule(IsEqual, {
  syntax: "{operator:is_or_is_not} {expression:operand}",
  tests: [["thing is other", "(thing === other)"], ["thing is not other", "(thing !== other)"]]
})

// rules/expressions/expressions.es.ts:  the same rules, in Spanish
expressions.addRule(Negatable.specialize({ ruleName: "is_or_is_not" }), { syntax: "(es|está|(negated:no es|no está))" })
expressions.addRule(IsEqual, {
  syntax: "{operator:is_or_is_not} {expression:operand}",
  tests: [["cosa es otra", "(cosa === otra)"], ["cosa no es otra", "(cosa !== otra)"]]
})

How a pack is kept whole (P7):

  • spell translate check compares every language with English: a rule, a word rule, a table entry or a message English has and Spanish lacks is listed, per file, and fails the check; it runs in spell-parser's tests too
  • spell translate fix writes the missing entries as stubs marked TODO: translate
  • fix --ai drafts each translation by asking Claude, through the claude command on the machine. Each is marked AI draft for review.
  • a deliberate difference is marked in the pack's file (// packs: ok -- why), so the check passes
  • so a new English rule never leaves a language behind silently, and a third language starts from a draft

How a file picks its pack (P19, in place of P4's project setting):

  • its name: Carta.es.spell is Spanish; Card.spell and Card.en.spell are English
  • one project may mix them: each file parses with its own language's parser, and they share the project's types
  • a words file per language present: <Project>.es.js (and .py.es.json5 for Python)
  • the editor, the language server, the highlighter and the parser's messages follow each file's language

Names stay the author's:

  • para "mover (una carta) a (una pila)" compiles to moverAPila
    • as move (a card) to (a pile) compiles to moveToPile
  • an accent stays: corazón is a legal name in JavaScript and Python (question Q2)
  • the core's own names (itemCountOf, randomItemOf) stay English: compiled code calls them, nobody reads them

Spell's packs copy them: a rule class is the canonical name, its syntax string the dictionary entry.

  • Spell UI gives every component an English vocabulary (UIButton.en.ts)
  • and a Dictionary per language, mapping those canonical names to local ones, a miss falling back to English
  • Spell UI's SharedVocabulary.es.ts already names a few attributes in Spanish
