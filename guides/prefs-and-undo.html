Preferences and Undo

new PrefStore("spell-site").set("scheme", "dark") writes spell-site:scheme = dark into the browser's storage: the same bytes the site's head script has always read.

A preference kept, and a card game's deal undone · 12 lines 
const site = new PrefStore("spell-site")       // every key it writes starts "spell-site:"
site.declare("scheme", { oneOf: ["light", "dark", "auto"] })
site.get("scheme")           // "light":  nothing kept yet, so its first choice
site.set("scheme", "dark")   // the browser's storage now holds  spell-site:scheme = dark

// a card game, written the way compiled Spell writes it, its deal declared undoable
static { this.declareAction("deal", { undoneAs: "Deal" }) }

await game.deal(3)           // waits between cards, turns each one over:  ONE step
game.undoTitle               // "Undo Deal"
game.undo()                  // every card back in the stock, face down, at once
game.redo()                  // dealt again at once:  the deal doesn't run again

Every repo now keeps people's preferences through ONE pref store, and Spell apps can undo. Before, a dozen one-off stores each guarded their own storage and picked their own keys, and nothing anywhere had undo.

  • A preference lives in the browser's storage, its database, memory, or the person's space on the page server: the app asks the same way for each.
  • The undo stack under it all is generic, and Spell's runtime builds undoable actions on it.
  • Spell properties also learned two things: an unset one reads a default by its type, and one declared remembered keeps its value from run to run.

Each part the way you meet it: a preference first, then the places that must be waited on, then undo, then what Spell's properties gained.

Make one store per app, named for it, and ask it for each value. The browser's storage holds every key under the store's name and a colon, so two apps on one site never share a value, and forgetAll() forgets only its own.

A store, its keys, its values · from the pref store's tests · 9 lines 
import { PrefStore } from "spell/util/persist/PrefStore"

const prefs = new PrefStore("PrefStore-test-values")
prefs.set("count", 1)              // localStorage:  PrefStore-test-values:count  = 1
prefs.set("label", "1")            //                PrefStore-test-values:label  = "1"
prefs.set("layout", { left: 30 })  //                PrefStore-test-values:layout = {"left":30}
prefs.get("count")                 // 1
prefs.get("label")                 // "1"
prefs.get("width", 250)            // 250:  nothing kept, so the fallback

A value is read as JSON only when it looks like JSON; anything else is text. So a key a person or a plain script wrote reads back as written.

set kept as reads back
set("scheme", "dark") dark the text "dark"
set("width", 240) 240 the number 240
set("tab", "1") "1", quoted the text "1"
set("open", ["a", "b"]) ["a","b"] the list
set("on", true) true the choice true
  • JSON means: it starts with a double quote, a curly brace or a square bracket, or it's a number, or one of the words true, false and null.
  • A string that would read back as something else is quoted when it's written.

A pref can be declared, with its type, its choices and its default. A declared pref answers its default while nothing's kept, and refuses to keep a value it doesn't allow.

Declared prefs · from the pref store's tests · 9 lines 
const prefs = new PrefStore("PrefStore-test-default").declare("scheme", {
  oneOf: ["light", "dark", "auto"],
  default: "auto"
})
prefs.get("scheme")            // "auto":  the declared default;  with none, "light", the first choice
prefs.get("scheme", "dark")    // "dark":  a fallback passed in wins over both
prefs.set("scheme", "purple")  // throws TypeError:  `scheme` is one of light, dark, auto;  not `purple`

new PrefStore("t").declare("count", { type: "number" }).get("count")    // 0;  text "", a choice false
  • A kept value its declaration no longer allows (a choice the app dropped) reads as the default, logged.
  • Keys with a shared start act like a folder: keysUnder("layout/"), forgetUnder("layout/").
  • rename(oldKey, newKey) moves a value once, when a pref is renamed.

It NEVER throws when storage fails.

  • Blocked storage (a private window): it keeps values in memory for the visit, and says so on the console once.
  • A full one: it logs, and answers the default.
  • A TypeError means a caller's mistake: no key, a store name with a colon, a value its declaration doesn't allow.

The catch: it isn't in Spell UI's util barrel. In the core bundle it cost every page 1.9 kB, so the few Spell UI files that keep preferences import spell/util/persist/PrefStore by file.

Hand a store a place, and the same calls keep its values somewhere else. Two of the four places must be waited on: there, use load() and save(), which answer promises.

place lasts waited on for
"local" (the default), "session" per site, or until the tab closes no small values: a theme, a panel's width
"memory" until the page goes no servers, tests, and when the browser blocks storage
DatabasePlace.shared per site yes big values, files, file handles
ServerPlace.shared in the person's space yes anything that should follow a person to another browser
The browser's database, and the page server · 9 lines 
const files = new PrefStore("spell-static", { place: DatabasePlace.shared })
await files.save("@owen/solitaire/cards.png", blob)   // kept as the browser copies it:  a Blob comes back a Blob
await files.load("@owen/solitaire/cards.png")

const prefs = new PrefStore("spellEditor", { place: ServerPlace.shared })
await prefs.save("mode", "split")     // spell.spaces/@spell/owen@/__prefs/spellEditor.json5
await prefs.update<number>("visits", (visits) => visits + 1)   // read, change and save as ONE step

prefs.get("mode")   // throws TypeError:  ... must be waited on;  use `load()` or `loadKeysUnder()`
  • The browser's database is one IndexedDB database for the site, spell-prefs, with one table, each value under its store and key.
    • A file's Blob, a Date or a Map comes back as it went in, and so would a file handle.
    • A 10 MB string fits.
    • update() runs in one database transaction, so two tabs never read the same value.
    • No database, or one the browser refuses: memory for the visit, said once.
  • The page server keeps each store as a JSON5 file in the person's space, in its __prefs/ folder.
    • A store named like a project is a folder and a file: __prefs/@owen/solitaire.json5.
    • You can read the file, and a comment you write in it stays.
    • Values travel as JSON: plain data only, no Blob.
    • Offline, refused or an error: it logs, and a read answers the default.
  • A quick set() on a waited-on place saves a moment later; a failure is logged.

The server's side is four requests under /api/prefs, answered by the spaces on the page server (prefsRoutes):

request answers
GET /api/prefs/load?store=&key= { value }, no value for none
POST /api/prefs/save, { store, key, value } { value }; no value forgets the key
GET /api/prefs/keys?store=&under= { keys }
POST /api/prefs/forget, { store, under } { keys }, the keys left

Not yet: there's no sign-in, so every person on one page server is this machine's person, owen.

  • One function names the person, and sign-in replaces it.
  • A store name that would reach outside the person's __prefs/ answers 400.

UndoStack is an app's undo history: two stacks of steps, each step a title and the records of what it changed. Each record says how to undo and redo itself, so the stack knows nothing about what it puts back.

A transaction that waits · from the undo stack's tests · 13 lines 
const history = new UndoStack()
const dealt = history.transaction("Deal", async () => {
  for (const cards of [1, 2, 3]) {
    await Promise.resolve()
    change(history, pile, cards, "Move Card")   // records { undo, redo }
  }
})
history.transaction("Flip", () => change(history, pile, 9, "Flip"))   // begun while Deal waits:  joins it
await dealt
history.steps.map((step) => step.title)   // ["Deal"]
history.undo()                              // pile.cards is 0 again
history.redo()                              // instant:  nothing runs again
history.undoTitle                           // "Undo Deal"
  • A transaction is ONE step: open until its function returns, or until its promise settles, chains included.
    • Work nested in it, or begun while it waits, joins it: never a step of its own.
    • A throw still records what changed, and passes the error on. Nothing recorded: no step.
  • FOLDING: a step with the same title AND the same target as the newest joins it.
    • So typing "hello" into one field undoes to "" and redoes to "hello".
    • A step with no target never folds.
  • The stacks move before the records run, so whatever they set off already sees the new history. Nothing records while it undoes or redoes.
  • A new step empties the redo stack; limit drops the oldest; clear() forgets both.
  • What an Edit menu reads is live (spell cells), so a menu drawn from it redraws by itself: canUndo and undoTitle, and the same for redo.
  • Titles are English by default; titleFor words them whole in another language, Deshacer «Margen».

Spell's runtime gives each run an undo history on that stack. Only an action declared undoable is recorded: a plain property write is no step.

A card game's actions · from the core's undo tests · 22 lines 
class Card extends Thing {
  static {
    this.declareProp("faceUp", { type: "choice" })
    this.declareProp("picked", { type: "choice", undoable: false })   // never undone, e.g. a selection
  }
  turnOver(): void {
    this.faceUp = !this.faceUp
  }
  static { this.declareAction("turnOver", { undoneAs: "Turn Card" }) }
}

class Game extends App {
  async deal(count: number) { ... }   // waits between cards, moves each to the waste, turns it over
  hint() { ... }
  newGame() { ... }
  static {
    this.declareAction("deal", { undoneAs: "Deal" })
    this.declareAction("hint", { cantBeUndone: "keeps history" })      // left out;  earlier steps stay
    this.declareAction("newGame", { cantBeUndone: "clears history" })  // left out;  every step forgotten
  }
}

await game.deal(3);  game.undo()   // the stock holds all three again, in order, face down, owned by the stock
  • declareAction() goes in a static block after the method. An action says exactly one of undoneAs and cantBeUndone; neither or both throws.
  • An undoable action is ONE step however long it waits: the cards it turns over, and every action it calls, join it.
  • A step keeps the least it needs: each property's value before its first change and after its last, and each list's items before and after. A 3-card deal is six records.
  • At most 100 steps a run.
  • While an undoable action still runs, undo and redo do nothing: ⌘Z mid-deal is ignored, and the next one undoes the whole deal.
  • One history per run. A new run starts with none, and loading saved state (core.fromJSON(), a Loader) forgets it: the person's document changed.

Every app has what an Edit menu needs:

on the app what it does
undo(), redo() undo the newest step, redo the last one undone; false with none
canUndo, canRedo live: a menu item greys out by itself
undoTitle, redoTitle Undo Turn Card, or just Undo; in the program's language, e.g. Spanish's Deshacer Turn Card

⌘Z and ⇧⌘Z (Ctrl on other platforms) undo and redo while the app has the focus, or nothing does. They go through Spell UI's keyboard registry, so a modal open over the app keeps its own keys.

  • A text field in the app keeps its own ⌘Z: the key passes on to it.
  • With nothing to undo, the key passes on too.
  • A page without Spell UI has no undo keys; undo() still works from a button.

An unset Spell property used to read as nothing, whatever its type. Now it reads its declared default, else its first choice, else its type's.

a property that's read while unset, before now
a number nothing 0
a choice (yes / no) nothing false
text nothing ""
one of a list nothing its first value
a list a new list a new list
a thing nothing nothing
  • A declared default, or a starting value, wins.
  • The default is never stored, so saved JSON doesn't change.
  • Python's runtime reads the same, so every target draws the same thing. Prefs and properties share one rule, defaultFor().
  • A drawn thing's element still shows no attribute for a value nobody set, as HTML doesn't: <solitaire-card> doesn't grow direction="up". A read-only getter's value always shows.

What people see change: the Task List, Lista de tareas and Habit Tracker examples' Add button starts disabled. An unset draft is "" now, which is empty, so the button waits until something is typed.

A property declared remembered: true keeps its value from one run to the next, in the person's preferences.

A remembered theme · from the core's tests · 10 lines 
class Solitaire extends App {
  static { this.declareProp("theme", { oneOf: ["light", "dark"], remembered: true }) }
}

core.resetRuntime()
await core.remember("@owen/solitaire")   // what its last run kept, read now
new Solitaire().theme = "dark"           // kept at  @owen/solitaire:theme

core.resetRuntime()
await core.remember("@owen/solitaire")
new Solitaire().theme                    // "dark";  another project's id reads "light"
  • Read the first time it's asked for: what the last run set, else its starting value, else its typed default. Kept again every time it's set.
  • The keys are the project's id, then:
    • on the app, the property's name: @owen/solitaire:theme
    • on any other thing, the id the program chose and the name: @owen/solitaire:main.zoom
    • a thing whose id was made up (new each run) isn't remembered: a warning on the console, once, naming the fix, new Settings({ id: "main" })
  • Whoever runs the program says which project, with core.remember(projectId) before it loads. The editor and <spell-viewer> (a published page) both do.
  • Any place works, the page server's too: everything kept is read in one go before the program starts, so the program never waits for it.
  • Only text, numbers and yes / no are kept: a thing or a list isn't, said once. A remembered value the property no longer allows is passed over, said once.

Three ideas carry the rest: a store's name is the start of its keys, a place decides only where values live, and an undo step records what changed, not a snapshot of everything.

A store's name is the key's part before its first colon, so every store that moved over kept what people had saved. The site header's store, spell-site, keeps its scheme at spell-site:scheme: exactly the key the site's head script reads before the page draws.

where what it keeps now
the site header, on every docs page light or dark, and the per-tab edit mode (still 1) a pref store
Spell UI's docs site its theme, nav favourites, open topics, section folds, a viewer's saved theme pref stores, each imported by file
the editor its mode, tabs, panel sizes, the type explorer one store, spellEditor; its doubled old keys moved over once
the editor's static preview a visitor's edits to an example: whole files the browser's database, store spell-static, moved over once
the epic pages folds, drafts, filters, read marks, the Epics list's sort pref stores; four keys with no store's name renamed, moved once
Spell UI's nag (DismissalStore) that a nag was dismissed stays: its keys are the page author's, and it keeps cookies too
the head scripts, the live-reload client, the syntax colourer, the page checker light or dark before the page draws, the scroll position, keys set from a test stay raw: they run before any module, or can't import one

Old keys move with PrefStore.moveOldKey(): once, byte for byte, and a value already at the new key wins. The editor's spellEditor:spellEditor.mode became spellEditor:mode that way.

Code that writes localStorage.setItem() itself also has to guard it, prefix it and parse it; each of the old stores did all three its own way. Here the store asks, and a place answers.

  • Quick places answer at once: StoragePlace over the browser's storage, and MemoryStorage.
  • Waited-on ones (WaitedOnPlace: the database, the server) refuse a quick read with a message naming load(), and save a quick write later.
  • A test hands a store a StoragePlace over its own storage; a class that took a Storage for its tests still does.
  • The folder imports nothing from outside itself but util's reactive engine (for the undo stack's live titles), so Spell UI can use it.

Many undo libraries snapshot the whole state, or replay commands. This records only what an undoable action changed, as it changes it.

  • Every property write in Spell's runtime comes through ONE place, noteSetting(), and every list change through noteItems().
    • The run's history (UndoHistory) records them while an undoable action runs.
    • A while handler's put-back, and a program running in Python, hear of the same writes.
  • Each property is one record in its step, however often it changes: its first value and its last. Each list is one record: its items before the step and after it, the same things, not copies.
  • Undo and redo set them back through the setters, so what draws them redraws, a pile's cards know their pile again, and a page's mirror hears of it.
  • declareAction() wraps the method in UndoHistory.run(); with no program running, the method just runs.

The choices a reader would question, each with the option it beat.

  • In the browser by default; the app may move them to the server.
    • It works today, with no sign-in.
    • An app with signed-in people names a server place, and changes nothing else.
    • It beat server first.
  • Values are text unless they look like JSON.
    • Head scripts and people read the keys as they are: spell-site:scheme holds dark.
    • The words true, false and null read as JSON too, so a choice comes back a choice.
    • It beat a serializer that keeps dates, and a format option per store.
  • A store's name is the key's part before the first colon.
    • No saved setting is lost, and nothing needs moving.
    • It beat the old app store's name::key, which would have changed every key.
  • One folder in the kit's util, generic.
    • Spell UI may import it, as it may not import Spell's own corner of util.
    • It beat a kit folder of its own, with its own namespace and test project.
  • Out of Spell UI's util barrel.
    • Measured, it grew the core bundle from 38.12 kB to 39.98 kB: a page with one button went from 73.78 kB to 75.64 kB.
    • Only a few files keep preferences, so they import it by file.
  • The browser's database store is built now, and written here.
    • It holds whole files with no 5 MB ceiling, and file handles, for saving straight to disk later.
    • About 80 lines on the browser's own IndexedDB beat adding a library; its tests cover three bugs an earlier version of the idea had.
  • One database table, each value under its store and key.
    • A browser database adds a table only while it changes version.
    • So a table per store would mean a new version, and a wait on every other open tab, for each new store.
  • Four named routes, the store and key in the query or the body.
    • A store is often named like a project, @owen/solitaire.
    • Its slashes would tangle with a path per key.
  • Kept in the person's space, through spaces.
    • One file per store, readable, its comments kept.
    • Sign-in changes one function.
  • Only actions marked undoable record.
    • Nothing is recorded by surprise.
    • The cost: an app has no undo until each action that should undo is marked.
    • It beat every change recording itself, folded.
  • An undoable action is a transaction, waits included.
    • "Undo Deal" puts every card back.
    • It beat the runtime's old rule, which kept only what was set before the first wait: dealing 28 cards would have been 28 steps.
  • One history per app, cleared on a new run and when saved state loads.
    • That's what a person expects of ⌘Z in most apps.
    • The runtime has no notion of opening a document yet, so those two moments stand in for it.
    • It beat a history per document or view.
  • The undo stack is generic.
    • A step is records that undo and redo themselves.
    • Spell's runtime adds the recorder of property and list changes; spell-app may add its own.
  • A list keeps its items before and after, whole.
    • Putting one pile back moves its cards out of the others.
    • So by the time the next pile's record runs, a recorded splice's place in it would be wrong.
    • Whole lists end right in any order, for one array of references per changed list per step.
  • Options in words, not true or false.
    • An undoable action: undoneAs and its step's title.
    • One that can't be undone: cantBeUndone, "keeps history" or "clears history".
    • A property left out: undoable: false.
  • An action that can't be undone says whether it empties the history.
    • Emptying it means undo never puts back a state the world has moved past.
    • As Finder's Empty Trash can't be undone.
  • ⌘Z through Spell UI's keyboard registry, while the app has the focus or nothing does.
    • Clicking a card doesn't move the focus: with the app's element alone, ⌘Z would do nothing right after a move.
    • It beat a plain key listener on the app: one more key mechanism to replace later.
  • Undo waits out a running action.
    • Putting the step before it back mid-deal would tangle the two.
    • The deal would go on moving cards out of piles just put back under it.
  • declareAction() on the class, kept.
    • The elemental-spell epic, whose actions and menus will describe every command, asked for a plain runtime call instead.
    • It stays, as a thin wrapper over the run's history, which that epic can call when it takes actions over.
  • Build the runtime now, the words later.
    • The store and the stack don't depend on Spell's words, so they landed first.
    • It beat waiting for the elemental-spell epic to settle its words.
  • Every property defaults by its type, with a declared default to override.
    • One helper for prefs and properties, so they can't disagree.
  • The project's id names an app's keys.
    • Two people's Solitaires on one site never share preferences.
    • The runner sets it, with no compiler change.
    • It beat the app's name, which two projects can share: the very bug that once mixed two apps' preferences in one pool.
  • Only on the app, or a thing whose id the program chose.
    • A made-up id is new each run, so nothing kept under it would be found again.
  • A warning, not an error, for a thing with no chosen id.
    • Nothing knows at the declaration whether a thing will be given an id.
    • A throw at its first read would break a running app over a preference.
  • No spell words for any of it.
    • The compiler writes no undoable action, remembered property or declared default until the elemental-spell epic settles the words.
    • Until then, they're reached from hand-written programs and tests.
  • No hand test of ⌘Z or a remembered property in a running app, since no compiled program uses either yet.
    • Then: ⌘Z and ⇧⌘Z in Solitaire in the editor's runner, and a theme surviving a restart and a reload.
  • The public preview keeping a visitor's edit across a reload hasn't been checked in a browser: only the static files' tests have.
  • The VS Code runner remembers nothing.
    • Its panel gets fresh browser storage each time it opens, so it hands the run no project id.
    • Remembering through the page server's place would fix it.
  • An app drawn by its page's markup gets no ⌘Z: a <spell-viewer> with markup inside.
    • The keys are listened for when an app mounts its own drawing.
    • Its undo() still works from a button.
  • No sign-in: everyone on one page server is the same person, owen.
  • File handles are kept, but nothing uses one yet, e.g. the editor saving a project straight to a folder on disk.
  • A key a plain script reads raw, or its value's form, can never change without changing that script too.
  • Something else that changes things while an undoable action waits (a timer, a second click) joins that action's step: the browser can't tell whose change it was.
  • A change made outside any undoable action isn't recorded: undoing an older step can put its values back over it.
  • A recompile that keeps the game in progress is a new run, so its undo history starts empty.
  • A remembered value is the property's value like any other:
    • it's in the thing's saved JSON
    • a value given when the thing is made wins, every run: new Settings({ id: "main", zoom: 1 })
  • spell run and tests remember nothing: they never call core.remember().
  • With two apps on one page and nothing focused, ⌘Z goes to the app whose keys were registered last.
  • A page with no Spell UI has no undo keys; its app's undo() still works.
  • Typed defaults change what programs see: a new counter's count was nothing, and is 0 now. A program that checked for nothing behaves differently.
