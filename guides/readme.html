Open the kit's README.md and its index links 35 pages: a front page for each Spell repo but spell-brand, and beside it a page for each major folder. Epic readme wrote them all to one brief, and four scripts keep them true. Here's where each one lives, the brief, and the scripts.

  • Every repo but spell-brand has a front page, its README.md. Beside it sits a README-<folder>.md page for each major folder or topic.
  • The kit's front page is the way in: what Spell is, the six repos in one picture, setup from zero, and an index of all 35 pages.
  • They're written first for developers who know another framework (React, say), and second for coding agents.
  • Every page has the same shape:
    • a plain lead, then short sections of bullets
    • pictures: Mermaid diagrams in one Spell look, and five drawn hero pictures
    • the details folded away in expands, so the page reads whole with them closed
    • a "🌱 Coming" stub for each thing that's planned but not built
    • a See also list at the end
  • The pages describe the layout AFTER repo-split P13 and P14. Where that hasn't landed yet, a folded "Until repo-split ... lands" note gives today's spelling.
  • The ten old in-folder READMEs were folded into the new pages and deleted, and every link to them was repointed.
  • Four scripts keep the pages true: a README check, a Mermaid prettifier, and two generated tables (The tools).
  • Open the kit's README.md: its index links every page.
  • Changing a page: run yarn readme:check at the kit's root before you're done.

Every page sits at the root of its repo: the front page, then the pages beside it. The line counts are from the doc review, folded details included.

  • The pages about working on Spell as a whole (the command line, development, VS Code, agents) are the kit's, because the kit is the checkout everyone works in.
  • The server and the page-writing steps (the assembler) share one page, as they'll be one folder.
  • spell-brand has no pages, because it's being reworked; the kit's repos table gives it one line.

A dozen writers made pages that read as one set, because every page was written to one brief. Write a new page to the same rules.

  • First, developers who know another framework. Explain Spell by contrast with what they know, never from zero.
  • Second, coding agents. A README says what a thing IS and how to run it; the rules for working on it stay in the repo's AGENTS.md, which the page links.
  • Setup is written for a Node novice: every command complete, run from a named folder, with what it prints when it worked.
  • A plain lead: what the thing is, and for whom. Then a picture.
  • Each section is a short paragraph, then bullets; a table for three or more rows of one shape.
  • Details fold into GitHub's expand blocks, with a blank line after the summary line so Markdown renders inside. The page reads whole with every expand closed.
  • A front page gives a full orientation (300-500 lines with expands closed is fine). A secondary page goes deep on one thing.
  • Every page ends with See also: the pages beside it, the repo's front page, the kit's.
  • Guides in the content folder are never linked, because GitHub can't see them. Instead, a folded "More in the docs site" list names them by title and served path.
  • Diagrams are Mermaid blocks, drawn plain, with a one-line italic caption under each. yarn mermaid:pretty gives them the Spell look.
  • Five drawn hero pictures, beside their pages, each with its Mermaid source folded under it.
  • Screenshots only where the real thing says more: PNGs under 300 KB, taken headless, with alt text.
  • "People", never "users".
  • WWOD is written out as "What Would Owen Do?" where a page introduces it. The owner's name appears nowhere else, except in the sample address of your own projects group.
  • No old names. The checker knows the list: the old monorepo paths, the alias prefix, "Fomantic reborn" ...
  • A planned feature gets a "🌱 Coming" stub: what it will do and where it stands, never a date, and nothing shown as working that a reader can't run.
  • The layout is the one after repo-split P13 and P14: the command line in the kit, package names in every import. Today's spelling sits in one folded note per section.

The hard part came first, on the epic page: what every page covers, and where it lives. Then came the writing, a repo at a time.

  1. Map and outlines (P1): the map of every page, the writers' brief, and one outline per repo, all reviewed on the epic page before a page was written.
    • Five research reports gave every writer the same facts.
  2. The pages, one phase per repo (P2-P7), each run by a background agent, several at once: the kit's five, the four cross-cutting ones, then spell-parser, spell-ui, spell-epic and spell-app.
    • Every command quoted in a setup or "try it" section was run once, and its output pasted.
    • Each writer recorded its choices on the epic page: 36 judgement calls in all.
    • What only a person can check became a test for the owner.
  3. Cross-links and pictures (P8), one pass over all 35:
    • the README check and the Mermaid prettifier, built and run
    • the five hero pictures drawn
    • See also completed on every page, and the stale-name sweep
  4. Doc review (P10): the text pass over the pages, the epic page pruned, this guide.
  5. Post-split cleanup (P9) comes last, once repo-split P13 and P14 land: every command and path checked again, and the "Until repo-split" notes removed.

Drive-bys along the way: spell-app's three superseded example projects deleted, its yarn serve fixed, and every Spell UI docs page's "Report a bug" pointed at spell-ui's own repo.

Four scripts, two in the kit and one each in spell-ui and spell-app.

Run Where What it does
yarn readme:check the kit's root checks every page: links and headings, pictures and captions, expands, the "Until" notes' wording, stale names; exits 1 on any finding
yarn mermaid:pretty the kit's root gives every Mermaid block the Spell look, in place; safe to run again
yarn readme:components spell-ui writes README-components' tables from the docs site's data, and can retake the thumbnails
yarn examples:readme spell-app writes README-examples' table from each example's project file, with a screenshot of each
  • The README check is the only Markdown check, because the format check skips Markdown. README-toolchain says so.
  • The kit's two live in its tools/ folder, now one of the kit's checked folders: tested, linted and typed with the rest.
  • The two generated tables sit between marker comments, and each has a check mode that runs in its repo's tests.
Their options · 12 lines 
yarn readme:check                    # every page in the kit and its child repos
yarn readme:check README.md          # only those pages (paths from the kit's root)
yarn mermaid:pretty                  # every page the README check walks
yarn mermaid:pretty --check          # change nothing;  exit 1 if a block isn't styled

# in spell-app
yarn examples:readme                 # rewrite the examples table and retake the screenshots
  1. Write it as README-<folder>.md at its repo's root, to the rules above.
  2. Draw its pictures plain, then run yarn mermaid:pretty.
  3. Add it to the See also of the pages beside it, its repo's front page, and the kit's index.
  4. Run yarn readme:check: it finds the new page by its name.

The twelve decisions that shaped every page, one line each.

  • Pictures: Mermaid for every diagram, plus a few drawn hero pictures (Q1).
  • Which layout: the one after repo-split P13 and P14, so the pages don't need rewriting when it lands (Q2).
  • Guides: the pages stand alone and name the guides in a folded list, since GitHub can't see the content folder (Q3).
  • WWOD: written out as "What Would Owen Do?" where a page introduces it (Q4).
  • The old READMEs: folded into the new pages and deleted, so there's one place for each fact (Q5).
  • The cross-cutting pages live at the kit's root, the checkout everyone works in (Q6).
  • One server page covers the assembler too, since they'll be one folder (Q7).
  • The element framework's page is the kit's, since that's where the framework lives now (Q8).
  • The outlines were reviewed on the epic page, one section per repo, before any writing (Q9).
  • The stubs: every planned feature that's named again and again gets a "Coming" section (Q10).
  • spell-parser's front page opens with the AI direction, then what's built (Q11).
  • Shared editing is written in stages: a shared running program first, shared source editing after (Q12).
  • Some commands don't run yet: the pages describe the layout after repo-split P13 and P14.
    • Until those land, the folded notes give today's spelling.
    • P9 checks every command again once they have.
  • Setup from zero is untried. GitHub's spell repo, on main, is still the old top repo, so a fresh clone gets the old layout until the kit's branch is pushed.
  • Nobody has looked at the pictures on GitHub yet:
    • the Mermaid render check used a headless Mermaid, not GitHub's or VS Code's
    • the hand checks for light and dark mode are open on the epic page
  • The kit's links into the child repos work in a checkout, not on GitHub, where the kit has no child repo folders.
  • Two guides are stale beyond their links: the command-line guide (old names like @workspace) and the Spell UI pages guide (old monorepo paths).
  • A few pages show what isn't built or published yet, and each says so in place:
    • spell lsp, in spell-app's README-lsp
    • Spell UI's npm recipes and the thirty-second demo, until the package is published
    • the Svelte recipe, written but not run
  • Screenshots of VS Code (its window, and spell-epic's side bar) are drawn as diagrams, because the headless tools can't reach VS Code.
  • spell app create fails in a fresh checkout until the person's space folder exists, so README-spaces makes it first.
  • The Spell Epic extension now ships without a README, so VS Code shows it no details page.
