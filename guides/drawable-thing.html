Views

One line of spell, a card is a view, and every card in Solitaire draws as its own <solitaire-card>. Edit how a card looks, and all 52 stay where they were, drawn the new way.

That line makes the card type a real web component: a tag like Spell UI's own, drawn on the same Solid engine. A React component is a function the page never holds; here each card is an element the page holds, with its own styles and its own error net, and a plain HTML page can use the tag too.

A view is a spell template that draws in an element of its own. Everything else about the template stays as it was: its properties, its methods, its to draw.

Four built-in templates say a template is drawn as an element: a view, a viewable list, a page and a two sided view.

the built-in templates, and what each compiles to · 5 lines 
a card is a view                     -- export class Card extends View
a card is a two sided view           -- export class Card extends TwoSidedView
high scores is a page                -- export class HighScores extends Page
a pile is a viewable list of cards   -- export class Pile extends ViewableList { static instanceType = Card }
a pile is a viewable list            -- export class Pile extends ViewableList
  • They compile to two classes in spell's runtime, which every compiled program imports.
    • View, a kind of thing
    • ViewableList, a kind of list
  • A template built on a view is a view too: a tableau that is a pile gets its own tag.
  • A type's name may be several words, with a short name after aka: a bank account aka account is a thing.
  • Only declared names count, the longest first: "a big card" stays a card unless someone declared a big card.

A view's drawing is the markup in its to draw it: each markup line is drawn, in order.

a drawing, with a choice and a loop · 8 lines 
- to draw it:
	<ui-header>{its title}</ui-header>
	if it is empty
		<ui-text>No cards</ui-text>
	otherwise
		for each card in its cards
			<ui-segment>{draw the card}</ui-segment>
  • No return: spell lines around the markup choose what's drawn. return <...> still works.
  • Several drawn lines become one list; a for each draws one per item.
  • A line that draws nothing, written after a drawn one, runs before the drawing.

A view may name the parts it draws, each with a drawing of its own.

a view with two parts · 6 lines 
a "card" is a view where:
	- it has parts "front" and "back"
	- to draw its front:
		<ui-text>{its rank} {its symbol}</ui-text>
	- to draw its back:
		<ui-image src="card-back.svg" />
  • to draw its front compiles to drawFront(); draw its front places it.
  • A part's markup carries part="front", so a page styles it with ::part(front).

A two sided view is a view with a front and a back that shows one at a time: a playing card, a tile.

  • It's written once, in spell (TwoSidedView.spell), and compiled into the runtime's TwoSidedView.
  • It gives each of its things a direction (down or up, starting face down), the words it is face up and turn it over, and a drawing that shows the back when face down, the front otherwise.
  • A template made from it only draws its parts: a card is a two sided view with to draw its front and to draw its back compiles to a class holding just those two.
  • In Spanish it's vista reversible, with voltear and está boca arriba.

A view can be written in a .spellx file, spell's tag-shaped form, and compiles to the same JavaScript.

a card in spellx · 7 lines 
<spell-view "playing card" aka="card" template="two sided view">
	<property "suit" one-of="clubs, diamonds, hearts, spades" alias="is a (suit)" />
	<draw "front">
		<text>{its rank} {its symbol}</>
	</draw>
	<draw "back"><image src="card-back.svg" /></>
</spell-view>
  • Component names are bare in spellx: <text> is Spell UI's ui-text.
  • The spellx guide has the rest.

The tag is the project's name made singular, then the type's name, in dashed lowercase words.

project type tag
Solitaire card <solitaire-card>
games bank account <game-bank-account>
Drawable Solitaire stock pile <solitaire-stock-pile>
Todos - Form Based task <todos-form-based-task>
  • The word "drawable" is left out of the project's name: Drawable Solitaire's tableau is <solitaire-tableau>.
    • A type's own name keeps it: a DrawableCard in project Games is <game-drawable-card>.
    • A project named only "Drawable" starts the tag with spell-.
  • A project name with no letters starts the tag with spell-.
  • The names are English only, for now.
  • One tag per type per page: two <spell-viewer>s of the same project share it, drawn by the runtime that defined it last.

A view's look is a <css> block in its outline, the lines indented under it.

Solitaire · Card.spell, shortened · 8 lines 
a card is a view:
	<css>
		:host { display: block; position: relative; }
		.card.red { color: crimson; }
		.card.face-down { background: repeating-linear-gradient(45deg, #3a6, #3a6 4px, #285 4px, #285 8px); }
	</css>
cards have a suit as one of clubs, diamonds, hearts or spades
a card has a direction as either up or down
  • The type's line needs its colon, or the indented lines aren't its outline, and the block is an error that says where it goes.
  • The block is read exactly as written, the way a browser reads <style>: its braces and angle brackets are never taken for spell.
  • VS Code and the spell editor colour it as CSS, and give CSS completion, hover and errors inside it.
  • The element adopts the page's theme sheets first, as Spell UI's own elements do, then the type's sheet. A super-type's sheet comes before its sub-type's.
  • Only a view may have one. Page CSS doesn't reach inside the element: style the template in its block, or its tag from outside.

  • The tag hands back the sheet as text, with the indent its lines share taken off.
  • CSS's own escapes, like "\201C", stay as written.
  • Spell's VS Code extension colours the inside of a css template in javascript and TypeScript files.
  • Core only names the tag: the page running the program defines it, because core may not import Solid or Spell UI.
  • The element class is a Spell UI component, SpellElement, on the page's own Solid and Spell UI.
  • A card that fails to draw shows its own "can't draw", and the other cards keep drawing.
  • A change to one card redraws that card only.
  • A thing with no element, or a page that defines no elements, draws as before.
  • A tag written by hand finds its thing in other ways: Its thing has all three.

Compiled TypeScript writes, after each view, its element class: a short subclass of the runtime's own element, SpellElement. It reads like a Spell UI element written by hand.

the DrawableSolitaire test project, compiled to TypeScript · the card's element, shortened · 25 lines 
import { E, SpellElement } from "@spell/elements"

export class Card extends View {
  // ... unchanged:  its tag, its css, its properties and methods ...
}

export class CardElement extends SpellElement<Card> {
  @E.proto static vocabulary = SpellElement.vocabularyFor("test-project-card", "card", [
    { name: "rank", kind: "string", description: "Its rank." },
    { name: "suit", kind: "string", description: "Its suit." },
    { name: "direction", kind: "string", description: "Its direction." }
  ])
  @E.protoMerged static elementSetup = {
    styleSheets: { "test-project-card": Card.css }
  } satisfies Partial<E.ElementSetup>

  turnOver() {
    return this.currentThing?.turnOver()
  }
  // ... one method per card method ...
}
core.useElement(Card, CardElement)

// at the end of the file:  each drawable type's tag, declared for the JSX
"test-project-card": HTMLAttributes<HTMLElement> & { [attribute: string]: unknown }
  • The class holds only what's the type's own: its attributes, its sheet, and one method per method of the type, calling the thing's.
    • What every view's element does, like drawing its thing, stays in SpellElement.
    • The page adds the rest as it builds the tag, as for javascript: super-types' properties, and the list holding it (a card's pile).
    • A type with no <css> of its own writes no sheet line.
  • It never defines the tag itself: core.useElement(Card, CardElement) hands the class to the page, which builds the tag on it, once.
  • So both output languages draw the same element, behaviour for behaviour.
  • A method the class has itself runs on the element. A type's method named like one of the element's own, such as send or render, is left out: the tag still calls the thing's.
  • Core can't import Spell UI, so the class imports its base from a module name of its own, @spell/elements, resolved in three places:
    • the type check: app's real element, from source
    • a page: the runtime the program runs on
    • a headless run (spell run, the core contract): a stand-in that makes no element
  • Each view's tag is declared for the JSX, so a tag written by hand in a drawing type-checks: every fixture's TypeScript passes tsc with no errors.
  • Where: the TypeScript writer's elementClassFor(), and the page's SpellElement.defineFor().

The element shows its type on the outside: the type's properties are its attributes and properties, the type's methods its methods.

It draws one thing of the program, its thing, and its id is that thing's name: id="T1".

A property holding another thing shows as a reference, pile="Tableau#T1", which spell can write too: tableau T1.

  • Each declared property is an attribute, kebab-cased, and an element property, camelCased.
    • A property face_up is the attribute face-up and the property faceUp.
  • Each method is an element method, camelCased: turn_over is card.turnOver(), calling the thing's.
    • Not draw(), and not a method with values in its name, like "is a (suit)".
  • The attribute's kind comes from the property's declared type.
declared as attribute example
text, character, date, or no type text suit="spades"
number, integer number score="12"
choice (yes or no) there or not face-up
another thing: a card, a pile its reference pile="Tableau#T1"
a list none: an element property only set from a script
  • A legal value written as text becomes the value itself: rank="2" sets the number 2, since 2 is one of a card's ranks.
  • Only DECLARED properties: a worked-out value, like a card's colour, isn't on the element.
    • But the list holding it is: a card belongs to one pile shows as the card's pile (A property holding a thing).
  • Names the page or Spell UI already mean something by are left out, like title and hidden: a script sets those on the thing.

A change on either side shows on the other, so the browser's inspector always tells the truth.

  • Turning the card over, from the program or with ace.turnOver(), changes the tag's direction="up" to "down".
  • Setting the attribute, or the element's property, changes the thing at once, and the card redraws: ace.setAttribute("rank", "2").
  • Reading ace.direction asks the thing, so it's never stale, and a number reads back as the number.
  • Removing an attribute makes the thing's property nothing.
  • No loops: a value the other side already has is never written, and an element never hears its own attribute writes.
  • It holds for every view's element: a card the program draws shows its rank, suit, direction and pile as attributes too.

An element's thing is the spell thing it shows. Every view's element draws ONE thing of the program.

  • A <solitaire-card> draws one card object: the element is that card's view.
  • It draws the card's own to draw inside itself, and keeps its attributes and the card's properties the same, both ways (above).

The element finds its thing in one of three ways. The first one that applies wins.

way how example
1. The program draws it Spell draws a card, or a pile draws its cards: the page makes the tag and hands it the card itself, in its thing property draw the card
2. A tag names it by its id On any page, the id is the part of a reference after its #, and the tag says the type <solitaire-tableau id="T1">
3. A tag with no id In a layout: the program's one thing of the tag's type. On a plain page: a new thing of its type, made from its attributes <solitaire-stock-pile>,
<solitaire-card rank="ace">

A tag's id reads as a reference does:

  • <solitaire-tableau id="T1"> is Tableau#T1, the tableau named T1.
  • <solitaire-pile id="discards"> is Pile#discards: a sub-type's thing too, here the discard pile.
  • Digits are a place: <solitaire-tableau id="1"> is the first tableau made.
  • The id is watched: a page changing it makes the tag draw the thing the new id names.
  • A tag with an id never makes a thing of its own. Until the program has the thing, it shows a stand-in, ⚠ no Tableau named "T9", and draws the thing as soon as the program makes it.
    • So a tag written by hand that should make its own thing has no id: find it by a class instead.
  • In a layout, a tag with no id whose type has no thing, or more than one, asks for an id.
  • A thing="..." attribute written in markup is no longer read: the tag acts as one with no id.
  • The handed thing always wins: in way 1, the element's id is its thing's name (Its id), and it's never looked up.
  • Where: SpellElement.currentThing.

An element the program draws takes its thing's name as its id, so the browser's inspector says which thing it draws.

a tableau holding both decks' queen of spades, as the inspector shows it, shortened · 4 lines 
<solitaire-tableau id="T1">
  <solitaire-card id="queen-of-spades" rank="queen" suit="spades" pile="Tableau#T1"></solitaire-card>
  <solitaire-card id="queen-of-spades-2" rank="queen" suit="spades" pile="Tableau#T1"></solitaire-card>
</solitaire-tableau>
  • Two things of one name, as in a game with two decks, are numbered:
    • the first made is queen-of-spades, the second queen-of-spades-2
    • a third ends in -3, and so on
    • Counted per program, in the order it made its things, among its views of every template.
    • Each <spell-viewer> counts its own program's things.
  • Stable: a thing keeps its id while it keeps its name.
    • A card moved to another pile is a new element there, with the same id.
    • A thing thrown away earlier doesn't renumber the ones after it.
  • It follows the name: after card.rank = "king", the queen of spades' element is king-of-spades, numbered afresh.
  • A space in a name is a dash: discard pile is discard-pile.
  • A thing with no name gets no id. An id the page wrote on the element itself is kept.
  • A layout's spell doesn't take a drawn element's id as a name: only tags written by hand are, like T1.
  • Where: core.elementIdFor(), written by SpellElement.nameAfterHandedThing().

A reference names one thing of the running program in text: its type, #, then its name or its place. It reads like CSS's tag#id.

references, and the thing each finds · 4 lines 
Tableau#T1    -- the tableau named T1
Tableau#1     -- the first tableau the program made, counting from 1
Pile#T1       -- the tableau named T1 too:  a tableau is a pile
Game#game     -- a thing with no name, by the top-level name the program keeps it under
  • The type is the class's name, as the program declares it: Tableau, never tableau.
  • A place is the order the program made the things in, not the order of their elements on the page (J42).
    • So moving elements on the page never renumbers anything.
    • A thing with no element still has a place.
  • A name finds a sub-type's thing too, but a place counts only things of that type exactly: Pile#2 isn't yet the second pile of any kind.
  • Digits are always a place: a thing named "3" can't be found by its name.
  • Two things with the same name: the first one made wins.
  • A thing with no name, or a name an earlier thing of its type has, is written as its place: Hand#2.
  • A thing that isn't the program's, like a scratch list, has no reference.
  • A tag's id is the part after the hash, its tag saying the type: <solitaire-tableau id="T1"> draws Tableau#T1 (Its thing).
  • In code: core.thingForReference("Tableau#T1") finds a thing, and core.referenceFor(tableau) writes the reference that finds it again.

A property holding a thing shows on the element as the thing's reference, and follows it as it changes.

a tableau and one of its cards, as the inspector shows them, shortened · 3 lines 
<solitaire-tableau id="T1">
  <solitaire-card rank="king" suit="spades" direction="up" pile="Tableau#T1"></solitaire-card>
</solitaire-tableau>
  • Every Solitaire card shows the pile holding it. A card played from the stock turns to pile="DiscardPile#discards".
  • A card's pile isn't declared: it's the list holding it, from a card belongs to one pile.
  • Setting it moves the card, as move the card to ... does: the piles' rules decide (J45).
    • From a script: card.setAttribute("pile", "Tableau#T1").
    • Or with the thing itself: card.pile = tableau.
    • A move the rules refuse leaves the card, and the attribute shows its pile again.
    • A reference that finds nothing (yet) changes nothing, and the attribute stays as written.
    • Removing the attribute leaves the card where it is.
  • A property declared as a thing, like a chip has a home as a stack, is set to the thing the reference finds.
  • Reading card.pile on the element gives the reference's text, "Tableau#T1".
  • A list of things has no attribute: it's set from a script.
  • A tag names the thing it draws by the part after the hash, as its id: <solitaire-pile id="discards"> is Pile#discards (Its thing).

Spell names one thing by its name or its place, as a reference does: tableau T1 is the tableau named T1.

the ThingReferences test project, shortened, and what each line compiles to · 7 lines 
set t1 to a new tableau with name = "T1"
get a new foundation with name = "hearts"

print the name of tableau T1          -- core.thingNamed(Tableau, "T1")?.name
print the name of foundation "hearts"
print the name of pile T1             -- a tableau is a pile
print the name of the last tableau    -- core.thingAtPlace(Tableau, -1)?.name
  • By name: tableau T1, the reference Tableau#T1.
    • the count of tableau T1 reads its count.
    • pile T1 finds a tableau too, since a tableau is a pile.
    • A name written bare starts with a capital letter; any other name goes in quotes: foundation "hearts".
  • By place: the first tableau, the reference Tableau#1.
    • Counted in the order the program made them: the last tableau is the last one made.
    • Every ordinal word spell has works: second to tenth, penultimate, last.
    • Only tableaus count: the first pile finds no tableau.
    • New meaning: the first card, with no "of" after it, was an error, and is now the first card made. the first card of the deck is still the deck's.
  • One the program hasn't made is nothing, not an error, and reading off it gives nothing too: both writers read off it with ?..
  • The words work in a page's layout too: {the count of tile T1} follows the tile live.
  • Two things with one name: where spell names one, and the project gives two things that name in so many words, the compiler warns.
    • The warning: More than one tableau is named "T1": this finds the first one made.
    • Counted: with name = "T1", as a thing is made.
    • Not counted: a name worked out as the program runs, like name = ("T" + the number), or a later rename.
    • Two things with one name that nothing names: no warning.
  • Where: spell's rules named_thing and thing_at_place.

    • So {the number of cards in T1} finds the tableau whose id is T1.
    • Only tags written by hand are names: a card the program drew, id="queen-of-hearts", isn't one.
    • Spell's own words find the program's tableau, tag or not: {the count of tableau T1} (Spell's words for one thing).
  • The layout's spell is compiled in the page, which loads spell's parser only for a layout with spell in it.

Any element in a layout handles events: a Spell UI tag, a plain one, or a view's.

  • As an attribute, in either spelling: on-click="{auto-play}", the browser's event name, or when-clicked="{...}", spell's.
  • As a <spell> block inside the element: when clicked: bump the score on one line, or the statements indented under it.
  • "on" works as well as "when": on drag: is when dragged:.
  • An event may be several words, joined with dashes before it's looked up: "when double clicked" is "when double-clicked".
  • Past-tense words map to the browser's events: clicked, double clicked, right clicked, hovered, unhovered, focused, blurred, changed, typed, submitted, dragged, dropped.
    • Any other word is the browser's own event name: on keydown:.
  • On a view's tag, or a plain tag inside one, the handler's "it" is that tag's thing.
  • A re-run takes back every handler the layout added, so none is left listening.
  • A <markdown> block draws formatted text, its holes live (Markdown blocks).
  • The browser reads the layout first, so the block's text is used: write a less-than sign as &lt;.
  • A child written in="header" lands in a frame's named place, as in a drawing.

A <markdown> block is formatted text in a spell file, read exactly as written, as a CSS block is.

the Klondike test project · a description, and a rules panel · 11 lines 
a game is an app:
	<markdown>
		A game of **Klondike**:  its piles, and its score.
	</markdown>

		<div className="rules">
			<markdown>
				## How to play
				Build each tableau **down**, alternating colours, and each foundation *up* from its ace.
				Score:  **{the score of the game}**
			</markdown>
		</div>
  • In a drawing, Spell UI's <ui-markdown> draws it: the compiled program holds the markdown as text.
  • A hole shows a live value, and the markdown is drawn again when one changes.
  • Outside code, a {...} is always a hole; one that doesn't read is a parse error. Code keeps its braces, and \{ is a real brace.
  • In a type's outline, it's the type's description: hover and the Type Explorer show it when the type has no comment docstring. It compiles to the class's static description.
  • In a <spell-viewer> layout, it's drawn the same way, its holes live.
  • The indent its lines share comes off, and VS Code and the spell editor colour it as markdown.

An edit in the editor keeps each tag defined, draws with the new program, and keeps the program's things, without running the program's start again. In Solitaire, an edit to a card's CSS keeps the game in progress, drawn in the new colour.

  • A page can't define a tag twice, so each view's tag stays defined.
  • The new run's class is recorded behind it, and the element draws with it from then on.
  • The type's CSS is replaced in every element of the tag already on the page, without drawing them again, through Spell UI's own style sheet replacement.
  • Each old thing becomes ONE new thing: a card held by the deck and a pile stays one card.
  • The console says what was kept: Kept allPiles, deck, ... from the last run: Restart starts afresh.
  • It works for any program: a counter keeps its count across an edit.
  • A run that throws mid-edit doesn't lose the game: the next good recompile carries the last good run over.
across the edit what happens
a property added the new thing's own starting value
a property removed, or now only worked out dropped
a property whose type changed, or a type renamed or gone the whole program starts afresh, as Restart does, and the console says why (J62)

A program's START is its top-level test calls and the line starting its app (Q26). An edit that keeps the program's things skips them, so the tests don't print again and the game isn't dealt again.

Solitaire's start, compiled · 2 lines 
if (!core.isCarryingOver) testCardSetup()   // test card setup
if (!core.isCarryingOver) game.start()      // start the game
  • The compiler marks each such line, at a file's top level only (J59, J60).
    • A test call is a call of a method defined to test ...: the tests spell test finds.
    • The same call inside a method, or inside a top-level if, isn't marked.
  • Every other top-level line still runs on an edit, prints included (J63).
    • So a pause still never ends while the program loads: a top-level deal stops at its first move.
    • The carried-over game then replaces what it made.
  • A first run, Restart, spell run and the core contract run the whole program.

The file an edit changed decides whether the game is kept (Q27):

the edit what happens
a type's file, e.g. Card.spell, or the styles the things carry over, the start skipped
the file that starts the app, e.g. Solitaire.spell afresh, as Restart does, and the console says why
a project of one file afresh only when the start's own lines change
a file added or removed afresh
a program that starts no app never afresh this way
  • The console line: Started afresh: the program's start changed, in the file that starts its app.
  • Which file changed is read off the compiled javascript, file by file, in every runner (J61).
  • A thing that can't come over starts the whole program afresh too, saying why (J62): one thing started afresh by itself would miss what the start does to it.
  • Restart starts afresh, on purpose: a new deal.
  • That's <spell-viewer>'s Restart and its restart(), the editor's Restart button, and VS Code's Restart.
  • Running another program starts afresh too.
  • An edit starts afresh by itself when it changed the file that starts the app, or when a thing can't come over (The start runs once).

Each output language says, in one place, how it writes each kind of name: its naming map. So a bank account is a thing compiles to class BankAccount.

  • The kinds of name: types, methods, variables, properties and constants, or one case for all.
    • javascript and TypeScript: types in PascalCase, everything else in camelCase.
    • Python (epic python-target): types in PascalCase, constants in SCREAMING_SNAKE_CASE, everything else in snake_case.
  • A type's name written as text in the compiled code, like a type check's, follows the map too: spell marks it with a tree node of its own, which every writer renames.
  • A view's tag doesn't change with the map: a bank account is <game-bank-account> either way.

The decisions behind the design, each settled in the epic page.

  • view and viewable list (once "drawable thing" and "drawable list") are built-in templates, not an adjective.
  • So the line needs no special rule, only multi-word types.
  • Adjectives in general ("sortable", "saved") are a future epic, mixins.
  • By the packages' one-way rule: Spell UI may not import spell, and core may not import Solid or Spell UI.
  • So core only names the tag, through a hook, and the app, which runs the program on a page, defines it.
  • The element gets its styles exactly as Spell UI's own do: "These elements are just like Spell UI's" (Owen).
  • The compiled TypeScript should read like a Spell UI element Owen would write by hand (Q6).
  • Each class builds on the runtime's own element, so everything an element does stays in one class, and both output languages draw the very same element (J41, option B).
    • A class of its own on Spell UI's element core would repeat the error net, layouts and outside.
  • Classes are flat: each lists only its own type's attributes and methods, and the page adds the rest (J52).
    • The list holding a thing, like a card's pile, is known only as the program runs.
    • So a class that wrote everything out would still miss it, and element classes inheriting as the types do would stack their sheets under two names.
  • Each tag is declared for the JSX taking any attribute, as Spell UI's tags are: a tag also takes attributes its type doesn't declare, like id and the list holding it (J56).
  • The project's or library's name, made singular, then the type's: <game-card>.
  • No "drawable" in it: Owen asked for <solitaire-tableau id="T1">, "no <drawable- prefix".
    • The word comes out of the project's name only, so a type named for it keeps its own word (J44).
  • The author naming the tag by hand is left for another epic.
  • One tag per type per page, since a page can't define a tag twice.
  • One place to read what a type is and how it looks: its outline.
  • Read as raw text, as HTML reads a style tag, so CSS is never taken for spell.
  • Compiled as a css-tagged template, as Lit writes it, so editors colour it (Owen, reviewing the first build). The tag hands back plain text, not a style sheet object.
  • First built one way, element to thing; Owen: "The dom and the component need to agree."
  • Reading an element's property asks the thing straight through, over the element's own copy, which would be stale for a moment after a change.
  • Owen asked for them, on a property holding a thing (J23): "maybe we could have a scheme like Tableau#T1?"
    • "Might be interesting to reflect it that way into the DOM as well."
    • So such a property gets an attribute after all.
  • A place is the order the program made things in, not page order (J42):
    • an element finds its thing BY the reference, so counting elements would go round in a circle
    • a thing with no element still has a place
    • Owen: "a) now, maybe b later": page order is a todo to think about
  • Digits are always a place, so one text has one meaning (J47).
  • Setting a card's pile moves it, so the piles' rules still decide what may go where (J45).
  • Lists stay properties: a tableau of 13 cards would be an attribute of 13 references, rewritten on every move (J46).
  • A tag's id IS its thing's reference (J43). Owen: "Seems simpler to not have the 'thing attribute' but use ID instead ... Allowing this to drift by assigning a 'thing' explicitly seems likely to have problems."
  • An id names its thing on any page, not only in a layout (J57):
    • so a plain page can still show one of a hidden app's things
    • an id that finds nothing never makes its own thing: tags mount before the program makes its things, so each would take the program's places, then switch things once the program's appeared
  • An element the program draws takes its thing's name as its id, so the inspector says which thing it draws (J58).
    • The id isn't one of Spell UI's attributes, so writing it isn't heard as the page changing the element, and the handed thing always wins over a lookup.
    • A second thing of a name is counted per program, in the order it made things: counted per page, a card moved to another pile, a new element there, would take the next number, and ids would drift as the game plays.
    • Owen, on two decks in a game: "Maybe queen-of-spades-2?"
  • Owen: "the <property> of tableau T1 is a reference that maps to Tableau#T1. Similarly, 'the first tableau' maps to Tableau#1."
  • A bare name starts with a capital letter, or goes in quotes (J49):
    • spell reads words for many things: turn card over mustn't read as the card "over"
    • spell's own words are lowercase, so a capital can't be mistaken for one
  • A place means what Tableau#1 means: a program has no page, and what it draws can change, but the order it made things in can't (J48).
  • A missing thing is nothing, not an error, so a layout's hole shows nothing until the program makes the thing (J51).
  • The warning is careful, as Owen asked: "need to be careful, this could get annoying very quickly" (J50).
  • A tag finds its thing by its id, or its type; the markup replaces the app's own drawing.
  • Holes and actions may hold any spell, since spell's own drawings already take any statement.
  • The layout's spell is compiled in the page, against the running program.
  • A hole is spell exactly, as everywhere else: an earlier retry with "the" in front was dropped (Owen).
  • Both attribute spellings, on- and when-, since each reads well to someone.
  • in for a named place, written out as the web's slot, in drawings and layouts alike.
  • Allowed in a drawing, a type's outline and a layout: every place.
  • Holes live, as a layout's text.
  • Drawn by Spell UI's markdown element in the page: no markdown parser in the compiler.
  • First, a re-run started afresh; Owen asked for the game to survive an edit, as a phase of its own.
  • First built with no compiler change: the program ran from the top, stopped at its first pause (J36). Its tests printed again on each edit.
  • Then, at Owen's ask, the compiler marks the start, so an edit skips it. Owen picked which lines count: "just tests and start the game" (Q26).
  • Owen: "if a type file (card/etc) changes, just reload the objects. If the app-file itself changes, re-run again from the top" (Q27).
  • A thing that can't come over starts the whole program afresh, not just the thing holding it, so the game is never left half-dealt (J62).
  • Things are copied object to object, not through saved JSON, which keeps no identity: so one card stays one card.
  • Restart is the way to start afresh on purpose.
  • Owen: "BankAccount. this should be settable in output language, as should all other term transformation".
  • A type's name in text is a tree node of its own, so a new place that writes one can't be missed by a writer.

What doesn't work yet, or works with a catch. Each links its item in the epic page.

  • No page runs TypeScript output yet, so the element classes the writer emits have never drawn on a page.
    • The browser tests use classes shaped like the writer's, and the runner's test a javascript program.
    • The real output runs only headless, where the stand-in makes no element.
  • A hand-written element class that uses more of Spell UI as it runs would type-check, then fail in a page (J54).
    • The runtime hands compiled code only two of Spell UI's decorators: exporting the whole of it put a second copy of two Spell UI files in the runtime bundle.
  • Element classes are flat: TableauElement's class doesn't show a pile's name, though its tag has it (J52).
  • A misspelt attribute on a view's tag isn't caught by the type check, as for Spell UI's tags (J56).
  • Compiled TypeScript draws a child view inline, with its own draw(), not as its element.
  • Every top-level line but the tests and the app's start still runs on an edit: a top-level print prints again, and a top-level alert would show again (J63).
  • Which file changed is read off the compiled javascript (J61).
    • A method one file declares on another file's type counts as that type's file: an edit to Solitaire's to play a card keeps the game.
    • An edit to a card's file that changes how Solitaire's code is written starts afresh.
  • A Python program never carries things over: its start's lines are written bare, and thing references and element classes aren't in Python's runtime yet (J64, J66).
  • A plain top-level variable, a number or a text, starts again from the new start. Carried things show under no heading in the Thing Explorer (T7).
  • A tag's attributes and methods are fixed the first time it's defined: one an edit adds needs a reload.
  • Page CSS doesn't reach inside a view's element: style it in its own block.
  • A card moved to another pile is a new element there, drawing the same card with the same id: code shouldn't hold a card's element across a move.
  • A frame without <children/> shows no items, with no warning.
  • A card written by hand inside a pile written by hand shows there, but isn't in the pile's list: a script adds cards to its thing.
  • A place counts only things of one type exactly: Pile#2 and the second pile don't count a sub-type's things (T10).
  • A list of things has no attribute, only an element property (T13).
  • A place is never the order of elements on the page (T14).
  • A reference or an id written by name finds its thing only while it keeps that name.
    • A card's name follows its rank and suit, so <solitaire-card id="queen-of-spades">, written by hand, loses the card when its rank changes.
    • An element the program draws is never looked up by its id, so it keeps its card.
  • Two <spell-viewer>s running the same game on one page each number their own things, so ids can repeat on the page (J58).
  • A tag written by hand can't both have an id and make its own thing: an id always names the program's thing (J57).
  • A thing="..." attribute left in older markup is silently ignored: the tag draws as one with no id.
  • The duplicate-name warning sees only names given in so many words as a thing is made, not ones worked out as the program runs.
  • Quote an attribute's spell when a word repeats: unquoted, the browser keeps only the first of two attributes with the same name.
  • An HTML formatter flattens a <spell> block: put a prettier-ignore comment above its element.
  • A layout knows only its own project's types and functions, not those of a library it imports.
  • Inside a markdown hole, editors give no spell hover or colouring, and an error underlines the whole block (C25).
  • In the spell editor, a CSS comment over several lines colours only its first line.
  • Spell UI's spell code blocks don't colour a CSS block as CSS.
  • A type's outline needs its colon, or a CSS or markdown block under it is an error.
  • A short name in a nested scope can hide a type of that name further out.
  • A language naming types in snake_case gives a type and its variable the same name (I6).
