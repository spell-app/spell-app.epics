Drawable Things

In spell, a card is a drawable thing makes the card type a real web component: a tag like Spell UI's own, drawn on the same Solid engine. Each card draws in its own element, with its own styles and its own error net, and a plain HTML page can use the tag too.

Plan doc: epic drawable-thing Written for: a spell author making a type its own element, or a developer changing how spell's elements are drawn Status: part 1 (P1-P9, P11) merged into main on 2026-10-11; part 2 (P10's first half, P12-P19) on the branch Branch drawable-thing Checked on: branch drawable-thing, 2026-10-11, against the code, the examples and the plan doc's decisions (see Sources)
  • One line makes a type its own element: a card is a drawable thing in a project called Solitaire draws as <solitaire-card>.
  • Spell has two built-in types for it: a drawable thing, and a drawable list, such as a pile of cards.
  • The type's look is a <css> block in its outline.
  • The element's attributes, properties and methods are the type's, and the tag and its thing always agree.
  • A drawable list draws its frame, and shows its items where the frame says <children/>.
  • One thing can be named in text, as a reference: Tableau#T1 by its name, Tableau#1 by its place. A card's element shows the pile holding it that way, pile="Tableau#T1".
  • Spell has words for it too: tableau T1, the first tableau (Thing references).
  • A <spell-app> can be laid out in plain HTML, with spell inside the markup: live holes, event handlers, and <markdown> blocks.
  • An edit in the editor keeps the program's things: in Drawable Solitaire, all 52 cards stay where they were, drawn the new way.
  • Not built yet: the TypeScript writer's own element class. For both output languages, the page makes the element today (Limits).
  • Write a card is a drawable thing:, with the colon, and give it a to draw.
  • Put its styles in a <css> block, indented under that line.

A drawable thing is a spell type that draws in an element of its own. Everything else about the type stays as it was: its properties, its methods, its to draw.

Two built-in types, each two words long, say a type is drawn as an element.

the two built-in types, and what each compiles to · 4 lines 
a card is a drawable thing           -- export class Card extends Drawable
a card is a drawable                 -- the same
a pile is a drawable list of cards   -- export class Pile extends DrawableList { static instanceType = Card }
a pile is a drawable list            -- export class Pile extends DrawableList
  • They compile to two classes in spell's runtime, which every compiled program imports.
    • Drawable, a kind of thing
    • DrawableList, a kind of list
  • A type built on a drawable type is drawable too: a tableau that is a pile gets its own tag.
  • A type's name may be several words, with a short name after aka: a bank account aka account is a thing.
  • Only declared names count, the longest first: "a big card" stays a card unless someone declared a big card.

The tag is the project's name made singular, then the type's name, in dashed lowercase words.

project type tag
Solitaire card <solitaire-card>
games bank account <game-bank-account>
Drawable Solitaire stock pile <solitaire-stock-pile>
Todos - Form Based task <todos-form-based-task>
  • The word "drawable" is left out of the project's name: Drawable Solitaire's tableau is <solitaire-tableau>.
    • A type's own name keeps it: a DrawableCard in project Games is <game-drawable-card>.
    • A project named only "Drawable" starts the tag with spell-.
  • A project name with no letters starts the tag with spell-.
  • The names are English only, for now.
  • One tag per type per page: two <spell-app>s of the same project share it, drawn by the runtime that defined it last.

A drawable type's look is a <css> block in its outline, the lines indented under it.

  • The type's line needs its colon, or the indented lines aren't its outline, and the block is an error that says where it goes.
  • The block is read exactly as written, the way a browser reads <style>: its braces and angle brackets are never taken for spell.
  • VS Code and the spell editor colour it as CSS, and give CSS completion, hover and errors inside it.
  • The element adopts the page's theme sheets first, as Spell UI's own elements do, then the type's sheet. A super-type's sheet comes before its sub-type's.
  • Only a drawable type may have one. Page CSS doesn't reach inside the element: style the type in its block, or its tag from outside.

  • CSS's own escapes, like "\201C", stay as written.

  • Core only names the tag: the page running the program defines it, because core may not import Solid or Spell UI.

A drawable list, such as a pile of cards, is an element whose children are its items' elements. Its to draw draws only its frame.

The element shows its type on the outside: the type's properties are its attributes and properties, the type's methods its methods.

It draws one thing of the program, its thing. A property holding another thing shows as a reference, pile="Tableau#T1", which spell can write too: tableau T1.

  • Each declared property is an attribute, kebab-cased, and an element property, camelCased.
    • A property face_up is the attribute face-up and the property faceUp.
  • Each method is an element method, camelCased: turn_over is card.turnOver(), calling the thing's.
    • Not draw(), and not a method with values in its name, like "is a (suit)".
  • The attribute's kind comes from the property's declared type.
declared as attribute example
text, character, date, or no type text suit="spades"
number, integer number score="12"
choice (yes or no) there or not face-up
another thing: a card, a pile its reference pile="Tableau#T1"
a list none: an element property only set from a script
  • A legal value written as text becomes the value itself: rank="2" sets the number 2, since 2 is one of a card's ranks.
  • Only DECLARED properties: a worked-out value, like a card's colour, isn't on the element.
    • But the list holding it is: a card belongs to one pile shows as the card's pile (A property holding a thing).
  • Names the page or Spell UI already mean something by are left out, like title and hidden: a script sets those on the thing.

A change on either side shows on the other, so the browser's inspector always tells the truth.

  • Turning the card over, from the program or with ace.turnOver(), changes the tag's direction="up" to "down".
  • Setting the attribute, or the element's property, changes the thing at once, and the card redraws: ace.setAttribute("rank", "2").
  • Reading ace.direction asks the thing, so it's never stale, and a number reads back as the number.
  • Removing an attribute makes the thing's property nothing.
  • No loops: a value the other side already has is never written, and an element never hears its own attribute writes.
  • It holds for every drawable element: a card the program draws shows its rank, suit, direction and pile as attributes too.

An element's thing is the spell thing it shows. Every drawable element draws ONE thing of the program.

  • A <solitaire-card> draws one card object: the element is that card's view.
  • It draws the card's own to draw inside itself, and keeps its attributes and the card's properties the same, both ways (above).

The element finds its thing in one of three ways. The first one that applies wins.

way how example
1. The program draws it Spell draws a card, or a pile draws its cards: the page makes the tag and hands it the card itself, in its thing property draw the card
2. A tag names it A reference in its thing attribute, on any page; or, in a layout, its id thing="Pile#stock",
id="T1"
3. A tag with neither In a layout: the program's one thing of the tag's type. On a plain page: a new thing of its type, made from its attributes <solitaire-stock-pile>,
<solitaire-card rank="ace">
  • A tag naming a thing the program hasn't made shows a stand-in, ⚠ no Pile#stock, and draws the thing as soon as the program makes it.
  • In a layout, a tag with no id whose type has no thing, or more than one, asks for an id.
  • In way 1 the card is only handed over: no thing="..." attribute is written, so the inspector doesn't show which card an element draws (Limits).
  • Where: SpellElement.currentThing.

A reference names one thing of the running program in text: its type, #, then its name or its place. It reads like CSS's tag#id.

references, and the thing each finds · 4 lines 
Tableau#T1    -- the tableau named T1
Tableau#1     -- the first tableau the program made, counting from 1
Pile#T1       -- the tableau named T1 too:  a tableau is a pile
Game#game     -- a thing with no name, by the top-level name the program keeps it under
  • The type is the class's name, as the program declares it: Tableau, never tableau.
  • A place is the order the program made the things in, not the order of their elements on the page (J42).
    • So moving elements on the page never renumbers anything.
    • A thing with no element still has a place.
  • A name finds a sub-type's thing too, but a place counts only things of that type exactly: Pile#2 isn't yet the second pile of any kind.
  • Digits are always a place: a thing named "3" can't be found by its name.
  • Two things with the same name: the first one made wins.
  • A thing with no name, or a name an earlier thing of its type has, is written as its place: Hand#2.
  • A thing that isn't the program's, like a scratch list, has no reference.
  • In code: spellCore.thingForReference("Tableau#T1") finds a thing, and spellCore.referenceFor(tableau) writes the reference that finds it again.

A property holding a thing shows on the element as the thing's reference, and follows it as it changes.

a tableau and one of its cards, as the inspector shows them, shortened · 3 lines 
<solitaire-tableau id="T1">
  <solitaire-card rank="king" suit="spades" direction="up" pile="Tableau#T1"></solitaire-card>
</solitaire-tableau>
  • Every Drawable Solitaire card shows the pile holding it. A card played from the stock turns to pile="DiscardPile#discards".
  • A card's pile isn't declared: it's the list holding it, from a card belongs to one pile.
  • Setting it moves the card, as move the card to ... does: the piles' rules decide (J45).
    • From a script: card.setAttribute("pile", "Tableau#T1").
    • Or with the thing itself: card.pile = tableau.
    • A move the rules refuse leaves the card, and the attribute shows its pile again.
    • A reference that finds nothing (yet) changes nothing, and the attribute stays as written.
    • Removing the attribute leaves the card where it is.
  • A property declared as a thing, like a chip has a home as a stack, is set to the thing the reference finds.
  • Reading card.pile on the element gives the reference's text, "Tableau#T1".
  • A list of things has no attribute: it's set from a script.
  • A tag can say which thing it draws with one, too: thing="Pile#discards" (Its thing).

Spell names one thing by its name or its place, as a reference does: tableau T1 is the tableau named T1.

the ThingReferences test project, shortened, and what each line compiles to · 7 lines 
set t1 to a new tableau with name = "T1"
get a new foundation with name = "hearts"

print the name of tableau T1          -- spellCore.thingNamed(Tableau, "T1")?.name
print the name of foundation "hearts"
print the name of pile T1             -- a tableau is a pile
print the name of the last tableau    -- spellCore.thingAtPlace(Tableau, -1)?.name
  • By name: tableau T1, the reference Tableau#T1.
    • the count of tableau T1 reads its count.
    • pile T1 finds a tableau too, since a tableau is a pile.
    • A name written bare starts with a capital letter; any other name goes in quotes: foundation "hearts".
  • By place: the first tableau, the reference Tableau#1.
    • Counted in the order the program made them: the last tableau is the last one made.
    • Every ordinal word spell has works: second to tenth, penultimate, last.
    • Only tableaus count: the first pile finds no tableau.
    • New meaning: the first card, with no "of" after it, was an error, and is now the first card made. the first card of the deck is still the deck's.
  • One the program hasn't made is nothing, not an error, and reading off it gives nothing too: both writers read off it with ?..
  • The words work in a page's layout too: {the count of tile T1} follows the tile live.
  • Two things with one name: where spell names one, and the project gives two things that name in so many words, the compiler warns.
    • The warning: More than one tableau is named "T1": this finds the first one made.
    • Counted: with name = "T1", as a thing is made.
    • Not counted: a name worked out as the program runs, like name = ("T" + the number), or a later rename.
    • Two things with one name that nothing names: no warning.
  • Where: spell's rules named_thing and thing_at_place.

  • The markup replaces the app's own to draw: the game's drawing isn't drawn.
  • Each drawable tag finds the program's thing, the first of these that applies (Its thing):
    • a reference in its thing attribute: thing="Pile#discards" is the pile named discards
    • its id, as the thing's name: id="clubs" is the foundation named clubs
    • neither: the program's one thing of the tag's type, like the stock

  • With neither, the type must match exactly: a pile tag with no id takes only a plain pile, never a tableau.
  • A tag whose thing the program hasn't made shows a stand-in, ⚠ no Pile#discards, until it does.
  • A drawable list the page wrote puts its own items in.
  • A hole in curly brackets is spell, and shows a live value: {the score of the game}.
  • It's spell exactly, as everywhere else in spell: {score of the game}, missing its "the", shows ⚠, and the program's console says why.
  • Names are looked up in order: the tag's own thing, its class, the page's named tags, then the program.
    • So {the number of cards in T1} finds the tableau whose id is T1.
    • Spell's own words find the program's tableau, tag or not: {the count of tableau T1} (Spell's words for one thing).
  • The layout's spell is compiled in the page, which loads spell's parser only for a layout with spell in it.

Any element in a layout handles events: a Spell UI tag, a plain one, or a drawable one.

  • As an attribute, in either spelling: on-click="{auto-play}", the browser's event name, or when-clicked="{...}", spell's.
  • As a <spell> block inside the element: when clicked: bump the score on one line, or the statements indented under it.
  • "on" works as well as "when": on drag: is when dragged:.
  • An event may be several words, joined with dashes before it's looked up: "when double clicked" is "when double-clicked".
  • Past-tense words map to the browser's events: clicked, double clicked, right clicked, hovered, unhovered, focused, blurred, changed, typed, submitted, dragged, dropped.
    • Any other word is the browser's own event name: on keydown:.
  • On a drawable tag, or a plain tag inside one, the handler's "it" is that tag's thing.
  • A re-run takes back every handler the layout added, so none is left listening.
  • A <markdown> block draws formatted text, its holes live (Markdown blocks).
  • The browser reads the layout first, so the block's text is used: write a less-than sign as &lt;.
  • A child written in="header" lands in a frame's named place, as in a drawing.

  • The indent its lines share comes off, and VS Code and the spell editor colour it as markdown.

An edit in the editor keeps each tag defined, draws with the new program, and keeps the program's things. In Drawable Solitaire, an edit to a card's CSS keeps the game in progress, drawn in the new colour.

  • A page can't define a tag twice, so each drawable type's tag stays defined.
  • The new run's class is recorded behind it, and the element draws with it from then on.
  • The type's CSS is replaced in every element of the tag already on the page, without drawing them again, through Spell UI's own style sheet replacement.
  • Each old thing becomes ONE new thing: a card held by the deck and a pile stays one card.
  • The console says what was kept: Kept allPiles, deck, ... from the last run: Restart starts afresh.
  • It works for any program: a counter keeps its count across an edit.
  • A run that throws mid-edit doesn't lose the game: the next good recompile carries the last good run over.
across the edit what happens
a property added the new thing's own starting value
a property removed, or now only worked out dropped
a property whose type changed, or a type renamed or gone each top-level thing holding one starts afresh, and the console says so
  • Restart starts afresh, on purpose: a new deal.
  • That's <spell-app>'s Restart and its restart(), the editor's Restart button, and VS Code's Restart.
  • Running another program starts afresh too.

Each output language says, in one place, how it writes each kind of name: its naming map. So a bank account is a thing compiles to class BankAccount.

  • The kinds of name: types, methods, variables, properties and constants, or one case for all.
    • javascript and TypeScript: types in PascalCase, everything else in camelCase.
    • A Python target will name everything in snake_case, in one line.
  • A type's name written as text in the compiled code, like a type check's, follows the map too: spell marks it with a tree node of its own, which every writer renames.
  • A drawable type's tag doesn't change with the map: a bank account is <game-bank-account> either way.

The decisions behind the design, each settled in the plan doc.

  • "drawable thing" and "drawable list" are built-in types of two words, not a "drawable" adjective.
  • So the line needs no special rule, only multi-word types.
  • Adjectives in general ("sortable", "saved") are a future epic, mixins.
  • By the packages' one-way rule: Spell UI may not import spell, and core may not import Solid or Spell UI.
  • So core only names the tag, through a hook, and the app, which runs the program on a page, defines it.
  • The element gets its styles exactly as Spell UI's own do: "These elements are just like Spell UI's" (Owen).
  • The project's or library's name, made singular, then the type's: <game-card>.
  • No "drawable" in it: Owen asked for <solitaire-tableau id="T1">, "no <drawable- prefix".
    • The word comes out of the project's name only, so a type named for it keeps its own word (J44).
  • The author naming the tag by hand is left for another epic.
  • One tag per type per page, since a page can't define a tag twice.
  • One place to read what a type is and how it looks: its outline.
  • Read as raw text, as HTML reads a style tag, so CSS is never taken for spell.
  • Compiled as a css-tagged template, as Lit writes it, so editors colour it (Owen, reviewing the first build). The tag hands back plain text, not a style sheet object.
  • First built one way, element to thing; Owen: "The dom and the component need to agree."
  • Reading an element's property asks the thing straight through, over the element's own copy, which would be stale for a moment after a change.
  • Owen asked for them, on a property holding a thing (J23): "maybe we could have a scheme like Tableau#T1?"
    • "Might be interesting to reflect it that way into the DOM as well."
    • So such a property gets an attribute after all.
  • A place is the order the program made things in, not page order (J42):
    • an element finds its thing BY the reference, so counting elements would go round in a circle
    • a thing with no element still has a place
    • Owen: "a) now, maybe b later": page order is a todo to think about
  • Digits are always a place, so one text has one meaning (J47).
  • Setting a card's pile moves it, so the piles' rules still decide what may go where (J45).
  • Lists stay properties: a tableau of 13 cards would be an attribute of 13 references, rewritten on every move (J46).
  • An element drawn by the program doesn't write its own thing attribute yet (J43):
    • Spell UI hears every attribute written on its elements as the page changing it.
    • So writing it would swap the card the element was handed for a text that looks the card up.
    • That text finds the card only while it keeps its name, and a card's name follows its rank.
  • Owen: "the <property> of tableau T1 is a reference that maps to Tableau#T1. Similarly, 'the first tableau' maps to Tableau#1."
  • A bare name starts with a capital letter, or goes in quotes (J49):
    • spell reads words for many things: turn card over mustn't read as the card "over"
    • spell's own words are lowercase, so a capital can't be mistaken for one
  • A place means what Tableau#1 means: a program has no page, and what it draws can change, but the order it made things in can't (J48).
  • A missing thing is nothing, not an error, so a layout's hole shows nothing until the program makes the thing (J51).
  • The warning is careful, as Owen asked: "need to be careful, this could get annoying very quickly" (J50).
  • A tag finds its thing by a reference, its id, or its type; the markup replaces the app's own drawing.
  • Holes and actions may hold any spell, since spell's own drawings already take any statement.
  • The layout's spell is compiled in the page, against the running program.
  • A hole is spell exactly, as everywhere else: an earlier retry with "the" in front was dropped (Owen).
  • Both attribute spellings, on- and when-, since each reads well to someone.
  • in for a named place, written out as the web's slot, in drawings and layouts alike.
  • Allowed in a drawing, a type's outline and a layout: every place.
  • Holes live, as a layout's text.
  • Drawn by Spell UI's markdown element in the page: no markdown parser in the compiler.
  • First, a re-run started afresh; Owen asked for the game to survive an edit, as a phase of its own.
  • No compiler change: the program still runs from the top, stopped at its first pause, so it works for every program compiled today.
  • Things are copied object to object, not through saved JSON, which keeps no identity: so one card stays one card.
  • Restart is the way to start afresh on purpose.
  • Owen: "BankAccount. this should be settable in output language, as should all other term transformation".
  • A type's name in text is a tree node of its own, so a new place that writes one can't be missed by a writer.

What doesn't work yet, or works with a catch. Each links its item in the plan doc.

  • The TypeScript writer doesn't write the element class yet: it writes a drawable thing as a plain class, and the page makes the element, as for javascript.
    • It's being built next, in P10, on the runtime's own element (J41, option B).
  • Compiled TypeScript draws a drawable child inline, with its own draw(), not as its element.
  • A drawable tag written by hand in a drawing doesn't type-check in TypeScript: no JSX tags are declared for the program's own types (I7).
  • What a program's start does before its first pause runs again on each edit: its tests print again, and a toast or alert there shows again (J36).
  • A start with no pause runs to its end, then its things are replaced.
  • A plain top-level variable, a number or a text, starts again from the new start. Carried things show under no heading in the Thing Explorer (T7).
  • A tag's attributes and methods are fixed the first time it's defined: one an edit adds needs a reload.
  • Page CSS doesn't reach inside a drawable thing's element: style it in its own block.
  • A card moved to another pile is a new element there, drawing the same card: code shouldn't hold a card's element across a move.
  • A frame without <children/> shows no items, with no warning.
  • A card written by hand inside a pile written by hand shows there, but isn't in the pile's list: a script adds cards to its thing.
  • A place counts only things of one type exactly: Pile#2 and the second pile don't count a sub-type's things (T10).
  • An element the program draws doesn't show which thing it draws: no thing="Card#..." in the inspector (T12).
  • A list of things has no attribute, only an element property (T13).
  • A place is never the order of elements on the page (T14).
  • A reference written by name finds its thing only while it keeps that name: a card's name follows its rank and suit, so thing="Card#queen-of-spades" loses the card when its rank changes.
  • The duplicate-name warning sees only names given in so many words as a thing is made, not ones worked out as the program runs.
  • Quote an attribute's spell when a word repeats: unquoted, the browser keeps only the first of two attributes with the same name.
  • An HTML formatter flattens a <spell> block: put a prettier-ignore comment above its element.
  • A layout knows only its own project's types and functions, not those of a library it imports.
  • Inside a markdown hole, editors give no spell hover or colouring, and an error underlines the whole block (T8).
  • In the spell editor, a CSS comment over several lines colours only its first line.
  • Spell UI's spell code blocks don't colour a CSS block as CSS.
  • A type's outline needs its colon, or a CSS or markdown block under it is an error.
  • A short name in a nested scope can hide a type of that name further out.
  • A language naming types in snake_case gives a type and its variable the same name (I6).
