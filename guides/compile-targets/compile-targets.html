Compile Targets

A sketch, not a plan: how spell could write the same program as JavaScript, TypeScript or Python, the way the human-language plan lets the same program be WRITTEN in English or Spanish.

Written for: Owen, deciding whether this becomes an epic Status: sketch Researched on: main, 2026-10-05, from the compiler's source and the test fixtures' compiled output (see Sources)
  • Spell's middle is ONE tree: syntaxes (English, Spanish ...) on the way in, targets (js/solid, ts/solid, py ...) on the way out. N syntaxes plus M targets, never N × M.
  • A target is three things: a WRITER (walks the tree, writes one language's code), a CORE (that language's spellCore), and what it CAN do (draw? react?).
  • The seam already exists: nearly every rule builds a tree node (getAST()), about 75 kinds of them. But today each node writes its own JavaScript, so the tree can't feed a second language yet.
  • Scopes, methods, types and properties carry over easily. The work is in the small things languages disagree on: truthiness, text plus number, nothing, multi-line lambdas, names. Known datatypes let a writer use the language's own operator; unknown ones fall back to a spellCore call.
  • Step 1 changes nothing you can see: move every node's compile() into a JSWriter with byte-identical output, proven by the fixture snapshots.
  • Call it a TARGET (the destination) with a WRITER (the code that walks the tree).
  • Do step 1 and 2 first: they're worth having even if no second language ever ships.
  • Then ts/solid, the cheap one; then py, the stress test.

Two things need names: the DESTINATION (js/solid, py) and the CODE that walks the tree and writes text for it. "Emitter" names the second, and reads like compiler jargon.

word names reads as verdict
target the destination the standard word: TypeScript's target, LLVM's targets, Rust's target triples pick, for the destination
writer the walker plain English; says what it does. JSWriter, PyWriter pick, for the walker
scribe the walker on theme: a scribe copies a spell into another script. Fun, but one more word to explain if you want flavour
backend either overloaded: "backend" already means the app's server here clashes
emitter / code generator the walker compiler jargon the one you don't like
printer the walker Prettier's word, but sounds like it formats, not translates misleading
translator / dialect either already taken by the HUMAN-language side: a Spanish translation of spell clashes

The rest of this page uses target and writer.

Read left to right. Everything left of the tree is about how spell is WRITTEN; everything right of it is about where it RUNS. The tree is the only thing both sides share.

Today every tree node is a class with TWO ways to write itself as JavaScript: compile() for the text, renderChildren() for the AST viewer's coloured copy of the same text. In the sketch, a node is just data, and one writer method per node kind does both jobs at once.

Moving the writing out isn't enough: some JavaScript is decided BEFORE the tree exists, in the rules. Each of these becomes meaning in the tree, and the writer decides the spelling.

Every core implements the same list of methods. what it can do Draw (into the page, into HTML, not at all), react to changes, wait. Checked while parsing, so a mismatch is an error in the editor.

A target's name is LANGUAGE / RUNTIME. The two parts are mostly independent: js/solid and js/react would write the same JavaScript, since drawing already goes through spellCore.element() and properties through getProp() / setProp(). What differs is the core they load.

target writer core draws reacts
js/solid JSWriter @spell/core (Solid) into the page yes
ts/solid TSWriter @spell/core (Solid) into the page yes
js/react JSWriter a React build of the core into the page yes
py/html PyWriter spell_core HTML text: server pages no
py PyWriter spell_core no no

A writer is a class with one method per node kind. Each returns CODE: text pieces, each tagged with the node that made it. That one value is flattened for the file, wrapped in spans for the AST viewer, and walked for a source map.

Writer.ts (sketch) · 24 lines 
/**
 * Writes the spell tree as one language's code.
 * - One method per node kind, named for it:  `If` writes an `If` node.
 * - Returns `Code`:  text pieces tagged with the node that made them, so ONE walk gives the text, the AST viewer's
 *   markup and a source map.
 */
export abstract class Writer {
  /** Writes `node` with the method named for its kind. */
  write(node: Node): Code {
    return this[node.kind](node)
  }

  /** A `spellCore` call:  each writer spells the core's name, and its methods' names, its own way. */
  abstract core(method: string, ...args: Node[]): Code

  /** `a + b` in the language's own operator when both sides are numbers, else the core's `add`. */
  Add({ left, right }: Add): Code {
    if (left.datatype === "number" && right.datatype === "number") return code`${left} + ${right}`
    return this.core("add", left, right)
  }

  abstract If(node: If): Code
  abstract Lambda(node: Lambda): Code
}
 JSWriter.ts (sketch) · 13 lines 
export class JSWriter extends Writer {
  If({ condition, body, otherwise }: If): Code {
    return code`if (${condition}) ${this.block(body)}${otherwise && code` else ${otherwise}`}`
  }

  Lambda({ params, body }: Lambda): Code {
    return code`(${params.join(", ")}) => ${this.block(body)}`
  }

  core(method: string, ...args: Node[]): Code {
    return code`spellCore.${method}(${this.list(args)})`
  }
}
 PyWriter.ts (sketch) · 22 lines 
export class PyWriter extends Writer {
  If({ condition, body, otherwise }: If): Code {
    const rest = otherwise instanceof If ? code`el${otherwise}` : otherwise && code`else:${this.indented(otherwise)}`
    return code`if ${condition}:${this.indented(body)}${rest}`
  }

  /**
   * A one-expression body stays a `lambda`;  anything longer is lifted into a nested `def` written just before
   * the statement that uses it, named for what it does, e.g. `each_number`.
   */
  Lambda(node: Lambda): Code {
    if (node.body.isExpression) return code`lambda ${node.params.join(", ")}: ${node.body}`
    const name = this.names.fresh(node.purpose)
    this.before(code`def ${name}(${node.params.join(", ")}):${this.indented(node.body)}`)
    return code`${name}`
  }

  /** `getRange` -> `core.get_range`:  Python's names. */
  core(method: string, ...args: Node[]): Code {
    return code`core.${snakeCase(method)}(${this.list(args)})`
  }
}

The big concepts carry over. These small ones don't, and each needs a home: the WRITER (it's spelling), the CORE (it's behaviour at run time), or the TYPES (known datatypes let the writer use the fast, native form).

thing JavaScript Python handled by
an empty list, as a condition true false core (isTruthy), or native when the type is flag
text plus a number joins them TypeError writer (str(…)) when types are known; else core add
nothing undefined (and null) None writer
whole-number division 6 6.0 core (isOfType, printing)
a multi-line block passed as a function arrow function lifted nested def writer
computed properties, setters get / set @property writer
class set-up (static { … }) static block calls after the class writer
waiting (pause for 50 msec) async / await async def, asyncio writer + core
names $ legal; class, new reserved $ illegal; class, None, is reserved writer, from the SPELL name
lists counted from 1 neither core
drawing Solid, into the page HTML text, or nothing core (element()), and the target's "can"
reactive properties signals behind getProp a plain dictionary core
  • Without datatypes, every + becomes core.add(a, b): correct, but slow and ugly. precedence-and-types put a datatype on every match; the gaps it lists (C10, C14: calls, recursive calls) decide how often a writer has to fall back.

packages/core/src/spellCore.types.ts already lists the core's methods by family. It becomes the list EVERY core must implement, and one set of spell programs proves they agree: each target runs them, and their printed output must match, line for line.

  1. The names: target + writer? Or scribe for the walker? (See What to call it.)
  2. Where writers live: inside spell (packages/spell/src/targets/), or a package of their own between spell and lsp? Leaning: inside spell until a second writer exists.
  3. js/react: only a different core build, the writer unchanged? Leaning: yes.
  4. Python's goal: code a person would happily read and edit, or code that just runs? Readable leans much harder on the types, and on the writer.
  5. When: after precedence-and-types' wrap-up, so the types it leaves open (C10, C14) are known first? Leaning: yes; step 1 doesn't depend on them, so it could start any time.
