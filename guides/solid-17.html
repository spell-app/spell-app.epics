Solid rc.17

<ui-dropdown options={options} on-ui-change={f} /> now just works: in plain Solid that object would arrive as text, and the listener would need a ref. Every repo runs on Solid 2 rc.17; this page says what moved, what broke (270 tests, from one new check) and how it was fixed, and how a Solid page passes events and data to our elements as plain props.

Epic page: epic solid-17 Written for: anyone writing Solid code in these repos, or a Solid page that uses Spell UI's elements Status: built on branch solid-17, in every repo; not merged yet Checked: every repo's type check, lint, format and tests, and the pages in a headless browser, 2026-10-22. What nobody has tried by hand yet is under Limits.
  • Solid moved from rc.13 to rc.17 in all six repos, with its Vite plugin and router: one copy of each in the install.
  • One new rule broke 270 tests: rc.17 throws when a Solid root is made inside an effect's callback with no owner.
    • That's where the browser builds our elements, so every element now makes its root a safe way.
  • Two smaller changes:
    • the router now decodes the editor's address itself
    • <Errored> builds a stand-in once
  • Plain props on our elements: on-ui-change={f} listens for an event, and an object reaches the element as itself.
    • No prop: is left in hand-written JSX.
  • Never make a memo, effect or root inside an effect's callback with no owner: use E.Reactive.ownRoot() for a root of its own.

Nothing in our source used an API rc.14-rc.17 removed, so the type check passed as it was. What broke was behaviour, and only the tests found it.

The first test run on rc.17 failed 270 tests in five repos, nearly all from one new check.

  • Solid inserts our elements from inside an effect's callback.
  • The browser builds the element right there, in its connectedCallback().
  • The element made its Solid root with a plain createRoot(), with no owner, and rc.17's dev build throws for that.
The error · rc.17's dev build 
[PRIMITIVE_IN_EFFECT_CALLBACK] Cannot create a memo, effect or root with no owner inside an effect callback

The fix is Reactive.ownRoot(), from spell-kit/element: a root made under one owner of our own, which holds nothing and never goes.

throws on rc.17, inside an effect's callback 
import { createRoot } from "solid-js"

const component = createRoot((dispose) => mount(dispose))
 safe anywhere 
import { E } from "spell-kit/element"

const component = E.Reactive.ownRoot((dispose) => mount(dispose))
  • Every element and every detached root uses it.
  • The element still lives until it's disposed.
  • No context reaches inside: not the caller's, not an app's.
  • Work that should live with a component instead keeps its owner: getOwner() in the body, then runWithOwner() in the effect's callback.
  • A conditional prop (layout={isWide() ? a : b}) becomes a memo on its first read, so reading it first inside an effect's callback throws the same way.

Since next.40 the router decodes each route param itself, and the editor went on decoding its address a second time.

  • A file named with %25 in it would have opened the wrong file.
    • Each decode takes one step: %2541 → %41 → A.
  • The second decode, SpellLocation.addressForUrl(), is gone.
  • A route test pins a name with %25 in it.

Since rc.15, <Errored> and <Loading> build their fallback once, even as what's around them changes.

  • spell-lang's drawing had its own catch for a failing draw(), because rc.13 built a new stand-in each time the drawing around it changed.
  • A test pins the case: a card added to a pile leaves the broken card's stand-in as it was.
  • It passes without the catch, so the catch is gone. One way to show a stand-in is left: Solid's.
spell-lang's drawInBoundary() · the one boundary every drawn thing sits in 
function drawInBoundary(thing: object, draw: () => Drawing): Drawing {
  return createComponent(Errored, {
    fallback: (error: () => unknown) => drawingFailed(thing, error()),
    get children() {
      return createMemo(() => madeOnce(draw())) as unknown as Drawing
    }
  })
}
  • h()'s narrower return type needed six casts in spell-lang.
  • rc.14: only a name with a capital after "on" is an event (onClick); a lowercase one is a plain attribute. We had no lowercase ones.
  • rc.16: <For>'s keyed reconciler was rewritten.
  • rc.16: writes inside a cleanup are allowed.
  • rc.17: Solid 1's attribute forms (on:, attr: ...) are compile errors. We had none of those either.
  • rc.17: a cleanup that throws no longer stops the others.
  • Our reads of Solid's event-delegation internals all still hold.

A Solid page passes everything to our elements as plain props now: an event listener, an object, a list.

rc.13 · prop: for data, a ref for each event 
<ui-dropdown
  prop:options={options}
  prop:value={value()}
  ref={(el) => el.addEventListener("ui-change", onChange)}
/>
 rc.17 · plain props 
<ui-dropdown
  options={options}
  value={value()}
  on-ui-change={(event) => setValue(String(event.detail.value))}
/>

on-, then the event's own name, listens for it.

  • on-ui-change={f} listens for ui-change.
  • on-ui-open={f} listens for ui-open.
  • On a translated tag, it listens for that tag's own name for the event.
  • Giving it a new function replaces the old listener; removing the prop removes it.
  • onUIChange doesn't work: Solid lowercases the name after "on".
    • So it listens for uichange, which nothing sends.

A function or an object, given to any other attribute, sets the element's property.

an object, a list 
<ui-tree-diagram tree={tree()} />
<ui-dropdown options={options} />
  • Text, numbers and booleans stay attributes, as the browser has them.
  • So an element given text for its script API reads that attribute too: <ui-code content={markup}>.
  • A later value or open attribute sets the element's current value.
    • So value={selected()} keeps it in step.

Solid sets a prop it doesn't know with setAttribute(), the value as it is, not as text. Our elements catch it there, through the kit's RichAttributes.

A page that wants the browser's own setAttribute() untouched says so on its root.

a page with no patch 
<ui-root pure>
  <ui-dropdown></ui-dropdown>
</ui-root>
  • Then a function or object given to a tag whose component hasn't loaded becomes text, as in plain Solid.
  • The root must be in the page's markup: a <ui-root pure> the app draws itself comes too late for what the patch held before it.

The decisions that shaped it, one line each.

  • Everything moves together, one commit per repo: the packages require each other at minimum versions (Q2).
  • spell-app's build tests were fixed here, not logged: they're exactly what an upgrade like this could break (Q1).
  • Events as on-ui-change, caught by our elements' own setAttribute() (Q3).
    • Over a twin event without dashes, a compile step, or rewriting everyone's listeners.
  • No prop: in our JSX: the same catch sends functions and objects to the property (Q4).
  • Elements not loaded yet are covered by a page-wide patch that a page can turn off (Q5, Q8).
  • A later value / open attribute sets the current value (Q6).
  • Text meant for a property: the element reads that attribute too (Q7).
  • One way to show a stand-in, Solid's <Errored>: drawing's own catch went (J1).
  • Not tried by hand yet: the app's editor on rc.17, and its dropdowns, settings and tree viewer with plain props (V1, V2).
  • Tags aren't defined up front: only the patch covers elements not loaded yet (J6).
    • So on a <ui-root pure> page, a function or object given to such a tag is lost.
    • Defining every catalog tag early reaches about 30 files that read "defined"; it's for its own epic.
  • Compiled spell still writes prop:: only hand-written JSX is plain (J7).
    • It still works: prop: is still Solid's way to set a property.
  • It leans on Solid's behaviour, not a promise (C2): Solid hands an unknown prop to setAttribute() as it is.
    • A later release could turn it into text first, or reject on-*: then every one breaks at once.
  • The patch touches every element on the page (C4): one extra check on each setAttribute() call.
  • Solid's dev build warns once per on-* name (C7), telling you to write onUi-change.
    • The warning is wrong for our elements, and Solid has no switch to quiet it.
  • A server render writes a function's source into the HTML (C9), and an object as [object Object].
    • Hydration doesn't set them again, so listeners and objects are missing after it.
  • One rule wasn't measured again: whether an error in an effect's first function now reaches <Errored> (J2).
