Airplane Mode

How Owen works on the epics and docs with no Claude (a plane, bad wifi), and how Claude takes what he left once he's back.

Plan doc: epic airplane How a plan doc works, and how to review one: Plan Docs Written for: Owen before and after a flight, and any agent running the landing Status: built on branch airplane, 2026-10-09 Checked: each package's tests, and the whole flow end to end on a scratch epic and guide (P5)
  • Everything Owen does on a page saves to this laptop's page server: no internet, no Claude.
  • /airplane before the flight: checks the laptop is ready, fixes what it can, turns airplane mode on.
  • On the plane: read any plan doc or guide in VS Code's side bar; mark items, write notes on any section, phase or the summary, add new todos and questions.
  • /airplane land after: gathers everything he left, by place, and works through it in the background; then /epic review for what came back.
  • The branch must be on main, the extension reinstalled from main, and /airplane run in the main checkout: the side bar shows the MAIN checkout's page server.

  • Pages blank or unstyled: the page server stopped (laptop asleep, restarted): the Review tab's "Restart Page Server" button.
  • Wifi that asks you to pay first makes requests hang: turn Wi-Fi fully off while reading.

Five parts, one per gap the explore agents found.

  • Every docs page loaded highlight.js from cdnjs with a blocking tag: on a hanging network the page showed raw markup for tens of seconds.
  • The repo now has the same file, packages/docs/tools/_assets/highlight.min.js, and the page server swaps the tag as it serves a page (localHighlight()): no page changes on disk.
  • New plan docs and list pages name the local copy; spell dev docs offline [--fix] lists anything a page still fetches, and points the old tags at the local copy.
  • One per machine: ~/.spell/airplane.json, { on: true, since } (AirplaneMode, packages/server/src/page/).
  • spell dev airplane on | off | status flips and reads it.
  • The page server tells each page as it serves it (window.SPELL_SERVER.airplane): a plan doc then says "queued for when you land" wherever it said "no Claude session is reviewing", and its review line names /airplane land, with no orange warning.
  • The summary and every phase take Revisit, Make Todo and Do Now, as Overview sections do (no Approve).
  • New items: a mark of their own kind in the inbox, { action: "new", kind, title, note, near }, keyed new1, new2; shown dashed at the end of their section until applied.
  • spell dev plan-doc inbox <name> apply makes them as plan-doc add does; --all takes marks never sent.
  • Written INTO the page: <spell-notes for="<section id>"><spell-note id="n3" status="new">, so the shared repo commits it with the page.
  • Drawn by the docs runtime as a folded card, Claude's replies under it; the page updates in place after a note.
  • Not on plan docs (their inbox), templates, goals (thoughts), details pages with questions, Spell UI or brand pages.
  • Claude's side: spell dev notes list | answer <page> <id> --file | done.
  • Queue only, no Claude mid-flight (Q6): plane wifi is too flaky to run a session on; everything waits for the landing.
  • Notes inside the page (Q2): they travel with the page, committed, rather than in a side file on one laptop.
  • The landing takes every mark, sent or not (Q3): nobody was there to send them to; drafts are asked about, since Owen never submitted them.
  • The landing works in the background, then hands over to a review (Q4): like /bedtime, so a 30-60 mark backlog isn't hours of one-at-a-time talk.
  • The page server swaps the CDN tag (J1): the shared pages keep it until this branch is on main, so main's pages never lose their code colours; /airplane rewrites them after.
  • Old marks get taken too (J9): an inbox can't tell a mark made on the plane from one left earlier; /airplane's waiting line lists them before the flight.
  • Inboxes live on this laptop only; page notes are committed with the shared repo, but only after the next Claude turn, so after landing.
  • A new worktree on the plane needs yarn install: it ran in offline mode on an installed worktree, never on a fresh one.
  • The new-item form keeps no draft: a reload while typing loses it.
  • The landing's background half never ran on a real backlog: expect to steer the first one.
  • The orange "nobody is reviewing" line fails the contrast check (4.46:1 against 4.5); airplane mode doesn't show it.
