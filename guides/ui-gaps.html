Spell UI Gaps

 The same button, before and after · 2 lines 
<ui-button primary basic compact href="save.html">Save</ui-button>
<ui-button color="primary" appearance="basic" padding="compact" link="save.html">Save</ui-button>

Every Spell UI tag now says one idea with one word. And a page can be drawn without a single native HTML tag: tables, paragraphs, links, layout, video and the page itself are Spell UI tags.

A Spell drawing holds no native HTML, so whatever HTML could draw and Spell UI couldn't was a gap. This epic closed the gaps drawings need.

First it gave every attribute one name, so the new tags were born in the new words.

Then it moved what only the docs pages could do into Spell UI: toolbars that fit their titles, zoom, a textarea that grows, the page contents and the live example.

  • One word per idea, on every tag: color, appearance, padding, spacing, direction, align, attach, length, selected, open, label, badge, heading, selector.
  • Five attributes every tag takes: link and target, font, tooltip, label.
  • spell ui rename rewrites old markup. The old names no longer do anything on a page: run it on anything written before.
  • Ten new tags for drawings: cell (with row, in a table), stack, link, quote, keys, page, video, audio, terms and term; then zoom, toc and example.
  • Two new attributes: a paragraph on text, a caption on an image or a table.
  • Floated is gone, but on an image: a stack places things instead.
  • What only the docs pages could do is Spell UI's now: menus and toolbars that fit their titles, zoom, a textarea that grows, the page contents and the live example (section 4).
  • spell readme pictures draws a README's examples, since GitHub can't run them.
  • No drawing surface (shapes, a canvas, charts): the one large gap, set aside for later (section 6).

Fomantic UI, whose vocabulary Spell UI keeps, gave each look a bare switch of its own: <ui-button primary basic>.

That made a dozen spellings of one idea across tags. Now each idea is one attribute, and the old switch is one of its values.

 link, font, tooltip and label · 4 lines 
Read <ui-text link="rules.html">the rules</ui-text> first.
It's <ui-text font="bold italic">free</ui-text>:  run <ui-text font="code">spell</ui-text>.
<ui-card link="game.html" tooltip="Start a game">...</ui-card>
<ui-icon name="trash" label="Delete"></ui-icon>
  • link and target: on text, a real link you reach with Tab. On a tag that draws no link of its own, a click goes there.
  • font takes eight words, several at once: bold, italic, underline, strikethrough, code, highlight, subscript, superscript.
    • Inside text, each draws its HTML element, so a screen reader hears it.
    • On any other tag, the look alone.
  • tooltip: the browser's own tooltip, written as the element's title.
  • label: the accessible name, where the family has no label of its own.
  • In Spanish: enlace, destino, letra, ayuda, etiqueta.
 spell ui rename · 2 lines 
spell ui rename docs/            # a dry run:  lists each file and what it would change
spell ui rename --write docs/    # rewrites them
  • It reads every old name from the vocabularies themselves, so it keeps no list of its own.
  • It rewrites HTML pages, Markdown and the JSX in TypeScript files: tags in markup, and escaped markup in code samples.
  • Several old switches on one tag become one appearance.
  • It lists what it can't see, a JSX expression or a tag it can't read, and never guesses.
  • --markup-only leaves escaped markup alone, for pages that quote old names on purpose.
  • A dry run exits 1 when there's something to change.
  • It ran over every repo and the content pages: 3172 files in the content repo alone.
  • <ui-breadcrumbs> is the trail now, and <ui-breadcrumb> one step.
    • The old trail's name became the new step's, so the two couldn't both work at once.
    • Every page changed in the same commit.
  • Floated is gone from ten tags: a stack places things left and right instead.
  • <ui-image floated="left"> stays: text wraps round an image, which no stack can do.

Each tag below is written <ui-stack> on a page, and <stack> in a drawing.

Each has a components page (Link's is a section of Text's), its Spanish name and its tests.

A table of rows and cells · 9 lines 
<ui-table celled appearance="striped" client-sort caption="Scores">
  <ui-row header>
    <ui-cell>Player</ui-cell><ui-cell>Score</ui-cell>
  </ui-row>
  <ui-row>
    <ui-cell header>Ann</ui-cell><ui-cell align="right">12</ui-cell>
  </ui-row>
  <ui-row footer><ui-cell span="2">One player</ui-cell></ui-row>
</ui-table>
  • A row with header is the header row; a cell with header is its row's own header.
  • A row with footer is a footer row.
  • Every table look works as on a native table: celled, striped, padding, selectable, inverted, a colour. It stacks at phone width.
  • Screen readers hear a real table: rows, column and row headers, cells, named by the caption.
  • Sorting moves the row elements, header rows first, footer rows last.
  • Why one row tag: <ui-row> already was the grid's row. Its parent decides: in a table it's a table row, in a grid the grid row it was.
  • It beat a separate grid row, which would have changed every grid, and <table-row>, longer and not the name Owen asked for.
  • Why tags at all: column tags filled from a list were cheaper, but a cell holding more than text would have needed a cell template. A drawing's own for each fills typed-out rows instead.
  • The catch: a cell covers columns (span), never rows. And a caption draws inside the table's border, not above it as a native table's does.
A row of buttons, and one at each end · 7 lines 
<ui-stack direction="horizontal" wrap spacing="sm">
  <ui-button>New game</ui-button>
  <ui-button>Undo</ui-button>
</ui-stack>
<ui-stack direction="horizontal" justify="between">
  <ui-header>Solitaire</ui-header><ui-button>Deal</ui-button>
</ui-stack>
  • A column by default; a horizontal one is a row, and wrap lets it wrap.
  • spacing: none to xl, md (1em) by default.
  • align lines children up across it: start, center, end, stretch, baseline.
  • justify places them along it: start, center, end, between, around.
  • fluid takes the full width. No padding, border or colour of its own.
  • Why one tag: Web Awesome, whose layout Spell UI's utility classes copy, has six layouts. They're all CSS classes on a <div>, and a drawing has none, so it needs an element.
  • Stack and cluster are what drawings need nine times in ten, so they're one tag.
  • Six tags (flank, split, frame ...) meant six words to learn and translate. One layout tag with a type meant six sets of attributes on one tag.
  • Why justify beside align: the plan had one align. But in a column, center means across it, and between only makes sense along it: so it takes two, as CSS does.
Running text · 7 lines 
<ui-text paragraph>
  You have 12 points.  Read <ui-link link="rules.html">the rules</ui-link>, then press Deal.
</ui-text>
<ui-quote cite="https://example.com/ada">Imagination is the discovering faculty.</ui-quote>
She said <ui-quote inline>go</ui-quote>.
Save with <ui-keys shortcut="mod+S"></ui-keys>.
<ui-keys shortcut="mod+S" platform="apple"></ui-keys>
  • <ui-text paragraph> draws a paragraph: a block, with a line height for reading and room after it. Font and link work inside it.
  • <ui-link> is text's link as a tag of its own: disabled fades it and drops the link.
  • <ui-quote> is a block quote; inline, a quotation in a sentence, with the language's own marks.
  • A quote's cite is the address it's from, for readers' tools, not shown.
  • <ui-keys> draws key caps: mod+S is ⌘S on a Mac, Ctrl S elsewhere.
    • Mod (or modifier) is ⌘ or Ctrl; meta is the Meta key itself.
    • platform="apple" draws a Mac's keys whatever the reader has, and other everyone else's.
    • The docs search draws its own keys with it.
  • Why a paragraph is text's: everything text takes (size, colour, font) works on it too, and there's one less tag to learn and translate.
  • Why a link tag as well as the attribute: Owen picked both. The tag is closer to an HTML habit; the cost is two ways to write one link.
  • Why the keys go in shortcut: it's the action's own word, so a shortcut copies straight across. Keys written as text couldn't hold a value, and translation would read them as words.
  • Why a quote isn't a font word: a quotation isn't a way letters look.
 A whole window · 7 lines 
<ui-page>
  <ui-header slot="header" level="1">Solitaire</ui-header>
  <ui-menu slot="nav" direction="vertical">...</ui-menu>
  <ui-stack>... the game ...</ui-stack>
  <ui-card slot="aside" heading="Best scores"></ui-card>
  <ui-text slot="footer">Made with Spell</ui-text>
</ui-page>
  • Its slots are the landmarks screen readers jump between: header, nav, aside, footer. What has no slot is the main content.
  • A Skip to content link comes first, shown only while it has the keyboard's focus.
  • It's a root too, like <ui-root>: it loads what's inside it, and paints the window's background.
  • With no theme set, it follows the system's light or dark.
  • One per page: a second notes itself in the console, and still draws.
  • On a narrow screen, the nav and aside stack above and below the content.
  • Why not body: HTML's body is the whole document, not its regions. And "body" already means a card's or a modal's main text in Spell UI.
  • Not yet: a nav that becomes a drawer on phones; a sticky header.
 A video, and a sound played on a click · 3 lines 
<ui-video src="intro.mp4" poster="intro.jpg" captions="intro.vtt" ratio="16/9"></ui-video>
<ui-audio id="deal" src="deal.mp3"></ui-audio>
<ui-button onclick="document.getElementById('deal').play()">Deal</ui-button>
  • The browser's own players, each file relative to the page.
  • A video shows its controls unless controls="false".
  • Without controls, an audio shows nothing: for a game's sounds.
  • From script: play(), pause() and currentTime.
  • Events: ui-play, ui-pause and ui-ended.
  • Autoplay plays only when muted, or after the reader has clicked. Browsers allow nothing else, and there's no workaround.
  • One family: importing spell-ui/ui-video defines both players.
  • Why the browser's players: keyboard, full screen and captions work everywhere, for free.
  • A player in Spell UI's own look would have taken a day or more, rebuilding all three by hand.
 A card's details · 4 lines 
<ui-terms>
  <ui-term label="Suit" value="hearts"></ui-term>
  <ui-term label="Owner"><ui-link link="ann.html">Ann</ui-link></ui-term>
</ui-terms>
  • Labels in one column, values in the next, lined up.
  • A horizontal one puts the pairs in a row.
  • A value can be anything inside the term; a label slot holds a label with markup.
  • Screen readers hear term and definition, through ARIA roles: HTML's own list can't reach across each term's shadow root.
  • Why not a list: a list's item is a bullet row, and its look and role would change by an attribute on its parent.
caption · 1 line 
<ui-image src="deck.png" caption="The deck"></ui-image>
  • With a caption it draws a figure and its caption, so screen readers tie the two.
  • A caption slot holds one with markup.
  • An image without one draws exactly as before.
  • Why not a figure tag: a caption is part of the image, the way a field's label is part of the field.
  • A figure round a table or a video waits until something needs it.

The docs pages had a few tricks of their own: toolbars that fit their titles, screenshots that open full size, boxes that grow, the page contents and the live example. Each lived in the docs' own scripts, so no other page could have it.

Now each is a Spell UI tag or attribute, and the docs pages use those like any page would.

A toolbar that fits its row · 4 lines 
<ui-toolbar shrinkable>
  <ui-item icon="question">Questions <ui-label slot="badge">3</ui-label></ui-item>
  <ui-item>Todos</ui-item>
</ui-toolbar>

Make the row narrower, and it gives way in four steps:

  1. Every title whole, while they fit.
  2. The longest titles are cut first, each ending in "…".
  3. Once a title would be cut under 50px, the whole row shows icons only. An item with no icon shows its title's first letter, and each title becomes its item's tooltip.
  4. Once even an icon button would be under 34px, every item folds into one "…" button, whose menu holds them all. A dot on it says an item inside has a count.
  • A segmented menu doesn't cut its titles: once a choice wouldn't fit, it becomes one button showing the chosen item, opening the same choices.
  • Two tokens set the steps: --ui-menu-title-min (50px) and --ui-menu-item-min (34px).
  • A page can style each step by its state: icons only, overflow, and a segmented menu's dropdown.
  • A count that must stay goes in the item's badge slot; the "…" button's own look in its overflow slot.
  • A shrinkable toolbar folds into its "…" menu instead of scrolling with ‹ ›.
  • Without shrinkable, nothing changes: a toolbar scrolls as before.
 Anything, shown shrunk, then full size · 4 lines 
<ui-zoom max-width="320px" shrink="50%">
  <ui-table>...</ui-table>
</ui-zoom>
<ui-image src="board.png" alt="The board" zoom></ui-image>
  • <ui-zoom> wraps any content and shows it at half size, by default.
    • shrink sets how small.
    • max-width and max-height cut it off.
  • A click shows it full size, over the page; Escape, a click outside or its close button close it.
  • <ui-image zoom> is a button: a click (or Enter) shows the image full size. The zoom loads on that first click.
  • Plain screenshots open full size on any page that loads Spell UI: an <img> shown smaller than it really is, no markup needed.
grow · 1 line 
<ui-textarea grow max-rows="8" placeholder="Tell me more"></ui-textarea>
  • It starts one line tall, and grows a line as the text wraps.
  • At max-rows it stops and scrolls; without it, at a third of the window.
  • It gets shorter again as text goes.
  • The epic pages' text boxes, the review note, the choice pages' answers and the editor Inspector's event code use it now, looking the same as before.
A page's contents, and one live example · 4 lines 
<ui-toc heading="Buttons"></ui-toc>
<ui-example heading="Emphasis" description="A primary button is the page's main action.">
  <ui-button color="primary">Save</ui-button>
</ui-example>
  • <ui-toc> lists the page's sections and examples as links, opens the one in view and follows the scroll. Each section folds, and the reader's folds are kept.
  • <ui-example> shows its markup live, under a heading and description, with a button that shows the same markup as code.
  • They were the docs site's <ui-docs-toc> and <ui-docs-example>. Every page in every repo was rewritten to the new names.
  • Spanish: <es-indice>, <es-ejemplo>.
 Renaming old tags, and drawing a README's examples · 2 lines 
spell ui rename --write docs/      # <ui-docs-toc> becomes <ui-toc>, in markup and CSS
spell readme pictures README.md    # each html example block, drawn light and dark
  • spell ui rename renames whole tags now, as well as attributes: in markup, in CSS selectors and tokens, and in .spell files.
  • A branch cut before the new names gets them when it merges main: the merge runs the rename by itself.
  • GitHub runs no custom elements, so a README can't show a live example. Instead, spell readme pictures draws each html example block headlessly, light and dark, and puts the picture under it.
  • spell readme check fails a picture older than its markup.
  • Renames first, then the tags: every new tag was born in the new words, so nothing was renamed twice; the cost, the first new tag landed after the renames.
  • Appearance, not style. Style is HTML's inline CSS, on every element: the browser would read style="basic" as CSS.
  • Web Awesome uses appearance for the same idea.
  • Heading, not title: title draws the browser's own tooltip over the whole card, so title became tooltip's old name, and header became heading.
  • Selector, not part. Part is the browser's attribute for styling inside a component, and it splits a selector with spaces into words.
  • The old names worked until the epic's end, then stopped. Other branches still wrote them meanwhile: each was told to run the rename.
  • The vocabularies keep each attribute's old names as a record. The rename and the API tables read it; pages don't.
  • Kept as they were: labeled, source and speed (each one idea after all); both panel and section; a field's type.
  • A button keeps its type: type="submit" is how a button submits its form. Dropping it, as asked, would have broken every form.
  • An include keeps page-styles: the docs site draws its header and footer with it. Dropping it needs another way to put a part into a page first.
  • Spanish tag names stay ASCII (es-celda, es-pila). A drawing's Spanish words keep their accents, and its reader maps the two.
  • A plain shrinkable, no fit=: nothing else would share a fit attribute (epic-engine Q29).
  • A toolbar opts in: one that isn't shrinkable scrolls with ‹ › as before; a shrinkable one folds into its "…" menu instead (Q34, Q38).
  • Every item goes into the "…" menu, none stays in the row, and a token sets how small a button may get first (Q35, Owen's ask). The button is "…" unless a page puts its own in the overflow slot (Q36).
  • A segmented menu becomes a dropdown, rather than being left alone or cut: one choice whose labels vanish is a different control (Q31, Owen's own answer).
  • A first letter for an item with no icon, so every row can go to icons only; two items starting alike are told apart by their tooltips (Q32).
  • The item marks its title and counts: a title box round its text, a badge slot for counts that must stay (Q30). Icons only is just :state(icons-only), no extra class (Q33); a dot, not a sum, on the "…" button (Q37).
  • Zoom two ways: a <ui-zoom> that wraps anything, not only images, and zoom on an image (Q22, Owen's own answer).
  • Growing is opt-in, not every textarea's default (Q24). The two "tell me more" boxes moved onto it; the brand composer and the kit's section editor stayed (Q25).
  • Two inspectors, for now: the docs' live view and the editor's Inspector stay apart, a todo to share one (Q26).
  • The Spanish names follow the words already chosen: zoom is ampliacion, the contents indice, the example ejemplo; shrinkable is encogible, grow crece (Q23).
  • Merging main renames old tags by itself, so an older branch can't bring them back (Q27).
  • READMEs get a picture of each example, not a live one: GitHub runs no custom elements (Q28).
  • No drawing surface yet: shapes, a canvas, charts. Maybe it's just SVG and its own tags; that's for later.
  • A page outside the repos still in the old names draws them as if they weren't there.
  • A link on a tag that draws no link of its own (a segment) is a click only: no Tab stop, no middle-click, no link role.
  • A real link is text with a link, or the link tag.
  • Font's highlight, subscript and superscript show only inside text.
  • Table cells span columns, never rows.
  • The new families have no visual-test baselines yet: they need Docker.
  • A table of rows has no static server render yet.
  • Video and audio look like the browser's players, not Spell UI.
  • Web Awesome's flank, split and frame stay CSS classes, until a drawing needs one.
  • Two checks wait for a person with VoiceOver: a table of rows and cells read as a table, and a page's landmarks and Skip to content.
  • Fitting titles is checked in Chromium only. Its steps are CSS style queries, untried in Firefox and Safari, and it has no visual-test baselines yet.
  • The "…" button's "More" is read once: a page that turns Spanish after the menu draws keeps "More".
  • A growing textarea doesn't measure again when only its width changes.
  • <ui-zoom open> set from script keeps no room in the page while it's open.
  • spell ui rename still lists 8 lines it leaves for a person: JSX values it can't see, and a button label that could be either.
  • It still renames the old ui-docs-toc and ui-docs-example until every open branch has merged main.
