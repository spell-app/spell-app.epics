The epic engine used to be one person's: every page said "Owen", and the plans sat in a git repo on one laptop that nothing pushed. Now a team shares them through git, each person is named on what they write, and a teammate on Codex works the same epic as one on Claude Code.

Epic page: epic epic-friend Setting it up, step by step: README-epics.md, at the kit's root Written for: someone adopting epics with a team, or changing how the sharing works Status: built on branch epic-friend, not merged yet Checked: the epic/ folder's tests, two people against a stand-in for GitHub, and Codex's side against stand-ins for its files: no real Codex yet
  • The plans (epic pages, guides, sagas) live in their own git repo beside the code, my-app.epics. It now has a remote on GitHub, my-app.epics, made by the first person's epic init and cloned by everyone else's.
  • Every agent turn ends with a commit of that repo, then a pull and a push. Ids two people both made are renumbered on the way in, so nobody resolves a merge by hand for the common cases.
  • Each machine knows its person by a short name, with no login: your GitHub login unless you pick another. It's stamped on every reply, comment, pick, test run and log line.
  • On a page, your own words say "You", everyone else's their name, and an agent's "Claude (Ana)" or "Codex (Bob)".
  • Comments are shared the moment the turn syncs, answered or not; each person's agent answers theirs.
  • Codex runs the same skills from the same files, and its own end-of-turn hooks; any other agent follows epic guide.
  • Sharing works only with GitHub, unless you make the epic repo by hand.
  • Codex's side has run only against stand-ins: no real Codex session has tried it.

Every step, with what each command printed: README-epics.md. In short:

  • Install GitHub's command and log in: brew install gh, then gh auth login (other systems: https://cli.github.com).
  • From any folder of your project, ONE command: npx spell@next epic init. Until the next spell@next is published, from a clone of Spell: node ~/www/spell/bin/spell.mjs epic init.
  • It installs the epic plugin for Claude Code first, when the machine doesn't have it (once per machine; --no-plugin skips it), and puts epic on your PATH.
  • In a terminal it asks every question first (but the commit), each in yellow, then sums up the answers, the values bold; a pick-one question is a numbered list (arrow keys and Enter, or a number key):
    • "What do you want to be called?", every time, suggesting the name you keep, else your GitHub login (--name Ana)
    • "Which colour should your words be?", a list of Spell UI's colour names nobody has yet, the first marked (--color green)
    • "What should the epic repo be called?", only when it'll make one, suggesting <repo>.epics (--content-repo <name>)
    • "Private or public?", a list of the two, private marked (--public)
  • It makes the repo on GitHub under your account, or the code repo's organization, pushes, and writes its address in .epic/config.json5 as contentRemote.
  • Then each step under a bold heading, the files it wrote in a gray table, a gray line before each slow step (GitHub, a push, the server).
  • It commits the two files it wrote on the base branch, and pushes them, asking first ("Commit and push ... on main?", yes suggested; --no-commit skips it): .epic/config.json5 and .gitignore. A teammate's epic init reads the address from there.
  • It ends by starting the epic server, serving your repo, and says where to see the epics: its address, a link in a terminal, and how to open them in VS Code or Cursor (--no-server skips the server).
  • Add each teammate to the epic repo with write access.
  • --remote <address> uses a repo you made yourself, anywhere git reaches.
  • --no-remote keeps the plans on this machine, as before.
  • Without gh, or logged out, it says how to get it and sets up everything else; run it again once you're logged in.

Clone the code repo, then the same one command, npx spell@next epic init: the output at the top of this page.

  • There's no "join" command: epic init finds the address in the committed config, and clones the plans beside the checkout.
  • It asks their name and their colour, as it asked the first person, and installs the plugin and starts the server for them too.
  • Run it from any folder of the code repo: it finds the repo's main checkout from wherever it runs.
  • Cloning needs plain git, not gh.

  • epic whois Ben: his replies and comments, by epic, and when he was last active.
  • The last line is the agent running epic, which is what an agent's words are stamped with ("How it works", below).

Ben's sync, after Ana and he each added a todo to the same epic page: hers kept T1, his became T2. You rarely type it: every turn's end runs the same thing, epic turn end.

  • Offline, the commits wait, and the next turn pushes them.
  • A clash it can't settle (the same words changed two ways) undoes the rebase, keeps your commits here, and your next session starts by naming the files.
  • A repo whose config names no contentRemote only commits, as before.
  • A comment you leave on a page reaches your teammates at the next sync, answered or not; they can reply on your thread.
  • Your Send hands your agent only your threads. The thread says whose agent took it: "Claude (Ana): thinking…".
  • Only a comment's writer edits, deletes or clears it.
  • Your marks (the pills on items), your Send and who's listening stay on your machine; what your agent makes of them lands in the epic page, which everyone shares.

  • Fifteen skills run in both. Five stay Claude Code's: bg, bedtime, comment, session and title.
  • A Codex session hears your Send while it runs epic inbox wait <epic>. The page says "Your Codex is listening", or, when it isn't, how to start it.
  • Any other agent: epic guide prints the workflow in plain steps, and epic turn end ends each turn. It names itself with SPELL_EPIC_AGENT=gemini, set in its own settings.

A person's words are violet and an agent's terracotta, on every page, comment threads included, until they pick their own. epic init asks each person "Which colour should your words be?", from the colour names nobody on the team has yet, and keeps the answer with the plans, in the epic repo's people/<name>.json5: it reaches everyone with the next sync, and nobody commits anything in the code repo for it. The repo's settings can give anyone their own too, and win:

colors, in .epic/config.json5 · 4 lines 
"colors": {
  "people": { "ana": "green", "bob": "#3b7dd8" },
  "agents": { "codex": "#0f8b8d" }
}
  • People go by the short name epic whoami prints, agents by name.
  • A reply from Bob's Codex takes Codex's colour: the agent wrote the words.
  • A colour is one of Spell UI's names (red, orange, yellow, olive, green, teal, blue, violet, purple, pink, brown, grey, black), drawn from the theme so it suits light and dark, or any CSS colour.
  • Anyone left out keeps the shared one.

A pull request merges a branch once, after review. This merges the plans every turn, so it has to settle the common clashes itself.

Renumbering comes BEFORE the rebase: two people both making the same part file is a conflict that would stop it. Claude Code's end-of-turn hook and Codex's run the same function, epic turn end.

  • Each item and phase body is a file of its own, so edits to different items never meet.
  • Each person's comments are a file beside the page, seo.comments.ana.json5, written only by Ana's machine; a reply on Ben's thread goes in Ana's file too. Reading a page puts every file together.
  • The review inbox, rewritten whole on every change with a 30-second heartbeat, stays on each machine and is never committed.
  • The page server stamps a comment with its machine's person as it saves it, never trusting what the page says.
  • An agent's words carry an attribute of their own, <epic-reply from="Ana" agent="claude">. A person who calls themselves "Claude" stays a person.
  • Which agent, the first that answers:
    • SPELL_EPIC_AGENT, set in an agent's own settings
    • the mark each agent leaves on the commands it runs: Claude Code's CLAUDECODE, Codex's CODEX_THREAD_ID
    • a guess of Claude, which epic whoami owns up to
  • Old pages read as before: a migration marks Claude's old replies with the attribute.
  • Once epic init has installed it, the plugin is the machine's, whichever way it came (npm, or a clone of Spell), so its hooks run in every repo. In a repo epic init never set up they do nothing, and a worktree there is Claude Code's own plain one, in its usual folder.
  • A setting the config leaves out reads as epic init would write it for that repo, never Spell's own values.
The choice Over Because
the plans in their own repo, with a remote a folder inside the code repo each epic's edits would ride its code branch, and every merge into main would merge epic pages too; every worktree would see its own copy, not one page
epic init makes that repo, asking its name the README telling the team to make one Owen: "epic init should set this up for them automatically"
your GitHub login as your short name, git's user.name as your full one git's user.name alone, or a name file you must fill in nothing to set up, and short on a page; the login is looked up once with gh and kept, so no page or hook waits on the network
the name IS the identity; --rename rewrites it everywhere a stable id (git's email) beside the name one value, and a rename command covers the one case an id would
epic whoami and epic whois epic person, the noun-verb rule the Unix command everyone knows; nobody looks it up
one command from npm, npx spell@next epic init, installing the plugin itself the plugin from a clone of Spell; a separate install step, then init, then the server nothing to clone and one thing to remember; the plugin marketplace replaces the plugin step when Spell is published
comments shared through git, one file per person inboxes kept local until a comment is answered a teammate sees your question before it's answered, and can reply; one writer per file means a pull never conflicts there
sync on its own, every turn a sync command people remember to run pages drift apart until someone remembers
renumber this machine's clashing ids after a pull a person's letter in every id (T22a, T22b) ids stay short enough to say in chat; the cost is that an id said before a sync can change, and the log says so
"you" on pages, "person" in code "reviewer" everywhere not everyone who comments is reviewing; "Owen" stays only in quotes and history
an agent attribute on an agent's words telling Claude by the name "Claude", or a role attribute a person may be called Claude; role is the browser's accessibility attribute; agent names any agent, not only Claude
the agent found from the environment, SPELL_EPIC_AGENT for the rest a setting per machine, or per repo one person may use Claude for one task and Codex for the next, in the same repo
Send never wakes Codex; the page says how to Codex's end-of-turn hook waiting for a Send, or a new Codex session from the page a waiting hook leaves the session busy and untypable; a new session needs a terminal opened from the page
the skills themselves run in Codex, one copy a guide only, or the guide plus hooks Owen wanted the skills in this epic; a generated Codex copy of 20 skills was rejected: two to keep honest, and a build step between an edit and trying it
threads take the voice colours, and a colour per person and agent threads left violet violet would mean a person in a reply and Claude in a thread; one meaning per colour
  • GitHub only. epic init makes the epic repo through GitHub's command; on GitLab, Bitbucket or a bare server, make it by hand and pass it as --remote.
  • VS Code or Cursor, tried only on macOS. Cursor runs the same extension and takes VS Code's flags, so the tools run cursor where they'd run code (they tell from the window, or editor in the settings), but only its command line has been tried: its Review tab may need View: Open View..., since Cursor keeps its right side bar for its own agent. Linux and Windows have their own ways in (processes, links, a pasted picture), and epic init installs the extension everywhere, but no person has run them there yet: epics epic-windows and epic-linux will. On Windows a session's window can't be told from its process, so epic session open opens in the last window.
  • Codex untried: its hooks, skills and custom agents ran only against stand-ins for its files, so not seen yet:
    • its /hooks trust screen
    • whether its hooks get CODEX_THREAD_ID
    • Codex listing the linked skills, and a Codex agent following the "In Codex:" lines
  • Send wakes only Claude Code. A Codex session hears it only while it waits.
  • Phase times count Claude only. A phase's "took" time is read from Claude Code's saved sessions, not Codex's yet; session titles and window moves are Claude Code's too.
  • Names don't reach everything. The "thinking…" stub and a one-line status card name no session; a guide's old page-note replies aren't marked; epic whois Ana counts her Claude's replies with hers.
  • The rename stops at authorship. It rewrites a name where it says who wrote something, never in a sentence, and matches regardless of case.
  • A page that isn't split into parts keeps its log as merged: its lines aren't re-sorted.
  • Older checkouts miss new comments. One on code from before shared comments reads only its inbox, not the comments files.
