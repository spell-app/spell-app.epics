IntelliSense for Custom Elements

What VS Code knows about our <ui-*> tags as you type them, in JSX, HTML and CSS; how a program turns it on; and where it stops.

Epic page: epic intellisense Written for: anyone writing <ui-*> tags in JSX, HTML or CSS, or adding a program that does Status: built on branch intellisense, in every repo; not merged yet Checked 2026-10-22: yarn ts clean in all six repos; the plugin run on TypeScript 6's real editor server; the VS Code checks are still to do by hand (Limits)
  • In JSX, every one of Spell UI's 104 <ui-*> tags completes, shows its docs on hover, and is checked: a misspelt attribute or a wrong value is red, in the editor and in yarn ts.
  • Each tag's events are typed, so event.detail is known.
  • In HTML and CSS files, Spell UI's and Spell Brand's tags, custom properties, parts and states complete, in every window the kit is a folder of.
  • A TypeScript plugin in the kit adds what types can't say: slot names, part names, and misspelt dashed attributes. It runs in the editor only.
  • The first run of the exact types caught 21 errors in our own JSX, one of them a real accessibility bug.
  • The plugin only runs when VS Code uses the repo's TypeScript 6. VS Code asks once per window; say yes (The plugin).

One source feeds all of it: each element's vocabulary, the plain-data file that describes its attributes, events, slots, parts and states.

Typing <ui-button in a .tsx file:

  • every attribute the button has completes, then its values: size=" offers the eight sizes, mini to massive
  • hovering an attribute shows its description, its values and its default
  • a misspelt name (sise="large") or a value it doesn't take is an error
  • still allowed: HTML's global attributes (class, id, slot, style ...), and any name with a dash in it (Limits)

How values are typed:

  • a flag: basic, or basic={true}, or the empty text
    • basic={false} removes it
  • a number: {5} or "5"
  • a shared value set (the hues, the sizes): its real list, not plain text
  • rich data (an object, an array, a function) goes to the property, by its plain name; and as prop:options too, until epic solid-17 lands
  • any attribute may also be set as its property, typed the same: prop:value={value()}
generated, shortened · Spell UI's JSX types · 12 lines 
export interface UIButtonAttributes {
  /**
   * Size, `mini` ... `massive`;  `medium` is the default.
   * - takes:  `mini` · `tiny` · `small` · `medium` · `large` · `big` · `huge` · `massive`
   */
  size?: "mini" | "tiny" | "small" | "medium" | "large" | "big" | "huge" | "massive"
  /** `size`, as the DOM element's property. */
  "prop:size"?: "mini" | "tiny" | "small" | "medium" | "large" | "big" | "huge" | "massive"
}

  • In an .html file, <ui- completes Spell UI's and Spell Brand's tags, then their attributes and values, with docs.
  • In a .css file:
    • custom properties complete where you set them, with their default and their tag in the hover: Spell UI's 1,326, the brand's 62
    • ::part() names: Spell UI's 136, the brand's 38
    • :state() names: Spell UI's 103, the brand's 18
  • Parts and states are offered after any selector: VS Code's CSS data can't tie a name to a tag. So each one's docs list the tags that have it.
  • Inside var(--, VS Code completes only the variables the file itself declares: the data helps where you set a property, not where you read it.
  • Both data files are written by each repo's yarn site:data, and turned on by the kit's own VS Code settings, so they work in every epic's window too.

A TypeScript program gets the exact <ui-*> types by importing them once, in any of its files. Its .types.ts file is a good home.

any one file of the program · 1 line 
import type {} from "spell-ui/jsx"
  • Then every <ui-*> tag in that program's JSX is checked.
  • Not through the tsconfig's types list: that finds packages, not a package's files.
  • Type-only: nothing is added at run time.
  • Each tag's types can be imported by name too, for a wrapper's props: UIButtonAttributes (its own attributes), UIMenuJSXAttributes (those plus HTML's).

Who does it today:

  • Spell UI itself, its docs elements and its tests
  • the app, in solid.types.ts
  • Spell Epic, in EpicPage.types.ts
  • the spell compiler's type check of compiled spell (typecheck.ts)

Where the types come from:

  • ElementManifests writes them, one file, as part of yarn site:data in Spell UI, beside the HTML and CSS data and the Custom Elements Manifest.
  • A test fails while the file is stale: run yarn site:data after changing a vocabulary.
  • The file is large, about 23,700 lines, and committed in Spell UI's source.
  • Never edit it by hand.

Every event a tag sends is typed, with its event.detail, in two places.

events, in JSX and plain code · 6 lines 
// JSX:  on- plus the event's name, one prop per event the tag sends
<ui-input on-ui-change={(event) => setName(event.detail.value)} />

// plain code:  the tag's own element knows its events
const input = document.querySelector("ui-input")
input?.addEventListener("ui-change", (event) => event.detail.value)
  • In JSX: on-ui-change, typed per tag.
    • Typed only, for now: Solid calls these props once epic solid-17 lands. Until then, listen with addEventListener() from a ref.
    • The list of props is closed, but a misspelt one has a dash, so only the plugin catches it.
  • In plain code: querySelector("ui-input"), or a JSX ref, gives an element whose addEventListener() completes its events, each detail exact.
    • Its other members (value, open() ...) aren't typed there: cast to the DOM element class for those.
  • On the document, or any other element: every ui-* event name completes, but its detail is unknown.
    • Narrow it, or listen on the tag.
  • A detail's type names Spell UI's real types (close reasons, form changes ...): a name the generator doesn't know makes yarn site:data fail, naming the table to add it to.

A TypeScript language-service plugin in the kit adds what types can't say. It reads the Custom Elements Manifest of each package and its dependencies, so Spell Brand's tags work too.

  • slot=" on a child of a custom tag lists the parent's slots, with their descriptions.
  • part=" in a component's own JSX lists its parts.
  • A misspelt slot, part or dashed attribute gets a yellow warning, with "did you mean" (at most two letters off).
    • Always allowed besides the tag's own: data-*, aria-*, and an on- prop for each event the tag sends.
    • Run over every .tsx file in Spell UI, the app, Spell Epic and Spell Brand: no false alarms.
  • Each program's tsconfig names it, in its plugins list.
tsconfig.json · 1 line 
"plugins": [{ "name": "spell-kit/src/element-tools/ts-plugin/plugin.cjs" }]

The plugin runs only when VS Code uses the repo's TypeScript 6 editor server.

  • tsc and yarn ts run TypeScript 7, which has no editor server that loads plugins; neither does VS Code's TypeScript 7 preview.
  • So the kit's VS Code settings point the editor at TypeScript 6 (installed as @typescript/old) and turn the preview off. That overrides the preview your user settings turn on, in kit windows only.
  • VS Code asks once, "Use Workspace Version": accept it.
  • An epic's window reads these from its window file, not the kit's settings. spell-epic writes them there from the kit's epic settings (windows.settings): after the merge, run epic window init once.
  • Not working? "TypeScript: Open TS Server log", and look for lines starting spell-elements.
the kit's VS Code settings · 3 lines 
"js/ts.tsdk.path": "node_modules/@typescript/old/lib",
"js/ts.tsdk.promptToUseWorkspaceVersion": true,
"js/ts.experimental.useTsgo": false
  • Generated types, not types computed from the vocabularies: only a generated file carries hover docs, since descriptions are values TypeScript can't show; and only it turns a shared value set into its real list.
  • Written by Spell UI's ElementManifests, not a new generator in the kit: the shared value sets are Spell UI's, and the kit may never import Spell UI.
    • ElementManifests already read every vocabulary with its sets resolved.
    • Spell Brand uses the same class, so its JSX types come cheap later.
  • Exact, not open: an attribute a vocabulary doesn't name is an error. The cost was a clean-up of 21 errors:
    • 5 real mistakes in our JSX, such as a settings dialog with no name for screen readers
    • 6 of our own types looser than the values they held, narrowed
    • 3 gaps in the generated types, filled in the generator
    • 1 left as a typed cast, in 3 files (Limits)
    • no vocabulary was missing an attribute
  • Spell UI first: Spell Epic's, Spell Brand's and the app's own tags keep their loose stand-ins, a todo each.
  • Events as on-ui-change: epic solid-17 settled on the dashed prop, so the types follow it. Solid's own onUIChange would listen for uichange.
  • An event map per tag, not one per name: ui-change has a different detail on 18 tags, and other sets send ui-* names too. One global type per name would lie.
  • Flags take the empty text too: our code writes primary="", and Solid 2 sets true as the empty text. Typed boolean only, there'd have been 46 more errors.
  • The plugin loads its TypeScript as it starts, through a tiny CommonJS file and tsx: nothing to build, so it can never be stale.
  • HTML and CSS data from the kit's folder settings, not window files: they're a folder's settings in VS Code, so they already apply in every window the kit is in. Naming them in the window file too would list each tag twice.
  • No docs link in a tag's hover: the site data has no public site address yet.
  • A misspelt dashed name passes tsc: TypeScript never checks a JSX attribute with a dash in it, which is how data-* stays allowed.
    • <ui-button text-alin="x"> passes, where sise="large" is an error.
    • A dashed name the vocabulary does name is still typed: a wrong value is caught.
    • The plugin warns on the name in the editor; yarn ts runs no plugins.
  • Event props don't fire yet: on-ui-change is typed, but Solid calls it only once epic solid-17 lands. Until then, use a ref.
  • 4 typed casts, marked as hacks, in 3 files: a component's own size or colour reads as plain text, so handing it on to a <ui-*> tag needs a cast.
    • The fix: the kit's element types learn a shared set's values, as they know its name today.
  • Tags may show twice in HTML completion, once merged: an epic's window has two kit folders, the worktree and the main checkout, and each names its own copy of the HTML data.
    • Read from VS Code's HTML extension, not seen yet in a window.
    • Ways out: drop the main checkout from epic windows, or name the HTML data in each window file instead.
  • Which children a tag takes isn't checked: no vocabulary says so yet.
  • Spell Epic's and the app's tags have no JSX types and no Custom Elements Manifest, so their slots and parts aren't completed either.
  • Still to check by hand in VS Code: slot completion and warnings, and HTML and CSS completion in an epic window (the epic page's tests).
