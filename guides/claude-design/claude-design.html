Designing with Spell UI

Claude Design (on claude.ai) and Claude in VS Code build pages from Spell's real <ui-*> elements, not look-alikes. This guide says how the pieces fit, how to design in each place, and how a design comes back into spell-app-dev.

Epic page: epic claude-design Written for: Owen, and any Claude session asked to design a page or change a component Status: built, merged into main Checked: 2026-10-05, in a local copy of Claude Design's own runtime (Playwright), and by Owen on claude.ai (see Sources)
  • Spell has a design system on claude.ai, named Spell. It's private: only Owen can open it until he shares it.
  • It's GENERATED from the code:
    • every element's vocabulary file becomes a card, with a README and a live preview
    • the spell-brand theme (the one the docs wear) becomes its colour tokens, tokens.json
    • the brand rules become its README
    • the brand's own <ui-brand-*> elements are cards too, in a Brand group, their examples taken from their docs pages (epic page P11)
  • Its components are ONE classic (non-module) script, bundle.js.
    • Loading it defines every <ui-*> element (the brand's too), in the Spell theme.
    • So a design writes plain markup: <ui-button primary icon="check">Save</ui-button>.
    • No React wrappers, no npm publish.
  • The bundle goes INTO the system as a file: Claude Design can't reach this laptop, so a component change reaches it through one command, /design push, then a reload.
  • A design comes back as a page with /design pull; in VS Code, the same element data gives autocomplete and hover docs for every <ui-*> tag.
  • After changing a component: /design push, then reload the design in Claude Design.
  • To start a design on the Spell system: /design new "<title>".
  • To bring one back: /design pull <design link> [page].
  • To build a page here: /design, or just ask for a page "with Spell UI".

Four pieces, each generated from the one before it, so nothing about an element's shape is written down twice.

The vocabularies One UI<Name>.en.ts per element: attributes and their values, slots, events, parts. yarn site:data gathers them into one file, components.json5. The design system's files spell dev design build writes them into ui's build folder: the README, the colour tokens (tokens.json), the components' types (index.d.ts), a README and preview per family, and the cover. The bundle spell dev design bundle makes one classic script (window.SpellUI), with everything inside it: every Font Awesome Free icon, the code and markdown engines, and the Spell theme. spell dev design check proves it works. The system on claude.ai /design push sends the changed files with Claude's Artifact tool. A shared record, design-system.json, says what's there, so every checkout knows.
  • A Design keeps its own COPY of the system (project/ds/spell/), so a Design made before a push still shows the old bundle until its copy is refreshed.

The system's README says all of this to Claude Design; here's the short form.

  • Load the bundle once, after the board's support.js line: <script src="ds/spell/components/bundle.js">.
  • Write plain markup inside <ui-root>. Never x-import or React: there are no React components.
  • A flag is present or absent (primary); in a board, branch with <sc-if> rather than binding a flag to a hole.
  • Any Font Awesome Free icon name works (icon="wand magic sparkles"); regular ones end in outline.
  • Page typography is opt-in: class="ui-typography" on a container.
  • Clicks run only in a board's Play view (the board filling the window); on the canvas, a click selects.
  • The boards are listed under the canvas's small sidebar icon, upper right.

The first one back: pony.html, Sparkle the Spell pony, pulled from her Design and finished with a 30-line script.

  • VS Code autocompletes <ui-*> tags and their attributes in any HTML file, with hover docs.
    • It reads them from html-custom-data.json, which the repo's VS Code settings load.
    • custom-elements.json beside it is the standard Custom Elements Manifest.
  • /design alone: Claude reads the same README and cards Claude Design reads (built locally by spell dev design build), writes the page, and shows it live in the doc preview.
  • Nothing to sync: the page server serves this checkout's bundle, so a component change shows on reload.
  • Plain markup, no React wrappers (epic page Q10).
    • A design system's bundle may be any single classic script, and custom elements register themselves when it runs.
    • The spike proved it renders on a Design canvas, clicks included.
    • Claude Code's own /design-sync handles React libraries only.
  • The bundle as a file, not npm or localhost.
    • Claude Design loads only a few CDNs and the system's own files.
    • Publishing ui to npm would be a real release step.
  • Generated, not hand-written. The vocabularies already describe every element; generating means a re-sync rewrites the system from the same source, and nothing drifts.
  • A new system, not the older Claude Design project (epic page J7).
    • That project (exported to the brand's spell-design-system/ folder) holds React look-alikes drawn from reference images.
    • Claude Code reaches it only through /design-sync, which Owen starts himself.
  • Emoji names (<ui-emoji>) draw nothing in Claude Design: their data loads lazily, which a design frame blocks.
  • Content loaded from a file (source=) can't load there: write it inline.
  • Some token forms (alpha rgb() with a slash, extra families) haven't been seen in Claude Design's token views yet.
  • A pulled page needs finishing by hand where the board used renderVals().
  • Claude Design's own controls are tiny; nothing here can change them.
  • A Brand card shows its docs page's examples without the page's scripts: an example that needs one (the colour picker's family chips) shows its markup, but its buttons do nothing.
