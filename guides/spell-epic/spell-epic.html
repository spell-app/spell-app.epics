spell-epic: the epic engine, one copy for every repo

 epic --version · from any window, in any worktree 
$ epic --version
epic 8c93afa6e (main) /Users/<you>/www/spell/epic

Every window on the machine answers with that one line: the same commit, the same folder. Change an epic verb there, and every session runs the new code at its next call, with no merge and no worktree 274 commits behind running its own old copy.

spell-epic is the epic tooling as one copy per machine: a Claude Code plugin that every repo and every window runs. In Spell it's the kit's epic/ folder; anywhere else, the spell-epic package from npm, set up by one command.

Written for: anyone changing the epic tools, or setting up a repo to use them Status: built 2026-10-18, as a repo of its own; a folder of the kit's one repo, epic/, since epic repo-split's P20 The epic: Epic Eject, its phases, decisions and hand checks Checked on: one epic run end to end in a repo that has never heard of Spell, 2026-10-17; this page checked against the kit's main, 2026-11-17
  • It's a Claude Code plugin: 20 skills, 13 hooks, and the epic command, with every epic verb in it.
  • It also holds the elements epic pages are drawn with, one epic server for every repo on the machine, and a VS Code extension (the Review tab, the window bridge).
  • A repo says where its epic things are in ONE file, .epic/config.json5, which epic init writes.

The epic system is TOOLING, but it first lived inside spell-app, the PRODUCT repo, so git versioned it per branch like the product's code. Three things went wrong because of that:

problem before now
the lag each worktree ran its own copy of some tools, as old as its branch: one was 274 commits behind every window runs the one copy; an edit is live at the next verb
the duplicate files the main checkout was every worktree window's first folder, so Quick Open and Find showed each file twice a worktree's window holds only the worktree and the epic folder
another repo spell-app's paths written into about 30 places one config file per repo, and epic init to write it

The edge: the one copy is the main checkout's. A change made on a branch reaches the other windows only when it merges into main, which is why an epic's agents merge their work the moment it's done.

In the repo, from any folder of it · 2 lines 
epic init --dry-run              # what it would do
npx spell@next epic init         # the plugin, the config, the epic repo, your name, the epic server

Each step is skipped when it's done already, so it's safe to run twice:

  1. The plugin, installed for Claude Code once per machine (epic plugin install), and the VS Code extension with it.
  2. The config file, valued for THIS repo:
    • the epic folder beside the repo, ../<repo>.epics
    • worktrees beside it too, ../<repo>.worktrees
    • the base branch, from git
    • the command that gets a new worktree ready: asked, the one the README or lock file names suggested
  3. The epic repo, a git repo of its own for the plans: made, or cloned from the team's when the config names one; shared on GitHub or GitLab, private unless you say public.
  4. Your name and colour on the pages.
  5. The config and .gitignore committed on the base branch; where it takes only pull requests, on a branch of their own, with a pull request opened.
  6. The epic server, started, serving the repo.

Then /epic <name> works there as it does in Spell.

The catch: --local sets a repo up on this machine only, with nothing committed, so each teammate runs their own.

Every flag, and what a team shares: README-setup and README-teams.

A git hook lives in each repo, and a branch can change it. This plugin is installed for the MACHINE instead, and loads in place: Claude Code reads a local marketplace's plugin straight from its folder, so an edit to the folder is the plugin.

  • Where the copy is. In Spell, it's the kit's own folder, the plugin epic@spell, which epic plugin install sets up.
    • Installed from npm, its code sits inside the spell package instead, and the engine finds its own files by asking, never by counting folders up from itself (EngineFiles).
  • Bare /epic. A plugin's skills are named after it (/epic:epic), so epic plugin install links each one into your own skills folder as well.
  • Every verb is epic, the epic-page verbs and the ones for windows, worktrees, parked work, sessions, the epic repo and the servers alike, each group a class.
    • No verb loads the Spell compiler: epic worktree list went from 1.3s to 0.5s when that went.
    • In a fresh worktree, before its install, the epic link runs the main checkout's; once the worktree is installed, that hands off to the worktree's own.
  • The config file. Every key is optional, folders are relative to the main checkout, and every worktree reads the main checkout's file; epic config [key] prints what's in force.
    • The hooks act only in a repo that has the file, except the worktree hook, which Claude Code needs everywhere.
    • A repo's generated files, the ones a merge rebuilds instead of merging, are its own list, .epic/generators.json5.
    • Every key, its default and its values: README-config.

epic hub runs ONE page server for every repo that uses the plugin, on port 4848, beside each checkout's own page server.

Starting it · 3 lines 
epic repos add ~/www/my-app --default   # register a repo, served at / too
epic repos list
epic hub ensure                         # start it:  http://127.0.0.1:4848/
address what
/_epic/assets/, /_epic/pack/ the engine's styles, scripts and elements, so a page in any repo draws the same
/r/<repo>/... a registered repo's epic folder
/... the default repo's epic folder too
/api/... the review, details, choices, comments, agents, airplane and links calls
  • Its files are in ~/.spell-epic/: the repo list, its pid file and its log.
  • ensure restarts it when its code or the repo list changed since it started.
  • The kit's page server serves /_epic/ as well, so a page draws on either server.

A worktree inside the repo drags the main checkout into its window. Beside it, a worktree's window holds just the worktree and the epic folder: Quick Open and Find show each file once, and Source Control shows one repo.

  • Every session listed: the worktree hook links each new worktree's saved-session folder to the main checkout's, so Claude Code saves every session in one place, and every window's Claude panel lists them all.
  • Packages first: a worktree beside the repo can't borrow the main checkout's packages, so the hook runs the install before it hands the worktree over, before any window opens.
  • Back in the right folder: every skill enters a worktree with Claude Code's EnterWorktree, never by starting in its folder: only then does Claude Code bring a reopened session back to it. A session-start guard tells a session that comes back elsewhere to go back in.
  • epic worktree says where one is, moves an idle one, and stops its servers before removing one.

Tried by hand first, in a throwaway worktree: each file showed once, and the panel listed every session.

Resuming a session from another window failed: it came back with its history, but worked on the main checkout. The EnterWorktree rule and the guard are the fix.

Each decision is yours (Q) or a judgement call you can review (J), on the epic page.

  • One copy per machine, apart from the pages it makes (Q2). The engine is installed once; each repo's pages stay in its own epic folder.
    • First a repo of its own, beside spell-app, with a fresh history (Q9). Epic repo-split's P20 merged it into the kit as its epic/ folder, with that history: still one copy, the main checkout's, now in the same repo as the code it stands on.
  • Bare /epic kept (Q6): the skills are linked into your own skills folder, not only named after the plugin.
  • One config file per repo, every key optional (Q13), and the hooks quiet in a repo without one (J15), so the plugin is silent everywhere else.
  • Every verb group a class (Q15), as the epic-page verbs already were.
  • Templates in the engine (Q8): a repo adds its own only if it wants one.
  • Worktrees beside the repo, session folders linked (Q3, Q4), picked on a layout page. No Sessions view (J25): the link lists every session.
  • The engine at one address, /_epic/ (J19, J21): a page in any repo draws the same, on either server.
  • The closing line as a hook too (J42): leaving a worktree with a bare ExitWorktree loads no skill, so only a hook reaches that reply in another repo.
  • Reopening from the Claude panel (I3, I8): the panel itself can't be fixed from here, and a hook can't move a session, only tell Claude to.
  • Claude Code facts seen only in part (C3): the plugin loads in place, and its worktree hook worked when run by hand; a worktree made by Claude Code itself, through the installed plugin, is still a hand check.
  • Still Spell-shaped in places: the parts of the engine that assume Spell's layout are listed in README-config, "What's still Spell-shaped".
  • The config file is read by a small reader of its own, not the shared data-file reader (J2).
folder of epic/ what
skills/ the 20 skills: planning and review (epic, epics, details, comment, docs-check, voice, coherence, designer, send), worktrees and sessions (isolate, park, unpark, wait-for, worktrees, session, title, wtf), background and offline (bg, bedtime, airplane)
hooks/, monitors/ the hooks: worktrees made and removed, the behind-main notice, the worktree guard, the server prune, the prompt gate, the closing-line reminder, the end-of-turn window move and commit, the sync notice, the inbox poller, and the wakes after a Send or a restart
bin/epic the epic command, on every session's path while the plugin is on
src/ the code: the <epic-*> elements, the epic tool, the command, the docs tools and their assets, Epic UI's pages, and the window script (epic window)
tests/ its tests, at the same paths as the code
vscode/ the VS Code extension: the Review, Details and Epic Docs tabs, and the window bridge
templates/ every kind of page's starting point: details, review and choice pages, guides, cheatsheets ...
designer/, coherence/, plan-check/ the three reviewer agents, and their rules
voices/ how each kind of page is written: readme, novice, blog, brand
.claude-plugin/, .codex-plugin/ the plugin's manifests, for Claude Code and Codex
