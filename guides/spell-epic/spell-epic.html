spell-epic: the epic engine, outside spell-app

Change an epic verb in spell-epic's folder, and every window on the machine runs the new code at its next call: no merge, no worktree 274 commits behind running its own old copy.

spell-epic is the epic tooling in a repo of its own, beside spell-app: one copy per machine, that every repo and every window can run.

Written for: anyone changing the epic tools, setting up a repo to use them, or switching another repo over to them Status: switched over: spell-app runs spell-epic since 2026-10-18, and carries no copy of its own The epic: Epic Eject, its phases, decisions and hand checks Checked on: spell-epic's own tests (1293) and spell-app's (9200) at the switch-over, 2026-10-18; one epic run end to end in a repo that has never heard of Spell, 2026-10-17
  • The epic tooling lives in spell-epic, a repo beside spell-app at ~/www/spell-app/spell-epic.
  • It's a Claude Code plugin: 17 skills, the hooks, and the epic command with every epic verb in it.
  • It also holds the epics package (the epic pages' elements and tools), one epic server for every repo, and its own VS Code extension.
  • A repo says where its epic things are in ONE file, .epic/config.json5. epic init writes it for a new repo.
  • Worktrees can go beside the repo, in windows that show each file once and still list every session.
  • It ran one epic from start to finish in a throwaway repo that has never heard of Spell, with no spell-app path in any output.
  • spell-app runs spell-epic. Every window's epic verbs, epic skills, hooks, Review tab and epic pages come from the one copy in spell-epic's folder.
  • An epic change goes into spell-epic now, and reaches every window at once.
  • What was done, step by step, and what's where now: Switching spell-app over, below.

The epic system is TOOLING, but it lived inside the PRODUCT repo, so git versioned it per branch like the product code. Three things went wrong because of that.

  • The lag: a feature added in one window reached the others one piece at a time, some only when their branch merged main. One worktree was 274 commits behind.
  • The duplicate files: every worktree window showed main's files too, so Quick Open and Find showed each file twice.
  • /epic couldn't run in another repo: it was tied to spell-app's folders and names.

What spell-epic does about each one, once a repo runs it:

problem before with spell-epic
the lag each worktree ran its own copy of some tools, as old as its branch every window runs the one copy; an edit is live at the next verb
the duplicate files main's checkout was every window's first folder a worktree's window holds only the worktree and the content folder
another repo spell-app's paths written into about 30 places one config file per repo, and epic init to write it

spell-epic's folders, each with one job:

folder what
skills/ the 17 skills: planning (epic, epics, details, comment, docs-check, send), worktrees and sessions (isolate, park, unpark, wait-for, worktrees, session, title, wtf), background and offline (bg, bedtime, airplane)
hooks/ making and removing worktrees, the behind-main notice, the worktree guard, the reminder on leaving a worktree, the prompt gate, and the end-of-turn window move and shared-content commit
bin/epic the epic command, on every session's path while the plugin is on
src/ the epics package, the repo's one package: the <epic-*> elements, the epic tool, the command's code, the docs tools and their assets, Epic UI's pages, and the window script (epic window)
tests/ its tests, at the same paths as the code
scripts/ scripts for working on spell-epic itself, never run by a repo that uses it
vscode/ its VS Code extension: the Review tab, Epic Docs, "Open Epic…", the window bridge and the handoff
templates/ every kind of page's starting point: details, review, choice pages, guides, cheatsheets ...
.claude-plugin/ the plugin's manifest, and a marketplace of one: this folder, so the plugin loads in place
  • Its README says how to install it, how a repo uses it, and how a repo switches over, as spell-app did.
    • Its own checks: types, tests (node and browser), lint, and Claude Code's plugin check.
  • Its git history starts fresh: the first commit names the spell-app commit the files came from, 79c78e58c.
    • To see how a file came to be before that, look in spell-app's history.
  • Staying in spell-app, since they're about spell itself: WWOD, and the fussbudget, design, solid-2, spell-docs and spell-serve skills.

Each repo says where it keeps its epic things in ONE file, .epic/config.json5, in its main checkout.

  • Every key is optional: a key left out takes its default, which is spell-app's layout.
  • Folders are relative to the main checkout, and every worktree reads the main checkout's file.
  • epic config [key] prints what's in force.
  • The hooks act only in a repo that has the file, except the worktree hook, which Claude Code needs everywhere.
  • The engine's data about ONE repo stays in that repo's content folder: the tooling home, the favourites, the list of sagas.
  • A repo's generated files, the ones a merge rebuilds instead of merging, are its own list, .epic/generators.json5.
key what
contentFolder the shared content repo: epics, guides, sagas, pages
baseBranch the branch worktrees start from and merge into
worktreesFolder where NEW worktrees go; may be beside the repo
installCommand what makes a new worktree ready to run
installOnCreate, installTimeout whether the worktree hook runs that install before it hands the worktree over, and for how long
windows the window names, and whether a worktree's window holds only the worktree
linkSessionFolders whether each new worktree's saved-session folder is linked to main's
sharedFolders the content folder's folders every checkout links in at its root
  • Each key's default and its exact values: spell-epic's README, "A repo that uses it".

In the repo's main checkout, with the plugin on:

Setting up a repo · 5 lines 
git init -b main                 # a git repo, with a first commit
epic init --dry-run              # what it would write
epic init                        # .epic/config.json5, the content repo, the links, .gitignore
git add .epic/config.json5 .gitignore && git commit -m "epic init"
epic repo add && epic hub ensure # the epic server serves its pages

What epic init does, each step skipped when it's done, so it's safe to run twice:

  1. Writes the config with every key, each with a comment, valued for THIS repo.
    • The content folder goes beside the repo, ../<repo>.epics, and worktrees in ../<repo>.worktrees.
    • The install command is what the lock file names; none, nothing to install.
  2. Makes the content folder a git repo of its own, with its epics, sagas, guides and pages folders.
  3. Links each folder in at the checkout's root.
  4. Lists the links, and the VS Code window files, in the repo's .gitignore.

Then /epic <name> works there as it does in spell-app.
  • Every epic verb is epic: the epic-page verbs, and window, worktree, park, session, stock, shared and server, under their own headings in epic --help.
  • Every verb runs ONE copy of the code, the called epic's, on the caller's checkout. epic --version says which.
    • So a worktree far behind main no longer runs its own old tools.
  • No verb loads the spell compiler: epic worktree list went from 1.3s to 0.5s.
  • Each verb group is a class, registered by one EpicProgram.
  • spell-app keeps the spell dev spellings, as hidden aliases. That part is on spell-app's branch already, and reaches main when it merges.

epic hub runs ONE page server for every repo that uses spell-epic, on port 4848, beside each checkout's own page server.

Starting it · 3 lines 
epic repo add ~/www/spell-app/spell-app --default   # register a repo, served at / too
epic repo list
epic hub ensure                                      # start it:  http://127.0.0.1:4848/
address what
/_epic/assets/, /_epic/pack/ the engine's styles, scripts and component pack, so a page in any repo draws the same
/r/<repo>/... a registered repo's content folder
/... the default repo's content folder too, so today's addresses keep working
/api/... the review, details, choices, comments, agents, airplane and links calls, for the default repo
  • Its files are in ~/.spell-epic/: the repo list, its pid file and its log.
  • ensure restarts it when its code or the repo list changed since it started.
  • spell-app's own page server serves /_epic/ as well, so a page moved to the new addresses draws on both.
  • A page not moved yet still draws on the epic server, from its old addresses.

Worktrees can move OUT of the repo, so a worktree's window holds just the worktree and the content folder: no main checkout, each file once.

The catch: every part of it is off by default. A repo turns it on in its config.

  • Where: ../spell-app.worktrees/<name>, when the config's worktrees folder points there.
    • Worktrees left in the old place keep working until their /isolate done: every tool reads both places.
    • epic worktree path <name> says where one is; epic worktree move moves an idle one.
  • One window, one checkout: ⎇ <name>, then the content folder. Quick Open and Find show each file once, and Source Control shows one repo.
  • Every session listed: the worktree hook links each new worktree's saved-session folder to main's, so Claude Code saves every session in one place, and every window's Claude panel lists them all.
  • Packages first: a worktree beside the repo can't borrow main's packages, so the hook runs the install before it hands the worktree over, before any window opens.
  • Back in the right folder: every skill enters a worktree with Claude's EnterWorktree, never by starting in its folder.
    • Only then does Claude Code bring a reopened session back to its worktree.
    • A session-start guard tells a session that comes back elsewhere, or starts in a worktree unrecorded, to enter it.
  • The content folder's new name: epic shared rename spell-app.epics renames it, leaving a link at the old name for old paths and running sessions.

Owen tried the layout by hand first, in a throwaway worktree beside the repo:

  1. Explorer and Quick Open show each file once. Yes.
  2. The window's Claude panel lists main's sessions. Yes.
  3. A session started there shows in main's window, saved through the link. Yes.
  4. Resuming it from another window. Failed: it came back with its history, but worked on the main checkout.
    • The EnterWorktree rule and the guard above are the fix.
  5. Entering that worktree from a session in the main checkout, by its path. Yes.

Done for spell-app on 2026-10-18. Every window runs spell-epic, and spell-app carries no copy of it.

  • The engine: spell-epic's folder, one copy for the machine.
    • The plugin is installed for the user, loading in place from that folder.
    • Its 17 skills are linked into Claude's own skills folder, so bare /epic works.
    • The epic on the path is spell-epic's.
  • In each spell-app checkout: a spell-epic link at its root, into the engine.
    • The page server's epic routes, Epic UI's pages and the spell-epic aliases go through it.
    • The old spell dev verbs (plan-doc, window, worktree, shared ...) hand on to epic.
    • spell-app's Claude settings hold no hooks: the plugin's run, once each.
  • VS Code: two extensions side by side.
    • The spell extension: the spell language alone.
    • spell-epic's: the Review tab, Epic Docs, "Open Epic…", the window bridge and the handoff.
  • The pages: in spell-app.epics, beside the repo (a spell-app-dev link left behind).
    • They load the engine's assets from /_epic/, on main's page server and on the epic server.
    • Templates come from spell-epic: the content folder has none of its own.
  • Worktrees: new ones beside the repo, in spell-app.worktrees, their packages installed first.
  • The epic server: epic hub on port 4848, spell-app its default repo.

A repo that ran its own copy of the epic tools takes the same steps, in this order:

  1. Bring spell-epic up to date with any epic changes the repo made to its own copy, and port each.
  2. Install the plugin for the machine, from spell-epic's own marketplace.
  3. Bare /epic: link spell-epic's skills into Claude's skills folder, and remove the repo's own copies.
  4. Take the repo's own hooks out of its Claude settings, or each hook runs twice.
  5. Put spell-epic's epic first on the path.
  6. The epic server: register the repo, and start it.
  7. Move the repo's pages to the engine's addresses, with the migration step, dry run first.
  8. Install spell-epic's VS Code extension.
  9. Remove the content folder's own templates, once the tools read spell-epic's.
  10. Rename the content folder if it should be, dry run first; then epic window init.
  11. New worktrees beside the repo: the worktrees folder, linked session folders and install-first, in its config.
  12. Move the idle worktrees, dry run first. Busy ones move at their /isolate done.
  • The exact commands: spell-epic's README, "Switching a repo over".
  • A repo new to the epic tools needs none of this: epic init (above).

The decisions behind it, each Owen's (Q) or a judgement call he can review (J), on the epic page:

  • A repo of its own, separate from the pages it makes (Q2): the engine is one copy per machine; each repo's pages stay in its own content folder.
  • A fresh git history (Q9): its first commit names the spell-app commit it came from.
  • Spell's packages linked from a spell-app checkout (Q5, J13): the epic pages are drawn with Spell UI and served by Spell's page server. They go to npm at release.
    • Linked from spell-app's main checkout, since epic-eject merged into it.
  • One package, in a standard layout (J14, Owen's A): the epics package is the repo's src/, its tests in tests/ mirroring it, the plugin's parts at the root.
  • Bare /epic kept (Q6): the plugin's skills are also linked into ~/.claude/skills.
  • Every verb group a class (Q15), as the epic-page verbs already were.
  • One config file per repo (Q13), with every key optional and spell-app's layout as the defaults, so spell-app needs no change to keep working.
  • The hooks act only in a repo with that file (J15), so the plugin is quiet everywhere else.
  • Templates move into spell-epic (Q8): a repo adds its own only if it wants one.
  • Worktrees beside the repo, session folders linked (Q3, Q4): Owen picked both on the layout page. No Sessions view (J25): the link lists every session.
  • The engine at one address, /_epic/ (J19, J21): a page in any repo draws the same, on either server.
  • The closing line as a hook too (J42): leaving a worktree with a bare ExitWorktree loads no skill, so only a hook reaches that reply in another repo.
  • Code only, overnight (Q16, Q17): nothing was installed, renamed or moved until Owen's morning steps.
    • spell-app's own copies were frozen meanwhile (J32), and removed at the switch-over.

What's open, each on the epic page:

  • Windows opened before the switch-over (T27, T28): they keep the old Review tab until reloaded, and a moved worktree's window names its old folder until reopened.
  • Reopening from the Claude panel (I3, I8): the panel itself can't be fixed from here, and a hook can't move a session, only tell Claude to.
  • One repo's calls on the epic server (J22, T17): a second repo's pages draw, but their review controls reach the default repo.
  • The skills still name a few of spell-app's own tools (T24): spell app vscode, the WWOD check, the changelog.
  • Claude Code facts seen only in part (C3):
    • seen: the plugin loads in place, and its worktree hook worked when run by hand (V10)

    • epic session list shows a running session twice (I4).
