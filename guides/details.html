Details Pages

Claude runs epic ask show <slug> --wait and ends its turn. A page of tables, code and option cards opens in VS Code's right side bar; Owen picks, types a note, presses Send, and the session wakes up with his answer. That's a details page: for a question that needs a picture, or more answers than the modal holds.

Epic page: epic details Written for: anyone changing /details, its page, its route or its CLI Status: built (epic details) Checked: route and CLI tests, a Playwright click-through, and a real background wait woken by an answer sent from the page
  • The AskUserQuestion modal holds 4 options per question and 4 questions, and no pictures.
  • A DETAILS PAGE has no such limit: tables, real code, diagrams, then option cards to pick from.
  • It needed no VS Code extension change: the "Spell Docs" view already shows any page from the page server (epic window show).
  • The answer comes back through a page server ROUTE MODULE, which writes it beside the page.
  • A waiter Claude left running in the background sees the answer and exits, and that exit wakes the session.
  • What Owen has typed and not sent is a DRAFT, saved beside the page a moment after each change.
    • A reload, or an agent rewriting the page under him, puts it back by id.
    • Text whose question the rewrite removed is kept in a box of its own, never dropped (epic epic-workflow P18).
  • Fits the modal and needs no picture: the modal.
  • Fits the modal, but a picture helps: a picture page, then the modal.
  • Doesn't fit: an answer page. The rules: /details skill.
  • Owen answers in chat instead: Claude stops the waiter.
  • No answer in 8 hours: the waiter exits 2, and says so, once.
  • The page never locks (2026-10-08). A partial answer is fine, and sending again replaces the answer: changes counts up, and changed says what's new.

A details page is written in the epics pack's elements (epic epic-workflow P12). So a question reads as an epic page's does: the same question text, option cards, thumbs-up and colours.

  • It starts from details.html, the tool's own template: context, then one <ui-section> per question, each holding an <epic-ask>.
    • It's never copied by hand: epic ask create fixes the paths for the page's depth.
    • The tool builds the page as elements, never as markup in strings: answerPages.js.
  • The elements, each with its page in Epic UI ("Pages Owen answers on"):
    • <epic-ask>: the question.
      • Each option draws a tick box (round for pick one, square with multiple) and a comment box under it, then an Other box comes last.
      • Its chip takes the epic page's state colours.
    • <epic-text-box>: a box Owen types in, the notes or a section's comment.
    • <epic-send>: Send, in the sticky header, and where the answer stands.
  • No page script any more. The old _assets/details.js, which built the cards from .spell-option markup, is gone; the migration step answer-elements converts a page written before it, once.

  • detailsRoutes.ts is a page server route module, listed in the root package.json (Page server). It answers four calls:
    • POST /api/details/answer -- writes <slug>.answer.json beside the page, atomically, after checking the token and origin (guard.writeCheck)
    • GET /api/details/answer?page= -- the answer, or { answer: null }, for the page on load
    • POST /api/details/draft -- writes <slug>.draft.json, what's typed and not sent (P18), 2s after Owen stops typing and as the page goes away. It wakes nobody, and Send deletes it
    • GET /api/details/draft?page= -- the draft, or { draft: null }: the page puts it back on load when it's newer than the answer
  • page is the page's URL path, mapped to its file through the server's own mounts (StaticHandler.resolve()).
    • So a worktree's page on the main server (/worktrees/<w>/...) works too.
  • It takes only a page in a details/ folder of docs; anything else is a 403.
  • It's listed BEFORE appRoutes.ts, whose /api router ends in a catch-all 404.
  • Why it exists (epic epic-workflow P18, request r4): Owen typed picks and about 10 notes on a page in the browser, and didn't Send.
    • Agents rewrote the page twice that night. It reloaded each time, and everything he hadn't sent was lost.
  • What's kept: every pick, Other, option comment, section comment and the notes, by the id it's under (q1, q1-B, context, notes), with each id's title.
  • Where:
    • <slug>.draft.json beside the page, through the route, 2s after the last change and as the page goes away
    • a copy in the browser (localStorage), at once, for when the page server can't take it
    • Send's line says how it stands: draft saved 06:12, or in orange, draft kept in this browser only: ..., when the server refuses it
  • Coming back: when the page loads (a reload, an agent's rewrite), the newest draft that's newer than the answer goes back into each question and box by id, over what was sent.
    • Send then says "Changes not sent".
    • A rewrite patched in place (no reload) does the same for each question it replaces.
  • Text whose id the rewrite REMOVED shows in a box of its own above the notes, "Kept from before the page changed", under its old title, with a × to drop it.
    • It's sent with the rest, and epic ask answer / wait print it last.
  • Once sent, the draft file and the browser's copy go. A draft older than the answer (another window's) is never put back.
  • The code: AnswerForm decides when, and AnswerDraft holds the rules: what's laid over what, and what's kept.
Command Does
new <slug> [--title] [--epic] a page from the template; sweeps old scratch pages first
show <page> [--wait] in this session's side bar (Chrome outside VS Code); then wait
wait <page> [--timeout 8h] until an answer NEWER than its start; prints it; timeout exits 2
answer <page> the answer already sent
draft <page> what's typed and not sent (exit 1: nothing); read it before rewriting a page Owen may have open
list / sweep [--days 14] every page; delete old scratch ones
  • The tool is details.js, run as epic ask ... from anywhere. It prints paths absolute.
  • Scratch pages live in details/, ignored by version control, and are swept after 14 days.
  • An epic's pages live in its own details/ folder, committed with its epic page.
  • findPages() skips both, so they're on no list page, and docs update doesn't check them.
  • Every page Claude names (a details page, an epic page, any docs page) comes as two links, from epic pages link <page> --hash <id> --show:
    • the title shows it in the side bar
    • (_browser_) opens it in Chrome
    • --show also shows it at once
  • Both go through the page server, GET /api/docs/show (showRoutes.ts), because the Claude panel ignores vscode:// links and opens localhost ones in a VS Code tab.
    • side bar: the server asks the session's VS Code window (its pid is in the link) to show the page
    • in=browser: the server opens Chrome, in front, reusing the page's tab
    • either way, the tab the click opened closes itself, and VS Code comes back to the front
    • refused unless the click started it (Sec-Fetch-Site), so no other site can trigger it
  • --hash: the page lands on that id, below the sticky titles, unfolded. The docs runtime does this for any #id.
  • End the turn and wake on Send, rather than block inside the turn: Owen can still type, and nothing times out in 10 minutes.
  • Page or modal goes by size. The modal is quicker for a small pick, so a page whose question fits the modal is only a picture, and the modal asks.
  • An epic's pages are committed, because the decisions they led to link them: the epic page keeps the picture.
  • Stacked cards with folding details, all ui: Owen's pick (epic page D6).
  • Never locked after Send (2026-10-08; before, it locked, with a Change answer button): partial answers, sent again any time.
  • Short option markup, drawn by elements (a page script before epic epic-workflow P12): a third of the typing per question, and a card fix reaches every page.
  • Every page has a "Where we are" box, questions that stand alone, and plain short lines, because Owen runs 5+ epics at once and reads each page cold.

Every decision and the overnight judgement calls are on the epic page.

  • Route modules load when a page server STARTS. A server running from before the route existed answers 404, and the page says "can't take answers yet".
    • Restart it: spell server stop, then spell dev server ensure.
  • A worktree's page shows from the MAIN checkout's page server, so a worktree's own route changes reach the side bar only after they merge.
  • A page server restart changes the write token: an open page must reload before Send.
  • The same page open in two places (the side bar and Chrome) keeps one draft, and the last to save wins. A reload puts back the newest.
