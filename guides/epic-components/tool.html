The Epic Tool

epic edits an epic page from code, skills and agents: never by hand. How it works on the <epic-*> markup.

Written for: anyone editing an epic page from a skill, an agent or code Status: built TypeScript in tool/ since P7, writing the elements since P8 The rules in full: PLAN-DOC.md (the markup) and plan-doc.md (how to write a doc, every command)
  • The one way to change an epic page: epic <verb> <epic>[#<id>] ..., from any checkout. Every checkout's epics/ is the same shared folder, so it edits the one doc.
  • It runs the CLI checkout's tool code in-process (no child process), on the caller's checkout. Only two commands, open and phase, show the doc through a child open.js.
  • It writes <epic-*> elements through Markup, which reads the same element descriptions the browser does. It never writes layout: only attributes and children.
  • Every edit is checked before it's written (Markup.validate()): an edit that would break the markup is refused, and nothing is written.
  • Writes are locked and atomic, so a background agent and the session never race.
  • Every write first MIGRATES an older doc to today's markup (Migrations, in the tool's migrations/), logged; then each phase's changes attribute says how many plan changes it holds.
    • updates-as-epic-update (2026-10-11): a phase's <epic-updated> lines (and their copies above the phases) become <epic-update at summary> blocks at the end of its description; an UPDATE note before a block moves after it, dated and summed up.
    • A later phase of epic epic-workflow adds epic migrate, to run them on every epic page.
  • A doc still in the OLD ui-* markup is read, never edited: "convert it first". Since the switch (P12) every real doc is in the new markup.

The ones a session uses most, grouped. Every command, with its flags: plan-doc.md, "Commands".

  • Edit through a command wherever one exists: it keeps ids, states, counts, the log and UPDATE markers in step.
  • Never edit the inbox file (<name>.inbox.json): it goes through ReviewInbox and its lock.

A doc is stored SPLIT: a skeleton, plus one body file per bulky block, which the page loads the first time it's opened. So the side bar opens fast, and an edit to one item patches only that item.

  • The skeleton keeps everything a reader or a script needs without a body: every id, title, status and review mark. So links, counts, filters and the docs' home page work with no body loaded.
  • The bodies: epics/<name>/parts/<id>.html, named for their host's id (an Overview part, a phase, an item with details, the log).
  • In the skeleton, the host names its body (source="parts/q7.html"), and carries:
    • part-ids: the ids inside the body, so a link to one loads it first
    • commits
  • The tool reads either shape whole, and writes it back split, each changed file once, atomically. split / join switch a doc by hand.
  • They end in .html, not .htm, since the switch. Every tool that walks the pages skips parts/ folders, so a part is never taken for a page.
  • Claude's status cards always stay in the skeleton, beside the title.

Agents and skills hand the tool HTML (--details, --file, a phase's fields), some of it still in the OLD hand-made shapes.

The way in, IncomingHtml, turns each into its element, so a doc never holds them:

Written Stored as
an option grid, ui-grid.spell-pros-cons (labels A · Title (recommended)) <epic-choices> of <epic-option>, wherever it sits
div.plan-reply <epic-reply>
<p><b>Net effect:</b></p> and its list <epic-net-effect>
ui-accordion.spell-code, .spell-aside <epic-code>, <epic-aside>
ui-message.plan-update <epic-note>
  • Never inside code, or inside an Original Discussion.
  • A question's lead (the prose up to the first element or bold label line) goes in an <epic-question>, unless the HTML has one.
  • A rewrite never drops text: what it replaces moves into <epic-original>, one <epic-version> per version.
  • Write the elements directly in new HTML: the shapes above are only accepted, not wanted.

A markup change ships with a converter run, never a second way to read old markup (Q2). This epic ran it twice, through one command: epic convert.

  • It picks the pass by itself: a doc already in <epic-page> markup gets the second; one with nothing to do is left alone.
  • Each pass ends with a PROOF (ConversionProof): the same ids, the same link targets, the same words, item by item. Anything that moved is listed.
  • It read every generation of old markup still in use: questions born answered, an answer-first layout, option grids, about 600 old #d7 answer cards (kept as ids), docs in one file (they came out split).
  • It's a dry run without --out, and refuses to write into epics/. Only the switch wrote the real docs, after a backup (~/.spell/backups/epics.pre-switch.2026-10-07, then epics.pre-more-components.2026-10-08).
  • The code: convert/, in three classes:
    • Converter
    • Upgrader
    • ConvertRun
