Epic Pages as Components

A plan doc is now made of <epic-*> custom elements. The file says WHAT is there; the elements draw how it looks.

Written for: anyone reading, writing or changing a plan doc, or the tools and skills that edit one Status: built P1-P14 merged into main on 2026-10-08; P15 (Cleanup) and P16 (this guide) land with the branch's /isolate done Plan doc: Epic Pages as Components, branch epic-components, 2026-10-07 to 10-08 Checked on: the branch, 2026-10-09, against the code in packages/epics and its rules, packages/epics/AGENTS.md
  • A plan doc used to carry its own layout: every item was a stack of ui-* widgets and CSS classes, written into the file.
  • Now a doc holds only its DATA and its PROSE.
    • data in attributes: status="decided", dates, the phase
    • prose in children: paragraphs, lists, code, as before
  • The 25 <epic-*> tags draw everything else: id chips, review buttons, option cards, folds, counts, the page header.
  • So a change to the look is a change to one element, and every doc follows at once. No doc is ever rewritten for it.
  • The elements live in a new package, packages/epics, loaded by the page as a component pack .
  • The plan-doc tool (spell dev plan-doc) moved into the same package, as TypeScript. It writes the elements through the same descriptions the browser reads.
  • Every plan doc was converted by a script that proves nothing was lost: the same ids, link targets and words.
  • to read or write a doc's markup: The Epic Elements
  • to edit a doc from code or a skill: The Plan-Doc Tool
  • to review a doc, or answer a review: Reviewing a Plan Doc
  • to pick a colour for anything on a doc page: Plan Doc Colours

Three pieces, one description of each element shared by all three.

the doc epics/<name>/<name>.plan.html and its part files: attributes and prose, nothing drawn. the pack packages/epics/pack/epics.pack.js: the elements, which draw the doc in the browser. the tool spell dev plan-doc, in packages/epics/src/tool: edits the doc in node, and refuses a bad edit.
  • Each element is described ONCE, in packages/epics/src/definitions/: its attributes, their values, and which children it takes.
  • The elements read that description to know their attributes. The tool and the converter read it to write and check markup.

  • The chip (Q1), the review label and the fold are gone from the file: the element draws them.
  • The question text, the option cards and the answer stay the page's own children, so find-in-page and #id links reach them.
  • Chrome is everything the element draws itself. It lives in the element's shadow root, like any Spell UI element's.
  • The prose stays in the page (Q12), so the page's live update patches it in place: an open item stays open, a half-typed note keeps its text.
  • From disk (file://) the skeleton draws, since the pack is a classic script. Bodies in part files need the page server.

The decisions behind the shape, each from the plan doc's questions (Q1 ...). Owen's reasons for components at all (2026-10-06):

  • much easier and faster for Claude to read and write a doc
  • no need to tell other epics' docs to update when the format changes
  • pieces inside a page can be components too (option cards, notes ...)
  • dogfood for <ui-root> and Spell UI
  • Plan docs are shared files; code is per branch. So whose elements draw a doc?
  • main's, always (Q1): every plan-doc link goes to main's page server. A branch previews its own elements on its own server, against copies of the docs.
  • So packages/epics has its own rule (Q3): small fixes straight on main, real changes in a worktree, merged promptly.
  • When an element changes, old docs must still draw.
  • Owen picked "a script rewrites the docs" (Q2) over keeping old versions of each element. So no v="1" on any tag (Q13).
  • A markup change ships with a converter run, never with a second way to read old markup. This epic used it twice: the switch (P12) and the second pass (P14).
  • The elements had to reach the page without a second copy of Solid or Spell UI, and still work from file://.
  • Owen sketched <ui-components source> inside <ui-root> (Q6), in place of the two bundling options offered.
  • Built generic, in Spell UI (P1): any package, any tag prefix. A pack is a classic script calling SpellUI.registerPack(), using the page's own Solid.
  • Packs got their own commands (P2), and pack check runs in each pack's tests, so a stale pack fails yarn review.
  • Only plan docs load the epics pack; other docs pages don't carry it.
  • The tool was packages/docs/tools/plan-doc.js: 4,625 lines of JavaScript, run as a child process.
  • Owen picked moving all of it into packages/epics as TypeScript (Q7) over moving only the element descriptions. One home for everything about plan docs.
  • Done in two steps to keep each reviewable: P7 ported it unchanged (byte-for-byte the same output on all 26 docs), P8 switched it to the elements.
  • Its writes need link targets and formatting from packages/docs, which it may not import. So those moved into a new shared package, packages/assembler (Q15).
  • Since main draws every doc, converting early would show every doc undrawn in every window.
  • Owen picked one switch (Q9): everything, review buttons included, previewed on copies until P12. Then merge into main and convert all 26 docs at once.
  • No in-between step where the old page code decorated the new elements.
  • Questions, judgement calls, caveats, todos, issues and tests are all <epic-item> (Q11).
  • The kind is the id's letter (q7, j3), and the section it sits in.
  • One element to style and test, not six; no kind attribute to keep in step with the id.
  • Each element draws its chrome in its own shadow root, as every Spell UI element does (Q12).
  • The prose stays the page's children, so #d7 links, find-in-page and the live update keep working.
  • A body in a part file loads into the element's own children the first time it opens.
  • Part files became parts/<id>.html, not .htm; every page walker skips parts/.
  • After the switch, about 1,000 hand-shaped blocks were left in the prose: Net effect lists, question text, code and aside accordions, the crumbs.
  • Owen picked "more components" (P14): an element for anything that might reasonably be styled. Then plan-doc.css was deleted.
  • A second conversion pass moved every doc onto them, with the same proof.
  • After a review, Owen couldn't see what Claude took each mark to mean, or when it was done (P13).
  • Now each mark that sets Claude working gets a card on its item: "Claude • Underway" with Claude's reading of the task, then the SAME card "Claude • Done".
  • Picks and todos get a Done card at once, saying what was filed (Q19); approvals get none.
  • Before, orange meant about nine things on a plan doc, and solid meant "not sent" on one button and "done" on another.
  • Settled over four rounds (Q20): each colour means one thing on every doc page, and the fill says how far along a button is.
  • The scheme: Plan Doc Colours.
  • Goals pages kept their own markup (Q8), with the rules they borrowed moved into a small goals.css.
  • Overview sub-sections (o1, o2 ...) take review marks like items (Q14), so the plan's prose can be commented on too.
  • The look was tidied freely while the elements were drawn (Q16): icons and text centred, no gap under a folded section.
  • Two side changes made along the way: shared auto-commits are grouped by folder, one per epic or guide (Q17); Spell UI's site and the brand pages' bundles are built by the page server at startup, no longer committed (Q18).

What doesn't work yet, or works with a catch. Each has an item in the plan doc.

  • A worktree that hasn't merged main draws plan docs blank on its own page server (C2): its code has no <epic-*> elements.
    • The side bar uses main's server, so only a browser tab on that worktree's port shows it.
  • A long-running page server builds bundles only at startup (T20): restart it, or run spell dev bundles build --stale, after a merge.
  • Part bodies need the page server: from file:// a folded item opens empty.
  • An <epic-item> draws unstyled on a page that also has a <ui-item> (I9): both register their stylesheet under the name item, and the first one wins. Plan docs have no <ui-item>; a guide's meta list does.
  • Whether a host's title shows as a browser tooltip over its whole body is still to be checked by hand (T8).
  • One doc (seo) keeps its durable-doc line as a plain paragraph in its Overview, not in the page header (I7).
  • Overview sub-sections take no picks and no Approve: only Make Todo, Revisit and Do Now (J35).
  • A full review round with status cards hasn't been tried by hand yet (V5); nor an Overview sub-section's note box sending a todo or a revisit (V4).
  • Three chip and fold calls from the last night (J85-J87) are waiting for Owen's review.
  • Goals pages aren't on the elements (T1); the brand and skill pages have no packs of their own (T2, T3).
  • <ui-components> isn't a Spell UI library entry yet, and its docs page holds stub text (T7). The epic elements have no Spell UI docs pages.
  • The cli's type check can't follow the tool (T19): its import uses non-literal specifiers until the vocabularies stop reaching $/ui/core.
  • The server's page assembly, and goals pages, could move onto packages/assembler (T4, T5).
  • recent-since on <epic-page> colours nothing now, but the tool still writes it (a REFACTOR: note in PlanReader).
