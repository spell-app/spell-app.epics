The Epic Elements

Every <epic-*> tag a plan doc is made of: what it holds, and what it draws. The examples on this page are live: the real elements, loaded from the epics pack.

Written for: anyone reading or writing a plan doc's markup, or changing an element Status: built 25 tags in packages/epics/components/ The full markup rules: packages/epics/src/tool/PLAN-DOC.md; each element's own description: its <Name>.en.ts
  • An element is a tag that draws itself. Its ATTRIBUTES are data: an item's status, a phase's estimate.
  • Its CHILDREN are prose: paragraphs, lists, code, the doc's own words.
  • What it draws (the chip, the title line, buttons, card headings) is in its shadow root, never in the file. That's its chrome.
  • Each tag is described once, in its vocabulary file (<Name>.en.ts): its attributes, their values, and which children it takes, in which order. The browser and the tool both read it.
  • Dates are WRITTEN 2026-10-08 14:34 (or ISO with an offset) and DRAWN 10/8/26 14:34, by every element but the log's.
  • They load the same pack plan docs do, so they show what main draws today.
  • Click a line to open an item. No review buttons here: those show only on a plan doc under review.

The tags that make a doc's skeleton, outermost first.

ONE tag, <epic-item>, for every kind of item. The kind is its id's letter, and the section it sits in.

Letter Kind Section
q question (an answered one is a decision) #decisions
j judgement call: a choice Claude made without Owen #judgements
c caveat: a limit we accept #caveats
t todo #todos
i issue: a problem found #issues
v test: a check only Owen can do by hand #tests
  • id, title (without the id; with markup, a <span slot="title"> child instead)
  • status: open, decided (an answered question), done (closed), canceled (made moot, struck through)
  • state: its colour, which the tool works out on every edit (attention, open, progress, recent, old): Item states
  • changed, phase, answered
  • review marks: reviewed, deferred, queued, work, working, review-as (how Owen's mark was handled: the record, never drawn)
  • source, part-ids, commits: for a body in a part file

It draws the chevron, the id chip in its state's colour, the review label and the title. Its details fold under the line.

Which colour names /epic <name> -<color> accepts. The colour is the title bar's; the theme stays the window's own.

  • /epic new-thing -purple opens a window with a dark purple title bar
  • 12 names, each a dark title-bar shade
  • an unknown name lists the 12
  • anything goes
  • a light colour makes the white title unreadable

Blocks the prose used to shape by hand, each now an element (P14). Each draws only its label or fold around prose that stays the page's own.

Tag Draws Replaced
epic-net-effect [option] [recommended] "Net effect (A, recommended):" over its list <p><b>Net effect:</b></p><ul> (798 of them)
epic-code title language [open] a folded, highlighted code block; ONE <pre> of text inside ui-accordion.spell-code (133)
epic-aside title a folded "Aside: ..." ui-accordion.spell-aside
epic-note state title a small orange UPDATE note, or a green DONE one, that stays ui-message.plan-update
epic-field label "Where:" (or any label) before its prose bold "Where:", "Step:" lines
epic-question, epic-summary, epic-prompt "Question"; the Overview's lede; a folded "Kickoff prompt" leading prose; p[slot=summary], blockquote[slot=prompt]
  • Each goes wherever prose goes (an item's text, a reply, an option card, a phase field, an Overview sub-section), but epic-question, epic-summary and epic-prompt, which have one place each.
  • Never write the old shapes: the tool turns them into these on the way in anyway.

The elements reach a page as a component pack: a Spell UI feature any package can use (P1), with its own commands (P2).

  • A page names the pack inside its <ui-root>: <ui-components source="…/epics.pack.js">. This page does.
  • The root shows a skeleton for each of the pack's tags, then loads the script. The pack is a CLASSIC script (no import), so it works from file:// too.
  • It calls SpellUI.registerPack({ name, prefix, catalog, define }). Solid and Spell UI's shared code come from SpellUI.packModules: a page never holds two copies.
  • A pack that fails to load doesn't hang the page: the root still gets ready, and the error names the pack's file.
  • Every tag starts with the pack's prefix (epic-): that's how <ui-root> knows whose tag it is.
Command Does
spell dev pack new <name> [--prefix x-] a new pack package (packages/epics was made this way, no fixes by hand)
spell dev pack element <pack> <tag> a new element family in it
spell dev pack build <pack> (yarn pack:build) the catalog, the entry and the script, into pack/
spell dev pack check [<pack>] (yarn pack:check) exits 1 while pack/ is stale; each pack's tests run it

More on packs: Spell UI's <ui-components> and <ui-root> pages, and packages/epics/README.md.

  • Plan docs are drawn by main's pack. Until a change merges, every window shows main's elements: small fixes go straight on main, real changes in a worktree, merged promptly.
  • Elements import Spell UI only from $/ui/core / $/ui/forms, and Solid from solid-js / @solidjs/web. The build fails on anything else, which the page couldn't share.
  • A tag the docs already use needs a converter run if its markup changes: never a second way to read old markup.
