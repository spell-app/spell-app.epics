Custom Elements in Spell

How a <ui-*> element works, from the browser's side and from ours: for anyone about to write or change a Spell UI component, new to custom elements or not.

Epic page: epic spell-element Written for: whoever writes ui components (Owen, agents, contributors); no custom-element knowledge assumed Status: built (epic spell-element, P6; brought up to date in P13) Checked on: branch spell-element, 2026-10-10; every code block is quoted from the file it names

Every Spell UI tag (<ui-button>, <ui-select> ...) is a custom element: a tag of our own, which the browser runs like one of its own.

  • Behind each tag are TWO objects (see Two objects per tag):
    • the DOM element in the page, a DOMElement
    • its component, a UIComponent subclass (UIButton), which holds the state and draws the element's inside
  • A component is a class, with:
    • decorators that say how each member works (@E.state, @E.controlled ...)
    • hooks it fills in (render(), onConnect() ...)
  • A lint guard keeps component files on the decorators: it flags an effect, listener or timer written by hand (6).
  • The components draw with Solid 2; this guide only says what's ours, and links Solid's own rules.
  • New to custom elements: read 2. The platform first, then build the counter in 4.
  • Writing a component today: 5. A real one, then 6. The decorators and 7. The life of an element.
  • The live examples are real elements: click them, and their inspector beside them shows what changed.
  • Solid's rules (no writes while drawing, effects in two halves): Solid 2. The short form for agents: ui's AGENTS.md, "Solid authoring".

What the browser gives every custom element, each in a sentence or two, with where to read more. Spell UI uses all of it.

  • A custom element is a tag with a dash in its name, backed by a class that extends HTMLElement.
  • customElements.define("ui-button", Class) registers it. A tag already in the page before that is an ordinary element until then; defining it upgrades every one of them in place.
  • A tag can be defined only ONCE per page.
  • MDN: Using custom elements, customElements.define()
  • The browser calls methods of the class as things happen: connectedCallback() when the element is added to a page, disconnectedCallback() when it's removed.
  • A move (re-parenting, sorting a list) is a disconnect, then a connect: the object itself stays the same.
  • MDN: Custom element lifecycle callbacks
  • A static observedAttributes list names the attributes the class wants to hear about.
  • The browser then calls attributeChangedCallback(name, old, new) on every change of one, with the TEXT (or null, removed).
  • It reads the list once, when the tag is defined.
  • MDN: Responding to attribute changes
  • A shadow root is a private tree inside the element: the page's CSS and querySelector() don't reach in, and its CSS doesn't leak out. Every Spell UI element draws into one.
  • The element's own children (its light DOM) show where the shadow tree has a <slot>; slot="icon" on a child picks a named slot.
  • part="button" on a shadow node lets a page style it from outside: ui-button::part(button).
  • MDN: Using shadow DOM, <slot>, ::part()
  • A shadow root can share one CSSStyleSheet object with every other root (root.adoptedStyleSheets = [sheet]): 1,000 buttons, one parsed sheet.
  • The runtime makes each component sheet once (UI.styles), and each element adopts it.
  • MDN: ShadowRoot.adoptedStyleSheets
  • attachInternals() hands the class a private object for things only the element itself should set: its default ARIA role and states, its custom states, and its form value.
  • ARIA set there (internals.role = "group") is a DEFAULT: an aria-* attribute the page writes still wins.
  • MDN: ElementInternals
  • internals.states.add("active") puts the element in a state CSS can select: ui-button:state(active).
  • Like :checked for a checkbox: it isn't an attribute, so the page's markup stays as written.
  • MDN: CustomStateSet, :state()
  • A class with static formAssociated = true takes part in its form, as an input does:
    • it submits a value (internals.setFormValue())
    • it has validity
    • it's reset with the form
  • The browser reports form events through more callbacks:
    • formAssociatedCallback()
    • formDisabledCallback()
    • formResetCallback()
    • formStateRestoreCallback()
  • MDN: ElementInternals.setFormValue(), ElementInternals.form
  • An event made with composed: true leaves the shadow root; outside, its target is the element itself (it's retargeted), not the inner node.
  • Spell UI's own events (ui-change ...) are CustomEvents that bubble and are composed.
  • MDN: Event.composed, CustomEvent
  • <template shadowrootmode="open"> in HTML makes a shadow root as the page parses, before any script runs.
  • An element that finds one already there draws into it (see 16. The static server render).
  • MDN: <template shadowrootmode>

Each <ui-button> in a page is TWO objects that point at each other.

  • The <ui-button> in the page is an instance of DOMElement.
    • The same way, an <a> is an HTMLAnchorElement.
  • It's the browser's side:
    • the DOM API callbacks
    • a property per attribute (button.size = "large")
    • the converted values (attributeValues)
    • internals
    • the shadow root (renderRoot)
    • the ready promise
  • Each tag gets its OWN subclass, made by define(), carrying that tag's tagSetup.
  • A family that adds script API names its own subclass (see 12. Patterns).
    • <ui-include>'s is DOMIncludeElement. It adds contentRoot.
  • One instance per element of its UIComponent subclass:
    • built the first time the element connects
    • kept across moves, until domElement.dispose()
  • It holds the state, draws the shadow DOM with render(), and handles the events.
  • It reads every attribute as a getter, converted and typed: this.size, this.toggle.
  • It draws inside a Solid root of its OWN: a Solid app's context doesn't reach in (appContext does that).
  • UIButton.en.ts names EVERYTHING the tag uses: its tag, attributes (and how each converts), events, slots, parts, states and texts.
  • Code never writes those names as strings: it reads them through the vocabulary, so a translated tag (<ie-boton primario>) runs the same code.
  • define() builds an ElementDefinition from it for the actual tag: each attribute's attribute name, property name and canonical key, and the converters.
  • The vocabulary also gives:
    • the tag's topics and aka: how people look for it
    • its skeleton: what <ui-root display="skeleton"> draws

A family's index.ts calls UIButton.define() as it loads. It builds the definition, records it for the page, makes the tag's DOM element class, and hands it to the browser.

static define(this: E.UIComponentClass, tag?: string, dictionary?: E.Dictionary): CustomElementConstructor {
  const definition = new E.ElementDefinition(this.prototype.vocabulary, { tag, dictionary })
  const existing = customElements.get(definition.tag)
  if (existing) return existing
  // record it, make the tag's own DOM element class on `elementSetup.DOMElement`, and define it (DOM API)
  UIComponent.register.call(this, definition)
  const Class = DOMElement.subclassForTag(
    this.prototype.elementSetup.DOMElement,
    UIComponent.tagSetupFor(this, definition)
  )
  customElements.define(definition.tag, Class)
  return Class
}

Some state can be changed from BOTH sides: the page may set it, and a person may change it. @E.controlled is how one member serves both.

  • a dropdown's open
  • a select's value
  • a button's active
  • Reading: the DOM element's property when it has a value (the page set it, as an attribute or a property), else the component's own starting value.
  • Writing: always to the DOM element's PROPERTY, which writes the attribute back. So el.open is always current, as a native <details open>'s is.
  • A person's change: this.requestChange("isOpen", next, () => this.send("ui-open", ...)):
    1. announce() sends the event first
    2. a page that cancels it (a cancelable event) keeps the old value
    3. a page that sets the property itself while handling it wins too (its value stands)
    4. otherwise next is written
  • Handing back: writing undefined to the property gives control back to the component's own value (a form reset does it).
  • isControlledByPage("value"): is it reading the page's value right now? <ui-select> keeps the page's starting value, to restore on a form reset.
  • Why "controlled": React's word for an input whose value the page owns. Here the element works either way, with no mode to pick.
  • Live: the counter and the toggle button both use it.

Shown or hidden is ONE fact about an element, and visible and the platform's hidden are its two names, opposites (epic spell-element, P12).

  • el.visible is always !el.hidden; writing either one sets the fact.
  • The hidden attribute is where it's kept: the browser, CSS and a page before its scripts load all read it.
  • The element writes a visible attribute back only where the page wrote one.
    • So a page that only uses hidden never sees visible appear.
  • Neither written: the family decides, by elementSetup.visible ("shown" by default).
    • A modal, popup, flyout, sidebar, dimmer, loader or transition starts hidden, and writes hidden on itself when it first connects.
    • Removing visible later, with no hidden written, hands the choice back to the family: a modal hides, a message stays shown.
  • Both written in markup and disagreeing: hidden wins (the browser already hid it). After the first connect, the latest write wins.
  • Both animate the same way (animation, below): at once before the element first draws, and wherever motion is off.
  • hidden="until-found" stays the browser's: it counts as hidden, and never animates.
  • Two attributes whose old meaning clashed were renamed: <ui-divider spacer> (Fomantic's hidden divider) and <ui-reveal unclipped> (its visible reveal).

Every element takes animation: how it shows and hides, in the transition's names (fade, fade up, scale ...), or none.

  1. Motion off wins first: the element's own animation="none", none from around it, or the person's reduced-motion setting. An element inside can't turn motion back on.
  2. Then the element's own animation (<ui-modal animation="fly down">).
  3. Then its family's default, elementSetup.animation.
  4. Then fade.
  • none spreads down through a custom property, --ui-motion: none, which shadow roots inherit too.
    • So one attribute turns off a whole page, <ui-root animation="none">; or one CSS line, :root { --ui-motion: none }.
  • The switch stills a family's own CSS motion too (an overlay's transition), as reduced motion does; a loader keeps spinning.
    • That part is a CSS style query: a browser without style queries still runs the family's CSS motion, though showing and hiding stay at once.
  • :state(still) marks an element whose own animation is none; the reset sheet stills everything inside it by that state, so a translated tag works too.
  • UIComponent.animationToRun works it out. <ui-visibility>'s lazy images use it too; <ui-sidebar transition> (over, push, uncover) is something else and keeps its name.
  • readonly: every form control's vocabulary declares it.
    • Its property is readOnly.
    • FormComponent.isReadOnly reads it, and sets :state(readonly).
    • Each control refuses changes its own way: a native readonly, or a change undone.
  • inert: the platform's, unstyled. Overlays set it on what they cover, which has a look of its own (<ui-pushable>'s pusher, under its dimmer).

Every element draws inside an error boundary of its own (Solid's <Errored>, in mount()). When its constructor, render() or an effect throws:

  1. it gets :state(errored)
  2. one console.error names the tag
  3. it sends a cancelable ui-error ({ error }): an app that cancels it keeps the fallback away
  4. domElement.ready resolves, and the broken component is dropped
  5. a microtask later it shows its fallback: a form control's plain native one (elementSetup.Fallback), else a bare <slot>, so its children still show
  • The rest of the page keeps working. Without a net per element, one error would halt Solid for the whole page.
  • A container's net can't catch it instead: each element's Solid root has no parent.

static define(Class: E.UIComponentClass, tag?: string, dictionary?: E.Dictionary): CustomElementConstructor {
  const original = HotDefinitions.original!
  const resolved = new E.ElementDefinition(Class.prototype.vocabulary, { tag, dictionary }).tag
  const known = HotDefinitions.tags.get(resolved)
  if (!known) {
    HotDefinitions.tags.set(resolved, { Class, tag, dictionary })
    return original.call(Class, tag, dictionary)
  }
  const defined = customElements.get(resolved)
  if (!defined || known.Class === Class || known.Class.name !== Class.name)
    return original.call(Class, tag, dictionary)
  HotDefinitions.replace(known.Class, Class)
  return defined
}
