Property Editor

A PROPERTY EDITOR is a form Spell UI draws for you from a description of a thing: a header, folding groups, and a field per property, each with its label, tip, hint, choices and rules.

  • It edits one thing, or many at once, and writes each change at once or holds them all until Save.
  • Its layout can be saved as a plain .editor.html page, tweaked by hand, checked and compiled.
  • The rules a value must follow can be written in spell, on the type itself.

What it is made of, from the field up, and how to use it. Spell UI's own docs page shows each part live: the Property Editor page.

An editor for a theme, laid out by hand. Labels, tips, choices and rules come from the schema; the markup says only how this one form shows them.

A theme's editor, laid out · 12 lines
  • Left empty, the editor draws every property, in the schema's order, each with the control its type calls for.
  • as picks a control; a dotted name reaches into a nested thing.
  • apply="on save" holds the edits until Save; validate="on leave" checks a field as you leave it.

<ui-field> is the shell every field is drawn in, on every Spell UI form, not only the property editor's.

  • A label row:
    • label, which also names the control for screen readers
    • description: a tip behind an "i" icon
    • output: a value at the end of the row, "100%"
    • an actions slot, for small buttons such as Reset
  • The control, then the hint under it.
  • The error: a plain line under the control, shown as you type.
    • Every form's errors look like this now.
  • Each text is an attribute, or a slot of the same name for a rich version.
  • rules: validation rules of its own, added to the form's.
  • readonly: shows the value, which can't be changed.
    • It nests like disabled: on an editor or a group, it reaches every property inside.
  • An inline field puts the label row beside the control.
  • A field that slots its own <label> keeps its old look.
  • The brand pages' <brand-field> is gone: they use <ui-field> and look the same, pixel for pixel.
    • Their compact inspector look is a sheet of the brand's own, inspector.css, reaching only a field in a <ui-panel> on those pages.

The editor reads a SCHEMA: a name, and a list of attributes. It's the vocabulary every Spell UI element is already declared with, grown, not a new shape.

  • What an attribute can now say, all optional, so every existing vocabulary is unchanged:
    • type: text, number, boolean, date, choice, list, thing or data
    • of: a list's item type; attributesOf: a nested thing's attributes
    • label, and tip: what a person reads behind the field's info icon
    • limits: a lowest and highest value (min / max)
    • step: a step size
    • pattern: a regex the value must match
    • ordered: a scale, which may show as a slider or buttons
    • choicesFrom: a named, maybe async, source of choices ("every font")
    • rules, and onChange: named rules run after a write
  • The attribute's own description stays the developers' docs text; the person's text is tip.
  • Where a schema comes from:
    • a tag, schema="ui-button": its vocabulary
    • a name the page registered, schema="Theme"
    • an object, as a property or JSON
  • The readers:
    • Spell UI's PropertySchemas reads a vocabulary, a JSON Schema, or a JSON block's values (guessing their types).
      • It gives a label from a name too: listsStartAt shows as "Lists start at".
    • The spell editor's ClassSchemas reads a running spell class: types, legal values, defaults, list item types, superclasses first.
    • TypeSchemas reads a type from the project's compiled declarations, with nothing running.
  • What stays OUT of the schema is how one form shows it: groups, order, which control, hints, presets. That's the page's (Editor pages).

The editor writes through <ui-form>'s binding, grown, so every form gets these. When a value is written is split in two: each field says when it takes an edit, and the form says when edits land.

Where Says Means
a field, apply immediately every change is taken at once (the default)
a field, apply delayed, delayed 100 after a pause in typing, 300ms unless given; leaving the field takes it at once
a field, apply on leave only when the cursor leaves the field: an id, a version
the form, apply immediately each edit lands in the thing at once (the default)
the form, apply on save edits are held until Save; Cancel drops them
the form, validate
  • immediately
  • on leave
  • on save
 when fields check their values (default on save); was validate-on
  • Save and Cancel:
    • save() checks every field first, then writes the held edits.
    • cancel() drops them, and shows the thing as it is again.
    • Events: ui-saving (cancelable), then ui-saved.
    • And: ui-cancelling (cancelable), then ui-cancelled.
    • While edits are held, the form shows :state(changed).
    • A field still waiting (delayed, on leave) is written first.
  • Many things: give the form a list as its value.
    • A field shows the value they all agree on.
    • Else it's blank and mixed; a text field shows a "Mixed" placeholder.
    • Typing into it sets that property on all of them.
  • A field showing an error checks again as it changes, whatever validate says.
  • A value that fails its rules is never written.
  • "On change" rules run after a write: setting the font family can change the weights offered.

Each new element is built on one Spell UI has, and PASSES THROUGH its words: write collapsed on a group as on a <ui-section>.

Element Is a Its own words
<ui-property-editor> <ui-form>; with a label, it draws a section around its properties
  • schema: what it edits
  • value: a thing, or a list of things
  • source: its layout page; select: part of it
  • readonly
  • events: ui-change
  • events: ui-loading, then ui-loaded
  • methods: save() and the rest
<ui-property-group> <ui-section>, as <ui-panel> is
  • select: its part of the editor's layout page
  • readonly
  • a property in it fails: :state(error) and ui-invalid
  • else: ui-success
  • one holds an edit: :state(changed)
<ui-property> <ui-field>
  • name: may be a dotted path
  • as: which control
  • options: where its choices come from
  • readonly
  • A property makes its own control, by as, else by its type:
    • the usual ones: input, select and six more
    • range: a slider with named steps, for an ordered scale
    • buttons: a button group (radios, for now: Limits)
    • editor: a whole editor, for a property whose value is a thing
  • UI.propertyControls is the page's registry:
    • a control kind for as, and the types it's the default for
    • a choice source for options or a schema's choicesFrom, maybe async
    • an "on change" rule for a schema's onChange
    • a schema, by name
  • The editor's ui-change carries { name, value, things }.
  • It works in a side bar, in a modal with apply="on save", and in a popup.

An editor's layout can live in a page of its own, Card.editor.html: plain markup, which the editor loads as it is, with no build.

  • <ui-property-editor source="Card.editor.html"> loads it.
    • Same origin only: inside the spell editor, it's handed a /spaces/ address.
    • select takes part of it, and a group's select its own part.
    • Events: ui-loading, then ui-loaded.
  • The page holds only the layout: groups, order, controls, hints, presets, each field's apply. Everything else still comes from the schema, so the page stays short.
  • Writing one: the spell editor's file menu, New Property Editor..., after New File.
    • Pick a type: it writes Card.editor.html, listing every property of the type.
    • It never writes over a page: a second one is Card2.editor.html, since a page is for tweaking by hand.
    • The type's schema: the running class, when the editor last ran THIS project; else the project's declarations.
  • Keeping it in step: spell check checks every *.editor.html in a project against its types as they are now.
    • a property the page names that the type dropped
    • a property the type has that the page doesn't place
    • a control that no longer fits (a list of choices became free text)
    • Each problem is a line, path:line:col, like its other errors.
  • spell check --fix mends what it can, and lists each fix.
    • Dropped properties go; new ones land in an "Other" group.
    • It exits 0 when everything was fixed, else 1.
    • With --json, the fix lines go to stderr, so stdout stays the JSON of what's left.
    • It never writes into the frozen test projects.
  • The project's server lists .editor.html files, so the editor shows them, as plain text.
Theme.editor.html, Spell UI's example page · 7 lines

spell compile also turns each editor page into a javascript module, beside the program's own output.

  • Card.editor.html becomes Card.editor.js.
  • That module defines <card-editor>.
  • The page's layout and the type's schema are inlined.
  • It imports Spell UI's property editor, and nothing else: no page loading, no spell parser.
  • The element's value and its methods (save() and the rest) reach the editor inside it.
  • The rules come with the schema: there's no separate rules file.
  • The code: PropertyEditorPages.compile(), proven by a browser test that imports a module and draws it.

Sparkle, on the brand pages' pony page, gallops with her legs now, not by rocking the whole drawing.

  • Each leg is its own group, turning at its hip.
    • The back and front pairs are half a stride apart, each pair's far leg a little behind.
    • Her body bobs once a stride.
  • Back to front: the far legs, the near legs, then her body over the tops of all four.
    • The far legs are a shade darker, and she has hooves.
  • Her settings are a property editor on her page: name, galloping, gallop speed, mane colour, wizard hat.
    • Speed is a slider, 1 to 10, shown as 4 / 10: her stride is 2 / (speed + 1) seconds.
    • Her buttons and the editor change one object, so each shows what the other did.
    • Her drawing stays in sight as the settings scroll.
  • spell pony --gallop: her legs gallop in place in a terminal for 6 strides, then she stands.
    • No bob there: it would break the speech bubble's pointer.
    • Piped, it prints one stride's four frames.

A spell type can say what a property's value MUST be, not only what kind it is. Written once on the type, a rule is checked everywhere the type is edited or set.

Card.spell · rules in all three places · 8 lines
  • A line of its own: - its title must not be empty.
    • The property must be declared above it, or the line warns and the declarations leave it out.
  • On the property's own line: - it has a title as text, which must not be empty.
  • Indented under the property's line: - it must not be empty.
  • Or as a kind: as a url and as an email are text that brings its rule with it.

After must, one of nine:

  • not be empty
  • match "<pattern>": the text in quotes is read exactly as typed, so [a-z] is a set of letters
  • be at least N letters long, be at most N letters long
  • be between A and B
  • be at least N, be at most N
  • be an email, be a url

Then, if you like, its own message: with suggestion "..." or saying "...". Without one, a form says the rule with the label it shows: "Name must have a value".

  • Each rule compiles to the rule object Spell UI's form checks read: { type: "minLength", value: "3", prompt: "..." }.
    • javascript: declareProp("title", { type: "text", rules: [...] }), or Card.declareRules() for a line of its own
    • Python: prop(type="text", rules=[...]) and Card.declare_rules()
  • The property editor: the project's declarations record each property's rules, so the spell editor checks them with nothing running; a running class's schema has them too.
  • VS Code: the type's JSON Schema gets the matching keywords, such as minLength.
  • The running program: a value that breaks a rule is still set, and the console warns, in the same words in javascript and Python.
    • title must not be empty, got:
    • or its own message: version: Write it like 1.2.3, got: 1.x
  • The declarations' version stays 0.8.0: rules is a new optional field, and older readers ignore it.
  • Parser speed is unchanged: 129 ms on average, with this change and without.
