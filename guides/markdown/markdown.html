Markdown on the parser

@spell-app/markdown (MD): GitHub-flavoured markdown on the generic parser, the second language on it after spell. How it's built, where it plugs in, and what it costs.

Written for: anyone changing spell-lang/src/markdown, or deciding whether it replaces marked Status: built (branch markdown, merged into main) Checked on: branch markdown, 2026-10-04, with the GFM spec suite and the experiments in Sources Epic page: Markdown; the rulex changes it drove: rulex
  • Markdown in, the parser's markup (P.Markup) out.
    • As plain HTML,
    • or with Spell UI's elements: MD.render(text, { ui: true }).
  • Passes every GFM spec example (670/670), with GitHub's extensions on: tables, task lists, strikethrough, autolinks, the tag filter, and alerts (> [!NOTE]).
  • Part rulex, part hand-written.
    • Each kind of line is a rulex rule.
    • The container stack and the inline pass (emphasis, links) are hand-written ports of commonmark.js 0.29.
    • Why: rulex can't say "the open containers" or "pair these delimiters".
  • Fast enough to re-render on every keystroke.
    • 1.8× marked's time over the repo's 172 .md files (101 ms vs 56 ms).
    • 2.2 ms for the biggest (32 kB).
  • Too big to replace marked everywhere yet.
    • The browser bundle is 59 kB gzipped (88 kB before its bundle-time cuts), vs marked's 14 kB.
    • DOMPurify now loads only for sanitized.
    • So <ui-markdown> keeps marked, editable or not. Only spell's own <spell-markdown> loads this package (MD).
  • In use: the app's docstrings (<Markdown>), the LSP's colouring of markdown in comments, and <spell-markdown> (spell-app's app package, since epic repo-split P2).
  • Slim the bundle (HTML entities, lodash, AST.ts: epic page I6), then pages could write <spell-markdown> where they write <ui-markdown> today. Spell UI itself keeps marked: it holds nothing of spell since epic repo-split P2.

spell-lang/src/markdown depends only on spell-lang/parser and spell-kit/util. Its shape follows commonmark: blocks first, then inlines inside each leaf block.

MarkdownTokenizer Words, one symbol per other character, whitespace riding on the token before it, so rulex's spacing sees it. lineRules 8 line kinds in rulex: thematic break, ATX heading, fence, setext underline, list markers, table delimiter row ... BlockScanner The open-container stack, lazy continuation, list tightness, GFM tables. A port of commonmark.js 0.29's blocks. InlineParser Delimiter and bracket stacks, references, entities, raw HTML. A port of commonmark.js 0.29's inlines. render Block and inline trees to P.Markup; GitHub heading slugs, the ui-* mapping, alerts, tasks.
  • Rulex says what a line IS: each line kind is a rule, asked with lineRules.matchWhole(tokens, "atx_heading").
    • The scanner reads columns, levels and info strings from the raw text: they're about characters, not tokens.
    • Cheap one-character guards (LINE_GUARDS, a regex per kind) skip a rule that can't match: they took the block phase from 342 ms to 50 ms over the repo's files.
  • Hand-written: the container stack (block quotes and list items nest, and continue lazily) and emphasis (* / _ runs pair by the left- / right-flanking rules). Neither is a grammar a rule can say.
  • The inline pass is a straight port, not rulex: most of it is "any token but X" scanning.
spell-lang/src/markdown/blocks/lineRules.ts (excerpt) · 14 lines 
/** Three or more of one of `-`, `*`, `_`, spaced or not. */
class thematic_break extends P.Sequence {}
lineRules.addRule(thematic_break, { syntax: "(- {3,}|\\* {3,}|_ {3,})" })

/** A run of 1-6 `#`, then nothing, or a space and anything. */
class atx_heading extends P.Sequence {}
lineRules.addRule(atx_heading, { syntax: "#{1,6}" })
lineRules.addRule(atx_heading, { syntax: "#{1,6}{spaces}{any}*" })

/** A run of 3+ backticks or tildes, then any info string. */
class fence_open extends P.Sequence {}
lineRules.addRule(fence_open, { syntax: "(`{3,}|~{3,})" })
lineRules.addRule(fence_open, { syntax: "(`{3,}|~{3,}) {any}+" })
  • MD.toHTML(text, options): plain HTML, as the spec writes it.
  • MD.toMarkup(text, options): the P.Markup tree.
  • MD.render(text, options): the markup, the HTML and the headings, together.
    • Returns { markup, html, headings }.
    • Its options: ui, headingIds, headingOffset, breaks, autolinks, tagfilter.
    • headingIds gives headings GitHub's slugs.
  • Raw HTML passes through; the caller sanitizes (<ui-markdown> uses DOMPurify only with sanitized, epic page Q31).

  • Markdown.tsx draws docstrings with MD (marked is gone from app).
  • It imports spell-lang/markdown LAZILY, showing plain text meanwhile (an async memo and <Loading>).
    • Why: the runner and <spell-app> show docstrings too.
    • A static import would put the parser in every runner bundle.
  • The language server (SpellLanguageService) colours markdown inside comments.
    • Its semantic tokens have four new modifiers: bold, italic, link, strikethrough.
    • They come from the inline source positions MD reports.
  • Every comment, not only docstrings: telling them apart needs the parse, and spell's comments are markdown-styled anyway.
  • The VS Code extension declares and styles the modifiers; it needs spell app vscode from main after the merge (a worktree build would bake in the worktree's path).
  • Checks in docstrings (broken #heading links, unknown identifiers): a todo.
  • Spell UI holds nothing of spell since epic repo-split P2 (2026-10-20).
    • <ui-markdown editable>'s Write / Preview tabs preview with marked, as plain <ui-markdown> draws.
    • Before, Spell UI bundled this package into md.bundle.js (yarn gen:markdown) and previewed with it.
  • Spell's engine previews in <spell-markdown editable>: spell-markdown, in spell-app's app package, a page's spell-markdown.js.
    • It extends <ui-markdown>, drawing with MDEngine instead of marked.
    • MDEngine loads on the first render, in its own lazy chunk.
    • It draws with Spell UI's ui-* elements; with sanitized, DOMPurify keeps those tags.
    • On a docs page it extends the page's own <ui-markdown>: the docs bundle shares the family with it (SpellUI.packModules, epic epic-engine P7).
  • Each preview renders the whole text (~2 ms), then swaps only the top-level blocks whose markup changed.
    • So unchanged code blocks aren't re-highlighted.
    • No incremental parser: it would buy ~2 ms for a lot of complexity (lazy continuation, document-global references).
  • Plain <ui-markdown> still uses marked: see the bundle size below.
  • All 670 examples of cmark-gfm's spec.txt pass, vendored as gfm-spec.json (yarn spec:update <spec.txt>).
  • spec.test.ts pins the pass count per section in a snapshot: a regression fails, a gain updates it. The tag filter and extended autolinks are per-example options, as the spec tests them.
  • yarn tsx scripts/spec-report.mts [section…] (in spell-lang/src/markdown) prints the failures of a section.
