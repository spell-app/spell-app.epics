Targets and Writers

How spell compiles one program for several destinations. A target is where the code goes (js/solid, ts/solid); a writer is the class that walks the spell tree and writes that target's code.

Written for: a developer who knows the repo, about to change what the compiler writes, add a target, or read a spell tree Status: built on branch output-targets, epic Output Targets (P1-P8) Checked on: branch output-targets, 2026-10-06, against the code, the fixtures' snapshots, and spell parse --tree run for the examples (see Sources)
  • Spell's middle is ONE tree: syntaxes (English today) on the way in, targets on the way out. N syntaxes plus M targets, never N × M.
  • Two targets today:
    • js/solid: always compiled, since the editor, the runners and spell run run it
    • ts/solid: the same code with types, checked by tsc; the app never runs it
  • A writer is a class with one method per tree class, found by the class's NAME. P.JSWriter writes JavaScript; P.TSWriter extends it through a few hooks; P.TreeWriter writes boxes for a diagram.
  • The tree says what a program MEANS: 14 operators as meanings (equals, not ==), plain text values, Self and Nothing. Names are still spelled for JavaScript (see Limits).
  • A project's declarations live in <Project>.declarations.json beside its output: the compiled JavaScript is just code.
  • Any line's tree can be drawn: <ui-tree-diagram>, spell parse --tree, the app's Spell Tree pane, VS Code's "Show Tree for This Line".
  • Proven by the fixture snapshots (JavaScript, TypeScript, and what tsc says about it) and the CORE CONTRACT: every test program prints the same on both targets. Solitaire as TypeScript still has 35 tsc errors (105 before the typed writer), nearly all from @spell/core's loose types.
  • A writer class, an entry in SP.TARGETS, a line in the contract test, and a core if the language is new: 8. Adding a target.

A target is a LANGUAGE / RUNTIME pair: js/solid is JavaScript running on @spell/core (Solid). Each target has a writer, a file it writes, and what its runtime can do.

Read left to right. Everything left of the tree is about how spell is WRITTEN; everything right of it is about where it RUNS. The tree is the only thing both sides share.

/** A target spell compiles to -- see `TARGETS`. */
export type Target = {
  /** Its name, LANGUAGE/RUNTIME, e.g. `js/solid`. */
  name: string
  /** Writes its code. */
  writer: P.Writer
  /** End of its compiled output file's name, e.g. `.compiled.js`. */
  suffix: string
  /** What its runtime can do. */
  can: TargetAbilities
}

/** What a target's runtime can do -- checked while compiling, so a project asks only what its targets give. */
export type TargetAbilities = {
  /** Draw a UI:  `dom` into the page, `html` as text (e.g. server pages), or not at all. */
  draw: "dom" | "html" | false
}

/** Every target, by name. */
export const TARGETS: Record<string, Target> = {
  "js/solid": { name: "js/solid", writer: P.JSWriter.instance, suffix: ".compiled.js", can: { draw: "dom" } },
  // the same code and runtime, typed:  checked by `tsc`, never run
  "ts/solid": { name: "ts/solid", writer: P.TSWriter.instance, suffix: ".compiled.ts", can: { draw: "dom" } }
}

  • spell compile <project> --target <name> compiles to that one, this run only, instead of the list. js/solid is still compiled with it.
  • --stdout prints the asked-for target's output (else js/solid's) and writes nothing.

Every writer lives in packages/parser/src/writers/, beside the tree it writes (packages/parser/src/ast/). P.Writer<Output> is the base: a target's writer outputs a string, TreeWriter a box.

P.Writer The base: finds a node's method by its class name, and knows nothing about any language. P.JSWriter JavaScript: the js/solid writer, and what ASTNode.compile() calls. P.TSWriter A JSWriter that adds types: overrides a few hooks and three node kinds. P.TreeWriter Not a target: writes each node as a box for <ui-tree-diagram> (see 6).

Before this epic, every tree class wrote its own JavaScript, twice: compile() for the text, renderChildren() for the AST viewer's coloured copy. Now a node is data, and one method per class, in one writer, writes it.

  • A writer finds its method for a node by the node's CLASS NAME: ASTIfStatement(node) writes an ASTIfStatement.
  • No method of its own: the nearest base class's writes it, e.g. ASTCoreMethodInvocation by ASTScopedMethodInvocation(node). None at all: write() throws, unless the writer has ASTNode(node), the root of every chain (TreeWriter does).
  • Each class's method is looked up once, then remembered.
  • Because it goes by name, EVERY build must keep class names (keepNames; rule names already needed it). packages/app/src/build.test.ts pins that, and packages/parser/src/writers/JSWriter.test.ts checks every tree class finds a method.
  • Write a child with this.write(child), NEVER child.compile(): compile() is always JSWriter.instance.write(this), so a subclass's overrides would never reach the child.
Writer.ts (excerpt, docs left out) · 27 lines 
write(node: P.ASTNode): Output {
  return this.methodFor(node, "").call(this, node)
}

writeAsMember(member: P.ASTClassMember): Output {
  return this.methodFor(member, "AsMember").call(this, member)
}

protected methodFor(node: P.ASTNode, suffix: "" | "AsMember"): (node: P.ASTNode) => Output {
  const key = `${node.nodeType}${suffix}`
  let method = this.methods.get(key)
  if (method) return method
  for (let type = node.constructor; type && type !== Object; type = Object.getPrototypeOf(type)) {
    const found = (this as unknown as Record<string, unknown>)[`${type.name}${suffix}`]
    if (typeof found === "function") {
      method = found as (node: P.ASTNode) => Output
      break
    }
  }
  if (!method) {
    throw new TypeError(
      `${this.constructor.name}.write():  no \`${key}()\` method writes a ${node.nodeType}, nor one for any class it extends`
    )
  }
  this.methods.set(key, method)
  return method
}
  • A class member is written two ways: INSIDE its class's body, or patched onto its class from outside.
  • writeAsMember(member) calls <class>AsMember(node), e.g. ASTReactivePropertyAsMember writes get rank() {…} / set rank(value) {…} in the class body.
  • Plain write() patches it on from outside: Card.prototype.play = function () {…}, or Object.defineProperty(Card.prototype, 'pile', {…}) for a property.
  • Members from every file of a project are gathered into their class first (SP.hoistClassMembers(), in SpellProject.combineCompiled()): Card.move_to_$pile from Pile.spell goes in class Card.
  • packages/parser/src/writers/JSWriter.ts: every compile() method the tree classes had (53 of them, plus the member variants), moved here with byte-identical output.
  • list(), args(), array() write lists of nodes; P.jsText (packages/parser/src/writers/jsText.ts, once stringifyAST.ts) is plain text helpers: InParens, Block, inQuotes() …
  • JSWriter.OPERATORS spells each operator's meaning (see 4).
  • JSWriter.instance is the one ASTNode.compile() and js/solid use.

And three node kinds of its own:

  • ASTAssignmentStatement: a new variable, typed when spell knows its datatype.
  • ASTReactiveProperty, ASTPropertyDefinition: patched on from outside, so an interface merged with the class comes first.
  • typeFor(datatype) turns spell's datatype into TypeScript: text and character → string, number and integer → number, choice → boolean, date → Date, nothing → undefined, thing → Thing, app → App; a project's own type (Card) as is.
  • Parameters: every one typed. Spell doesn't know: any /* spell: type unknown */, since TypeScript needs something there.
  • Reactive properties: from their check: { type: 'number' } → number, { oneOf: Card.Suits } → (typeof Card.Suits)[number].
  • New variables: typed when spell knows (let count: number = 0). Set from a spellCore call, which returns unknown: as Card when spell knows, else the marker. Anything else left bare, so TypeScript works it out (let it = new Card(…)).
  • Lists: any /* spell: list */. @spell/core's List doesn't say what it holds, and spell sets properties on lists, which a List can't have.
  • Every gap is greppable: Solitaire has 56 spell: type unknown markers, FizzBuzz 1 (its loop variable).

Moving the writing out of the tree classes wasn't enough: some JavaScript was decided BEFORE the tree existed, in the rules. Now the tree holds the meaning, and the writer decides the spelling.

what before in the tree now JSWriter writes
operators the JavaScript, from the rule: getOutputOperator(), or "===" written by the rule itself a meaning, P.ASTOperator: equals, and … ==, && … (JSWriter.OPERATORS)
text values already quoted: `"${tagName}"` ASTStringLiteral: value the plain text, escapes undone, plus its quote the source's own spelling (raw), else the value in its quote
the thing a method runs on ASTThisLiteral ASTSelfLiteral this
spell's nothing ASTUndefinedLiteral ASTNothingLiteral undefined
JSX that didn't parse ASTNullLiteral ASTMissingExpression, beside the error saying why null
names, constants, enumeration values is_a_$suit, 'up', "clubs" unchanged: still JavaScript, in scope records as is (see Limits)
  • Rules say what an operator MEANS with getOperator() (was getOutputOperator(), which returned JavaScript). Its default throws, so a new operator rule must say.
  • equals is spell's forgiving is ("2" is 2); exactly equals is is exactly.
  • plus adds numbers or joins text: a writer can tell which from the two sides' datatypes.
meaning JavaScript meaning JavaScript
and && less than <
or || greater than >
equals == at most <=
not equals != at least >=
exactly equals === plus / minus + / -
not exactly equals !== times / divided by * / /
  • quote set (", ' or a back tick): a text VALUE. A writer quotes it its own way, or writes raw, how the spell source spelled it.
  • quote unset: a FRAGMENT of output, written as is, e.g. inside an ASTQuotedExpression, which adds the quotes itself.
  • Converted: spell's text literals, JSX text, attribute text and tag names, test messages, expect / echo strings, headings, a list's instanceType.

  • version (from project.json, when it has one), spellVersion, provides: what it exports.
  • statements: what each declaring statement added to scope.
  • codeLines: the line (counted from 0) of .compiled.js where each statement's code starts.
  • While compiling, each declaring statement still gets a marker above its code, /*! SPELL: DECLARES {…} */ (commentFor()). It's never written to disk.
  • SpellDeclarations.split() takes the markers out of the compiled text: the code is just code, and each marker's object (read with JSON5) goes into statements, with its line in codeLines.
  • Made from js/solid's output only: the file is the same for every target, and its codeLines point into .compiled.js.
  • Importing: SpellProject.declarationsOf(), fresh each time. A project compiled before the file existed still works: SpellDeclarations.fromComments() reads its .compiled.js's old comments.
  • The Type Explorer (packages/lsp/src/ScopesSource.ts) finds a declaration's code by codeLines; it falls back to scanning for markers.
  • The runner fetches declarations lazily, only when you open one's details: from the server (/api/projects/declarations/<id>), beside a src= app's .compiled.js, or pushed by <spell-editor>.
  • Scope packs (.scopes.js) didn't change.

packages/parser/src/writers/TreeWriter.ts: labels in spell's words.

  • Operators: their meaning (divided by, equals).
  • Literals: Number 30, Text "fizzbuzz", Choice true, Nothing, Self.
  • Calls: Call name; a spellCore call is Core name; printing is Print.
  • Names: Variable number, Type Card, Property rank.
  • Statements: If, Otherwise if, Otherwise, Set, Return, Method name.
  • Anything else: ASTNode(node), its class name in words (ASTTryCatchBlock → Try catch block), and a child box per field holding tree.
  • Left out, their contents drawn in their place: parentheses, a call's argument list, a block's braces. TreeWriter.treeOf() gives nothing for a blank line.
  • Slots: the tree's field names (condition, statements, lhs).
  • Second line: the node's datatype, else its match's; NOT for operators, whose match is only their suffix (+ 2). Hover text: the spell it came from.

packages/ui/src/components/ui-tree-diagram/; its Spell UI docs page: ui/components/ui-tree-diagram.html.

  • Data: { label, detail?, slot?, title?, children? } per box (TreeDiagramNode), set as the tree property, a tree='{…}' attribute, or a <script type="application/json"> child for static pages.
  • Draws top-down, the root accented, the datatype as a muted second line, light and dark. Redraws only when tree is set to a NEW object.
  • Slot labels sit ON their line, at its midpoint, the line broken under them: spaced so no label overlaps another label or line.

 PyWriter.ts (sketch) · 30 lines 
export class PyWriter extends P.Writer {
  ASTIfStatement(node: P.ASTIfStatement): string {
    return `if ${this.write(node.condition)}:${this.indented(node.statements)}`
  }

  ASTElseIfStatement(node: P.ASTElseIfStatement): string {
    return `elif ${this.write(node.condition)}:${this.indented(node.statements)}`
  }

  /** `spellCore` is `core`, from `spell_core`. */
  ASTSpellCoreExpression(node: P.ASTSpellCoreExpression): string {
    return "core"
  }

  /** `spellCore.getRange(...)` => `core.get_range(...)`:  Python's names. */
  ASTScopedMethodInvocation(node: P.ASTScopedMethodInvocation): string {
    return `${this.write(node.thing)}.${snakeCase(node.methodName)}${this.write(node.args)}`
  }

  /**
   * An inline method (`node.inline`) with a one-expression body stays a `lambda`;  anything longer is lifted
   * into a nested `def` just before the statement that uses it, named for what it does, e.g. `each_number`.
   */
  ASTMethodDefinition(node: P.ASTMethodDefinition): string {
    if (!node.inline) return `def ${node.methodName}${this.params(node)}:${this.indented(node.body)}`
    if (isOneExpression(node.body)) return `lambda ${this.paramNames(node)}: ${this.write(node.body)}`
    const name = this.names.fresh(node)
    this.before(`def ${name}${this.params(node)}:${this.indented(node.body)}`)
    return name
  }
}
  • The node classes are real (packages/parser/src/ast/AST.ts); the helpers (params(), paramNames(), indented(), before(), names, snakeCase(), isOneExpression()) don't exist yet.

From the plan doc's questions (Q) and judgement calls (J): each links to the full reasoning and the options turned down.

  • Target, not "output": the standard word (TypeScript's target, LLVM's targets). The CLI used "target" for the project a command acts on, so that argument became project: spell compile <project> --target <name> (Q1, Q11).
  • Writer, not "emitter" or "scribe": plain English, and no new word to explain. "Translator" and "dialect" already mean the human-language side; "backend" means the app's server (Q2).
  • The CLI says "project" inside too: CliProject, resolveProject(), session.projects(); its recent-picks file moved to .recent-projects.json (first done for what people read only, then inside at the review: J11, T6).
  • ts/solid is cheap: TSWriter extends JSWriter, runs on the same core, and tsc says at once how good spell's datatypes are.
  • Python is big (a core in Python, a readable-or-runs decision), so it's its own epic, starting from a working harness: the contract's test programs (Q3).
  • Writers in the parser, packages/parser/src/writers/, beside src/ast/: the tree classes are there already, and match.compile() reaches a writer with no new wiring. A new package would mean moving 76 classes and every P.AST* use (Q4).
  • The targets table in spell, packages/spell/src/targets.ts: a target is about a spell PROJECT (its file, whether its spell may draw), and the parser shouldn't know projects exist (J12).
  • Only can.draw: no core field and no can.observe (redraws when a value changes; not react, which reads as ReactJS) until a target needs them; one core exists, and nothing checks reactivity (J12).
  • Methods found by CLASS NAME, not a kind on every node: 76 classes would each grow one, and inheritance (a core call written as a scoped call) needs the chain walk anyway. Names are safe here: builds keep them already for rule names, and a rename fails a test, not a project (J3).
  • Plain strings, not tagged Code: P2's whole point was byte-identical output, and nothing reads the tags yet. Tagging comes with its first reader, source maps (J2, T2).
  • The ASTViewer went: Monaco already colours code, and keeping it meant moving 54 renderChildren() methods into the writer too. The Javascript Output pane is a read-only Monaco now (Q6, J1).
  • Operators, text values and this / undefined / null are decided in the tree and rules, so they moved.
  • Names, constants and enumeration values are baked into SCOPE RECORDS, which the language server, scope packs and importing projects read. Changing them changes every reader: a phase of its own (J4, T4).
  • A file beside the output, the same for every target, rather than a comment per language: a Python project could import a JavaScript-built one (Q8).
  • Markers inside compiling, split out at the end, rather than declarations made straight from the tree: one place still decides what a statement declares, and code lines are exact, whatever the writer printed. Straight from the tree needs source maps first (J10).
  • Both: project.json says what a project is for; --target overrides it for one run (Q7).
  • js/solid always: the app, runners and language server run it, whatever else is picked (J12).
  • Types only where spell knows them or TypeScript can't work them out: writing any where TypeScript already has a type would throw it away (J13).
  • Unknown is any /* spell: type unknown */: passes tsc --strict, and every gap is greppable (Q16).
  • tsc's errors are a snapshot, not a failure, so a change shows as a diff; strictFunctionTypes off, since core types every callback's item unknown and a callback taking a Card could never be passed (J14).
  • An element plus a command, not a command printing SVG: one element works in docs pages, the app and VS Code, live (Q5). The command is spell parse --tree, not a new one (Q12).
  • The app's Spell Tree pane replaces the Match inspector (Q13); a box shows its datatype as a second, muted line (Q14).
  • VS Code: a view of its own, from the language server's live parse, so unsaved edits show; a page in Spell Docs could only see saved files (Q15, J5).
  • Labels in spell's words, wrappers left out (J6); slot labels on the line, so they never collide (J7); sizes from character counts, so layout is pure and testable (J8); nested lists as the fallback, since the layout may be what threw (J9).
  • Every fixture, Solitaire under a fake page (Q17).
  • In the cli's tests, running each target as spell run does; linkedom rather than jsdom: already in the repo (ui, docs), and React draws into it fine (J15).

What's open, from the plan doc's caveats (C) and todos (T).

  • Names are still JavaScript. A method's name (is_a_$suit), a constant ('up') and an enumeration's values ("clubs") live in scope records spelled for JavaScript. A Python writer would see them as is until T4 makes them spell names, read by every reader and spelled by each writer.
  • No source maps. Writers return strings, not text tagged with its node (T2). So the Javascript Output pane no longer follows the cursor, as the old ASTViewer did (J1).
  • The parser, meant to be generic, holds spell's tree and its writers (C1, recorded in agents/CODE-DEBT.md).
  • No target can't-draw yet: the check only fires for one that comes later. A target has no core or can.observe field yet.
  • Solitaire as TypeScript has 35 tsc errors (C5; packages/spell/projects/test/Solitaire/Solitaire.snapshot.tsc.txt), nearly all from @spell/core's loose types:
    • 17 from spellCore methods returning unknown, used inline, e.g. spellCore.getItemOf(deck, -1).name
    • 4 from new List() / new Deck() (List's constructor requires its props); 2 from typeof Pile not being a new () => unknown
    • 3 from spellCore.RUNTIME typed | undefined
    • card.value + 1 (spellCore.itemOf() returns string | number | undefined), event.card on a SpellEvent
    • 2 that are spell's own: this.symbol on Foundation, a property nothing declares; start_pile.can_pick_up_$card(...) on a Pile, a method only its sub-classes have
  • The writer can't fix core's: T7 tightens its types (List<T>, getItemOf<T>(), callbacks over T, optional List props, RUNTIME always set), which also lets strictFunctionTypes back on.
  • A member patched onto a class from ANOTHER project can't be typed: its interface clashes with the import, and the fix is a declare module block. No fixture does this yet (C6).
  • tsx compiles core's App.tsx with classic JSX in the runner, so the fake page sets a global React: harmless, but the runner's JSX settings differ from the app's build (C7).
  • Only the page when the program ends is compared: clicks never happen, so event handlers (on card-click) aren't exercised (C7).
  • There's no machine-readable list of core methods yet: Python's epic will want one (T1).
  • Redraws only when tree is set to a NEW object (C2).
  • Its screen-reader name is a one-line summary (root and child count): pages should describe the shape in text where it matters (C3).
  • Layout packs small subtrees to the left, counts wide CJK characters as one cell, and a scrolling wide tree may not be keyboard-focusable in Safari (C4).
  • VS Code's Spell Tree view is built, not installed: an installed extension runs the source of the checkout it was built in. Install from main after merging (spell dev vscode).
  • main's docs bundle has no <ui-tree-diagram> yet: pasted --tree --html draws nothing there. The Compile Targets sketch's tree figure is redrawn with it at merge (T5), and shared guides naming the parser's removed markup code are fixed then too (T3).
