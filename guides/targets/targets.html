Targets and Writers

How spell compiles one program for several destinations. A target is where the code goes (js/solid, ts/solid); a writer is the class that walks the spell tree and writes that target's code.

A target is a LANGUAGE / RUNTIME pair: js/solid is JavaScript running on @spell/core (Solid). Each target has a writer, a file it writes, and what its runtime can do.

Read left to right. Everything left of the tree is about how spell is WRITTEN; everything right of it is about where it RUNS. The tree is the only thing both sides share.

targets.ts (excerpt) · 30 lines 
/** A target spell compiles to -- see `TARGETS`. */
export type Target = {
  /** Its name, LANGUAGE/RUNTIME, e.g. `js/solid`. */
  name: string
  /** Writes its code. */
  writer: P.Writer
  /** End of its compiled output file's name, e.g. `.compiled.js`. */
  suffix: string
  /** What its runtime can do. */
  can: TargetAbilities
  /** What checks its output after `spell compile`, e.g. `tsc` -- see `typecheck()` in `$/spell/node/typecheck`. */
  checkedBy?: "tsc"
}

/** What a target's runtime can do -- checked while compiling, so a project asks only what its targets give. */
export type TargetAbilities = {
  /** Draw a UI:  `dom` into the page, `html` as text (e.g. server pages), or not at all. */
  draw: "dom" | "html" | false
}

/** Every target, by name. */
export const TARGETS: Record<string, Target> = {
  "js/solid": { name: "js/solid", writer: P.JSWriter.instance, suffix: ".compiled.js", can: { draw: "dom" } },
  // Solid TypeScript, as a person writes it:  JSX, decorators (`@prop`, `@drawn`), on the same runtime.  Checked by
  // `tsc`;  never run as is -- it needs a build first (`buildTsx()` in `$/spell/node/buildTsx`)
  "ts/solid": {
    name: "ts/solid",
    writer: P.TSWriter.instance,
    suffix: ".compiled.tsx",
    can: { draw: "dom" },
    checkedBy: "tsc"

}

Both targets draw with Solid, through @spell/core's drawing module, drawing.ts. A value that changes updates only its own node: flipping a card changes that card, and nothing redraws the board.

  • Compiled spell has no build step, so its JSX is a call: spellCore.element(), built on Solid's @solidjs/h.
  • Every value in a drawing that can change is written as a function, so Solid calls it again when what it read changes.
    • Literals, elements, inline handlers and on* props stay as they were.
    • In the tree, such a value is an ASTJSXLiveValue.
  • element() turns the spellings spell programs write into the page's:
    • className is class, htmlFor is for
    • a camelCase attribute on an HTML tag is lowercased: colSpan is colspan
    • on a tag with a dash (<ui-form>), an object or a live value is set as a PROPERTY: an attribute holds only text
    • a dotted tag (<UI.Form>) throws: "isn't an element: write Spell UI's own tag"
  • A thing's draw() runs again when something it read outside its live values changes, e.g. the is face down an if chose by. Only that thing's node is drawn again.
  • A list drawn with drawItems() keeps each item's node, by identity (Solid's <For>).

One broken drawing no longer takes the app down. When a thing's draw() throws:

  • one line goes on the program's console
  • the app's element sends a cancelable ui-error event, { error, thing }, the same name Spell UI's elements use
  • the thing shows a small stand-in, unless that event was cancelled
  • the rest of the drawing keeps working, and the net heals when the thing draws again

ONE net, for both targets (drawInNet()):

  • javascript draws a thing with spellCore.drawThing(card), which puts its draw() in the net
  • TypeScript, and hand-written code, mark draw() with @drawn, which puts it there itself
  • drawThing() calls a @drawn method straight: a second net would catch nothing more

Inside, the net is three things, as Solid 2's own error boundary isn't enough alone:

  • Solid's <Errored>, for what a live value throws later
  • a memo running draw(), so it runs again only for what IT read
  • a try / catch making the stand-in once: <Errored> makes its fallback again whenever anything under it changes (C13)
  • App.start() mounts the app with Solid's render(), in a root of its own (mountApp()).
    • It's left on the element as spellRoot.
    • A runner unmounts it before running a program again.
  • spell-runtime.js, compiled spell's @spell/core, uses the page's ONE shared Solid, from spell-solid.js.
    • That file also holds Spell UI's element core, since <spell-app> is a Spell UI component (J54).
    • The runtime never holds a Solid of its own, nor the whole of Spell UI: the build tests pin both.
  • spell run and the core contract load Solid's browser builds under node, on a fake page (linkedom), with no global React.
  • notify, alert, confirm and prompt are Spell UI's toast and dialogs, and the program waits for each answer.
    • Under spell run they print on the program's console, and take a default answer.

Every writer lives in writers/, beside the tree it writes (ast/). P.Writer<Output> is the base: a target's writer outputs a string, TreeWriter a box.

P.Writer The base: finds a node's method by its class name, and knows nothing about any language. P.JSWriter JavaScript: the js/solid writer, and what ASTNode.compile() calls. P.TSWriter Solid TypeScript: a JSWriter that writes JSX, decorators, types and TypeScript's names, from a TSProject that has seen the whole project. P.TreeWriter Not a target: writes each node as a box for <ui-tree-diagram> (see 9).

Before this epic, every tree class wrote its own JavaScript, twice: compile() for the text, renderChildren() for the AST viewer's coloured copy. Now a node is data, and one method per class, in one writer, writes it.

  • A writer finds its method for a node by the node's CLASS NAME: ASTIfStatement(node) writes an ASTIfStatement.
  • No method of its own: the nearest base class's writes it, e.g. ASTCoreMethodInvocation by ASTScopedMethodInvocation(node). None at all: write() throws, unless the writer has ASTNode(node), the root of every chain (TreeWriter does).
  • Each class's method is looked up once, then remembered.
  • Because it goes by name, EVERY build must keep class names (keepNames; rule names already needed it). build.test.ts pins that, and JSWriter.test.ts checks every tree class finds a method.
  • Write a child with this.write(child), NEVER child.compile(): compile() is always JSWriter.instance.write(this), so a subclass's overrides would never reach the child.
Writer.ts (excerpt, docs left out) · 27 lines 
write(node: P.ASTNode): Output {
  return this.methodFor(node, "").call(this, node)
}

writeAsMember(member: P.ASTClassMember): Output {
  return this.methodFor(member, "AsMember").call(this, member)
}

protected methodFor(node: P.ASTNode, suffix: "" | "AsMember"): (node: P.ASTNode) => Output {
  const key = `${node.nodeType}${suffix}`
  let method = this.methods.get(key)
  if (method) return method
  for (let type = node.constructor; type && type !== Object; type = Object.getPrototypeOf(type)) {
    const found = (this as unknown as Record<string, unknown>)[`${type.name}${suffix}`]
    if (typeof found === "function") {
      method = found as (node: P.ASTNode) => Output
      break
    }
  }
  if (!method) {
    throw new TypeError(
      `${this.constructor.name}.write():  no \`${key}()\` method writes a ${node.nodeType}, nor one for any class it extends`
    )
  }
  this.methods.set(key, method)
  return method
}
  • A class member is written two ways: INSIDE its class's body, or patched onto its class from outside.
  • writeAsMember(member) calls <class>AsMember(node), e.g. ASTReactivePropertyAsMember writes get rank() {…} / set rank(value) {…} in the class body.
  • Plain write() patches it on from outside: Card.prototype.play = function () {…}, or Object.defineProperty(Card.prototype, 'pile', {…}) for a property.
  • Members from every file of a project are gathered into their class first (SP.hoistClassMembers(), in SpellProject.combineCompiled()): Card.move_to_$pile from Pile.spell goes in class Card.
  • TypeScript goes further: EVERY member goes inside its class, even one spell patches on from outside (the pile of a card, set first in Pile.spell). One class body per type, as a person would write it (J21).
  • Only a member of a class ANOTHER project declares is still patched on, with an interface merged with the class first.
  • JSWriter.ts: every compile() method the tree classes had (53 of them, plus the member variants), moved here with byte-identical output.
  • list(), args(), array() write lists of nodes; P.jsText (jsText.ts, once stringifyAST.ts) is plain text helpers: InParens, Block, inQuotes() …
  • JSWriter.OPERATORS spells each operator's meaning (see 7).
  • JSWriter.instance is the one ASTNode.compile() and js/solid use.
  • What changed in the javascript since P9:
    • a value in a drawing that can change is a function (see In javascript)
    • events are spellCore.on() / spellCore.trigger(): no compiled program writes spellCore.RUNTIME
    • ?. where a value may be nothing: spellCore.getItemAt(deck, -1)?.name
    • a method's name keeps its receiver's type after a little word: update_the_total_of_calculator(), where the name would end in a dangling "of"
    • core's position names: positionOf(), getItemAt() (see Position names)

TSWriter.ts: Solid TypeScript, written as a person would write it by hand (Owen: "as if I was writing the class by hand").

  • It sees the whole project first: TSWriter.forProject() makes a TSProject, the plain facts it needs.
    • which members are getters, so a read can use TypeScript's name
    • which variables are set again (let), and which aren't (const)
    • which members move into their classes, and what each class declares
    • which lists become typed constants, and each list class's item type
  • TSWriter.instance alone knows no project, e.g. writing one node in a test: then nothing is renamed where it's read, and nothing moves.
  • It extends JSWriter, overriding about 80 of its methods; the javascript never changes because of it.
  • Real JSX and Solid's shapes: <Show>, <Switch>, <For> (see In TypeScript).
  • Decorators instead of four lines per property, from @spell/core:
    • @prop({ oneOf: RANKS }) accessor rank!: Rank
    • @prop() on a property spell never declared
    • @derived on a getter that loops (has a callback); any other getter stays plain
    • @drawn on draw(), and @thing where a class needs it
  • A list of values is a typed constant: const RANKS = [...] as const, then type Rank.
  • TypeScript's names for methods, getters, functions and variables: isASuit(), turnFaceUp(), allPiles.
    • Properties keep spell's names: they're data a program prints, so both targets print the same.
    • A member read is renamed only when the project declares it a getter, never a property (J20).
    • A getter another project declares as a property is read by TypeScript's name too: its declarations say "getter": true.
  • Tidy, as by hand:
    • const unless the variable is set again
    • template text, no extra parentheses or braces, no unused handler parameters
    • a handler a drawing uses twice, written once as a local
    • a const and its type together; one export interface block per class, a member a line
  • Spell's built-ins that count from 1 stay core calls, so both targets print the same: spellCore.getItemAt(rank, 1).
  • A spell list uses its own methods, counting from 1, as spell does: foundations.getItem(2), stock.lastItem, tableaus.filter(...) (see List methods).
    • for each is forEach(); a loop whose body waits is for ... of.
  • Events from core, the payload taken apart: on<{ card: Card }>("card-click", ({ card }) => card.play()), and a bare trigger(...).
  • No ! where a value may be nothing: stock.lastItem?.turnFaceUp().
    • What may be nothing is followed through locals, guards and getters.
    • ! stays only where ?. can't go: a value passed to a typed parameter, or one being set.
  • Comparisons in TypeScript's own words:
    • === where both sides are known and alike; === undefined for "is defined"
    • a yes / no choice, and text that isn't empty, tested bare
    • type tests: instanceof for a class, typeof x === "number", isOfType() for the rest
    • text known to be text uses its own methods: .includes(), toLocaleUpperCase()
  • A method's name keeps its receiver's type after a little word, in both targets: updateTheTotalOfCalculator().

  • params() types a method's named arguments by their fields, each optional: createANewTask(props: { title?: string } = {}).
  • A property patched on from outside (ASTReactiveProperty) gets an interface merged with its class first, so TypeScript knows it's there.
  • typeFor(datatype) turns spell's datatype into TypeScript: text and character → string, number and integer → number, choice → boolean, date → Date, nothing → undefined, thing → Thing, app → App; a project's own type (Card) as is.
  • The rule (J13): a type is written only where spell knows it, or where TypeScript can't work it out. Writing any where TypeScript has a type would throw it away.

Where spell writes the type:

  • parameters: every one; a slot named for a property takes that property's type, isASuit(suit: Suit)
  • properties, from their check: @prop({ type: "number" }) accessor score!: number, @prop({ oneOf: SUITS }) accessor suit!: Suit
  • loop and where variables, items read from a list, a guard's item
  • named arguments, an event's payload (as a parameter), a getter's return
  • a list class says what it holds, class Pile extends List<Card>; core's helpers return their collection's type
  • a property over an inherited getter keeps a getter / setter pair

Where TypeScript works it out, so nothing is written:

  • a callback's item: this.forEach((card) => ...)
  • a local set from a value TypeScript knows: let state = `${this.name || "pile"}:`

Where spell fills a gap the program left (Q25, Q54):

  • A member a class uses but never declares is declared for TypeScript, on the class its users share: declare droppable: boolean on Pile. Spell still warns about it.
  • A value whose type the program never says is typed from what the program gives it (P17): new Stock_Pile({ name: "stock" }) makes a pile's name a string.
    • What counts: a value given when one is made, a value it's set to anywhere in the project, and its initial value.
    • All alike (all text): that type. Mixed, or one it can't tell: the marker stays.
    • Set on something the writer can't tell is one of that class: it doesn't count.
  • A member declared only on sub-classes (canPlayCard() on each kind of pile) is typed on the shared class from what their definitions return (P17), canPlayCard(card: Card): boolean: a comparison, and / or, yes / no. If they disagree, or one can't be told (or may end without returning, or waits), the marker stays.

What's left:

  • Only when nothing says: any /* spell: type unknown */, with spell's warning, so the author sees where to say it. Every gap is greppable.
  • A plain list: any /* spell: list */, as spell sets properties on lists, which a List can't have.
  • Reading by position, or a list holding an item, may find nothing: read with ?., as found (Q26, then Q38).

export class PyWriter extends P.Writer {
  ASTIfStatement(node: P.ASTIfStatement): string {
    return `if ${this.write(node.condition)}:${this.indented(node.statements)}`
  }

  ASTElseIfStatement(node: P.ASTElseIfStatement): string {
    return `elif ${this.write(node.condition)}:${this.indented(node.statements)}`
  }

  /** `spellCore` is `core`, from `spell_core`. */
  ASTSpellCoreExpression(node: P.ASTSpellCoreExpression): string {
    return "core"
  }

  /** `spellCore.getRange(...)` => `core.get_range(...)`:  Python's names. */
  ASTScopedMethodInvocation(node: P.ASTScopedMethodInvocation): string {
    return `${this.write(node.thing)}.${snakeCase(node.methodName)}${this.write(node.args)}`
  }

  /**
   * An inline method (`node.inline`) with a one-expression body stays a `lambda`;  anything longer is lifted
   * into a nested `def` just before the statement that uses it, named for what it does, e.g. `each_number`.
   */
  ASTMethodDefinition(node: P.ASTMethodDefinition): string {
    if (!node.inline) return `def ${node.methodName}${this.params(node)}:${this.indented(node.body)}`
    if (isOneExpression(node.body)) return `lambda ${this.paramNames(node)}: ${this.write(node.body)}`
    const name = this.names.fresh(node)
    this.before(`def ${name}${this.params(node)}:${this.indented(node.body)}`)
    return name
  }
}

From the plan doc's questions (Q) and judgement calls (J): each links to the full reasoning and the options turned down.

  • Target, not "output": the standard word (TypeScript's target, LLVM's targets). The CLI used "target" for the project a command acts on, so that argument became project: spell compile <project> --target <name> (Q1, Q11).
  • Writer, not "emitter" or "scribe": plain English, and no new word to explain. "Translator" and "dialect" already mean the human-language side; "backend" means the app's server (Q2).
  • The CLI says "project" inside too: CliProject, resolveProject(), session.projects(); its recent-picks file moved to .recent-projects.json (first done for what people read only, then inside at the review: J11, T6).
  • ts/solid is cheap: TSWriter extends JSWriter, runs on the same core, and tsc says at once how good spell's datatypes are.
  • Python is big (a core in Python, a readable-or-runs decision), so it's its own epic, starting from a working harness: the contract's test programs (Q3).
  • Writers in the parser, writers/, beside src/ast/: the tree classes are there already, and match.compile() reaches a writer with no new wiring. A new package would mean moving 76 classes and every P.AST* use (Q4).
  • The targets table in spell, targets.ts: a target is about a spell PROJECT (its file, whether its spell may draw), and the parser shouldn't know projects exist (J12).
  • Only can.draw: no core field and no can.observe (redraws when a value changes; not react, which reads as ReactJS) until a target needs them; one core exists, and nothing checks reactivity (J12).
  • Methods found by CLASS NAME, not a kind on every node: 76 classes would each grow one, and inheritance (a core call written as a scoped call) needs the chain walk anyway. Names are safe here: builds keep them already for rule names, and a rename fails a test, not a project (J3).
  • Plain strings, not tagged Code: P2's whole point was byte-identical output, and nothing reads the tags yet. Tagging comes with its first reader, source maps (J2, T2).
  • The ASTViewer went: Monaco already colours code, and keeping it meant moving 54 renderChildren() methods into the writer too. The Javascript Output pane is a read-only Monaco now (Q6, J1).
  • Operators, text values and this / undefined / null are decided in the tree and rules, so they moved.
  • Names, constants and enumeration values are baked into SCOPE RECORDS, which the language server, scope packs and importing projects read. Changing them changes every reader: a phase of its own (J4, T4).
  • A file beside the output, the same for every target, rather than a comment per language: a Python project could import a JavaScript-built one (Q8).
  • Markers inside compiling, split out at the end, rather than declarations made straight from the tree: one place still decides what a statement declares, and code lines are exact, whatever the writer printed. Straight from the tree needs source maps first (J10).
  • Both: project.json says what a project is for; --target overrides it for one run (Q7).
  • js/solid always: the app, runners and language server run it, whatever else is picked (J12).
  • Types only where spell knows them or TypeScript can't work them out: writing any where TypeScript already has a type would throw it away (J13).
  • Unknown is any /* spell: type unknown */: passes tsc --strict, and every gap is greppable (Q16).
  • tsc's errors are a snapshot, not a failure, so a change shows as a diff; strictFunctionTypes was off at first, since core typed every callback's item unknown, and came back on once T7 typed them over what a list holds (J14).
  • An element plus a command, not a command printing SVG: one element works in docs pages, the app and VS Code, live (Q5). The command is spell parse --tree, not a new one (Q12).
  • The app's Spell Tree pane replaces the Match inspector (Q13); a box shows its datatype as a second, muted line (Q14).
  • VS Code: a view of its own, from the language server's live parse, so unsaved edits show; a page in Spell Docs could only see saved files (Q15, J5). Epic epic-components has since taken that view out of VS Code's side bar (its J8).
  • Labels in spell's words, wrappers left out (J6); slot labels on the line, so they never collide (J7); sizes from character counts, so layout is pure and testable (J8); nested lists as the fallback, since the layout may be what threw (J9).
  • Every fixture, Solitaire under a fake page (Q17).
  • In the cli's tests, running each target as spell run does; linkedom rather than jsdom: already in the repo (ui, docs), and drawing into it works (J15). It drew with React then; Solid's browser builds draw into it now.
  • Owen asked for TypeScript that is "straight solid calls, it can use decorators, etc. ... as if I was writing the class by hand".
  • Both targets, javascript first ("Do the js => solid first"), so React left compiled spell (Q23). The work was split into four phases, P10 to P13 (Q27).
  • Javascript's net is core's drawThing(), with no wrapper in the compiled code (Q28).
  • A thing's draw() runs again for what it read, not "once, untracked": javascript has no <Show>, so a card could never flip (Q29).
  • Core's React drawing went in P10, not P11: nothing could call it once drawThing() drew with Solid (J18).
  • Owen: "Converging the two is the highest priority. ... We will be creating spell/ui-type web components with spell very very soon. They should share a reactive runtime engine" (Q20).
  • So the engine and the decorators moved to $/util/reactive before anything drew with Solid, and the TypeScript imports them from @spell/core.
  • Spell UI's reactive members come onto it later, as the SAME decorators, not a second set beside spell's, after four checks (C12).
  • A decorator on draw(), @drawn, not a <Drawn> component around each child (Q21): the class says it once, and a parent draws a child with a plain call.
  • @drawn lives in core, sharing drawThing()'s one net, so both targets fail the same way (J23).
  • Real JSX in a .tsx, not h() calls or Solid's compiled calls: what a person writes, built by the same compiler (Q18).
  • The shapes the writer knows become <Show> / <For>; any other drawing re-runs whole, inside its net (Q19).
  • The page's spellings (class, colspan, prop:): Solid 2's JSX types take no others (C19).
  • camelCase, as a TypeScript author writes, but properties keep spell's names: they're data a program prints, and both targets must print the same (Q22).
  • A member read is renamed only when the project declares it a getter: a read can't tell a getter from a property (J20).
  • A method's name keeps its receiver's type where a little word would dangle (Q44).
  • Where a program never says a type, spell ASKS, with a warning, rather than working it out from what the program does (the recommended option). The cost: programs get longer, and a beginner meets types sooner (Q24).
  • A member a type uses but never declares is declared by spell, for TypeScript only (Q25), and spell warns on the read (Q45).
  • A read that may find nothing was read as found, ! (Q26), then ?. instead, in both targets (Q38).
  • P17's rules, answered before bed (Q54): infer an unsaid type from what the program gives it; type a member declared only on sub-classes from what they return; keep J28's four smaller rules.

  • A program writes <ui-form>, the name Spell UI's docs show, not <ui.form> (Q30).
  • On a ui-* tag, a live value or an object is a property, as an attribute holds only text (Q31).
  • The form binding and the repeat are Spell UI's, for any page, with nothing spell-specific (Q32); a repeat takes its list as a spell expression (Q48).
  • A list's own methods, in TypeScript only: the javascript keeps its spellCore calls (Q33); their names and rules (Q35, Q36).
  • Events from core in both targets, the payload taken apart (Q34, Q37).
  • Comparisons, type tests, text methods, loops and layout in TypeScript's own words (Q39-Q43).
  • JSON says its type, "@type", so it can be rebuilt as that type (Q49); spellCore.fromJSON() is the one way in (J50).
  • Position names, with the old ones kept as deprecated aliases, so saved compiled programs still run (Q47).

What's open, from the plan doc's caveats (C) and todos (T).

  • Names are still JavaScript. Scope records hold names spelled for JavaScript:
    • a method's name (is_a_$suit)
    • a constant ('up')
    • an enumeration's values ("clubs")
    • A Python writer would see them as is, until T4 makes them spell names: read by every reader, and spelled by each writer.
  • No source maps. Writers return strings, not text tagged with its node (T2). So the Javascript Output pane no longer follows the cursor, as the old ASTViewer did (J1).
  • The parser, meant to be generic, holds spell's tree and its writers (C1, recorded in CODE-DEBT.md).
  • No target can't-draw yet: the check only fires for one that comes later. A target has no core or can.observe field yet.
  • The app's runners can't run TypeScript output yet. Only the core contract builds and runs it: the runtime the runners load re-exports only spellCore, Thing, List and App, not the decorators or on() / trigger() (spellRuntime.ts).
  • Built Solid TypeScript hears clicks only once its module has finished loading: Solid's compiler adds its click listener at the module's end. A program's own top-level code that clicks something goes unheard; a person's clicks always come later (C20).
  • A list property can't say its item type in spell yet: only a new thing is taken after as (I7).
  • An enumeration's kind (Suit, Rank) is an empty class: as a type it accepts any value (C10).
  • A list's methods keep two odd spell rules (C24):
    • startingWith() an item that isn't there gives the WHOLE list
    • all() on an empty list is no, where TypeScript's every() says yes
    • and a list type with a property or action named like a list method (max, reverse ...) hides that method: silently in javascript, an error in TypeScript
  • As of this page, P17 is being built. The snapshots shown here still have Solitaire's three markers that P17 types (see Where types come from).
  • Three rough edges (C23):
    • in a with list, the example still says (title as text), parens and all
    • inside a quoted signature, the warning sits under the whole quoted text, not just the slot
    • spell check counts warnings on stderr without listing them, and spell watch doesn't list them yet
  • The Solitaire examples still warn about a pile's droppable and a foundation's symbol, which they set but never declare. The fixtures are frozen as they are (C25).
  • The examples' committed compiled files are behind their sources, but for Todos - Form Based's: the app and VS Code compile from the source anyway (C22).
  • VS Code marked the Todos example's <ui-*> lines "Don't understand", while the CLI compiled them: probably a stale extension (I3).
  • Solid 2 rc.13's <Errored> re-reads its children on any change under it, and makes its stand-in again: so the net adds a memo and a try / catch (C13).
  • spellCore.element() builds its DOM at once, not when Solid asks for it: a drawing builds every element it names (C14). The TypeScript's JSX doesn't go through it.
  • A plain local in a javascript drawing is wrapped as a live value too: className: () => className (C15).
  • The error net mirrors spell-element's: check the two still agree, now that it has merged (C8).
  • <ui-repeat>'s rows have no wrapper element (C17), and the form binding has rules of its own for radios, numbers, reset, late-defined controls and template copies (C18).
  • The spell CLI keeps React, for its terminal screens (Ink) (C16).
  • Spell UI's reactive members don't run on the shared engine yet. Until they do, a derived value sees only its own side's members: a Spell UI @derived reading a spell thing's prop never recomputes, nor the other way round (C11). Plain getters are fine.
  • Moving Spell UI over has four costs to check first (C12):
    • the bridge to Solid on every Spell UI page (re-run the 1,000-button check)
    • test helpers that must flush the cells, not just Solid
    • the static server render, where the bridge has never run
    • spell-element's rewrite of Spell UI's reactive members, merged 2026-10-10
  • JSON keeps no identity: a thing held in two places reads back as two things, and a thing that holds itself can't be written at all (C26). Read a board back from parts that hold each card once.
  • spell run and the core contract don't hand fromJSON() their modules: there, a class is found only once one of its things is made (J51).
  • A program calling fromJSON() in its own top-level code is the same: its module hasn't finished loading.
  • A spell object's JSON tracked its keys, not its values, so the form's debug view missed changes made outside the form (I9, open).
  • Only the page when the program ends is compared: clicks never happen, so event handlers (on card-click) aren't exercised (C7). Its first half, a global React on the fake page, went with React.
  • The Todos examples aren't contract fixtures: a runner browser test plays Todos - Form Based instead.
  • There's no machine-readable list of core methods yet: Python's epic will want one (T1).
  • Redraws only when tree is set to a NEW object (C2).
  • Its screen-reader name is a one-line summary (root and child count): pages should describe the shape in text where it matters (C3).
  • Layout quirks (C4):
    • it packs small subtrees to the left
    • it counts wide CJK characters as one cell
    • a scrolling wide tree may not be keyboard-focusable in Safari
  • P10-P17 aren't in main: there, compiled spell still draws with React, and ts/solid writes typed javascript in a .compiled.ts.
  • The VS Code extension isn't rebuilt from this branch: an extension is never built from a branch behind main, so "Run Project" on the Todos example waits for the merge (spell dev vscode).
  • At merge: recompile the examples' committed outputs (C22), and fix the shared docs that name the reactive files' old home, src/spell/ (T22).
  • Still open from the first merge: the Compile Targets sketch's tree figure, to redraw with <ui-tree-diagram> (T5), and shared guides naming the parser's removed markup code (T3).
