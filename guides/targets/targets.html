Targets and Writers

How spell compiles one program for several destinations. A target is where the code goes (js/solid, py); a writer is the class that walks the spell tree and writes that target's code.

A target is a LANGUAGE / RUNTIME pair: js/solid is JavaScript running on @spell/core (Solid). Each target has a writer, a file it writes, and what its runtime can do.

Read it left to right. The tree is the only thing both sides share:

  • everything left of the tree is about how spell is WRITTEN
  • everything right of it is about where it RUNS

/** A target spell compiles to -- see `TARGETS`. */
export type Target = {
  /** Its name, LANGUAGE/RUNTIME, e.g. `js/solid`. */
  name: string
  /** Writes its code. */
  writer: P.ProgramWriter
  /** End of its compiled output file's name, e.g. `.compiled.js`. */
  suffix: string
  /** What its runtime can do. */
  can: TargetAbilities
  /**
   * What checks its output after `spell compile`, a function in `$/spell/node`:
   * - `tsc`:  `typecheck()`
   * - `pyright`:  `pyright()`
   */
  checkedBy?: "tsc" | "pyright"
  /**
   * End of the name of its own words file, beside its output, e.g. `.py.en.json`:  spell's wording of each member,
   * keyed by THIS target's names (`move_to_pile`) -- see `SP.SpellWords.json()`.
   * - `js/solid`'s words are `<Project>.en.js`, which every runner loads -- see `SP.SpellProject.wordsFile`.
   */
  wordsSuffix?: string
}

/** What a target's runtime can do -- checked while compiling, so a project asks only what its targets give. */
export type TargetAbilities = {
  /** Draw a UI:  `dom` into the page, `html` as text (e.g. server pages), or not at all. */
  draw: "dom" | "html" | false
}

  • Compiled spell has no build step, so its JSX is a call to Solid's own h(), as a person writing Solid without JSX would (P20).
    • h(tag, props, ...children): an element with no props has no {} at all.
    • h comes from @spell/core with the rest, only in a module that draws (Q57).
    • It's the page's one copy, already loaded for drawing, so the runners link it as they did.
  • Every value in a drawing that can change is written as a function, so Solid calls it again when what it read changes.
    • Literals, elements, inline handlers and on* props stay as they were.
    • In the tree, such a value is an ASTJSXLiveValue.
  • The writer turns the spellings spell programs write into the page's, when it compiles. It's the same rule the TypeScript writer follows, one function both call (attributeName()):
    • className is class
    • htmlFor is for
    • a camelCase attribute on an HTML tag is lowercased: colSpan is colspan
    • on a tag with a dash (<ui-form>), an object or a live value is set as a PROPERTY, "prop:value": an attribute holds only text
    • class comes first, then the rest as the program wrote them
  • A dotted tag (<UI.Form>) is a parse error, caught when it compiles (J91).
    • Why: h() would quietly draw a <UI> element, classed "Form".
    • The editor and spell compile show it with the line's other parse errors.
    • The javascript gets null where the element would be, and the error in a comment.
  • h() hands back a thunk, a function that makes the element. A draw() returns it as is, and the thing's error boundary makes it, once (J93).
    • A part that throws while it's made shows the thing's stand-in, as a throwing draw() does.
    • Elements inside it need nothing: h() makes them with their parent.
    • The boundary makes ONLY h()'s own thunks, by the mark h() puts on them. Any other function is a live value, which Solid calls itself.
  • A thing's draw() runs again when something it read outside its live values changes. Only that thing's node is drawn again.
    • e.g. the is face down an if chose by
  • A list drawn with drawItems() keeps each item's node, by identity (Solid's <For>).
  • spellCore.element(), what javascript called before P20, is gone (P22, J94).
    • Every committed example is recompiled, so each one draws with h().

Every writer lives in writers/, beside the tree it writes (ast/).

  • P.Writer<Output> is the base of them all.
  • A target's writer outputs a string of code, and TreeWriter a box.
P.Writer The base: finds a node's method by its class name, and knows nothing about any language. P.JSWriter JavaScript: the js/solid writer, and what ASTNode.compile() calls. P.TSWriter Solid TypeScript: a JSWriter that adds what only TypeScript has, JSX, decorators and types. P.TreeWriter Not a target: writes each node as a box for <ui-tree-diagram> (see 9).

Before this epic, every tree class wrote its own JavaScript, twice: compile() for the text, renderChildren() for the AST viewer's coloured copy. Now a node is data, and one method per class, in one writer, writes it.

  • A writer finds its method for a node by the node's CLASS NAME: ASTIfStatement(node) writes an ASTIfStatement.
  • No method of its own: the nearest base class's writes it.
    • e.g. an ASTCoreMethodInvocation, by ASTScopedMethodInvocation(node)
  • None at all: write() throws.
    • Unless the writer has ASTNode(node), the root of every chain, as the tree writer does.
  • Each class's method is looked up once, then remembered.
  • Because it goes by name, EVERY build must keep class names (keepNames), as rule names already needed.
    • The app's build.test.ts pins that.
    • JSWriter.test.ts checks every tree class finds a method.
  • Write a child with this.write(child), NEVER child.compile().
    • compile() is always the javascript writer's, so a subclass's overrides would never reach the child.
Writer.ts (excerpt, docs left out) · 27 lines 
write(node: P.ASTNode): Output {
  return this.methodFor(node, "").call(this, node)
}

writeAsMember(member: P.ASTClassMember): Output {
  return this.methodFor(member, "AsMember").call(this, member)
}

protected methodFor(node: P.ASTNode, suffix: "" | "AsMember"): (node: P.ASTNode) => Output {
  const key = `${node.nodeType}${suffix}`
  let method = this.methods.get(key)
  if (method) return method
  for (let type = node.constructor; type && type !== Object; type = Object.getPrototypeOf(type)) {
    const found = (this as unknown as Record<string, unknown>)[`${type.name}${suffix}`]
    if (typeof found === "function") {
      method = found as (node: P.ASTNode) => Output
      break
    }
  }
  if (!method) {
    throw new TypeError(
      `${this.constructor.name}.write():  no \`${key}()\` method writes a ${node.nodeType}, nor one for any class it extends`
    )
  }
  this.methods.set(key, method)
  return method
}

export class PyWriter extends P.Writer {
  ASTIfStatement(node: P.ASTIfStatement): string {
    return `if ${this.write(node.condition)}:${this.indented(node.statements)}`
  }

  ASTElseIfStatement(node: P.ASTElseIfStatement): string {
    return `elif ${this.write(node.condition)}:${this.indented(node.statements)}`
  }

  /** `spellCore` is `core`, from `spell_core`. */
  ASTSpellCoreExpression(node: P.ASTSpellCoreExpression): string {
    return "core"
  }

  /** `spellCore.getRange(...)` => `core.get_range(...)`:  Python's names. */
  ASTScopedMethodInvocation(node: P.ASTScopedMethodInvocation): string {
    return `${this.write(node.thing)}.${snakeCase(node.methodName)}${this.write(node.args)}`
  }

  /**
   * An inline method (`node.inline`) with a one-expression body stays a `lambda`;  anything longer is lifted
   * into a nested `def` just before the statement that uses it, named for what it does, e.g. `each_number`.
   */
  ASTMethodDefinition(node: P.ASTMethodDefinition): string {
    if (!node.inline) return `def ${node.methodName}${this.params(node)}:${this.indented(node.body)}`
    if (isOneExpression(node.body)) return `lambda ${this.paramNames(node)}: ${this.write(node.body)}`
    const name = this.names.fresh(node)
    this.before(`def ${name}${this.params(node)}:${this.indented(node.body)}`)
    return name
  }
