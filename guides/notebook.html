Pages That Draw Their Body

A small notebook page, as such a page is written. There's no <draw> in it, and no notebook type: the page draws its own body, and holds the view it shows off.

A notebook page, 25 lines 
<spell-page "counter notebook" notebook>
	<header level="1">
		Counter
		<header>A button that counts its clicks.</header>
	</header>

	<view "counter">
		<property "count" type="number">0</property>
		<action "count up">set its count to its count + 1</>
		<draw><button onClick={count up}>Clicked {its count} times</button></draw>
	</view>

	<section label="Counter">
		<example "One counter" description="A counter starts at 0, and adds one each time it's clicked.">
			<counter/>
		</example>
	</section>

	<section label="Several counters">
		<example "Two counters" description="Each counter keeps its own count:  clicking one leaves the others alone.">
			<counter/>
			<counter/>
		</example>
		<text color="grey">Click either one.</text>
	</section>
</spell-page>

Open it in the editor and it's the running program's own page, in Spell UI's docs look: type in an example's code and only that example draws again; drag an example above another and the file changes by those lines alone.

A notebook used to be a type of its own: a page with a few writing shortcuts, plus a page the editor drew for it alone, with its own renderer and a row of tools on every cell. Now it's a page with one flag.

  • <spell-notebook "x"> is only a short spelling of <spell-page "x" notebook>. Spanish: <encanto-cuaderno> and <encanto-página cuaderno>.
  • What notebooks did that suits any page, every page does now:
    • with no <draw>, it draws its body
    • it holds its own views, <view counter>
    • it takes locked
  • The notebook flag means one thing: the editor shows the page in place, editable.
  • The cell tools are gone. Cells move the way everything else in the editor moves: by drag and drop, the Edit menu and the palette.

The catch: this is on the notebook branch, not merged yet. Two hand checks in a live window are still open.

A page with no <draw> of its own draws its body, flag or not. A page WITH one reads as it always did: loose text is a comment, and the lines just above a member are its description.

A page that draws its body · 15 lines 
<spell-page "counter page">
	# A counter
	A button that counts its clicks.

	<view counter>
		<property "count" type="number">0</property>
		<action "count up">set its count to its count + 1</>
		<draw><button onClick={count up}>Clicked {its count} times</button></draw>
	</view>

	## Try it
	<example "one counter" description="Click it.">
		<counter/>
	</example>
</spell-page>
  • Loose text is markdown, # headings too. Markup (<section>, <text>) draws where it sits.
  • Each ## heading starts a section, sticky and foldable like the docs pages', holding what follows it up to the next. A <section label="..."> written at the page's top level gets the same look.
  • Views inside a page: <view counter>, or <view "one counter"> for a name of several words. Spanish says <vista>.
    • It's an ordinary view of the project, usable from any file: it's only written where it's first used.
    • view is the only template word that drops its prefix, and only inside a page.
    • <spell-view "counter"> still reads there.
    • Any template's name may be one bare word, <spell-view counter>; a word the tag takes as an attribute stays one, so <view locked> is unnamed and locked.
  • An example's description is its description="...", as Spell UI's <ui-example> takes it. Text just before an example is only text.
  • locked (Spanish bloqueado) on any page: in the editor, every edit is a try-out, saved for nobody.
  • A page starts by itself, as any app does: nothing is added to start it.

Old spellings still read, and spell lint --fix rewrites them:

written rewritten as
<spell-notebook "x"> <spell-page "x" notebook>
<spell-view "counter"> inside a page <view "counter">
a <text> just before an example that example's description="..."

Plain spell lint warns of the last one, as description-before-example. A warning alone exits 0. That's how all 352 notebook files of Spell UI's site, in @spell/guides/SpellUI today, were rewritten: only Counter had descriptions written before its examples, and only Counter's drawing changed.

A page with the notebook flag opens as the running program's own drawing, in the app area, inside the docs frame: title, tab bar, sticky foldable sections, and "On this page" (a flyout in a narrow pane). Open one at: 

/edit/@spell/guides/SpellUI/Divider/Usage.spellml

The frame is the docs site's, fitted to a pane of any width:

  • The section tabs under the page's tabs are a <toolbar>: they show which one you're on, and scroll with ‹ › when they don't fit. On a phone the page's own tabs scroll sideways too, rather than squeezing their words.
  • Stuck section titles sit 4px apart, each with its own round corners, and nothing shows through the gap.
  • An example whose title is its section's (Button's Examples, under "Button") shows no title of its own. The code still names it.
  • The open code button looks pressed in.
  • Prose stops at 75 characters a line, while an example's notes run its whole width. The measure is <ui-markdown>'s new --ui-markdown-measure setting; unset, prose runs the column's width, as before.
  • Each example's code pane holds a code editor; typing goes into the file as the code column's does.
  • Only that example draws again: 8-17 ms, where the whole page took 1.2-2 s.
    • From a key to the example shown, the 1 s typing pause included: Button's Examples 1.4 s, Dropdown's 1.6-1.8 s. The rest is the compile, 0.1-0.4 s.
    • A line typed above an example only moves it: nothing draws again.
  • Kept across an edit: the code, the cursor, focus, the open code pane, folded sections, the scroll, "On this page".
  • ⌘Z undoes a run of typing.
  • Each example shows its Spellx or Spell code. The Spell view names a project's own views by their tags (<counter-counter/>), the same tags as the editor's code-spell tab and the language server.

A cell is an example, a run of prose, a ## section or a header. They're handled the way the rest of the editor handles things:

  • Click one to pick it: the Inspector's marching ants, 4-6px outside it, so they never cross its text, and round when it's round.
  • Drag it to another place, or drag its row in the Inspector's Views tree; ⌘Z puts it back byte for byte.
  • Cut, copy, paste, duplicate (⌘D) and delete (Backspace), from the keys or the right-click menu.
  • The palette adds an Example, a Section or a View, all three under "This page". Every app's palette offers Example and Section now, under their own topics.
  • Prose dropped beside other prose joins it.

The catch: a move draws the whole page again, about 2 s on Button's Examples (61 examples).
  • Saving is the editor's: AutoSave or ⌘S. Reset is File › Reset to Saved.
  • The lock icon in the header, or the Inspector's attribute edit, locks a page. Only whoever may save the page's design sees the lock, the same rule as Save.
  • Locked, the header says "Locked: changes aren't saved". AutoSave, ⌘S and Publish ask one check, so nothing saves.
  • The editor reads any open project file again every 2 s, so a change made elsewhere draws in about 1 s.

Spell UI's 351 component pages will be one project in the Guides group, @spell/guides/SpellUI, once this epic merges: a folder per component, each page alone in its file.

  • Run shows the site: its side navigation lists 94 components, A to Z.
  • A component's pages are tabs above the page, drawn by the site itself with <ui-site-tabs>: pages write nothing, and every site gets them.
  • A page reached through the site in Run is only read: pressing Edit opens that page's file.
  • Nothing on the home page leads to it. Pick "Spell UI" in the project menu of any guide, or type /run/@spell/guides/SpellUI.
  • A page alone in its file compiles by itself: typing in one re-parses only it. The editor compiles the rest of the project plus the pages it's showing; spell compile compiles them all.

Most frameworks ship a notebook as a second document type, with its own cells and its own renderer. Here there's one page, read one way, and the editor draws nothing of its own.

  • The one test is SpellxTag.drawsBody, set by isPageDrawingItsBody().
  • An example's part is core.drawPart(); the editor's LiveEdit finds the one that changed by its code, not its place.
  • Which tag each name became is one table, SP.ComponentTags, shared by every code-spell view and the language server.
  • Page is a hand-written class, like View. Its lock is a member in the JavaScript and Python cores, Spanish candado.
  • Any page with no <draw> draws its body, over keeping that behind the flag. A page with a <draw> keeps its loose text as comments, so no existing page's comments turn into drawn text.
  • Every page holds views and takes locked, over keeping them notebook-only: neither needs the editor's page.
  • A view inside a page is usable anywhere in the project, over one local to its page. Local views would need tag names scoped to the page, a new kind of type, and changes to the editor's lists: about 4-6 hours, for a convenience of placement.
  • The page is the running program's own drawing, over the notebook's own renderer: one drawing, so drag and drop, the Inspector and the palette work on it as on any app.
  • Each example is a part of the page's drawing, over making each one a generated view: no new types appear in the program, and an edit still redraws only its example.
  • Saving is the editor's, with its undo, over the notebook saving 600 ms after each edit: one way to change and save a file.
  • Page stays hand-written, taking the lock as a member, over a built-in page template written in spell. It sits beside View and App, which are hand-written too.
  • Who may lock a page is whoever may save its design, over whoever may write the project: a lock is saved as any edit to a page is, so anyone else's click would fail to save.
  • The 352 files were rewritten, over leaving both spellings in the content: what people copy shows the current way.
  • A moved cell waits for the compile: on Button's Examples it shows about 0.5 s after the drop, the compile's half-second; every example and section stays as it was, only what moved goes elsewhere.
  • The first key on a big page is slow: 3.3-3.9 s on Dropdown's Examples, then 1.5-1.8 s. Not the redraw (17 ms): the code editor reading its layout (~0.5 s) and Solid's first flush of the panes (~0.5 s).
  • A half-typed example can take the page down to one element until it's fixed, e.g. a broken attribute name. Better would be the broken example drawn as an error in its own place.
  • An example mixing an <html> block with other markup loses that block's tags in the Spell view, so an edit there writes its web tags bare. An example that's one HTML block is fine.
  • The editor's colouring still goes by the flag: it reads a line at a time, so a plain page with no <draw> colours its loose text as comments. Nothing compiles differently.
  • Python's core has no drawPart yet.
  • Spanish: a default on an inherited built-in member, su candado es "bloqueado", compiles under its Spanish name. No built-in project locks a page, so nothing draws differently.
  • Spell UI's 94 notebook projects stay one project per component. Turning them into one site, each page at its own address, waits on pages-by-address (epic mockup); views scoped to a page belong with that work.
  • Who may lock a page, whoever may save its design, is still to be confirmed.
  • On a phone, the page's own tabs have no ‹ ›: the row scrolls, but Theming starts past the right edge with nothing saying so. Each notebook's tab bar is a <ui-menu>; making it a <toolbar>, as the section tabs are, would add them.
  • The code button sits over a full-width demo's right end: a wide input or message runs under it. Giving it room would take a column from every example, and the button belongs inside the frame's corner.
