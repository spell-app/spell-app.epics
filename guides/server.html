Page Server

spell dev server ensure, run in a worktree, answers in about a second: a page server on port 55703, because the main checkout already has 4747. Every docs page, epic page, saga page and Spell UI page of that checkout is now live on it.

Below: how the repo serves its pages locally. The spell-kit/server library (SRV), the one page server per checkout built on it, and everything that plugs into it.

Epic page: epic unified-server Written for: anyone opening, editing or serving a page, or adding routes to the page server Status: merged into main (P1-P7) Checked on: main, 2026-10-09, against the code (not just the epic page)
  • The server package serves pages locally, for every package.
    • Its name is @spell-app/server, imported as spell-kit/server.
    • Its namespace is SRV.
    • Before it, six servers each had their own mime table, path check, port choice and opener.
    • Now they share one library.
  • The PAGE SERVER (spell server): ONE per checkout, serving the whole repo on one port.
    • One for the main checkout, and one for each worktree.
    • live reload on every page; edit a section in place; the server-only properties
    • / redirects to the docs' home page
    • port: 4747 if free, else any free one (SPELL_SERVER_PORT overrides)

    • its output goes to <root>/.spell-server.log
  • Every page carries the site header (<spell-site-header>): a fixed bar switching between the site's parts, its tabs.
    • It also holds:
      • the checkout's worktree / branch badge
      • an "open in VS Code" link
      • edit mode

The page server itself, spell-kit/server/page: opt-in, since it brings parse5 and loads route modules.

  • PageServer.ts -- THE server: a live WebServer on the checkout.
    • Plus /_server/ping, the editor, /components/ui/ and the route modules.
    • PageServer.ensure(root): what spell dev server ensure, goals and the openers call
  • PageEditor.ts -- /_server/page: read, replace or patch a page's source
  • RunningEpics.ts -- the epic pages of running epics on the main checkout's server: /worktrees/<w>/, /_server/epics, and their cards in the home page's Epics section (Running epics)
  • cli.ts -- spell server
  • page.types.ts -- RouteModule, RouteContext, PageServerSettings

Browser code, spell-kit/server/site: bundled into the docs' spell-ui.js and Spell UI's site bundle (site.js).

  • SiteHeader.ts -- <spell-site-header>: own shadow DOM and CSS, no UI elements, so it looks the same on every property
  • SectionEditor.ts -- <spell-section-editor>: edit mode's hover, dialog and save
  • site.types.ts -- SiteTab and litTab(): the header's tabs as data, and the one a page lights
  • index.ts -- defineSite(): defines the header, and mounts the editor on served pages
  • The barrel is node built-ins only: json5 and esbuild come in as the caller's hooks (parseJson, transforms).
  • Its users: ui's tools and site, spell/node, cli, app, docs, goals, the VS Code extension.
  • page/ may use dependencies (parse5), and site/ is DOM code.
  • Neither is in the barrel.

Each flow, step by step, in the order it happens.

  1. The opener (epic pages open, epic open, spell dev goals open) calls PageServer.ensure() -- the docs' scripts through ensurePageServer().
  2. It reads the pid file, .spell-server.json, and asks that server's /_server/ping.
    • It counts only if it answers for THIS checkout.
  3. None: it spawns cli.ts serve under tsx, detached, logging to .spell-server.log, and waits up to 15s.
    • about 1s when it has to start, 0.3s when it already runs
  4. The URL is base + the file's path from the checkout, shown in:
    • a Chrome tab keyed by the page's path, so the same page from another checkout reuses it
    • a new browser window (saga pages), or VS Code's Simple Browser
  5. Every .html page it serves gets three things before </head>:
    • window.SPELL_SERVER (port, token, file, ETag, branch)
    • /_server/live.js
    • Spell's favicon links, unless its <head> links its own icon
  6. Spell's favicon, on every WebServer, live or not: /_server/favicon.svg, /_server/favicon-32.png, /_server/apple-touch-icon.png, and /favicon.ico (the 32px PNG, after the static folders).
  7. The favicon is made by yarn favicon in src/server (favicon.ts) into favicon.ts; pages opened from disk get it from the site header.
  1. fs.watch on the named folders only:
    • "pageServer".watch (the shared pages' folders, the docs' bundle, the brand pages)
    • plus goals/ from goals' route module
    • never scripts/ or experiments/
  2. Why not the whole root: it would flood the watcher (node_modules, .git, worktrees).
  3. Each changed path waits 250ms for quiet: a write is often two (write, then a formatter).
  4. A change message with the URL path goes to every page holding its /_server/events websocket open.
    • A ping every 30s keeps the sockets alive.
  5. A websocket, not server-sent events (2026-10-06).
    • An EventSource holds one of Chrome's 6 connections per host for good, and every VS Code window shares them.
    • So 6 docs pages open anywhere left every other page's parts and scripts waiting forever.
    • Websockets don't count toward the 6.
  6. The page reloads if the path is its own file, or any .css / .js; its scroll position survives.
  1. The header's pencil turns edit mode on, for this tab.
  2. Hovering outlines the editable thing under the pointer: an element with an id (sections, paragraphs, list items, cards ...), or a section through its heading's id.
  3. "edit" fetches its source fresh: GET /_server/page?path=&id=[&parent=section] -> { html, etag }.
  4. Save sends PATCH /_server/page?path= with the token and If-Match.
  5. The server:
    • checks the token and origin, and that the path is an .html file inside the checkout
    • takes the file's FileLock; a changed ETag is a 409
    • finds exactly ONE #id with parse5 (none: 404, several: 409), and splices its byte range: every other byte stays as it was
    • writes a temp file and renames it over the original
  6. Live reload shows the result.
  7. Nothing is committed: the change waits in the working tree.
  • Also: PUT replaces the whole page.
  • Scripts in a page call SPELL_SERVER.editPage({ id, html }).

A running epic's page lives in its worktree until it merges, and each worktree has its own page server. Yet the main checkout's server shows them all:

  1. /worktrees/<w>/... serves worktree <w>'s files (a StaticHandler mount on .claude/worktrees; dot files still 403).
    • An epic page's relative assets resolve inside its own worktree.
    • Since epic epic-eject (P4 and P7, on main once it merges), the server knows no worktree folder of its own.
    • The repo's epic config names it (worktreesFolder), and the running-epics route module tells the server.
    • Pages learn the served path from the server (SPELL_SERVER.worktreesPath), not from a path written into them.
    • The server also serves the epic engine's assets and pack at /_epic/assets/ and /_epic/pack/, so pages written for spell-epic's server draw here too.
  2. /_server/epics lists them, as JSON: each worktree's own epic (named like the worktree), and any epic the main checkout lacks.
    • Copies of epics merged before the worktree was cut are skipped.
  3. The Epics page's cards are filled in again on each request.
    • They sit between its <!-- running-epics --> markers, around its card groups; epic pages index writes the markers.
    • Running and merged epics go in five groups: Favorites, Active, Planning, Urgent, Done (EpicCards).
    • Each title is followed by its state: in progress (3/6), errors, paused, future, done (spell-kit/server/site/EpicState).
    • A merged epic's card is dropped when it runs in a worktree too.
    • Every card is marked again as the page is served: in progress or paused, by whether a Claude session runs for it (~/.claude/sessions) and today's date.
    • None running: no cards added.
    • Opened from disk: the marks as docs index wrote them.
  4. A worktree's epic page changing reloads its page and the home page (one recursive watch on .claude/worktrees).
  5. spell server url and the VS Code preview hand out these URLs for a worktree's file (SRV.mainServerUrl()), so every link is on port 4747.
  6. epic doesn't rewrite the committed index inside a worktree: two worktrees doing so conflicted on merge.
    • The epic's card comes with Doc Review's epic pages index.

The editor is the PAGE SERVER's child, so spell server alone runs it too.

The app's route module (appRoutes.ts) starts it with EditorServer once the page server listens (onListening), and stops it with the page server (onStop).

  1. --port, if given, goes to a page server this STARTS as SPELL_EDITOR_PORT (default 3000, else any free port).
    • One already running keeps its editor where it is.
  2. PageServer.ensure(): the page server, with every route module.
  3. Once it listens, the app's module starts vite (its script, under this node, in spell-app/app) with PORT = the page server's port and API_SERVER=127.0.0.1.
    • So its proxy sends /api there.
    Its output goes to .spell-server.editor.log.
  4. Once vite answers, the module records it in .spell-server.editor.json: the page server's /editor redirects there.
  5. spell app serve waits (up to 90s) for that record to answer, then opens the editor, unless --headless.
  6. Ctrl-C: stop the page server -- and with it the editor -- only if spell app serve started it.

How a package adds routes to the page server without the server importing it. Like Express middleware, but registered by a path in the settings, not an import in the server's code.

  • A ROUTE MODULE is a file whose default export is a RouteModule: { name, setup(context) }.
    • setup() runs once, before the server listens
    • loaded by dynamic import under tsx; a failure is logged, not fatal
  • RouteContext, what setup() gets:
    • router -- add routes; they run BEFORE static files
    • guard -- put guard.writeCheck on every route that changes something
    • live -- live.watch(dir) reloads pages when files under it change
    • web -- the whole server, e.g. web.files.html.push() for an html hook
    • root, info -- the checkout; pid, port, branch
    • onListening(start) -- run once the server listens (info.port is set), e.g. to start a child process that needs the page server's port: the app's editor
    • onStop(stop) -- run when the server stops, e.g. to end a child process
  • Listed in the repo root's package.json, "pageServer": routes (paths from the root) and watch (folders to live-reload; default DEFAULT_WATCH, the shared pages' folders and the docs' bundle).

A route module: goalsRoutes.ts, abridged · 30 lines 
import { SRV } from "spell-kit/server"
import type { RouteModule } from "spell-kit/server/page"

const goalsRoutes: RouteModule = {
  name: "goals",
  setup({ router, guard, live, web }) {
    live.watch(GOALS, { ignore: /(^|\/)_(tools|skills)\// })
    web.files.html.push((html, { file }) =>
      file.startsWith(`${GOALS}/`)
        ? html.replace("</head>", `<script>window.GOALS_SERVER = ${JSON.stringify({ api: API })}</script>\n</head>`)
        : html
    )

    const api = new SRV.Router()
    api.get("/claude", (_request, reply) => reply.set("Cache-Control", "no-store").json(claude(true)))
    api.use(guard.writeCheck, SRV.parseBodies({ limit: MAX_BODY }))
    api.post("/thought", (request, reply) => {
      const body = request.body as { target?: string; text?: string }
      const target = resolveTarget(body.target ?? "", preferences())
      const id = addThought(target, String(body.text ?? "")) as string
      reply.json({ ok: true, id: id.toUpperCase(), target: target.name })
    })
    // ... /run, /claude/login, /open-vscode
    router.use(API, (request, reply, next) =>
      api.handle(request, reply, (error) => next(error === undefined ? undefined : goalsError(error)))
    )
  }
}

export default goalsRoutes
  • The page server parses no bodies itself; each route parses its own:
    • page edits: 10mb
    • goals: 64kb
    • the app's /api: JSON5, 10mb
  • Why: a proxy (/ui) must stream the raw body, and a body can be read only once.
  • A second parseBodies() in a chain leaves an already-read body alone, instead of waiting for a stream that has ended.
    • Found when the saga pages' buttons hung.

A local server is reachable by every web page the browser opens, not just yours. These checks keep it to its own pages.

  • Loopback only: every server binds 127.0.0.1, so nothing on the network reaches it.
    • exception: the app's standalone API (yarn start:server) binds 0.0.0.0 with no host check, as Express did, for vite and LAN devices
  • Host check, on every request and websocket: 127.0.0.1:<port>, localhost:<port> or [::1]:<port>, else 403.
    • So a site pointing its own name at 127.0.0.1 (DNS rebinding) is refused.
  • Write token: random each run, given only to pages the server serves (window.SPELL_SERVER.token), sent as x-server-token.
    • a page from an older run must reload: "bad token: reload the page"
    • an Origin header, when sent, must be the server's own
  • resolveInside() is the ONE path check:
    • each segment decoded on its own: an encoded / (%2F) is a 400
    • .., . and NUL bytes refused
    • the result checked to be inside the root after resolving, as a last line
  • Dot files are 403 unless a mount says dotFiles: .git, .env and .spell-server.json stay private.
  • Live reload never reports them.
  • Page edits: .html files inside the checkout only, never committed.
  • If-Match MUST be the ETag the page was served with (size + modified time): missing 428, stale 409.
    • This catches writers that don't lock: VS Code, an agent's edit tool.
  • FileLock (<file>.lock, created atomically) makes cooperating tools take turns: page edits, epic, spell dev goals, the app's saves.
    • waits up to 20s; a lock older than 60s is a crashed holder's, and taken over
  • The app's /api takes no token: the editor calls it from vite's origin, through vite's proxy.
    • But a write whose Origin isn't this machine is 403.
    • Express had no check at all.

Known costs and open caveats, from the epic page's Caveats.

  • Slower under tsx.
    • goals.sh help: 0.05s with node, 0.18s under tsx.
    • yarn goals help: ~0.6s, mostly yarn.
  • Less portable: goals now needs three things from this repo.
    • the server package
    • tsx
    • the root package.json's "pageServer" field
  • Already-open saga pages need one reload: the token header moved from x-goals-token to x-server-token.
  • A page opened through ?file= with no page server running gets the extension's own server.
    • It has no saga page buttons and no /components/ui/, until spell server start.
  • "Open in VS Code" opens in the LAST FOCUSED VS Code window, not this session's.
  • The header's theme toggle and the Spell UI site's can disagree.
  • The editor has no site header, and the Editor tab leaves the page server's origin.
  • No edit mode on a worktree's page through the main server: PageEditor refuses dot paths too.
    • The worktree's own server edits it.
  • A main server started before this code (an old checkout, not restarted) has no /worktrees/.
    • mainServerUrl() checks /_server/epics first.
    • Without it, links fall back to the worktree's own server.
  • Phases are read by pattern, since the server is a leaf with no HTML parser.
    • So an epic page whose phase tags lose their phase or status (data-phase / data-status) shows as "planning".
  • /components/ui/ shows the bundle as last built: a library change shows only after a rebuild.
    • spell bundle --stale rebuilds it,
    • or the page server's next start,
    • or yarn site:dev while working.
  • _assets/icon-packs is a symlink into icons/: served fine, but a static deploy must copy through it.
