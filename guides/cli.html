spell Command Line

spell, from the CLI package: compile, check, explore, run, test and debug spell projects from a terminal, seeing exactly what the editor sees. Under spell dev, the repo's own tools: plan docs, docs pages, windows, worktrees, servers.

Plan docs: epic cli-additions (the language commands); epic epic-workflow, P1 (this refresh, and the Renames) Written for: people and agents working on spell or its tools Status: built (2026-10-01); every command brought up to date, and the Renames proposed, 2026-10-11; not yet reviewed by a person Checked: the language commands are covered by the CLI package's tests (see Sources); the spell dev tables come from each group's own help, 2026-10-11
  • One command, spell, runs spell's SOURCE through tsx: no build step, so it's always the working copy.
  • What spell says, the editor says: it loads projects and answers questions with the language server's own code.
    • Projects load through SpellDiskWorkspace.
    • Questions go to its SpellLanguageService and ScopeExplorer.
  • Three kinds of command:
    • 19 language commands, from compile to pony, and help: see Commands.
    • spell dev, the repo's own tools: 23 groups, 156 verbs. See spell dev.
    • spell epic, new: working with epics from any session. Being built (epic epic-workflow).
  • The epic tools now under spell dev are to move to spell epic: see Renames, the proposed names.
  • No target: the project here -- or, outside one, an autocompleting prompt.
  • A UI project's run opens in your browser.
  • Output goes to stdout; progress and screens go to stderr.
  • Exit codes:
    • 0: fine
    • 1: the spell has errors, or a test failed
    • 2: the command line is wrong
  • yarn cli:install in the CLI package, then spell --help.
  • The repo's tools: spell dev --help, then spell dev <group>.

Every project command takes the same kinds of target:

  • a .spell file, or a project folder
  • @workspace: the project here
  • a project by name, @library/cards, or its full id
  • a whole root, like @examples; --all means all its projects
  • none: see Target prompt

--verbose, on any command, shows spell's own logging on stderr.

A command is one function; long-running work happens in child processes or on Ink screens.

spell.mjs registers tsx, then imports main.ts. For spell dev, the lean devMain.ts main.ts silences console.* first, then commander picks the command <name>Command (session, args, options) => exitCode; CliSession owns the workspace, language service and explorer
  • spell dev's tree is built in one place, devProgram(), for both entries.
    • A pass-through runs a repo tool with the arguments as typed; which tool, and how, is TOOLS.
    • The plan-doc tool runs in the same process, loaded on first use.
  • Child processes, in runner/:
    • runProject.ts: runs and tests a project
    • speedTest.mts for speed
    • renderStatic.ts for static
    • They never import $/cli's values.
  • Ink screens, in ui/: they never take over the console (patchConsole: false).
  • <Project>.scopes.js: the Type Explorer's data for a page with no parser, e.g. <spell-app>.
  • Written after a CLEAN compile (compiled, no errors), always by SpellDiskWorkspace.writeScopes(). Four things call it:
    • the language server
    • yarn scopes
    • spell compile
    • spell watch
  • Checked: spell compile on the three example projects rewrote their checked-in packs unchanged.
  1. Each run is a fresh node process running SP.spellParser.speedTest(): a warm-up, then 20 timed passes.
  2. --against <ref> runs the same test on an older version of the code:
    • it checks the ref out into a temporary git worktree
    • it links our node_modules in, and COPIES the runner in
    • it runs there, then removes the worktree, links first
  3. The two sides take turns, run by run, so a busy moment hits both alike.
  4. A side's runs combine as the mean of their averages, the lowest min, and the highest max. With 3+ runs, one fluke (an average over 1.25x the median) is dropped.
  • parse and repl parse in a scope of their own.
    • With --in, that scope sits inside the project's: its types and phrases are known, but nothing typed lands in it.
  • Which rule parses a line, when none is given:
    • one line: statement, then expression
    • several lines: block
  • repl commits each line, so later lines know what it declared.
  • explain: rules by name or by the first word of their syntax; declarations as the editor's hover, less its first section (the declaring rule).
lineScope() · 8 lines 
/**
 * A fresh scope to parse lines in:  inside `project`'s, so its types and phrases are known -- or, with none, a bare
 * one with only spell's own rules.
 */
export function lineScope(project?: SP.SpellProject): P.Scope {
  if (!project?.scope) return SP.spellParser.getScope("cli")
  return new P.ProjectScope({ name: "cli", parentScope: project.scope })
}
  • It watches each project's folder (fs.watch()) for its spell files, CSS and project.json.
  • The kind of change comes from what's on disk, not the event: macOS reports a save as a rename.
  • A watched importer rebuilds from scratch after a project it imports, as if its project.json changed.
    • Why: a compiled import's declarations are only read on a full parse.
  • --test runs the tests in a child process, capturing its output: failures show under the project's row.
  • explore reloads the same way, keeping what's open and the cursor, by path.
  • No target, in a project's folder or below: that project, for every command.
  • Outside one, in a terminal: a prompt that completes like a shell.
    • Tab completes a root (@examples/), then a project, then "entire project" or one of its files.
    • Piped: an error.
  • The last 3 picks come first, from .recent-projects.json, git-ignored, one per checkout.
    • Before epic output-targets it was .recent-targets.json, moved on first read.
  • Keys arriving together -- typed while it's busy, or pasted -- are split and taken one at a time: Ink only names a key that arrives alone.
  • serve.ts: a small server on localhost, answering only its routes.
  • SPELL_NO_BROWSER=1 prints the URL instead of opening a browser.
  • icons --open: a gallery page of the packs' SVGs, with a filter box; click to copy a name.
  • run: when the project tries to show a UI, the child process tells spell.
    • Then a page with app's <spell-app src=...> serves the project as compiled for this run, its scope pack, and its imports.
    • The web component's build (dist-element/) is built first if missing.
  • serve runs this checkout's page server, starting it if it isn't running.
    • The editor (vite) is the page server's child, and the app's API is one of its routes.
    • It waits for the editor to answer, then opens it on the project.
    • Ctrl-C stops the page server, and so the editor, only if serve started it.
  • The language server's workspace, not a parallel loader: so the command line and the editor can't disagree.
  • spell dev starts lean: a repo tool is called many times a turn, and loading spell costs about half a second each time.
  • speed copies its runner into the other checkout: the $/ aliases only resolve inside a tree, so a script outside it can't import spell.
  • new writes its own files: the shared way to make a project (createProject()) adds an Untitled.spell. Default folder: @user.
  • Test name filter is --name: test takes several targets, so a positional name couldn't be told from one.
  • explore edits inline, one line: quick for the common case; several-line descriptions go to the editor (o).
  • Never writes into projects/test/: test projects stay frozen. format and e refuse; tests use temporary copies.
  • Browser runs use <spell-app src=>, not the app server: compiled JS and its scope pack, served beside each other -- no /api to run.
  • serve isn't yarn start: that also installs packages and stops the page server, which other sessions may be using.
  • Icon keywords match a word's start: names and aliases match anywhere. So bell finds dumbbell, but not brain by its keyword "cerebellum".
  • It runs spell's WORKING COPY: a half-done change in the language server or SpellProject can break spell with nothing in spell noticing.
  • The spell link runs the MAIN checkout's CLI.
    • A command a branch adds or changes shows only from that branch's own copy, its spell.mjs.
  • speed --against links today's packages into the old tree, and needs a ref from the monorepo on. A ref with different dependencies may not run.
  • format trusts formatting() to change whitespace only.
  • repl's live screen is tested through ink-testing-library; piped mode end to end.
  • explore's e: one-line descriptions only.
  • watch sees only what it watches: an imported project not watched doesn't rebuild its importer.
  • Under node, run skips what needs a browser, e.g. starting a UI; other browser-only code throws.
  • In the browser, run serves what was compiled at the start: no live reload.
  • @examples/Solitaire-import deals nothing, in the browser and in the app alike: a known spell runtime problem with importing an app project, not the CLI's.
  • serve opens only projects in the app's roots; others open the chooser.
  • The commands page's check reads group names only: a verb a group gains or loses isn't checked against it.
