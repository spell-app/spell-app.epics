spell Command Line

spell lint Hello answers Hello/Hello.spell:3:1 Don't understand "print greeting", and exits 1: the same error the editor underlines, because it runs the language server's own code. spell compiles, lints, explores, runs, tests and times Spell projects from a terminal. Its base is the kit's command line folder, and each repo adds its own commands to it: the language's, Spell UI's, the app's, and each repo's own tools, by noun (spell server start, spell pack build). Beside spell, epic holds the epic tools (epic pages, the pages Owen answers on, windows, worktrees, agents, airplane mode).

Epic pages: epic cli-additions (the language commands); epic epic-workflow, P1 (this refresh, and the Renames); P9 (the epic command); epic repo-split P13 (each repo's commands, under one spell) Written for: people and agents working on Spell or its tools Status: built (2026-10-01); every command brought up to date, and the Renames proposed, 2026-10-11; the epic tools moved to the epic command, 2026-10-12; every command brought up to date again, after epic repo-split, 2026-10-22. Not yet reviewed by a person. Checked: the language commands are covered by spell-app's command-line tests (see Sources); the tables come from spell --help and each command's help, and from epic --help and each group's, 2026-10-22 (before that: the spell dev tables from each group's own help, 2026-10-11, the epic ones from its verbs' help, 2026-10-12)
  • One command, spell, runs every repo's SOURCE through tsx. There's no build step, so it's always the working copy.
  • What spell says, the editor says, because it loads projects and answers questions with the language server's own code.
    • Projects load through SpellDiskWorkspace.
    • Questions go to its SpellLanguageService and ScopeExplorer.
  • Each repo brings its own commands, and spell --help lists them under the repo that added them:
    • the kit's: server, bundle, commands, wwod, pony, and help
    • spell-parser's: the eleven language commands, from compile to explain, and lang: see Commands
    • Spell UI's: icon, ssr, pack, design
    • spell-app's: app create | serve | vscode, and projects
  • The repo tools among them go by noun, then verb (spell server start; 14 groups under spell dev before epic repo-split P13): see Repo tools.
  • epic, a command of its own: epic pages, the pages Owen answers on, windows, worktrees, sessions, agents, airplane mode, requests between sessions. 63 verbs, called as epic <verb> <epic>#<id>.
  • The epic tools moved out of spell dev into epic (epic epic-workflow, P9): see Done. Their old spellings went with spell dev itself (epic repo-split P13).
  • No target: the project here -- or, outside one, an autocompleting prompt.
  • A UI project's run opens in your browser.
  • Output goes to stdout; progress and screens go to stderr.
  • Exit codes:
    • 0: fine
    • 1: the spell has errors, or a test failed
    • 2: the command line is wrong
  • yarn cli:install at the kit's root, which links spell.mjs onto your PATH, then spell --help.
  • A command's options, or a noun's verbs: spell <command> --help.
  • The epic tools: epic --help, then epic help <verb>.

spell-parser's language commands. Their work is spell-app's for now, through its language hook, so they need spell-app cloned. Every project command takes the same kinds of target:

  • a .spell file, or a project folder
  • @here: the project in the current folder
  • a project by its address, @spell/library/cards, owen@spell/x
  • a file in one, @spell/test/solitaire/Card.spell: its name has a dot
  • a group, @spell/library, or all of a space's, @spell: pick from their projects, or --all takes them all
  • none: see Target prompt

--verbose, on any command, shows Spell's own logging on stderr.

A command is one function; long-running work happens in child processes or on Ink screens.

spell.mjs registers tsx with the kit's node settings, then imports main.ts main.ts reads every installed repo's command list, adds them to one program, then commander picks the command <name>Command (session, args, options) => exitCode; spell-app's CliSession owns the workspace, language service and explorer
  • The base is the kit's spell/cli, in its src/cli/: it reads the command line, prints the help, and finds every installed repo's commands.
    • spellRepos() finds the repos: the kit, then each child repo in repos.json5, lowest first, whose package.json names its list, "spell": { "commands", "hooks" }.
    • addRepoCommands() adds them; a word two repos both add goes under each one's short name (spell parser check, spell app check).
    • Its barrel stays lean, node built-ins, commander and chalk, because spell help loads every repo's list. Each list imports its command's work only when it runs.
    • findCheckout(): a command works on the checkout the current folder is in, else the kit spell runs from.
  • Each repo's own folder adds its commands: spell-parser's, Spell UI's and spell-app's src/cli/.
    • spell-app's language hook, in hooks.ts, does the work of spell-parser's commands, because they find projects the app's way for now.
    • Its loadApp() loads consoleGuard.ts FIRST, which silences console.*, then Spell, then the commands' work.
  • epic's verbs are built in EpicProgram, run by spell-epic's bin/epic through the lean epicMain.ts.
    • epicArgs.ts reads <epic>#<id>, and hands the epic tool its arguments.
    • Every verb runs without Spell (epic epic-eject P5).
  • Child processes, in runner/:
    • runProject.ts: runs and tests a project
    • speedTest.mts for speedtest
    • renderStatic.ts for ssr, Spell UI's
    • They never import spell-app/cli's values.
  • Ink screens, in ui/, which never take over the console (patchConsole: false).
  • <Project>.scopes.js: the Type Explorer's data for a page with no parser, e.g. <spell-viewer>.
  • It's written after a CLEAN compile (compiled, no errors), always by SpellDiskWorkspace.writeScopes(). Four things call it:
    • the language server
    • spell-app's yarn lsp:scopes
    • spell compile
    • spell watch
  • Checked: spell compile on the three example projects rewrote their checked-in packs unchanged.
  1. Each run is a fresh node process running SP.spellParser.speedTest(): a warm-up, then 20 timed passes.
  2. --against <ref> runs the same test on an older version of the code:
    • it checks spell-parser out at the ref into a temporary git worktree
    • it links the kit's node_modules in, and points the runner at that worktree's src/spell/
    • it runs there, then removes the worktree, links first, even on failure
  3. The two sides take turns, run by run, so a busy moment hits both alike.
  4. A side's runs combine as the mean of their averages, the lowest min, and the highest max.
    • With 3+ runs, one fluke (an average over 1.25x the median) is dropped.
  • parse and repl parse in a scope of their own.
    • With --in, that scope sits inside the project's. Its types and aliases are known, but nothing typed lands in it.
  • Which rule parses a line, when none is given:
    • one line: statement, then expression
    • several lines: block
  • repl commits each line, so later lines know what it declared.
  • explain finds rules by name, or by the first word of their syntax. It shows a declaration as the editor's hover does, less its first section (the declaring rule).

/**
 * A fresh scope to parse lines in:  inside `project`'s, so its types and phrases are known -- or, with none, a bare
 * one with only spell's own rules.
 */
export function lineScope(project?: SP.SpellProject): P.Scope {
  if (!project?.scope) return SP.spellParser.getScope("cli")
  return new P.ProjectScope({ name: "cli", parentScope: project.scope })
}
