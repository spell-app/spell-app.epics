The Python Target

How spell compiles to Python a person would write by hand, what it runs on, and why it reads the way it does.

Written for: a developer about to change what the Python writer writes, port a core method to Python, or run a compiled program Status: merged P1-P16 into main, 2026-10-11; built P17-P26, P29 and P30 on branch python-target, not merged yet; parked P27 and P28, waiting on epic drawable-thing merging into main; epic Python Target Checked on: branch python-target, 2026-10-11, against the code, the test programs' snapshots and the plan doc's decisions (see Sources)
  • spell compile Cards --target py writes Cards.compiled.py: Python a Python programmer would write, and happily edit.
  • It's spell's first target that isn't JavaScript underneath: one target, py, on asyncio.
    • A function that waits is async def, and every call of it is awaited.
    • A program that never waits, like FizzBuzz, is plain Python.
  • Compiled Python runs on spell_core, the Python twin of the core.
    • It lives in the py package, with the TypeScript that writes Python and the web app's Python, spell_quart.
    • It needs nothing but Python's standard library, 3.12 or later.
  • All six test programs print in Python exactly what they print in JavaScript.
    • The core contract checks it on every test run.
    • That includes the drawn page: Python draws HTML text, as there's no page to draw on.
  • Type hints come from what spell knows of each value, and pyright checks them, as tsc checks the TypeScript.
    • pyright finds no errors in any test program.
    • Where spell can't tell what a value is, the hint says so: Any.
  • Compiled code counts positions from 0, as Python and JavaScript do, on every target.
    • Spell that counts from 1 is turned into those positions as it compiles.
    • Neither core knows how a project counts.
  • Python needed things the JavaScript targets now have too:
    • a seedable random owned by the core, and a machine-readable list of its methods
    • spell's own values in the tree, not JavaScript spellings like 'up'
    • rounding said in each language's own words
  • Python is compile-only for now: spell run and spell test still run JavaScript. spell_core's own runner runs the Python.
  • A program compiled to Python can be a web app, on branch python-target (see Python apps on the web):
    • its logic runs in Python, on a Quart server, a game per visitor
    • the browser draws it with its own classes compiled to javascript, from the things Python sends
    • a test can play it the same way, by the page's messages, checking what comes back (see Playing by the page's messages)

Everything spell has for Python is in one package, packages/py (P21): Owen's "keep all of the python stuff in one place".

  • ts/: the TypeScript that writes Python, imported as $/py (PY).
    • PY.PyWriter and PY.PyBaseWriter: the Python itself
    • PY.ElementsWriter: a program's drawing half, in javascript
    • PY.pyText: Python's punctuation, its indents, quotes and line breaks
    • PY.quartApp(): a program's web app
  • core/: spell_core, what compiled Python imports (see 5).
  • quart/: spell_quart, which serves a program as a web app (see Serving it on Quart).
  • Spell imports it, for its Python target; it imports only the parser and util.
    • core/ and quart/ are uv projects of their own, where yarn doesn't look.
    • Its yarn review covers all three: the TypeScript's checks and tests, then ruff and pytest in each uv project.
  • Its guide for agents: AGENTS.md.
  • A project lists its targets in its project.json: "targets": ["py"].
  • Or for one compile: spell compile <project> --target py.
  • js/solid is always compiled too: the editor, the runners and the language server run it.
  • Each compile runs pyright on the Python it wrote, and says how many errors it found, e.g. "2 pyright errors", listing them.
    • They don't fail the compile.
    • There's no flag for it: it always runs.

spell_core has a runner of its own, spell_core.run: it runs one compiled program, seeded as spell run seeds the JavaScript.

  • uv run --project packages/py/core runs it on the Python uv pins for spell_core (3.13), with spell_core importable. Nothing to install but uv.
  • --seed n: the random numbers start from n, so the game deals the same cards every run, and the same cards as the JavaScript run with that seed.
    • Without it, each run deals differently, as in JavaScript.
  • --no-pauses: a pause doesn't wait.
  • --page: when the program ends, print what it drew, a blank line then its HTML on one line.
  • --state: when the program ends, print its state as JSON, by id (see The state, by id).
  • The program's own folder comes first on Python's import path: a project it imports (from cards import Card) sits beside it.
  • Printing a whole thing (print the card) goes to stderr: Python's Card(rank='queen', ...) where node prints its own dump. Every other line is the same as JavaScript's.

Python a Python programmer would write: Owen's "as idiomatic as Python can possibly be". Python's own words wherever it has them; the core only where it has none.

  • A native loop over a range(), not a core call per number.
  • (number / 15).is_integer() asks whether the result is whole: in Python, 45 divided by 15 is 3.0, not 3.
  • print() where Python prints a value as spell does; the core's console otherwise.
  • It imports only what it uses: FizzBuzz imports nothing.
FizzBuzz.snapshot.py · as compiled · 16 lines 
from __future__ import annotations

def play_fizzbuzz() -> None:
    """File FizzBuzz.spell"""
    for number in range(1, 101):
        if (number / 15).is_integer():
            print(number, "fizzbuzz")
        elif (number / 3).is_integer():
            print(number, "fizz")
        elif (number / 5).is_integer():
            print(number, "buzz")
        else:
            print(number)

Names follow PEP 8, Python's style guide: one line in the naming table, Naming.PYTHON.

  • functions, methods, variables and properties in snake_case: turn_face_up
  • classes in PascalCase: Card
  • constants in capitals joined by underscores: Card.RANKS
  • A name that clashes steps aside with PEP 8's trailing underscore:
    • a Python keyword, as any kind of name: class_, from_
    • a builtin, only as a variable or parameter, where it would hide it: list_, max_
    • a spell_core helper compiled code imports, only as a variable: position_ (see Clashes in today's spell)
    • a member keeps its name: card.type, pile.max
    • soft keywords stay names, such as match and type
  • A spell name never becomes a dunder, a name with two underscores each side like __init__: PEP 8 says never to invent one.
  • spell_core gives lists and things the dunders Python documents, so Python's own words work on them:
    • len(deck)
    • card in pile
    • for card in deck
    • deck[0]
    • a == b
    • printing a thing
Naming.ts · Python's map · 5 lines 
static readonly PYTHON: NamingMap = {
  type: "PascalCase",
  constant: "SCREAMING_SNAKE_CASE",
  all: "snake_case"
}
  • A thing is a Python class:
    • its docstring from spell's comment
    • constants as tuples; properties declared in the class body with prop()
    • getters as @property, with self
    • made by keyword: Card(rank="queen", suit="spades")
  • A spell list is a real Python sequence (a MutableSequence):
    • an item: deck[2]
    • how many: len(deck)
    • a loop: for card in deck
    • if not stock: for "the stock is empty"
    • a position out of range is None, as spell reads it, not an error
    • owners ("a card is in one pile at a time"), guards, and JSON with "@type"
  • Native operators where the kinds are known:
    • == and in
    • f-strings
    • isinstance()
    • is None
  • A block passed along is a one-line lambda, or a def lifted above the call.
  • A bare return in a loop's body ends that turn only: it's written continue.
Cards.snapshot.py · Card, in part · 38 lines 
from spell_core import core, Thing, List, prop, h, spell_position


class Card(Thing):
    """definition of a Card with nice english aliases for working with it"""

    # card ranks
    RANKS = ("ace", 2, 3, 4, 5, 6, 7, 8, 9, 10, "jack", "queen", "king")
    rank = prop(one_of=RANKS)

    # card suits
    SUITS = ("clubs", "diamonds", "hearts", "spades")
    suit = prop(one_of=SUITS)

    @property
    def color(self) -> str:
        """color as derivation of suit"""
        if self.suit in ["diamonds", "hearts"]:
            return "red"
        return "black"

    @property
    def value(self) -> float:
        """value as a derivation of rank"""
        return spell_position(core.position_of(Card.RANKS, self.rank))

    def is_a_suit(self, suit: Any) -> bool:
        """\"card is a spade", "...is a club" etc"""
        return self.suit == suit

    @property
    def name(self) -> str:
        """name as a derivation of name/suit"""
        return f"{self.rank}-of-{self.suit}"

    @property
    def pile(self) -> Pile | None:
        return Pile.owner_of(self)

class Deck(List):

pause for 50 msec is the one place the two targets differ.

  • py: plain functions; a pause is core.pause_for(50, "msec"), which sleeps.
  • py/asyncio: a function that pauses, or calls one that does, is async def, and every call to it is awaited.
    • The pause is await core.sleep(50, "msec").
    • At the module's top level, where Python can't await, it runs through asyncio.run().
  • Which functions wait is worked out by NAME, over the whole project: if one method called turn_over waits, every method of that name is async.
    • So an awaited call never reaches a plain function, at the cost of a few needless asyncs.
  • A project's declarations say which of its methods wait, "waits": true.
    • So Klondike, importing Cards, awaits Cards' turn_face_up().

    Flip card to opposite direction
    Note that this will animate if you `wait for turn the card face up`

Python has no page, so a to draw method builds HTML.

  • spell_core's h() builds an element tree: tag, attributes, children. str() writes it as HTML.
  • It writes exactly what the JavaScript run's page writes for the same drawing, quirks included, so the core contract compares the two line for line.
  • An app (class Game(App)) is drawn when the page is written, at the end, showing each thing as the program left it.
  • core.draw_thing() and core.draw_items() draw a thing, or a list's items, inside another drawing.
  • Clicks do nothing here: there's nothing to click, and the tree keeps no click handlers. A web app's page does take them (see Python apps on the web).

A project can say its lists count from 0, as Python and JavaScript do: Owen's "let's try the first item is 0 here".

  • It's "listsStartAt": 0 in the project's project.json. Without it, lists count from 1, as before.
  • It works on every target, the JavaScript and TypeScript ones too.
  • Only NUMBERS change: "item 3 of the deck", "the position of the queen", a loop's position.
    • Ordinal words don't: "the first card" and "the last card" mean the same either way.
    • "position of queen in card ranks" is 12 counting from 1, 11 counting from 0.
    • "position of joker in card ranks" is still nothing, never -1 or 0.
  • Negative positions don't change: -1 is the last item, -2 the one before, whatever lists start at. It's Python's own deck[-1].
  • The core's position methods are told where counting starts, on every call: a last startAt, 1 when left out.
    • Per call, not one switch for the whole program: a library counting from 1 and a program counting from 0 share one core, and neither reads the wrong item.
  • Compiled code uses each language's own words where it has them:
    • Python: deck[0]; JavaScript: deck.at(0)
    • a range, "cards 0 to 3", through the list's own between(), since spell's ranges include their end and take negative ends
  • The hover text and the Type Explorer say "counts from 0" in such a project.
  • Counting from 1, "item 0" is nothing now. It used to read the SECOND item; two more position bugs were fixed on the way.
  • The test program CardsFromZero is Cards counting from 0, and prints the same game.

spell_core is what compiled Python imports to do what Python has no word for: the Python twin of the core.

  • In the core package's py folder, beside the JavaScript it ports.
  • The standard Python layout: a pyproject.toml, and the spell_core folder beside it.
  • Standard library only: compiled programs need nothing else installed.
  • Its tests (pytest) and its tidying (ruff) run through uv.
    • Core's yarn test runs them, so yarn review does too.
    • So core's scripts need uv on the machine.
  • Compiled code imports one object, core, and the classes it extends: from spell_core import core, Thing, List, App, prop, h.

A machine-readable list of the core's methods, so a port can't miss one: spellCore.declarations.json.

The Core Reference shows it as a page, file by file, with Python's name for each and whether spell_core has it yet.

  • Written in the format projects already write for themselves, a <Project>.declarations.json.
  • 127 names on spellCore, and 12 that compiled code imports.
  • yarn gen:declarations, in core, writes it; a test fails when it's out of date.
  • A Python test checks spell_core against it, in snake_case: a missing method fails, unless it's listed as not ported yet.
  • It found methods spell writes that the core didn't have: absoluteValue, now added, and three for rounding, still missing (see Limits).
  • spellCore.seedRandom(n), after which every random is repeatable.
  • Its own number generator (Park and Miller's) and its own shuffle: no lodash, no Math.random.
  • The shuffle walks from the front, as lodash's did, one random number per item: so the saved games deal the cards they always dealt.
  • spell_core copies both exactly: one seed deals the same cards in both languages.
  • The JavaScript runs take a seed too, spell run --seed n, and so does spell test. The contract seeds with 1.

A program compiled to Python can be a web app: its logic runs in Python on a server, and a browser page draws it.

  • Owen's ask: "python compiler outputs compiled JS web components for the HTML bits", and "spell apps" in Python served by a Python web framework.
  • Python keeps everything that changes things, and every event handler.
  • The page draws with the program's own classes, compiled to javascript, from the things Python sends.
  • The two keep in step through the program's things, each sent by its id: the whole state once, then only what changed.
  • Built on branch python-target as P17-P20, not merged yet.
Serving Solitaire as a web app · from the repo root · 4 lines 
yarn workspace @spell-app/app build:page                       # the page side, once:  packages/app/dist-page/
cp -R packages/spell/projects/test/Solitaire /tmp/Solitaire   # never compile a test project in place
spell compile /tmp/Solitaire --target py/asyncio              # the program, its drawing half, and its app
uv run --project packages/core/py-quart python /tmp/Solitaire/Solitaire.app.py   # http://localhost:5000
  1. Compile: Compiling Solitaire to py/asyncio writes its Python, and two files beside it: its drawing half in javascript, and a short Quart app, Solitaire.app.py.
  2. Serve: Running the app starts a Quart server, on spell-quart, a package of its own beside spell_core.
  3. A visitor comes: A browser opens the page. A cookie names the visitor, and the program runs once for them, on a core of their own: their own deal.
  4. The page connects: The page loads the javascript core, Spell UI and the drawing half, and opens a WebSocket back to the server.
  5. The whole state: Python sends every thing the program keeps, each with its id. The page reads them into mirrors, javascript things standing in for Python's, and draws the board from them.
  6. A click: Clicking a card sends card-click up the WebSocket, with the card's id. Python finds that card, and runs the game's handler, in Python, where it was written.
  7. Only what changed: After the handler, and at each pause in it, Python sends a patch: only the things that changed. The mirrors take it, and what draws them redraws, so AutoPlay animates.

A program's state is its things as JSON, each with an id, so a thing can be found again, and a card in two places stays one card (P17).

  • Both cores have a state writer and a mirror: StateWriter and StateMirror in Python. Their twins are in the javascript core's state.ts.
  • The writer writes the same JSON as to_json(), plus an id on each thing and spell list, "@id", after its type.
    • The first mention of a thing is whole; each later one is {"@id": "3"} alone, as JSON-LD writes a reference (J48).
    • Each writer counts its own ids from 1, and keeps them: one writer per page (J49).
    • A thing's plain fields go too: what its constructor was given and doesn't declare, such as a foundation's symbol.
  • The mirror reads each new state INTO the things it read before, by id.
    • A thing it has keeps being the same object: changed in place, so what draws it redraws.
    • A new one is made; a property a thing no longer has is unset.
  • Reading JSON back, core.from_json() and spellCore.fromJSON(), now goes through a mirror, so JSON with ids keeps a thing as one (J51).
  • A program's state is its top-level things, by their Python names (J50). spell_core's runner prints it when the program ends, with --state.
  • A saved state, stateById.expected.json, is written and read back by both cores' tests: they agree on every character.

After the first state, a page needs only what changed: a click turns over a card or two, not the deck (P18).

  • spell_core notes each change to a thing's property, or to a spell list's items, and tells every state writer still alive: note_change().
  • StateWriter.patch() writes the things that changed since the writer last wrote, as a list.
    • Each one whole, and what it holds by id (J52): a card moved to another pile is the two piles, each naming its cards by id.
    • A thing new since then, held by one that changed, is written whole inside it, with a new id.
    • [] when nothing changed.
  • A mirror reads a patch as it reads any state.
  • Only Python's core tracks changes: the javascript core writes whole states, and reads patches (J53).

Checked click by click

A change nobody noted would leave a page wrong without a word, so the core contract checks every click.

  • It plays Solitaire, Klondike and OutlineSolitaire in Python, seeded, 300 card clicks each: patches_in_a_game.py.
  • After every click, a mirror reads the patch, and must hold the same state as the game written whole.
  • A click that throws fails the test too.
  • In Klondike's Python, every click failed (I12).
  • Klondike adds a method to Cards' Card, to play a card: the Python writer wrote it as a bare function, never set on the class.
  • Fixed: it's def _card_play(self), then Card.play = _card_play. The javascript sets it on Card's prototype the same way (J54).
  • pyright dislikes that line: one more error pinned in Klondike's snapshot.
  • Until then, nothing had clicked anything in a test (C1).

Compiling to either Python target also writes the program's drawing half in javascript, <Project>.elements.js, for a program that draws (P19).

  • P.ElementsWriter writes it, on the javascript writer:

The page's side

The javascript core's startPage() starts a page from Python's state.

  • It reads the state into mirrors, Python's property names read as javascript's: is_set_up is isSetUp (J57).
  • It binds the program's things (adopt()), and starts the app the state holds.
  • Its receive() reads each patch into the same mirrors.
  • sendCall() and sendTrigger() send a call or an event, each thing in it by its id.

How it's checked

  • The core contract runs Solitaire, Klondike and OutlineSolitaire in Python, seeded, and draws each from its state, with its elements file, on the contract's fake page.
  • The board it draws must equal the javascript run's, exactly.
  • A click on a face-up card must send card-click with the card's id, which Python then runs.
  • A fake page, not a real browser (J59): the real browser comes with the Quart app's test.
  • A drawable type doesn't get its own custom element class yet, a class the browser knows for <solitaire-card> (I13).
  • It waits on epic drawable-thing's P10, which writes those classes, still on its own branch.
  • Until then the page draws with the core's own drawing, inside the drawable tags it already makes (J56).
  • A drawable's plain properties as attributes on its tag wait with it (J47).

A game per visitor

Each browser plays its own game: a cookie names the visitor, and the program runs once for each (Q24, C4).

  • Compiled Python's core stands in for the core of the program running now: spell_core's using_core() gives each visitor's run its own.
    • It goes by Python's context variables, so a timer a click starts keeps the visitor's core.
    • A plain run, with no host, uses the one default core, as before.
  • A visitor's tabs share their game: a click in one shows in every one.
  • Each tab gets the whole state when it opens, then a patch after each of its clicks, and at each pause.
  • A message that fails is logged, and the page goes on.

Pauses send what changed so far

  • On asyncio, a pause tells its host first (core.before_pause): the server sends every tab what changed so far, then waits.
  • So AutoPlay animates on the page, as it does in the editor's runner.

An app you've edited is yours

  • The app's first line holds a hash of the rest (J45).
  • Compiling again rewrites the app only while that hash still matches: an edited one is left alone.

Settings

  • $PORT: the port it serves on, else 5000, which AirPlay often takes on a Mac.
  • $SPELL_SEED: every visitor is dealt from that seed, so each gets the same game; a test's.
  • $SPELL_PAGE_ASSETS: where the page side was built, else the repo's own build, made by yarn build:page in the app package.

What it costs on the wire

  • Measured by the browser test below, Solitaire on seed 1, on 2026-10-11.
  • A stock click's patches run from about 100 to 640 characters, against a state of about 8,000.
  • AutoPlay sent 8 patches, one at each pause: so the page animates.

How it's checked

  • spell-quart's own pytest, on Quart's test client: the page, the state and its patches, pauses and all, and a game per visitor.
  • A browser test, quartApp.test.ts, compiles Solitaire, serves it, and plays it seeded in headless Chromium:
    • the page draws the javascript run's board
    • a click on the stock plays in Python, and the discards change
    • AutoPlay sends more than one patch
    • two visitors each play their own game
    • compiling again leaves an edited app alone, and rewrites an unedited one

From the plan doc's questions (Q) and judgement calls (J): each links to the full reasoning, and the options turned down.

  • Python a person would write by hand and happily edit, not a thin layer of core calls imitating JavaScript (Q8).
  • The cost: the writer leans on what kind each value is much harder than the JavaScript one does, and spell_core's lists and things act like Python's own.
  • Every Python phase was judged by "would a Python programmer write this?", not only "does it run?".
  • So compiled Python looks like any other Python (Q9). Owen's start: "python names should be snake_case".
  • Clashes take PEP 8's trailing underscore, never a new dunder (Q14). PEP 8 on dunders: "Never invent such names; only use them as documented."

  • A spell variable named position would hide the helper, so it steps aside.

  • h() builds a tree rather than a string, so tests and a later terminal target can read it (J29).
  • It copies what the JavaScript run really prints, quirks and all, because the contract compares them (J31).
  • Plain functions by default: with no page, a pause only slows the program down (Q3).
  • Owen asked for asyncio as an option, "or twisted python?": asyncio, as it's built into Python and what new code uses.
  • It became a target of its own, py/asyncio, not a project setting, so the contract runs both on every test program (Q18).
  • Which functions wait is worked out by name, so a call is never left unawaited: Python's unawaited call does nothing at all, silently (J34).
  • The declarations carry "waits": true, because an importing project can't see it in its own source (J35).
  • Python can't print node's dump of an object, and shouldn't: it shows node's insides, not the card.
  • So a whole thing's dump goes to stderr, each language its own way, and the contract compares stdout only: no rule for which lines to skip (Q4, Q17).
  • Modern Python has hints, and editors use them; the writer already knows most kinds (Q5).
  • pyright, because it's what VS Code's Python extension runs, and an npm package.
  • Hints only where known, never Any, which reads noisier and turns checking off anyway (J37).
  • Basic mode, with the solitaire games' errors pinned: strict mode would report hundreds on spell_core's dynamic parts (J38).
  • One package, two languages, beside the code it ports; core's yarn test runs both (Q6).
  • Python 3.12 or later: the oldest still widely installed with int | None hints, match, and f-strings that hold any expression (Q11).
  • pyright and Textual are dev dependencies only; spell_core stays standard library only (Q19).
  • The core respects the setting call by call, rather than staying 1-based while the compiler shifts every position. Owen: "core methods in JS should respect listStartAt" (Q10).
  • -1 stays the last item, because it's Python's own way. Owen: "-1 = last only if this is pythonic" (Q7).
  • Each language's own words where it has them (Q15), but a range through between(), never a slice: "cards 2 to -1" would be empty as slice(2, 0) (J3).
  • Counting from 1, item 0 is nothing, like a position past the end (Q16).
  • The contract used to patch JavaScript's Math.random from outside.
  • Python can't share that trick, and has no lodash (Q13).
  • Owen: "add runtime seed mechanism to JS/spellcore".
  • The shuffle keeps lodash's order, so the saved games needed no rebase (J8).
  • Python is checked by the test programs' snapshots and the contract, not a third line in every rule test: hundreds of hand-written Python lines, for little more than the snapshots catch (Q12).
  • Owen added the web app after the Doc Review, 2026-10-11, and answered seven questions on it, Q20 to Q26.
  • The page draws with compiled javascript, not Python's HTML (Q20, A). Owen's first answer had Python draw the page, as Phoenix LiveView and htmx do; he revised it the same day: "the python writer can use the js/solid writer to create the components".
  • The whole state by id first, then only the changes, each its own phase, before the page that reads them (Q21). Attributes on a drawable's tag, Q21's third part, wait for the element classes (J47).
  • One WebSocket per page, rather than posting clicks with a stream back (Q22).
  • Quart rather than Flask: the same API, on asyncio, so a pause awaits and one thread serves every page (Q23).
  • A game per visitor rather than one shared game (Q24): it needed a core per visitor (C4).
  • A generated app file, every route spelled out, rather than a create_app() hiding them (Q25); left alone once edited (J45).
  • A package of its own, spell-quart, so spell_core stays standard library only (Q26, J44).

What's open, from the plan doc's caveats (C), todos (T) and issues (I).

  • spell's own run and test commands don't run Python yet: spell run has no --target py, nor has spell test (T4). Use spell_core's runner.
  • Every machine that runs the tests needs uv, and through it Python 3.12 or later, or the Python half of the contract and of core's tests fails (C2). uv fetches the pinned Python by itself.
  • A compiled program finds spell_core only from inside the repo: it isn't on PyPI yet (T2).
  • spell compile --stdout still writes an imported project's compiled files, even into the frozen test projects (I11).
  • pyright finds 9 errors in the solitaire games' Python, which still runs correctly: Solitaire 2, Klondike 3, OutlineSolitaire 4 (C3, J38).
    • All but one are a value spell's tree says may be nothing, used as if it's there: a card's pile, a list's last item.
    • One calls a value spell only knows as an object.
    • Klondike's third is Card.play = _card_play, a method set on another project's class (J54).
    • Each fix needs spell to know more, e.g. a pile that's never empty: later type work.
  • Clicks are run in Python, but never compared with JavaScript's (C1).
    • Since P18 the contract plays each solitaire game in Python, 300 clicks, and a click that throws fails it (see Only what changed).
    • What a click prints or draws isn't checked against JavaScript's, on any target.
    • Events a program fires itself are run and compared.
  • A rule no test program uses isn't checked in Python at all (Q12).
  • A program that rounds a number throws, on every target: round, round up and round down compile to core methods no core has (I3).
    • Not added, because JavaScript rounds 2.5 up to 3, and Python's round() to the even 2.
    • Which one spell means is Owen's call.
  • Things and lists read any undeclared name as None, so a compiled self.name works as spell's does (I5).
    • It hides typos: a misspelt method call fails as "'NoneType' object is not callable".
    • hasattr() is always true.
    • getattr(card, "x", 0) gives None, not 0.
    • So hand-written Python should use x or default instead.
  • A list class whose set-up adds items puts them into every scratch result too, every filter(), slice and copy, in both cores (I6). Cards never meets it.
  • Every change to a spell list copies its items, as JavaScript's do: fine for 52 cards, slow for many thousands (I9).
  • Only a program that imports no other project is served whole: Klondike, which imports Cards, isn't yet.
    • Compiling doesn't copy an imported project's files beside the app.
    • The app it writes lists no imported project's drawing half for the page.
    • Solitaire, with its cards built in, is the one served and checked in a browser.
  • The page side comes from the repo's own build, made by yarn build:page in the app package: an app run outside the repo needs $SPELL_PAGE_ASSETS.
    • spell-quart isn't on PyPI, like spell_core (T2).
  • One server process holds every game, in memory (C4).
    • Restarting the server ends every game.
    • Several worker processes would split a visitor's clicks between games.
    • No game is dropped yet: each visitor's stays until the server stops. The plan meant to drop one idle for an hour or so.
    • Things an imported project makes at its top level are shared by every visitor: it's imported once per process.
  • A drawable type has no custom element class of its own yet (I13): see The page draws in javascript.
  • Only py/asyncio writes an app: a plain py program's handlers and pauses don't await, so it stays a terminal program.
  • spell run doesn't start the app: run it with uv (T4).
  • A list whose item type is defined after it gets a static method, instance_type(), where item_type = Card would do (I10). spell_core reads neither yet.
  • Reading off what may be nothing is still getattr(x, "name", None), and a method called on what may be nothing isn't guarded.
  • The editor's one-file compiled view still counts from 1 in a project counting from 0 (T3).
  • Nothing in Python reads the words file yet: Python has no Thing Explorer.
  • Drawing is HTML text, or a web app's page; a terminal target is a future epic (T1).
