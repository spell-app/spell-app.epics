What people do with an agent

What a person does, step by step, when an agent changes or makes something in the Spell editor: which of it the editor does today, which is missing, and the calls to make before any planning.

Epic page: epic agents-in-spell Written for: Owen, reviewing the agent flows before any planning; and whoever plans them after Status: draft (discussion) Researched on: branch agents-in-spell, 2026-11-20. The editor's flows were checked by reading the code; the other tools' by their own pages (see Sources). Guesses say so.
  • The first flow is BUILT: select a part, say what should change, and an agent changes the code.
    • It's the editor's Change This (⌘K), from epic editor P18, T62, T66 and I138.
    • It works the way Claude Design, v0, Lovable, Bolt and Cursor all do: select, say, see it change.
    • The agent is Claude Code on this Mac, started headless, allowed to edit only the project's files.
  • What it lacks, next to those tools:
    • a conversation: each request starts afresh, with no follow-up
    • a review before the change lands: it goes straight into your draft, and ⌘Z is the way back
    • more than one part, and more than one request at a time
    • new files: one the agent makes shows only once the project is opened again
    • any agent but Claude Code, and anywhere but this Mac (the public preview hides it)
  • Making something NEW (an app, a site, a page, a view) has no agent flow yet.
    • The pieces are there: New App, a site's new page, examples to start from, drafts, the compile.
  • Review, undo and preview are mostly there already, built for people's own edits:
    • undo: the editor's history, one step per changed file
    • review: your draft, and Publish's side-by-side diff
    • versions: a draft kept as a version, and every publish zipped into the project's versions
    • preview: the running app takes the edit as it runs, its state kept
  • Grow Change This into the ONE agent flow, rather than building a second: the same box for a selected part, a page, or a whole new app.
  • Every agent change lands in the person's draft, as ONE undo step per request, with a version kept before it starts.
  • Then add the conversation, a queue of requests, and "make me an app" from the home page.
  • The word in code and in what people read is agent ().
  • ONE agent client, in the kit's own new src/agents/ ().
  • Change This KEEPS its flow, but its plumbing is replaced: AG-UI events in place of the inbox file and the log reader, MCP tools in place of the agent's free run of the files (). How that looks: section 2, "On the new plumbing".

The flow Owen called "change this" (epic editor, its kickoff): "select things and say 'change this.' Once that bridge has been crossed, it's much easier to think about full-on agentic development." It's built, and on main.

Checked by reading the code: ChangeThis and the changes folder on the server.

return [
  promptFor(request, spell),            // "run spell app changes take c3, then do what it says"
  "--print",                            // headless, no terminal
  "--permission-mode", "acceptEdits",   // edits inside the project's folder, no asking
  "--permission-prompts", "none",       // anything else would ask, nobody answers:  refused
  "--tools", "Read,Glob,Grep,Edit,Write,Bash",   // no web, no agents
  "--output-format", "stream-json",     // its events, as they happen:  the box's progress line
  "--settings", '{"disableAllHooks":true}', "--strict-mcp-config",  // none of this Mac's hooks or MCP servers
  "--add-dir", dirname(request.diskPath),        // the draft may be outside the project folder
  "--allowedTools", "Read", "Glob", "Grep",
  `Bash(${spell} app changes take:*)`, `Bash(${spell} app changes done:*)`
]

Every tool has the same core: select, say, see. They differ in what you can tweak without the agent, and whether a change waits for you to accept it.

tool select, then tweaks without the agent lands back out
Spell's Change This a box under the part; words and pictures the Inspector: every property of the part, edited live, written into the source straight into your draft ⌘Z, a step per file; Revert Changes
Claude Design a comment on the element; several queued, sent as a batch type over text; "knobs" for spacing, colour, layout, which Claude makes for each design in the design "apply across the design" for wider changes; history not documented
v0 Design Mode a design panel for the element, and words type, colour, spacing, borders, radius, shadow PENDING until Apply; before / after toggle each Apply is a new chat version, with its diff
Lovable Visual Edits Edit, then the element Figma-like controls, Tailwind classes; no prompt, no cost at once every change a version; revert is the whole project
Bolt Visual Edits select mode in the chat box edits batched above the chat box batched until Save changes version history
Cursor Design Mode the element in its browser, then the agent; several since 3.7, voice and drawing too drag to move and resize; sliders, palettes, design tokens the agent edits the code, hot reload the editor's undo, git
Figma Make "point and edit", then words its properties panel, in new files at once version history (often reported broken in its forum)
  • The Inspector IS the "tweaks" panel, with no agent and no cost: it edits a part's real properties, and writes them into the Spell, readable.
  • The running app keeps its state through the edit: the game in progress stays.
  • The selected part knows its line in the source, so the agent starts at the right place.
  1. A conversation. Each request is a fresh session, with no memory of the last. "Now make it bigger" means nothing to it.
  2. A look before it lands. The change goes straight into your draft. v0 and Bolt hold it until you say Apply.
  3. More than one part. The Inspector selects several (Shift-click, a rubber band), but Change This asks about one.
  4. More than one request. One at a time; Claude Design queues comments and sends them together.
  5. New files. A file the agent makes shows only when the project is opened again (the class's docs say so).
  6. One undo for one request. A request that changes three files is three ⌘Zs. The history can already group changes (it's an UndoStack, with transactions).
  7. Any agent but Claude Code, anywhere but this Mac. Decided: the new plumbing below (). Which models and where: models.html, local-models.html, byo-agent.html.
  8. Its words name Claude: "Tell your buddy Claude:" where the settled word is agent: .

The person's steps stay exactly as above. What changes is underneath: how the request reaches the agent, how the box hears back, and what the agent may touch.

step today on the new plumbing
the request goes out written into a file on this Mac, the inbox (ChangeRequests), with a lock and a heartbeat an AG-UI run starts: the request is its first message, the selected part its context
an agent takes it Claude Code listening, or started headless by the page server (ClaudeStarter) the kit's one agent client, src/agents/, with whichever model the person picked
the agent reads and edits Claude Code's own Read, Edit, Write, Bash, held to the project's folder the editor's MCP tools: read a file, edit it as text edits, check, run, look (editor-surface.html, its tool list)
the box says what it's doing the page polls every half second; the server reads Claude Code's stream-json log (SessionLog) AG-UI's events, streamed: text as it's written, each tool call as it starts and ends, the run's end
the change lands read back from disk, then one history step per changed file each edit tool call goes into your draft through SourceEdits as it's made, the request ONE history step; a new file shows at once
it fails "stalled" after a minute without taking it; ended without done AG-UI's run error, with the agent's words
  • What it buys the flows: a follow-up is the same run's next message, so the conversation comes for free; edits arrive one by one, so the box can show each and a queue is natural.
  • What goes: the inbox file, the heartbeat, the log reader, the half-second poll, and the spell app changes commands. Whether a Claude Code session in a terminal can still take a request (it reaches the same MCP tools) is for the plan.
  • Explain This moves too: one run with no edit tools.
  • The standards themselves: standards.html.

"Make me an app where…": an app, a site, a page of a site, or a view (Spell's component). None of these has an agent flow yet. Below is a guess at the flow, built from what the editor has.

asked for in Spell made today by
an app a project: its project file, one or more .spell files, maybe CSS New App, from the home page or the project menu (editor.createApp())
a site a project whose Spell declares a site: pages at addresses, a side nav the site editor, /site/<project> (epic mockup)
a page a page of a site, at an address; or a notebook page file the site editor's new page (SiteWrites.addPage()), or a double click on a page
a component a VIEW type: a "counter" is a view, drawn as its own element, <counter-view> by typing it; the palette adds Spell UI parts to a drawing
a Spell UI element TypeScript, in the kit's ui/: not something a person's project makes us, in VS Code
  • Whether a plan step is worth its click is unknown: v0 and Lovable skip it, Claude Code's plan mode doesn't. Open question 3.
  • A page: in the site editor, the new page's box takes words too ("a page listing every planet, with its films"). The editor adds the page as today (SiteWrites.addPage()), then hands the agent that page to fill.
  • A view: "a rating of 1 to 5 stars", said in a drawing, writes a new view type and draws it there. The agent should look for a Spell UI element first (<ui-rating>), as the examples' rules say: "Avoid custom widgets".

Once there's an app, most asks are about more than one part: "add a dark theme", "let two people play", "keep the list on the server". Those don't start from a selection.

  • The same box, opened with nothing selected, asks about the whole project. Today nothing selected means nothing opens.
  • A project's requests read as one CONVERSATION: what was asked, what the agent did, each with its undo.
    • Where it lives is open (question 2): the small box alone, a panel beside the code, or both, the box sending into the panel's thread.
  • A change to the data (a place, a server) is bigger than a change to a page. It should name what it will touch before it starts: the places, the roles, anything published.
  • The agent edits as a DESIGNER of the project, never more:
    • it writes drafts (canDesign), never publishes (canPublish)
    • Publish stays the person's own click

What's there, built for people's own edits, and what an agent's change needs on top.

  • The editor has three histories, each with one job (EditorHistory):
    • the running program's own moves, gone at each run
    • the code editor's, per file: what's typed
    • the editor's: the side bar's changes, a notebook's, and Change This's
  • A step remembers a meaning, "this text was that", not a position: so typing elsewhere doesn't break it, and a step whose text has gone says so.
  • An agent's change is one step per file today; one step per request is the fix (above).
  • Further back than ⌘Z: Revert Changes (your draft dropped), and versions (below).
  • Every save of a project's file is YOUR DRAFT, not the public file (ProjectDrafts, epic editor P24): so an agent's change is private until you Publish.
  • Publish already shows a side-by-side diff, yours left, theirs right, each change takeable back (CodeMirrorMerge).
  • Missing, for an agent's change:
    • a diff of ONE request, not the whole draft
    • the agent's own account of it, kept with the request
    • what it checked: compiled clean, the tests it ran, a picture before and after
  • A draft can be kept as a version of its own, never published (Keep Draft, keepDraft()).
  • Every Publish zips the project into its versions; how many are kept is the org's policy.
  • Proposed: keep a version before each agent request starts, by itself. Then "go back to before the agent" is one pick, as Lovable's per-change versions are.
  • The running app takes an edit as it runs (LiveEdit): the same elements and things, only what changed drawn again.
  • What it can't take (a type removed or renamed) waits for Restart, and the editor says so: never a surprise reload.
  • While you have drafts, what the editor runs is YOUR build, served to you alone.
  • Proposed: the agent sees the preview too, as a picture, so it can check its own work. See editor-surface.html, "The feedback loop".
  • The code's right-click Explain This (epic editor P32) is the other agent flow built: each line's own words at once, then a summary from Claude Code, with no tools at all.
  • No Claude Code here: the summary just doesn't come. "Don't barf if claude is not available" (Owen).
  • The same rule should hold for every agent flow: the editor works without one.
