Epics for people new to building

How someone making an app in Spell could ask an agent for something big and follow it on a lighter epic page: the same epic engine in a novice mode, its git, ids and log out of sight, every word in the novice voice.

Epic page: epic agents-in-spell Written for: Owen, reviewing the discussion docs before any plan; and whoever plans novice mode after Status: draft (discussion) Researched on: branch agents-in-spell, 2026-11-20. What the engine has today was checked by reading its code and its rules; everything about novice mode is a proposal, and says so. The sample texts were run through epic voice check (see Sources).
  • A novice epic is what someone gets when they ask an agent in Spell for something too big for one change: "make me a recipe app".
    • One page, four parts: what you asked for, the agent's questions as choice cards, the steps, and what's done.
    • What needs you sits at the top, in plain words.
  • The full epic page has eight sections and a lot of machinery: commits, the log, ids like Q3 and J7, branches and worktrees, stages and accepts, change marks, judgement-call colours.
    • About half carries over, renamed: questions, phases (as steps), manual tests (as "try it"), notes.
    • The rest is hidden, never deleted: the page still holds it, for a developer's view.
  • The same code can draw both: the 47 element families are Spell UI families already, and the page is already a place (EpicPageFormat on ChunkedPlace).
    • One setting on the page picks the view, and a novice set of words beside each element's own.
  • What has to come apart is the part that drives Claude Code and git: the hooks, waking a session in a VS Code window, the commit log, worktrees, and the epic command run in a shell.
    • In Spell, the editor runs the agent itself (the kit's planned src/agents/), so "waking" is starting a run, and undo is the editor's versions, not git.
  • Its pages belong in the person's project, beside their drafts, and the agent writes them through MCP tools that wrap the same model the epic command uses (PlanDoc).
  • The novice voice is already the engine's: its file is epic/voices/novice.md, and the kickoff box's words are in it. The voice check can run on any model: its reader is a parameter.
  • Build novice mode as one attribute on the epic page, audience="novice", read by the existing elements, not as a second set of elements.
  • Do it after the editor's MCP tools and src/agents/ exist: a novice epic is those tools plus a page, so it can't come first.
  • Start with the smallest page that's useful: ask, questions, steps, done. Leave judgement calls, notes and the developer view for a second round.

A person is making an app in the Spell editor. Change This handles "make this button blue" (flows, section 2). A bigger ask, an app, a site, a feature over several pages, needs a plan, questions answered and work in steps. That's what an epic is for, and today only Owen has one.

A novice epic is the same thing, sized and worded for the person: a proposal.

What you asked for The person's words, quoted, pictures and all. The kickoff prompt, today's <epic-prompt>. Questions for you Each question one card set, each card a plain choice with what it means for them, one marked recommended. Today's questions with <epic-choices>. The steps Three to seven, each a line in the person's terms ("A week of dinners"), with done, working on it, or waiting for an answer. Today's phases. What's done, and what needs you What you can do in the app now, and how to try it; and anything waiting on the person, at the top. Today's Done field, manual tests and red chips.
  • Not a chat. The conversation panel the other docs propose (flows, section 4) still carries the back and forth; the page is what stays when the chat scrolls away.
  • Not a project manager. No dates, no estimates, no people to assign.
  • Not a different engine. Owen's epic pages and a novice one are the same file kind, drawn by the same elements, edited by the same model.

The engine has three layers: the elements that draw a page, the model and inbox that change it, and the Claude Code and git glue around them. The first two can serve Spell; the third can't.

Proposal: on the page, as <epic-page audience="novice">, written when the page is made.

  • It's how the page already carries its other variants, as attributes the elements read: kind="saga", standing, stage, a future epic's notice (checked: EpicPage.types.ts, PLAN-DOC.md).
  • The PERSON decides the default: Spell makes a novice page for anyone not marked a developer. The PROJECT never does: one project can have both kinds of page.
  • A "Show details" pick in the gear flips one view, for one reader, without changing the file.

All proposals; the elements named are real (epic/src/components/, 47 families).

element in novice mode
<epic-page> No meta lines, step label, bedtime label or review line; the gear shows Theme and Show details.
<epic-section> Hides Log, Issues the person didn't report, and empty sections; renames the rest.
<epic-item>, <epic-mark> No id chip; three colours; the title alone.
<epic-phase> "Step N", title and Done; no Commits, Files, Verify, estimate, plan field.
<epic-review>, <epic-send-buttons> Go ahead, Not quite, Send my answers; no Defer, Revisit, Review Now.
<epic-commit>, <epic-change>, <epic-update> Not drawn.
<epic-agents> "The agent", one line of what it's doing; no running helpers.
<epic-choices>, <epic-option>, <epic-kickoff> As they are, with novice words.

The words: every element's names are in its vocabulary file (EpicKickoff.en.ts ...). A novice set could sit beside each, the way Spell UI keeps a second language beside English (UIButton.es.ts), picked by the page's audience instead of its language.

  • The voice exists: novice.md, nine habits (explain every word once, show what happens, never "just" or "simply").
  • The engine already picks a voice by kind of page: pageVoices in the epic settings maps "epic-page" to "code" today (EpicConfig.ts). A novice page maps to "novice", and the agent reads that file before it writes (epic voice --for).
  • The gate: epic voice check reads a text cold and fails jargon, ids, run-ons and agent speak. Its reader is a parameter (VoiceCheck's ask), today claude -p with Sonnet; in Spell it would be the agent client on its fast tier.
  • What gets checked: each new step title, question and card the agent writes, once, before the page shows it. The element words are checked once, when they're written, as the kickoff box's were.
  • The first draft of the mock in section 6 FAILED: "extra code", "Needs you (2)", "Waits for your first answer" and "easy" were all flagged. The second draft passed.
  • It also flagged "Spell" as unexplained, which on a page inside Spell it isn't: it needs the --about line to say where the text appears.

Today an epic page lives in the epic repo, spell.epics/epics/<id>/, served by the page server. A person's project has no such folder. Proposal below; the facts about drafts and places were checked in editor-surface, "Drafts".

  • In the person's project, beside their drafts: __epic/<id>/, the way __draft/ sits there today (ProjectDrafts).
    • It travels with the project: copy, zip, version.
    • It's private like a draft, never part of the published app.
  • Through a place, so where the project lives decides where the page lives: on this Mac, in the person's Spell space, later on their own server. The page is already a place (EpicPageFormat), so no new format.
  • The inbox (marks, notes, drafts of notes) is per person, as today's comments already are (one file per person, SharedComments).
  • Pictures the person drops in go in the page's own pictures/, as today.
way for against
The epic command, through a shell exists, every verb tested Only an agent with a shell can call it; the hosted and local models in Spell have none.
MCP tools, in the editor's one MCP server every agent the other docs plan for calls them; the same server as the editing tools A handful to write: wrappers over PlanDoc, not new logic.
AG-UI shared state only live, and a question can be a run's interrupt Gone when the run ends; the page would have no record of its own.

Proposal: both of the last two, each for its own job.

  • The page file is the RECORD, written through MCP tools: say, plan_steps, ask_question, step_done, try_it, decided. Names are placeholders.
  • AG-UI is the LIVE channel: the page shows "the agent is building the recipe page" from the run's events, and an open question ends the run with an interrupt (standards, section 2).
  • Send my answers resumes that run with the person's picks, through the same inbox the page uses today.

Your recipe app

What you asked for: "Make me a recipe app. I want to save my recipes and plan dinners for the week."

  • I'll keep building the rest while you think.

Where should your recipes be kept?

A. On this computer only Only you can see them. B. In your Spell account we suggest this You can open them on your phone too.

You asked for recipe cards that flip over when you tap them. Spell can't make a card flip yet.

A. Show the steps below the picture we suggest this Tap a card and its steps appear below the picture. No flip, but it's simpler to change later. B. Add the flip a harder way It looks the way you asked, but that part will be harder to change later.

The steps

1. A list of your recipes. Done. 2. A page for one recipe. I'm working on it now. 3. A week of dinners. Starts once you pick where to keep your recipes. 4. Try it on your phone. I'll tell you when it's ready.

What's done

You can add a recipe, give it a picture, and see it in your list. Open the app and press "Add a recipe" to try it.

Why it matters: it decides whether one project can hold both kinds of page, and who can flip it.

A. On the page, its default from the person recommended Written when the page is made; any reader can show details for themselves. Like kind and standing today. B. On the project Every page in it alike; a developer helping out sees the novice view too. C. On the person only Each reader sees their own view; the agent can't tell which voice to write in.

Why it matters: "the same epic code" is the ask, but 47 families carry a lot of Owen-only behaviour.

A. The same elements, a novice word set beside each vocabulary recommended One code path; hiding by attribute; words as a second "language". Each fix helps both. B. The same elements, novice words written inline in each Quicker to start; two sets of words tangled in every component. C. Four or five new elements over the same file and model Simplest to read; the page's look and behaviour drift from the epic page's.

Why it matters: it decides whether the plan travels with the app, and who can see it.

A. In the project, beside its drafts (__epic/) recommended Copied and versioned with the project; private, never published. B. In the person's space, outside any project One plan can make several projects; lost when a project is copied. C. In an epic repo, as Owen's are No change to the engine; a git repo per person is the opposite of novice.

Why it matters: hosted and local models have no shell, so the epic command can't be the only way.

A. MCP tools for the record, AG-UI for the live view recommended Any agent; the page survives the run; questions are a run's interrupts. B. The epic command Works today, for Claude Code and Codex alone. C. AG-UI state only No new tools; nothing kept when the run ends.

Why it matters: git is how Owen's epics take a phase back; a person's project has none.

A. A kept version before each step recommended Undo this step goes back to it. Keep Draft already makes versions; flows' question 1 recommends one per request. B. The editor's history only ⌘Z per file; a step that touched five files is five undos. C. One version for the whole epic Simple; all or nothing.

Why it matters: Owen accepts an Overview, then phases, then each plan; a newcomer won't sit through three.

A. One Go ahead, on the steps recommended The agent may start steps no question blocks before it; Go ahead lets the rest run. B. None: build at once Fastest; the person can't redirect before the work is done. C. Keep today's stages No engine change; too much ceremony for "make me an app".

Why it matters: judgement calls are how Owen catches a wrong turn; red and yellow mean nothing to a newcomer.

A. "What I decided for you", a quiet list, each with Change this recommended Visible, never in the way; only a call that would surprise them becomes a question. B. Hidden Cleanest page; a wrong guess shows only once it's built. C. Every one asked as a question Nothing hidden; the page fills with questions they can't judge.

Why it matters: a person who grows into building, or a developer helping them, will want the ids and the record.

A. "Show details" in the gear, for that reader recommended The file is the same either way; only the view changes. B. Only developers, by a setting on the person A newcomer never stumbles into it; nor can they grow into it. C. Never Simplest; the record is only for the agent.

Why it matters: too eager, and "make the title bigger" opens a plan; too shy, and "make me an app" has none.

A. The agent decides, and says so recommended More than one step, or a question only the person can answer: "This is a bigger job, so I made a plan." B. The person asks for one A "Plan it first" button; a newcomer won't know when to press it. C. Every new app or site Predictable; small changes stay Change This.
