Teaching agents to write clean Spell

How any agent can be taught to write clean Spell, with no model training: the language's own features, Spell UI's elements, and no CSS unless a look demands it. Then how a check keeps it honest, and what the person sees when a look can't be had.

Epic page: epic agents-in-spell Written for: Owen, reviewing the discussion docs before any plan; and whoever writes Spell's agent skill and its checks Status: draft (discussion) Researched on: branch agents-in-spell, 2026-11-20, by reading the code, the examples and their history, and running spell explain (see Sources). Each section says what's verified and what's a proposal.
  • Clean Spell is three habits, all already Owen's rules for the examples:
    • say it with the language's own feature, not spelled out by hand
    • draw with Spell UI's elements, never a hand-made copy of one
    • no CSS, unless a look no attribute gives demands it, and then say why
  • The proof is in the examples' own history: Task List's rewrite swapped an HTML block and about 70 lines of CSS for a <stack> and a fluid input. 22 of the 33 examples have no CSS file at all.
  • Every agent can be taught the same way, from ONE source, made into the shapes each one reads:
    • an Agent Skill, "writing Spell", for Claude Code, Codex, Cursor and the rest
    • an AGENTS.md in every Spell project, and an llms.txt on spell.app
    • a short context pack for Spell's own agent, and for a small local model
    • look-ups over MCP: a Spell UI element's attributes, "which feature does X", examples using a word
  • The gap: no look-up answers "which feature does X" today. spell explain stack and spell explain draggable both say "Nothing called".
  • Cleanliness can't be left to the prompt: a check has to say it. spell lint already has four "write it this way" checks; about six more would cover clean Spell, and a 0-100 score, like spell coherence score, gives an agent loop a number to raise.
  • When a look can't be had without CSS, the agent stops and asks, as Owen's rule asks agents in this repo: change the element, add CSS, or live without it. Three choice cards, in the conversation.
  • No model has been measured writing Spell yet. A test set of asks, scored four ways, would say how close each gets.
  • Write ONE Spell guide for agents, and generate the skill, AGENTS.md, llms.txt and context pack from it.
  • Teach spell explain Spell UI's tags, abilities and phrases: it's the look-up every agent needs.
  • Add the cleanliness checks to spell lint as warnings, with a score; the agent loop fixes them like errors.
  • CSS only after the person picks it from the choice cards, each rule saying what it gives.
  • Measure with held-out examples rebuilt from their descriptions, in the same runs as models' Q22.

Owen's rules for the examples already say it, since "examples are what people and agents copy" (the app folder's AGENTS.md, "Writing an example"): plain Spell, all the latest features, no HTML, minimal CSS, ui-* widgets before custom ones. WWOD §2's "Spell UI for ABSOLUTELY EVERYTHING possible" is the same rule for the kit's own pages.

The language's own feature One line that says what it means, where code would spell out how. A drag, a save, a menu, a form's binding: each is a phrase. Spell UI's elements A <stack>, not a row of boxes made to line up. About 100 elements, each with its attributes; a drawing names them bare. No CSS by default An attribute first, then the app's <ui-defaults> or a site's theme. CSS only for a look none of those give, saying what it adds.

What changed, one habit each:

  • the <html> block and its ui- prefixes: gone, Spell UI's elements by their bare names
  • <div part="row"> and its flexbox: <stack direction="horizontal" spacing="sm">
  • the title's flex: 1: the input's fluid
  • the grip's color: grey: the icon's color="grey"
  • a delete button: <action "delete" />, its title and icon the action's own
  • what's left of the CSS is one look no attribute gives yet, and its header says so

  • Proposal: ONE feature index, generated, that answers all three missing rows: each phrase, ability and element, with its one-line meaning, the words a person would search by, and the examples that use it.
  • Its sources exist: README-spell.md's headings and tables, the parser's rule names, Spell UI's vocabularies, and the examples themselves.
  • spell explain reads it, so people get it too; the MCP tools wrap that.
  • 33 examples in @spell/examples, written to be copied, each kept current by the content check's snapshots. They're the best teacher Spell has.
  • Too many to put in every prompt: Star Wars alone is 730 lines of Spell.
  • Proposal: the agent asks for the two or three closest, by the elements and phrases the ask needs (find_examples), and copies their shape.
  • Their file headers already explain each file ("A task, and the checklist that holds it"), so a picked example comes with its own notes.

A prompt is a hope; a check is a fact. Spell's checker already speaks in fixes, and runs in every agent's loop (the feedback loop). Clean Spell needs it to say "this works, but here's the cleaner way", too.

A number an agent loop can read and raise, the way spell coherence score gives one for the kit. Proposal, not designed:

  • spell lint --json already returns each problem with its rule: the score counts the clean-Spell rules' warnings.
  • Plus two measures: CSS lines without a reason, and Spell UI's share of a drawing's tags.
  • 100 is clean; each finding costs points; the JSON lists what to fix first.
  • The agent loop treats it like errors: fix, check again, stop at a threshold or after a few rounds.
  • The editor could show it beside the project, so a person sees it too.

Some looks need CSS, or a new attribute. The agent shouldn't quietly write CSS around an element: it asks, as Owen's own rule asks agents in this repo (WWOD §2: "A look Owen asks for that the element can't give: ASK him, with the choices ... before building around it").

  • Tokens: Spell will cost more, mostly its teaching. The work's own tokens are the fairer number.
  • Correctness: Spell matching React is already a win; React losing on the same tasks says something about React.
  • The trend matters more than one result: the gap as the context pack improves, and on a small model, where teaching shows most.

ReactiveScript, a Solid language with its own checker, ran this comparison on itself (the research notes, "Is it worth it?").

  • How: fresh agents built the same apps in ReactiveScript and in React, judged by hidden browser tests that land server answers in hostile orders.
  • Pilot (2026-10-27): no difference in defects, 0 of 9 each. ReactiveScript took 73 lines against 168, but 2.4 times the tokens and 2.5 times the check cycles.
    • 3 of 9 runs avoided its actions and numbered their requests by hand, as React code does.
  • Round 15 (2026-11-16, 144 apps): on the task its guide was written around, the fewest defects (Opus 0.00, Haiku 1.50, against React's 3.17 and 9.00).
    • On a held-out task, a board, among the worst (Opus 6.33, Haiku 25.17, against 0.67 and 3.00). None of its three written-down guesses held.
  • Its way in is a spec of 35,000 words; Spell's README-spell.md is 15,020. The 2.4 times is the number to match or beat.
  • Models' token measuring (): the same log, priced per task, not per token. Spell's English and React's TSX don't split into tokens alike.
  • The fast tier (): run both sides on it too. ReactiveScript's held-out gap was widest on Haiku.
