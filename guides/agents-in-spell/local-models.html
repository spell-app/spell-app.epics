Local models: Mac, Electron, phone

What it would take for Spell's agent to run on a model on your own machine, with no account and no bill: which models are good enough, how the editor would reach them on a Mac, in a browser and on a phone, and when to send the work to a hosted model instead.

Written for: Owen, reviewing the agents-in-spell discussion docs before any planning Status: draft (discussion) Researched on: 2026-11-20, from the web (release notes, model cards, benchmark boards, people's own measurements) and the kit's app/ folder; no experiments run. Each number says where it came from (see Sources).
  • Qwen earned its reputation. Its open models come in every size from phone to data centre, mostly under Apache 2.0, and every runtime supports them on day one.
    • The pick today is Qwen3.8 27B (August 2026): about 18 GB at 4 bits, so it wants a 32 GB Mac, and 64 GB for its full context.
    • The fast pick for smaller or slower Macs is a "3B active" model: Qwen3-Coder 30B-A3B or Qwen3.6 35B-A3B, 3-5 times faster for a little less quality.
  • The strongest alternatives at laptop size: Devstral Small 2 (Mistral, 24B), Laguna XS 2.1 (Poolside), Muse Glimmer (Meta, 30B), Gemma 4 (Google), gpt-oss-20b (OpenAI). All are open for commercial use.
  • The gap to hosted models is real for agent work.
    • On the independent Terminal-Bench 4.0 board, the best open model (GLM-5.3, far too big for a laptop) scores 41.8% against Claude Opus 5.5's 64.8%.
    • A laptop model is a step below that again, and much slower: one person's single task on an M5 Max took 21 minutes of "thinking".
    • Good enough for small, checked edits; not yet for "make me an app".
  • Reaching a model on a Mac is a solved problem. Ollama and LM Studio both run a local server that speaks the OpenAI format, and since early 2026 Anthropic's too. Spell only has to find one and talk to it.
  • A local model is one more piece behind Spell's one agent client (the kit's new src/agents/, as decided).
    • One piece covers every runtime that speaks the OpenAI format: Ollama, LM Studio, llama.cpp, MLX's server. Apple's on-device model is a second, through a small Swift helper.
    • The client runs the agent loop, sends AG-UI events to the editor and calls its MCP tools, the same for a local model as for a hosted one.
  • Spell doesn't need Electron to start. Its editor already runs from a local server (spell app serve), which can talk to Ollama without the browser's cross-site limits. Electron would add one-click install, managing the model download, and Apple's on-device model.
  • The browser and the phone are for small jobs. Chrome's built-in Gemini Nano (stable for web pages since Chrome 148), Apple's on-device model and 2-4B models on a phone can explain, rename, summarise and take a spoken command. A phone is best as a remote for an agent running elsewhere.
  • Spell's own checker is the trump card for a hybrid. Spell parses and checks a program in milliseconds, so a local model's edit can be tried and checked at once, and sent to a hosted model only when it fails.
  • First: give the agent client one piece for OpenAI-format local servers, let the editor's local server find Ollama or LM Studio, and route small edits there, checked by Spell's own checker.
  • Later, with an Electron app: Apple's on-device model for tiny jobs, and a guided model download for people with no runtime installed.
  • Don't bundle our own inference engine until people ask for it.

Five words come up in every section below.

  • parameters : the size of a model, in billions (27B).
  • quantization : squeezing a model to fewer bits per parameter. "Q4" or "4-bit" means about 0.6 GB per billion parameters, so a 27B model is about 17-18 GB.
  • mixture of experts ("MoE", written 30B-A3B): all of it must fit in memory, but only the "active" part runs, so it's several times faster than a "dense" model of the same size.
  • tokens/sec : how fast a model writes. There are two speeds:
    • prefill: reading what it's given (the project, the instructions), often thousands a second
    • decode: writing its answer, the number quoted below unless it says otherwise
  • context : how much a model can read at once. On a Mac it costs memory on top of the model: about 2 GB per 32K tokens for Qwen3.8 27B.
  • Apple Silicon shares one memory between the processor and the graphics chip.
  • macOS lets the graphics side use about two-thirds to three-quarters of it, so a 32 GB Mac runs a model of about 20-24 GB, context included.
  • Speed follows memory bandwidth: a Max or Ultra chip is 2-4 times a base chip.

  • Sizes and dates: model cards and guides (Sources). Estimates: the gpt-oss sizes, Qwen3.6 35B-A3B's and Glimmer's at 4 bits, and every "smallest Mac", worked out from the memory rule in section 2.
  • Microsoft has no Phi-5. Its newest open models are the Fara1.5 family, made to click and type in an app the way a person would. Its MAI models are hosted only.
  • DeepSeek's small "distills" (its reasoning taught to small Qwen and Llama models) were 2025's story. In 2026 the Qwen and Gemma models made them redundant.
  • Every size: 0.8B to 27B dense models, 30B-A3B to 2.4T mixtures. The same family runs on a phone, a laptop and a server, so one set of prompts works on all three.
  • Strong for its size: Qwen says Qwen3.8 27B scores 61.7 on SWE-bench Pro (fixing real bugs in real repos), up from Qwen3.6 27B's 53.5. That's the vendor's number; nobody has reproduced it yet.
  • Good at tool calls: one mid-2026 guide counts Qwen in about 10 of the top 13 places on the Berkeley Function-Calling Leaderboard. Not checked against the board itself.
  • Permissive: the small and mid-size models are Apache 2.0.
    • The huge 2.4T model's license asks for a commercial license above a revenue threshold, and the hosted "Max" models are closed.
  • Supported everywhere, at once: Ollama (ollama run qwen3.8), LM Studio, MLX and llama.cpp all had it within days.
  • It thinks at length: one test on an M5 Max spent 22,276 tokens thinking to write 3,223, over 21 minutes.
  • People found Gemma 4 and Muse Glimmer reach similar answers with about a tenth of the thinking, and prefer Glimmer for quick "find this in the code" jobs.
  • Its tool calls depend on the chat template, the runtime's file that formats the conversation for the model. One person's agent went from 67% to 92.5% success with a fixed one.
  • Below 4 bits its quality drops more than expected.

On benchmarks the labs run themselves, the best open models look close to the best hosted ones. On independent ones, they don't.

benchmark open model score hosted model score who ran it

Terminal-Bench 2.1 Qwen3.8 27B, a laptop model 73.0 Claude Opus 4.6 78.2 Qwen's own table
SWE-bench Pro GLM-5.2 62.1 GPT-5.5 58.6 Z.ai's own table
  • Quality: roughly a generation behind on long, many-step tasks. The models that come closest (GLM-5.3, DeepSeek V4, Kimi K3) need a 256-512 GB Mac Studio, not a laptop.
  • Speed is the bigger gap. A hosted model writes 50-200 tokens a second on a server and reads a project in a second or two.
    • A dense 27B model on a laptop writes 8-35, and thinks at length first.
    • An agent loop of 20 steps that takes a minute hosted can take 10-30 minutes locally.
  • Reading a project: a Spell project plus Spell's language reference could be 20-60K tokens.
    • Ollama measured 1,810 tokens/sec reading on a 35B-A3B model, so 30K tokens is about 17 seconds.
    • Estimate: a dense 27B reads several times slower, so a minute or more before it writes a word. Caching the part that doesn't change (the reference) matters a lot.
  • Spell is new to every model. No model has seen Spell in training.
    • A hosted model learns it from a reference in the prompt; a small model learns less from the same text.
    • Two ways to help it, both open questions: constrain its output to Spell's grammar, or teach it Spell by fine-tuning (Open questions, 4).

A runtime is the program that loads a model and runs it. Spell should use one people already have, not ship its own (section 5).

  • From a web page, the browser gets in the way.
    • A page on spell.app calling localhost needs the runtime to allow it (OLLAMA_ORIGINS, LM Studio's CORS switch).
    • Chrome now asks people before a public site may reach their own machine. Not verified for Safari in Nov 2026.
  • From Spell's own local server, nothing does. The editor already runs from spell app serve on localhost:3000. That server can call Ollama itself and pass the answer on, so the web editor gets local models with no browser limits and no Electron.
  • An outside agent works too. Because Ollama and LM Studio speak Anthropic's format, an agent built on Claude's Agent SDK (a bring-your-own agent) can point at one with ANTHROPIC_BASE_URL. Anthropic doesn't support this, and its new features can break it.

Owen's decisions (2026-11-20): one model and agent client in the kit, src/agents/, with each provider one piece behind it; the editor's agent flow runs on AG-UI events and MCP tools. Local models fit that shape without special cases.

the agent client
  • Runs the loop: ask the model, call the tools it asks for, ask again.
  • Sends AG-UI events to the editor: text as it's written, each tool call, the end of a run.
  • Calls the editor's MCP tools, and checks each edit with Spell's checker.
  • Picks the piece (section 8), and escalates when a check fails.
 local server piece
  • One piece for Ollama, LM Studio, llama.cpp, MLX's server and vLLM: only the address differs.
  • Speaks the OpenAI chat format, tool calls included.
  • Finds servers (section 4) and lists their models.
 Apple on-device piece
  • Talks to a small Swift helper, in the desktop app or a Mac's local server.
  • Small context, so it gets a short tool list and tiny jobs.
 in-browser pieces, later
  • Chrome's built-in model, WebLLM: the client runs in the page for these.
  • One prompt, one answer; no tools.
  • Each piece says what its model can do: call tools or not, see images, how much context, a forced answer structure or grammar. The client uses that to pick a piece, and to trim the tool list and the Spell reference for a small model.
  • Tool calls from local models are the weak spot. The runtime turns the model's text into OpenAI tool calls through the chat template (section 3). When that fails, the piece can ask for the call as forced JSON instead, which llama.cpp, Ollama and Apple's model all support.
  • The editor can't tell the difference. AG-UI events from a local run look the same as from a hosted one, so the same panel shows both; a label says which model did the work.
  • Where the client runs: in Node, in the editor's local server or the desktop app, for every local runtime; a web page can't reach them reliably (above).
  • The protocols themselves: Standards for agents in apps. What the tools are: What an agent drives in the editor.

Today Spell ships three ways: the web editor, served by spell app serve from the kit (Node, plus Python through uv); a public preview built as plain files, not yet deployed; and the VS Code extension for the language. A desktop app would wrap the first.

For
  • One download: no terminal, no Node, no uv, no yarn.
  • It can run and watch a model runtime in the background, and start it when needed.
  • It can call Apple's on-device model, which a web page can't.
  • Projects are plain folders on disk, open in any other tool.
  • Works offline, on a plane, with local models.
  • No browser rules between the page and a local model.
 Against
  • A third thing to build, sign, update and support, beside the web editor and VS Code.
  • 250-320 MB for an Electron app, before any model.
  • Python has to come along too (the Python target's servers), or stay optional.
  • The local server already gives the web editor local models (section 4), so it isn't needed to start.
A. Find Ollama or LM Studio
  • Section 4's steps, nothing bundled.
  • The person installs and picks models in a tool built for it.
  • Offer a link to install Ollama when none is found.
 B. Bundle llama.cpp
  • node-llama-cpp (3.22, Nov 2026) runs GGUF models on Metal inside Node.
  • Kept outside the app's packed files, and every binary signed.
  • One of its versions shipped a 34 MB copy of the engine's source by mistake.
 C. A small MLX helper
  • A Swift program built on mlx-swift, started by the app.
  • Fastest on a Mac.
  • Mac only, and Swift to maintain.
 D. Apple's own model
  • A small Swift helper calls the Foundation Models framework.
  • Free, private, nothing to download.
  • Too small for an agent; right for tiny jobs.
  • On the device: a small model, about 3B (Apple's 2025 figure), with a 4K-token context in the 26.0 releases and 8K on newer devices in 27.
    • WWDC 2026 improved its tool calls and instruction following, and added images as input.
    • Tool calls can be allowed, refused or required; it can be made to answer in a given structure ("guided generation").
  • Apple's servers (Private Cloud Compute): new in 2026, a larger model with a 32K context.
    • No key, no bill for the app: each person gets a daily limit, higher with iCloud+.
    • Apps apply to Apple, and it's only for apps with under 2 million downloads.
    • Not found: whether an app outside the Mac App Store (a Developer ID app, as Electron apps usually are) can use it.
  • One interface for several models: the framework now has a model-provider protocol, with ones for Apple's two models and for open models through MLX and Apple's new Core AI. Reports say Gemini plugs in too.
  • Core AI (WWDC 2026), which replaces Core ML, runs open models (Qwen, Mistral and others, from Apple's curated set) on the Neural Engine and graphics chip.
  • From Electron: a small signed Swift program the app starts, talking over standard input and output, is the simplest bridge. Estimate: I found no maintained Node module for it.
  • A useful coding model is 15-20 GB: a long download, so it can't come with the app.
  • Estimate, the shape it would take:
    • ask first, naming the model, its size and the disk space left
    • download in the background, resumable, while hosted models do the work
    • suggest one model for this Mac's memory (section 3's table), not a list of fifty
    • keep models where Ollama or LM Studio would find them, so they're shared, not doubled

From general Apple and Electron practice, not checked against a 2026 Spell build.

  • Outside the App Store (Developer ID, notarized, "hardened runtime"): the usual route. It can start helpers and reach localhost, as long as every helper and native module is signed.
  • In the Mac App Store: the app is sandboxed.
    • It can't download programs to run, though models are data and fine.
    • Helpers it ships must be signed to inherit the sandbox.
    • It needs permission to use the network, even to reach localhost.
  • Ship outside the store first; the store is a later question.

Local for small edits and private work, hosted for creating. What makes this work for Spell is its checker: every answer can be checked in milliseconds before anyone sees it.

    Why: the server already exists, and it's the smallest step that gets a real answer.

  2. Which local pieces does the agent client get, inside an Electron app? It decides the app's size, its upkeep, and who manages the downloads.

    Find Ollama or LM Studio, plus Apple's model recommended Nothing big bundled; a small Swift helper for Apple's model. Bundle llama.cpp node-llama-cpp, models downloaded by the app. Works with no other install. Bundle an MLX helper Fastest on a Mac; Swift to write and keep.

    Why: Ollama and LM Studio already solve downloads, updates and memory well; bundling repeats their work.

  3. The smallest Mac we design local agent work for? It decides which model we tune prompts and tools for.

    16 GB 4-9B models: explain and rename only. 32 GB recommended A 3B-active model or Qwen3.8 27B: small checked edits. 64 GB Qwen3.8 27B with room: a real local agent, for few people.

    Why: 32 GB is common on new Macs, and is where edits become useful.

  4. How does a small model learn Spell? No model has seen it, and small ones learn least from a prompt.

    A reference in the prompt, cached recommended The same text hosted models get, trimmed; checked by Spell's checker after. Constrain it to Spell's grammar llama.cpp can only let the model write text that parses. Needs Spell's grammar in its format. Fine-tune a Qwen on Spell A small add-on trained on Spell's examples. Best results; most work, and redone for each new model.

    Why: it's the biggest unknown in how good a local model will be at Spell. Worth an experiment.
