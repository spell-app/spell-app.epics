How agents hand work to cheaper agents

How a frontier agent hands parts of a job to cheaper models, starting with what Claude does, so Spell's agent can plan with its best tier and do the edits with its fast one.

Epic page: epic agents-in-spell Written for: Owen, reviewing the epic's discussion docs before any planning; whoever builds the tiers in src/agents/ after Status: draft (discussion) Researched on: branch agents-in-spell, 2026-11-20. Claude's side from Anthropic's own docs and posts, read that day; the other agents from one quick search each; Spell's own tiers by reading its code (see Sources). A claim marked guess is ours, not a source's.
  • Claude hands work to cheaper models in five ways, and they differ in WHO decides and WHEN the strong model runs:
    • subagents: Claude delegates a whole task to a worker, which can run on a cheaper model
    • opusplan: Opus while planning, Sonnet while doing
    • the advisor: the cheap model does all the work, and asks a stronger one at hard moments
    • workflows: a script Claude writes runs dozens to hundreds of agents
    • background calls: small jobs (titles, recaps) go to the Haiku-tier model
  • Delegation costs tokens before it saves any:
    • Anthropic's research system used about 15 times a chat's tokens, and beat one Opus by 90.2%.
    • Its later advice: multi-agent designs "typically use 3-10x more tokens" than one agent.
    • It saves money only when the workers are cheaper AND the context they read is small.
  • Anthropic's newest pattern turns orchestration upside down, and it's the cheapest:
    • The advisor: Haiku with an Opus advisor scored 41.2% against Haiku's 19.7% alone.
    • It costs 85% less per task than Sonnet alone, though it scores 29% lower than Sonnet.
    • Sonnet with an Opus advisor gained 2.7 points and cost 11.9% less than Sonnet alone.
  • Coding is the case Anthropic names as a poor fit for many agents: the work shares too much context. Delegation pays in code for searching, checking and big fan-outs, not for one edit split up.
  • The other frontier agents (Codex, Antigravity, Copilot, Cursor, Qwen Code, Kimi) all have subagents now; how each picks the worker's model is the part to evaluate (section 3).
  • Spell has a checker no general agent has: a program parses and checks in milliseconds. So a cheap model's edit can be checked at once, and handed up a tier only when it fails.
  • Spell's agent escalates, rather than orchestrates: the fast tier does the edit, Spell's checker checks it, and the best tier is asked only when the check fails, or before a big change.
  • A local model is the first rung below fast, for edits on a Mac that has one.
  • Keep subagents for the jobs that fan out (making a new app, explaining a whole project), not for Change This.

Claude Code and Anthropic's platform give five ways to put part of a job on a cheaper model. The table lines them up; a sub-section on each follows.

  • The model names are November 2026's: Fable 5.2 (the top), Opus 5.5, Sonnet 5.5, Haiku 5.5. Their prices are in models.html.

Claude Code's own comparison of the advisor, opusplan, subagents and /model is in its advisor page (Sources). Agent teams, a sixth shape, are peer sessions rather than cheaper workers: left out here.

A subagent is a worker the main agent starts with its Agent tool (once called Task). What it gets:

  • Its own context window, its own instructions, its own tools and permissions.
    • It doesn't see the conversation: only the task message Claude writes for it.
    • Only its final report comes back, so its file reads never fill the main context.
    • A fork is the exception: it copies the whole conversation, and runs on the parent's model.
  • Its model, picked in this order:
    1. the model Claude passes when it starts the subagent
    2. the model line in the subagent's definition
    3. CLAUDE_CODE_SUBAGENT_MODEL, the setting for every subagent
    4. else the main conversation's model
    The values: haiku, sonnet, opus, fable, a full model id, or inherit.
  • Its own effort level (low to max); thinking it inherits from the parent.
  • Limits: subagents may start subagents, three layers deep by default; at most 20 run at once.
  • In an interactive session they now start in the background by default; their reports arrive later.

The built-in subagents, and their models:

subagent model for
Explore the opus alias (Fable on the cloud providers) read-only searching, at three levels of thoroughness
Plan the parent's read-only research in plan mode
general-purpose the parent's multi-step work that reads and changes
claude-code-guide Haiku questions about Claude Code
statusline-setup Sonnet /statusline
  • Explore once ran on Haiku (guess: from memory of the 2025 docs, not re-checked). Today it runs on the opus alias; Haiku is left with the small jobs.
  • Anthropic's own advice for cost: put simple subagents on model: haiku, and keep the main conversation on Sonnet unless the task needs Opus.
  • Opus 5 "delegates to subagents more readily than earlier models": so the Agent SDK's Claude Code prompt tells Opus 5 not to start one unless asked.
  • opusplan is a model setting: Opus in plan mode, Sonnet once the plan is accepted.
  • It's the oldest and plainest shape of "a best model plans, a cheaper one edits": the person draws the line, by entering and leaving plan mode.
  • Its catch: every switch is a switch of model, and each model has its own prompt cache, so the first turn after each switch re-reads the whole conversation at full price.

The advisor (Anthropic's post of 2026-04-09) turns orchestration upside down: the cheap model drives, and asks up.

  • On the Claude API it's a server tool: one request, and Anthropic runs the advisor's pass itself. A max_uses caps the consultations per request.
  • In Claude Code: /advisor opus, or the advisorModel setting.
  • In Managed Agents: one line in the agent's multiagent settings.
  • The advisor must be at least as strong as the worker: Opus advising Sonnet or Haiku, never the other way.
  • Cache: turning it on keeps the main model's cache, but each consultation reads the whole transcript anew, uncached. So late consultations in a long session cost the most.
  • Not on Bedrock, Google's Agent Platform or Microsoft Foundry; experimental in Claude Code.

The post's numbers are for the models of April 2026 (Sonnet and Opus 4.x); none were re-run for the 5.5 models.

  • Claude Code sends some small side jobs to the Haiku-tier model, whatever the session runs on.
    • Checked: the setting ANTHROPIC_DEFAULT_HAIKU_MODEL is "the model to use for haiku, or background functionality"; it replaced ANTHROPIC_SMALL_FAST_MODEL.
    • Checked: session titles, compaction, subagents and workflows are requests "outside the main conversation", with their own cache rules.
    • From third-party write-ups only: titles and topic detection run on Haiku; behind a gateway with no Haiku configured, Claude Code falls back to the main model. One user report says the away-recap bills the main model instead.
  • Not every side job is cheap: the next-prompt suggestion goes to the session's OWN model, because it reuses the conversation's cache (mostly cache reads, a few tokens out).
  • The lesson for Spell: a side job that reads the whole conversation is cheaper on the same model, cache warm, than on a cheap model, cache cold. Only a side job with a small input belongs on the cheap model. (guess, drawn from the two cases above.)
  • Effort is the second dial beside the model: how hard a model thinks, low, medium, high, xhigh or max.
  • The 5.5 models and Fable default to medium, and can't turn thinking off: "the model decides per step how much to think based on the effort level."
  • Thinking is billed as output, so lowering effort is the way to spend less on a model.
  • Changing effort mid-session used to cost the cache; on Fable 5.1+, Opus 5.5, Sonnet 5.5 and Haiku 5.5, through Anthropic's own API, it no longer does.
  • Every subagent can have its own effort, and CLAUDE_CODE_SUBAGENT_EFFORT sets one for all of them.
  • Spell measured this itself, and found the dial matters more than the model (below, what Spell measured).

Three posts set out when to split a job between models, and how.

Building effective agents (2024-12-19) Five shapes, simplest first: a chain of steps, routing (easy questions to Haiku, hard ones to Sonnet), parallel calls, orchestrator-workers, and an evaluator checking a generator. Its advice: the simplest thing that works, and add a part only when it measurably helps. The multi-agent research system (2025-06-13) An Opus lead plans and starts Sonnet workers in parallel, each searching one angle; a citation agent checks the sources. 90.2% better than one Opus on Anthropic's research test, at about 15 times a chat's tokens. Token use alone explained about 80% of how well it did. When to use multi-agent systems (2026-01-23) Start with one agent. Split only to keep the main context clean, to run independent work in parallel, or for a specialist. Split by CONTEXT, not by kind of work: the agent that writes a feature writes its tests too. 3-10 times the tokens.
  • The research post: coding has "fewer truly parallelizable tasks than research", and agents aren't yet good at coordinating in real time.
  • The 2026 post: splitting by kind of work (one writes, one tests, one reviews) is "often counterproductive".
  • The Claude Agent SDK (the library Claude Code is built on) takes the same subagents in code: an agents option, each with its description, instructions, tools, model and effort.
    • Its caps: how deep subagents nest, how many run at once, and a spend limit in dollars (maxBudgetUsd), which subagents count toward.
    • Its example of a dynamic choice: Opus for a strict security review, Sonnet otherwise.
  • Managed Agents (Anthropic's hosted agents, beta since April 2026) put all three ways in one multiagent setting:
    • subagents, one level deep, at most 25 threads, each with its own model
    • workflows, whose made-up agents run on the lead's model: a cheaper model only for agents you created and listed
    • an advisor, for the lead thread only
    • Anthropic's own examples: an Opus 5.5 lead, with Haiku 5.5 reviewers, test writers and researchers
    • a session budget caps the spend, workflows included
  • Workflows, in Claude Code too: a short script of agent(), pipeline() and parallel() calls, up to 16 agents at once and 1,000 a run. A run over 25 agents or 1.5 million projected tokens shows a "Large workflow" warning.

Spell won't run on Managed Agents (its agent is the kit's own client, standards.html), but its settings are the clearest map of the choices Spell's client will face.

A cached prompt is read back for a small fraction of the input price (2-5% on most models, models.html). Delegation changes what can be cached:

case does it read the parent's cache?
a subagent (fresh context) no: its instructions differ, so it warms its own
a fork (copies the conversation) yes, from its first request
workflow agents alike in model, tools and instructions yes, each other's: Claude Code holds back all but the first for up to 5 seconds, so they share
a switch of model (opusplan, a skill naming a model) no: each model has its own cache
the advisor the main model's cache stays; the advisor's own read is never cached
  • Subagents' caches last five minutes, even on a subscription; the main conversation's an hour there.
  • The parent's cache is untouched by a subagent: its call and report are only added to the end.

Each from Anthropic's posts and docs, except the two forum reports marked so.

  • Too many agents. Early research versions started 50 subagents for a simple question. Fix: say in the prompt how many agents a size of task deserves.
  • Vague hand-offs. Workers given a short task duplicated each other's searches. Every hand-off needs its goal, its output's shape, its tools and its limits.
  • The telephone game. Facts are lost at each hand-off: a subagent sees only what its task message says.
  • Early victory. A checking agent runs one or two tests, sees them pass, and says it's done. Fix: concrete criteria, and the whole suite.
  • Coordination costs more than the work. In one split-by-role test, workers spent more tokens talking than working.
  • Misrouting. A router that sends a hard task to the cheap model gives a poor result, confidently.
  • Cache thrash. Each switch of model re-reads the conversation at full price.
  • The model you didn't pick. Forum reports (not Anthropic's): Cursor's subagents run on pricier models than the one selected; Codex's stopped taking a model of their own in mid-2026 (section 3).

Spell's agent is one client, in the kit's new src/agents/, with three tiers in no provider's terms: fast, balanced, best (standards.html). This section is how those tiers would share a job. It's all proposal: guess, unless it cites Spell's code.

The advisor's shape fits Spell better than an orchestrator's: Change This is one small, coupled edit, the case Anthropic says not to split. What Spell adds is a check no general agent has.

  • The checker decides when to escalate, not the model: no router to misroute.
  • Before a BIG change (a new view, a whole page), the best tier plans first, as opusplan does; the fast tier does the steps of its plan.
  • The advisor itself is Claude-only, and not on every cloud. Spell's client would do it by hand, the same for every provider: ask the best tier with the conversation so far, and hand its answer back.
  • A local model is free to run, so it's the rung below fast: try it first on a Mac that has one.
  • local-models.html already proposes the hybrid: route small edits to Ollama or LM Studio, checked by Spell's checker, and up to a hosted model when they fail (local-models.html).
  • The same escalation as above, one rung lower: local, then fast, then best.
  • Its cost is time, not money: a laptop model is much slower, so a timeout matters as much as a failed check.

The jobs are the ones flows.html lists. A first cut, all guess, to argue with:

job who does it escalates to split into subagents?

a follow-up in the conversation the same tier as before best, when the check fails no: same model keeps its cache
change what was made (a whole page or app) best plans, fast edits best, per failing step maybe: a step per file

Spell already has tiers: spell translate's passes ask Claude at a tier, and a table maps each to a model and effort (CLAUDE_TIERS, epic spanish P27, measured 2026-10-23). Checked by reading the code:

  • Every tier of every pass runs Opus; only the effort differs (low, up to high for "best").
  • Why: Opus at low effort was the fastest and the best at names. Sonnet glued words, and Haiku was the SLOWEST (about 33 seconds) and broke a test.
  • So "fast" didn't mean "the small model" there: a strong model thinking little beat a small model thinking a lot.
  • Those runs were on the 4.x and 5 models, before Haiku 5.5. Measure again before mapping fast to Haiku.

Already decided on the epic page, and not asked again: the word "agent", the one client in src/agents/, and Change This on AG-UI and MCP.

  1. How does Spell's agent share a job between tiers? A. Escalate on a failed check recommended The fast tier does the work; Spell's checker sends it up a tier when it fails. The advisor's shape, with the checker deciding. B. Best plans, fast does Every request planned by the best tier first. Safer, but a best-tier call on every small edit. C. One tier per request Pick the tier from the kind of job, no switching. Simplest; no rescue when the cheap model fails.

    Why it matters: it sets what a small edit costs, and how often it fails.

  2. Does Change This ever start subagents? A. Never recommended One coupled edit, the case Anthropic says not to split; subagents only for making something new and explaining a whole project. B. A read-only searcher A cheap Explore-like worker finds the code to change, so the editing model reads less. C. When the agent decides As Claude Code does. Flexible, but the costs are the hardest to predict.
  3. What does fast map to on Claude? A. Measure first, on Spell's own edits recommended Haiku 5.5 against Opus 5.5 at low effort, as spell translate did, on a set of Change This requests. B. Haiku 5.5 40 times cheaper than Opus; unmeasured on Spell. C. Opus at low effort What Spell's translate tiers use today; dearer per token, but fewer retries.
  4. Where does a local model sit? A. A rung below fast, tried first when there recommended Free, checked by Spell, and up to the fast tier on a failed check or a timeout. B. Only when the person picks it No surprises in speed; but nobody gets it without knowing to ask. C. Side jobs only Titles, notes and explaining, never edits. Safe, and saves least.
