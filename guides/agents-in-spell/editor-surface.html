What the editor gives an agent

What the Spell editor already has that an agent would drive, what the agent should write, how it checks its own work, and the MCP tools it needs: for planning the tool set Change This will run on.

Epic page: epic agents-in-spell Written for: Owen, before planning; and whoever builds the editor's MCP tools Status: draft (discussion) Researched on: branch agents-in-spell, 2026-11-20, by reading the code; two timings run here (see Sources). Guesses say so.
  • Almost everything an agent needs is already in the editor, built for people:
    • projects as plain files, named by address (@spell/examples/Counter)
    • your draft, versions and Publish, by role
    • text edits that undo by meaning, and semantic edits: add a page, move a part, set a property
    • checks with fix-it messages: parse, compile, lint, types, tests
    • the running app, its things, a line of Spell run on it, the selected part and its line in the source
  • Agents today are Claude Code, started as a program, in six places across the kit; the three that matter here are Change This, Explain This, and spell translate / spell place ingest (which can call the Claude API instead).
    • No MCP server, no model call from the browser, no other provider.
  • The agent should write SPELL, its drawings' markup included: it's what people read, what the Inspector edits, and what the checks speak.
    • The catch: no model has seen Spell. It needs the examples, the reference and look-up tools.
  • The tools split across two hosts:
    • the page server (node): files, drafts, the compile, the checks
    • the open editor (the browser): the selected part, the running app, a picture of it
  • One MCP server, in the page server, whose tools wrap what section 6 lists; the browser-side ones reach the open editor over the page server's live channel.
  • Edits only as text edits through SourceEdits, into the person's draft: never a whole file written, never the public file (I152).
  • Give the agent the examples and two look-ups (spell explain, spell describe) before any long prompt.
  • The word is agent ().
  • One agent client, in the kit's new src/agents/ ().
  • Change This runs on AG-UI events and MCP tools, its inbox and log reader gone (): so section 6's list IS the MCP tool set.

The editor's parts an agent touches, each with where it lives. All checked in the code.

  • A project is a folder: a project file (__project.json5), its .spell files, CSS, pictures.
    • Built-in ones are in the app's spaces/@spell/; people's in spell.spaces, beside the kit.
    • Named by address: @spell/examples/Counter, owen@spell/errors; a file by its name after it (SP.SpellUrls).
  • Made, copied, renamed, deleted through the spaces' models: a group's projects (SpellProjectRoot), a project's files (ProjectFiles).
  • Read and saved over HTTP: /spaces/<project>/<file>, and POST /api/projects/file/<project>/<file>.
  • A save is checked by ROLE: a page or its source needs the design right (canDesign); a new file, a rename or a delete, a manager (canCreate).
  • Every save of a project's own file is YOUR DRAFT, beside it: __draft/<name>.<person>-<day> (ProjectDrafts).
  • While you have drafts, the editor compiles and runs YOUR build, served to you alone.
  • Keep Draft makes a version of its own; Publish writes the public files and zips a version.
  • Only a manager publishes (canPublish).
  • So the draft is the agent's sandbox already: private, undoable, never live until a person publishes.
  • SourceEdits is the ONE home for changing text: only the characters that change, each thing keeping its words and comments.
  • On top of it, edits that MEAN something, each one history step:
    • InspectorWrites: a part's property set
    • PartEdits: a part added, moved, cut, pasted, deleted; by the flow, never x and y
    • SiteWrites: a site's page added, renamed, moved
    • editor.applySourceEdits(): any edits to a file, as the language service would make them
  • EditorHistory keeps them: a step remembers "this text was that", so it survives typing elsewhere; changes can be grouped into one step.
  • editor.compileApp() compiles the project and runs it in the run pane; a compile cache on the page server skips what hasn't changed.
  • The running app takes an edit as it runs (LiveEdit), its things kept; what it can't take waits for Restart, and the editor says why (editor.restartNeededBecause).
  • The Spell Console runs ONE line of Spell on the running app, its things kept (editor.runInConsole()): "deal a new game", "print the score".
  • The Thing Explorer reads every thing the app made (core.things).
  • editor.runTests() runs the project's to test … sections.
  • The Inspector selects a part in the running app: a drawn thing or a Spell UI element; several with Shift or a rubber band.
  • Each knows where it's written: Inspector.writtenPlaceOf() gives its file, line and column, from the source marks the compile leaves on what it draws.
  • That's what Change This sends: project, file, line, column, the tag, 5 lines of source.

What exists to hand a model, and what's missing. How well any model does with it is untested: a guess until measured.

  • The examples, written to be copied: "Examples are what people and agents copy, so each one shows the current way" (app's AGENTS.md, "Writing an example"). About 40 in @spell/examples.
  • The guides, @spell/guides: "a first spell", "a tour of spell", and how each example works.
  • The language's page, README-spell.md.
  • Spell UI's tags and attributes, with what each does: the help table the language service reads (SP.ComponentPacks.help()); the same vocabularies made Claude Design's Spell design system (Designing with Spell UI).
  • Look-ups: spell explain <word> (the rules a word names, with an example); spell describe (what a project declares); spell parse (how a line reads).
  • Missing: ONE short context pack, a few thousand words, for the start of every run; and a measure of how often a model's first Spell parses.

An agent writes, checks, and fixes until clean. Spell's checks are fast and speak in fixes, which is the best case for that loop.

  • Half the tools need the OPEN editor: the selection, the running app, the history the person's ⌘Z reaches. Those can't run on the server alone.
  • Proposed: ONE MCP server, in the page server, beside the app's other routes.
    • The server's tools it answers itself.
    • The editor's it hands to the open editor over the page server's live channel, which every page already joins, and waits for the answer.
  • No editor open: only the server's tools, and edits go to the draft on disk (as today's Change This).
  • A guess at the shape, not designed: the hand-off's messages, timeouts and which tab answers are for the plan.
