Standards for agents in apps

Which standards and kits Spell's agents should stand on, one per layer, so we use what's already out there and write only what's ours.

Written for: Owen, reviewing the epic's discussion docs before any planning Status: draft Researched on: branch agents-in-spell, 2026-11-20. The scaffolder was downloaded and read; packages and download counts checked on npm; the rest from the projects' own pages (see Sources). Each claim says whether it was checked or is a guess.
  • By November 2026 the field has settled into a few standards, and most of them now sit with neutral foundations:
    • MCP: how an agent reaches tools. Everyone speaks it.
    • AG-UI: how an app watches an agent work, event by event. It reached 1.0 on 2026-09-30.
    • ACP: how an app hosts a coding agent someone already has (Claude Code, Codex, Gemini CLI ...).
    • A2UI and MCP Apps: how an agent shows UI. A2UI sends a description that the app draws with its own components; MCP Apps sends a whole page that runs in an iframe.
    • Agent Skills, AGENTS.md and llms.txt: how you teach an agent about a project.
  • create-ag-ui-app is a thin wizard of about 5 KB.
    • Its web choice hands off to CopilotKit's CLI, which builds a React or Next.js app.
    • Its terminal choice downloads a plain TypeScript example.
    • That example is the useful part: it shows the AG-UI client running with no framework at all, which is what Spell UI needs.
  • No chat kit fits Spell UI as it is:
    • CopilotKit, assistant-ui and OpenAI's ChatKit are React first.
    • TanStack AI has Solid bindings, but for Solid 1.
    • Their headless clients (@ag-ui/client, the AI SDK's AbstractChat) do work without a framework.
    So Spell takes a client off the shelf and draws the chat itself, with <ui-*> elements.
  • Spell already has an agent flow: Change This, on the selected part.
    • Its plumbing is ours: an inbox file, a headless Claude Code, and a reader for its log.
    • The stack below keeps that flow and replaces the plumbing (see Change This, on standards).
  • One new kit folder, src/agents/, holding ONE client for every agent.
  • It speaks AG-UI to the editor, and MCP to the editor's tools.
  • It hosts outside coding agents through ACP, and models through the two wire formats everyone copies.
  • The same MCP server, put online, lets Claude, ChatGPT and Cursor work on Spell projects too.

Six layers, from the model up to the people. Each sub-section says what the layer is, which standard to take, and what Spell would still write itself. The comparison table at the end lines them all up.

layer what crosses it take Spell writes
1. model API prompts, tokens, tool calls OpenAI-style and Anthropic Messages, through one adapter kit the settings: which model, which key
2. agent loop think, call a tool, read, repeat a kit's loop for models; ACP for agents people already have the system prompt, the Spell skill
3. agent and editor tools "read this part", "change that file" MCP the tools themselves (editor-surface.html)
4. agent and UI events text as it streams, tool calls, state, questions back AG-UI, with its framework-free client the chat and progress views, in Spell UI
5. generated UI cards, forms, whole apps Spell itself, for apps; A2UI for cards in the chat, later a catalog mapping A2UI to <ui-*>
6. outside agents driving Spell Claude, ChatGPT, Cursor editing a project a remote MCP server, Agent Skills, AGENTS.md, llms.txt the server's sign-in, the skill's text

Every model is reached through one of two wire formats, and nearly every provider now copies at least one.

  • OpenAI's formats: Chat Completions, the old one every local server speaks, and Responses, the new one.
    • Responses is now an open spec, Open Responses (from 2026-01-15), given to the Agentic AI Foundation on 2026-10-22.
    • OpenRouter, Ollama, LM Studio, vLLM, Hugging Face and Vercel support it. Anthropic and Google don't, at the start (reported, not checked).
  • Anthropic Messages: Ollama, LM Studio, vLLM and OpenRouter each serve a /v1/messages route too (their docs, checked by search, not by running them).
  • So the client never needs a provider's own SDK.
    • A kit with provider adapters does the work: the Vercel AI SDK, or TanStack AI.
    • Both are framework-free at the core. Both are on npm, checked: ai 7.0.177 is fetched 48.7M times a week, @tanstack/ai 1.8.0 3.7M.
  • Which models, what they cost, and the gateways: models.html.
  • Models on your own machine: local-models.html.

An agent is a model in a loop. Spell meets two kinds, and needs both.

A loop Spell runs
  • For a bare model behind a key: Qwen on a laptop, a cheap model on spell.app.
  • Take a kit's loop: the AI SDK's ToolLoopAgent (checked in its types), or TanStack AI's.
  • It runs in the browser, in Electron, or on a server.
 An agent someone already has
  • Claude Code, Codex, Gemini CLI, Qwen Code: each has its own loop, sign-in and plan.
  • Host it through ACP, the Agent Client Protocol.
  • Or, for Claude only, the Claude Agent SDK: the loop Claude Code runs, as a library.

ACP, the Agent Client Protocol

  • What it is: LSP for coding agents. The editor starts the agent and talks JSON-RPC to it over stdio.
  • Who: started by Zed in August 2025, joined by JetBrains. Their shared registry opened in January 2026.
  • Its registry lists 49 agents (checked 2026-11-20), among them:
    • Claude Agent, Codex, Gemini CLI, GitHub Copilot, Cursor
    • goose, OpenCode, Qwen Code, Mistral Vibe, Kimi Code, Junie
  • @agentclientprotocol/sdk 2.8.0 is fetched 9.9M times a week (checked on npm).
  • The catch: local agents run as a child process, so it needs Node, which means the page server or Electron, never a phone or a plain tab.
    • Remote agents over HTTP or WebSocket are "a work in progress", by ACP's own site.
  • Why it matters: it's the cheapest bring-your-own-agent there is. People use the plan they already pay for, and Spell pays nothing (byo-agent.html).

The agent frameworks, briefly

All of these speak AG-UI, through adapters in AG-UI's own repo (its folders were checked). None is needed to start; each is a backend someone else might bring.

  • What it is: the Model Context Protocol. A server offers tools, resources and prompts; any agent that speaks it can use them.
  • Who: Anthropic made it. Since 2025-12-09 it belongs to the Agentic AI Foundation, under the Linux Foundation, with OpenAI, Block, Google, Microsoft and AWS among its members.
  • How wide: @modelcontextprotocol/sdk is fetched 94M times a week (checked). Every agent in this doc speaks it.
  • The latest spec, 2026-07-28 (checked on MCP's blog):
    • stateless: no handshake, no session id; each request carries its version and abilities
    • Streamable HTTP is the transport; the old HTTP+SSE one is deprecated, with a year to move off
    • a server that needs an answer mid-call (a confirmation) returns "input required", and the client calls again with it
    • sign-in is OAuth: client ID metadata documents replace dynamic registration, which is deprecated
    • a framework for extensions: Tasks (long jobs) and MCP Apps (below) are extensions now
  • How it fits: the editor's tools are written once, as an MCP server, and every agent gets them:
    • Spell's own loop calls them in-process.
    • An ACP agent (Claude Code ...) is handed the server when its session starts.
    • Claude, ChatGPT or Cursor reach it over HTTP, signed in (layer 6).
  • The tools that only the open page can run (select a part, show a preview): AG-UI calls them frontend tools .
    • The page lists them in its run request, and answers their calls itself.
    • AG-UI's Claude adapter already turns that list into an in-process MCP server for Claude (from CopilotKit's onboarding notes, read in the package).
    • So one tool list, written once, serves both kinds.
  • Later, WebMCP: a browser API (document.modelContext) for a page to offer tools to the browser's own agent.
    • A W3C community draft; in a Chrome origin trial only (reported, not checked).
    • Not to build on yet, but the same tool list could feed it.
  • What it is: the Agent-User Interaction protocol, a stream of typed events from an agent to a page.
    • The page posts one request (a RunAgentInput) and reads events back, usually over SSE.
    • A binary encoding exists too (@ag-ui/proto, a dependency of the client, checked).
  • Who: CopilotKit made it and runs it. 1.0 shipped 2026-09-30, with a JSON Schema the TypeScript, Python and .NET SDKs are generated from.
    • Its repo has 20.8k stars, pushed to today (checked).
    • CopilotKit lists Google, Microsoft, Amazon and Oracle as adopters. That comes from CopilotKit itself: no announcement from those companies was found.
    • What was checked: adapter folders in AG-UI's repo for Claude Agent SDK, Claude Managed Agents, OpenAI Agents, Microsoft Agent Framework, Google ADK, AWS Strands, Vercel AI SDK, Mastra, LangGraph, Pydantic AI and more.
  • Its events (from the 1.0 types, checked), in groups:
    • a run: RUN_STARTED, RUN_FINISHED, RUN_ERROR, steps
    • text: TEXT_MESSAGE_START / _CONTENT / _END
    • tools: TOOL_CALL_START / _ARGS / _END / _RESULT
    • shared state: STATE_SNAPSHOT, and STATE_DELTA as JSON Patch
    • thinking: REASONING_*
    • helpers: SUBAGENT_STARTED / _FINISHED / _ERROR
    • the rest: activity, CUSTOM, RAW; and a run can end with interrupts, questions that wait for a person
  • Without React: yes, checked.
    • @ag-ui/client 1.0.5 depends on rxjs and a few small helpers, and on no framework.
    • Its HttpAgent takes a subscriber with one callback per event: Solid 2 signals can be set straight from those.
    • The scaffolder's terminal example uses it that way (below).
  • Against it: one company leads it, and it's young. The AI SDK's own UI stream is the alternative: more downloads, but it ties the backend to that SDK, while AG-UI has adapters for every framework above.

Three ways an agent shows UI. Spell's own case is unusual: its agents' main job is to write UI, as Spell.

way what the agent sends who draws it for Spell
Spell itself Spell source the editor, compiled the apps, sites, pages and components people make
A2UI (Google) a description: which registered components, with what data the app, with its own components small cards in the chat: a picker, a question; later
MCP Apps a whole HTML page a sandboxed iframe Spell's previews inside Claude and ChatGPT; others' apps inside Spell

A2UI

  • Google's; 0.9 in spring 2026, 1.0 on 2026-11-11 (Google's blog, checked).
  • The agent can place only components the app registered, so it's safe, and the app keeps its look.
  • Renderers: React, Angular and Lit on the web; Flutter, SwiftUI, Jetpack Compose.
    • The Lit one is custom elements, the closest to Spell UI (@a2ui/lit 0.15.0, checked).
  • Used at Atlassian (Jira), Alation, ByteDance and in Gemini Enterprise, by Google's account.
  • It rides on AG-UI: AG-UI's repo has an A2UI middleware (checked).

MCP Apps

  • The official MCP extension for UI, stable since 2026-01-26. It merged MCP-UI and OpenAI's Apps SDK.
  • A tool names a ui:// page in its _meta.ui; the host shows that page in an iframe, and the two talk over postMessage.
  • Shown in ChatGPT, Claude, VS Code, Goose and Postman, by the project's README.
  • Its examples include a Solid one and a vanilla one (checked); the vanilla one is excerpted in the review.
  • OpenAI's Apps SDK is now MCP Apps, plus ChatGPT-only extras. OpenAI is shutting Agent Builder on 2026-11-30; ChatKit stays (reported, not checked on OpenAI's site).

The reverse direction: someone's own Claude, ChatGPT or Cursor makes or changes a Spell project.

  • A remote MCP server on spell.app: the same tools as layer 3, over Streamable HTTP, signed in with OAuth.
  • MCP Apps on that server: the agent shows the running app, inline in its chat.
  • Agent Skills (SKILL.md folders): how to write Spell, as a skill any agent loads.
    • Anthropic's, given to the Agentic AI Foundation on 2026-10-22: "more than 70 agent platforms", ChatGPT, Cursor, GitHub Copilot and VS Code among them, by Anthropic's post.
    • Spell already writes skills for Claude Code, so this is a format we know.
  • AGENTS.md: a project's notes for coding agents. OpenAI's; a founding project of the foundation; 60,000+ projects by the Linux Foundation's count. The kit already has one.
  • llms.txt: a site's summary for language models.
    • Cheap, but little read: Ahrefs found 97% of 137k files never fetched.
    • Coding agents (Claude Code) are the ones that do fetch it, which is Spell's audience.
  • A2A, Google's agent-to-agent protocol, 1.0 in early 2026, at the Linux Foundation, 150+ organisations.
    • For agents handing work to other agents, across companies. Not a need Spell has yet.

Owen decided (Q3, B): keep the editor's Change This flow, and replace its plumbing with AG-UI events and MCP tools. Here's what each part becomes.

today what it does becomes
ChangeRequests, the inbox file holds a request until a session takes it an AG-UI run: the request id is the threadId, the words and pictures its messages, the selected part its context
ClaudeStarter starts claude --print in the project's folder, with tight permissions the src/agents/ client starts the person's chosen agent: Claude Code through ACP or the Agent SDK, or a model in Spell's own loop
SessionLog reads Claude's stream-json log, guesses the step from the last tool used gone: steps arrive as TOOL_CALL_START events, the last word as TEXT_MESSAGE_*
spell app changes take / done how the session gets the request, and says it's finished gone: the request is the run's input, and RUN_FINISHED or RUN_ERROR ends it
Claude's own Read and Edit tools change files on disk Spell's MCP tools: read a part, change a file, through the editor's history (see editor-surface.html)
ChangeThis polling GET /api/changes asks every so often what's happened subscribes to the run with @ag-ui/client's HttpAgent, setting Solid 2 signals from its callbacks
  • What survives: the box, the selection's place, and "one step of editor.history" for the result.
  • What's lost: a request waiting with no agent running, for a session typed into by hand (spell app changes wait).
    • An outside agent could still pick requests up as an MCP tool, if Owen wants that kept (open question 4).
  • The permissions today's starter sets (edit only in the project's folder, never skip permissions) carry over: an MCP tool can do only what it's written to do.

// A sketch for discussion, not code in any branch.
import { HttpAgent } from "@ag-ui/client"
import { createSignal } from "solid-js"

const [step, setStep] = createSignal("starting")
const [answer, setAnswer] = createSignal("")

const agent = new HttpAgent({ url: "/api/agents/run", threadId: request.id })
agent.messages.push({ id: request.id, role: "user", content: request.text })

await agent.runAgent(
  {
    tools: SpellTools.frontend, // select a part, show the preview
    context: [{ description: "the selected part", value: JSON.stringify(place) }]
  },
  {
    onToolCallStartEvent: ({ event }) => setStep(event.toolCallName),
    onTextMessageContentEvent: ({ event }) => setAnswer((text) => text + event.delta),
    onRunFinishedEvent: () => setStep("done"),
    onRunErrorEvent: ({ event }) => setStep(`failed:  ${event.message}`)
  }
)

 CopilotKit's Claude quickstart: the agent's AG-UI endpoint · excerpt, 26 lines 
// docs.copilotkit.ai/claude-sdk-typescript/quickstart, src/agent-server.ts
const agent = new ClaudeAgentAdapter({
  agentId: "claude-sdk-typescript",
  model: process.env.CLAUDE_MODEL ?? "claude-opus-4-8",
  systemPrompt: "You are a helpful assistant embedded in a CopilotKit app.",
  tools: [],
  permissionMode: "dontAsk",
  maxTurns: 10
})

app.post("/", (req, res) => {
  const input = req.body as RunAgentInput
  const encoder = new EventEncoder()
  res.setHeader("Content-Type", "text/event-stream")
  agent.run({ ...input, runId, threadId }).subscribe({
    next: (event) => res.write(encoder.encodeSSE(event)),
    error: (error) => {
      res.write(encoder.encodeSSE({ type: EventType.RUN_ERROR, runId, threadId, message: String(error) }))
      res.end()
    },
    complete: () => res.end()
  })
})

  1. Spell's own model loop: which kit? Why it matters: it's the one big dependency of src/agents/, and adding one needs Owen's OK (WWOD §2). A, recommended: TanStack AI's headless client
    • AG-UI is its own wire format: nothing to translate.
    • Young: release candidate in August, 1.8 now.
         B: the Vercel AI SDK
    • The most used, every provider.
    • Speaks its own stream; AG-UI only through a bridge.
         C: write the loop
    • About a hundred lines over the two wire formats.
    • Ours to keep up with every provider's changes.
  2. Outside coding agents: through ACP, or Claude's Agent SDK? Why it matters: it decides whether Codex, Gemini CLI and Qwen Code work on day one. A, recommended: ACP
    • 49 agents, one protocol; people use the plan they already pay for.
    • Spell writes an ACP-to-AG-UI bridge: none was found.
         B: Claude Agent SDK first
    • AG-UI's adapter exists today; least to write.
    • Claude only, and its API key, not the person's plan (a guess, to check).
  3. Cards in the chat: A2UI, or Spell itself? Why it matters: the agent will sometimes need to ask with more than words (pick a colour, pick one of three layouts). A, recommended: wait
    • AG-UI's interrupts and frontend tools cover the first needs.
    • Choose once the flows (flows.html) show the cards.
    B: A2UI, with a Spell UI catalog
    • A standard Gemini and Jira speak.
    • A catalog mapping its components to <ui-*> to write.
         C: the agent writes Spell
    • One language for everything.
    • Slower, and a compile per card.
  4. Keep the "waiting request" mode? Today a request waits in the inbox for a Claude session someone started by hand. Why it matters: with AG-UI, a run needs an agent at once. A, recommended: drop it
    • The client starts the agent itself, every time.
    • The inbox file and spell app changes go.
         B: keep it, as an MCP tool
    • A session in any agent asks Spell's MCP server for the next request.
    • Two ways to do one thing.
  5. When to put the MCP server online, for Claude, ChatGPT and Cursor? Why it matters: it needs sign-in (OAuth) and hosting on spell.app, which is byo-agent.html's ground. A, recommended: local first, online second
    • The same server runs in the page server now, online later.
    • MCP Apps previews come with the online step.
         B: online from the start
    • Spell shows up in ChatGPT and Claude early.
    • Sign-in and hosting before the editor's own agent works.
