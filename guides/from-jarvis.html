From Jarvis

A 5,000-row column in <ui-tree appearance="columns"> now opens in 33 ms, drawing 72 rows. It took 2,041 ms before, drawing all 5,000.

A column view from data · from the tree's docs page 
<ui-tree id="work" appearance="columns" tools sticky-detail
  column-titles="Clients, Folders, Files" show="icon which count chevron" size="8em, 30%, auto">
  <ui-input slot="tools" icon="search" placeholder="Filter the whole tree"></ui-input>
  <ui-json slot="detail" depth="2"></ui-json>
</ui-tree>
<script type="module">
  const tree = document.getElementById("work")
  tree.items = [
    { id: "Acme", label: "Acme Bakery", icon: "building outline", data: { since: 2019 },
      // a list, a function run the first time it opens, or a promise
      children: () => fetch("/clients/acme").then((answer) => answer.json()) }
  ]
</script>

That's the Finder's column view, on a web page, for a tree too big to draw whole.

  • Only the open path's columns are drawn, and in each column only the rows near the screen.
  • The pane on the right shows whatever is picked, with no page code.

The Jarvis project builds its pages from Spell, and kept hitting the same walls: a netlist is a tree of thousands of nodes, a circuit is a graph, and its API answers JSON nobody wants to read raw. It had built its own pieces for each; now they're Spell's.

  • The tree's column view takes data, draws only what shows, and gained a path line, narrow columns, sizes, a remembered pick, a detail pane, Open levels and a whole-tree filter.
  • <ui-graph> draws nodes with ports and edges, laid out for you, with nested graphs shown inline, in a dialog, or drilled into.
  • <ui-json> draws JSON as an outline that opens and closes, and can edit it.
  • Under the page: Spell's OpenAPI reader keeps the routes that answer one record under a thing; each runtime copy in a production build gets its own core; the editor's console is quiet, and it hears file changes instead of polling.

Real today: all of the above, on main. Not yet: file upload, calling TypeScript helpers and subclassing elements from Spell, keyed places for pages, and lists asked for by a parameter.

appearance="columns" is one attribute on the tree you already have: no second tag, no mode. Rows come from markup, as before, or from data in items, and only data rows get the speed.

  • Each item has an id and a label. It may also have an icon, a short kind word (which), a count, its own data, and children.
  • children is a list, a function run the first time the row opens, or a promise.
    • While it loads, the column shows a spinner, never an empty column.
    • A function that returns nothing drops the row's chevron.
  • show picks each row's parts from icon which count chevron. It replaces the old counts attribute.
  • A subclass can style rows by data: rowClass(item) returns a class name for each data row.
  • The tree sends ui-changed on a pick, and ui-settled once the arrow keys stop.
  • A path line above the columns names every pick on the way down. Click a name, and that column's row is picked again, the columns after it kept, as the left arrow key does.
  • The outline draws the same line with sticky-path.
    • Long paths fold their outer names into one …, whose tooltip lists them.
    • Screen readers skip the line: the tree itself says where you are.
  • While the columns don't fit, the first ones narrow to a strip: the pick's icon, its name written sideways.
    • The last narrow-before columns (2 by default) and the selected one never narrow.
    • Hover or focus a strip, and it widens over its neighbours.
  • size gives a width per level, the last entry covering every deeper column. Each is one of:
    • a length in px, em or rem
    • a percent of the tree, never under 80px
    • a star, for the default width
    • auto, to fit the rows shown, up to three times the default
  • Resizing works as in the Finder: drag a line for one column, Option-drag for all.
    • Double-click fits a column to its longest row; Option-double-click fits them all.
    • Option works with the arrow keys too.
  • A width set by hand wins over size. Give the tree an id, and its widths and its pick are kept in the browser, and opened again on the next visit, unless the page sets a path.
  • <ui-split-panel> reads sizes the same way: one reader, shared by both.
  • Put an element in the tree's detail slot, and it shows after the last column whenever something is picked. The tree sets its item to the picked row.
  • A <ui-json> there shows the row's data with no page code at all.
  • It's as wide as its content, up to half the tree, and the columns narrow to make room. Its edge drags and double-clicks like a column's, and its width is kept.
  • sticky-detail pins it while the columns scroll sideways, as on a phone.
  • tools adds three small buttons: Open 2 levels, Open 3 levels, Close all. A tools slot puts your own field, a filter say, at the end of their line.
  • From code: await tree.openTo(2) and tree.closeAll(). openTo() opens level by level, waiting for lazy rows, and picks the path so far while a list loads.
  • In columns, filter filters the last column, then lists every other match at any depth under "Elsewhere in the tree", each with its path. A click opens the path to it.
  • To find those, it runs lazy children one level at a time, showing "Looking through the tree".
    • It lists 200 matches, and stops after 100,000 rows.
    • A tree shaped like a real netlist (8,772 nodes, 38,400 ports, all lazy) is searched in about 23 ms.
  • A data column draws 24 rows first, then more as you scroll; what's drawn stays drawn.
    • That's what turned 2,041 ms into 33 ms.
    • A 300-row column is unchanged, at 33 ms.
  • The pick and the tab-stop row are always drawn, with every row before them, so End, a path set by the page, openTo() and a filter match all land on a real row.
  • It's Spell's own drawnInWindow(), the one that draws Spell's long lists, moved down to spell/element so Spell UI can use it too.

The catch: markup rows are still all drawn. For a big tree, give it items.

<ui-graph> draws boxes with ports, and the edges between them, laid out left to right for you. Hand it JSON in its graph attribute, or an object in its property.

Two nodes and an edge · shortened from the graph's element examples 
<ui-graph style="--ui-graph-height: 16em" graph='{
  "nodes": [
    { "id": "parse", "label": "Parse", "ports": [{ "id": "ast", "label": "ast", "kind": "out" }] },
    { "id": "check", "label": "Check", "ports": [{ "id": "ast", "label": "ast", "kind": "in" }] }
  ],
  "edges": [{ "from": { "node": "parse", "port": "ast" }, "to": { "node": "check", "port": "ast" }, "label": "tree" }]
}'></ui-graph>
  • A node may hold a whole graph in its children, and child-view says how it opens:
    • inline, in place
    • modal, in a dialog
    • drill, which replaces the view and adds a breadcrumb back
  • It measures text the way <ui-diagram> and <ui-tree-diagram> do, and each one's docs say when to pick which: a graph has ports and edges in any direction; a tree diagram has one parent per box.
  • English and Spanish names, and a docs page with Examples, Usage, API and Theming tabs.

Not yet:

  • The keyboard reaches only the open and close toggles.
  • Back edges loop wide, and edge labels can collide on dense graphs.
  • Text isn't measured again after a web font loads.
  • Its height can't follow a percentage.
  • A right-side port's label can sit under a node's toggle.

<ui-json> always held JSON, for a diagram or a page to read; now it draws it too, as an outline whose objects and arrays open and close. hidden hides it, and one inside a diagram stays unseen, as before.

From the JSON outline's docs page 
<ui-json depth="2" editable>{ "name": "port-a", "lanes": [0, 1, 2, 3], "since": "2026-11-18" }</ui-json>
<ui-json quotes="no">{ "name": "port-a", "two words": 2 }</ui-json>
<ui-json source="examples/json-ports.json"></ui-json>
  • Its attributes:
    • depth opens that many levels
    • quotes shows or drops the quotes
    • no-header drops its Copy and quotes buttons
    Alt-click opens a whole branch, and a closed line is cut to its width.
  • editable picks each value's Spell UI input by its type: text, number, date or date-time (written back in its own time zone), a checkbox, and JSON for null or a key.
    • A pick list's choices come from the editors property.
    • Edits go through its text, so saving works.
  • Copy sends ui-copied, as the code element does, and a click on a key or value sends ui-navigating. Text that isn't JSON shows the parser's message.

The catch: each toggle is its own Tab stop; the arrow keys don't move between lines yet. To show JSON as code, use <ui-code>.

A Spell file can now call a function from the project's own TypeScript or Python with one statement, call native. A library wraps it in an action, so the programs that import it only ever see Spell words.

A clipboard library: its four files 
// __project.json5:  the code files beside the Spell files
imports: [
  { path: "/clipboard.ts", active: true },
  { path: "/clipboard.py", active: true },
  { path: "/Clipboard.spell", active: true },
  { path: "/Clipboard.es.spell", active: true }
]

// clipboard.ts:  plain TypeScript, nothing Spell-shaped in it
export async function copyText(text: string): Promise<void> {
  await navigator.clipboard.writeText(text)
}

// clipboard.py:  the same function for Python, in Python's case
async def copy_text(text: str) -> None: ...

// Clipboard.spell
use copyText from clipboard.ts

to copy (text as text) to the clipboard
	call native copyText with text

// Clipboard.es.spell
usar todo de clipboard.ts

para copiar (texto como texto) al portapapeles
	llamar al código nativo copyText con texto
 A program using it, and what each target compiles 
// a program's Spell:  the library's words, never a code name
copy the note's text to the clipboard

// the library's javascript
import { copyText } from "@spell/native/owen@spell/clipboard/clipboard.ts"
export async function copyTextToTheClipboard(text) {
  return core.asAction({ ... }, async () => await copyText(text))
}

// the library's Python
from clipboard import copy_text
async def copy_text_to_the_clipboard(text: str) -> Any:
    return await copy_text(text)
  • The call: call native copyText with text; several inputs with commas, with source, options; no inputs, just the name. Spanish: llamar al código nativo copyText con texto.
    • Only as a line in a to action's steps: anywhere else the line says so.
    • It waits when the function gives back a promise, or is async def, and so does its action.
    • A typo is a mistake on that line, naming the code files it looked in. "native" can no longer name a place.
  • The use line, at the top of a Spell file, says where its natives come from: use copyText from clipboard.ts, use a, b, c from clipboard.ts, use all from clipboard.ts; Spanish usar ... de clipboard.ts.
    • The file must still be listed in the project file, and must export each name it says.
    • A name in a use line comes from that file, even when another code file has one too.
    • A name in none is looked for in every code file the project lists, in order.
  • One code file per target, the same name before the dot: clipboard.ts (or .js) for javascript and TypeScript, clipboard.py for Python, its names in Python's case (copyText is copy_text).
    • A target with no file for a name is a compile error naming the file to add.
    • { path: "/clipboard.ts", only: "browser" } marks code only a browser can run: Python refuses it while compiling, naming the action that can't run there.
  • What each file exports is read, not guessed: Python's top-level def lines; TypeScript by the kit's TypeScript reader on the command line, and by its export function lines in the editor.
  • spell run runs it as javascript, TypeScript and Python (--target ts, --target py), and spell compile copies the .py file beside the compiled program.

Spell's OpenAPI reader, spell place ingest --spec, used to skip a GET under a thing that answers one object, like a system's deployment snapshot. Now it writes it as part of its owner, with the line Spell already had for lists under a thing:

What the reader writes · from its tests 
an instance's snapshot lives at "/api/systems/instance/{id}/snapshot"
  • No new place rule: lists_under takes one thing too (Spanish: está en).
  • The REST place reads the answer as its one row. spell place verify tries each record.

The catch: a record type written by hand without its "found at" line, holding one list, reads as that list.

  • A production build now gives each runtime copy its own core and runner, by the same rule the dev server uses. Solid, Spell UI, spell/util and the places stay shared.
  • The cost: spell-runtime.js grew from 195,775 to 279,580 bytes.
  • Hand defineElement() or useElement() a view from another copy, and it warns, naming the class.

Not yet: tried on a packed editor. The browser test declares its views by hand.
  • The "Server path for path" line is gone, and so are the API's per-request banner and "Sending JSON file": removed, not hidden behind a logger.
  • The editor no longer re-reads the open file every 2 seconds.
    • The page server tells it of project file changes over its live channel, and it re-reads only files in the open project.
    • In a headless check, a file written on disk reached the editor in 264 ms, and 15 idle seconds showed no polling.
  • It polls every 30 seconds only while the live channel is down.
  • The one shared watch is watchServerFiles(), in spell/util; the epic pages use it too.
  • One attribute, not a column tag. The handoff from the Jarvis project had its own column element; its pieces moved into <ui-tree> instead, so the row grid, show and the chevron are the tree's, and Jarvis's element shrinks to a subclass.
  • Markup rows draw themselves. Only data rows get the tree's own grid and windowing; markup rows keep working as before, with no retrying for tags that haven't loaded.
  • <ui-graph> kept its own tag, rather than becoming a mode of <ui-diagram>: its ports and edges are a different shape of data.
  • <ui-json> draws the outline itself, rather than a second viewer tag beside it. There's no appearance="code": it never drew JSON as code, and <ui-code> does.
  • Kept in local storage, not per tab. Widths and the pick live in one ui-tree store that outlasts the browser session, and only a person's picks are kept, never a path the page sets.
  • One filter, not a new search. It reuses the filter the tree had, and lists other matches after the column's own rows.
  • The windowing moved down to spell/element instead of a second copy in Spell UI. Spell hands in its own parts as settings.
  • The kit's watch moved down from the epic engine into spell/util, so the editor and the epic pages share one.
  • The arrow keys don't reach the filter's matches listed elsewhere in the tree: click them.
  • In a big column, the which words shift right as wider rows draw in.
  • The tree's columns have no visual baselines: the visual test runner can't load its config.
  • <ui-graph>'s rough edges (section 3) and <ui-json>'s Tab stops (section 4).
  • call native doesn't run in the editor's own runner yet: it compiles there, and runs with spell run. Python's web app (a program that draws, served on Quart) doesn't copy its .py code files in yet either.
  • The runtime split and the pushed file changes aren't yet tried on a packed editor; two hand checks wait on the epic page.
