Epic page: epic elemental-spell Written for: someone writing a Spell template in tags, or a developer changing how spellx reads, edits or runs Status: merged into main, 2026-10-25, in the kit, spell-parser, spell-ui, spell-app and spell-epic Checked on: main, 2026-10-25, by running the pair tests, converting a file and running a program that throws, and against the epic page's decisions
  • A .spellx file wraps each template in a tag, and each thing it declares in a short one: a property, an alias, an action, a drawing, an event handler, a menu.
  • Prose goes between the tags, as markdown: the lines just above a tag are its docstring.
  • It compiles to exactly what its plain Spell twin does, because each tag line is read AS that twin's line.
  • It sits beside .spell files in a project, and each kind uses what the other declares.
  • In the editor it opens as text, coloured, with errors and hover, as any Spell file.
  • Along the way Spell got the words it needed:
    • Template, View, Page, App, and alias for the words a template answers to
    • built-in templates written in Spell itself (a two sided view)
    • events that a handler takes, passes on or cancels
    • actions with a title, shortcut and undo step, gathered into menus
    • a converter from .spell to .spellx, and source maps
  • Open the Solitaire example in the editor app, then Card.spellx.
  • The full reference, every word in English and Spanish: README-spellx, in spell-parser.

A file holds one or more templates. Each opens with a prefixed tag naming what kind of thing it makes, and everything inside uses short words.

Card.spellx · from the Solitaire example, shortened 
<spell-view "card" template="two sided view">
	<group "rank" description="Ace is low:  ace = 1 ... king = 13"/>
	<property "rank" one-of="ace, 2 ... 10, jack, queen, king" alias="is a (rank)"/>
	<property "value">the position of its rank</>
	<alias "is a face card">if its rank is jack, queen or king</>

	<group "suit"/>
	<property "suit" one-of="clubs, diamonds, hearts or spades" alias="is a (suit)"/>
	<property "color" one-of="red, black">
		red if it is a diamond or it is a heart
		black otherwise
	</property>

	<draw "front">
		<text color={its color}>{its picture}</text>
	</draw>
	<draw "back">
		<text color="blue">🂠</text>
	</draw>
</spell-view>
  • The template's tag says its kind: <spell-view> draws itself, <spell-thing> doesn't, and there are a page, an app and a template for each. Add template="card" to make one from another.
  • Inside, short words, one per kind of member:
    • what it is and says: <property>, <alias>
    • what it does: <action>, <test>
    • how it looks: <draw>, <menu>
    • what it sends and hears: <event>, <on mouse down>
  • Every body is plain Spell, word for word what you'd write under the same line in a .spell file.
  • Closing:
    • </> closes whatever is open
    • </property> closes it, and checks it's a property
    • /> ends a tag with no body
  • Anything with no tag of its own (a file's functions, its starting lines) goes in a <spell> chunk, read exactly where it sits.
  • A comment is <!-- ... -->, anywhere, never drawn:
    • among a template's members, in a body, in a drawing's markup, in an <html> block
    • over as many lines as it takes; one never closed is an error on its first line
    • its plain Spell twin is a // line for each of its lines, so the two still compile the same
    • just above a member, it's that member's docstring, as the // lines above its twin are
    • not inside a <markdown> block, whose <!-- is the markdown's own
  • A member's comment can be its description= too, its docstring: every tag takes one, a handler at the end of its phrase, <on click description="...">. A // ... line still works in a body, which is plain Spell.
  • A word Spell doesn't know is an error that names the closest one: "<propety>" isn't a spellx word: did you mean "<property>"?
  • A drawing names a component bare: <text> is Spell UI's <ui-text>.
  • A name is looked up in the project's own views first (<card>), then in each component pack the project lists, Spell UI's alone unless it says more.
  • There's no plain HTML in a tag's drawing: <div> is an error naming the packs it looked in.
  • The web's own elements go in a <spell> chunk, plain Spell as written: there <div> and <button> are the web's.
    • Converting a file writes each member whose drawing has one as a chunk, just that member, so the program stays the same.
  • A drawing draws several things in a row.
    • It branches with <if ...> and <otherwise>: at its top level the branch picks what the drawing returns, rebuilt as it changes.
    • Inside an element, every branch stays on the page, hidden while it isn't the one: <text><if its active count is 0>All done<otherwise>{its active count} to do</></text>. A flip keeps the element, its state and focus; text and the web's elements are hidden="until-found", so find-in-page still reaches them, and a Spell UI element takes its own hidden. Plain Spell writes the same tags.
    • It loops with <for each ...>.
  • <draw "front" /> places one of a view's named slots.
  • Where a view is drawn, its slots can be filled with the web's slot=: <card><text slot="front">Ace</text></card>. A slot nothing fills draws its own <draw "front">.

A file's name says its language, and in Spanish Spell is Encanto. So Carta.es.spellx opens with <encanto-vista>.

  • Inside, the words are Spanish too: <propiedad>, <al clic>.
  • Words read with their accents and without; the editor puts the accent back as you type.
  • A drawing's bare names come from Spell UI's Spanish tags: <botón> is <es-boton>.
  • The Spanish examples (Solitario, ListaDeTareas) are still plain Spell; their spellx forms are test fixtures, .es.spellx, which a test compiles the same.

A .spellx file is a full citizen wherever a .spell file is: the editor app, the command line, the language server and VS Code.

  • One file per template. A template lives in ONE file, .spell or .spellx, never both: two copies drift apart. The other form is a read-only view.
  • VS Code's title bar has Show as Code Spell, and the editor app a Code Spell tab: the plain Spell a .spellx file means, written rule by rule.
  • The other way, on a .spell file: Show as Spellx in VS Code, and a Spellx tab in the editor app, the file laid out in tags as spell spellx convert would write it.
  • Edits happen only in the real file, so the view always matches it.
  • It's for reading: it differs from a hand-written twin only in layout, and compiles the same.
  • Hover, completion, colours and folding work in the .spellx file itself, on the words you typed, never the twin's.

Would write 1 file
  • An action's shortcut and undo name become its attributes; a lone comment above a member, its description.
  • What has no tag yet stays as written, in a <spell> chunk: here, the menu.
  • The .spell file stays. Keep only one of the two in a project, or it declares everything twice.
  • Spanish files convert too, into Spanish spellx.

Spellx and plain Spell must say the same things, so plain Spell grew everything spellx needed. These work in both.

  • A template declares a kind of thing; a thing is one of them.
  • A view is a template that draws itself (it was "drawable thing"); a viewable list was "drawable list".
  • A page is a view with its own address, and an app is a view you publish.
  • An alias is the words a template answers to (it "is a face card"); it was "phrase".
  • The old words are errors that name their fix, and spell lint --fix rewrites them.
  • The page element that runs an app is now <spell-viewer>, so <spell-app> is free for an app template.
  • A two sided view (a card, a tile) is written in Spell itself, in TwoSidedView.spell and its Spanish twin, and compiled once.
  • It brings a direction, face up and face down, turn it over, and a drawing that picks the side: a card made from it writes only its front and back.

In a browser, an event bubbles past every handler unless one stops it. Here it's the other way round: the first handler that runs takes it.

  • send flipped with side = up goes to the thing first, then the list holding it, then the app.
  • A handler hands it on up with pass event; an event nobody takes is dropped.
  • An event still happening (closing) can be cancelled, and the sender's next step doesn't run.
  • send waits for each handler in turn, so wait for send x waits for them all.
  • A handler says when it runs: on, when or while. In spellx it's a tag, <on mouse down>.
  • The keys and the mouse can be read anywhere, not only in a handler: the shift key is down, the mouse is still down (held a second).

The events Spell UI, the editor and the epic pages send were renamed by one rule.

  • While it can still be cancelled, its name ends in -ing: ui-opening.
  • Once it's done, in -ed: ui-opened.
  • An action can say more than its steps:
    • its shortcut and icon
    • when it's enabled, and when it shows a tick
    • its name as an undo step, undone as "Deal"
  • However it's run (a key, a click, a menu, code), it goes through one place: nothing runs while it's not enabled, and undone as makes it one undo step.
  • A shortcut starts at the focused thing and goes up to the app; the first enabled action takes the key. Meta is ⌘ on a Mac, Ctrl elsewhere.
  • A named menu of actions is used three ways: the menu bar, a toolbar, and a right-click menu (context-menu=).
  • Undo and redo are the app's own actions, their titles live: Undo Deal.
  • Spell UI's new <ui-action> draws one: title, icon, key caps, greyed or ticked.
  • Every compile writes a standard source map beside the compiled file, in the project's git-ignored build folder.
  • The editor's runner, spell run and <spell-viewer> use it, so an error names a Spell line, not a line of compiled JavaScript.
  • A .spellx file maps to its own lines directly: its positions are its own.
  • The declarations files moved into the build folder too, so no compile, test or README run leaves a stray file in a checkout.

A Vue file hands its <template> to an HTML parser. A spellx file never meets one: Spell's own tokenizer reads it, and Spell's own rules parse it.

  • Each language's twin words are data in its words file (English its {name} is one of {one-of}, Spanish su {name} es uno de {one-of}), so a third language adds words, not code.
  • Since the tokens keep their places in the .spellx file, errors and hover land on the right line with no map in between.
  • A body line ending in </> ends its body, even if it meant a JSX fragment.
  • Spell's own parser reads spellx, over a reader of its own that wrote the file out as plain Spell and compiled that. The writer would have needed a map from every .spellx line to its .spell line, for errors, hover and source maps; reading it in place needs none.
  • A tag line parses as its twin, over new rules for each tag. New rules could drift from the old ones; a twin can't, and the 8 pairs prove it.
  • A closed set of short words, over HTML's open one, or a prefix on every tag. Only the template's tag says spell-, so a reader sees where Spell starts, and a typo is an error, not an unknown element.
  • No native HTML in a drawing, over allowing <div>.
    • Components come from packs by bare name, so a Spanish file can say <botón>.
    • What Spell UI still lacks next to HTML is its own epic, ui-gaps.
    • An escape hatch like <html-button> was set aside: agents would reach for it first.
  • Plain Spell grew to match, over features only spellx has. Slots, aliases under a property, an action's shortcut and undo name, tests inside a template, events a template sends: each landed in plain Spell first, English and Spanish, so the two stay equal.
  • One file per template, over keeping both forms side by side (Owen, 2026-10-25: "one file"). The showcases, Solitaire and Task List, are written in spellx, their plain Spell twins kept beside the tests; the other examples keep their .spell files, their spellx copies the fixtures. A test keeps each pair compiling the same. The other form is a view, Show as Spellx or Show as Code Spell.
  • Built-in templates are written in Spell, over hand-written classes. A two sided view's words are read like any other Spell, so a card made from one compiles to only its own front and back.
  • A handler takes the event, over the browser's bubbling. A card that handles a click usually means its pile shouldn't also act; pass event is the rarer case, so it's the one you write.
  • One place runs every action, over each caller checking enabled and recording undo. A key, a menu and a click can't disagree about whether an action may run.
  • Source maps and declarations live in the build folder, over beside the source: out of every diff, rebuilt when stale.
  • A <for each ...> or a handler inside an element isn't read: write it on a line of its own in the drawing. An <if ...> there is.
  • A Spell UI element in a hidden branch isn't found by find-in-page: it takes its own hidden, as the browser's until-found draws nothing different for its box.
  • An if among other drawn lines can only draw: a branch that also sets something draws nothing, with a note in the compiled code.
  • In Spanish, an action named with a built-in template's words is called as the template's: Solitario's voltearla boca arriba.
  • A native element in a drawing is written in an <html> block, as the web writes it: the whole block, not one element inside a drawing of Spell UI's.
  • A template's members are all in its own file: spellx has no tag that adds to a template from another file, as plain Spell's a card: does. Solitaire's moves, a card's and a pile's, are its game's, in a <spell> chunk.
  • A function, and a few lines (it can be dragged, it can take a card if:), have no tag yet: <spell> chunks hold them.
  • In spellx, a handler's pass event and cancel event aren't read and written yet.
  • A while handler can only wait on the mouse so far. The timed forms (for 1 second, every 5 seconds) aren't built.
  • The page's mouse and key events don't have Spanish words yet.
  • The Python core has no send, and no readable mouse and keys.
  • Many renamed events have only one half of their pair so far (an -ed with no -ing, or the other way).
  • An action's enabled and selected conditions can't use the action's inputs.
  • A toolbar's actions go in only once it has drawn.
  • No VS Code menu, Python runtime or visual tests for actions.
  • Completion in a tag's head offers types, not spellx's own words.
  • The converter leaves a menu in a <spell> chunk, not a <menu> tag.
  • Re-parsing an edit inside a <spell> chunk is untested.
  • spell run's stack trace names a temporary copy of the file, and one line early: Boom.spell:5:2 for a throw on line 6.
  • The Python target writes no source map, and TypeScript's isn't chained through Solid's JSX build.
  • A page has no address yet.
