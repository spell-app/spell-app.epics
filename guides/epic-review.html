Epic Review

 The first line of a session your Send woke 
📬 seo:  taking your Send from the epic page (3 marks:  J149 approve, I91 approve, I83 do this).  Take it:  `epic inbox wait seo --timeout 5`, then the /epic skill's "7.3 Woken";  and keep `epic inbox wait seo` running in the background while you work.

You marked three items on the seo epic's page and pressed Send. Nobody had typed anything: the epic's session was idle, and that line woke it. A moment later J149 and I91 are closed on the page, and I83 shows a blue Underway card naming the agent fixing it.

That's /epic review [<name>] today: a session that listens to an epic page while you mark it, applies what you send, and writes every answer INTO its item, never only into the chat. A pull request's review is a batch you submit; this one can wait a day, and comes back as edits to the plan.

  • Every mark, button and colour on the page: README-pages, "A review round".
  • The session itself does only quick things; anything longer goes to a named agent, so it's free to hear your next Send within seconds (README-skills, "The session answers; agents build").

You rarely type /epic review: an epic's own session listens whenever it's open.

  • Typed: /epic review <name>, from any window, the main checkout's or a worktree's.
    • It says in three lines what the epic is, what's waiting on you and when you last reviewed it, then shows the page at the first red item (else the first yellow one).
    • No name: every epic in the chat, most not-reviewed first, then a question modal of two at a time plus More.
    • The prompt hook lets it through and keeps the session's title, except in a session titled for a DIFFERENT epic (🚧 seo typing /epic review airplane): that it refuses, in one line.
  • From the page: a click on the orange "No Claude session is reviewing" pill. The page server finds the ONE running session titled for the epic, and asks it through its inbox, or types /epic review <name> into its tab for you to press Enter. None, or several: nothing is sent, and the page says which sessions it found.
  • Woken by Send, with nobody listening. The page server takes the first of these that applies:
    1. the epic's running session: told through its inbox, or /epic review <name> typed in for you to press Enter
    2. else a new session in the epic's worktree window, opened if it's closed: titled 🚧 <name> as it starts, it wakes by itself with the 📬 line
    3. else, for an epic with no worktree, a new session in a main window, the command typed in
    • At most once per epic per 10 minutes, or until a session listens; never a second session while one of the epic's runs.
    • Never with several sessions titled for the epic, in airplane mode, or for a Send with nothing new.
    • The pill says what it did ("Typed /epic review seo into 🚧 seo: press Enter there") until a session listens.

A chat waits for you to type. An epic session also waits for the PAGE, at almost no cost: nothing runs between your Sends but a small poller, about 45MB a session.

  • The plugin starts the poller as each session starts and at each turn's end (an asyncRewake hook), for the session whose title or worktree names the epic.
    • It prints nothing until you Send; then the one 📬 line above, which wakes the session.
    • It ends once it has woken the session, so from then on the session keeps epic inbox wait <epic> running in the background while it works: a Send reaches it mid-work, at its next step, not when its turn ends.
    • /epic review's epic inbox watch takes the inbox over; once that session's wait stops for good, the poller takes it back within about 90 seconds.
  • A VS Code restart ends every background agent with its session: the session is woken at once with a 📬 line naming each agent the restart cut off, and resumes them.
  • The catch: a scripted claude -p waits for every session-start hook before it answers, so in an unattended session (Claude Code's CLAUDE_CODE_SESSION_ATTENDED is 0) the poller and the restart wake end at once. claude -p "say hi" with the plugin on took 4 seconds after that, and was killed at 120 before.
  • Codex has no background commands: its session runs epic inbox wait in the foreground, so a Send reaches it only while it waits.

Epic pages pile up open items, and nothing recorded which ones you had already been through. Three attributes on an <epic-item> do now, each drawn as a label after its id:

Attribute Means Label
reviewed="2026-10-03" gone through with you that day; the outcome is in the log green "reviewed 10/3/26"
deferred="2026-10-03" put off; still not reviewed grey "deferred" (the date on hover)
queued="2026-10-03" + work work a review decided on, not started yet; also reviewed blue "to do" (the work on hover)
  • Reviewed also counts an item that's struck, decided, or linked from a decision's details, so a page settled before the marks existed isn't all "not reviewed".
  • Applying your marks sets them, and every /epic session marks the items it talks through with you.
  • Older pages: a one-off epic backfill finds items you named in past sessions, a dry run unless --apply. The edge: it's a guess, and finds little, since you rarely type item ids.

inbox status <name> "<text>"            the line beside Send:  what the session is doing
update <name>#<id> underway|done|noted "..."   Claude's status card on an item
inbox done <name>#<id>  /  clear          a request finished  /  marks dropped after a talk
review <name>#<id> ["outcome"]           mark reviewed today;  the outcome goes in the log
defer <name>#<id>                        put off;  still not reviewed
queue <name>#<id> "work"  /  unqueue      on / off the to-do list
backfill <name> | --all [--apply]        one-off:  what past sessions show you went through
  • Every command edits the epic's ONE page, the same file in every checkout: no per-worktree copy to find or avoid.
  • The page's controls need a page server with the review routes (epic server ensure); opened from disk, the page shows no buttons.
  • Every epic, running and merged, is a card on one Epics list, in five groups: Favorites, Active, Planning, Urgent (every phase done, items waiting on you) and Done.
  • Two writers fill it: epic pages index writes the merged epics' cards and a slot, and the main checkout's page server (RunningEpics) fills the slot with the running ones.
  • Each card shows its state: in progress (blue), errors (red: every phase done, items need you), paused (grey: phases left, untouched for 3 days), done (green).
  • The edge: a card is as fresh as what drew it. Served, it's judged on every load; opened from disk, it's as of the last epic pages index.
  • Review on the page, not in modals. The first build walked items one at a time in question modals, four options each, and the session held you until the walk ended. On the page you mark what you like, in any order, and leave halfway.
  • Answers in the items. A chat scrolls away; the epic page is what you come back to cold, weeks later.
  • Marks wait for Send. You can mark for an hour and send once: the session wakes once, not per click.
  • Nothing is ever sent for you. A wake types the command, and you press Enter; only a session the page server opens itself, with nothing typed, starts by itself.
  • Every epic-page command edits the live page. Otherwise a review from main of an epic running in a worktree would edit a stale copy.
  • Your marks wait in a file on THIS machine (the epic's inbox, git-ignored) until they're applied: mark on the laptop, press Send on the desktop, and the desktop has nothing to send.
  • Send wakes only Claude Code; a Codex session hears it only while it waits.
  • A wake that types into a tab already open can't: VS Code refuses it, so nothing is typed and the page says to paste the command.
  • A review picked a section in a modal (sections by most not reviewed, "Todos · 17/21"), then you ticked items on a details page, a card per open item with its whole text.
  • Each came up in the chat as clean bullets, then a modal: Accept (if it had a recommendation), Explore, Explain further, or Defer.
  • Explain further wrote a details page, then a second modal of up to two options.
  • Work an answer called for went on the to-do list, and "Start work" opened it in its own worktree.
  • Reshaped six times on canned data before any real state existed; the picker moved from typed ids to a details page once the details skill landed.
