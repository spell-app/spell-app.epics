Windows and Review

Type a note on an epic page in the side bar, reload from another port, and it's still there. Press the wand, and a background agent answers into the item; type /epic color teal, and the window turns teal without a reload. Epic windows-and-review made all three: reviewing an epic page ON the page, reading one, and the VS Code windows and session names around it.

  • A note you type on the review page is saved on the server as you type.
    • So a reload from any address brings it back.
    • A sent note stays in view under its item.
  • Each item's ⋯ menu became buttons: Approve, Make Todo, Revisit, then Add Details Now.
    • Grey until chosen, green = decided, orange = pending.
    • Click a chosen one again to clear it.
  • An opened item ends in a note box, with Make Todo, Later and Do Now beside it.
    • A running request can be called off ("nevermind").
  • Review Now (a wand beside the paper plane) has the listening session work through all your marks at once.
    • Every answer lands in its item, never only in the chat.
  • Epic pages read better:
    • phases are Symptom, Changes, then the details
    • plan changes are fenced, dated lines
    • an open item's line sticks while you read it, and folds from a button at its end
  • A VS Code window can take a look: Tomorrow Night Blue's colours in one of 12 hues (/epic color teal, /epic x -teal), with no reload.
  • A session that stays in its window retitles and tints it ⎇ <name> at once; /isolate done puts both back.
  • A finished session's name gets ✅ (epic session done), one prompt late. Reopening the work takes it off.

Open an epic page in the side bar's Review tab (/epic review <name>). Every item can be marked, and a session listening on the epic's review inbox acts on them.

  • Before: a note lived only in the browser storage of the page's exact address, port included (127.0.0.1:4747 and 127.0.0.1:58173 each had their own).
    • A worktree's page server restarting on a new port, or the side bar showing the main server's copy, lost it.
  • Now: every note box saves to the inbox as an unsent draft (POST /api/review/draft):
    • 10 seconds after the last key, and at once when you leave the box or the page.
    • A small floppy in the box's corner says it's saved (its tooltip says when), red if it failed.
    • A reload from either server, at any address, brings the text back.
    • Browser storage is only a backup now, handed to the inbox when the page loads.
  • A marked note stays in view under its line ("You · revisit soon · sent 10:42"), with Edit to reopen it.
    • Before, a sent note vanished from the page (I1).
  • A speech bubble on the line says a note is there: outlined for a draft, solid once marked, and your words on hover.
  • When Claude is done with a note (plan-doc inbox done | clear), the note is written INTO the item first, as your own orange reply card. Nothing you wrote leaves the page.
  • A page whose server restarted takes the new write token and retries once, instead of refusing your note. That was likely one of the ways notes were lost.
  • Each item's line ends in a tight group of its STATES, then one action:
    button icon colour when chosen what it does
    Approve check green (decided) fine as it is
    Make Todo list check green (decided) follow it up later, as a todo
    Revisit clock with arrow orange (pending) talk it over: opens the note box
    Add Details Now wand, its own round button orange (pending) Claude writes a fuller explanation into the item, at once
  • How a button looks says where its mark stands:
    • grey outline: not chosen
    • filled: chosen, not sent
    • outlined in its colour: sent, and still after Claude applied it, even after a reload (the doc records data-review-as on the item)
  • Clicking the chosen one again clears the mark: no action.
  • Add Details Now and a revisit asked "now" spin while Claude works on them.
    • Asked with no session listening: a still, dashed ring, and a notice at the window's bottom.
  • Tooltips are the plain browser ones: just the name.
  • The buttons sit at the line's far right, in room the line keeps free, so a title never wraps under them.
  • It's docked at the END of every opened item that isn't approved, inside its details, before the fold button.
    • An item with no details gets it under its line, opened by Revisit.
  • Three round buttons stacked at its right, in the line's order (Q10):
    • Make Todo (list check, green): the todo, with your note written into it.
    • Later (comment dots, orange): revisit soon, talked over in the next batch.
    • Do Now (the wand, blue): revisit now; a background agent answers at once.
  • Each is a ring in its colour, filled when pointed at, and for the item's current mark.
  • Every review button takes the Spell UI theme's hues (--ui-green, --ui-orange, --ui-blue), each with its own ink.
  • It grows as you type (field-sizing: content), and so do the details pages' Other and Notes boxes (Q7).
  • The SAME box survives its item's body re-fetching from its part file: text, focus and caret are kept.
  • Click a spinning Add Details Now or Do Now again to call it off (POST /api/review/cancel).
  • The inbox records it canceled, and the listening session stops that item's background agent.
  • plan-doc details refuses a late write for it, so no unwanted text lands in the item.
  • A called-off revisit's note comes back as a draft.
  • Before: Add Details rewrote the item, burying what was there.
  • Now: the item's text stays on top, titled Original Reply. The new text goes under it in a white More Details card, open, that folds from its title (plan-doc details --more).
  • A second Add Details replaces the card, and the old card's text moves into the item's folded Original Discussion, dated (J1).
    • So an item never shows more than one More Details card.
  • The page header holds two buttons: Send (the paper plane) and Review Now (a wand, right of it), blue while there's anything to work through.
  • Send works as before: it queues your marks for the session's next batch.
  • Review Now sends every mark too, and turns each revisit still waiting (unsent, or sent and still to talk over) into a request for now, as Do Now does (J7):
    • a background agent per item answers it into the item, its Revisit spinning meanwhile
    • approvals, picks and todos are applied as with Send
    • a mark carrying a pick ("B, but ...") keeps it, so the agent answers about B
  • The catch: it needs a session already listening (/epic review <name>).
  • Before: answers to "revisit now" went into the item, but answers to "revisit soon" came in the chat, one at a time. That was a long scroll after a big review.
  • Now: every answer goes into its item as a reply card on the page, revisit soon too. The chat only says which items got one, with links (the epic skill, step 7.3).
  • Details pages (/details, epic ask show) now open in the side bar's Review tab, where Owen answers things, not in Spell Docs.
  • Cmd+C, X, V, A, Z (and the Edit menu) did nothing in the Spell Docs and Review side bar pages.
  • Why: VS Code turns them into document.execCommand("copy") ... on the side-bar view's OWN document, the wrapper, never the page framed inside it.
  • The fix: the wrapper's script (DocView.ts) replaces execCommand for those six and sends each to the extension, which hands it into the page (liveClient.ts edit()). Owen confirmed it works.

  • A change to a phase's plan (plan-doc updated) is a fenced, dated line right under its Symptom / Changes, never a word buried in the text.
  • It stays for good: a record of how the plan moved (J2).
  • A Plan changes box at the top of the Phases section lists each change while its phase is still to do (todo or active), then drops it.

Since 2026-10-11 (epic epic-workflow P6): the Plan changes box moved into each phase, atop its body, with the same look. It's open while the phase isn't done and folded once it is, and a phase still to do shows an orange pen and the count on its title. Nothing draws a box above the phases any more.

  • The "Plan hung?" notice starts folded, an aside, instead of always open.
  • plan-doc new folds it as it creates the doc, and migrate folds an older doc's. The shared template keeps it open, for older checkouts (J3).
  • An open item's line (question, issue, caveat ...) sticks under its section's stuck title while you read its body, with its review buttons usable.
  • Its details end in a small round fold button (chevron up).
    • It floats at the window's bottom while any of them is on screen, in a gutter at their right: never over the text or the note box's buttons.
  • Folding an item you're inside, from the button or its line, keeps the line where it was stuck, so the page doesn't jump.
  • The cost: an open item's text is 22px narrower, and ends in a 24px line holding the button (J5).
  • Page Down, live updates and links to an id inside the item all keep clear of the stuck line (J6).
  • The note box sits INSIDE the item's details, so the sticky line and the fold button both stay in view down to the box's end (Owen asked, C3).
  • So while you write in an item's box, you still see which item it is, and can fold it from there.

Telling windows and sessions apart at a glance (P5, P6). The window tools live in window.mjs.

A look is a colour scheme for the whole window, not just its title bar.

  • 12 names: red, orange, amber, green, teal, cyan, blue, indigo, purple, pink, brown, grey. blue is Tomorrow Night Blue itself.
  • Each is made by re-hueing the blues in Tomorrow Night Blue's own window colours. Its greys, whites and terminal colours stay, and so does the rest of your own colour settings.
  • /epic color <look> (epic window color <look>) recolours the window you're in, at once. With no look, it lists them.
  • /epic <name> -<look> and /isolate <name> -<look> open the new window in that look (window open --color). With no look, the current window's.
  • The prompt hook keeps -teal out of the kickoff text, and lets /epic color through.
  • The edge: only a window opened from a .code-workspace file can take a look. Every package and worktree window is.

  • Before: a session that stayed in its window for /epic x or /isolate x left the old title up (it said docs-sidebar (Workspace) while a session worked in quick-open).
  • Now: epic window stay <name> titles the window ⎇ <name> and tints its title bar the worktree's colour, at once.
    • The isolate, epic and unpark skills run it when you pick "Stay in this window".
  • What it replaced is kept in the window file's spell.stay, and stay --end (run by /isolate done) puts it back.
  • A starting window draws the theme colours VS Code cached from the last window that had them. It reads its own colour settings only when they CHANGE: a probe opened green came up in an older probe's purple.
  • So epic window open writes the window file without its colours, opens the window, and waits until it's up (its registry entry, then 1.5s). Then it writes the colours: a live change, which applies.
  • You may see the old colours for a second or two while it opens (C5).
  • Window not up within 60s: the colours are written anyway, and any later change to them applies them.
  • The worry: changing a window's file might restart its extensions, the Claude panel included. Folder changes have (PAPERCUTS, 2026-10-01 and 2026-10-04).
  • Tested 2026-10-06 on a throwaway worktree's window, probe-colors, before anything relied on it:
    • test 1: its workbench.colorCustomizations and window.title changed by hand. The window took both at once, and its extension host kept its pid (43119).
    • test 2: the theme switched too (workbench.colorTheme, plus theme-scoped colours). Same pid; Owen confirmed it went purple and was retitled.
  • So looks and stay write the workspace file: no extension change, no window reload.
  • epic session done: this session's name becomes ✅ <name>. done <name> marks every session of that worktree.
  • /isolate done runs it after its merge, and /worktrees when it removes a merged worktree.
  • It lands one prompt late: after your next message to that session (even "thanks"), or when it's resumed.
    • Why: the Claude panel ignores a title written into its title file from outside (tried on precedence-and-types, I4). Only a hook can apply a queued title.
  • Marking OTHER sessions (from /worktrees) takes only when each is reopened.
  • Reopening the work (/isolate <name>, /epic <name>, /unpark <name>) takes the ✅ off, and drops one still queued.

Every command, flag and route the epic added or changed. The map of all commands: Commands.

command what it does
epic add-phase <name> "Name" --symptom html --changes html changed, P3: a phase that reads Symptom, Changes, then the details; without either flag, the old Goal / Files / Verify shape (J4)
epic update <name>#P<N> [--symptom] [--changes] [--goal] [--files] [--verify] new, P3: set a phase's body fields; "" removes one
epic updated <name>#P<N> "html" | --file path new, P3: a change to phase N's plan, in its fenced, dated Updated block; listed in Plan changes while N is to do
epic details <name>#<id> --file <html> --more new flag, P3: Add Details: the text stays on top as Original Reply, the file's HTML in a More Details card
epic migrate <name> changed, P3: also splits Symptom / Changes out of older phases' goals, and folds an old Plan hung? notice. Gone since epic epic-components: epic convert replaced it.
epic inbox done <name>#<id> | clear changed, P1: inbox lists drafts; done / clear keep a mark's note in the item as Owen's reply card
POST /api/review/draft { page, id, action, note } new route, P1: a note box's text, saved as typed
POST /api/review/cancel { page, id } new route, P2: nevermind: call off an item's request for now
POST /api/review/send { page, now: true } new flag, P4: Review Now: send every mark, and ask each waiting revisit now
epic window color [<look>], /epic color <look> new, P5: give this window a look; no look: list the 12
epic window open <name> --color <look>, /epic <name> -<look>, /isolate <name> -<look> new flag, P5: open the new window in that look; default: this window's
epic window stay <name> | --end new, P5: title this window ⎇ <name> and tint its title bar / put both back
epic session done [<name>] new, P6: queue ✅ <title> for this session, or every session of a worktree
epic ask show <page> changed, P6: opens the page in the side bar's Review tab, not Spell Docs

Each decision as "chose X over Y, because Z". Q is Owen's answer to a question; J, a call made without him.

  • Drafts on the server over browser storage, because browser storage belongs to one address, port included, and notes went missing whenever the page came back from another (P1).
  • Green = decided, orange = pending (Q4) over four colours of their own (the proposal: green, slate, teal, amber), because Owen picked it from live button sets on the action-colours page.
  • States in the group, Add Details Now on its own (Q8) over four buttons in one group, because Add Details Now is an action, not a state an item is in.
  • Plain browser tooltips over popups, because the popups were jumpy (Q8).
  • Later: comment dots, orange (Q10) over a check (read as accepted), a clock (Q8's pick), a paper plane (read as "sent to Claude now") or green (Q9, canceled): orange is pending, as Revisit on the line.
  • The theme's hues over hand-picked colours like #e09b0d, because the hand-picked ones were ugly (Q10).
  • Review Now = send and act now (Q2 B) over a button that starts a review session for you (A), because Owen wanted marks worked through at once; Send keeps queuing as before.
  • Review Now reuses requests for now (J7) over a new mode for the session, because that path already has the spinner, nevermind and the late-write refusal: nothing new to build or learn.
  • Answers in their items (Q3 A) over a quieter notice pill, because the "bottom pane" Owen meant was the chat, which didn't scale to a big review.
  • A second Add Details replaces the card (J1) over stacking cards, because the item stays short, and nothing is lost: the old card goes into Original Discussion.
  • Edit keys through execCommand (I2) over keybindings, because VS Code never sets focusedView for a side-bar webview, so the keybindings never fired.
  • Updated blocks stay for good (J2) over dropping them when the phase is done, because they record how the plan moved. The Plan changes box lists only work not yet done, so the top never crowds.
  • Plan hung? folded at creation (J3) over changing the shared template, because older checkouts' add-phase looks for the notice as a ui-message, and would leave it up for good.
  • add-phase without the flags keeps the old shape (J4) over empty Symptom / Changes fields, because older callers shouldn't write blanks. /epic passes both.
  • The fold button on its own line, in a gutter (J5) over floating over the text (it would cover whatever line is at the window's bottom) or beside the last line (tried: it rode up over Add Details Now as the details came into view).
  • The sticky line in plain CSS (J6, ui-accordion.plan-item::part(title)) over a change to spell-ui: no ui fix, no runtime style.
  • The note box inside the details (C3) over after them, because after them the sticky line and fold button scrolled away just as you reached the box.
  • 12 named looks (Q1) over any CSS colour, because they're short to type, always readable, and the same purple every time.
  • The whole window in Tomorrow Night Blue's look (Q1) over just the title bar: Owen's answer.
  • Retitle and tint live over reloading the window (Owen, 2026-10-06), once the restart test showed nothing restarts (Q11).
  • Colours written once the window is up (C5) over writing them with the file, because a starting window ignores colours that haven't changed.
  • A queued ✅ title (I4) over writing Claude's title file, because the panel ignores a title written from outside.
  • C2: check-review-epics.mjs skips its Choose steps (a pick, "pick B, but ...", un-pick).
    • Why: no epic page it can use has an open question with option cards A and B and an empty inbox.
    • The pick code didn't change, but the new buttons beside it weren't clicked through with a pick.
    • Next time a doc has one, run it: node spell-epic/src/demo/check-review-epics.mjs --doc <epic>.
  • C3: two small, cosmetic limits of the sticky line and fold button, both from how the browser lays the page out:
    • folding an item near the page's end can't keep its line in place once the page gets shorter than the window (the browser clamps the scroll); I2, the last issue, at 700x500, drops about 30px
    • the review notice at the window's bottom (6 seconds, full width at 280px) can sit over the fold button while it shows
  • C5: a new window opened with a look shows older, cached colours for a second or two first.
  • The ✅ arrives one prompt late, and on other sessions only when each is reopened (I4).
  • V1: type a note, then reload the side bar. The box is open again with your words and an outline speech bubble; mark it, and it shows under the line with Edit.
  • V3: open this epic's phases: each reads Symptom, Changes, then the details.
  • V4: Add Details Now on an item with text: Original Reply on top, a white More Details card under it, nothing above rewritten.
  • V5: fold a long item (Q1, I2) from its bottom, in the side bar and in Chrome, dark mode and narrow. The line stays put, and the button never covers text or buttons.
  • V6: Review Now with /epic review listening, on two Later notes and an Approve. Both revisits spin at once and get reply cards, the approval lands, and the chat only links.
  • V7: /isolate x -teal with a new window: titled ⎇ x, teal after a brief flash. /epic color pink turns any window pink at once.
  • V8: the next /isolate done that merges: ✅ <name> after the next message, and /isolate <name> again takes it off.
