  1. Press Start at the top of the page, which also says where the CSV file and the folder are: open both in VS Code. Restart goes back to the first recipes. What the buttons start ends when the page server does. Started by hand, they stay until stopped: 
    yarn tsx scripts/recipe-servers.ts
  2. Change a recipe in REST. It's in the CSV file at once, and GraphQL and the sheet show it within a second or two.
  3. Add, move, change and remove a recipe in the sheet, with the file's diff open in VS Code, or git diff --no-index against a copy: only that line changes. A note with a comma keeps its quotes, and the row you didn't touch stays byte for byte. Move a row and edit it at once, and both show.
  4. Edit a row in VS Code, and save. All three show it within a second.
  5. A clash: type in the same recipe's title in REST, and in VS Code or GraphQL, within a second of each other. REST keeps yours, and a notice holds the other, with Use theirs. Change another field or another row, and both stand with no notice.
  6. Change a recipe in the folder frame, or its file in VS Code. Both room windows show it at once. Change it in the room, and it's in the file, and the folder frame shows it within a second.
  7. Change a recipe in one Airtable frame. The other shows it within a few seconds: nothing tells it, and it finds out by reading again. However many tabs are open, the server reads Airtable once for each read in each window.
  8. Edit it the way someone in Airtable's own window would: a request straight to the stub, as if a person typed there. Both frames show it within a few seconds, and nobody is told who changed it. 
    curl -s http://127.0.0.1:4795/v0/appStubStubStub01/Recipes -H "Authorization: Bearer patStub.notARealToken" | head -c 300
curl -s -X PATCH http://127.0.0.1:4795/v0/appStubStubStub01/Recipes -H "Authorization: Bearer patStub.notARealToken" -H "Content-Type: application/json" -d '{"records":[{"id":"rec00000000000001","fields":{"Title":"Edited in Airtable"}}]}'
  9. A clash in Airtable: type in one recipe's title in both frames. The last save wins that field, and the other frame's words go, with no notice. Airtable has no way to refuse a stale save. Two different fields both stand.
  10. Clash in a room: type in one recipe's title in both windows. Each may flicker, then both show one of them, and whoever lost a long text keeps it in a notice.
  • The CSV file: a copy of recipes.csv, made the first time the servers start, in the system's temporary folder. The file beside this page never changes. On the recipe box's own page, the sheet reads that one, at its plain address, and can't write: a browser can only fetch a file, so a program writing to a plain address won't compile. A server in front is its address: a place server's, /api/places/..., with no other word.
  • Saving compares new rows with old. Rows are matched by the id column, so an edit and a move at once are both understood. Only the lines that differ are rewritten: quotes, line ends, a byte order mark, blank lines and columns the program doesn't know all stay.
  • With no id column, rows are matched by their whole text: an added or moved row is found, but an edited row reads as one removed and one added. Saving a change to one such row from a program is refused, and says why.
  • Versions: a CSV file has no version column, so a row's version is a hash of what it holds. Editing one row moves only that row's version, so only that row can clash.
  • How close "at the same time" is: every request reads the file first, so a save is seen at the next request. VS Code has its own say: with unsaved edits, it warns you the file changed on disk.
  • A file that doesn't read: half saved, not UTF-8, or with a blank or repeated id. Every way in answers as it last read and refuses to save over it, in words. Two saves at once take turns, under the file's lock, and neither loses a row.
  • The folder: the room's referee keeps its recipes there, in the same files. A recipe added in the folder frame has no place in the room's order yet, so it shows last.
  • Airtable: behind the servers, which hold its key: no page ever sees it. A row added in Airtable has no Spell id, so it goes by Airtable's own id, rec.... A formula column reads and takes no write. Your own base is the epic page's manual test.
  • This device is only in this browser, with no server. It starts empty, and a reload keeps what you add.
  • One process. The servers are one program on one port, so stopping it stops the eight frames that need it.
  • Not a compiled program. Each frame runs the page's <recipe-box>, on the same places a Spell program uses. The lines of Spell above are what a program says to reach that same place. The built-in example @spell/examples/RecipeBox is that program.
