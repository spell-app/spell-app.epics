Data in Spell

One line says where a program's things live. The rest of the program reads and changes them as if they were in memory: it waits, cancels, saves, heals and shares by itself.

Epic page: epic data Why it's built this way: The Data Problem: A Survey Written for: someone writing a Spell program that keeps data, or working on the code under it Status: built, merged into main; real Google Sheets, Airtable and AT Protocol accounts are still manual tests
  • Where is one line: family cookbook is a web server at "...", then it lives in family cookbook on each type kept there.
    • Changing that one line moves the data, and nothing else in the program changes.
  • Reading waits by itself: a drawing that reads shows a loader, then the things; leaving it cancels the request.
    • <for> adds Try again, an empty message, pages and a title.
  • Changing is saving. There's no save step: each change is kept on the device, sent when its action ends, undone by undo, and healed when the server says no.
  • Several people settle: two people on one thing see it wobble, then agree.
    • Per field, the last change wins, with a notice for the one who lost; no CRDT.
  • The server's spelling is its own business: its "hair color" is text finds hair_color.
    • And "1,200" reads as a number.
  • Real servers, untouched. Seven public APIs come in through spell place ingest with no hand edits: PokéAPI for PokéSpell, and six more in the Public Servers example.
  • A copy on this device, when asked. - keep a copy on this device makes a reload before the next check send no request at all: Star Wars' second load sends 0, its first 6.

  • at and from mean the same.
  • A server that can't say what changed is asked again: check it every 5 minutes.
    • Or check it once a day at 5am, which reads again when 5am comes round on the person's clock.
    • at 5am UTC goes by the server's clock instead.
  • A server that searches says so: it searches names with "search".
    • Then every character where its name includes the search asks it, with ?search=sky, not every page.
    • The program still checks what comes back; the ingest finds the parameter by trying one.
  • A key is named, never written: its key is the secret "COOKBOOK_KEY", kept on a server side. A key written into a program won't compile.
  • spell place ingest <address> --into App.api.spell looks at a real server and writes these lines, one server to a file.
    • Its description goes beside them, App.api.json5, which the project file names in development.apis.
    • spell place update App.api.spell looks again.

  • Lists side by side (one list of hours, one per measure) read as one thing per hour.
  • A map keyed by a code ("EUR": { ... }) reads as a list of things, each with its code: its "currencies" is a list of currencies.

  • In a .spellml drawing: <for recipe in the matches empty="No recipes yet." />.
    • the matches is a property of the drawing: every recipe where its title includes the search.
    • No body: each item draws itself. for films names the item film.
    • Its attributes:
      • what it says while it waits: loading
      • when it's empty: empty, hide-empty
      • when it fails: failed
      • its heading: title
      • how it pages: paging="infinite | pages | none"
      • how it draws: as="cards | list | table"
      • any other attribute goes to what as draws
    • Its attributes read from the drawing around the loop; only its body reads the item.
  • In plain Spell, riders under a read say the same:
    • while waiting:, if there are none:
    • if that fails:, if that fails say "..."
  • A long list draws what fits, and more as you scroll, reading the place's next page.
  • The compiler gathers what a page reads, and a place is asked only for those fields.
  • A field that holds an address follows it: its "homeworld" is a planet, then the name of its homeworld.
  • The X of nothing is nothing: the name of its homeworld is nothing when it has no homeworld, where it used to throw, and draw again without end.
  • A filter says what a where would, shorter: every favourite with the same address and name "blah". A place gets it as its query too.
  • A search goes to the server: every artwork matching the search, or a where looking for text in a field the server searches. The program still checks what comes back.
  • the saved todos always means the place's, even beside a property of that name; an add to a list worked out from a place warns that it saves nothing.
  • An app's and a page's variable belong to the project, so any file can say the showing of the pokedex; a place's variable stays its own file's.
  • A change is one field of one thing, kept on the device, sent when the action that made it ends.
  • in one go: sends several together, or none.
  • Undo before it's sent drops it; after, it sends the change back.
  • A refused save merges per field, yours winning, with a notice and Use theirs.
  • A failed save shows a notice with Retry.
  • A form with Save and Cancel buttons works on a draft: a copy that changes as you type, while the real recipe stays as it was.
    • set d to a draft of the recipe makes one.
    • save d sends every changed field as one group, one Undo.
    • discard d forgets it.
    • Today all three go in one action: a draft kept in a property, for the form's buttons to save later (its "draft" is a draft of its recipe), doesn't read yet.
    • A form on the recipe itself is live instead: each field is kept as it's typed, as Recipe Box's is.
    • A shorter way, <form edits={its recipe}>, its submit button saving and its reset button discarding, is Q36, still to decide.
  • remove saved favourites with the same address, or remove favourites from the favourites where ..., takes each match out of its place: one go, one Undo, refused on a read-only place.
  • A loop over a read of saved things goes round a copy, so removing each one as it goes reaches every match.
  • a new card with suit hearts, rank queen sets each field, and a new card with the suit takes the suit in reach. Anything it can't read is an error, never dropped.

    • everyone here is who's in the room now.
  • when someone else changes it: runs for another person's change only.
  • A room's referee gives every change one order: two people settle in about half a second.
  • A field finds the server's spelling by its words: its "hair color" is text.

  • A place that says so keeps what it reads in the browser's database: its rows, its pages, the things its links reach. Without the line nothing is kept, as before.
  • Fresh until the place's next check: a page draws from the copy and sends no request. Stale: it draws from the copy at once, and reads again behind it.
  • A server's longer max-age wins; no-store keeps nothing.
  • 50 MB a place, unless the line says (- keep a copy on this device, up to 20 MB): what was read least recently goes first, and a full database discards the same way, then tries again.
  • A write discards that place's copies; reload the films asks the server whatever's kept. A place with a key keeps each person's copies apart, forgotten when they sign out.
  • Spanish: - guarda una copia en este dispositivo, hasta 20 MB. Star Wars and PokéSpell keep one; the ingest never writes the line.

The long version is The Data Problem: A Survey. The calls a reader would trip on:

  • A server a page can no longer ask is read from where it publishes its data, pinned.
    • It happens when a free version is taken down, and the next one needs a key or refuses requests from a browser page.
    • REST Countries, for one: its free version (v3.1) is gone, and its v5 is both. So its tab reads the same data from the code repository it's published in, at a fixed version, with no key.
    • Choosing fields (?fields=) is lost.
    • Owen picked keeping it over dropping the tab; moving to v5 stays a todo.
  • A copy on the device is opt-in: Owen, "make sure the caching is opt-in!"
    • Without the line a page reads as it always did, memory only.
    • A place that needs a key or a sign-in is kept only because its line says so, like any other.
  • A stale copy is re-read through the browser's own cache, not with an If-None-Match of ours: swapi refuses that header from a page.
  • A search handed to a server is still checked in the browser.
    • A server's own search may match more loosely than the program asked: it may look in more fields than the one the where names.
    • So the program goes over the few rows that came back, and keeps exactly what its where says.
    • The Star Wars server (swapi), for one, looks in more than one field on some of its lists.
  • A field a server names its things by is still a field you can read.
    • Some servers have no number for a thing: they name it by one of its fields, and Spell uses that field as its id.
    • It's still there under its own name too, so the program can show it. It used to be moved into the id, and read empty.
    • GitHub, for one, names a person by their login: its login showed nothing, and so did a Wikipedia page's title.
  • A list kept under each thing shows only what the server answered.
    • Some servers keep a list under each thing, at that thing's own address: a post's comments, under the post.
    • A thing the program adds doesn't join that list until the server answers with it. Nothing in a new one says which thing it's under, so it would have joined every thing's list at once.
    • JSONPlaceholder, for one, keeps each post's comments under it: a new comment would have shown under every post.
    • To see a new one at once, read the whole list with a where: every todo where its user id is 1 takes a todo added here.
  • A server that searches everything about a thing gets words of its own: every artwork matching the search.
    • Some servers search by their own rules: they look at all of each thing (its tags, its maker ...) and answer only the ids that matched, not where the text was found.
    • matching hands the text to that search and takes what it answers, as it is.
    • A where couldn't: where its title includes the search would read every result in full, then drop the ones that matched on a tag.
    • The Metropolitan Museum's collection, for one, searches this way.
  • In the code Spell writes, a property holding one saved thing is read carefully.
    • Such a property can be empty: its thing may not have arrived yet, or been removed. So the title of its page becomes this.page?.title, which is nothing then, not a crash.
    • When the line just before has checked (if its page, its page and ...), the care is dropped: this.page.title.
    • Not inside a drawing's function, though: it runs again later, when the page may be gone.
  • Not yet: manual tests on real accounts: a Google Sheet, Airtable, an AT Protocol account, two people on one recipe, Use a sample, two windows on a live room, PokéSpell's cry playing.
  • Python can't run a place yet: a Python project with a place doesn't compile, and says why.
  • REST Countries is a pinned file checked every 30 seconds: 1.4 MB of countries, cached by the CDN a week.
  • The Met: its search gives its first 100 only, and every artwork reads all 500,000 ids in one 3.4 MB answer.
  • GitHub's issues include its pull requests; a field whose words hold a number ("isbn 10") can't be read.
  • A copy on the device is built and tested per person, but no web place in a browser has a key or a sign-in yet.
  • spell place ingest can't look at a room, a data folder, a file, an Airtable or an atmosphere account, and writes English Spell only.
    • What works now, kind by kind: the table in Saying where.
  • Sorting a table by asking the place; a Google Sheet's own locale; how many a page holds.
  • The Cloud and publishing are the future epic atmosphere.
