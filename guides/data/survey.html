The Data Problem: A Survey

How other systems let people read and change data from many back-ends, share it, and say it in plain words: the research behind what Spell will do.

Epic page: epic data Written for: whoever is choosing how Spell does data, or checking why it did Status: research nothing is built Researched on: 2026-10-31, from each system's own docs where they could be read (see Not verified)

Three findings shape everything else.

  • Nobody infers what a page needs. Relay's compiler gathers what authors wrote out, and fate does the same at run time, where Spell could work it out from the program itself.
  • The best back-end interfaces are small, with written fallbacks. fate requires one method, and rclone publishes a table of what each back-end lacks and what happens instead.
  • Real products already run on "wonky, then heals". Figma says plainly that it doesn't use true CRDTs: one server per document, and the last change to arrive wins for each property.
  • The kickoff describes fate as gathering each part's data needs and sending them to a coordinator at the app level.
  • fate has no compiler: its views are plain objects, composed at run time, and its Vite plugin only keeps the server's API types in sync.
  • The docs read speak of a single request at the root and of batching, and name no "coordinator".
  • So the compiler part isn't something to copy from fate. It would be new.

No quotations here: the pages were read through a tool that summarises them, so everything is in this page's own words. Open the linked source before quoting one.

What an author writes in each, what a layperson would pay, and what's worth keeping.

Every query runs against a partial copy of the database, kept in the browser's memory.

  • The author writes: a publish on the server, a subscribe in the browser, and a Mongo query.
  • Writes: the same method runs in the browser at once as a guess, and the server's real writes replace the guess when they arrive.
  • Worth keeping: a subscription made inside a reactive computation stops when that computation is invalidated: the closest thing found to "the part went away, so its data stopped".
  • Layperson's cost: very little to start, and then the language is Mongo's, with per-client work on the server. A vendor's own benchmark saturated at 1,200 virtual users, or 1,680 with change streams.
  • Why it declined: no official account was found, only opinion. Blaming a language shaped like one database is this survey's reading.

Sources: Collections, Meteor API, its protocol, Galaxy's benchmark, control-mergebox, a forum thread, Sacha Greif's letter.

A data client inspired by Relay and GraphQL, with neither the query language nor the compiler. Its 1.0 is dated 2026-05-14.

fate's views, requests and actions · 9 lines 
export const PostView = view<Post>()({

  content: true,
  id: true,
  comments: defer(CommentConnectionView)   // loads when read
})
const post = useView(PostView, postRef)

  • The author writes: every field each part reads, in a view.
  • Masking: a part can only read what it selected: a TypeScript error at compile time, and undefined at run time.
  • Cancelling: an abort signal. When a request is shared, cancelling one reader doesn't cancel the others.
  • Keeping: the last 10 released requests stay, so going back is fast.
  • Back-ends: an interface with one required method (fetch by id), and optional ones for lists, queries, mutations and subscriptions. The most directly useful thing in this survey.
  • Lists: automatic insertion was removed as the default, so where a new item goes must be said out loud.
  • Offline: saved mutations are sent in order, but temporary ids aren't rewritten in later ones.
  • Layperson's cost: medium, and all of it is the views. Spell's chance is to make them disappear.

Sources: Why fate, the 1.0 post, Views, Core concepts, Requests, Actions, List views, Live views, Persistence, Transport, GraphQL, Server.

  • Relay's author writes: a GraphQL fragment per component. A compiler joins them into one query for the whole subtree, ahead of time.
  • Apollo's cache: an object's id is its type plus its id. Nested objects are flattened into one lookup table, so one edit shows everywhere.
  • Worth keeping: the cache by type and id, and joining what parts need. Not the query language.
  • Layperson's cost: high. Both need GraphQL, and Relay its compiler and conventions.

Sources: Fragments, Thinking in Relay, Compiler, Apollo caching.

  • The author writes: a key that names the data, and a function that fetches it.
  • Defaults: stale at once, refetched on mount, focus and reconnect, kept 5 minutes when unused, 3 retries.
  • Cancelling: not by default. A query whose part goes away keeps going unless the fetch uses the signal it's given.
  • Writes: either draw what's pending, or do four steps by hand through the cache: cancel, snapshot, set, restore on error. fate's whole pitch is removing those steps.
  • Layperson's cost: low until invalidation, which is where everyone gets stuck.

Sources: Keys, Defaults, Cancellation, Optimistic updates, SWR, SWR mutation, SWR's abort proposal.

Each keeps data near the browser and keeps it current, mostly tied to one database.

  • TanStack DB: typed collections with fast live queries, about 0.7 ms to update one row in a sorted 100,000-row collection on an M1 Pro. Its sync mode changes with size, under about 10,000 rows or over about 50,000: the size of the data changes the strategy.
  • Zero: a query runs locally at once, then on the server, each result saying if it's unknown, complete or cached. Show "not found" only when complete, or it flickers.
  • Convex: query functions on the server, dependencies tracked by themselves, every subscription on the same snapshot.
  • Firestore: listeners fire on local writes before they're sent, with a flag saying they're pending. Last write wins.
  • Supabase: subscribes to table changes; past about 3,000 subscribers it recommends something else.
  • ElectricSQL: reads only, with four patterns for writes of rising power: online, optimistic per component, shared optimistic, through a local database. A useful ladder.
  • PowerSync: SQLite in the browser. Writes queue, and go through a function you write to your own API, which keeps validation and permissions yours.
  • Layperson's cost: low to read, high to run, and swapping back-ends is mostly impossible by design.

Sources: TanStack DB, its sources, Zero queries, Zero mutators, a 2025 review, InfoQ, Convex realtime, Convex optimistic, Firestore listeners, Firestore offline, Supabase, Electric writes, Electric shapes, PowerSync, its writes, its protocol.

  • Prisma, Rails, Django: one lazy query that reads nearly like English, with an adapter per database. Ten books and their authors is 11 queries, unless told to gather them.
  • WarpDrive: a chain of request handlers and a replaceable cache: flexible, with many concepts.
  • Hasura: live queries by polling, once a second by default. It chose polling on purpose, since working out which event affects which complex query is intractable.
  • PostGraphile: GraphQL from a Postgres schema, permissions left to the database.
  • OData: a uniform query language, with what each service can do declared in its metadata, per property if need be. A service refuses what it can't do.
  • Datomic: the database is a value, so a query at a point in time always gives the same answer.
  • Layperson's cost: ORMs are the lowest in this survey, because the code is the question. The rest are high.

Sources: Prisma drivers, Prisma features, Rails, Django queries, Django options, WarpDrive, RequestManager, JSONAPICache, Hasura live queries, its architecture, its benchmark, PostGraphile, OData URLs, its capabilities, its protocol, Datomic, its queries.

  • rclone is the best model found for what a back-end may lack. Few required methods, optional ones in small separate interfaces, and a published table: no copy means it's downloaded then uploaded again; no move means copy then delete; no clean-up means an error.
  • Plan 9's 9P: every service is a file tree, in about twelve messages. Cancelling is a request of its own, and the client must wait for its reply even if the first answer got there first.
  • FUSE: an interrupt doesn't by itself cancel the operation, and a reply is still expected.
  • Layperson's cost: low, since people know what a file is, but a folder can't answer a question.

Sources: rclone's interfaces, its table, fuse(4), intro(5).

  • React Router: a load function per route, run in parallel. A newer navigation cancels older ones, and the server keeps working on what was cancelled.
  • SvelteKit: load functions track what they used, down to a single search parameter.
  • Server Components: an await in the component, and the browser gets only the output. The simplest to write here, for server data alone.
  • Solid Router: a named query shares its request, and an action revalidates the page's queries.
  • Solid 2: async is part of the graph: a memo may return a promise, with an optimistic overlay discarded when the change settles.
  • Layperson's cost: low, with data tied to routes and code, which is hard to swap.

Sources: React Router loading, its race conditions, its fetchers, SvelteKit, Server Components, Solid queries, Solid actions, Solid 2 beta notes, its design discussion.

The sources couldn't say whether a replaced async memo gets an abort signal, so this was tried against the version in the repo, Solid 2.0 rc.17, with a small script.

  • No signal is handed in: the memo's function receives only one argument.
  • A replaced answer is dropped: the slow first fetch answered after the second, and was never shown.
  • Aborting works by hand: an onCleanup() inside the memo ran when its input changed, and when the memo was disposed, aborting the request in flight.
  • The same in createDeferred(), the form epic language will use. Not tried: how it behaves across thousands of them.

Each person's records live in their own account, on a host they can change, so one app's data is spread across many accounts. Epic data's seven back-ends include it.

  • What's stored: records in named collections, each with a key, addressed like at://did:plc:abc/com.example.recipe/3k5nob. A permanent account id is the stable form, since a handle can change.
  • Reading: anyone can list an account's collection with no sign-in, 100 at a time, in key order or its reverse. There's no filter or sort there; search and anything across accounts come from separate services.
  • Writing: only the owner can write, to their own account.
    • The caller can choose the key, so ids made in the browser fit.
    • A write can carry the version it expects, and fails if the record has moved on.
  • Live: a public websocket stream of plain JSON, filtered to as many as 100 collections and 10,000 accounts. Delivery can repeat, so handling must tolerate that.
  • Signing in: a browser-only app can sign a person in to their own account, with no server of its own. Such a session lasts at most two weeks.
  • Private data: all of it is public today. Spaces, the extension for non-public data, is an alpha whose design isn't final, and it gives access control without encryption.
  • Schemas: a lexicon's changes must stay compatible: new fields optional, and no renames. By default a host accepts records of a lexicon it doesn't know.

Sources: repositories, AT URIs, lexicons, sign-in, overview, Spaces, Jetstream, listRecords, putRecord.

A hosted spreadsheet-like database that many people already keep their data in. Epic data's seven back-ends include it.

  • Reading: a formula filter, a sort, chosen fields, and pages of at most 100. Paging can time out and have to start again.
  • Writing: a change can touch only the fields it names.
    • Airtable's support pages give 10 records a request.
    • No version check was found, so two people's changes can overwrite each other with no warning.
  • Ids: Airtable makes them (rec560UJdUtocSouk). An upsert can match on up to three of your own fields instead, which leaves room for ids made in the browser.
  • Limits: 5 requests a second per base and 50 per person. Going over means failures for 30 seconds, and Airtable suggests a caching proxy for heavy reading.
  • Live: webhooks must be handled by a server, say only that something changed, and expire after 7 days unless renewed. A browser polls.
  • Links: a linked-record field holds record ids, and can point back from the other table. Lookups, rollups and formulas are read only.
  • Keys: its data API answers browsers (checked by asking it, 2026-10-31), so a key in a page would work, and anyone could read it. Its sign-in can't finish from a browser yet, its docs say.

Sources: listing records, updating, rate limits, webhooks, fields, keys, sign-in, call limits.

Other mechanisms looked at, beyond REST, GraphQL, chunked files and the file system. Epic data's seven back-ends take Sheet or CSV from this list, along with AT Protocol and Airtable above.

  • Google Sheets: 60 reads and 60 writes per person per minute. It has a SQL-like query, with columns addressed by letter.
  • Airtable: a formula filter, sort, and pages of at most 100.
  • RSS: read only, with a real id per item and a stated time to cache: a cheap sixth.
  • SQLite in the browser: proves "local feels like server", but its storage needs a worker and, on the basic setup, particular page headers. Browsers can clear it.
  • MCP: the closest shape (URIs, list, read, flagged subscribe), though aimed at model hosts; its reach from a browser wasn't checked. An update says only which resource changed.
  • WebSockets: a way to deliver changes, not a back-end: no reads, no keys, no back-pressure.
  • DuckDB over HTTP: prior art for chunked files, fetching only the parts of a file it needs by range requests.
  • The browser's file system: file handles that can be kept, with a change observer. It needs permission and HTTPS.

Sources: Sheets limits, its query language, Airtable, RSS, SQLite, MCP resources, MCP cancelling, WebSockets, DuckDB httpfs, DuckDB-Wasm, File System API.

  • One server process per document, whose order replaces any timestamps.
  • Unrelated properties never conflict, and the final value is always one somebody really sent.
  • Text isn't merged: one person's AB against another's BC ends as one or the other.
  • Ids are made in the browser, so creating things works offline.
  • A deleted thing lives on in the undo history of whoever deleted it.
  • A list position is a fraction between its neighbours, and parent and position change together.
  • Reconnecting is one routine: download a fresh copy, then reapply offline edits.
  • Its reliability work: a checkpoint every 30-60 seconds, a journal, aiming to lose under a second.

Sources: How it works, Ordered sequences, Making it more reliable.

  • A change is a named function with its arguments. It runs locally as a guess, then for real on the server.
  • The browser rewinds to the server's state and replays what's still pending, so a replay may turn out differently.
  • Every change has an id, so retrying is safe. One that can never work must still be marked done, or it blocks the rest.
  • Convex commits only if everything it read is still current, and re-runs itself if not.
  • Rocicorp's example against plain last-wins: two people adding to a counter lose one of the additions.
  • Zero's warning: a retry can only undo what's in the database. A sent email stays sent.

Sources: How Replicache works, its push rules, its strategies, Replicache, Zero: when to use it, Rocicorp on Reflect, Meteor methods, Convex concurrency.

  • Speed is no longer the issue: one benchmark of 260,000 edits ran Yjs in 0.97 s and 3.3 MB, against a plain string's 0.61 s and 0.1 MB. Automerge has since fixed its old numbers.
  • Even a full CRDT is last-writer-wins on a plain field: Automerge picks a fixed winner, and keeps the losers readable.
  • The real costs, as this survey reads them: metadata kept forever, a harder story for changing a data's shape, no place for rules ("only one person may take the seat"), and no way for a server to say no.
  • Ink & Switch report that people rarely hit conflicts, because tracking is fine-grained and people avoid each other by instinct. So seeing who's there is the cheapest conflict tool of all.

Sources: Yjs internals, its updates, its presence, y-monaco, Seph Gentle's benchmark, Automerge 3, its conflicts, Local-first software.

  • Linear, by secondary sources only: per-attribute changes, a server-given number deciding, a CRDT added later for issue descriptions alone.
  • Liveblocks: last writer means last to reach the server, so a faster connection can decide. Its trap: an edit to an object someone replaced shows on your screen and may reach nobody.
  • Durable Objects, PartyKit: one single-threaded instance per name, already the shape of one referee per shared space.
  • Text: ProseMirror rejects a change made on an old version, and the client rebases it. Fraser's differential sync diffs against a shadow copy and starts over on a bad checksum, but can merge into nonsense.
  • HTTP already names this: If-Match exists to prevent lost updates. An idempotency key makes a retry safe, though its standard is still a draft.

These are judgements built on the sources, not claims from them.

  1. The compiler infers each part's selection, so nobody writes one, and masking comes free.
  2. Cache objects by type and id, not requests, so one edit shows everywhere with no invalidation.
  3. A required core, optional features, written fallbacks (fate, rclone, MCP, OData).
  4. The back-end says what it did, and the engine does the rest, visibly.
  5. Results say what they know. Never draw "none found" until the answer is complete.
  6. One action, run on both sides, as a local overlay and a back-end call.
  7. Lifetime follows the part, with counted sharing: the last reader leaving aborts. Keep about 10 released requests.
  8. Polling is the live fallback everywhere.
  1. A silent fallback that downloads everything. Uniform words must come with visible cost: a ceiling, a compile note, then an error.
  2. A language shaped like one database, with per-client state on the server. A warning, not a proven cause of Meteor's decline.
  3. Identity isn't free. Sheets, CSV and files have no reliable key, and inserting a row shifts every row number.
  4. Cancelling isn't undoing. Abort reads, since a write already sent is only ever reconciled.
  5. Optimistic writes past one click. Start low on Electric's ladder, with offline as a later rung.
