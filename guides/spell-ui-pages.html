Spell UI Pages

66 pages and 1608 live examples, each showing its own source, and not one widget on them that isn't the library's own. Every Fomantic example a widget couldn't draw became an issue: 100 are still open.

That's Spell UI's docs site: plain HTML pages in Fomantic's docs style, made only of <ui-*> widgets, so every page doubles as a test of the library. Here's how it's built and kept.

  • Spell UI's README-site.md: the site's own how-to. This page adds the anatomy, the reasons and the limits.

Two widget features the frame leans on, added for these pages (P10, P11) but usable anywhere, not only on the site.

Stacking: stack-with

  • Fomantic's responsive words (stackable, doubling, per-device widths, reversed) measure the SCREEN.
    • Ours measure the element's own width by default.
    • That's right for a component in a 300px sidebar, and wrong in the ~755px docs column, where examples stacked on a desktop.
  • stack-with picks which:
    • on the element: stack-with="container" (default) or "page", e.g. <ui-grid stackable columns="3" stack-with="page">
    • for a subtree: the inherited token --ui-stack-with: page | container, which <ui-root stack-with="page"> sets
  • On <ui-grid> (its rows and columns follow), <ui-cards>, <ui-steps>, <ui-form> (its <ui-fields> follow), <ui-items>, <ui-statistics>. The attribute beats the token; neither: container.
  • <ui-table> keeps its own stack-by (viewport by default); without one it follows the token.
  • None on menus, button groups, horizontal segments: they already stack by the screen (J13).
  • The site: every page's root says stack-with="page", so examples lay out as on fomantic-ui.com.
    • So keep Fomantic's markup: no unstackable to stop a desktop stack, and no stack-with on an example unless it is ABOUT stack-with.
  • The design: theming.md "Stacking".

The tab bar: appearance, alignment, equal

  • appearance on <ui-menu> and <ui-tabs>: the look, one word.
    • tabular, pointing, secondary, text (Fomantic's), and segmented (ours): a bordered group of joined items, the selected one filled with color, else the primary colour.
    • The old booleans (tabular, pointing ...) stay as aliases and combine.
  • alignment="fluid | left | center | right" on the same two: where the items sit along a horizontal bar, packed at one end or filling it (fluid).
    • A segmented menu moves as a whole; ignored when vertical.
  • equal on menus, tabs, <ui-buttons>, <ui-statistics>, <ui-steps>, <ui-fields>: every child the same width, worked out from the children, no count.
    • packed: each as wide as the widest, the group hugging them
    • fluid: an equal share of the bar; statistics and fields always share their row
    • the old counts (items="3", width, widths) stay as aliases
  • The site's top tabs: appearance="segmented" alignment="fluid" equal, four equal tabs across the column; the icons page's pack switcher is <ui-buttons equal>.
  • The grammar: grammar.md "Menus".

Six <ui-docs-*> families in docs-components/ do what no component should: show an example's source, draw API and token tables, list the site, pick a theme, build a table of contents.

Each is written EXACTLY like a component family (controller, vocabulary, fallback, css, tests, examples), but is NOT a component.

element does key attributes data from
<ui-docs-example> a live example plus its source in <ui-code>, behind a code button (Fomantic's .example) header, description, level (4), code (open), language (html), bare, variation its own children (below)
<ui-docs-api> a tag's or family's API tables; scrolls to #ui-or once drawn tag, family, level; emits ui-render {tags} components.json5
<ui-docs-tokens> a family's public --ui-<tag>-* tokens with live swatches; or, with global, ~390 foundation tokens in groups; an optional playground column family / tag, global, groups, tokens (a pick, globs allowed), playground, target="page", caption, level components.json5
<ui-docs-nav> the left nav: one inverted vertical <ui-menu>, A-Z or Topics, search (/ focuses it), favourites current, base, view, size; host API focusSearch(), revealCurrent() components.json5 + per-viewer localStorage
<ui-docs-themes> a palette button opening the theme list (Spell, Spell Brand, Plain, Classic, then Fomantic's themes) and "Match system", and a sun / moon button that flips the scheme for (a tag: only its themes), show (both | theme | scheme), size, inverted components.json5 themes + ThemePreference
<ui-docs-toc> "On this page": level-2 headings as sections, examples and level-3 headings as entries, following the scroll for (an element; a <ui-tabs> means its shown pane), header, size, expanded the page itself

Families load lazily, so by the time <ui-docs-example> runs its children may already have rewritten themselves. ExampleSource.of() takes the first of:

  1. a <template> child: shown exactly, stamped out live
  2. the snapshot snapshot.ts takes of every example as the bundle's FIRST module, before any family loads
  3. the live innerHTML, minus runtime attributes

Then description-slot children are dropped and HtmlFormatter re-indents it.
  • The docs elements read components.json5 through SiteData (SiteData.ts), NEVER the vocabularies. Shape: SiteDataFile in docs-components.types.ts.
  • yarn site:data writes it from the vocabularies and the generated sheets:
    • topics; every tag (names, folder, main tag, href, topics, aka, attributes with values, slots, events, parts, states, texts)
    • families (title, summary, status, tags, tokens with a guessed type)
    • foundation: token groups (typography, sizes, spacing, palette ...) from the generated sheets' :root blocks
    • themes: { name, title, families, global }, worked out from each theme sheet's selectors and tokens (ThemeFamilies.ts)
  • ~573 KB raw, 80 KB gzipped, fetched once per page. 2-space JSON, skipped by oxfmt.
  • SiteDataBuilder.test.ts fails while it's stale.
  • yarn gen:root scans src/docs-components/ as well as src/components/, so their tags are in <ui-root>'s catalog.
  • RootLoader.ts has a SECOND literal import.meta.glob("../../docs-components/*/index.ts"), tried after the components'.
  • ComponentDefinitions.docs lists them; ComponentDefinitions.all, the component list, byTag() and the library build's entries leave them out. Every one is filed under the documentation topic.
  • ui's package.json sideEffects lists each docs barrel: without it the bundler silently drops define() (chunk loads, tag stays undefined, no error).
  1. Copy a family: make src/docs-components/ui-docs-<name>/ from ui-docs-example/: same files, a vocabulary with topics (documentation) and aka.
  2. Register it: add its barrel to package.json sideEffects, then yarn gen:root and yarn site:data.
  3. Its inner widgets: add the ui-* tags its JSX renders to DocsJSXTags, and import their families in its barrel: a root only loads what's in the light DOM.
  4. Build: yarn site:build, and commit _data/ (the bundle isn't committed).

The rules from PAGES.md that matter most:

  • Sources: Fomantic's page in reference/Fomantic-UI-Docs/server/documents/<group>/<name>.html.eco; EVERY section and example, in Fomantic's order, with its text. Our names: the tag's UI<Name>.en.ts, the ONLY attributes that exist. The old MDX: git show df8ca0bf:packages/ui/site/src/content/components/ui-<name>.mdx.
  • Section ids: lowercase-kebab, unique, NEVER examples / usage / api / theming (those are tab hashes).
  • Markup: clean <ui-*>, 2-space indent, no style=, no <div class>; a wrapper only if the example needs one, and then a <ui-*>.
  • NO comments inside an example: they show in its code. Gap notes go BEFORE it: <!-- GAP I23: one line. -->.
  • Icon names in canonical word order (arrow right): Fomantic's right arrow draws nothing and warns nothing.
  • Stacking: keep Fomantic's stackable / doubling as they are. The root's stack-with="page" already stacks them by the screen; no unstackable to stop a desktop stack, no stack-with unless the example is about it (section 3).
  • Menus and tabs: Fomantic's tabular / pointing / secondary / text words work as they are; our own look, alignment and equal widths are appearance, alignment and equal.
  • Text holding <tags>: wrap <ui-markdown> content in <script type="text/markdown"> and <ui-code> content in <script type="text/plain">, or the tags parse as real elements.
  • A Fomantic feature we deliberately lack: <ui-message size="small" class="site-not-ported">Not ported: ...</ui-message> in its place.
  • A new gap: search the epic page first, else epic add spell-ui-pages#I "Gap: ..." from the worktree root. Fix it in the widget only if under ~15 min and local, with a test.

yarn site:build, after changing a vocabulary, a family sheet, an example, or any source the site shows. It runs, in order:

step writes from
site:data components.json5, icons.json5; seeds pages.json5 for a new family vocabularies and sheets, imported in node
site:index components' index.html's cards the site data
site:kitchen kitchen-sink.html's examples every family's types.html
site:bundle _assets/ (clean), sizes printed site.ts through vite.site.config.ts
  • The bundle is an app build, base: "./", minified, no sourcemaps. Stable names for site.js, <family>.js and emoji chunks; other shared chunks are hashed.
  • Today: 183 files, 3.6 MB without the icon packs; site.js 51 KB, site.css 125 KB.
  • yarn site:dev: a fresh site:bundle, the page server (started if needed), the /components/ui/ URL printed, then a Vite WATCH build. Every src/ or site/_src/ edit rebuilds _assets/, and live reload reloads open pages.
  • Not watched: site:data, site:index, site:kitchen.
  • Ctrl-C stops the watch, not the page server.
  • A watch rebuild leaves old hashed chunks behind: yarn site:build clears them.
  • yarn site:check <page...> or --all (site-check.ts, on SiteCheck.ts): loads pages from the page server in Playwright, at desktop, phone and dark.
  • Fails on console errors, 404s, undefined or unrendered ui-*, a missing tab, an empty "On this page" on Examples, phone-width overflow, a nav flyout that won't open.
  • Screenshots in site-check/: LOOK at them; the checks can't see a wrong icon or an overlap.
  • epic pages update in packages/docs skips the site pages: they load site.js, not spell-ui.js.
  • Commit _data/ with every change to ui/src/ that the site shows.
  • Never commit _assets/: git-ignored since 2026-10-07, because its hashed chunk names churned every diff. The page server builds it when it starts, if it's stale.
  • oxfmt skips the shared ui/ folder (the pages), _assets/ and _data/ (vite.lint.ts): it once reflowed markdown inside pages. So the kitchen sink's unwrapped lines are canonical.
  • Tests that fail while generated files are stale: SiteDataBuilder.test.ts (site data), UIRoot.catalog.test.ts (gen:root); site:index --check, site:kitchen --check.
  • A change that alters rendering also needs yarn test:visual and its baselines, as any ui change.

import { UI } from "@spell-app/ui/core" // `spell-ui/core` in the package

const { themes } = await UI.load() // the runtime:  `UI.themes` exists once it has loaded
themes.names // ["fomantic-classic", "github", "material" ...]:  the Fomantic themes, A-Z
await themes.apply("github") // classic + github, on the page and in every shadow root
await themes.apply("classic") // classic alone
await themes.apply(undefined) // our own look
  • Fomantic's themes are DELTAS on its default look, which is our classic.css. So a theme applies on top of classic; both in @layer ui.theme.
  • dark is a colour scheme, not a theme: not in names, and apply("dark") throws. Pickers offer Spell, Spell Brand, Plain, Classic, then names, plus a sun / moon button for the scheme, with "Match system" in the overlay.
  • Themes globs the themes folder, so a new sheet is a theme with no registry edit, and each is its own lazy chunk.
  • On the site, ThemePreference remembers the viewer's choice (spell-ui-site:theme; spell-site:scheme, the one scheme every site shares) and site.ts restores it on every page.
  • A theme sheet has two halves: TOKENS on :root (inherit into shadow roots by themselves) and OVERRIDES in class grammar (.ui.menu .item), which target the markup INSIDE each component's shadow root.
  • A page sheet can't reach in there, so apply() registers two UI.styles slots, classic and theme, both { page: true, shadow: true }: adopted on the page AND into every shadow root, present and future.
  • Order inside a root: foundation, component, utilities, shadow sheets, app sheet.
  • register(name, "") unregisters.
  • Without the runtime (a plain <link>), only the token half reaches components.
  • Rule: bundle EXACTLY what Fomantic's theme @imported, nothing more.
  • Bundled as woff2 + the font's OFL.txt in themes/<name>/, declared by @font-face outside the layer, URLs relative: bookish (Karma), instagram (Montserrat), material (Roboto), chubby (Source Sans 3, under Fomantic's name Source Sans Pro).
  • Named but not loaded, as in Fomantic: flat (Open Sans), fomantic-classic (Open Sans headers), rtl (Noto Kufi Arabic), and classic itself (Lato).
  • Why bundle: a constructed sheet ignores @import, and a Google Fonts link would be a third-party request.
  • The recipe: theming.md, "Porting a Fomantic theme". Models: github.css (big), material.css (fonts, palette), fomantic-classic.css (small).
  • In short: tokens first on :root, overrides second as class grammar scoped to what Fomantic meant, re-check each changed hue's --ui-<hue>-on for 4.5:1 contrast, list what can't port in the sheet's header ("NOT ported"), and append a describe to themes.test.ts with one computed style per touched component.
  • Then yarn site:data: the theme shows up in every picker for the families it touches.
