Background agents: /bg

/bg "docstrings" 2 add a docstring to every export in util/string.ts, and the panel is free again in seconds: a helper named skillz-docstrings does it, and its report comes back when it's done (52s, the first time). Like & in a shell, but each job has a name, shows on the epic page, and takes a note from Owen mid-task. Written for whoever uses /bg, or changes it.

Epic page: Skillz: /bg Written for: Owen, Claude sessions starting agents, and whoever changes /bg, epic agents or the epic page's Agents panel Status: built, tried live The rules: the /bg skill, and the root CLAUDE.md, "Delegated work" Checked on: branch skillz, 2026-10-07: every hand test run from the VS Code panel (epic page, P5)
  • /bg ["name"] [n] <task> hands the task to ONE background helper.
    • The session says one line and ends its turn, so the panel is free again in seconds.
    • The helper's report comes back when it's done.
  • Every agent Claude starts, by /bg or on its own, is NAMED and LISTED while it runs.
    • Its name starts with the epic's name, else the worktree's, else main: skillz-aaa.
    • The list is kept by epic agents.
  • /bg ? shows the list; /bg stop <name> stops one.
  • Each epic page shows its epic's running agents.
    • A note typed under one reaches it mid-task (in about 7s), and changes its course.
  • /epic phase adds a phase to the epic under way, from its items or from scratch. /epic start works a phase, or a block of items, now.
  • spell dev server ensure restarts a page server that is older than its code, so new routes show up after a merge.
  • The budget n is a rule the helper is told, not something Claude Code enforces (Limits).
  • /bg "docstrings" 2 add a docstring to every export in util/string.ts, then keep working.
the three forms · 3 lines 
/bg ["name"] [n] <task>     start one:  /bg "docstrings" 2 add a docstring to every export in util/string.ts
/bg ?                       what's running:  name, status, age, task
/bg stop <name>             stop one
  • "name": a quoted FIRST word.
    • None: Claude makes one up from the task, 1-3 words, kebab-case (string-docstrings).
  • n: a whole number 1-5 next, the most agents the task may use IN ALL, the helper included.
    • Default 1: the helper alone.
    • /bg 3 means the helper plus up to 2 of its own.
  • The rest is the task, word for word.
    • No task: Claude asks for one, and starts nothing.
  • The real name is a prefix plus the name: the epic's name, else the worktree's, else main.
    • /bg "aaa" in epic skillz is skillz-aaa.
    • On main, it's main-aaa.
  • An agent's own helpers add to its name: skillz-aaa-tests.
  • Claude Code's Agent call has no name field.
    • So the name goes first in its description (skillz-aaa: docstrings in string.ts), which is what Claude Code shows, and in the list.
  • A name already running is refused, and Claude takes aaa-2.
  • The reply that relays a report opens with a bold line of its own: Agent skillz-aaa came back with:

The helper's prompt, a template in the skill, carries:

  • the task, word for word, and a Context line: what the conversation said that the task leans on
  • the checkout (and worktree, branch), the epic and epic page, and its budget
  • the house rules:
    • WWOD
    • stage, never commit unless told
    • shared content edited at its real path, never git-added
    • plain, separate shell commands in a worktree
  • no questions to Owen (no AskUserQuestion):
    • a choice Owen might make differently is taken, then recorded as a judgement call in the epic page (else in the report)
    • it stops only on a risky one: deleting or overwriting work, publishing, changing what the task means
  • its LAST message is its report: what changed, where to look, checks with numbers, questions last
  • A fork (subagent_type: "fork") is a copy of the session that sees the whole conversation, so "fix the thing we just talked about" works as is.
  • The catch: the VS Code panel's sessions have no fork agent type.
    • The call fails with Agent type 'fork' not found, and the skill makes the same call with general-purpose.
  • That helper sees NOTHING of the conversation.
    • So the session fills in the prompt's Context line: which thing, which files.
  • Either way, a helper's own helpers are ordinary agents (general-purpose, Explore ...), never forks.
  • n counts the helper too. With n = 1 the helper starts no helpers of its own.
  • Unlike the root rule (up to 5 agents, unasked), n is meant as a hard cap.
  • Each helper's helper is named <its name>-<x>, listed when it starts, and taken off the list when it's back.
  • Tried with /bg 3 on a task that fanned out: 2 Explore helpers, named, listed, unlisted, 3 agents in all.
  • Helpers work in the session's own checkout, so two of them on one file would collide.
    • The second is listed blocked on <first> and doesn't start yet.
  • When the first one's report arrives, the session sets the second active and starts it, in the same turn.
  • Epic-page work always overlaps other epic-page work: one at a time.
  • Its notice wakes the session, which:
    • runs epic agents done <name>
    • replies with the bold first line and a short report, with links as the root rules say
    • puts a question only Owen can answer in a modal
  • /bg ? shows the list (epic agents list --json) as a short table.
    • The list is the record, not the session's memory, so it survives a compacted session.
    • It also shows agents that other sessions in the same epic started.
  • /bg stop <name> stops the agent's task (TaskStop), then marks it done.
    • Its staged changes stay.
    • It won't stop another session's agent.
  • Where it is kept (git-ignored, gone when empty):
    • in an epic: agents.json, beside the epic page (ignored by the shared repo's .gitignore)
    • no epic: .spell-agents.json, at the checkout's root (ignored by spell-app's .gitignore)
  • Only the command (and the page server's redirect route) writes it, never Claude by hand.
    • Several helpers write at once, so every write is locked and atomic.

  • The code: AgentList (the class) and agents.ts (the command line).
  • epic agents passes through to it, as spell dev plan-doc once did.
  • The standing rule is in the root CLAUDE.md, "Delegated work":
    • every agent Claude starts is named and listed: add before it starts, done when it's back
    • epic-page work goes to a background agent, as if Owen had typed /bg "plan-doc" ...

An epic page shows its epic's running agents in an "Agents running" panel above section 1, whenever the list isn't empty.

  • Owen steers an agent there, from the side bar, without typing into a busy session.
  • One row per agent: its name, its status (active blue, blocked on ... orange), its age, its task, and the notes sent to it ("You · 12:52 PM · waiting for the session", then "told").
  • Under the rows: a note box that grows as you type, and Send (Cmd/Ctrl+Enter too).
  • The waiter's other exits:
    • 3: nothing runs any more (don't restart it)
    • 2: an hour passed (restart it while agents run)
  • An agent another session started keeps its notes untold, for that session's waiter.
  • The routes: agentRoutes.ts, listed in the root package.json (pageServer.routes).
  • The page polls GET /api/agents?page= for the list.
  • The panel itself is drawn by <epic-page> since epic epic-components: AgentsPanel.
    • It talks to the server through AgentsClient, which shares its server link with the review client.
  • Tried live: two notes reached a running helper in about 7s each; the second changed its course.

Two /epic forms that act on the session's OWN epic, the epic page of its worktree.

  • With no epic, they say so and stop.
  • Rules: the /epic skill, "10. Add a phase" and "11. Start".
the forms · 8 lines 
/epic phase                      a new phase with no antecedents:  the text on the lines after says what
/epic phase J1 J5, t3            from those items (spaces or commas, any case)
/epic phase add-phases           named "Add Phases"
/epic phase t3 Retry Logic       both:  from T3, named "Retry Logic"
/epic start P3                   phase 3, now
/epic start J3 J4 T6             those three items, worked as one block
  <text on the lines after>      Owen's input, word for word
  • /epic phase: a background <epic>-plan-doc agent drafts the phase.
    • It writes symptom, changes, goal (each antecedent linked), files, verify and estimate.
    • While Doc Review is still to do, it inserts the phase before Doc Review.
    • It queues each antecedent into the phase.
  • /epic start with items: each is closed when done, and the block goes in ONE commit.
    • The commit is titled <epic> J3 + J4 + T6: ..., so commits --backfill files it under each item.
    • A phase out of order: said in one line, then started anyway.
  • phase and start are reserved epic ids. The prompt hook lets them through without renaming or blocking.
  • epic add-phase ... --before N inserts the phase as PN.
    • The to-do phases from N on move down one, with their ids, part files, links and data-phase.
    • It's refused once any of them has started.
    • Prose without a link is left as written.
    • The log says what moved: P6 · Doc Review moved down to P7.
  • A page server loads its route modules only when it starts.
    • The main checkout's server had run since before the panel's route merged, so the epic page showed no panel.
  • Now spell dev server ensure, which every opener calls, restarts a server that started before its code last changed.
  • Its code means the server package's source and each route module's folder.
  • PageServer.ensure() hands those folders to PidFile.ensure(), which compares the server's start with their newest file time (newestChange()).
  • So after a merge (or a pull), the next page opened comes from a fresh server, and a second opener keeps it.
  • The session starts the helper, not the skill itself (Q1).
    • The alternative was to fork the whole skill (frontmatter context: fork).
    • That frees the panel instantly, but then every /bg forks, ? and stop included, and nothing checks for two tasks on the same files.
    • The few seconds the session takes buy the same-files check.
  • Same checkout, not a worktree per helper (Q2).
    • Most tasks are small and belong to the work under way.
    • A worktree would mean a merge per task, and a helper couldn't see uncommitted changes.
  • /bg ? and /bg stop, beside Claude Code's /tasks (Q3): to find and stop a helper by its name, in chat. Owen named the list form ?.
  • Decide, record, stop only if stuck (Q4): the same rule as /bedtime, so Owen reviews both the same way.
    • Always stopping would bring most tasks back half done.
  • A list outside an epic, at the checkout root (Q5): .spell-agents.json, so /bg ? and the same-files check work on main too.
  • A command writes the list, never Claude by hand (Q6): several helpers write at once, and one place knows the path, the prefix and the format.
  • Every agent named and listed, not just /bg's (Q8, Owen's plan comments): so Claude, and Owen, can always tell what is in flight.
  • Epic-page work in a background agent (Q9): filling or updating an epic page is slow, and the session should stay free to talk.
  • A panel on the epic page to steer agents (Q10): Owen sees and redirects an epic's helpers from the side bar.
  • /epic phase and /epic start (Q11): Owen asked for them once /bg landed, to add phases and work blocks of items without spelling it out each time.
  • epic agents for the list; the WWOD check became spell wwod check (Q12): each name says what its command does. Two nouns one letter apart was the alternative.
  • The server restarts when it is older than its code (Q13, option C).
    • A restart on merge would miss a pull or a hand merge.
    • A server can't reload its own routes: Node caches modules, and routes can't be removed.
  • The list's code lives in the docs package's tools, not the CLI package (J1).
    • The page route needs the same class, and neither import direction is allowed:
      • nothing may import the docs package
      • the docs package may import $/cli only through its barrel
    • The cost: starting a child node, about 0.3s.
  • pages.js shares one parseArgs() (J2), rather than a 4th copy.
    • It carries JSDoc type tags against WWOD §6, because TypeScript reads a JS file's types only from them.
  • Listed before it starts (J3): a clashing name is caught before any agent exists, and an interrupted session still shows it.
    • The cost is one more command, set --task-id.
  • The rule in CLAUDE.md, its steps in the skill (J4).
    • It's Claude-only: Codex has neither Agent nor TaskStop.
    • And a rule lives in one place.
  • The panel's look (J5, J6): a plain panel whose rows update in place, so a note box keeps its text and focus through polls.
    • Send is the row's one primary action.
  • --before renumbers links, not prose (J7): plain text may mean the phase as it was numbered then. Link phases when naming them, and they stay right.
  • The budget is a rule, not a fence.
    • Nothing in Claude Code counts a helper's agents.
    • The cap holds because the prompt says so, and each agent must be listed.
    • A helper that ignored it could start more, and /bg ? would show them only if it listed them.
  • The name is ours, not Claude Code's.
    • The Agent call has no name field.
    • An agent started without epic agents add has no name anywhere but its description.
    • /bg stop finds the task id in the list, never in Claude Code's task list.
  • A helper can't run a plain sleep 30. A guard refuses long foreground sleeps. Only test tasks sleep, so nothing changed for it.
  • The self-restart needs the merged CLI. spell runs the MAIN checkout's CLI, so the main checkout's page server goes stale after merges until this work is in main.
  • No command removes a phase. /epic phase's test phase was taken out by hand.
