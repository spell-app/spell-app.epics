People and Orgs

owen@spell/__me.json5 is Owen: a readable JSON5 file that keeps its comments through every save, found by the same kind of address as @spell/examples/solitaire/Card.spell. Spell now names everything with one kind of address, saves things as readable JSON5 files, and keeps its first person and org on disk, in a package of their own.

Written for: a developer new to spaces, saving or addresses, about to change how projects, people or saved files are found, read or written Status: built on branch people-and-orgs, not merged into main yet; epic People and Orgs Checked on: branch people-and-orgs, 2026-10-14, against the code and the packages' own rules (their AGENTS.md files)
  • Everything Spell names has ONE kind of address: a group, a project, a file, a folder, a page of a running app, a type.
    • e.g. @spell/examples/solitaire/Card.spell, or owen@spell/errors.
    • The old forms (@system:examples:Solitaire, @examples/...) are read nowhere.
  • Every thing has a built-in id, and saves by it.
    • A thing is written inside what holds it, whole the first time and a reference after.
    • So a card in two piles saves once, and reads back as one card.
    • A kind that says so, like a person, gets a file of its own.
  • Saved files have versions, upgraded as they're read, and are checked against their class.
    • The Spell declaration is the only description anyone writes.
    • VS Code gets a JSON Schema made from it, never committed.
  • Spell has its first person and org: the people library, written in Spell, compiled to a TypeScript library the server imports.
    • A person is a readable __me.json5 file, an org an __org.json5.
    • Saving keeps every comment in the file.
    • The app's "Log In" is now "You", a small panel that edits your own file.
  • Where projects and people live is a package of its own, spaces.
    • It holds Spell's project groups, the built-in projects, the editor's server and Python's web server.
    • Owen's own projects and people are in spell-spaces, a folder outside git.
  • Spell's own files are JSON5, and the repo has a new layout:
    • tests in tests/<package>/, compiled output in build/
    • the docs tooling folded into the epics package
    • the code that makes custom elements in its own package, spell-solid
    • every component set laid out the same way, served at /components/<set>/

The numbers above, with their caveats:

  • One address scheme: about 450 old addresses were rewritten, in about 100 files of code, tests and docs.
  • Two new packages, and one gone: the docs package's tools are now the epics package's.
  • 49 files renamed: project files, declarations, test data and the core's method list. The component sets' 12 site data files are still .json (section 6).
  • Four component sets: Spell UI, Epic UI, App UI and Brand UI.
  • Spaces: a person's or org's folder of projects, with its special folders for settings, sessions, docs and data.
  • Sign-in, roles and invites, on Better Auth.
  • Sharing and live editing together, in the crdt epic.

One scheme names every group, project, file, folder, page and type, with slashes only.

Its reader is Spell's SpellLocation.

  • A SPACE is an org, @spell, or a person at an org, owen@spell.
  • A GROUP is a space and a short name, or a person's space alone.
  • A PROJECT is its group, a slash, and ONE part, its name in lower-kebab.
  • What follows the project is told apart by its last part.
names e.g. told by
a group @spell/examples, owen@spell one of spaces' project groups
a project @spell/examples/solitaire the group, then one part
a file @spell/examples/solitaire/Card.spell a dot in the last part
a folder @spell/examples/solitaire/assets/ a slash at the end
a space's own file owen@spell/__me.json5 a dot, right after the space
a page of a running app owen@spell/solitaire/rules neither a dot nor a slash at the end
a type @spell/library/people/Person looks like a page, read as a type only where one is expected
one version of a type @spell/library/people/Person__v2 __v and a number at the end
a thing in another place Person#matt@three-degrees a saved reference: type, #, id, @, place
  • Every file has a dot in its name; a group's, a project's or a page's name has none.
    • So .hidden is a file, and rules a page.
  • Where a project ends needs no lookup: its group's address, then one part. There are no nested projects.
  • An address with an empty part is refused, so solitaire//Card.spell is an error.
  • A type is read by SpellLocation.typeFor(), in a "$schema" or a reference.
    • It gives the project, the type and the version, if the address names one.
    • Without __v2, the address means the newest version.
  • A reference to another place splits at the FIRST @ after the #, since the place can hold an @ of its own.
    • So an id may never hold an @: saving one throws.

    • Each part is encoded and decoded on its own, never the whole address.

What lasts, as opposed to a page's state: things saved by id, read back as the same objects.

The code: the core's Saver and Loader, and their Python twin.

  • Every thing and list has an id, built in. No program declares it.
    • a person has an id as text is refused, saying every thing has one built in.
  • Read before it's set, it's made up, like person-k3x9q2mf.
    • From real randomness, never the seeded random, so saved ids never repeat.
  • Set it like any property: set the id of the person to "owen", or a new person with id = "owen".
  • A drawable thing's element leaves the built-in id out, so it can't clash with the element's own id.
  • Python's core has the same, with the item type of each list.

A thing is saved INSIDE what holds it, by default.

  • Written whole the first time it's reached, a reference after: { "$ref": "Card#ace" }.
  • Its id is written only when something else holds it too.
  • So a saved game is a handful of entries, never a file per card.
  • A property's plain list is its items, a JSON array: it's part of its owner.
    • A list TYPE (a club is a list of people) is a thing, inside like any other.
  • A list says what it holds before it holds anything, so saving knows a list of people holds people:
    • a person has dates as a new list of dated-events
    • or in its outline body, - its "dates" is a list of dated-events
  • An entry is written in this order:
    • "$type", then its id
    • its props, then the plain fields it was made with
    • a list's "$items"
  • Dates are written as ISO text.

  • new Saver().save(thing) gives every entry it made, by key, and the key it started from.
  • new Loader({ entryFor }).load(key) makes each entry once, however many references name it.
    • Two people who are each other's friends load as two things, each holding the other.
  • Where entries live is the caller's: a map in a test, a file each in the people store.
  • Both cores write and read the same example file, savedById.expected.json5, so they agree.
  • A reference is { "$ref": "Person#matt" }: the type, #, the id.
    • The same text names a thing anywhere: a drawable element's pile="Tableau#T1", say.
  • A reference from another entry says which entry the thing is written in: { "$ref": "Card#ace", "$in": "Game#g" }.
    • So a loader reads that entry first.
  • A thing kept in ANOTHER place is a reference with that place: Person#matt@three-degrees.
    • It gets no entry here: its own place saves it.
    • The saver's placeOf option says where each thing is kept.
    • parseRef() reads one, refText() writes one, in both cores.
  • Every key the JSON uses for itself starts with $, never a property of the thing:
    • $type: a thing's class
    • $items: a list type's items
    • $ref and $in: a reference, and the entry it's in
    • $id: a thing's number in a page's state
    • $version and $schema: a file's version and type
  • A kind that says so gets an entry of its own, and what holds it writes a reference to that.
    • a person is saved in its own file, or - it is saved in its own file in its outline body
    • compiled to Person.savedInFile = true, after the class; a plain thing says false
    • refused for a built-in type
  • a dated-event is saved inline says the default, and changes nothing.
    • A drawable thing may say it.
  • Not built: one property opting out (..., saved externally), and the comma form on a declaration (a person is a thing, saved in its own file). Nothing needs them yet.

A type has versions, so renaming a property doesn't break the files written before.

  • A version step renames or drops a property:
    • a person version 2 renames name to names, compiled to Person.v2RenamesName = "names"
    • a person version 3 drops nickname, compiled to Person.v3DropsNickname = true
  • An upgrade method does the rest: to upgrade (a person) to version 4: ..., compiled to upgradeToVersion4().
    • It runs on the thing read from an older file, after that version's renames and drops.
    • What an old file holds that the type no longer declares stays as plain fields, for it to read.
  • A type's version is the highest its steps name: 1 with none.
    • Adding a property needs no new version: only renaming, dropping or changing one does.
  • The saver writes "$version" past 1, right after "$type". A file with none is version 1.
  • The loader brings an older entry up step by step, and the next save writes the newest version.
  • A file NEWER than its type reads as it is, and its save writes the type's own version.
    • So a checkout behind a branch's Person can drop what it doesn't know: no special rule for it.
  • Python's core doesn't upgrade old files yet.

The Spell declaration is the ONLY description of a type anyone writes. Both checks are made from the compiled class, in the core's checking.ts.

checkEntry() For the app, the store and the command line: each property declared, of its kind. It returns the problems, by property. jsonSchemaFor() For VS Code only: the same, as JSON Schema. Made by a compile, never committed, never edited.
  • checkEntry(entry, { classNamed }) checks each property is one the class declares, of its kind: text, a number, yes or no, a date, a list, or a thing.
    • A thing may be a reference naming that type or a kind of it, or written whole inside, which is checked too.
    • Nothing (null) is always allowed.
    • A key starting with $ is the file's own, never a property.
    • A problem says where and what: { property: "dates[0].label", message: "label is text, not a number" }.
  • An old file is checked as its type reads it today, after its version's renames.
  • Both read a property's kind through ONE function, kindOf(), so they can't disagree.
  • No JSON Schema library: the checker reads the class's own description, what the saver reads.
  • Only the JavaScript core checks: nothing in Python reads a person's file yet.

In VS Code

  • spell compile writes a library's schemas into its build folder, in a schemas folder.
    • One file a class: Person's is Person.schema.json.
  • The repo's VS Code settings map a file's NAME to its schema: __me.json5 to Person's, __org.json5 to Org's.
    • VS Code resolves a "$schema" only as a URL or a path, so a bare address names nothing it can fetch.
    • A file the mapping doesn't name isn't checked in VS Code; the app still checks it.
    • The schemas are there once the library has been compiled in that checkout.
  • .json5 files open as "JSON with comments", the one mode VS Code checks schemas in.
    • Spell writes keys and text in double quotes, so its files read cleanly there.
    • A bare key typed by hand gets one squiggle, and the schema check still runs.

The server imports compiled Spell like any module, without running a program.

  • The model core, spell-lang/core/model: things, lists and properties, with no drawing and no Solid.
    • Imported by the package's name, @spell-app/core/model, the one export in its package file.
    • Things made outside a running program stay out of its list of things.
    • Its things are plain data, so the server and the app may each hold a copy.
    • Code it loads asks programThings() for the running program's things.
  • A library, the ts/lib target: one TypeScript file, <Project>.lib.ts, beside its source.
    • The project's classes and top-level functions: no drawing, no headings, tests or top-level steps.
    • Checked by tsc, as the Solid TypeScript target is.
    • Written as every target writes a class (P19):
      • where it's saved first, static savedInFile = true, whatever line said it
      • each property below the Spell that made it, in a comment: // - its "notes" is a list of notes
      • a decorator with arguments on the line above its accessor; one without on the same line, @derived get state()
    • Committed, and marked generated, so a merge recompiles it.
    • A test fails while it isn't what its Spell compiles to now.
    • A project asks for it in its project file: "targets": ["ts/lib"].
    • spell run refuses it: a library doesn't run.
  • Vite, tsx and the repo's type check read a .lib.ts as it is. A bare browser page, or plain node, can't without a build.
people.lib.ts · Person, as the library target writes it · 27 lines 
export class Person extends Thing {
  static savedInFile = true

  // - it has names as text
  @prop({ type: "text" })
  accessor names!: string

  // - it has a nickname as text
  @prop({ type: "text" })
  accessor nickname!: string

  // - its "emails" is a list of text
  @prop({ itemType: "text", init: () => new List<string>({ instanceType: "text" }) })
  accessor emails!: List<string>

  // - its "dates" is a list of dated-events
  @prop({ itemType: "DatedEvent", init: () => new List<DatedEvent>({ instanceType: "DatedEvent" }) })
  accessor dates!: List<DatedEvent>

  // - its "friend-lists" is a list of friend-lists
  @prop({ itemType: "FriendList", init: () => new List<FriendList>({ instanceType: "FriendList" }) })
  accessor friendLists!: List<FriendList>

  // - its "notes" is a list of notes
  @prop({ itemType: "Note", init: () => new List<Note>({ instanceType: "Note" }) })
  accessor notes!: List<Note>
}
  • A reference names one thing by its name, Tableau#T1, or its place, Tableau#1 (the first tableau made).
    • A name finds a sub-type's thing too: Pile#T1 is the tableau T1.
  • The lookups search the running program's things, or what the caller hands core.searchThings() instead.
    • So a library's code finds Person#owen under the model core, among the people store's people and orgs.
    • searchThings() returns what was searched before, for the caller to put back.
  • The code: the core's references.ts.

One person on this machine, and their orgs, in readable files. No sign-in.

Person and Org are a built-in library written in Spell, @spell/library/people.

Its source is People.spell, compiled to people.lib.ts.

  • A person, saved in their own file: names (one text), a nickname, emails, dated events, friend lists and notes.
  • A friend list holds relationships: a kind such as "brother", a person by reference, and notes.
  • An org, saved in its own file: a name, and its members.
    • Each member is a membership: a person and a role, guest, member, admin or spell-admin.
    • A value per member, like a role, is a thing of its own: Spell has no "per" syntax.
  • The app, the people store and the spell command import the compiled library.
  • Person and Org hold data and plain methods only: no events, and no rules that run when a value changes.
    • Compiled Spell runs on one shared core per process, so what fires for one person could reach another.
    • Events can come once there's a core per request.

	- it has a person as a person
	- its "role" is one of guest, member, admin, spell-admin

Spaces' files go through ONE interface, SpaceStorage, so S3 or Git can replace the disk later.

  • Five calls: read, write, list, remove, watch.
  • Paths are relative to spell-spaces: @spell/owen@/__me.json5.
  • Text in, text out: JSON5 is a layer above it.
  • The disk's is DiskStorage:
    • It writes through the page server's file operations, under the file's lock, all at once.
    • It keeps each folder's list in memory; one watcher on the root drops a folder's list when anyone changes it.
    • A path outside its root, or a dot file, is refused.
    • No index file on disk: the lists are memory only.
  • The page server's --spaces <dir> points it elsewhere, as SPELL_SPACES_DIR does.

JSON5 is read and written in ONE place, spaces' json5.ts, on the json5-writer library.

  • json5-writer writes a WHOLE value at a time, and removes any key the value leaves out.
    • So an edit reads the file, changes the object, and writes all of it back.
    • Every comment stays where it was, one at a line's end included.
  • Spell writes keys and text in double quotes, with no trailing commas.
  • The library has no types of its own: the repo's root types give them.
  • Node only: json5-writer stands on jscodeshift.
  • Behind this one file, so the library can be swapped later.

A fresh checkout or worktree needs nothing run by hand.

  • The page server, as it starts, compiles the built-in projects that are out of date, in the background: spell compile --stale --all @spell/examples @spell/library.
  • A request for a built file that isn't there compiles its project first, then serves it.
    • One compile per project at a time; a request waits at most a minute.
    • It compiles only when a built file is MISSING, never when one is merely out of date.
  • Both are spaces' ProjectBuild, running the checkout's own spell compile as a child.
  • By hand: spell compile --all <group>; --stale for only what's out of date.
    • Out of date: a built file is missing, or the project's files, its project file, an import's declarations or Spell's compiler are newer than its oldest built file.
  • A compile leaves nothing new to commit.
  • The editor's server, spaces' routes/:
    • two route tables: the app's API, /api/..., and reading a file, /spaces/...
    • a route module the page server loads by its path, from the root's package file
    • it starts the editor, vite's dev server, once the page server listens
    • the API alone, on port 3001, for the app's yarn start:server
  • Python's web server, spell_quart: a Python Spell program served as a web app on Quart.
    • Its link to py's spell_core is a path in its project file.
    • A Python web app names its program's folder inside the checkout's build/, e.g. spaces/@spell/examples/solitaire.
    • spell_quart.built_folder() finds that checkout's build folder, so the app needs no ../.

Spell's own files are JSON5, and spaces' special files and folders start with __.

  • Spell's own .json files are .json5 now, but for the few below:
    • a project's file, __project.json5 (21 committed ones)
    • every declarations file, and its test snapshot
    • the core's method list, core.declarations.json5
    • Python's words, <Project>.py.en.json5
    • the core's three expected files, and Python's not_ported_yet.json5
    • the record of moved packages, package-moves.json5
  • Spell writes the JSON-compatible part of JSON5: keys and text in double quotes.
    • So VS Code reads them as "JSON with comments", and checks them against a schema.
    • The formatter keeps a .json5 file's keys quoted.
  • A project's file keeps its comments when the editor saves it: it goes through the same JSON5 editor as a person's file.
  • Python reads them with its own json module, and has no JSON5 editor: no Python code changes a file a person edits.
