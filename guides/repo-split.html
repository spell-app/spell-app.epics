The Repos and the Kit

yarn clone spell-ui, run in the kit, clones Spell UI and nothing else: the kit is all it needs. Its button is then spell-ui/components/ui-button in every repo, its own included.

That's Spell's code since the monorepo was split: six repos in layers, one install, one name per file. Below: what each repo holds, how they fit together, how one file imports another, and how you work across them.

Epic page: epic repo-split Written for: anyone new to the layout, about to clone it, change code in one repo, or make a change across several Status: built P1-P14 merged into main in every repo, 2026-10-20 to 10-21 Checked against: the kit's and each child repo's files on main, 2026-10-22. What nobody has tried by hand yet is under Limits.
  • The kit, spell-kit, is the bottom of everything, checked out at ~/www/spell.
    • It holds the code every repo stands on: util, the toolchain, the server, the element framework, the CLI.
    • It holds the house style (WWOD) and the one install for every repo.
  • Five child repos are cloned inside it, each its own git repo: spell-lang, spell-ui, spell-brand, spell-epic, spell-app.
  • Every arrow points down: a repo uses only the kit and the repos below it.
    • A fix to Spell UI is one commit in spell-ui.
    • yarn clone spell-ui needs nothing but the kit.
  • Every repo is ONE npm package, named after the repo, with its code under one src/.
  • Every file has ONE name, the same everywhere: the package's name plus its path under src/, like spell-ui/components/ui-button.
  • Run yarn install in the kit, never in a child repo.
  • Run git in the child repo you mean: at the kit's root, git sees only the kit.

  • The kit is always there, so no repo lists it.
  • A wrong import shows up early. yarn clone <repo> clones only what that repo needs, so an import of anything else fails there.

All of it is one package, spell-kit, with one version.

folder imported as what it is
util spell-kit/util the helpers every package shares, and the reactive engine

server spell-kit/server serving pages locally, and assembling them (it took in the old assembler)
element spell-kit/element what makes a custom element on Solid 2, for every set of elements
element-tools spell-kit/element-tools/... the pack build and the elements' Vite settings, node only
test-helpers spell-kit/test-helpers/... the helpers every set's tests use
cli spell-kit/cli the spell command's base; every repo adds its own commands
  • Nothing in the kit imports a child repo.
  • Each folder has its own agents' notes beside its code.
  • The kit's AGENTS.md holds what's about the kit, and what's across repos.
repo holds needs
spell-lang the parser, markdown, core, the Python target and the language the kit
spell-ui Spell UI, with its own code and markdown elements the kit
spell-brand the brand's elements and the design system's bundle spell-ui
spell-epic the epic engine, its pages and its VS Code extension spell-ui

  • Spell UI has no Spell in it. <spell-code> and <spell-markdown> are spell-app's: subclasses of Spell UI's own code and markdown elements.
  • Docs pages get them from spell-app's page server.
  • spell-epic imports nothing of spell-app.

One name per file: the package's name, then its path under src/. It's the same in every repo, the file's own repo included, so an import can be copied anywhere.

file imported as
the kit's string helpers spell-kit/util/string
spell-lang's parser, a folder's barrel (its index.ts) spell-lang/parser
Spell UI's button spell-ui/components/ui-button
  • Never an alias or a climb up the tree:
    • no $/ alias, no # subpath
    • no ../ into a package
    • Lint fails a ../ import, and its message names the import to write.
    • Same-folder peers stay ./Peer.
  • No extension, the way a bundler resolves it.
    • The exception: plain node adds none, so there it writes .ts.
  • A repo's tests sit in its tests/ folder, at the same paths as its code.
    • The kit's router test is Router.test.ts.

Each package lists its files in one wildcard entry of its package.json, read three ways.

  • A package's own type check reads its own source.
  • Another repo's type check reads the package's built declarations, in its dist-types/.
    • spell-types builds them.
    • Each repo's yarn ts rebuilds the ones below it first, where stale.
  • Vite, Vitest, tsx, lint and node read the source, as it is.
  • esbuild used directly (the docs and design bundles) finds the names through the toolchain's sourceNames() plugin.

Clone the kit, install, clone the child repos: one install covers them all.

Setting up · 6 lines 
git clone git@github.com:spell-app/spell-kit.git ~/www/spell && cd ~/www/spell
yarn install            # the kit alone:  no child repos yet
yarn clone              # every child repo, then installs again
yarn clone spell-ui     # or one repo, and only what it needs
yarn pull               # git pull in every child repo
yarn status             # each child repo's git status
 The checks · 9 lines 
# at the kit's root:  the kit first, then each child repo, lowest first
yarn ts    yarn test    yarn lint    yarn review

# the kit's own only
yarn kit:ts    yarn kit:test    yarn kit:lint    yarn kit:review

# in a child repo:  just its own
cd spell-ui && yarn ts
yarn cli:install        # puts `spell` on your PATH
  • The spell command is the kit's base, plus each repo's own commands.
    • A repo names them in its package.json; their code is in its src/cli/.
    • spell help lists them all, grouped by repo.
    • A word two repos both want goes under each one's short name: spell lang check, spell app check.
  • A change across repos is a commit in each, merged lowest first.
    • Nothing is published or version-bumped while developing.
  • Tool versions are bumped in the kit only: one yarn release, one copy of each package, above all Solid.

An epic's worktree covers every repo at once, on one branch name.

  • /isolate <name> makes one, in ~/www/spell.worktrees/<name>/ (and so does starting an epic):
    • a worktree of the kit, on branch <name>
    • inside it, a worktree of each child repo, on the same branch
    • one install for all of them
  • Its VS Code window shows the kit's root, the worktree and the content repo.
  • Merge main in with epic worktree merge-main, never a bare git merge.
  • Leave with /isolate done: it offers to merge into main, and to open a pull request.
  • The content repo is shared, not branched: an epic page or guide changed in a worktree is the same file everywhere.

Every repo has one GitHub Actions workflow, run on a push to main, a pull request, or by hand.

  • The kit's checks the kit alone: its type check, lint and tests, with no child repo cloned.
  • A child repo's builds the layout it's worked on:
    • the kit at the root, on the branch under test if the kit has one, else main
    • the repo itself inside it, at the commit under test
    • the repos it needs, each on the branch under test if it has one, else its default branch
    • then its own checks: type check, lint and tests
  • So a change across repos is checked together when every repo's branch has the same name.
  • The repos are public, so CI needs no token.

The decisions that shaped the layout, one line each.

  • Layers, no cycles: each repo uses only the ones below it (Q1).
  • One kit at the bottom: planned as three small repos (util, server, element) under a top repo of glue only; merged into one, spell-kit, so the bottom is always there (Q15, Q31).
  • Cut the seams first: every wrong-way import was cut inside the one repo, merged, then the repos split (Q12).
  • Spell out of Spell UI: Spell's code and markdown elements subclass Spell UI's, no plugin system (Q19).
  • The parser and the language are one repo, spell-lang (Q20).
  • Setting up is yarn install, then yarn clone (Q17).
  • One npm package per repo, named after it and unscoped (Q35, Q36).
  • The spell command's base is the kit's; each repo hands it its commands (Q33, Q42).
  • The assembler joined the server (Q43).
  • One src/ per repo, one name per file, with no aliases (Q47).
  • WWOD lives in the kit; the three logs stay in the content repo (Q6, Q31).
  • npm at release: while developing, the kit's checkout is the meta repo; nothing is published (Q4).
  • The hand checks are open on the epic page: CI green in two repos, spell app serve, the page servers starting and stopping, spell on your PATH, the extension build and install, the Claude panel's session list.
  • A change across three repos is three commits, three pushes and three CI runs (C5).
  • The generic server still knows the docs content's layout and a few spell-epic names (C9).
  • spell-lang looks up once: its type check of compiled Spell reads the editor's types, and skips itself when spell-app isn't there (C12).
  • A partial clone rewrites the kit's yarn.lock (C16).
  • Nothing is on npm yet: the six names aren't reserved, and publishing the kit needs a build of its TypeScript (T13, T18).
  • Old names in old pages: content pages written before the split still name spell-util, spell-server, spell-element or @spell-app/... packages (T20).
    • The epic page's layout page is still the plan from before the cut.
  • Docs opened from disk load no bundle: their scripts are served paths, so serve them (I21).
