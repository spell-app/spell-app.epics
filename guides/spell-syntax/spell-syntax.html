Spell Syntax

Every rule of the base spell language: its class, an example, what each writer makes of it, and what it's for. Drawn from the code, so it stays current as rules are added and changed.

Written for: Owen, going through spell's syntax rule by rule, and anyone adding or changing a rule Status: built 2026-10-12 Data: spellSyntax.json, generated from the rules; drawn from the checkout serving this page Related: Choice Pages, Core Reference
  • One table per module of the base language (2. The rules, by module), one row per rule class.
    • The modules are the folders spell registers its rules from, e.g. math, lists.
    • A class registered with several syntaxes, or as several rules, is one row.
    • A purpose starting internal is a class no syntax uses directly: a base class other rules build on, or a rule spell makes while it parses. They come first in their module.
  • Each row:
    • Rule name: the class. Click it to open its source; hover it for its rule names (what syntax and error messages say).
      • Under it, each syntax it's registered with, as the code writes it.
      • Then its aliases, the other names it answers to, e.g. aka: expression.
    • Syntax: an example of each syntax, the first input its tests try, and what it compiles to with each writer: javascript, TypeScript and Python. Hover an example for the syntax it matches. Comments are left out.
    • Purpose: one sentence, from the class's docstring.
  • To suggest a change, type over a box: any writer's output, or the class's name, behind the pencil beside it.
    • A changed box turns orange; its round button puts back what the code has.
    • What you type is saved every few seconds, beside this page, never into the code.
    • Send, at the bottom, gives every changed box and your feedback to Claude.
  • The wand beside a purpose asks Claude for more details there.
    • It leaves a comment on that row, and the comment's thread shows under the purpose.
    • Claude answers on the thread; the wand stays blue until then.

Each module in the order spell registers it; within one, its internal classes by name, then its rules in the order they're registered. Expand all and Collapse all, in the toolbar at the top, open or fold every section at once.

  • The tables come from one generated file, spellSyntax.json, in the spell package.
    • It's written by yarn gen:syntax, run in packages/spell.
    • It reads the rules from the parser itself, as spell registers them, so nothing is listed by hand (spellSyntax()).
    • Each example is compiled the way the rule's own tests compile it, by all three writers. So the javascript and TypeScript are what the tests expect, once they pass.
  • A spell test fails when the file is out of date: spellSyntax.test.ts. So adding, renaming or changing a rule, its docstring or its tests means running yarn gen:syntax.
  • Merging main into a branch regenerates it (spell dev worktree merge-main).
  • Your suggestions are kept apart from it, so regenerating never loses them:
    • Each box is kept by its class and what it holds, e.g. IsGtLt.py; a second example's, AssignmentStatement.py.2.
    • They're in spell-syntax.draft.json beside this page; what Send sent, in spell-syntax.answer.json.
    • A box whose code now says what you typed is no longer a change.
    • One for a rule that's gone stays saved, counted in the toolbar.
