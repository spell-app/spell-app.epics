Claude Design builds on a design system: an artifact on claude.ai that holds a brand book, tokens, and a component library. Every design made "with" that system loads its library, so Claude draws with our real <ui-*> elements instead of inventing look-alikes.

  • What a design system holds (the claude.ai "Design System" artifact type, files under project/):
    • README.md: the brand book, which every reader starts from
    • tokens.json: colors (light and dark), type scale, spacing, radius
    • components/bundle.js: ONE classic script that assigns window.<namespace> (no import, no network)
    • components/bundle.css and components/index.d.ts (types, read as docs)
    • components/<Comp>/README.md (guidelines) and components/<Comp>/preview.html (a live card)
  • Claude Code's own /design-sync handles React libraries only. We don't need it: a design system takes any single-script bundle, and custom elements register themselves when that script runs.
  • Your old Claude Design project is already in the repo, at packages/brand/spell-design-system/. It's React mock-ups drawn from reference images ("No codebase or Figma was provided"). The new system is built from the real elements instead, and reuses that project's brand book and tokens.
  • Not yet proven: the claims above come from the artifact type's instructions, not from a working system. The first phase builds a throwaway system to test them (1.3).

Yes: we already have every element's shape written down, so nothing has to be guessed. Each tag has a <tag>.vocabulary.en.ts, and yarn site:data already gathers all of them into one file, packages/ui/site/_data/components.json (760 KB, 97 tags in 58 families, plus 391 foundation tokens and 27 themes).

1.3 One bundle, <ui-root>, and where scripts load from

The bundle is uploaded INTO the design system as a file, so nothing has to be public, and nothing goes to npm. Claude Design can't reach your laptop (localhost is blocked; only a few CDNs and the system's own files load), so an update is one sync command, not zero steps.

  • <ui-root> is fine. It loads each family with import(), and the one-file build already turns those into inline code: packages/docs/tools/_assets/spell-ui.js is a classic script (var SpellUI = (() => {...})(), 2.7 MB, about 800 KB zipped), and its build fails if any import() survives.
  • The design bundle is that build minus the docs-only parts (the docs page runtime, the site header). Things to settle in the spike phase:
    • icons: the one-file build inlines only about 90 icons; the rest draw nothing unless the icon packs go in as files
    • the lazy engines (code highlighting, markdown, emoji): inline them, or upload them as files
    • fonts: the spell theme uses local Palatino only, so a design shows a fallback serif unless we ship a font file
  • The update loop, as planned:
    1. change a component
    2. in Claude Code: /design push (rebuilds, then sends only the changed files, about a minute)
    3. reload the design in Claude Design
  • Alternatives we're not taking: publish @spell-app/ui to npm and load it from jsDelivr (a real publish, and @spell-app/solid-element is private); host it on GitHub (jsDelivr's npm path is the allowed one, and its cache lags).

The research behind it, from before the answer:

  • Why it reloads today (spell-doc-runtime.js, canPatch / patchPage):
    • any inline script on the page, even <script type="text/plain">: the "Plan hung?" notice has one, so every edit to a doc still being planned reloads it (this doc, right now)
    • anything outside main changed: every edit rewrites <body data-recent-since>, which differs per checkout and moves with each commit (PAPERCUTS, 2026-10-04)
    • more than half of main changed
  • Each edit writes the file 3 times over about 1 second (the edit, link rewriting, then formatting), against a 250 ms watch debounce, so one edit can patch the page twice.
  • What fragments with <ui-include> would cost:
    • <ui-include> refuses file://, so plan docs would stop opening from disk, and the browser check loads them from disk
    • find-in-page and #q12 links can't reach content that hasn't loaded
    • about 15 readers parse plan-doc HTML today (the plan-doc commands, the docs index, the main server's epic cards, the review inbox, the browser checks), and every one would need to follow includes
    • live updates ignore any changed file except the page itself
  • What fragments would gain: less parsing and element set-up on load (a folded section's content is still built, only not drawn). The biggest doc, spell-ui-pages, is 522 KB with 6,666 elements; most of that is item details.
  • Script speed: most of a plan-doc command's time is process start-up and formatting, not file size (parsing the biggest doc takes 19 ms), so smaller files wouldn't make scripts much faster.

  • the bundle goes into the system as a file; a Design copies it in
Q11 P2: source lives in the UISection CLASS and its vocabulary (UIT.SOURCE_BODY_*), so <ui-panel> (a UISection subclass) gets it for free J1 P2: source bodies share one core helper, SourceBody, not a hidden <ui-include> inside each section

Chose a small helper in the element core over two alternatives: making the section a SourceElement (that base is for elements that SHOW a text file: inline text, edits, save(), its own render), or having the section put a <ui-include page-styles> inside itself (an extra element between the section and its content, which breaks ui-section > p-style selectors and every reader that walks a section's children).

Net effect:

  • one fetch path: UI.sources.load(), the cache <ui-include> uses
  • the include's markup handling moved out of UIInclude.tsx into packages/ui/src/elements/SourceMarkup.ts (parse the <body> or the select match, rewrite relative URLs, the cycle / depth guard), now used by both
  • packages/ui/src/elements/SourceBody.ts: load once, insert, ui-load / ui-error, reload(); SourceBodyHost.ts: el.load() / el.reload()
  • the body sits DIRECTLY in the section: <ui-section source="parts/p3.html"><p>...</p></ui-section> once loaded
  • URL_ATTRIBUTES / ORIGINAL_PREFIX / MAX_DEPTH moved from ui-include.types.ts to the core (elements.types.ts); SiteShell.ts and ExampleSource.ts import them from $/ui/core now
J2 P2: an opening section or panel waits up to 300 ms for its body, then opens on the placeholder

Owen's brief said fetch, insert, THEN unfold. Chose to hold only the content box, not the state: collapsed, aria-expanded and ui-open change at once as before, but the content stays hidden while the body is on its way (SourceBody.veiled()), for at most SOURCE_BODY_HOLD_MS = 300. Over that, the placeholder shows under the section's existing loading look (dimmer + spinner, aria-busy) until the body arrives.

Why not wait for the fetch inside toggle(): the page runtime unfolds by removing collapsed (a #id link), with no toggle at all; holding the box works the same for every route, and the fold animates once, to the real height.

Net effect:

  • a same-origin body (a few ms) appears with the unfold, no flash of the placeholder
  • a slow or failing server never leaves a click looking dead for more than 300 ms
  • an accordion holds its first <details> closed the same way
J3 P2: the file's body REPLACES the placeholder; slotted title pieces stay; reload() replaces the body it put there

Chose: every light child WITHOUT a slot attribute is the placeholder (text, a <p>Loading…</p>), removed when the body goes in; slot="header" / icon / badge / actions children stay. reload() removes exactly the nodes the last load inserted, so a body with a top-level slot child never doubles.

Net effect:

  • a skeleton can carry a rich title: <ui-section source="parts/p3.html"><ui-icon slot="icon" name="circle half stroke"></ui-icon></ui-section>
  • anything else written inside a source section is thrown away on first unfold
J4 P2: <ui-accordion source> fills its FIRST panel, making a <ui-content> after the title when there's none

Chose: source on an accordion is for ONE title (a plan item line); the body goes into the first title's content child. When the title has no content after it, the accordion adds an empty <ui-content> right after it, at load time (not on connect: the parser may not have added the children yet). A <ui-content> already there is kept (its class and attributes too) and its children are the placeholder.

Net effect:

  • Owen's skeleton line works as written: <ui-accordion class="plan-item" source="parts/q2.html"><ui-title>...</ui-title></ui-accordion>
  • an accordion with several panels and a source loads only the first panel's content
  • states :state(loading) / loaded / error on the accordion
J5 P2: a failed body shows a plain error line and tries again on the next open; no family loading, no ui-insert
  • Failure: the cancelable ui-error ({ kind, source, error }), :state(error), and unless cancelled one line <p class="source error" part="error" role="alert">Couldn't load parts/p3.html.</p> above the placeholder (in the shadow content box, not a <ui-message>, which would pull in another family). el.load() rejects. A failure isn't remembered: fold and unfold again and it fetches again.
  • The ui-* families a body uses are NOT loaded by the section (the include does, through RootLoader): the body is light DOM, the page's own, so a <ui-root> (it watches its subtree) or the page's bundle defines its tags, as for any markup in the page.   • No ui-insert (edit the fragment before it goes in) and no load="visible|idle" modes: P3 doesn't need them; listen for ui-load to touch the body after.

I1 The bundle threw while loading when inlined: Invalid base URL
